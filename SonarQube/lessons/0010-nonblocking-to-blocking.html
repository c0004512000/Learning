SonarQube / Phase 05 / Lesson 10

L10 / QUALITY GATE → CI POLICY → DEPLOYMENT

Gate FAIL 了，
部署要怎麼真的被擋下？

SonarQube 的 Quality Gate 只負責產生品質判定；是否阻止部署，是 GitHub Actions 的 Job Dependency 與組織治理政策。從 Non-blocking 升級成 Blocking，必須同時設計成功路徑與失敗路徑。

Phase 05 · Lesson 10約 20 分鐘治理／回退演練

學習目標

設計一條可逐步啟用的 CI Quality Gate：區分 Quality Gate FAIL、Scanner Fail、CE Fail、Timeout／平台不可用，能解釋 sonar.qualitygate.wait、needs、continue-on-error、例外、回退及部署授權。

01 / 五個看似一樣的「紅燈」其實不同

狀態發生在哪個階段？政策該回答
Code Issue 引起 Gate FAILCE 完成、Quality Gate 判定品質不達標，要禁止發布嗎？
Scanner FailRunner、Token、TLS、設定沒有可信分析，能否繼續？
CE Task FAILEDServer 背景處理Report 上傳了但結果無效，是否中止？
等待逾時／Server 不可用CI 等待／連線階段重試、人工核准或 Fail Closed？
資料錯位／不是該 ReleaseTrigger、Checkout、Project / Version綠燈能代表這個 Tag 和 SHA 嗎？

前四種分別是品質決策與品質服務無法提供可信決策；第五種甚至可能讓你錯把「別的版本的 PASS」當成這個 Release 的證據。正式 Gate 不能只問綠或紅，要先問它是不是這次部署所對應的分析。

02 / Rule、Gate、CI 三個責任分層

03 / 如何由觀測轉成阻擋？

階段Quality Gate 實際狀態GitHub Actions 如何處置？
A / Observe正常計算 PASS／FAIL分析作為獨立觀測 Job；部署不依賴 Gate Check，絕不為了不擋部署而強迫 Gate PASS
B / WarnFAIL 仍可辨識將不合格關聯到 Commit、Owner、Issue／報告；通知及追蹤趨勢，確認噪音／誤報與 Server 可用性
C / EnforceFAIL 是阻擋訊號Gate Check 成功才放行 Release Job；逾時或不可用時依事先核准的 Fail Policy 處理
切換到 Blocking 前應完成的條件

已能穩定重現成功掃描／CE 完成／紅色 Gate、建立每次 Tag → SHA → Gate 的關聯、確認 Rules 與 New Code Definition 符合治理政策、分析誤報與 Timeout 行為、定義誰能核准例外及何時回退。這些是驗收準則，不是已在真實環境通過的證據。

04 / 讓 Gate FAIL 確實阻擋一個示範部署 Job

以下是隔離環境的教學工作流程。假設 Runner 已安裝相容 SonarScanner CLI，且測試 Project Key 已存在。deploy-demo 只列印字串，不進行真實部署。

name: Sonar Quality Gate Lab
on:
  workflow_dispatch:

jobs:
  quality-check:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Scan and wait
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
        run: |
          sonar-scanner \
            -Dsonar.projectKey=demo-api \
            -Dsonar.qualitygate.wait=true \
            -Dsonar.qualitygate.timeout=300

  deploy-demo:
    needs: quality-check
    runs-on: ubuntu-latest
    steps:
      - run: echo "Simulation only — no deployment"

這個範例中，當 CE 算出 Gate FAIL、Scanner 正常等待並取得結果時，quality-check Job 會失敗；因為 deploy-demo 有 needs: quality-check，後者預設會被略過。這不是 SonarQube 直接終止部署，而是 GitHub Actions 根據依賴關係停止後續 Job。GitHub needs 官方說明。

最常見的兩種誤設

第一，只有 sonar.qualitygate.wait=false：Scanner 上傳成功就可結束，Gate FAIL 不會讓該 Step 失敗。第二，只設 wait=true 卻讓 Deploy Job 完全不依賴 Quality-check，部署仍可繼續。還要檢查 if: always() 或 continue-on-error 是否意外繞過政策。

05 / Non-blocking 不是把所有錯誤都吞掉

在 Observe 階段，你可以保留獨立的分析 Job（若掃描失敗，它自己仍標紅），讓原有 Deployment 只依賴原本已建立的 Build／Test／Security Gate。這樣部署可以不受 SonarQube 影響，但你仍看得到 Scanner 失敗與 Gate FAIL。若把整個分析流程無條件 continue-on-error: true，可能同時掩蓋 Token、網路與真正的品質問題，不利於判斷何時可升級為 Blocking。

Fail-closed vs. Fail-open：Fail-closed 是無法取得可信品質判定就暫停部署；Fail-open 是平台故障時，依事先核准的例外程序放行。沒有一個選項適用所有服務；正式策略必須定義環境範圍、風險、時效、Owner、紀錄及復原後的補驗。不能把 SonarQube Server Outage 誤記成「程式碼品質 PASS」。

06 / 例外與回退要怎麼設計？

  1. 先界定：是新碼 Gate FAIL、Scanner 故障、CE FAILED，還是等待 Timeout？依失敗來源選路徑，不能直接所有狀態放行。
  2. 若需例外：記錄 Release Tag／SHA、Gate 指標、風險說明、核准人、截止時間與補驗動作；保留可追溯的 CI 執行結果。
  3. 受控回退：先停止這個 Sonar Quality Enforcement 的部署依賴、恢復原觀測模式；不要為了綠燈全面停用 Rules 或把 Gate 改成永遠 PASS。
  4. 復原驗證：在隔離環境重跑 PASS、FAIL、Timeout、Server 不可用四類情境，再決定是否重新開啟阻擋。

兩個不同的回退必須分清：Release 回退是把服務部署退回舊版；Quality Gate Enforcement 回退是暫時調整 CI 阻擋政策。兩者不互相替代。

07 / 請用失效注入證明你真的理解

在隔離環境製造應記錄的可觀察證據
受控 New Code Issue 導致 Gate FAILCE SUCCESS、Gate FAIL、Scanner Exit Code、Deploy Job skip
Token 或 TLS 失效Scanner Fail、無有效 Gate 判定、部署處置
Server CE 逾時或不可用Timeout 與 Retry／例外／阻擋結果
重跑較舊 Release TagTag、SHA、CE Task、Gate 結果能否仍精確對應

驗收要證明同一個 Release／Commit 在 PASS、FAIL 和 Unknown 三個狀態下的部署決策；不能只截一張「Dashboard 綠燈」當成治理完成。更完整的政策矩陣見 Reference 07。

RETRIEVAL / 決策責任

Dashboard 已顯示這次分析 Gate FAIL，Deployment Job 卻仍執行。最先檢查哪一層？

08 / 一分鐘回顧

  • Gate FAIL 是品質結果，不等於 Scanner／CE 執行失敗。
  • wait=true（或獨立 Gate Check）把結果送入 CI；needs 控制後續部署。
  • Non-blocking 仍應保留可觀測的紅燈；不應停用 Rules 或將 Gate 假設為 PASS。
  • Enforcement 需要例外、Timeout、Outage、回退、Owner 及正確 Release SHA 身分。
優先閱讀：SonarSource：Quality Gate Check／wait · GitHub：needs、if、continue-on-error · 治理矩陣速查。若失效注入的觀察與推導不同，請帶著 CE Task ID、Exit Code、Release SHA 返回對話定位。
