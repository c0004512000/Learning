你已經知道 Runner 能執行 Scanner。現在真正需要決定的是：哪個事件值得掃？這次 Scanner 真正 Checkout 哪個 Git Commit？分析又被存入哪個 SonarQube Project？

Phase 05 · Lesson 09約 18 分鐘CI/CD 決策情境

學習目標

針對 Community Build 的 PR 開啟／PR 合併／main Push／Release Tag 事件，能選擇掃描時點，對照事件 SHA、Project Key、sonar.projectVersion，並辨識重複分析、歷史覆寫及不受支援的原生 PR 分析。

01 / 先把四個問題拆開

Figure / 四個不互相替代的決定

GitHub Event何時啟動工作流程？例如 push、pull_request、Tag
↓ Event payload 和 actions/checkout 選定
Checkout Commit SHARunner 眼前究竟是哪份完整的原始碼？
↓ Scanner 以 Project Key 提交
SonarQube Project / Main Branch這次分析被保存到哪一個品質歷史？
↓ 可同時附上 Release Version 標記

箭頭是流程中的決策／傳送，不代表 Event、SHA、Project Version 自動等價。Scanner 分析 Checkout 的完整原始碼；New Code 是在這個分析中界定的範圍。

02 / 四個常見事件的能力矩陣

事件實際分析內容Community Build 的定位
PR opened / synchronize通常是 PR 的模擬合併 Checkout；可顯式改為 head SHA可以執行一般 CI，但沒有原生 PR Analysis / Decoration；不應直接共用 main Project Key 覆寫主分支歷史
PR closed 且 merged明確 Checkout 合併結果 SHA，避免抓到已繼續前進的 main HEAD可對已合併程式碼做主分支持續分析；不等於合併前的 PR Gate
push main觸發這次 Push 的 main SHA官方建議的免費版主分支分析模式；對所有 main 變更較單純
push Release Tag該 Tag 指向的 Commit（確認 Checkout）適合發布版本追蹤；Tag 名稱可給 sonar.projectVersion，但不保證精確比較上一個 Release Tag 的 Git Diff

官方 Community Build 文件建議只分析你的主分支，且不要在免費版的同一 Project 以 on.pull_request 當原生 PR 分析使用。GitHub 的 PR 事件仍可以進行 Build、Test、Lint，只是這些並非 SonarQube 的獨立 PR 結果。官方 Community CI 建議 · 原生 PR 版別差異。

03 / 選擇一個權威的掃描事件

一個 Repo 的 main 可能先在 10:00 合併 PR，10:01 觸發 push main，隔天再在同一個 Commit 打 Release Tag。若三個事件都掃描同一個 sonar.projectKey，便可能發生重複分析、相同 SHA 不同版本標記、相互覆寫最新品質狀態。

初始治理建議：把 main push 當成主要、連續的品質分析路徑。

它能包含直接 Push、合併 PR 等 main 更新，不必對每個 PR merge 再掃一次同一個 Project。若業務要求僅在 Release Tag 掃描，就改成 Tag 為唯一權威路徑，但那是Release 品質觀測，不是「合併前 PR 阻擋」。

如果必須在 pull_request: closed 時執行，例如要接既有的 Post-Merge E2E，應加上 merged == true、base.ref == main，並明確判定使用的 Merge Commit；不要只用 main 字串 Checkout，因為 main 可能已在事件後前進。詳見 Reference：事件選擇與重複掃描。

04 / 兩種最小 GitHub Actions 觸發方式

A：main push 持續掃描（Community Build 較單純的基線）。

on:
  push:
    branches: [main]

jobs:
  sonar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - run: |
          git rev-parse HEAD
          # 其後使用已核准的 Scanner / Token 執行分析

B：只在 Release Tag 掃描並記錄版本（擇一政策，不是與 A 無條件疊加）。

on:
  push:
    tags: ['release/**']

jobs:
  sonar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Analyze the tagged revision
        env:
          RELEASE_VERSION: ${{ github.ref_name }}
        run: |
          git rev-parse HEAD
          sonar-scanner \
            -Dsonar.projectKey=demo-api \
            -Dsonar.projectVersion="$RELEASE_VERSION"

教學片段：B 假設 Scanner CLI 已安裝、連線資訊與 Token 已用安全方式提供。完整 Runner 前提看 Lesson 07。請在部署前使用授權 Runner、固定 Action 版本、核對 Event 類型及 GITHUB_SHA；Tag Workflow 並不保證該 Tag 必在 main 或指向最新版本。

05 / Edge Case：舊 Tag 在新版本之後被重掃

Figure / Latest Project Analysis 不是最新 Release 保證

11/01：Tag v1.2 → Commit CProject demo-api 看到 v1.2 的分析結果
↓ 新 Release 發布
11/08：Tag v1.3 → Commit D最新分析變成 v1.3
↓ 有人重新跑 v1.2 的 Workflow
11/09：舊 Commit C 重新分析同 Project Key 的最新 Dashboard 可能改顯舊版本的分析；不是自動建立 Tag 分支

因此，Release 必須建立一筆可稽核的Tag → SHA → Project Key → Project Version → CE Task → Gate 結果關聯。只看「目前 Dashboard 是綠燈」不能推出「待部署的 Tag 已經通過」。若並行分析同一個 Project，還要設計序列化、完成時序與結果歸屬；不要依賴沒有綁定分析 ID 的「最新 Project 狀態」。

另外，Release Tag 改變 sonar.projectVersion 只是記錄版本，不會自動產生原生 Tag 分支，也不等於 Git diff。回顧 Previous Version 的首次分析起點陷阱。

RETRIEVAL / 事件與產品能力

團隊希望在 PR 尚未合併前，於 Community Project 取得原生 PR 專屬 Gate。哪一個判斷正確？

06 / 一分鐘回顧

  • Event 決定時機；Checkout SHA 決定掃哪份完整原始碼。
  • Community Build 的單一 Project 沒有原生 PR 或 Tag 分支。
  • 主分支持續掃描與每次 Release Tag 掃描各有用途；不要無設計地疊加。
  • Project Version 可記錄 Tag，並不保證上一個 Release 的 Git Diff。
  • Gate 放行的對象必須是正確的 Commit／分析結果，不只是 Project 最新狀態。
優先閱讀：SonarSource：Community Actions 分支建議 · GitHub：事件與 SHA · Reference：事件／Gate 決策矩陣。若某個 Commit 歸屬不直覺，請將事件與 Checkout SHA 帶回 ChatGPT 一起推導。
