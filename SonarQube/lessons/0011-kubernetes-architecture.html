Phase 06 · Lesson 11約 20 分鐘Architecture Decision

本堂學習目標

能從 Server／Database／Elasticsearch／Runner 的資料流推導 Kubernetes 架構，說明 H2、PostgreSQL、PVC 的不同責任，並提出 Helm、Pod Security、Probe、TLS 與故障驗收的設計。

01 / 先建立四個元件的資料責任

Figure / 資料從哪裡進來，又在哪裡持久保存？

Scanner / GitHub Actions Runner讀取 Checkout 程式碼 → HTTPS 上傳報告；它不是 SonarQube 的 Server Pod
↓ 通過 DNS／TLS／反向代理，送往 Web API
SonarQube Server Pod包含 Web、Compute Engine（CE）、Elasticsearch（ES）等程序
↓ Web／CE 儲存分析結果、Issues、設定與背景任務
PostgreSQL（外部資料庫）可恢復的權威資料；與 Server Pod 的生命週期分離

Elasticsearch 索引用於加速查詢，是資料庫的索引副本，可由 SonarQube 重建；圖中將它畫在 Server Pod 內，不代表所有 ES 實作都與 PostgreSQL 同樣需要獨立備份。

關鍵區別：Database ≠ ES Index ≠ PVC。

PostgreSQL 存在資料；ES 是可重建的搜尋索引；PVC 是 Kubernetes 提供的持久儲存介面。對 ES 設 PVC 不會自動保護 PostgreSQL；把資料放在 PostgreSQL 也不代表已經做好備份。官方 Server Components

02 / POC 能跑，與正式可維運差在哪？

面向一次性 POC長期／正式使用
分析歷史可接受重建與遺失需保存 Issues、History、Profiles、Gate 與設定
DatabaseH2 只適合試驗以受支援的獨立 PostgreSQL 等資料庫為主
Elasticsearch隨 Pod 重建索引可依重建時間選擇是否持久化；索引不是備份
存取臨時連線即可HTTPS、身分驗證、Secrets、網路邊界與權限
運作看 UI 能開監控、容量、備份還原、升級演練與 Runbook

Community Build 26.2 的官方部署文件特別提到 Helm Chart 移除隨附 PostgreSQL Dependency；實際 Chart／Server 版本不同，H2 預設與資料庫設定也可能不同。**不要因舊版教學的 PostgreSQL Subchart 或新版預設 H2，就推論正式環境不需要外部資料庫。** 官方部署先決條件 · 資料庫要求。

03 / PVC 要不要開？先問資料能不能重建

Figure / 分清恢復的是什麼

Pod 被重排，ES Index 消失如果 PostgreSQL 完整，SonarQube 可以重新建立索引
↓ 重新建立 Index 需要時間、CPU、I/O
啟用 ES Persistence可能縮短啟動時間，但官方警告 Pod 中斷可能導致 Index 毀損
↓ 兩條路都不能取代 DB Backup
外部 PostgreSQL + 備份復原決定是否能保住歷史與設定

官方 Helm Chart 的 persistence.enabled 主要涉及 ES 資料索引的儲存；預設關閉，Pod 重啟需要重建，可能使 Readiness 變慢。若開啟，須先了解 Index 損毀與 PVC／StorageClass 的風險。**不能把「啟用 ES PVC」與「讓 H2 或 PostgreSQL 變可靠」畫等號。** 官方 Chart Persistence。

04 / Helm Values 設定：哪個欄位代表什麼？

以下是示意片段，不是可直接部署的完整 Values；以對應 Helm Chart 版本的 helm show values 與 Artifact Hub README 核對所有參數。不要把密碼直接寫入 Git 或 --set 的 Shell History。

# values-example.yaml（概念示意，需依 Chart 版本校驗）
community:
  enabled: true

jdbcOverwrite:
  enabled: true
  jdbcUrl: jdbc:postgresql://postgres.example.internal:5432/sonarqube
  jdbcUsername: sonar_user
  jdbcSecretName: sonar-db-credentials
  jdbcSecretPasswordKey: password

persistence:
  enabled: false  # ES 索引重建策略；不是 PostgreSQL 備份設定

initSysctl:
  enabled: false
initFs:
  enabled: false

jdbcOverwrite 決定 Server 連哪個資料庫；密碼透過 Kubernetes Secret Reference 注入；initSysctl 和 initFs 關係到 Pod Security。關閉需要高權限的 Init Containers 後，Cluster Node 仍必須符合 Elasticsearch 的 OS 前置要求，否則 Pod 可能 CrashLoop／啟動失敗，不能只為了符合 Restricted 就把必要 Host 設定忽略。官方 Helm Customization。

# 僅為檢視與渲染：不修改叢集
helm show values sonarqube/sonarqube --version CHART_VERSION
helm template sonar sonarqube/sonarqube \
  --version CHART_VERSION \
  -n sq-learning \
  -f values-example.yaml

部署前還需固定 Chart 版本與 SonarQube Image／Build Version，檢查 requests／limits、Secret／Monitoring Passcode、Probe、StorageClass、Ingress、Pod Security Admission 與 NetworkPolicy。上面的 Hostname 和使用者名稱都是合成示例。

05 / GitOps 需要另外驗證，不能直接當成官方保證

Community Build Kubernetes 文件指出，以 Argo CD 部署 SonarQube Helm Chart 尚未獲得完整支援或驗證。這不代表 Argo CD 一定不能部署，而是不能把 GitOps Sync Success 直接當成官方相容性認證。正式採用前應在隔離環境檢查 Helm Hooks、Init Containers、Reconciliation、Upgrade／Rollback 與 Secret 更新行為。官方聲明

06 / 連線方向、TLS 與 Probe 要分別驗證

路徑誰連誰？該驗證什麼？
Scanner → SonarQubeRunner 經 HTTPS／Proxy → Web APIDNS、Ingress、TLS CA、Token、Request Size 與 Firewall
SonarQube → PostgreSQLServer Pod → DB JDBCSecret、DB DNS／Port、TLS、Connection Limit、Latency
Browser → Dashboard使用者 → HTTPS Reverse ProxyBase URL、路由、HTTP Header、驗證與授權
Server 啟動 → ReadinessKubernetes Probe → PodDB 可用性、ES Reindex 延遲、CPU／Memory

SonarQube Web 的入站原生通訊由 HTTP 處理，正式 HTTPS 通常由 Reverse Proxy／Gateway 終止 TLS。若 ES 索引重建需要幾分鐘，過於積極的 Liveness Probe 可能反覆重啟 Pod，反而無法就緒；要用實測啟動時間調整 Startup／Readiness／Liveness，而不是憑空指定秒數。官方 Networking · 官方 Readiness 注意事項。

07 / 不要只看 Pod Running：設計驗收證據

  1. 記錄 helm version、Chart Version、Image Tag、Kubernetes Version、資源設定和 Runtime Node 的前置條件；在授權測試環境先執行 helm template。
  2. 確認 Server 能連 DB，並在隔離 Project 分析一份合成 Repo；記錄 Project Key、CE Task、Quality Gate 與分析時間。
  3. 以受控方式重啟測試 Server Pod，驗證分析歷史仍在、ES 可能重建、Readiness 與 CE 處理恢復；不更動正式環境。
  4. 逐條驗證 Runner → Web API、Server → DB、Browser → Gateway 的 TLS／DNS／NetworkPolicy；記錄到 Phase 06 維運清單。

RETRIEVAL / 資料所有權

Pod 重啟後 ES Index 消失，但外部 PostgreSQL 完整。哪個敘述最合理？

08 / 一分鐘回顧

  • Server Pod 是運算與索引服務；外部 DB 保存權威品質資料。
  • ES PVC 是啟動與索引策略，不等於資料庫備份。
  • 正式導入還要處理資源、限制、Secrets、Network、TLS、Probe 與 GitOps 相容性。
  • POC 成功與可維運是不同證據門檻；下一堂驗證故障後是否能真正復原。
官方優先來源：Server Components · Kubernetes Preconditions · Chart Customization。如果實驗有異常，請帶上 Pod Events、CE/ES Logs 與 DB 連線狀態討論；不要公開 Credentials。
