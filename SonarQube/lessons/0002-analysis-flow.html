L02 / DATA FLOW

Scanner 上傳了什麼？
Dashboard 從哪裡來？

將 SonarQube 拆成「短暫執行的分析工具」與「長期保存並提供查詢的服務」，你就能理解為什麼 CI 只跑一個 Action 還不夠。

約 10–15 分鐘承接 Lesson 01一張資料流圖

01 / 第一個必要條件：分析需要原始碼

程式碼在 GitHub；GitHub Actions 在 Runner 上 Checkout 該版本，取得原始碼與 Git metadata。Runner 內的 SonarScanner 讀取這些資料，根據適用的分析規則產生結果。它不是 Dashboard，也不是資料庫。

Scanner 是「執行分析的一次性工作」；SonarQube Server 是「接收、處理、保存並提供查看的長期服務」。

02 / 把每個箭頭都說清楚

  1. Checkout / 準備：Runner 取得 repository 檔案。部分語言需要先編譯、執行測試或產生額外報告。
  2. Scan / 上傳：SonarScanner 分析原始碼，將分析報告提交給 SonarQube Server。
  3. Process / 計算：Compute Engine 非同步處理分析任務、計算品質指標與 Quality Gate 狀態。
  4. Store / 保存：Server 將需要長期保存的結果寫入支援的資料庫；正式化可採 PostgreSQL。
  5. View / 查詢：內建 Web UI（Dashboard）與 API 提供 Issue、指標與 Gate 結果。
  6. Enforce / 門禁：CI 如有需要，可等待服務端計算完成，依 Gate 狀態讓 job 成功或失敗。

03 / 為什麼不是 Scanner 上傳就完成了？

因為「報告上傳成功」和「Server 已處理完成」是不同事件。Server 的 Compute Engine 以背景任務處理報告，所以 CI 若想可靠地依品質標準阻擋，必須等待結果或透過後續步驟確認。

sonar.qualitygate.wait=true

這個參數會讓掃描步驟等待 Quality Gate 結果；若 Gate 失敗，該步驟可以失敗。它不是免費版自動替你決定「Production 必須阻擋」：阻擋範圍仍由 workflow 的依賴與分支保護決定。

04 / Dashboard 跟 Coverage 的常見誤會

觀念精確模型
Dashboard 要另外部署？不需要；它由 SonarQube Server 提供。
Dashboard 會自己讀 GitHub？典型 CI 分析是 Runner 執行 Scanner，再上傳到 Server；不是 Dashboard 主動掃描。
Coverage 會自己出現？不會；要先由 Jest/Vitest、JaCoCo、Coverlet 等工具產出報告，Scanner 再匯入。
Scanner 與 Server 可不可以同機？POC 可以；公司 CI 中則常由 Runner 連線到集中管理的 Server。

SCENARIO / 故障定位

Scanner 顯示報告上傳成功，但 Dashboard 還沒有最新指標。先檢查哪個假設？

05 / POC 的第一個觀察目標

你要在後續實驗中親自確認三件事：Scanner log 顯示提交成功；Server 端 Background Tasks 顯示分析完成；Dashboard 顯示對應 Project 與 Quality Gate。三者才構成一條可追蹤的完整證據鏈。
