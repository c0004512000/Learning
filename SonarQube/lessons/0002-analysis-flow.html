L02 / DATA FLOW

Scanner 上傳了什麼？
Dashboard 從哪裡來？

將 SonarQube 拆成「短暫執行的分析工具」與「長期保存並提供查詢的服務」，你就能理解為什麼 CI 只跑一個 Action 還不夠。

約 10–15 分鐘承接 Lesson 01一張資料流圖

01 / 第一個必要條件：分析需要原始碼

一份 GitHub Repository 是原始碼所在的位置；SonarQube Project 是 Server 為這份程式碼建立的品質資料歸屬，Project Key 是辨識它的唯一鍵。現在先把 Project 想成「放分析結果的資料夾」，詳細設定留在 Phase 03。

程式碼在 GitHub；GitHub Actions 在 Runner 上 Checkout 該版本，取得原始碼與 Git metadata。Runner 內的 SonarScanner 讀取這些資料，根據適用的分析規則產生結果。它不是 Dashboard，也不是資料庫。

Scanner 是「執行分析的一次性工作」；SonarQube Server 是「接收、處理、保存並提供查看的長期服務」。

02 / Analysis Report 不是 Dashboard 報表

先想像一個只包含三個原始碼檔案的專案。Runner 上的 Scanner 讀取原始碼、執行語言規則，並收集每個檔案的分析資訊：

檔案Scanner 取得的資料（簡化示例）
UserService.java200 行、2 個 Issues
OrderService.java300 行、3 個 Issues
PaymentService.java100 行、0 個 Issues

Scanner 把這些原始碼分析輸出，以及來源資訊和其他 Metrics，封裝成供 Server 消費的 Analysis Report。它是機器處理的資料包，不是已經整理好的 PDF、HTML 或 Dashboard 報表；上表只是概念示例，並非實際封包格式。

Scanner 已經完成程式碼規則檢查；Compute Engine 並不是再對原始碼跑一次相同的掃描。

Compute Engine 要做的是整合、彙總、計算衍生指標、關聯 Issues、保存結果。例如可以彙總各檔案行數、計算品質評級與 Quality Gate，然後把結果寫入資料庫供 Dashboard 查詢。這是第二個處理階段，不是同一件工作重做兩遍。

03 / 把每個箭頭都說清楚

  1. Checkout / 準備：Runner 取得 repository 檔案。部分語言需要先編譯、執行測試或產生額外報告。
  2. Scan / 上傳：SonarScanner 在 Runner 執行程式碼規則檢查，產生結構化 Analysis Report 並提交給 Server。
  3. Process / 整合：Compute Engine 非同步整合 Scanner 輸出、彙總 Metrics、計算衍生指標／評級與 Quality Gate、處理 Issue 關聯；不重跑一次相同的原始碼規則掃描。
  4. Store / 保存：Server 將需要長期保存的結果寫入支援的資料庫；正式化可採 PostgreSQL。
  5. View / 查詢：內建 Web UI（Dashboard）與 API 提供 Issue、指標與 Gate 結果。
  6. Enforce / 門禁：CI 如有需要，可等待服務端計算完成，依 Gate 狀態讓 job 成功或失敗。

04 / 為什麼不是 Scanner 上傳就完成了？

因為「Scanner 已產生分析資料」與「Server 已將資料整合成 Project 的正式品質狀態」是兩個不同事件。這個背景處理必須完成，新的 Issues、指標及 Gate 狀態才會供 Web UI 查詢。所以 CI 若要根據 Quality Gate 決定成功或失敗，就必須等待處理完成，而不只看 Scanner 是否成功上傳。

sonar.qualitygate.wait=true

這個參數會讓掃描步驟等待 Quality Gate 結果；若 Gate 失敗，該步驟可以失敗。它不是免費版自動替你決定「Production 必須阻擋」：阻擋範圍仍由 workflow 的依賴與分支保護決定。

05 / Dashboard 跟 Coverage 的常見誤會

觀念精確模型
Dashboard 要另外部署？不需要；它由 SonarQube Server 提供。
Dashboard 會自己讀 GitHub？典型 CI 分析是 Runner 執行 Scanner，再上傳到 Server；不是 Dashboard 主動掃描。
Coverage 會自己出現？不會；要先由 Jest/Vitest、JaCoCo、Coverlet 等工具產出報告，Scanner 再匯入。
Scanner 與 Server 可不可以同機？POC 可以；公司 CI 中則常由 Runner 連線到集中管理的 Server。

SCENARIO / 故障定位

Scanner 顯示報告上傳成功，但 Dashboard 還沒有最新指標。先檢查哪個假設？

06 / POC 的第一個觀察目標

你要在後續實驗中親自確認三件事：Scanner log 顯示提交成功；Server 端 Background Tasks 顯示分析完成；Dashboard 顯示對應 Project 與 Quality Gate。三者才構成一條可追蹤的完整證據鏈。
