GitHub Runner 不需直接接觸 SonarQube Database。Server Dashboard 是同一 Server 的 Web UI，不是另一個獨立的資料推送目的地。

02 / GitHub Checkout 為什麼要確認 SHA？

Scanner 讀的是實際 Checkout 的檔案，而不是 SonarQube Main Branch 顯示的文字。GitHub push main 的 Checkout 預設取得觸發事件 SHA；即使本地是 detached HEAD，仍能分析。fetch-depth: 0 是保留 Git History 供 SCM blame 等使用，不是指定 Branch。

- uses: actions/checkout@v4
  with:
    fetch-depth: 0
- name: Confirm revision
  run: |
    git rev-parse HEAD
    git log -1 --format='%h %cs %s'

免費 Community Build 的同一 Project 不會為每個 Git Branch 自動建立獨立品質歷史；CI 必須固定一致的來源與 Project Key。完整邊界見 Lesson 03 與 版本比較 Reference。

03 / 最小 Non-blocking Workflow

此範例使用已公開的官方 Scan Action；假設測試 Project Key 為 demo-api。必須先在 GitHub 設定 SONAR_TOKEN Secret、SONAR_HOST_URL Variable。若 Server 是內網位址，不可用無路由的 GitHub-hosted Runner。正式部署應審核 Action 版本與 Runner runtime，pin 確切 Commit SHA。

name: Sonar Observe
on:
  push:
    branches: [main]
  workflow_dispatch:
jobs:
  analyze:
    runs-on: ubuntu-latest # 私網請換核准 self-hosted Runner
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Verify SHA
        run: git rev-parse HEAD
      - name: Scan
        uses: SonarSource/sonarqube-scan-action@v7
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
        with:
          args: >
            -Dsonar.projectKey=demo-api
            -Dsonar.qualitygate.wait=false
這裡的 Non-blocking 是「不因 Gate FAIL 使 Scanner Fail」。

sonar.qualitygate.wait=false 是預設值，但 TLS 錯誤、Token 無效或 Scanner 自己出錯仍可能讓 Job 失敗。若 Deployment Job 依賴 Analyze Job，這類失敗仍可能擋住它。正式導入不可把「不等 Gate」當成「所有失敗都放行」。

04 / 從症狀定位第一個失敗環節

現象先查哪裡
DNS、Timeout、Connection refusedRunner → Server DNS／Route／Firewall／Service
certificate verify failed / unknown CATLS 憑證鏈、Hostname、Runner / Scanner CA Trust
401 / 403Token、期限、專案分析權限
Report uploaded 但頁面未更新Server Compute Engine Background Task
CE SUCCESS 但內容不符Checkout SHA、Project Key、Profile、Exclusions

不要用 curl -k 當成 TLS 的正式修復。應安裝可信 CA、確認憑證 SAN／鏈及 Server URL；Debug 記錄需遮蔽 Token／內網機敏資料。

05 / 實際驗收要留下什麼？

  1. 在授權隔離 Repo 執行上述概念 Workflow，記錄事件、git rev-parse HEAD、Scanner Exit Code（不記 Token）。
  2. 找到 Scanner 產出的 report-task.txt、CE Task ID，確認 Server Background Task 是 SUCCESS，而非只有上傳成功。
  3. 從同一 Project Dashboard 查到分析時間、Gate 和 Issues / Metrics，核對 Project Key／Revision 對得上。
  4. 各模擬一次連線失敗與授權失敗，說明它們和 Gate FAIL 不是同一層責任。

06 / 一分鐘回顧

  • Trigger 決定時機；Checkout SHA 決定程式碼；Project Key 決定分析歸屬。
  • TLS、Token、網路是提交分析報告的前提，不是 Quality Rule。
  • Scanner 成功上傳與 CE 成功完成是不同的事件。
  • 下堂再加入 Coverage 報告與 Gate Fail 的 CI 處理。
