SonarQube / Phase 06 / Lesson 12

L12 / RECOVERY / UPGRADE & ROLLBACK

Pod 換回舊版，
為什麼資料庫不一定跟著回去？

在 Kubernetes 上讓 Pod 自動重啟很容易；真正的難題是 PostgreSQL 損毀、版本升級修改 Schema、Elasticsearch（ES）重新索引、CI Gate 無法提供結果時，如何讓品質平台可預期地復原。這堂從「哪裡有唯一資料」倒推出備份與回退設計。

Phase 06 · Lesson 12約 20 分鐘Restore Drill／Upgrade Plan

學習目標

能分辨 Server Pod、ES Index、PostgreSQL 故障；能設計安全的備份與隔離還原演練，解釋為何 Helm Rollback 不是資料庫 Schema Rollback；並留下 RPO、RTO、Upgrade Path、Release Gate 維護策略的可驗證證據。

01 / 三種「壞掉」不能用同一招

失效元件狀態應該優先採取的策略
Pod／NodeDB 與資料仍完整重新排程／重建 Pod，核對 DB Connection、Readiness、Compute Engine（CE）Task
Elasticsearch IndexDB 仍完整，搜尋索引損毀／遺失依官方程序重建 Index；可能延遲，但不必把 DB 還原到舊時間點
PostgreSQL權威資料損毀／遺失從可驗證的 DB Backup 還原；不能靠重建 Pod 或 ES Index 找回遺失的資料

Figure / 判斷資料是否仍有來源

品質歷史／Issues 不見了先確認是 UI Index 問題還是 DB 資料問題
↓ Database 完整，只有 ES 損壞
重新建立 Elasticsearch Index重建時間依資料量而異；不是資料庫還原
↓ 若 Database 自身已損壞
備份 → Database Restore決定 RPO／RTO；恢復後再索引

箭頭代表排障判斷路徑，不是無論出現什麼狀態都必須清除 ES PVC。重建／刪除之前應確認故障層級。

02 / 備份到底要保什麼？

SonarQube Database 保存 Issues、Metrics、Quality Profiles／Gates、使用者及權限設定、分析任務等。官方支援資料庫Hot Backup，建議使用資料庫自己的工具。備份成功的定義不是「檔案存在」，而是能在隔離環境還原並查驗資料。官方 Backup / Restore。

建議設計三種保護範圍：

DB Backup：權威資料的回復點；IaC／Helm Values／Secret References：重建服務設定（機密本體由受控 Secret System 管理）；ES Index：大部分情況可重建，不能代替前兩者。同步保存使用過的 Chart／Image／Plugin 版本，以便回到相容的環境。

RPO 與 RTO 是兩個不同問題

指標真正問的是示例政策
RPO（Recovery Point Objective）最多能接受失去多少時間的資料？例如最多 24 小時；必須配合備份頻率與 WAL 策略驗證
RTO（Recovery Time Objective）服務故障後最多能停止多久？例如 2 小時；要用實際 DB Restore + ES Reindex + Smoke Test 時間證明

上述 24 小時／2 小時純屬教學範例，不是官方或任何組織已定義的 SLA。若使用 PostgreSQL 邏輯備份，也需確認版本相容性、權限、物件所有權及是否還需要 WAL/PITR 才能滿足 RPO。

03 / 隔離 Restore Drill 的正確順序

  1. 準備：核對目前 Server／DB 版本，記錄 Project Count、抽樣 Project Key、Issues、Quality Gate、Users／Profiles、最近 CE Task；建立受控的備份並驗證可讀。
  2. 隔離：建立獨立 namespace 與獨立測試資料庫，不讓 Restore Drill 指向原始正式 DB；控制 Secrets、NetworkPolicy 與外部整合，避免兩套 Server 同時寫入同一 DB。
  3. 還原：按照官方備份程序停止測試 Server、還原測試 Database，並在必要時清除測試 ES Index 後重啟重建。對 Kubernetes 的 ES PVC，遵照官方 Reindex 指引；**不得盲目刪除正式 PVC**。
  4. 驗證：比對原有抽樣 Issues／Metrics、Quality Gate、設定與登入；觀察 Index Rebuild 與 Background Tasks、Scanner 回報與 Gate 能否恢復。
  5. 量測：記錄 Backup Timestamp、Restore Started／Ended、Reindex Ended、可供 CI 查詢的時間，與實際 RPO／RTO 差距。

ES Reindex 不是 Database Restore。官方明確表示在 Kubernetes 若 persistence.enabled=false，因為沒有持久保存 ES Index，啟動時自然需要重新建索引；若已開啟 ES Persistence，重建程序涉及 Scale Down 和 PVC，不應未經核准直接操作生產資源。官方 Reindexing。

04 / Upgrade 前先查更新路徑，而不是直接換 Image Tag

Figure / Upgrade 工作的必要依賴

Current Build → Target Build核對 Release Notes、支援 DB／Java／K8s、Chart Values、Plugins
↓ 先確認官方允許的中繼版本與 Upgrade Path
Backup + Staging Restore在隔離環境完整演練，測量停機與 Migration 時間
↓ 在正式環境鎖定版本及變更窗口
Upgrade + DB Migration + ES Reindex觀察 Server／CE／UI 的健康與背景工作
↓ Smoke Test + Scanner + Gate 查驗

官方 Community Build 的 Calendar Version 更新並非任意跨版本直升：同年版本通常可直接更新；跨年原則上要先到前一年的 December 版本，且有特定例外。必須查 官方 Update Path，不能僅由 Helm Chart Version 推論 Server Schema 可相容。Pre-update 也提醒 Migration 可能使資料庫暫時接近平常使用量的兩倍。

05 / 為什麼 helm rollback 不等於整個系統回退？

想像從 26.x 升到之後某個新版時，新的 SonarQube 啟動並已修改 DB Schema。此時執行：

# 概念：僅顯示 Helm Revision History
helm history sonar -n sq-learning
# 只回滾 chart resource/template 不等於回滾資料庫 Migration
# 請勿直接對生產執行 helm rollback

Helm 可以把 Kubernetes Manifest／容器版本指回先前 Revision，但不能自動把 PostgreSQL Schema 與資料倒回舊版本。若舊版 Server 不相容於新 Schema，Pod 即使看似成功重建也可能無法啟動；真實回退須依版本相容性與事先可用的 DB Backup，將 Application、Schema、配置一起恢復到一致狀態。

升級失敗時，先決定資料庫的狀態。

如果 DB Migration 尚未開始，恢復舊版的方案與「Migration 已成功改變 DB Schema」的方案不同。後者不能把 helm rollback 當成保證安全的唯一指令；要依官方支援的回復程序，停用所有連到該資料庫的 Server，先在測試環境驗證還原與相容性。官方 Update Procedure。

06 / CI/CD Gate 遇到 SonarQube 故障怎麼辦？

備份與更新不只是 K8s 工作，還會影響 GitHub Actions。當 Server 暫停服務或重新索引時，Scanner 可能連線失敗、Gate Wait 逾時。這不等於程式碼 Quality Gate FAIL。正式政策應把結果分成 PASS／FAIL／UNKNOWN，分別交給既有的部署門禁、維護窗口與受控例外機制；不得默默把 UNKNOWN 當作 PASS。

另外，官方文件提到 ES Reindex 期間部分 Project 功能會逐步恢復，且 Gate 計算可能等待 Index 完成而超時；這正是必須在 Upgrade Drill 觀察的實際 CI 副作用。Reindex 時 Gate Timeout 行為。

RETRIEVAL / 升級與回復

新版 SonarQube 已成功修改 DB Schema，現在要回到舊版。哪個判斷合理？

08 / 一分鐘回顧

  • DB Backup 保障權威資料；ES Index 可以重建，但需要時間。
  • 只有實際成功 Restore 的備份，才可作可靠的復原依據。
  • Upgrade 要先查合法路徑、Migration 容量、Plugins 和 Chart 相容性。
  • Helm Rollback 不包含 DB Schema Rollback。
  • SonarQube 故障是 UNKNOWN，不等於 PASS，也不是程式碼 Quality Gate 的 FAIL。
官方優先來源：Backup and Restore · Determine Update Path · Pre-update · Reindexing。若不清楚真實故障原因，先保存 DB 狀態、CE Task、Pod Events 和 Revision，不直接刪除資源。
