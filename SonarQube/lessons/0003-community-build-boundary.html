L03 / COMMUNITY BUILD / PRODUCT BOUNDARY

CI 觸發與分支分析，
是兩種不同的能力。

從一個最基本的例子開始：同一個 Repository 會有主分支與功能分支，PR 是合併前的變更請求。這堂先分清楚兩層：GitHub 何時執行 workflow，與 SonarQube 能辨識、保存哪一種分析結果。後者的功能邊界會限制你能做的 CI 治理。

Phase 02 · Lesson 03約 12 分鐘不需安裝

學完要能做到

面對主分支、Feature Branch、Pull Request、Release Tag 四種情境，你可以辨認 Community Build 的原生能力，以及哪些需求需要改設計、不能靠改 workflow 名稱達成。

01 / 先看兩個系統的工作邊界

GitHub Actions 的 on: 決定 Runner 什麼時候被叫起來。Runner 是執行 CI job 的機器或容器，可以在 PR、push 或 tag 事件執行 Scanner。Scanner 對讀到的程式碼做檢查，而 SonarQube Server 決定這份資料能否被視為某個 Branch / PR 的獨立分析結果。兩件事不同。

02 / ANALYSIS MODEL

Community Build

「哪個分支的分析結果能被正式管理？」

main branch

免費版原生主分支分析，不提供完整的多分支與 PR 分析。

這裡要把「有啟動 Scanner」與「SonarQube Server 有能力管理這種結果」拆開。執行 on: pull_request 後，Runner 確實可以 Checkout PR 程式碼、啟動 Scanner，Scanner 也可以開始進行規則檢查；但是免費版沒有提供 PR #123 專屬的原生分析結果、與目標分支的比較、PR Dashboard 或 PR Decoration。

不是「觸發了卻不分析」。

而是「Scanner 可以執行分析，但 Server 不支援用 PR 這個獨立維度，正確儲存與呈現結果」。嘗試上傳 PR/branch 分析可能因設定與版本而失敗；如果硬把它當成 main 結果上傳，還可能污染 main 的分析狀態。這不是可依賴的 PR Gate。

容易誤解的例子：你可以在 GitHub PR 工作流程執行一般測試或其他掃描工具，但不能因此聲稱「SonarQube Community Build 已完成原生 PR Analysis」。

02 / 用四種實際事件驗證

你希望分析什麼？Community Build 原生能力初期做法
選定的追蹤分支 push
可以是 main 或 develop		支援單一主分支結果固定 Checkout 同一個分支，由同一個 Project 接收分析。
另一個 Branch
例如 feature/payment		不支援同 Project 多分支結果可選為唯一追蹤來源，但不能與另一個 Branch 共享同一 Project 的獨立歷史。
Pull Request
例如 PR #128		不支援原生 PR Analysis不能期待 PR Decoration 或原生差異 Issue 結果。
Release Tag
例如 release/TW/PROD/…		沒有獨立 tag 分析維度若 SHA 來自既定追蹤分支，可研究品質結果對應，但仍需驗證 SHA。

這裡說的「Main Branch」是 SonarQube Project 的邏輯身分，不等同 GitHub Repository 的 Default Branch。它可以對應 develop 等任何你決定長期分析的分支。免費版限制的是同一 Project 僅管理一份主分支品質狀態，不是只能讀取名字叫 main 的原始碼。

真正決定程式碼來源的是 Checkout，而不是 Dashboard 上的名字

要分析哪份程式碼，先看 Runner 工作目錄裡有哪些檔案。例如，若要追蹤 GitHub 的 main，就必須讓 Scanner 看到 main 某次 Commit 的檔案；不一定要執行 git checkout main。

on:
  push:
    branches: [main]

jobs:
  sonar:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      # 下一步執行 SonarScanner

在這種 push 事件下，actions/checkout 預設取出觸發此次 workflow 的 Git Commit（GITHUB_SHA），即使處於 detached HEAD，Scanner 仍可分析該 Commit 的程式碼。fetch-depth: 0 是為了保留 Git 歷史與 SCM 資訊，不是指定要掃描的 Branch。你可以用 git rev-parse HEAD 確認工作目錄的 Commit SHA。

反過來，若 GitHub 的 Default Branch 是 main，但你想長期追蹤 develop，就固定讓 CI 取得 develop 對應的 Commit，並讓 SonarQube Project 的 Main Branch 身分與來源一致。要在非 main 事件中改掃 main，可明確指定 actions/checkout 的 ref（或精確 Commit SHA）。但此時掃描來源與觸發事件可能不同，必須把分析所用 SHA 記錄清楚。

官方依據：SonarSource — Checked-out code；GitHub actions/checkout — ref/SHA 與 fetch-depth。

GitHub RepositoryDefault Branch = main；另有 develop
↓ CI Checkout develop
SonarScanner分析 develop 這份原始碼；sonar.projectKey=mes-backend
↓ 將分析報告歸屬 Project
SonarQube Project：mes-backend唯一的 Main Branch 分析狀態，來源對應 develop

概念示例。SonarQube 不會因為你將 Main Branch 重新命名為 develop，就自行改去 GitHub 抓取 develop；必須讓 CI 實際 Checkout / 掃描對應分支。

這是維運上最需要避免的風險：如果用相同 Project Key 先掃 main，又不帶獨立 Branch 身分掃 develop，後一次分析可能覆寫該 Project 原本的主分支品質狀態。若希望同一 Repo 的兩個 Branch 各自長期追蹤，技術上可用不同 Project Key 建立兩個 Project，但這不是原生 Multi-Branch Analysis，資料與歷史也不共享。

依據 SonarSource 工程師對 Community 主分支的說明以及 2025 年 develop 追蹤設定的官方社群回答。若 Project 是透過 GitHub 整合匯入，初始 Main Branch 名稱可能跟 GitHub 預設分支一致；仍應檢查實際 Scanner 來源與版本設定。

先補一個名詞：SonarQube Project

Project 是 SonarQube 裡保存某份程式碼品質資訊的邏輯對象。GitHub Repository 裡放的是原始碼與 Git 歷史；SonarQube Project 裡管理的是這份原始碼的分析結果、Issues、Metrics、Quality Profile 與 Quality Gate。它不是 Kubernetes Namespace，也不是 Runner 本身。

例如 GitHub mes-backend 對應 SonarQube 的 Project Key mes-backend。Scanner 透過 sonar.projectKey=mes-backend 告訴 Server 報告要歸屬哪個 Project。入門階段採用一個 Repo 對應一個 Project最容易看懂，但並不是產品唯一允許的映射方式。

下階段會更仔細學：Phase 03 / Lesson 05 會從 Repository → Project → Project Key → Main Branch → Dashboard 的關係開始，再進入 Docker 啟動、資料庫與實際建置，不會突然要求你建立一個不知道用途的 Project。

03 / 免費版真正可以做到哪些事？

AVAILABLE

分析與 Dashboard

原始碼靜態分析、Issues、Metrics，以及主分支 Project 的品質結果。

AVAILABLE

Quality Profile / Gate

可自行設定啟用哪些規則、以及分析指標達到什麼門檻才算通過。

AVAILABLE

GitHub Actions 掃描

CI Runner 可以執行 Scanner、提交報告，並選擇等待 Quality Gate 結果。

EXTERNAL INPUT

Coverage

可以匯入 Coverage 報告；測試與 Coverage 報告仍需外部工具產生。

GitHub 帳號整合不是 Scanner 的同義詞。

使用 GitHub App 可協助匯入 repo、整合登入；但你可以先在 SonarQube 建立 Project，再由 CI 使用 URL、Project Key 與 Token 上傳。學習 POC 不必預設先建立完整企業級 GitHub App 整合。

04 / 免費版限制如何影響你們的 CI/CD？

你們目前主要從 release/** 標籤執行 build → deploy → E2E，也有 PR Merge 自動測試和 Production Release Gate。若想用免費版，先決定每個 Repo 哪個 Git Branch 值得持續追蹤（例如 default branch 或 develop），再由 CI 固定掃描它；不假設每個 PR 或 Release Tag 都能在同一 Project 形成獨立分析結果。

Concept / 免費版優先整合位置

PR Merge to default branch已有的合併事件
↓ 觸發
Main branch SonarQube Scan獨立 job · 先觀察、不阻擋
↓ 報告提交／背景處理
SonarQube Quality Gate在 Dashboard 與 API 查看狀態

這是下一階段要驗證的設計提案，不是已實際部署的公司 workflow。是否進入 Release Gate 留到 Phase 05 討論。

如果一定要阻擋尚未合併的 PR，就要明確評估其他免費工具、獨立自製檢查策略，或接受原生 PR Analysis 功能缺口；不要把主分支掃描硬稱為 PR Scan。

05 / New Code 並不等於 PR Analysis

免費版在主分支上仍可區分 New Code 與 Overall Code。前者是一段基於「前次版本、天數、指定分析」等設定所劃定的新增或修改程式碼範圍；後者包含整個專案。

這表示你可以主張「從今天開始，新增的程式碼要乾淨」，不必馬上修完全部 Legacy Issues。但它不是在 PR 尚未合併前，對該 PR 相對目標分支做獨立分析。兩件事不能畫等號。

06 / 本堂結論與決策

  • GitHub Actions on: 管的是觸發；SonarQube 版本管的是原生分析能力。
  • Community Build 適合先從 Main Branch + Dashboard + Quality Gate POC 切入。
  • New Code 可用於主分支的「新程式碼品質」，不能當成原生 PR Analysis。
  • GitHub App 整合與 Scanner 上傳分析是兩種不同層次；POC 可分開驗證。
