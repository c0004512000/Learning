L03 / COMMUNITY BUILD / PRODUCT BOUNDARY

CI 觸發與分支分析，
是兩種不同的能力。

從一個最基本的例子開始：同一個 Repository 會有主分支與功能分支，PR 是合併前的變更請求。這堂先分清楚兩層：GitHub 何時執行 workflow，與 SonarQube 能辨識、保存哪一種分析結果。後者的功能邊界會限制你能做的 CI 治理。

Phase 02 · Lesson 03約 18 分鐘不需安裝

學完要能做到

能從 Trigger → Checkout → Scanner → Project/Server 推導某次分析的程式碼來源與資料歸屬；判斷 Community Build 面對 Push、PR、Tag 時，哪些結果可以保存、哪些屬於商業版功能，以及何時需要另做整合測試。

01 / 先看兩個系統的工作邊界

先用一條完整的資料流理解所有名詞：Workflow 是 CI 步驟清單；Runner 是執行那些步驟的環境；SonarScanner 是其中被呼叫的分析工具，並不是整條 CI Pipeline，也不需要是另一個 Kubernetes Pod。

↓ 報告提交到 Project Key 指定的 Project

Scanner 顯示上傳成功，不代表 Dashboard 當下更新完成；必須等 Background Task 結束。參考 Lesson 02 的非同步分析流程。

GitHub Actions 的 on: 決定 Runner 什麼時候被叫起來。Runner 是執行 CI job 的機器或容器，可以在 PR、push 或 tag 事件執行 Scanner。Scanner 對讀到的程式碼做檢查，而 SonarQube Server 決定這份資料能否被視為某個 Branch / PR 的獨立分析結果。兩件事不同。

Community Build

「哪個分支的分析結果能被正式管理？」

main branch

免費版原生主分支分析，不提供完整的多分支與 PR 分析。

這裡要把「有啟動 Scanner」與「SonarQube Server 有能力管理這種結果」拆開。執行 on: pull_request 後，Runner 確實可以 Checkout PR 程式碼、啟動 Scanner，Scanner 也可以開始進行規則檢查；但是免費版沒有提供 PR #123 專屬的原生分析結果、與目標分支的比較、PR Dashboard 或 PR Decoration。

不是「觸發了卻不分析」。

而是「Scanner 可以執行分析，但 Server 不支援用 PR 這個獨立維度，正確儲存與呈現結果」。若明確要求原生獨立 PR／Branch Analysis，會碰到 Community 的功能限制；若沒有提供獨立分析身分，一般分析則會更新同一 Project 的主分支狀態，可能把其他來源的程式碼當成主分支結果。這不是可靠的 PR Gate；實際是否執行成功還取決於掃描設定、權限與環境。

一個具體的分析歸屬範例

分析歸屬不是由 on: push 或 on: pull_request 自動決定。Scanner 至少需要知道送到哪個 Project Key；而「是否要求獨立的 Branch／PR 結果」是另一組分析身分。這裡的分析模式是用來理解三類結果的說法，不是 Server 有一個「分析模式」切換按鈕。

Scanner 送出的分析身分結果要保存在哪裡？Community Build
sonar.projectKey=demo-web
未指定獨立 Branch/PR		該 Project 的 Main Branch一般主分支分析
相同 Key + sonar.branch.name=develop要求另建 develop 的獨立分析狀態不支援此分析身分
相同 Key + sonar.pullrequest.key=42
及相應 PR 身分		要求儲存 PR #42 的獨立分析結果不支援此分析身分

因果推論：若 Scanner 實際 Checkout develop，但只指定 sonar.projectKey=demo-web，成功分析後仍更新 Project 唯一的 Main Branch 狀態。Dashboard 上顯示名稱可能仍是 main，名稱不會跟著 Git Checkout 自動改成 develop。後續用同一 Key 掃其他來源，就可能使品質歷史與來源不一致。

依據：官方功能比較、Branch Analysis 身分。具體錯誤訊息依部署版本與 Scanner Log 確認，不能把這段假設為已完成的 POC。

這裡說的「Main Branch」是 SonarQube Project 的邏輯身分，不等同 GitHub Repository 的 Default Branch。它可以對應 develop 等任何你決定長期分析的分支。免費版限制的是同一 Project 僅管理一份主分支品質狀態，不是只能讀取名字叫 main 的原始碼。

真正決定程式碼來源的是 Checkout，而不是 Dashboard 上的名字

要分析哪份程式碼，先看 Runner 工作目錄裡有哪些檔案。例如，若要追蹤 GitHub 的 main，就必須讓 Scanner 看到 main 某次 Commit 的檔案；不一定要執行 git checkout main。

on:
  push:
    branches: [main]

jobs:
  sonar:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      # 下一步執行 SonarScanner

在這種 push 事件下，actions/checkout 預設取出觸發此次 workflow 的 Git Commit（GITHUB_SHA），即使處於 detached HEAD，Scanner 仍可分析該 Commit 的程式碼。fetch-depth: 0 是為了保留 Git 歷史與 SCM 資訊，不是指定要掃描的 Branch。你可以用 git rev-parse HEAD 確認工作目錄的 Commit SHA。

反過來，若 GitHub 的 Default Branch 是 main，但你想長期追蹤 develop，就固定讓 CI 取得 develop 對應的 Commit，並讓 SonarQube Project 的 Main Branch 身分與來源一致。要在非 main 事件中改掃 main，可明確指定 actions/checkout 的 ref（或精確 Commit SHA）。但此時掃描來源與觸發事件可能不同，必須把分析所用 SHA 記錄清楚。

官方依據：SonarSource — Checked-out code；GitHub actions/checkout — ref/SHA 與 fetch-depth。

PR 事件的 Checkout 還有一個特例：

GitHub 對開啟、可合併的 PR，pull_request 的預設 GITHUB_REF 是 refs/pull/N/merge；不特別指定 ref 時，actions/checkout 一般取得的是 GitHub 的模擬合併 Commit，而非 Feature Branch HEAD。若想取來源 HEAD，才明確指定 github.event.pull_request.head.sha。這個「GitHub 模擬合併」和「SonarQube 原生 PR Analysis」不是同一件事。詳見 GitHub PR 事件官方文件。

概念示例。SonarQube 不會因為你將 Main Branch 重新命名為 develop，就自行改去 GitHub 抓取 develop；必須讓 CI 實際 Checkout / 掃描對應分支。

這是維運上最需要避免的風險：如果用相同 Project Key 先掃 main，又不帶獨立 Branch 身分掃 develop，後一次分析可能覆寫該 Project 原本的主分支品質狀態。若希望同一 Repo 的兩個 Branch 各自長期追蹤，技術上可用不同 Project Key 建立兩個 Project，但這不是原生 Multi-Branch Analysis，資料與歷史也不共享。

依據 SonarSource 工程師對 Community 主分支的說明以及 2025 年 develop 追蹤設定的官方社群回答。若 Project 是透過 GitHub 整合匯入，初始 Main Branch 名稱可能跟 GitHub 預設分支一致；仍應檢查實際 Scanner 來源與版本設定。

先補一個名詞：SonarQube Project

Project 是 SonarQube 裡保存某份程式碼品質資訊的邏輯對象。GitHub Repository 裡放的是原始碼與 Git 歷史；SonarQube Project 裡管理的是這份原始碼的分析結果、Issues、Metrics、Quality Profile 與 Quality Gate。它不是 Kubernetes Namespace，也不是 Runner 本身。

例如 GitHub demo-web 對應 SonarQube 的 Project Key demo-web。Scanner 透過 sonar.projectKey=demo-web 告訴 Server 報告要歸屬哪個 Project。入門階段採用一個 Repo 對應一個 Project最容易看懂，但並不是產品唯一允許的映射方式。

一個 Repo 可以對應幾個 Project？

通常採一個 Repo 對一個 Project；但也可以把同一 Repo 的 main 和 develop，分別用 demo-web-main 與 demo-web-develop 兩個 Project Key 進行長期掃描。這會得到兩個互相獨立的分析歷史與 Dashboard，而不是在同一 Project 的 Branch 選單切換。免費版的「一個 Project 只有一條主分支」並不等於「一個 GitHub Repo 只能對應一個 Project」。

Project 在何時建立？Main Branch 名稱從哪來？

官方列出四條建立路徑：手動 Local Project、GitHub 等平台匯入、Web API、符合權限時第一次掃描自動建立。因此 Main Branch 初始名稱依建立方式、實際版本與設定而定，不能理解成每次從哪個 Git Branch 掃描，就自動用該 Branch 命名。重新命名 Main Branch 只調整 Server 的標籤／身分，不會使 Runner 自動改 Checkout；不同版別提供的 UI 與 API 操作應分別查證，不要把商業版「Set as main branch」功能直接套到免費版。

官方依據：Creating your project。建立或重新命名前，先核對該安裝版本；本堂不要求進 UI 操作。

下階段會更仔細學：Phase 03 / Lesson 05 會從 Repository → Project → Project Key → Main Branch → Dashboard 的關係開始，再進入 Docker 啟動、資料庫與實際建置，不會突然要求你建立一個不知道用途的 Project。

03 / 免費版真正可以做到哪些事？

AVAILABLE

分析與 Dashboard

原始碼靜態分析、Issues、Metrics，以及主分支 Project 的品質結果。

AVAILABLE

Quality Profile / Gate

可自行設定啟用哪些規則、以及分析指標達到什麼門檻才算通過。

AVAILABLE

GitHub Actions 掃描

CI Runner 可以執行 Scanner、提交報告，並選擇等待 Quality Gate 結果。

EXTERNAL INPUT

Coverage

可以匯入 Coverage 報告；測試與 Coverage 報告仍需外部工具產生。

GitHub 帳號整合不是 Scanner 的同義詞。

使用 GitHub App 可協助匯入 repo、整合登入；但你可以先在 SonarQube 建立 Project，再由 CI 使用 URL、Project Key 與 Token 上傳。學習 POC 不必預設先建立完整企業級 GitHub App 整合。

Scanner 不受限於 CI 或容器，也不由 Server 主動取代

CI 只是常見啟動方式。同一個 Scanner 也能在開發機或手動工作執行；SonarScanner CLI 可以在 Runner 執行期間下載並解壓、預先安裝，或透過 Docker Image／官方 GitHub Action 使用。Maven、Gradle、.NET 等則有整合的 Scanner 命令。Community 與商業版的核心差異是分析結果的能力與治理整合，不是免費版只能呼叫 CLI、商業版改由 Server 主動掃 GitHub。

外部測試的 Coverage 與 Test Execution Report 可以在 Scanner 前產生、交由 Scanner 匯入；E2E case 數量不等於 Coverage，壓測 RPS／延遲也不是內建的 SonarQube 壓測 Dashboard。需要參數與格式時可開啟 Scanner、PR 與測試報告速查。

04 / 免費版限制如何影響 CI/CD？

假設某個 Repository 有 main、develop、PR 與 Release Tag。你可以在 push、PR、Tag 或手動事件啟動 Scanner，不代表 SonarQube 會為每種事件另外建立結果。若沒有要求獨立 Branch／PR 分析身分，且其他條件允許分析成功，通常更新的仍是同一 Project 的 Main Branch 品質狀態。

所以不是「一定要在 merge 後才能掃」。

你可以自行決定掃描時機。官方建議 Community Build 固定對一條選定的 Git Branch 做 push analysis、不要設 on.pull_request，原因是避免 PR、Tag 或其他來源的結果取代你原本想持續追蹤的主分支狀態，而不是 Runner 無法在其他事件執行 Scanner。

Concept / 可重複判讀品質狀態的起點

Push 到固定追蹤分支例如 main；確認本次 Commit SHA
↓ 觸發 Workflow；Runner Checkout 相同來源
Scanner → 同一 Project Key未指定獨立 Branch／PR 分析身分
↓ Server 背景處理完成
Main Branch Dashboard / Gate品質趨勢的程式碼來源維持一致

這是推薦的教材設計示例，不是唯一合法的觸發方式，也不是已完成的實際部署證據。

若目標是合併前阻擋 PR，單靠把 on.push 改為 on.pull_request 不會產生原生 PR 差異分析；還需評估可支援獨立 PR 分析的產品，或另設合併前測試與品質檢查策略。這個界線不妨礙你在 Community Build 使用一般 Quality Gate。

05 / New Code 並不等於 PR Analysis

為什麼商業版要把 PR Analysis 與 Branch Analysis 分成兩種？ Branch Analysis 管的是「這條 Git Branch 本身現在的品質狀態及歷史」；PR Analysis 管的是「相對本次合併目標分支，這個 PR 準備引入哪些新增或修改程式碼，以及這些 New Code 是否達到品質門檻」。所以 PR 有三個 Commit 或更多 Commit 都不妨礙比較：關鍵是整個 PR 的變更集合，不是只掃最後一個 Commit。

例如 Feature Branch 已增加三次提交，同時目標 main 也多了五次提交。商業版的 PR 分析會依當次可用的目標分支歷史與 PR 變更界定 New Code，並依New Code 的 Quality Gate 條件判斷。這不表示 SonarQube 保證未來 merge 的整合結果永遠安全；來源和目標仍可能持續前進。要檢查合併後建置與功能是否正常，還要以目前版本執行 CI Build／Tests／必要時 Merge Queue 的合併結果驗證。

官方依據：商業版 PR 分析：New Code 與 Gate。PR 比較、GitHub 模擬合併 Checkout 是兩個不同機制，請對照 Reference。

免費版在主分支上仍可區分 New Code 與 Overall Code。前者是一段基於「前次版本、天數、指定分析」等設定所劃定的新增或修改程式碼範圍；後者包含整個專案。

這表示你可以主張「從今天開始，新增的程式碼要乾淨」，不必馬上修完全部 Legacy Issues。但它不是在 PR 尚未合併前，對該 PR 相對目標分支做獨立分析。兩件事不能畫等號。

目前官方文件對 Community Build 26.10 的 Quality Profile 分為 Sonar way core / extended / comprehensive；舊教學可能只寫 Sonar way。這是規則組的版本變化，不代表免費版突然開放 PR Analysis。下一堂會拆解規則與品質門檻。

情境練習：能否從事件和參數判定歸屬？

同一個 Project Key demo-web，Scanner 先掃 main，下次在 tag 事件中 Checkout 到較舊的 Commit；兩次均未指定 Branch／PR 身分。第二次若成功處理，會新增「Tag」分支，還是更新原本的 Main Branch？

推導：更新原本的 Main Branch。Trigger 與 Checkout 決定何時掃、掃哪個 SHA；Project Key 與分析身分決定結果放哪裡。反過來，如果額外指定 sonar.branch.name，就是要求 Community 不支援的獨立 Branch Analysis。此練習是概念推導，不是假造 Scanner Log。

06 / 本堂結論與決策

  • GitHub Actions on: 管的是觸發；SonarQube 版本管的是原生分析能力。
  • Community Build 適合先從 Main Branch + Dashboard + Quality Gate POC 切入。
  • New Code 可用於主分支的「新程式碼品質」，不能當成原生 PR Analysis。
  • GitHub App 整合與 Scanner 上傳分析是兩種不同層次；POC 可分開驗證。
