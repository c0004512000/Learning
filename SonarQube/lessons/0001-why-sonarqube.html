L01 / 第一性原理

程式碼能跑，
就代表品質沒問題嗎？

這堂課只建立一個觀念：執行測試與靜態程式碼分析，回答的是不同問題。學完要能判斷 SonarQube 在既有 CI/CD 裡應該扮演什麼角色。

約 8–12 分鐘零部署前提理解 → 判斷 → 反饋

01 / 從可觀察的情境開始

假設有一段 API 程式碼，所有 E2E Test 都通過。但它可能有重複邏輯、永遠不會被執行的分支，或在特定輸入下引入安全風險。測試通過只表示「被測到的行為符合預期」；它不會自動證明「整份原始碼沒有值得修正的問題」。

反過來，靜態分析可以在不啟動整個應用程式的情況下讀取原始碼，根據規則找出可疑結構；但它也不能證明登入、下單或部署流程實際可用。

必要性：我們需要一個與 runtime tests 不同的檢查視角。這個視角稱為 Static Analysis（靜態分析）。針對安全風險的靜態分析通常稱為 SAST（Static Application Security Testing）。

02 / 現有品質檢查與 SonarQube

檢查核心問題不能替代什麼
Secret Scanning程式碼是否含有不應暴露的憑證／Token？不能評估整體可維護性
SonarQube程式碼是否有可靠性、安全與可維護性問題？不能保證功能正確
E2E Testing從使用者流程執行，功能是否符合預期？不能涵蓋所有靜態風險
Stress Testing系統在負載下的效能與穩定性如何？不能證明原始碼沒有 Code Smells
Release Gate這個版本是否符合進入環境的條件？本身不是分析工具

03 / SonarQube 主要看什麼

可以先分三個方向理解，先不急著記住所有指標名稱。

RELIABILITY

可靠性

例如可能造成錯誤結果、空值問題或例外的程式碼模式。

SECURITY

安全性

找出部分漏洞風險與需要人工檢視的 Security Hotspots；免費版不等於完整資安掃描。

MAINTAINABILITY

可維護性

例如重複程式碼、複雜度與難以維護的寫法。

METRICS

品質指標

可呈現重複率與測試覆蓋率，但 Coverage 報告須先由其他測試工具產生。

04 / 目前不需要做的事

在還沒理解資料流程之前，不需要先研究 PostgreSQL HA、Kubernetes Helm values，或把 SonarQube 強行放進 Production Gate。那是後面才要處理的責任。

05 / 這堂的最小結論

  • Static Analysis 不需要依賴應用程式實際運作，主要透過程式碼與相關資訊尋找問題。
  • E2E、Stress Test 與 Secret Scanning 各自回答不同問題，SonarQube 是新增的一層品質訊號。
  • 找出問題 ≠ 自動阻擋部署；是否阻擋由之後的 Quality Gate 與 CI 策略決定。
