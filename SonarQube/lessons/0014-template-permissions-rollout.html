PHASE 07 / TEMPLATE & ROLLOUT DECISION

十個 Repo 都跑得動，
就能一次推到一千個嗎？

技術上可以把一段 Scanner Step 複製到所有 Repo，但這不是可治理的 Rollout。真正要標準化的是分析身分、掃描輸入、Credential 邊界、政策、錯誤處置與可回退性，而不是把每個服務都硬套同一條 Coverage Path。

Phase 07 · Lesson 14約 20 分鐘Decision Record

學完你應能做到

為多個 Repo 定義一份最小的共享 Scanner Contract，列出 Community Build 的權限邊界和 Quality Gate 治理；能提出按批次試點的 Go／No-Go 判斷、例外流程、監控指標與回退路徑。

01 / 為什麼複製 YAML 不等於標準化？

想像兩個服務：A 使用 Java / Maven、B 使用 TypeScript / Jest。兩邊都需要 SonarQube，但前者須先完成編譯並匯入 JaCoCo XML，後者須先有 LCOV；如果共用 Workflow 強制執行同一條 npm test，Java 直接失敗。如果完全忽略測試報告，又會出現Scanner SUCCESS，Coverage 不完整的假成功。

Figure / 共用 Contract 與語言差異的責任邊界

Repo 自己負責 Build / Test / Coverage每種語言準備好相容的 Bytecode／Coverage；團隊對程式碼與測試品質負責
↓ 將固定的分析輸入交給共用 Workflow

↓ Server 套用 Project 的 Profile、New Code 與 Gate
Release Policy + EvidenceCE Task／Gate 狀態／例外／Owner；Policy 決定是否阻擋部署

這是治理設計示意，不是聲稱 SonarQube 會替你建立 GitHub Actions Reusable Workflow、授權或部署策略。

02 / 共用 Workflow 最小 Contract

欄位／責任誰決定？為何必須存在？
project_keyPlatform 分配、Repo 綁定穩定分析歸屬；防止不同 Repo 用相同 Key 覆寫
source_shaCaller Workflow Checkout對應實際 Commit，不把最新 Dashboard 當作這次 Release
project_versionRelease PipelineTag 是正式發布版本時，記錄版本以供 Activity 回溯
coverage_report_path應用端依語言產生不強迫不同語言使用同一種格式
scanner_versionPlatform 固定並驗證避免不同 Repo 因 Runtime／Action 更新導致非預期失敗
gate_mode有權的治理負責人Observe／Warn／Enforce 必須可審核，不由任意 Repo 自行繞過

**Shared Workflow 本身不應替應用程式決定 Quality Profile 的 Rules，或偷偷把 Gate Fail 設成 PASS。** Profile／Gate 在 SonarQube 管理並記錄指派；共用 Workflow 控制執行與狀態傳遞。另可在 Repo 將語言參數放在受審核的 Scanner 設定檔，不必每個 Job 硬塞十幾個 -D。

03 / Reusable Workflow：抽掉共用流程，留下 Repo 差異

GitHub Actions 提供 workflow_call，但這只是 CI 工具提供的重用機制，不是 SonarQube Community 原生的多 Repo 管理服務。以下是概念化的 Caller；假設被呼叫 Workflow 已實作 Checkout／Scanner／Gate 檢查，並設計好的 project-key 輸入、Secret 與權限。

# .github/workflows/sonar.yml — 合成 Repo 範例
name: SonarQube Analysis
on:
  push:
    branches: [main]
jobs:
  sonar:
    uses: demo-platform/ci/.github/workflows/sonar-scan.yml@v1
    with:
      project-key: demo-service
      gate-mode: observe
    secrets:
      SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

這裡的 @v1 只是教學示意；正式導入應以受審核、不可變的 Commit SHA 或有保護的版本發布流程追蹤共享 Workflow 版本。Caller／Callee 的 Secret 可見範圍、最低 GITHUB_TOKEN 權限與 Runner 連通性都需要另行驗證。GitHub Reusable Workflows。

需要刻意避免的漏洞：

不要允許服務 Repo 只改 gate-mode: observe 就繞過原本已啟用的 Production Blocking Policy。可將部署授權檢查放在受控的共用 Release Gate／Environment Protection 中，並規定誰能調整或批准例外。

04 / Token 與權限不能用最高權限圖方便

官方提供 Project Analysis Token，只允許對特定 Project 執行分析；相比綁全域管理員的 User Token 或 Global Analysis Token，更適合跨 Repo 隔離。預設 sonar-users 可能具有 Global Execute Analysis 權限，導入時要檢查並按公司政策縮限。官方 Token · 官方權限。

權限／設定應由誰持有？
Project Execute Analysis該 Repo 的 Scanner Identity／Project Token
Administer Quality Profiles經授權的規則治理管理者
Administer Quality Gates經授權的品質政策管理者
Administer Project／Visibility特定 Project Owner／受控管理者
Secret／Token Rotation指定的平台憑證管理流程

每個 Project 可按語言套用專屬 Profile，Gate 也可由有權者指定；**不要因為同一個 Repo 會用共享 CI Template，就把所有 Project 的管理權交給同一個無差別 Token**。Project Visibility 也要核對：官方預設新 Project 可能是 Public，代表未經身份驗證也能瀏覽部分原始碼內容與 Issues。Project Permissions。

05 / 一個 Pilot 什麼時候可以擴大？

先定義成功標準，再用數據決定推廣。下面是合成決策範例，不是實測或公司核准門檻：

面向假設門檻若不達標
分析成功率≥ 99%（排除已歸因程式碼品質的 Gate FAIL）先修 Scanner／Token／CE／網路可靠性
CE 任務延遲P95 ≤ 3 分鐘先排查 Queue、CPU／記憶體、DB／ES
誤報處理明確定義 Review Owner 與回報時限先調整 Profile、Exclusions 或政策，而非大範圍關 Rule
Coverage 匯入每個試點 Repo 都能證明報告存在並正確讀取修正語言專屬建置與路徑
故障與回退Gate FAIL／Server Outage／Token 失效皆有演練記錄先維持 Observe，再完成政策驗收

為避免「只挑最好掃的專案」造成偏差，Pilot 至少選兩種不同語言或建置型態，記錄原本的測試覆蓋、Repo 規模與團隊維護成本。運作成功率、Gate PASS 率和品質改善率是不同指標，不能混在同一個 KPI。

06 / Go／No-Go 的可審核決策

Go：

已確認版本與支援邊界、Project 身分與最小權限、語言前置報告、CE／Gate 時序和 CI 例外回退；可在受控批次擴大，並保留儀表化指標和 Owner。

No-Go／Hold：

若仍有未定義的 Outage 放行政策、無法追溯 Release SHA、DB Backup 未能還原、Project 權限過大、誤報無 Owner，或跨語言 Coverage 大量缺漏，應維持或縮小 Pilot。這是「證據尚不足」，不是「工具本身沒價值」。

  1. 先在小批 Repo 上以 Observe 模式收集固定期間數據、分類 Failure，建立 Issue／Gate Owner。
  2. 審查規則噪音、Coverage 匯入、DB／CE 容量、Token 與權限；保持原有 E2E／Security Release Gate。
  3. 取得專案負責人與平台治理核准後，針對特定 Repo／環境轉成 Enforce；清楚記錄例外期限與回退開關。
  4. 逐批擴大；每次變更共享 Workflow 版本都做 Canary，若有問題先回退共用模板／Gate Enforcement，再評估是否需要 Release Rollback。

RETRIEVAL / Rollout 決策

兩個 Repo 掃描成功，但無法證明 Gate 對應的 Release SHA。下一步最適合？

07 / 一分鐘回顧

  • Repo 層準備語言特定資料；Shared Workflow 控制身份、執行、回報與政策。
  • Project Token 限縮授權；Profile、Gate 由獨立治理權限管理。
  • Scanner SUCCESS 不是 Coverage 完整、Gate PASS 或可正式推廣的證明。
  • Rollout 要有 Reliability、False Positive、成本、Owner、Exception、Canary 和 Rollback 的可觀察證據。
