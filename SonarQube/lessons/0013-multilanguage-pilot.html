PHASE 07 / LANGUAGE PILOT

兩個專案都掃成功，
能說品質一樣好嗎？

把 SonarQube 推廣到多個 Repo 時，最容易誤判的不是 Scanner 出錯，而是分析成功卻缺少必要輸入：Java 沒有編譯好的 Class、JS/TS 沒有 LCOV，或兩邊的 Quality Profile 規則不同。先建立可比較的分析條件，才有意義地比較結果。

03 / 同樣寫 80% Coverage，來源可能完全不同

Java 範例：測試工具先執行並產生 target/site/jacoco/jacoco.xml，供 Scanner 匯入；若這個 XML 根本不存在，不能因 Scanner Exit Code = 0 就宣稱 JaCoCo Coverage 已成功匯入。

# Java / Maven 的概念檢查（需專案事先配置 JaCoCo Plugin）
mvn test jacoco:report
test -s target/site/jacoco/jacoco.xml
# Maven Scanner 的執行時機依實際建置及 Scanner 設定安排

TypeScript 範例：Jest、Vitest 或其他工具先產生 LCOV，再指定 Scanner 匯入。

# TypeScript / 合成範例
npm ci
npm test -- --coverage
test -s coverage/lcov.info

sonar-scanner \
  -Dsonar.projectKey=demo-web \
  -Dsonar.javascript.lcov.reportPaths=coverage/lcov.info

這兩份檔案都必須先由外部測試工具產生，Scanner 再匯入；Test Execution 的「測試通過幾個」不是 Source Coverage。官方 Coverage Parameters。

04 / 不同 Quality Profile，怎麼比較？

Quality Profile 是按語言啟用規則的組合。你不能對 Java 和 TypeScript 套同一組 Rule Keys，再因 Java 有 12 個 Issues、TS 有 4 個，就推論 Java 程式碼品質更差。

最小公平比較模型：

先在每個 Repo 記錄語言、版本、Source Exclusions、Quality Profile、已啟用的 Rules、New Code Definition、Gate、Coverage 報告是否存在，再看相同治理政策下是否有新問題。Issues／千行碼、New Code Gate 失敗原因、誤報比例與分析成本，比分母不明的 Raw Issue Count 更有用，但仍不能視為跨語言的精確排名。

同一 Project 有多種語言時，可以各自關聯對應的 Quality Profile；預設使用該語言的 Instance Default，也可以由 Project 管理者明確指派。官方 Profile 指派。Quality Gate 則是 Project 層的條件集合，不是一個按語言執行的 Rule 清單。

05 / Pilot 實驗怎麼設計才有證據？

  1. 選兩個合成、結構簡單的 Repo：demo-java、demo-web。固定 SonarQube Build、Scanner 版本與 Runner 類型。
  2. 各跑一次沒有 Coverage 的 Baseline，記錄 Scanner Log、CE Task、Profile、Issues 與 Gate，**不把缺值自動當成 0%**。
  3. 準備 Bytecode／JaCoCo XML 與 LCOV，再跑一次。核對 Report 路徑、CE Task SUCCESS 與 Dashboard 上新增的 Coverage 指標。
  4. 對每種語言各引入一處可驗證的受控規則違規，記錄正確偵測／未偵測／誤報；不要選無法證明受 Profile 啟用的 Rule。
  5. 記錄分析時間、Runner CPU／Memory、Source 行數、Issues／New Code Gate，以及每個例外案例的根因。再討論是否值得推廣。

06 / 本堂結論

  • 相同的 Scanner 成功訊號，不代表語言前置資料都完整。
  • Java 需要適當 Bytecode；JaCoCo XML、LCOV 都由外部工具產生。
  • Quality Profile 按語言管理 Rules；跨語言不能直接比 Raw Issue Count。
  • Pilot 必須先有可追溯的輸入、配置與 CE Task，才有可解釋的結果。
