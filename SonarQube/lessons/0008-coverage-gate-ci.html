L08 / GITHUB ACTIONS / PRACTICE

Gate 變紅，
部署會停嗎？

有 Coverage 報告，不代表 Gate 就 PASS；Gate FAIL，也不代表 GitHub Actions 自動阻擋部署。本堂要從測試報告的來源，一直推導到 Job Dependency。

Phase 04 · Lesson 08約 20 分鐘受控 FAIL Lab

學習成果

區分 Coverage 與 Test Execution，能安排測試→Scanner→Server 的資料流；在 GitHub Actions 說明 sonar.qualitygate.wait 與 needs 的相互影響，並能用證據區分四類失敗。

實驗是假設情境，尚未在實機執行。

需核准的隔離 Repo、可連線 SonarQube Server、可產出 LCOV 的 JS／TS 測試工具。不要直接替換正式 Release Workflow。

01 / Coverage 是哪裡來的？

Figure / 誰產生數字、誰匯入數字

Test Runner例如 Jest / Vitest 執行測試，產出 LCOV
↓ coverage/lcov.info 是實際存在的檔案
SonarScanner讀取 LCOV 和原始碼，提交分析報告
↓ Compute Engine 彙整 Coverage 指標
Quality Gate根據 New Code / Overall Code 的 Coverage 門檻評估

JavaScript／TypeScript 以 sonar.javascript.lcov.reportPaths=coverage/lcov.info 指定已產生的報告；Scanner 自己不執行測試。Test Execution（哪個測試成功、失敗、耗時）是另一種格式，不等於程式碼覆蓋率；Playwright E2E 案例數也不是 Coverage。看測試資料速查。

02 / 不同 Failure 不能混為一談

現象責任位置應查什麼
測試失敗Test Runner測試 Exit Code、LCOV 是否產生
掃描失敗Runner / ScannerTLS、Token、路徑、Scanner Log
報告已上傳，但 CE 失敗Server Compute EngineCE Task ID / Error Detail
CE 成功，Gate FAIL品質政策判定哪條 Metric / Operator / Threshold 不達標

沒有 Coverage 報告不能直接斷言 Gate 一定 Fail。還要看 Gate 是否檢查 Coverage、是否有可覆蓋行數、新碼是否達到 Fudge Factor 門檻等。Sonar way 也包含 Issues、Duplications 等條件，不能只看 Coverage 一項。

03 / Gate 怎麼影響 GitHub Actions？

Figure / Gate Fail 傳遞到部署 Job

Compute Engine 完成Quality Gate = PASS / FAIL
↓ Scanner 是否等待 Gate？
Scanner Step Exit Codewait=false：不因 Gate FAIL；wait=true：Gate FAIL 導致 Step Fail
↓ Analyze Job 的結果
Deploy Job 的 needs / if決定是否等待／允許執行部署
整合方法直接影響
sonar.qualitygate.wait=false預設。不等待 Gate；即使 Gate FAIL，也不因此讓 Scanner Fail。
sonar.qualitygate.wait=true輪詢 Server 等待 Gate；Gate FAIL 會讓 Scanner Step Fail，timeout 預設 300 秒。
Quality Gate Check Action掃描與 Gate 查詢拆成獨立 Step；需要任務資訊與認證。
不要把「Non-blocking」做成「Gate 永遠 PASS」。

可以保留真實 Gate FAIL 供觀測，先讓部署不依賴 Gate Job；正式改成 Blocking 時才把 Gate Check 結果納入 needs。注意：即使 wait=false，Token／網路錯誤仍可能讓 Analyze Job Fail；如果 Deploy 依賴 Analyze，也可能被擋。

04 / Lab：讀懂依賴關係

以下示例假設 npm test -- --coverage 可在合成 JS 專案產生 coverage/lcov.info；僅使用 echo 模擬部署，不會實際更新環境。正式使用前必須核對 Action 版本／Runner 相容性，並 pin 經審核的 Action SHA。

name: Sonar Gate Lab
on:
  workflow_dispatch:
jobs:
  analyze:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Produce coverage
        run: |
          npm ci
          npm test -- --coverage
          test -s coverage/lcov.info
      - name: Scan and wait for Gate
        uses: SonarSource/sonarqube-scan-action@v7
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
        with:
          args: >
            -Dsonar.projectKey=demo-web
            -Dsonar.javascript.lcov.reportPaths=coverage/lcov.info
            -Dsonar.qualitygate.wait=true
            -Dsonar.qualitygate.timeout=300
  deploy-lab:
    needs: analyze
    runs-on: ubuntu-latest
    steps:
      - run: echo "Simulation only; no deployment"

此例的 needs: analyze 使示範部署依賴 Analyze Job：當 Gate FAIL 且 wait=true，Analyze Job Fail，Deploy Job 預設會被略過。若僅把 wait 改 false，Gate FAIL 不會造成 Scanner Step Fail；但其他掃描錯誤仍可能阻擋。

05 / 三次實驗應如何記錄？

  1. 成功：執行測試並取得 LCOV、Scanner Exit 0、CE Task SUCCESS，保存 Gate 與 Coverage 指標。
  2. 缺報告：只在 Sandbox 故意寫錯 LCOV Path，查看 Log 與實際指標；不可預先斷言一定 FAIL。
  3. Gate FAIL：在隔離 Project 使用受控違規或自訂 Gate 條件，比較 wait=false 與 true 的 Step Exit Code，並觀察 Deploy Job 是否被 skip。

驗收證據：Checkout SHA、Project Key、Report 路徑、CE Task ID、失敗的 Gate 指標、Scanner Job Exit Code、Deploy Job 結果。沒有做完前，頁面只列「預期」，不把練習寫成實測。

RETRIEVAL / Gate vs CI

Server 顯示 Quality Gate FAIL，但部署 Job 仍然成功；你應優先查哪一層？

下一階段：Lesson 09 將決定 PR Merge、main Push 和 Release Tag 哪個事件應建立權威分析；Lesson 10 再制定正式部署門禁。

06 / 一分鐘回顧

  • Coverage：外部工具產生；Scanner 匯入。
  • Gate：Server 以 Metrics 和門檻判定，不等於 Scanner 是否成功。
  • wait=true：讓 Scanner 等待並因 Gate FAIL 而失敗。
  • needs / if：控制 GitHub Actions 的後續 Job 是否執行。
