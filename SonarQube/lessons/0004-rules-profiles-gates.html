Phase 02 · Lesson 04約 20 分鐘互動門檻實驗

學完要能做到

從一個問題發生的程式碼情境，推導出 Rule → Quality Profile → Issue / Metric → Quality Gate → CI 的因果鏈，並判斷改變規則或 Gate 門檻會產生什麼不同結果。

01 / 假設你想禁止某種程式碼寫法

例如某個語言的程式存在已知易出錯的寫法。你希望 Scanner 找出這種寫法。那系統必須先有一個可執行的判定條件，描述什麼樣的程式碼要被標記。

這個判定條件叫 Rule（規則）。

Rule 是「某種寫法要不要被視為問題」的檢查定義；真正發生在你程式碼某個位置的違規結果，才叫 Issue（問題實例）。

所以一條 Rule 可以在整個 Project 中找出 0 個、1 個或很多個 Issues。不要把「規則數量」誤當成「程式碼問題數量」。

官方提供的是一批 Rules，以及從這批 Rules 選好部分啟用的內建 Quality Profiles。Rule 是檢查定義，不等於「公司自訂規則」；Issue 則是程式碼某處真正被這條 Rule 判定為違規的實例。

02 / 為什麼還需要 Quality Profile？

假設 Java 支援數百條 Rules。你不一定希望每個 Project 都套用全部規則；有的專案重視安全，有的專案會從較小的規則集合開始導入。

因此需要 Quality Profile：它是針對某種語言啟用哪些 Rules的設定組。沒有被啟用的規則，不會以該 Profile 的規則檢查程式碼。

以上是官方 26.10 文件描述。升級自舊版不一定自動改寫既有專案的 Profile 或 default；POC 應先確認所部署的版本與選用規則集。自訂時可 Extend 內建 Profile 以沿用上游規則更新。

Profile 不是只能整個 Instance 共用

Project A 和 Project B 都有 Python，也能選不同的 Python Profile；同一個 Project 的 Python 和 JavaScript 還可各自選 Profile。沒有自訂指派時，用該語言的 Instance Default Profile。官方內建 Profile 不能直接改；可建立自訂 Profile，選擇 Extend（繼承）、Copy（獨立副本） 或 Blank。Project 管理者可到 Project Settings → Quality Profiles 逐語言指定；正常情況下不必在每次 CI 傳入 Profile 名稱。查看設定與差異。

03 / 那 Quality Gate 負責哪一層？

Scanner 跑完有效規則後，會產生 Issues 與其他 Metrics，Server 綜合成 Project 品質資料。但即使你看到了 15 個 Issues，也不能直接推出「分析不合格」——因為組織可能只要求新程式碼不可新增問題。

↓ 可選擇讓 CI 等待並採用結果
GitHub Actions Job工作流程要不要因 Gate 而失敗？

Quality Profile 控制「檢查哪些規則」；Quality Gate 控制「哪些品質指標達到何種門檻才通過」。例如自訂 Gate 可設定「新程式碼 Issues 數量必須為 0」。

Quality Gate 是條件集合，不是總分。

每條條件是「Metric（指標）＋比較運算子＋門檻」，可以檢查 New Code 或 Overall Code 的 Issues、Rating、Coverage、Duplication 等官方支援指標；任一條失敗，整個 Gate 就 FAIL。例如 New Coverage 85% 符合「≥ 80%」，但 New Duplication 5% 不符合「≤ 3%」，因此 Gate FAIL，不會取平均分數。

同理，產生 Issue 並不會自動使 Gate FAIL；需要某條 Gate 條件不達標。Community Build 的 Gate 並不能直接以「指定 Rule Key 一犯就擋」當成一般原生條件；有這種要求應另在 CI 檢查。區分單條 Rule 與 Gate 指標。

停用 Rule 會使這條規則不再產生 Issue；提高 Gate 容忍門檻卻不會讓 Issue 消失，只是允許有問題的結果仍然通過。這兩個治理選項的影響完全不同。

自己想增加一種原本沒有的檢查呢？

從現有 Rules 中啟用一條只是啟用，不是建立新 Rule。若需要全新檢查能力，官方列出三種路線：XPath Rule Template（限支援語言、可在 UI 建 Rule）、Java Plugin（自己開發後在 SonarQube 註冊 Rule）、External Analyzer（在外部判定違規，匯入 Issues）。第三種只有外部 Issues，不會新增可在 Quality Profile 啟停的 Rule，但仍可參與 Gate 指標。

Java Plugin 的檢查邏輯和 Rule Metadata 是不同責任：邏輯判斷哪裡違規，Metadata 記錄 Rule Key、分類／Software Quality、Severity 等；在 Plugin 註冊時交給 SonarQube。UI 可在 Profile 啟用 Rule、調整可覆寫的 Severity／參數，不等於 UI 一定能更改 Plugin 所宣告的原始分類；XPath 模板型 Custom Rule 則可在 UI Create 時定義並編輯 Metadata。查看四種做法與 Metadata。

05 / New Code 與 Overall Code 的 Gate 差異

假設現在有 20 個舊 Issue，但是這次定義的 New Code 0 個新 Issue：

假設自訂 Gate 條件結果為什麼
Overall Issues ≤ 0FAIL全專案仍有 20 個問題。
New Issues ≤ 0PASS新程式碼沒有新增問題。

上表只比較單一 Issues 條件。真實的 Sonar way Gate 還有 Coverage、Duplication 等條件；任何一項失敗，整體 Gate 就可能 FAIL。因此不能拿這個例子宣稱「現實專案一定 PASS」。

另外，Coverage 不是 Scanner 自己跑測試得來；需要先匯入外部測試工具的報告。若實際採用新程式碼 Coverage 門檻，要先確定報告存在，並注意官方對少量新增行數的忽略機制（Fudge Factor）。

既往不咎與每次 Commit 掃描：不同的開關

New Code Definition 決定哪些新增或修改程式碼屬於 New Code；CI Trigger 決定何時掃描；Quality Gate / CI 策略 決定是否阻擋。固定導入基準與每次 Commit 重掃並不衝突。

Figure 05 / 固定起點，持續檢查

分析 A：導入基準A 以前舊 Issues 不以新碼 Gate 阻擋
↓ 以 A 作為固定 New Code 起點
Commit B → 掃描 BB 新增 1 個未修 Issue → New Issues Gate FAIL
↓ C 仍使用固定基準 A
Commit C → 掃描 CB 的 Issue 尚未修復，仍須受治理

合成例子：箭頭表示時間先後，而不是每次改寫基準。

如果你每次把比較起點移到上一個 Commit，先前引入但尚未修的問題可能會離開 New Code 範圍，因此不符合「導入後新問題持續受管制」的目的。

New Code Definition起算方式應注意
Specific analysis指定已完成的一次分析固定起點；目前 Community Build 官方要求透過 Web API 設定，不是直接在 Project UI 選取，也不能填未來時間或 Git SHA。
Number of days最近 N 天滑動時間窗；過期未修 Issue 可能離開 New Code。
Previous version本次 Project Version 開始隨版本更新，不等於上一個 Commit。
Reference branch相對參照分支的差異不能推論免費版有原生 PR／多分支分析。

「明天中午開始既往不咎」可規劃在切換點完成一次分析，以那次分析作固定基準，再讓 CI 從預定時點採用 Gate；不是直接輸入「明天 12:00」就會自動建立歷史基準。New Code 策略細節 · Release Version、Number of Days、Specific Analysis 詳細推演。

Coverage 與 GitHub Actions 的另外兩道邊界

Coverage 需由測試工具產出報告，Scanner 再匯入；Scanner 不會自行執行測試。沒有 Coverage 報告時不能一概說「一定 FAIL」：還要考慮可計算的 Coverage 指標、Gate 條件、新碼可覆蓋行數與 Fudge Factor。

GitHub Actions 必須接收 Gate 判定才可能阻擋後續部署，例如 Scanner 加 -Dsonar.qualitygate.wait=true，或另設查詢 Gate 的步驟。下一個 Job 還需要 needs 等依賴。查看 Coverage / CI 實際資料流。

選讀：版本差異與 MQR / Standard Experience（不影響本堂主要目標）

分類方式會因模式與版本不同

SonarQube 介面可選擇 Standard Experience 或 Multi-Quality Rule（MQR）模式：前者按 Bug / Vulnerability / Code Smell 等 Rule Type 分類；後者可讓同一 Rule 同時影響 Reliability / Security / Maintainability 等多個品質面向，而且各有 Severity。這並不等於產生多個 Issues。切換模式會影響 Issue 分類、Severity 與部分 Gate 指標，POC 中不要在未確認模式時直接複製舊教學數據。

不同版本的預設 Profile、Gate 條件及 Security Hotspot 呈現可能不同；不要把其他版本的畫面或條件當成已測事實。實驗時以部署版本、實際 Quality Gate 頁面與對應官方文件交叉核對。

06 / 本堂結論與下一階段

  • Rule 是「條件」；Issue 是「在程式碼某處被判定違規的一次具體結果」。
  • Quality Profile 選定「哪些 Rules 有效」，通常按語言管理。
  • Quality Gate 使用 Issues 與其他 Metrics 判斷 PASS / FAIL，可以只要求 New Code 達標。
  • Quality Gate FAIL 不必然等於部署失敗；CI 要如何採用它，需要另外設計。
  • 新增 Rule 可用 XPath Template 或 Java Plugin，External Analyzer 則匯入 Issues。
  • New Code 基準與 CI 掃描頻率可分開設定；固定導入基準同時逐次掃描。
  • Coverage 來自外部測試報告；要阻擋部署需 CI 等候或查詢 Gate。

有了這個基礎，便可以把規則與品質判定接入 CI。若已具備核准的測試 Server、Project 與 Token，可依目前學習安排先閱讀 Phase 04 / Lesson 07；Phase 03 的詳細 POC 教材暫緩撰寫，不等於前置環境已驗收。
