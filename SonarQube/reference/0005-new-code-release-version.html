REFERENCE 05 / RELEASE GOVERNANCE

一個 Release Tag，
三個不同的角色。

Git Tag 鎖定發布的 Git Commit；sonar.projectVersion 標記這次分析對應的軟體版本；New Code Definition 則決定哪一部分程式碼接受「新程式碼」的品質要求。這三者可以搭配，但不是同一種設定。

先記得這條因果鏈

Git Tag → Checkout CommitScanner 看到哪份程式碼
↓ Scanner 提交完整分析與版本標記
Project Key + Project Version分析歸到哪個 Project、記錄什麼發布版本
↓ Server 根據 New Code Definition 選定範圍
Quality Gate只針對選定的 New Code／Overall 指標判定 PASS 或 FAIL

01 / Project Version 究竟在記錄什麼？

sonar.projectVersion=v1.2.0 是「這次分析對應軟體版本 v1.2.0」的標記。Project Activity 能顯示版本事件、品質 Gate 與指標歷史，協助查找哪個版本的分析開始出現品質變化；它不會主動做 Git Tag diff，也不是任意時刻可重現的完整舊 Dashboard。

# Tag workflow 已 checkout 該 Tag 的 Commit 之後
sonar-scanner \
  -Dsonar.projectKey=demo-api \
  -Dsonar.projectVersion="$RELEASE_TAG"

對「每次正式 Release 打 Tag」的工作流程，將正式 Tag 值寫入 Project Version 是有意義的；不要把每次 CI Run Number 當版本。同一版本內的日常掃描可以使用相同版本值。Maven／Gradle Scanner 可能從 Build Metadata 推導版本，應核對實際送出的值。官方分析參數、Activity。

02 / 三種 New Code 模式的起點不是同一件事

設定New Code Period 起點適合問什麼？
Previous version目前 Project Version首次被分析的日期這個版本開發週期以來，新程式碼品質如何？
Number of days分析日往前 N 天的日期最近 7／30 天修改的程式碼品質如何？
Specific analysis明確指定某次既有分析的日期自我設定的固定導入基準以來，品質如何？

以上是官方定義的日期期間，不等於要求 Scanner 只看期間內 Commit，也不等於直接執行 git diff。完整掃描仍處理目前 Checkout 程式碼；SonarQube 利用分析結果與 SCM 資訊計算 New Code 指標。官方 New Code 定義。

Previous Version：版本切換不等於上一個 Release 的 Git Diff

分析傳入版本期間起點的意義
11/01 Av1.0首次分析 v1.0
11/08 Bv1.1首次分析 v1.1，成為此版本期間的起點
11/15 Cv1.1沿用 v1.1 的 11/08 起點
11/22 Dv1.2首次分析 v1.2，重新劃定期間
Release Tag-only 掃描的陷阱

若只在成品 Tag 出現之後，第一次把新版本值送入 SonarQube，這次分析同時就是新版本期間起點；不能因此斷言當次 Quality Gate 已精確檢查「上一個 Release Tag → 這個 Tag」的全部變更。若要驗證兩個 Tag 的 Git 差異，需有另一個明確比對方式或經過驗證的分析時序。

Number of Days：日期怎麼滾動？

假設 11/15 分析，Number of Days = 7，起點就是 11/08；到 11/16 分析，起點變成 11/09。每天向前滾動一天，並不是拿「七個 Commit 前」或「七天前的 Git SHA」做固定比較。

Figure / 同一個 7 天設定，兩天的期間

11/15 掃描期間：11/08 → 11/15
↓ 日期前進 1 天，設定不變
11/16 掃描期間：11/09 → 11/16

箭頭是時間推進，不代表 SonarQube 從分析歷史挑一筆最接近的 Git Commit。官方以期間起訖日期定義 New Code，Issue／變更的定位依 SCM 與分析資料計算。

適用情境：持續交付、沒有固定版本週期的服務，團隊只想關注「近期改動」。代價是未修的 New Issue 在超過時間窗口後可能離開 New Code 指標，不適合要求「導入日起所有新問題永遠維持在新碼門檻」的政策。

Specific Analysis：固定既往不咎的界線

先完成導入基準 A 的分析（等待 Compute Engine 完成），再用 Web API api/new_code_periods/set 指定那次分析作為起點。B、C、D 後續重掃但仍以 A 為固定起點；除非明確修改 New Code Definition，基準不隨 Tag、日期或新的 Scan 自行漂移。

不要把 Specific Analysis 當成填 Git SHA 或未來日期。

目前 Community Build 官方文件表示，Specific Analysis 要透過 Web API 設定，Project UI 並不提供直接選取。操作前應從該 Server 的 Web API 文件核對參數與合法分析 ID。

03 / 真實治理的 Edge Case：Issue 沒修，Gate 卻 PASS

假設導入時有 20 個歷史 Issues；版本 v1.1 又新增 Issue A，因為仍是 Non-blocking 所以先部署；v1.2 沒再新增，但 A 仍沒修。

政策v1.2 的 New Code GateOverall Code
固定 Specific Analysis 在導入 A若 Issue A 仍落在新碼範圍，繼續 FAILA 仍存在
每版更換 Previous Version 期間A 可能不再屬於此版新碼，可能 PASSA 仍存在

這是條件式案例，不是承諾 SonarQube 每個 Issue 都以相同方式重新分類。New Code 的行數、Issue 日期、SCM blame、Rule 與 Gate 條件，都可能影響真實判定。**不在 New Code ≠ 沒有 Issue；只代表它未必再觸發僅檢查 New Code 的 Gate。**

04 / 實務選擇與資料責任

若企業政策是「只有導入前舊問題豁免；之後所有新問題持續受管」，使用固定 Specific Analysis 作為新碼起點最直覺；CI 可以照樣每個 Release Tag 跑掃描並更新 sonar.projectVersion，版本標籤與固定基準不衝突。若政策是「每個新開發週期重新計算 New Code」，則評估 Previous Version 與分析的切換時點。

為了真正追溯每個發布版本，CI 還應保存 Git Tag、Commit SHA、Project Key、Project Version、CE Task ID、Gate 結果 的關聯；Project Activity 有歷史趨勢，但不是永久保存完整每版 Dashboard。Housekeeping 會清理部分舊 Snapshot，尤其要避免用每次 Build Number 不斷製造版本事件。官方 Housekeeping。

自我檢驗

當 v1.1 新增 Issue A，到了 v1.2 還沒修，你希望它繼續導致 New Code Gate FAIL 嗎？先決定治理政策，再選 New Code Definition；不要先選下拉選單才倒推政策。
