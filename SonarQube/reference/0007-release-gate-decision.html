REFERENCE 07 / CI POLICY

Release 要過 Gate，
先證明是哪一次分析。

這份速查把 GitHub 事件、Checkout SHA、SonarQube Project、Quality Gate 和 Deployment Job 連成同一個決策模型。它是制定規範的輔助表，不是已對任何正式 Repo 啟用的阻擋政策。

01 / 事件選擇與分析身分

要回答的事輸入與選擇最易忽略的風險
什麼時候掃？push main、pull_request closed + merged、push tags同一個 Commit 被多個 Trigger 重掃
掃哪個 Commit？直接檢查 git rev-parse HEADCheckout main HEAD 不是當時的 PR merge 或 Release Tag
結果放哪裡？sonar.projectKey 與 Server Main BranchCommunity 不是多分支系統，重掃可能更新同 Project 的最新結果
哪個 Release？Tag → sonar.projectVersion標版本≠分析上一版本的 Git diff，也不提供舊版完整 Dashboard 的永久快照
是否阻擋？CE Task → Gate → CI Job → Deploy needsDashboard 顯示 PASS 也可能不是該 SHA 的結果

主分支單一分析政策

選 push main 為唯一權威分析觸發；PR 開啟時執行 Build／Test／Lint，直到合併後再掃 SonarQube Main Project。這是 Community Build 較直接的導入起點。

僅 Release Tag 分析政策

在 push tags 事件 Checkout 該 Tag 的 Commit，傳入該 Tag 至 sonar.projectVersion。限制是沒有每次 main 更新的品質訊號，且 Tag 不一定是 main 最新 SHA；必須核對發布流程的 Commit 身分與版本順序。

獨立 PR Merge 後掃描政策

若使用 pull_request: closed，同時要求 merged == true 且 base.ref == main。確認 merge_commit_sha 確實對應合併結果；若和 push main 同時使用，先決定去重／優先順序。不要把此事件當成原生 PR Quality Gate。

02 / 同一個 Release，Gate 與部署如何決策？

分析狀態ObserveBlocking
CE SUCCESS，Gate PASS，SHA 相符記錄結果允許進入後續既有 Gate；不等於立即部署
CE SUCCESS，Gate FAIL記錄問題與 Owner，先不新增部署阻擋阻擋；依核准的例外流程處理
Scanner／Token／TLS 失敗標示 Scan Failure；部署是否繼續依觀測政策沒有可信 Gate，採事前核准的 Fail Policy
CE FAILED／Gate Timeout標示 Unknown；不應標為 PASS預設暫停／重試；若允許例外需授權與追蹤
Gate PASS 但不是這個 Tag SHA記錄版本身分不符不可視為這個 Release 已通過

本表是建議的治理範型，不是 SonarQube 或 GitHub Actions 自動內建的 Fail-open／Fail-closed 政策。需要由工作流程、批准機制與發版規範實現。

03 / 具體設定在哪一層？

Figure / 品質判定的傳遞方向

SonarScanner提交分析；預設 sonar.qualitygate.wait=false
↓ SonarQube CE 計算 Gate
Quality Gate = PASS / FAILProfile 決定查哪些 Rules；Gate 決定哪些 Metrics 未達標
↓ wait=true 或獨立 Gate Check 將結果轉成 CI Status
GitHub Actions needs / if當部署 Job 依賴 Gate Job 成功，FAIL 才會阻擋

對已有建置、E2E、Secret Scanning 等 Gate 的流程，新增 SonarQube 的依賴前，先確認所有既有條件的 needs 與 if，避免因 always()、continue-on-error 或獨立 Workflow 邊界造成意外放行。wait=true 的預設 Timeout 為 300 秒，是等 Gate 的時間上限，不是分析一定需要 300 秒。

04 / Release Evidence 最小契約

欄位為何記錄？
Repository／Project Key確定分析被存到哪個邏輯 Project
Trigger／Workflow Run ID確定本次檢查的執行來源
Git Tag／Commit SHA確定發布的是哪份不可變的程式碼
sonar.projectVersion可在 SonarQube Activity 追蹤的版本標籤
CE Task ID／Status查明 Report 是否已完成背景處理
Gate Status／失敗指標保留發布時採用的品質決策證據
部署 Job 結果／例外紀錄追查哪個 Policy 允許或阻止發布

查詢 Gate 不應只抓Project 現在最新的狀態就直接對舊版 Tag 放行；若多個分析同時完成，可能誤認另一個 Commit 的 PASS。應讓本次 CI 掃描與 CE Task 綁定，確認 Task 完成並保留當次 Gate Result；使用 scanner wait 或官方 Gate Check 的實際行為，在 POC 中驗證。

05 / 上線前最少四個 Failure Injection

  1. 建一個受控新 Issue，CE 完成但 Gate FAIL：確認 Observe 不新增阻擋、Enforce 會讓部署 Job skipped。
  2. 故意提供無效 Token：Scanner Fail 應顯示認證失敗，不得記為 Quality Gate PASS。
  3. 在測試環境模擬 CE 延遲／等待超時：記錄 Timeout、重試上限和人工介入。
  4. 重新分析較舊 Tag：確認查到的版本／SHA／Task 是自己要發布的版本，不用最新 Dashboard 取代證據。
例外是業務與資安決策，不是默默開關參數。

必須定義核准人、服務範圍、有效期限、風險理由、補驗方式與稽核記錄；不能用永久 continue-on-error: true 代替例外管理。
