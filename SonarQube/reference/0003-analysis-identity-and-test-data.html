REFERENCE / ANALYSIS IDENTITY

Scanner 與分析歸屬速查

同一份原始碼可由多種事件觸發掃描；真正決定結果在哪裡的，是 Checkout 的內容、Project Key、分析身分，以及 Server 版本能力。此頁是按問題查找的參考資料，不代表已完成實際 POC。

01 / 四個問題先分開

問題由誰決定？
什麼時候掃？GitHub Actions 的 push、pull_request、tag 或手動觸發；也可完全不經 GitHub Actions。
實際掃什麼？Runner 上 actions/checkout 取得的 Commit / 工作目錄檔案，不是 Dashboard 上的分支名稱。
分析要放哪？sonar.projectKey 找到 Project；有無 branch/PR analysis 身分，決定是否要求獨立分支／PR 結果。
結果何時可見？Scanner 提交 Report → Server Compute Engine 完成 Background Task → Dashboard / Quality Gate 更新。

02 / 最小參數對照

Scanner 參數作用與限制
sonar.projectKey指定 SonarQube Project；不表示來源 Git Branch。
沒有 branch / PR 身分一般主分支分析；Community Build 只有此原生儲存維度。同一 Key 反覆掃不同 Commit 會更動同一分析狀態。
sonar.branch.name要求獨立 Branch Analysis，原生 Community Build 不支援。
sonar.pullrequest.key
sonar.pullrequest.branch
sonar.pullrequest.base		要求獨立 PR Analysis，原生 Community Build 不支援。商業版可依 CI 自動辨識，但不等於 Community 也會自動處理。

這裡的「分析身分」是解釋用詞，不是 SonarQube UI 有一個名為 Analysis Mode 的切換鈕。錯誤訊息與處理階段應以該版本實測日誌為準。

同一 Repo，兩個 Project

Figure / 兩份獨立追蹤不是原生多分支

Repository：demo-webmain 與 develop 兩個 Git Branch
↓ 各自 Checkout 與執行 Scanner
Project Key：demo-web-main維護 main 的一份主分支狀態
Project Key：demo-web-develop維護 develop 的另一份主分支狀態

兩個 Project 各有設定、Issues、Gate 與歷史；不是一個 Project 內可切換兩條 Branch。

03 / Scanner 是執行程式，不是 CI Pipeline

CI Workflow 決定步驟，Runner 提供執行環境，SonarScanner 讀取 Checkout 的程式碼並提交分析報告。可選擇下載／安裝 SonarScanner CLI、在容器中執行 CLI、使用官方 Scan GitHub Action，或選 Maven、Gradle、.NET、NPM 等建置系統對應的 Scanner。這些不是 Community 與商業版的主要差異。

# 合成範例：執行環境已有 sonar-scanner
sonar-scanner -Dsonar.projectKey=demo-web
# 認證和 Server URL 由受保護的 CI 環境變數提供

Scanner 成功提交報告，不代表 Compute Engine 已經完成品質計算；可到 Background Tasks 觀察，再讀取 Quality Gate。Dashboard 與 API 由 SonarQube Server 提供，不需另外部署一個 Dashboard。

04 / GitHub PR Checkout 與 SonarQube PR Analysis 的差別

對開啟且可合併的 PR，GitHub Actions pull_request 的預設 GITHUB_REF 通常是 refs/pull/N/merge，因此預設 Checkout 取得的是 GitHub 產生的模擬合併 Commit；明確指定 PR 的 head.sha 才是直接取 Feature Branch HEAD。模擬合併 Checkout 只是 GitHub 的行為，不能據此宣稱 SonarQube 已完成原生 PR Analysis。

商業版 PR Analysis 要回答的是「此 PR 相對目標分支引入哪些 New Code 問題、New Code Quality Gate 是否通過？」它不是僅分析最後一個 Commit，而是依來源與目標分支的差異界定範圍。Branch Analysis 則是保存某分支的長期品質狀態，不等於有 PR 專屬的比較結果與門禁。

兩邊都繼續前進時怎麼辦？

Feature Branch 與 main 的 Commit 可能持續變動；PR 分析的品質結果代表該次分析所見的來源與目標基準，不等於永久保證未來合併版本無整合問題。要確保最新合併結果可運作，仍需依當前 base/head 重新執行建置、測試或 Merge Queue 驗證。SonarQube 官方亦要求 PR 分析前具備目標分支的歷史資料。

05 / Project 建立與主分支名稱

可以在 Server 建立 Local Project、從 DevOps 平台匯入、呼叫 Web API，或在有 Create Projects 權限時由第一次掃描建立。Project Key 決定歸屬；Main Branch 名稱是 Server 的分支標籤，並不指揮 Runner 去 Checkout。初始化名稱與重新命名 UI 隨版本與建立方式而異，不應假設「第一次掃描的 Git Branch 自動成為名稱」，也不應把商業版的 Branch UI 操作當成 Community 通用做法。

06 / 外部測試：可匯入與不可取代的資料

資料SonarQube 的角色
Coverage（行／分支覆蓋率）先由測試或 coverage 工具輸出相容報告；Scanner 匯入，例如 Generic Coverage 用 sonar.coverageReportPaths。
Test Execution（測試數、失敗／略過、耗時）外部報告需為支援格式。Generic Test Execution 使用 sonar.testExecutionReportPaths；file path 應能對應專案的測試檔。
Playwright E2E可評估將可對應的執行統計轉成 Generic 格式；這不會自動產生原始碼 Coverage，也不會提供完整 Allure 式逐步報表。
k6／JMeter 壓力測試RPS、p95 latency、吞吐量等不是 SonarQube 內建的負載測試趨勢介面；應保留於負載測試工具、Grafana 等合適系統。
資料流要對時機：

先執行測試產生報告 → Scanner 讀到相容檔案 → 上傳分析 → Compute Engine 處理 → Dashboard 查詢。不要把測試跑完後獨立產生的檔案，誤以為 SonarQube 會自動同步抓取。
