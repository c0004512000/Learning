REFERENCE / RULE GOVERNANCE

Rule、Profile、Gate 與 New Code 速查

Lesson 04 用來建立因果關係；這份 Reference 提供操作時需回查的分工、限制與設定路線。示意皆未宣稱在真實 Server 完成實測。

01 / Quality Profile：如何建立與指派？

SonarQube 針對每種程式語言提供一批 Rules，也提供預先選好啟用規則的內建 Quality Profiles。官方內建 Profile 不直接修改；要自訂時，可在 Quality Profiles → Create 選擇：

方式效果
Extend繼承上游已啟用規則與後續更新，再調整自訂部分。
Copy複製當下規則組，之後獨立管理，不隨 Parent 更新。
Blank建立空白規則組，只啟用刻意選定的規則。

Project A 可以在 Python 使用官方 Profile，Project B 的 Python 使用自訂；同一個 Project 的 Python 與 JavaScript 也可各選自己的 Profile。Project 管理者到 Project Settings → Quality Profiles，替指定語言選擇 Profile；沒指定時用 Instance 該語言的 Default Profile。Scanner 只需將報告送到由 sonar.projectKey 識別的 Project，不需每次傳入 Profile 名稱；CI 若藉 Web API 修改設定，會影響 Server 共用狀態。

官方建立 Profile · 官方 Project 指派

02 / 新增「檢查能力」有哪些方式？

方式是否新增由 Profile 管理的 Rule？
啟用現有 Rule否；只是啟用 SonarQube 已有規則。
XPath Template是；在支援語言的 UI 用 XPath 建立 Custom Rule。
Java Plugin是；Plugin 註冊新的 Rule 與檢查邏輯。
External Analyzer否；外部自己檢查後匯入 Issues，這些 Issues 可參與 Gate 指標。

XPath 是什麼？

XPath = XML Path Language，可用條件選取 XML 元素。例如：

<prices>
  <price currency="USD">100</price>
  <price currency="TWD">3000</price>
</prices>

//price[@currency!="USD"] 找到 TWD 的 price 節點。若 XML Analyzer 有 XPath Rule Template，可在 Rules → XML → Show Templates Only → Create 設 XPath 與 Metadata，再啟用於 Profile。不是每種程式語言都支援此模式；Python 不支援 XPath 模板。

Java Plugin 如何連到 Rule？

檢查邏輯負責判定哪段程式違規，Rule Metadata 描述 Rule Key、名稱、分類（Type / Software Quality）及 Severity 等。Plugin 使用 Java API 註冊 Rule，將兩者連結；檢查邏輯不需要自行讀取 Severity 變數。以 Python 為例，Java Plugin 可使用官方 Python Analyzer 的 AST Visitor 檢查 Python 語法樹。建置 Java Plugin → 宣告 Rule 與 Metadata → 打包部署 JAR 到 Server → 在 UI 將新 Rule 啟用到 Profile；不是 JavaScript Plugin 或 Dashboard 上傳任意邏輯。

Metadata 何時可以改？

官方現有 Rule 的原始 Type 由 Analyzer 定義；透過 Quality Profile 可以調整可覆寫的 Severity 與參數，而不是重寫它的原始分類。Java Plugin 的原始 Rule Metadata 通常在開發／註冊 Rule 時定義，若要改這些原始屬性，通常回到 Plugin 定義並重新部署。XPath 模板型 Custom Rule 不同：在 SonarQube UI Create 時填入 Metadata，官方也允許後續編輯此類 Custom Rule。

Standard Experience 使用 Bug、Vulnerability、Code Smell 等 Rule Type；MQR 可讓一條 Rule 影響 Reliability、Security、Maintainability 多個 Software Quality，並設定各自 Severity，不代表產生多個 Issues。MQR 裡可另外設定 Coding Attribute Category（例如 Consistency），不能與 Bug Type 混為一談。官方 Rule Metadata / MQR 文件。

External Analyzer 交付的是什麼？

CI 執行外部檢查器 → 自行判定違規
                    ↓ 產出 Generic Issue / SARIF
Scanner 匯入報告 → SonarQube 顯示 External Issues
                    ↓
                 Gate 對相關指標評估

SonarQube 只接收外部工具已判定的 Issues，不會替外部工具執行規則；External Rules 不會出現在 SonarQube 的 Rules 頁面與 Quality Profiles 內。官方三條擴充路線 · 外部 Issue 限制。

03 / Gate 能不能選單一 Rule 一犯就 FAIL？

Community Build 的一般 Quality Gate 使用「Metric + 比較運算子 + 門檻」，例如 New Issues > 0 ⇒ FAIL。若外部 Issues 被相關 Metric 計入，也會影響 Gate；但這不是可以在 Community Gate UI 指定某個 External Rule Key。官方的 Prioritized Rules Gate Condition 為 SonarQube Server 版別功能，不能直接假設 Community Build 具備。若必須單獨攔某條 Rule，可在 CI 額外依 Rule ID 或外部分析器的結果實作獨立阻擋；若只看某 Severity，其他同 Severity Rule 也會一起影響結果。

04 / New Code Definition：起點到底在哪？

Overall Code 是全程式碼；New Code 是相對某基準新增／修改的程式碼。不是「只掃改動檔案」、不是「永遠跟前一 Commit 比」，更不是「免費版原生 PR Analysis」。

選項起點語意
Specific analysis固定在已存在的一次分析；現行 Community Build 官方規定使用 Web API 設定，Project UI 無法直接選此項；不是輸入未來時間或 Git SHA。
Number of days最近 N 天滑動時間窗；過期未修問題可能不再算 New Code。
Previous version以 Project Version 變更為週期，不隨每次 Commit 移動。
Reference branch相對參照分支的差異；和時間型基準不同，不代表支援原生 PR／多分支分析。

合成情境：明天中午導入，舊問題不擋

  1. 導入時先對受管理的程式碼版本做一次成功分析，確認 Compute Engine 處理完成。
  2. 把這次分析作為 Specific analysis 基準（目前需以 api/new_code_periods/set 設定，依部署版核對權限與參數）。
  3. 選擇只對 New Code 適用的 Gate 條件，例如 New Issues = 0，舊 Overall Issues 不作阻擋。
  4. GitHub Actions 仍可對每次 Commit 執行完整 Scanner 並採用 Gate，不用每次改變 New Code 基準。
為何不用上一個 Commit 當基準？

A 是導入基準、B 產生一個未修 Issue、C 新增無關程式。若把基準從 A 移到 B，B 的問題可能離開此次 New Code 範圍；若固定 A，B 的問題仍屬導入後要管理的問題。

官方 New Code · Specific analysis 設定途徑。

05 / Coverage 與 CI Gate 怎麼串？

Coverage 要由外部測試工具先執行、產出相容 Coverage Report，然後 Scanner 匯入；Test Execution 與 Coverage 不是同一份報告。缺 Coverage 報告不能概括為「Gate 一定 FAIL」，仍需看 New Code 可覆蓋行數、門檻與 Fudge Factor（官方預設小變更時可能忽略 Coverage / Duplication 門檻）。

CI 測試 → Coverage Report → Scanner 匯入 → Server 計算 Gate
                                              ↓
                                         CI 等候／查詢 Gate
                                              ↓
                                            後續 Job
sonar-scanner -Dsonar.projectKey=demo-web -Dsonar.qualitygate.wait=true

Scanner 設 sonar.qualitygate.wait=true 會等 Gate 並在 FAIL 時回報失敗；也可用獨立 CI 步驟查 Gate。要真正擋部署，下一個 GitHub Actions Job 還需以 needs 等設定依賴該檢查步驟；Scanner 只是成功提交分析報告並不足以阻擋。

Coverage 官方資料流 · Gate 等待參數
