Stage A / 最小 POC，先證明分析鏈路

要做什麼應有的驗證證據
用核准的實驗環境啟動 Community BuildUI 可以登入；記錄 image 版本、資源及啟動 log
建立測試 Project、建立分析 TokenProject Key、Token 權限、保管方式皆已確認；不公開 Token
對 synthetic repo 執行 ScannerScanner report submission 成功、Background Task 完成
查看 Dashboard能定位 Issue、Quality Gate 與 analysis timestamp
刻意加入可重現的規則違反Issue / Gate 行為可被再次觀察，而非只看見漂亮截圖

實驗性單節點 Docker 可以使用 H2 做短暫功能驗證；正式部署不能依賴 H2，應使用支援的外部資料庫。使用前需先檢查 Docker 版本、系統核心參數與當前官方 image tag。

Stage B / GitHub Actions POC

先建立獨立、手動觸發、不影響 Production的 workflow。下面是針對具備相容 Runner 的簡化示意；實際 GitHub Enterprise／企業 Runner 需先確認能連到 SonarQube Server 與外部 Action 來源，必要時需走已核准的鏡像或內部 Action 路徑。

name: SonarQube POC
on:
  workflow_dispatch:

jobs:
  sonar:
    runs-on: self-hosted # 依實際 label 修改
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Analyze
        uses: SonarSource/sonarqube-scan-action@v8.3.0
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
        with:
          args: >
            -Dsonar.projectKey=demo-project
            -Dsonar.sources=src
            -Dsonar.qualitygate.wait=true
不要直接複製到公司部署 workflow。

這是供理解與 POC 調整的例子，僅適合對應語言的 scanner 配置。Maven/Gradle/.NET 應使用各自的分析方式。正式使用需審查 Action 版本 pinning、可用來源、權限、Token、CA chain、build 產物與 branch 限制。

失敗注入：如何分辨不同失敗？
  • Runner → Server 無法連線：先看 DNS / Firewall / Proxy / TLS CA；不應宣稱是品質不合格。
  • Token 失效：API 回應授權問題；不等同 Scanner 找到漏洞。
  • Scanner 成功、Gate 失敗：分析已完成，品質規則決策為 fail。
  • Coverage 為 0 / 缺失：先確認測試工具是否產生報告，以及 Scanner 取用的路徑是否正確。
  • Dashboard 舊結果：檢查 Background Tasks、Project Key、執行版本與 branch。

Stage C / 與既有 CI/CD 的整合策略

你們既有的典型流程可概念化為 build → deploy → E2E，並有獨立的 Secret Scanning 與 Production Release Gate。最初不要改變既有 Gate 的實際語意；可先在主分支合併後的獨立 job做非阻擋分析，再決定是否需要品質阻擋。

策略優點風險／限制
主分支合併後掃描符合免費版 main branch 模型、較容易接入問題在合併後才被發現
放入 Release tag 流程可建立版本發布前品質檢查免費版沒有原生獨立 tag / 多分支分析；不要假定每個 tag 有獨立分析快照
直接當 PR Gate理想上能提早攔截免費版缺少原生 PR Analysis / Decoration；需另行設計，不應假設等同付費版
所有服務統一阻擋標準一致初期誤報、Legacy Code、Runner 時間與不可用風險較高

Stage D / K8s 維運與 rollout

  1. 盤點 Helm Chart、社內容器映像政策、Image registry、Namespace、CPU/RAM 與版本升級路徑。
  2. 決定外部 PostgreSQL、備份／回復驗證、PVC 用途、Search index、容量觀測與故障處理責任。
  3. 驗證 Ingress / TLS / GitHub Runner → Server 網路及 CA trust chain；不要用略過憑證驗證取代修復。
  4. 定義 Token 權限、保管、rotation、RBAC、存取日誌與 SSO 需求（依免費版能力評估）。
  5. 選擇語言多樣的 pilot，記錄每次掃描時間、Issue 噪音、Gate 失敗率、失敗處理與例外政策。
  6. 確認可靠性與開發體驗後，才決定是否把 check 納入可阻擋部署的依賴鏈。

公司實際 repo 的 workflow YAML 尚未做完整審查，這份文件的 GitHub Actions 整合點是根據既有 CI/CD 模式制定的待驗證假設。
