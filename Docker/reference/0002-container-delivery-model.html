REFERENCE 02 / WHY CONTAINERIZATION?

Containerization 的價值，
到底固定了什麼？

不要把 Container 想成「任何環境都會自動相同」。它主要改變的是應用程式與依賴的交付方式：先建構可識別的 Image Artifact，再讓各環境使用它。

三種常見部署問題

Dependency Conflict（相依衝突）
不同服務依賴同一台主機全域 Runtime／System Libraries，升級其中一個可能影響另一個。Container 能封裝許多 User-space 依賴；Python venv 等工具也可解決其中部分需求。
Environment Drift（環境漂移）
開發、CI、Stage、Production 的套件、Runtime、設定逐漸不同；即使使用相同 Source Code，重裝結果仍可能不同。
Artifact Traceability（產物追溯）
若只有 Git Commit，卻不知道實際執行的建構結果或相依內容，故障時很難確定「當時在跑哪一份」。

Build Once, Deploy the Artifact

Tag、Digest、Image：最容易混淆的三個東西

Image

已建構、可用來建立 Container 的模板，包含檔案與 Image Configuration。

Tag：orders-api:1.2.3

方便人類辨識的名稱，但 Registry 若允許重新指派，1.2.3 仍可能指向新的 Image。

Digest：sha256:…

依內容產生的摘要識別，能在部署時鎖定預期 Image 內容。跨 CPU 架構時還需理解 Image Index / 平台對應，但不影響「Tag 可變、Digest 識別內容」的基礎規則。

排查問題：先確認哪個邊界不同

  1. Expected state：Stage 與 Prod 應使用同一個經 CI 測試的 Image 內容。
  2. Observed state：Prod 報錯，先核對 Image Digest，再核對 Runtime 設定與外部依賴。
  3. Failure path：Digest 不同 → 查建構／發佈／Tag 指向；Digest 相同 → 再查 Environment Variables、Secrets、DB Schema、Network、Host 條件以及非環境相關的程式問題。

注意：Digest 相同不代表所有問題都來自外部環境，也不能推出程式本身沒有 Bug；它只是縮小了要調查的差異範圍。

不適合直接當成 Container 的功勞

自動修復資料庫、保證安全隔離、跨所有 OS／CPU 架構無條件執行、確保每次 Build 同樣結果、保證 Rollback 成功：這些都需要額外設計或驗證。
