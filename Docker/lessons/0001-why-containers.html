Docker Fundamentals · Lesson 01

同一支 API，為什麼搬到 Server 就跑不起來？

你在開發機用 node server.js 啟動庫存 API，打 /health 回傳 200。你把同一份程式碼交給同事部署，他在新的 Linux Server 上輸入一模一樣的命令，卻得到 node: command not found。

讀完這章，你會用這次部署解釋兩件事：Image 隨部署帶走什麼，以及程式在 VM 和 Container 裡各由誰負責執行。

把程式跑起來，需要哪些東西？

node server.js 實際上請主機執行兩樣東西：先找到 node 這個可執行檔，再由它讀取並執行 server.js。node 是這支 JavaScript 程式的執行環境，也叫 runtime。第一個錯誤代表這條命令找不到它，這時 API 還沒開始執行。

同事裝好相容的 Node.js，再跑一次。這次 Node.js 啟動了，卻回報找不到 express。程式碼寫了要用 Express，部署時也得讓它找得到實際安裝的套件。逐台安裝能修好這次部署，但下一台機器又得重新準備；若有人安裝不同版本，結果也可能跟著變。

Image 是事先準備好的檔案與啟動設定。以這支 API 為例，它可以帶著程式碼、Node.js、Express 和預設的啟動命令。Container 是從 Image 建立出來的一個執行環境。啟動它時，裡面的 API 才成為一個實際執行中的 Process（行程）。同一份 Image 可以建立多個 Container，每個都能各自啟停。 Docker 官方說明

先預測，再打開結果

團隊讓 /health 同時檢查資料庫。Test 和 Prod 都部署同一份已建好的 Image，但 Prod Server 連不到資料庫。兩邊的 /health 會得到一樣的結果嗎？

查看結果與原因

Test 可以回 200，而 Prod 可能回 503，前提是 API 把資料庫連線失敗轉成 503。Image 固定了部署的程式和已封裝的依賴，部署環境仍然提供資料庫位址、憑證與網路。看到這類錯誤時，先檢查這些環境輸入。

VM 也能帶齊環境，差別在哪裡？

同事也可以先準備一台 Linux VM，把 Node.js、Express 和 API 裝好，再做成 VM 範本。從範本建立新的 VM，同樣可以保留這些依賴。現在真正的問題是：為了再跑一份 API，需要多啟動哪些東西？

先看一個大家都遇過的動作。兩支程式同時執行時，誰分配 CPU 時間、管理各自使用的記憶體？是作業系統的 Kernel（核心）。Node.js 跑起來以後，也是由 Kernel 管理這個 Process。就算你把 Node.js 放進 Image，這份工作一樣得有人做。

看下圖時，先找兩份 API，再沿著「交給誰管理」找它們各自使用的 Kernel。

所以，若每次擴展都要新增一台 VM，每台 VM 都會有自己的 Kernel 和開機工作。在同一個 Linux 環境新增普通的 Container，則可以共用已啟動的 Kernel。這省下每個實例的額外開機工作。API 本身要花多久載入資料、等資料庫連線，仍由程式與部署環境決定。

換個情境試試看

API A 需要 Node.js 22，API B 需要 Node.js 24。兩支 API 可以同時跑在同一台 Linux 主機、各用自己的版本嗎？如果 B 的需求改成「要用不同版本的 Linux Kernel」，答案會怎麼變？

查看推理

Node.js 是 Image 能提供的執行檔，兩個 Container 可以各用各的版本。Kernel 是兩個 Process 共用的那一份。若 B 必須使用另一個 Kernel，就得把它放到另一個提供該 Kernel 的 Linux 環境，例如另一台 VM。

到 Linux 主機上找這個 Process

用一台已安裝 Docker Engine 的 Linux 主機做。這次只跑 Node.js，讓我們能專心觀察版本和 Process，省去 API 和資料庫的準備。先猜兩件事：主機沒有安裝 Node.js，Container 還能啟動嗎？主機的 ps 能看到這個 Process 嗎？

docker run -d --name lesson01-node node:22-slim \
  node -e 'setInterval(() => {}, 1000)'
docker exec lesson01-node node --version

pid=$(docker inspect --format '{{.State.Pid}}' lesson01-node)
ps -p "$pid" -o pid,comm,args

docker rm -f lesson01-node

setInterval 讓 Process 保持執行，好讓我們觀察。預期版本是 v22.x.x，來自 Image 裡的 Node.js。docker inspect 取得主 Process 在 Linux 主機上的 PID，ps 用它找出正在執行的 node。前者看的是 Container 裡的檔案，後者看的是 Linux 主機上正在跑的行程。

如果使用 Docker Desktop 的 Linux 容器模式，Docker Engine 所在的 Linux 環境才是這裡說的主機。從 Windows PowerShell 或 macOS 的 ps 無法直接用同樣的方式觀察。分享前可先拉好 node:22-slim；無 Linux 環境時可請大家在上圖指出兩項預期結果各來自哪裡。 Docker Desktop 官方說明

離開這章前，用 60 秒解釋

同事問：「兩個 Container 分別用 Ubuntu 和 Alpine 當基底，又都跑在同一台 Linux 主機上。這算兩台不同的 Linux 嗎？」先自己回答，要說出哪些東西可能不同、哪一樣是共用的，以及服務由誰管理。

看完自己的答案，再核對

兩個 Image 提供的工具、函式庫和檔案可以不同，例如一個有 Bash，另一個只有 sh。兩支服務仍由同一個正在運作的 Linux Kernel 管理。換一份 Image 可以換裡面的檔案，要換正在管理 Process 的 Kernel，就需要另一個 Linux 執行環境。

  • 每次交付要固定的是程式與適合一起封裝的依賴。資料庫與部署設定在執行時提供。
  • Image 提供檔案與啟動設定。啟動 Container 才會執行應用程式。
  • VM 各自啟動 Kernel。同一環境的普通 Linux Container 共用 Kernel，仍能使用不同的一組檔案。

如果你能說出這三層的分工，下一堂就可以追問：既然 Kernel 是同一個，它怎麼讓兩個 Container 看到不同的行程和檔案？卡在哪一步，可以帶著你的 60 秒答案發問。

30 分鐘分享安排
  • 0–7 分鐘：讓大家從兩條錯誤訊息推斷部署少了哪些檔案，再預測 Prod 的健康檢查。
  • 7–16 分鐘：沿圖指出執行 API 的 Kernel，討論雙 Node.js 版本與雙 Kernel 需求。
  • 16–24 分鐘：先預測，再看 Node.js 版本與主機 PID。請同事說出兩項觀察各能說明什麼。
  • 24–30 分鐘：各自回答 Ubuntu／Alpine 題，兩人交換答案，留時間釐清混在一起的概念。
