Docker Fundamentals · Session 01 · 30 分鐘

既然已經有 VM，為什麼還需要 Container？

今天要上線新版庫存 API。你手上有一台已經跑著舊版 API 的 Linux VM；新版得先和舊版並行，才能把流量切過去。同事提議：「再開一台 VM，新舊就分開了。」這個方案行得通。那麼，什麼情況下，你會選擇在原本的 VM 裡啟動兩個 Container？

沿著一次上線來做這個決定。先看要交付什麼，再看兩種做法各自要啟動什麼。最後用一筆讀檔請求和一個 Linux 行程，檢查你畫出的架構是否說得通。

0–7 分鐘｜先試著部署第二份 API

開發者交給你 server.js。在測試機輸入 node server.js 就能啟動，正式機卻回報找不到 node。這行命令的第一個字就是要執行的程式；機器上少了 Node.js，連第一行 JavaScript 都還沒跑到。即使補裝 Node.js，程式引用的 Express 套件也得在場。這解釋了為什麼同一份原始碼會有兩種部署結果。

再加上一個條件：舊版 API 只驗證過 Node.js 20，新版需要 Node.js 22。若兩個服務都用系統預設的 /usr/bin/node，直接升級會連舊服務下次重啟時用到的版本一起改掉。你可以分開安裝、指定路徑；只是每增加一台機器，都得把這套安排正確重做一次。幾次手動修補後，原先相同的測試機和正式機逐漸有了差異，這就是環境漂移。

Image 保存這組檔案和啟動設定。Docker 可以從它建立獨立的執行環境，稱為 Container。舊版和新版各用自己的 Image，各自看到適合自己的 Node.js。若新版出問題，上一份 Image 也能重新部署；資料庫變更、密碼和網路仍需另外處理。

如果把已裝好新版 API 的 VM 做成範本，也能避免逐台安裝嗎？

對照你的推理

可以。交付測過的 VM 範本，同樣能提高部署一致性。現在請把問題縮小：如果兩個版本只需要不同的 Node.js，為了隔開這兩個執行檔，是否值得為每份服務準備一整套可開機的系統？

7–15 分鐘｜畫出「隔開」的邊界

先想像只有一台 Linux 主機。磁碟上可以存很多個版本的 Node.js；當其中一個開始執行，它就成了 Process（行程）。替行程安排 CPU 時間、管理記憶體、處理檔案存取，是作業系統核心 Kernel 的工作。Node.js 可以換版本，負責執行這些工作的 Kernel 仍可以是同一個。

VM 把邊界畫在硬體介面。Hypervisor（虛擬機器管理程式）提供虛擬 CPU、記憶體與裝置，讓每台 VM 像一台可開機的電腦。VM 裡安裝的作業系統叫 Guest OS，包含它自己的 Guest Kernel，以及工具、函式庫等檔案。這叫硬體虛擬化。即使兩台 VM 使用同版 Linux，開機後也是兩份獨立運作的 Kernel。

一般 Linux Container 把邊界畫在行程可以看見和使用的環境。執行 Docker 的 Linux 作業系統叫 Host OS；它正在運作的 Host Kernel 可以讓兩組行程看到不同的檔案，也能分別限制資源。兩個 API 可以各自看到一個 /usr/bin/node，路徑相同，檔案內容和版本卻不同。這叫作業系統層級虛擬化（OS-level virtualization）。

從圖頂端各挑一個 API，往下找替它管理記憶體的 Kernel。再從另一個 API 出發：兩條路徑在哪一欄會合？

這個差異也帶來成本取捨。每服務一台 VM，除了 API 的記憶體，還要容納各自的 Guest Kernel 和系統服務。若兩份 API 可共用 Kernel，同一台 VM 就能用兩個 Container 分開交付，增加副本時少了一套 Guest OS 的開銷。若新版必須使用另一種 Kernel，獨立 VM 則能直接滿足需求。實際可容納幾份 API，仍取決於服務消耗的 CPU 和記憶體。

15–21 分鐘｜再啟動一份服務，誰需要開機？

假設 Image 與 VM 範本都已下載，Linux 主機已開機。把起點設為「新增一個可服務的實例」，終點設為「API 開始接單」。先猜哪幾步是雙方都得做的，再看兩欄。

如果 API 啟動時得花 25 秒載入商品資料，改成 Container 後，那 25 秒會消失嗎？

仍然要載入。Container 省下的是再啟動一個 Guest Kernel 和必要系統服務的工作。畫出兩欄共有的末段，就能區分環境的啟動成本與 API 本身的啟動成本。

21–26 分鐘｜API 讀設定檔時，哪個 Kernel 收到請求？

服務已經啟動，現在要讀已開啟的 /app/config.json。程式透過 System Call（系統呼叫）要求 Kernel 提供服務；這次的請求叫 read()，意思是把檔案的一段資料讀進程式的記憶體。用這個動作就能檢驗剛才的圖：兩邊的程式碼一樣，接到請求的 Kernel 會是哪一個？

讀圖時，把手指停在第一個收到請求的 Kernel。左欄由 Guest Kernel 處理系統呼叫，之後才可能產生虛擬磁碟請求；右欄的 API 本來就是 Host Kernel 管理的行程。Docker 負責建立與管理它的執行環境，API 每次讀檔可以直接向這個 Kernel 請求服務。

26–30 分鐘｜從 Linux 主機找出容器裡的行程

最後驗證一個預測：如果 Container 使用這台 Linux 主機的 Kernel，那麼用主機的行程工具，應該能找到裡面的程式。請在 Docker Engine 所在的 Linux 主機執行，分享前先下載 alpine:3.22。Docker Desktop 的 Linux 主機位於其 Linux 後端，外層 Windows 或 macOS 的行程清單有不同的觀察範圍。

# 讓一個容易辨認的程式保持執行 300 秒
cid=$(docker run -d alpine:3.22 sleep 300)
docker top "$cid" -eo pid,comm,args

# 請 Docker 指出主行程在 Linux 主機的 PID，再用主機工具查它
pid=$(docker inspect --format '{{.State.Pid}}' "$cid")
ps -p "$pid" -o pid,comm,args

docker rm -f "$cid"

看哪裡？ PID 是 Kernel 用來辨認行程的編號。在 docker top 找到 sleep 300 那列，再和主機 ps 的 PID 與命令比對。預期兩邊指到同一個行程，實際編號由現場主機分配。這項觀察說明 Linux 主機看得到容器行程；下一堂再進入容器，觀察同一個行程在裡面看到的編號。 Docker CLI 操作說明

回到開頭。新版只要求不同的 Node.js，或改成要求不同的 Linux Kernel，這兩種情況你各會怎麼部署？請同事追問：新增實例要啟動什麼？讀設定檔時誰接到請求？

對照你的推理

只換 Node.js，可以在現有 Linux VM 上啟動第二個 Container。新版 Image 提供自己的 Node.js 與套件，既有 Kernel 建立並管理 API 行程，也接收它的讀檔請求。若必須換 Kernel，可另開一台 VM，讓新版 API 由那台 VM 開機載入的 Guest Kernel 服務。這個選擇取決於需要獨立的是執行檔還是核心。

複習時，把紙分成兩欄，每欄畫出兩個 API，標出它們使用的 Kernel，再畫出其中一個 API 的讀檔箭頭。如果有一個方塊不知道該放在哪裡，可以帶著那張圖提問。
