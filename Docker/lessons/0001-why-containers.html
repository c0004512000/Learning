為什麼需要 Container？
從 VM 與 Kernel 的差異開始

同樣一個 API，能在開發者電腦執行，到了測試環境卻失敗。問題未必出在程式碼，而可能出在執行環境。這堂課先把問題說清楚，再比較兩種不同的隔離方式：Virtual Machine（虛擬機器）和 Container（容器）。

本堂目標
  • 能說出容器化的價值不只有「解決版本衝突」，還包括封裝與交付、隔離及工作負載密度。
  • 能用架構圖比較 VM 的 Guest Kernel 與 Linux Container 的共享 Kernel。
  • 能解釋一個檔案讀取請求，為什麼在兩種環境會經過不同的 Kernel 邊界。

先備：知道應用程式需要 OS 提供檔案讀取、網路與 Process 管理；不需事先會 Docker CLI。

01 / 如果沒有 Container，我們是在部署什麼？

假設團隊維護三個 API：一個使用 Node.js 22、一個 Python 3.12、一個 Java 21。傳統方式常要在每台 Server 安裝 Runtime、系統函式庫、憑證、設定檔，然後把程式部署上去。這時程式碼版本和Server 當下的狀態共同決定結果。

把問題拆成四類。點選情境，觀察容器化主要替哪個環節降低不確定性。

Figure 01 · 選一個部署問題

測試環境能跑，正式環境卻缺套件

兩台 Server 的 Runtime、Library、設定不完全相同；更新時間也不同。

Container 的價值：把程式及大量 User Space 依賴放入可版本化的 Image，讓環境更可重現，而不是每台機器手動安裝。

限制：Kernel、CPU 架構、外部服務、Secret 與環境設定仍可能不同。

注意：這些問題 VM 也能處理。真正的下一個問題不是「VM 能不能」，而是「為什麼 VM 與 Container 需要付出的成本不同」。

02 / VM 為什麼要啟動一個 Guest OS？

一般程式不能自己直接控制所有硬體。當它要讀檔、開 Socket、建立 Process，就需要透過 System Call（系統呼叫）要求 Kernel（作業系統核心）提供服務。

VM 的做法是：Hypervisor 提供一組虛擬硬體介面，讓每台 VM 像是在獨立機器上開機。Guest OS 在這些虛擬硬體上啟動自己的 Guest Kernel。因此它能有自己的一套核心行為、驅動與 OS 生命週期。

Linux Container 沒有替每個應用程式建立另一個虛擬硬體與 Guest Kernel。容器裡的程式仍是 Linux Host Kernel 管理的 Process，只是使用 Kernel 提供的隔離與權限機制，讓它看到不同的環境。

Figure 02 · 兩種架構：差別在 Kernel 邊界

Virtual Machine

system call ↓

VM 有自己的 Kernel；這張圖以硬體虛擬化模型呈現，省略不同 Hypervisor 型態的差異。

Container 不含獨立的 Guest Kernel；隔離規則由共享的 Host Kernel 實施。

每支箭頭都表示上方元件如何向下方請求服務；不是 Docker Daemon 每次都參與 System Call。

第一個關鍵推論

VM 必須初始化 Guest Kernel，是因為它把可執行獨立 OS 的虛擬機器當成隔離單位；Container 把共享 Kernel 的 Process當成隔離單位。兩者的隔離邊界不同，並不是說 VM 的做法比較落後。

03 / 點一下：同樣是讀取檔案，請求去哪裡？

下面將兩種路徑展開。切換後，請自己找出「哪一個 Kernel 真正收到程式的 System Call」。

VM：Application → Guest Kernel → 虛擬化 I/O → Host

  1. 程式呼叫 read()。
  2. Guest Kernel 檢查並處理該系統呼叫。
  3. 需要存取虛擬磁碟時，透過虛擬裝置／Hypervisor 與 Host 底層互動。

不是每一次 read() 都真的走到實體磁碟，例如可能命中 Guest 的檔案快取。

04 / 那 Container 裡為什麼看起來有 Ubuntu？

因為「看起來有一整套 Linux 目錄」與「擁有自己的 Linux Kernel」是兩件不同的事。Container Image 可以提供 /bin、/usr、程式、函式庫、設定等User Space 檔案；Kernel 仍由 Host 提供。

Figure 03 · 檔案 ≠ Kernel

Image / Root Filesystem
  • /bin、/usr、/lib
  • Node.js、Python
  • 應用程式與設定
Host Kernel
  • 管理 Process
  • 處理 System Call
  • 控制隔離與資源

下堂課會拆解 Namespace、cgroups，以及 RootFS 怎麼組合出這個效果。

05 / 不要把「共享 Kernel」誤解成兩件事

限制一：Container 不是一個完整 OS VM。

它不能靠塞入 Windows 的系統檔案，就讓 Linux Kernel 原生實作 Windows Kernel 的 System Call。不同 OS Kernel 的應用程式執行要求不能這樣互換。

限制二：在 Windows 或 macOS 使用 Docker Desktop，不代表完全沒有 VM。

Docker Desktop 執行 Linux Container 時，通常使用 Linux VM 或 WSL 2 提供 Linux Kernel。真正被所有 Linux Containers 共享的是該 Linux 環境的 Kernel，不是 Windows 或 macOS Kernel。

Container 的啟動通常較輕量，也不代表所有 Container 都一定比較快或一定安全。工作負載、隔離設定與實作方式仍會影響結果。

06 / 用觀察而不是背定義

如果課堂現場有可用的 Linux Docker Engine，講者可以展示這個最小觀察：

docker run -d --name demo nginx:alpine
docker ps
docker top demo
# Linux Host 上可再觀察對應的 Process
ps -ef | grep nginx

看得到 Host 上的 Process，正是 Container 並非神祕小電腦的第一個線索。但這個 Demo 不能單獨證明所有隔離機制，只是建立下一堂課的觀察起點。

08 / 本堂重點回顧

  • Containerization 強化執行環境封裝、標準化交付與隔離，但不保證所有外部條件一致。
  • VM 對每個 Guest 提供虛擬硬體，能執行獨立 Guest Kernel。
  • Linux Container 的 Process 直接使用共享 Host Kernel，並受 Kernel 隔離機制管理。
  • Image 裡的 Ubuntu 或 Alpine 檔案是 User Space，不等於新啟動一個 Linux Kernel。
  • Docker Desktop 可以借助 VM 提供 Linux Kernel；這不會改變 Container 本身的原理。
