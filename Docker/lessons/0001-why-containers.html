SESSION 01 / WHY CONTAINERS?

既然已經有 VM，
為什麼還需要 Container？

先不要背 Docker 名詞。這堂課從「同一份程式換台 Server 就不能執行」開始，先理解程式需要什麼、OS 做什麼，最後再推導 VM 和 Container 的架構差異。

01 / 00–07′同一份程式碼，為什麼會因為 Server 不同而失敗？

假設你寫了一個 Python API，自己的電腦能執行，部署到測試環境卻顯示缺少 Python 套件。程式碼沒改，變的是程式執行所依賴的環境。

Runtime（執行工具／執行環境）是讓程式能被執行的軟體，例如 Python 直譯器。Library（函式庫）是程式引用的現成功能，例如 FastAPI 套件。設定決定程式在特定環境使用什麼 Port、連向哪個服務。

以前常把程式碼複製到 Server，再讓每台 Server 分別安裝和維護其他依賴。當兩台 Server 的 Runtime 或套件版本變得不一樣，就可能出現環境漂移。

為了減少這類差異，我們可以先把程式與大量執行依賴封裝成一個可保存、可交付的版本。Docker 把這種封裝稱為 Image（映像檔）；以它建立、執行的實例稱為 Container（容器）。Image 好比同一份已經準備好的執行內容，而 Container 是用它真正啟動的服務。

Image 提供更一致的起點，但外部資料庫、設定、硬體架構和作業系統核心仍可能不同。更重要的是：VM 也能封裝環境。Container 的意義不在於 VM 完全做不到，而是採用了不同的執行與隔離方式。

現場思考題

Test 與 Prod 取用同一份 Image，是否一定產生完全相同的結果？

查看推理

不一定。Image 使程式與大量依賴更一致，但外部 DB、設定和 Host 條件仍可能不同。

02 / 07–14′先弄懂 OS 與 Kernel，才能比較 VM

Operating System（OS，作業系統）是管理電腦資源、提供程式運行環境的系統軟體。它最核心的一部分是 Kernel（核心），負責管理執行中的程式、CPU 時間、記憶體、檔案及網路等。

還需要分清楚程式與 Process（行程／程序）。程式可以只是一份存放在硬碟的檔案；當它被啟動，作業系統開始安排它執行，這個正在執行的實例就是 Process。一份程式可以啟動多個 Process。

當程式需要讀檔、傳資料，實際上都是透過 OS 提供的服務完成。先只記住這個關係：Process 需要 Kernel 才能使用底層資源。

現場思考題

把同一份 Python 程式複製成兩份檔案，就等於已經有兩個 Process 嗎？

查看推理

不是。檔案可以存在卻沒有被執行。只有啟動程式後，Kernel 才會管理相應的 Process。

03 / 14–22′VM 與 Container：兩種不同的隔離邊界

如果同一台 Server 要同時運行 Service A 和 Service B，我們會希望兩者不會隨意影響彼此。這就是隔離的需求。但隔離到什麼程度，有不同選擇。

一種方法是 VM（Virtual Machine，虛擬機器）。使用 Hypervisor（虛擬機器管理程式）提供虛擬 CPU、記憶體與硬體介面，讓 VM 像一台獨立電腦一樣啟動自己的作業系統。VM 裡的 OS 稱為 Guest OS（客體作業系統），它的 Kernel 叫 Guest Kernel。

另一種方法是 Linux Container。它不需要替每個 Container 建立一台完整的虛擬電腦；Container 裡執行的程式仍使用所在 Linux 環境已經啟動的 Kernel，也就是 Host Kernel（主機核心）。

從圖上可以直接看出：VM A 和 VM B 有各自的 Guest Kernel；Container A 和 Container B 則是共用同一個 Host Linux Kernel。這就是兩種架構最重要的差異，並不是單純比較哪個 Image 檔案比較小。

延伸：Windows 或 macOS 上的 Docker Desktop 呢？

若要執行 Linux Container，Docker Desktop 通常會使用內部的 Linux 虛擬環境來提供 Linux Kernel。所以「共用 Host Kernel」指的是執行 Container 的 Linux 環境，不代表 Linux 程式直接由 Windows 或 macOS 的核心來執行。

那為什麼 Container 看起來像有自己的 Linux 目錄？因為它可以使用自己的一套程式、函式庫、設定與檔案。這些屬於 User Space（使用者空間），不代表又啟動另一個 Kernel。

現場思考題

Container A 使用 Ubuntu 的程式檔案，Container B 使用 Alpine 的程式檔案，是否就有兩個 Linux Kernel？

查看推理

沒有。不同 Image 可以提供不同程式與使用者空間檔案；兩個一般 Linux Containers 仍共用同一個 Host Linux Kernel。

04 / 22–27′為什麼 VM 與 Container 的啟動方式不同？

VM 要先讓一套 Guest OS 能開機、初始化，才能在裡面執行服務。Container 的 Host Kernel 已經在運作，因此可以準備好隔離環境與程式檔案後，啟動新的 Process。

這也是 Container 往往比較輕量的原因：不必替每個實例額外啟動 Guest Kernel。但仍不能據此斷言 Container 在所有工作負載都更快、更安全；兩種架構各自適合不同的隔離需求。

05 / 27–30′用一個 Demo 觀察程式真的在執行

CLI（Command-Line Interface）是透過終端機輸入指令的工具。Docker Engine是管理 Image、建立與執行 Container 的軟體；Docker CLI 可以向它送出要求。這堂只先知道它們的角色，內部實作留到後面的課。

若現場有可用的測試用 Docker Engine，可以輸入：

docker run -d --name demo nginx:alpine
docker ps
docker top demo
docker rm -f demo

docker run 啟動實例；-d 代表背景執行；--name demo 指定名稱；nginx:alpine 是範例 Image 名稱與標籤。docker ps 顯示執行中的 Container，docker top demo 列出它的 Process，docker rm -f demo 清理實例。

預期可以看到 nginx 的 Process。這個觀察支援「Container 裡跑的是實際 Process」，但單獨執行這些指令不能證明所有隔離細節；下一堂才會繼續驗證。這不是公司環境已執行的聲明。

最後用七句話整理本堂

  1. 執行條件：程式需要 Runtime、Library、設定與 OS 提供的功能。
  2. Image：把程式與大量依賴封裝成可版本化的交付單位。
  3. Process：已啟動、正在執行的程式實例。
  4. Kernel：作業系統中負責管理 Process 與資源的核心。
  5. VM：透過虛擬硬體啟動獨立 Guest OS 和 Guest Kernel。
  6. Container：Linux 上受隔離的程式執行環境，共用 Host Kernel。
  7. System Call：程式向 Kernel 請求系統服務的方式。
