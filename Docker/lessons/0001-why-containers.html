為什麼需要 Container？
從 VM 的 Kernel 邊界看懂。

先問一個工程師很熟悉的問題：同一份程式碼，為什麼換一台 Server 就可能無法啟動？我們不會先背 Docker 指令，而是沿著「部署 → Kernel → Process」一步步找出容器化的必要性。

這堂結束，你應該能：
  1. 從部署問題說明 Container Image 帶來的交付價值。
  2. 在架構圖指出 VM 的 Guest Kernel 與 Container 的共享 Host Kernel。
  3. 跟著互動式 read() 流程，判斷哪個 Kernel 處理 System Call。

01 / Container 解決的不是只有版本衝突

切換四個常見問題，看「交付程式碼」與「交付 Image」的差異。

02 / VM 與 Container，到底隔離了哪一層？

看圖的橘色區塊：VM 有兩份 Guest Kernel；右邊的兩個 Linux Containers 則使用同一份 Host Kernel。

為什麼 VM 要有 Guest Kernel？因為 Hypervisor 提供虛擬硬體，讓 Guest OS 像一台獨立機器一樣開機。Container 不走這條路：它的 Process 直接使用所在 Linux 環境已經執行中的 Kernel。

03 / 一次檔案讀取，兩種不同的執行路徑

程式對已打開的檔案呼叫 read(fd)，代表向 OS 要求資料。切換 VM／Container，再按「下一步」，流程圖會逐步指出哪個 Kernel 收到呼叫；也能改成 Cache 命中看看差別。

04 / Image 裡有 /bin、/usr，為何還不是一個獨立 OS？

因為程式和函式庫屬於 User Space；負責執行 System Call、排程與資源管理的是 Kernel。把它們畫成兩組來源就不容易混淆。

05 / 用兩個邊界問題檢查模型

在 Windows / macOS 上跑 Linux Container，還是共用 Host Kernel 嗎？

是共享「Linux 執行環境」的 Kernel，但那個 Linux 環境通常在 VM / WSL 2 裡，不會直接把 Windows/macOS Kernel 當成 Linux Kernel 使用。

Container 比 VM 輕量，是不是就等於隔離更安全？

不是。兩者安全邊界不同。Container 共享 Kernel，隔離還涉及 Namespace、cgroups、Capabilities、Seccomp 與其他機制；安全性取決於威脅模型及配置。

06 / 把圖轉成真實的觀察

在可用的 Linux Docker Engine 上建立一個最小 Container，使用 docker top 看 Host 可以觀察到的 Process。

docker run -d --name demo nginx:alpine
docker ps
docker top demo
docker rm -f demo

這個 Demo 是 Process 可見性的觀察，不是完整隔離證明。Linux Namespace / cgroups 的實作會放進 Session 02。
