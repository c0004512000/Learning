我們為什麼需要
Containerization？

第一堂已經知道 Container 是隔離的執行環境，Image 是建立它的模板。這堂不再重複名詞定義，而是從一個團隊反覆部署服務的過程出發，找出真正需要改善的環節，理解為什麼要把「建構環境」和「在環境執行」分開。

先備：分得清 Dockerfile、Image、Container、Process 即可。不需懂 Namespace、cgroups、VM 架構或 Kubernetes。

本堂能力目標
  1. 能指出傳統部署中「程式碼相同、執行結果不同」的至少三種原因。
  2. 能說明 Container 如何減少服務間相依衝突，以及它與 Python venv、VM 等替代方案的不同。
  3. 能推導「CI 建構 Image → Registry 保存 → 各環境部署同一份 Artifact」為什麼重要。
  4. 能區分 Image 中固定的內容，與部署時仍會改變的設定、資料和執行條件。
  5. 能判斷何時 Containerization 有幫助、何時還需要其他措施。

01 / 00–05′ · ONE APPLICATION, THREE ENVIRONMENTS程式碼都沒改，為什麼部署卻失敗？

想像一個團隊維護 orders-api。開發者在自己的機器完成測試，GitHub Actions 也順利通過單元測試，但部署至 Stage 後卻出現匯入套件錯誤；改好之後，Production 又遇到其他函式庫版本問題。

這不必然表示程式碼有 Bug。真正的問題可能是：同一份 Source Code，在不同機器上被組合成不同的執行環境。

我們先把「執行環境」當作一組需要協調的條件：Runtime 版本、系統函式庫、第三方套件、執行設定，以及外部服務。只要其中某項與程式的假設不相容，就可能失敗。

先預測

假設 Stage 的 library X 1.1 完全相容，Production 的 library X 1.0 卻缺少程式用到的函式：你應該先調整 Source Code，還是調查部署後的依賴版本？

查看推理

先查 Production 實際使用的依賴，並與 CI 成功時的版本比較。程式碼未改不代表執行環境未改；是否需要修改程式，要看確認後的相容性需求。

02 / 05–13′ · THREE ROOT CAUSES傳統部署真正困難的，不是「複製檔案」

問題 A：多個服務共享主機的執行條件

例如某台部署主機同時執行 Service A 與 Service B。A 需要 Python 3.10 和一組系統函式庫，B 需要 Python 3.13 和另一組版本。如果部署流程都依賴主機預先安裝的全域環境，更新 B 所需的套件，就可能影響 A。

這不是說一台 Linux 主機不能安裝多個 Python 版本。事實上可以，而且 Python virtual environment（venv） 能隔離很多 Python 套件。問題是：venv 主要處理 Python 的套件環境，並不是一個完整的 Process／檔案系統／網路隔離邊界，對 OS 層級函式庫和其他語言的依賴也不是通用解答。

Container 改善了什麼？ 讓每個服務能帶著自己需要的 Runtime、套件和應用程式檔案交付，而不必把所有依賴都要求安裝在 Host 的全域環境中。

問題 B：每個部署環境都在「重新組裝」服務

假設 CI 用 pip install -r requirements.txt 裝了套件，Stage 部署時又重新安裝一遍，Production 再裝第三遍。就算三次使用相同的需求宣告，仍可能因為未鎖定的相依版本、系統套件差異、套件來源變化或平台差異而得到不同結果。

這種環境內容隨時間改變的現象通常稱為 Environment Drift（環境漂移）。它不只會發生在不同環境之間：同一台主機隨著更新與人工修改，也會逐漸偏離最初狀態。

Container 的解法不是把安裝指令換成另一種寫法。 關鍵是把安裝與建構集中到較可控的建構階段，然後交付已建好的 Image，而不是要求每個環境重新做同一套安裝。

問題 C：難以回答「正式環境到底在跑哪一份東西？」

當交付內容散落在程式碼、部署腳本、主機已安裝的套件與人工作業之中，事故發生時，可能只能知道「Git Commit 是 abc123」，卻無法立即確定當時用了哪一版 Python 套件、哪個建構輸出、哪份設定。

一個明確、可保存、可識別的 Artifact（交付產物） 可以改善追蹤。Artifact 不必然是 Container Image：JAR、編譯後的 Binary、安裝包也可以是 Artifact。但 Docker Image 可以連同大量 User-space 執行依賴一起封裝，並交由 Registry 分發。

到這裡先建立的因果關係

問題不是「主機上不能直接執行程式」，而是當服務數量、環境數量、版本數量增加時，要維持每次組裝結果的一致性，會變得愈來愈困難。Containerization 提供的是另一種管理交付和執行環境的方式。

03 / 13–21′ · BUILD ONCE, DEPLOY THE ARTIFACT真正重要的轉變：從「部署程式碼」到「交付 Image」

回到 orders-api。如果每個環境都拿原始碼重新安裝相依套件，實際上是把「建構」這件事重做了很多次。

現在我們改成以下流程。先提醒：Dockerfile 是建構的說明書；Docker Image 才是已建好的產物。 正式部署應優先使用 CI 已驗證的產物，而不是在不同環境重新執行 Dockerfile。

這裡出現一個新名詞：Registry（映像檔倉庫）。它是儲存、提供 Image 的服務，常見的例子有 Docker Hub 與 Harbor。CI 可以將建好的 Image Push 到 Registry；Stage、Production 再將 Image Pull 下來執行。

這不表示「CI、Stage、Production 使用同一台主機」。恰好相反：它們可以在不同主機上，只要執行平台相容、能取得同一份 Image，就能避免各環境自行重新建立大量 User-space 依賴。

一個版本名稱，就一定代表同一份 Image 嗎？

看似合理的做法是讓 Stage 和 Production 都部署：

registry.example.com/team/orders-api:1.2.3

但 1.2.3 是一個 Tag，它通常只是指向 Image 的名稱；若 Registry 沒有禁止改寫，Tag 可以在不同時間指向不同的 Image。相同 Tag 字串 ≠ 一定是相同的 Image 內容。

Docker Image 還有依內容識別的 Digest，常見格式是 sha256:...。實務上可記錄 Build／Push 後的 Image Digest，並確保測試與部署使用預期的相同內容識別。這比只相信可變動的 Tag 更嚴謹。

你不必在第二堂學會每一種 Image 命名方式，但要理解：「建構一次、測試這個產物、部署這個產物」比「每次從同一份 Source Code 重新建構」更容易追蹤與驗證。

如果 Production 更新失敗，也能選擇重新部署先前保留、驗證過的 Image Artifact。這改善了應用程式產物的 Rollback 操作，但不會自動復原資料庫狀態、資料格式或外部設定。

對應 SRE / CI/CD 的實際架構

GitHub Actions 負責 Build / Test；Harbor 保存 Image；部署流程指定 Image，交由執行環境啟動 Container。這是一個通用架構示意，不表示本頁已讀取或驗證你們公司目前所有 Workflow 的實作細節。

用 30 秒回答

為什麼「CI 和 Prod 都 checkout 同一個 Git SHA」還不等於「Prod 跑的是 CI 測過的 Artifact」？

查看解析

因為兩邊如果各自重建，就有兩次建構過程，Runtime、外部相依、Base Image、套件來源等輸入可能不同。若 CI 已建構並驗證一份 Image，Prod 後續部署相同 Digest，就能避免重新組裝造成的差異；但外部執行環境仍需另外確認。

04 / 21–27′ · WHAT IT DOES AND DOES NOT SOLVEContainerization 的價值，與它的適用邊界

把 Container 稱為「環境一致性的解答」很容易造成誤會。實際上，它固定的是 Image 封裝的內容，而不是把整個世界複製進去。

例如同一份 API Image 可以在 Stage 使用測試資料庫、在 Production 使用正式資料庫。這是我們刻意保留的差異，不是 Containerization 失敗。真正重要的是清楚劃出「Image 固定了哪些內容，部署環境又負責哪些條件」。

所以這項技術帶來的價值至少有四個層次：

  1. 相依封裝：降低不同服務對 Host 全域 Runtime 與函式庫的互相牽制。
  2. 一致的交付起點：讓 Stage／Prod 使用同一份已建構 Image，而不是分別重建。
  3. 版本與追溯：將 Source Revision、CI Build、Image Digest 與部署版本關聯起來。
  4. 部署替換：更容易以新的 Image 替換舊版本，或重新部署先前保留的版本。

但不要把它當成萬能解法

Container 不能自動解決：程式邏輯錯誤、資料庫 Schema 不相容、外部服務故障、缺少 Secrets、CPU 架構不相容、Host Kernel 問題，或未妥善設定的權限與網路安全。Image 也需要持續更新有漏洞的 Runtime、OS 套件與 Base Image。

Container 不保證具有 VM 等級的隔離。 典型 Linux Container 共享 Host Kernel；隔離效果取決於執行設定與權限，對安全敏感工作負載仍要做額外評估。第三堂才會深入理解隔離機制及 VM 的架構差別。

不是每個服務都非 Container 不可。 Python venv、Node 版本管理、可重現建構、VM Image、Configuration Management、封裝成 Binary 或 JAR，都能處理其中部分問題。採用 Container 還會引入建構、Registry、Image 更新、漏洞管理和 Runtime 管理成本。

重要：不要把「可攜」理解成「任何機器都能直接跑」

例如為 Linux amd64 建立的 Image，不能直接假定能在任何 Windows Host 或不同 CPU 架構上原樣執行。執行平台、CPU 架構和 Kernel 的相容性仍是前提；Multi-platform Image 可以改善跨 CPU 架構分發，但不是讓一份 Binary 自動跨平台。

05 / 27–30′ · APPLY THE MODEL面對部署問題，應該選擇什麼解法？

先獨立判斷，不要只找「哪一題的答案是 Docker」。選項設計包含 Container 能改善的問題、需要其他措施的問題，以及仍需判斷前提的情境。

02｜Stage 與 Production 使用相同 Image Digest，但 Production 的資料庫欄位缺失，Container 會自動修復嗎？

60 秒口述練習：講給另一位工程師聽

一個團隊已經會用 GitHub Actions 測試、也有版本控制。為什麼還值得把 API 封裝成 Image 並存入 Registry？請依序回答：

  1. 傳統部署實際有哪些可能改變的條件？
  2. Build Once 的「Once」指的是什麼？
  3. 同 Image Digest 哪些差異被消除、哪些仍會存在？

能清楚解釋這三點，比記住 Docker 會「輕量、可攜、一致」更有價值。若卡住，可從 部署模型速查 重新畫一次流程，或把不確定的環節帶回 ChatGPT 討論。

本堂整理：五句真正重要的結論

  1. 相同 Source Code 不代表相同 Runtime、Library、設定與外部條件。
  2. Containerization 把大量應用程式依賴封裝為 Image，降低對 Host 全域環境的依賴。
  3. Build once, deploy the artifact 指的是盡可能部署 CI 已建構與驗證的產物，而不是各環境重建。
  4. Registry / Tag / Digest 分別是分發位置、方便命名的指標、內容識別；Tag 可能移動。
  5. Image 的一致性有邊界：外部資料、Secrets、Host、CPU 架構及安全仍需獨立管理。
