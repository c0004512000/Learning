1. Namespace 為什麼存在？

同一顆 Linux kernel，如何讓不同 process 看起來活在不同世界？

這一課只拿下一件事

看完後，你應該能不用背任何 namespace 類型，就自己說出：

Namespace 的本質：Linux kernel 仍然只有同一顆，但 kernel 可以依照 process 所屬的 namespace，讓它對某一類系統資源看到不同的視圖。

這是後面 container、Docker、containerd、Kubernetes Pod 的起點。如果這個模型不穩，直接背 PID / NET / MNT namespace 只會變成名詞記憶。

1. 先從 program 和 process 開始

假設你的 Linux 上有一個檔案：

/usr/bin/bash

這是一份 program：它是儲存在 filesystem 裡的程式內容。

當你真的執行它，Linux 會建立一個正在運作的 process。同一份 program 可以同時有很多 process：

bash        bash        bash
PID 421     PID 683     PID 901

同一份 program，三個正在執行的 process

所以先建立第一個界線：

program 是「程式檔案」；process 是「正在執行中的那一份 instance」。

2. Process 並不是自己管理整台電腦

Process 需要 memory、filesystem、networking、process list 等系統能力時，真正掌握底層資源的是 Linux kernel。

你現在先把 kernel 想成整台 Linux 的「資源管理核心」即可，不需要先理解 kernel source code。

背景來源：Linux namespaces(7)；本課只保留理解 namespace 必要的 kernel / process 模型。

3. 問題出現了：如果所有 process 都看到同一份全域狀態呢？

假設同一台 Linux 上同時跑 App A 與 App B，而某一類系統狀態只有一份全域版本。

例如先拿 hostname 當純粹的例子：

整台 Linux hostname = node-01

App A 問 kernel：「我的 hostname 是什麼？」 → node-01
App B 問 kernel：「我的 hostname 是什麼？」 → node-01

如果 App A 想把自己視為 app-a，App B 想把自己視為 app-b，但 kernel 永遠只提供同一份全域狀態，兩者就無法彼此隔離。

真正的需求不是「複製兩台 Linux」。
需求是：能不能仍然共用同一顆 kernel，但讓不同 process 對某一類資源取得不同答案？

4. Namespace 就是 kernel 解這個問題的方式

Linux 的 namespace 把原本全域的系統資源包進一層隔離 abstraction。Process 屬於哪個 namespace，kernel 就依那個 membership 決定它看見哪一份資源視圖。

這裡最重要的是 view 這個字。

Namespace 的核心不是把整個 Linux 複製一份，而是讓 process 對某一類 kernel-managed resource 看起來擁有自己的 isolated instance。

Linux man-pages 對 namespace 的核心描述是：它把 global system resource 包在 abstraction 中，讓 namespace 內的 process 看起來擁有自己的 isolated instance。

Primary source：namespaces(7)

5. 所以一個 process 身上其實有 namespace membership

你現在不用知道有哪些 namespace 類型。先只理解這件事：

Kernel 必須知道「這個 process 對這一類資源屬於哪個 namespace」；否則它無法決定該回哪一份 view。

Linux 甚至讓你直接從 /proc 看到這些 membership。

6. 第一個實驗：看自己的 namespace

在 Linux / WSL2 的 Bash 執行：

echo $$
ls -l /proc/$$/ns

$$ 是目前 shell 的 PID。假設它是 421，第二行就是在看：

/proc/421/ns

你可能會看到類似：

cgroup -> cgroup:[4026531835]
ipc    -> ipc:[4026531839]
mnt    -> mnt:[4026531841]
net    -> net:[4026531840]
pid    -> pid:[4026531836]
user   -> user:[4026531837]
uts    -> uts:[4026531838]

實際項目會依 kernel 版本與環境不同。現在不要背右邊那些名稱。

只讀懂其中一行：

pid -> pid:[4026531836]

它表示：目前 shell 對 PID 這一類資源，指向某一個 namespace object。方括號中的 identifier 可用來比較 namespace identity。

Primary source：proc_pid_ns(5)

比較兩個 process

再執行：

readlink /proc/$$/ns/pid
readlink /proc/1/ns/pid

如果兩個結果相同，代表從這個系統視角看，它們指向同一個 PID namespace object；不同則代表它們屬於不同的 PID namespace。

你目前不需要理解 PID namespace 的特殊規則。這個實驗只是在證明：namespace membership 是 kernel 中真實存在、而且可以觀察的狀態，不只是 container 工具的概念。

7. 一個很容易混淆的地方

Namespace ≠ container。
Namespace 只負責某些資源的隔離視圖。真正的 container 還會組合其他 Linux 機制，例如 filesystem setup、cgroups、capabilities 等。後面會等每個必要前置概念建立後再組起來。

8. Retrieval check

兩個 process 看到不同 hostname，是否一定代表它們使用兩顆不同 Linux kernel？

Recap

一句話：Linux namespace 是 kernel 依 process 的 namespace membership，對某一類全域資源提供隔離視圖的機制。
