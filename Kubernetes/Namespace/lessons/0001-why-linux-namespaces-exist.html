1. Namespace 為什麼存在？

先理解 process、kernel、view 與 isolation，再談任何 namespace 類型

這一課只拿下一件事

看完後，你應該能不用背 PID / NET / MNT / UTS 等名稱，就自己推導出：

Namespace 的本質：同一顆 Linux kernel 可以根據 process 所屬的 namespace，讓不同 process 對某一類 kernel-managed resource 得到不同的可見狀態。

要真正懂這句話，必須先把四個詞建立好：process、kernel、view、isolation。

1. Program 與 process 不是同一件事

假設 Linux filesystem 裡有：

/usr/bin/bash

這是一份 program：儲存在 filesystem 裡的程式內容。

當你執行它，Linux 建立一個正在運作的 process。同一份 program 可以同時產生很多 process：

bash        bash        bash
PID 421     PID 683     PID 901

同一份 program，三個執行中的 process instance
program 是程式內容；process 是 kernel 正在管理的一個執行中 instance。

2. Process 為什麼需要 kernel？

先看一個很具體的例子。Python 可以寫：

f = open("/tmp/demo.txt", "w")
f.write("hello")

Python process 並不是自己跑去操作 SSD，也不是自己維護「哪個檔案在哪個 block」。它最終必須要求 kernel 幫它完成 filesystem I/O。

同樣地，process 想要：

  • 建立另一個 process
  • 配置 virtual memory
  • 開啟檔案
  • 送 network packet
  • 詢問 hostname
  • 查其他 process 的資訊

都會碰到 kernel 管理的系統資源或系統狀態。

這就是為什麼 namespace 必須是 kernel feature：要控制 process 能看到哪一份系統資源，本來就只有管理那些資源的 kernel 做得到。

3. View 到底是什麼？

View 不是一個畫面，也不是 Linux 裡叫做 View 的 object。這裡的 view 只是描述：

同一個 process 透過 kernel interface 查詢某類資源時，kernel 讓它「看見的那份狀態」。

例如假設 kernel 實際管理很多 process：

kernel 中實際存在：
PID 100  app-a
PID 200  app-b
PID 300  sshd

如果某個 process 透過 kernel 取得 process list，kernel 可能讓它看到：

View A：100 app-a
View B：200 app-b

底層仍然是一顆 kernel；差別是 kernel 沒有把同一份可見狀態暴露給兩邊。

所以在本課中：

resource/state  = kernel 管理的東西
view            = 某個 process 從 kernel 看得到的那一份狀態

4. 怎樣才算 isolation？

「兩個 process 不一樣」不等於 isolation。隔離一定要問：隔離哪一種資源？

對某一類資源 R，如果 Process A 與 Process B 被隔離，至少代表：

  1. A 對 R 的觀察，不必等於 B 對 R 的觀察。
  2. A 對自己那份 R 所做的改變，不會自動改變 B 所看到的那份 R。

例如把「mount 列表」當成概念例子：

Process A 看見：
/       → app-a-root
/data   → app-a-data

Process B 看見：
/       → app-b-root
/cache  → app-b-cache

如果 A mount 一個新的 filesystem，只改變 A 所屬 mount namespace 的 mount view，而 B 完全看不到，這就是對 mount state 的 isolation。

Linux man-pages 對 mount namespace 的描述正是：不同 namespace instance 中的 process 看到不同的 mount list 與 directory hierarchy。mount_namespaces(7)

5. 那 hostname 例子到底哪裡容易誤導？

你的直覺是對的：

在沒有 UTS namespace 的傳統 Linux 模型裡，hostname 本來就是整台 system 的一份全域狀態，所以所有 process 問到相同 hostname 才是正常行為。

假設：

system hostname = node-01

Process A → gethostname() → node-01
Process B → gethostname() → node-01

這本身完全沒有問題，也不是「沒有隔離所以 Linux 壞掉」。

Namespace 解的是另一個需求：

如果我們想讓同一顆 kernel 上的兩群 process，各自像是活在自己的 system identity 裡，能不能把原本只有一份的 hostname 虛擬化？

有 UTS namespace 後，可以變成：

同一顆 kernel

UTS Namespace A
  hostname = app-a
  Process A → gethostname() → app-a

UTS Namespace B
  hostname = app-b
  Process B → gethostname() → app-b

更重要的是：

Process A 在自己的 UTS namespace：sethostname("new-a")

結果：
A → new-a
B → app-b     ← 不受影響

這才是 hostname 的 isolation。

官方定義：UTS namespace 隔離 hostname 與 NIS domain name；同 namespace 的修改彼此可見，不同 namespace 不可見。uts_namespaces(7)

所以不要把 hostname 當成 namespace 必然存在的理由。
它只是最好操作的第一個實驗。真正的共通需求是：把原本某些 system-wide resources / state 分成多個 isolated instances。

6. Namespace 真正做了什麼？

現在可以把模型補完整：

Process A ─┐
           ├─ 同一顆 Linux kernel
Process B ─┘

但 kernel 不再只問：
「這個 resource 的全域狀態是什麼？」

它還會知道：
「這個 process 對這類 resource 屬於哪個 namespace？」
一句關鍵話：Namespace 不是把 process 關進盒子，而是讓 kernel 在處理某些資源時，先依 namespace membership 決定該使用哪一份 namespaced state。

7. `/proc` 是什麼？先別把它想成普通磁碟資料夾

接著回答最容易誤會的問題：

「新建一個 process，kernel 就會在 /proc/<pid> 底下新增一份實體檔案嗎？」

不是「kernel 在硬碟上 mkdir + touch 一堆檔案」。

/proc 是一個特殊的 pseudo-filesystem（虛擬 filesystem）。它提供 filesystem 介面，讓 user-space 可以用 cat、ls、readlink 等熟悉操作去讀 kernel 目前掌握的資訊。

因此：

/proc/421/status
/proc/421/cmdline
/proc/421/ns/uts

看起來像檔案，但很多內容不是預先存在硬碟裡等你讀，而是 kernel 依目前 process / namespace 狀態透過 procfs 暴露出來。

Process 出現時

只要 PID 421 是目前可由這個 procfs 看見的 running process，/proc/421/ 就會存在。Linux man-pages 定義 /proc/<pid>/ 為每個 running process 對應的 numeric subdirectory。

proc_pid(5)

Process 結束時

process 不再存在後，對應的 /proc/<pid>/ view 也會消失。這不是 cleanup daemon 稍後刪除實體檔案；因為那些本來就是 kernel state 的 filesystem representation。

8. 那 `/proc/<pid>/ns/*` 是 namespace 本體嗎？

不是。

/proc/<pid>/ns/* 是通往該 process 所屬 namespace object 的 handle / reference，不是 namespace object 本身的資料內容。

例如：

$ readlink /proc/421/ns/uts
uts:[4026531838]

這表示 PID 421 的 UTS namespace reference 指向某個 namespace identity。Linux man-pages 說明：若兩個 process 位於同一 namespace，它們對應 namespace link 的 device ID 與 inode number 相同；這些 link 因此可以用來判斷 namespace identity。

namespaces(7)、proc_pid_ns(5)

9. Process 死掉，namespace 也一定立刻死嗎？

不一定。這裡要分清楚兩個生命週期：

Process lifetime      ≠      Namespace lifetime

最簡單情況：

Namespace X
 ├─ Process A
 └─ Process B

A 結束 → namespace 還有 B 使用 → X 繼續存在
B 也結束 → 如果沒有其他 reference pin 住 X → X 可被 kernel 銷毀

Linux 的一般規則是：若沒有其他因素，一個 namespace 在最後一個 member process 離開或終止後會被拆除。

但 namespace 還可能被其他 reference 保活，例如：

  • 有人對 /proc/<pid>/ns/* 開著 file descriptor
  • 該 namespace handle 被 bind mount 到別處
  • 某些 hierarchical namespace 還有 child namespace

官方文件特別指出：只要對 namespace file 的 file descriptor 還保持 open，即使 namespace 裡所有 process 都終止，該 namespace 仍可保持存在。

namespaces(7) — Namespace lifetime

10. 所以 `/proc`、process、namespace 三者到底是什麼關係？

                     kernel memory / kernel objects
                              │
             ┌────────────────┴────────────────┐
             │                                 │
        Process object                  Namespace object
          PID 421                        UTS namespace X
             │                                 ▲
             └──── namespace membership ───────┘
             │
             │ procfs 暴露 kernel state
             ▼
       /proc/421/
          └── ns/uts  ───── handle/reference ───→ UTS namespace X

因此：

  • /proc/421 的存在跟 PID 421 的 process lifetime 綁得很緊。
  • /proc/421/ns/uts 告訴你這個 process 指向哪個 UTS namespace。
  • namespace object 本身可以比 PID 421 活更久，只要還有別的 member 或 reference 把它保活。

11. 第一個實驗：只觀察，不背名稱

echo $$
ls -l /proc/$$/ns
readlink /proc/$$/ns/uts
readlink /proc/1/ns/uts

現在你只需要回答兩件事：

  1. /proc/$$ 為什麼會隨目前 shell process 存在？
  2. 如果兩個 uts:[...] identity 相同，這件事告訴我們什麼？

Retrieval check

如果 Process A 改 hostname 後，Process B 的 hostname 也立刻跟著改，這兩個 process 對 hostname 算隔離嗎？

Recap

一句話：Linux namespace 是 kernel 對某類原本偏全域的 system resource 建立多個隔離 instance，並依 process 的 namespace membership 決定它能看到與修改哪一份。
