Service 怎麼知道
哪些 Pod 是它要找的？

今天只練一件事：看懂選取條件，判斷哪些 Pod 符合。

你有兩份相同的網站程式同時運作，想讓使用者透過同一個入口存取它們。Kubernetes 裡，執行這些容器程式的單位叫 Pod；提供穩定存取入口的資源叫 Service。

先不處理網路封包怎麼走。眼前的問題是：這個入口，要把哪些 Pod 視為同一組應用？

本課情境：所有 Pod 和 Service 都放在同一個 Namespace（資源的命名分區），而且都已就緒。先只看「選到了誰」。

1. 先給 Pod 一個可辨認的標籤

下面有三個 Pod。A、B 是網站，C 是另一個 API 程式。名稱只讓我們分辨個體；要表達「屬於哪個應用」，可以加上 label（標籤）。

Pod Aapp: web
Pod Bapp: webenv: prod
Pod Capp: api

app: web 是一組「鍵：值」：鍵是 app，值是 web。這是我們給資源的標記，不是 Kubernetes 讀取程式內容後自動猜出來的。

來源：Labels and Selectors。標籤可以重複出現在不同資源上。

2. Service 寫下「我要哪一組」

現在讓 Service 使用這個 selector（選取條件）：

selector:
  app: web

它的意思是：「找出具有 app: web 標籤的 Pod。」A 和 B 都符合；C 的值是 api，不符合。

B 多了一個 env 標籤，仍然符合。Selector 指定的條件必須滿足，但沒有要求 Pod 只能有那些標籤。

3. 多一個條件，會發生什麼事？

把 Service 的條件改成：

selector:
  app: web
  env: prod

這次要同時滿足兩個條件。Pod A 沒有 env: prod，不符合；B 兩個都有，符合。這不是「符合其中一個就好」。

來源：多個 selector 條件以 AND 組合。

4. 自己改一次

先預測，再切換。選取 app: api 會找到誰？加上 env: prod 後呢？

概念練習：即時比對下列資料，不會操作 Kubernetes。

selector:
  app: web
Pod Aapp: web

Pod Bapp: webenv: prod

Pod Capp: api

5. 換一組資料，自己判斷

不要只記 A 或 B。這次 Pod 的標籤換了。

Pod Dapp: shoptier: frontend
Pod Eapp: shoptier: backend
Pod Fapp: billingtier: frontend

條件只有 app: shop

先用自己的話說一次

一個 Pod 具有 app: shop 與 version: v2。Service 只要求 app: shop。它會被選到嗎？請說明原因。

6. 回到實際設定

在 Pod 設定裡，標籤位於 metadata.labels；在 Service 設定裡，條件位於 spec.selector。以下只是要比較的片段，不是完整部署檔：

# Pod 的片段
metadata:
  name: shop-v2
  labels:
    app: shop
    version: v2

# Service 的片段
spec:
  selector:
    app: shop

Pod 名稱 shop-v2 不必與 Service 名稱一致。這個 selector 比較的是 app 標籤。

選到 ≠ 已證明連得通。

標籤匹配只回答「哪些 Pod 符合條件」。實際連線還要確認 Pod 是否就緒、服務埠與應用是否正常。本課先停在選取規則。

來源：Service 的定義與 selector。本課限定有 selector 的 Service；沒有 selector 的 Service 屬於另一種配置。

考試風格任務：修復選錯對象的 Service

原創模擬題，對應 Service 與 selector 能力；不是官方歷屆真題。第一次不限時，熟悉後挑戰 6 分鐘（教學目標，非官方配分或時限）。

任務：在 ckad-selector-lab Namespace，修正既有 store Service，只選取 app=store 且 tier=frontend 的 Pod。不得修改 Pod 標籤、重建 Service，或改變其 type、port、targetPort。

Pod             labels
store-front     app=store,tier=frontend
store-back      app=store,tier=backend
billing-front   app=billing,tier=frontend

store Service 現況：
spec:
  selector:
    app: store
    tier: backend
  ports:
  - port: 80
    targetPort: 80

先作答：目前選到誰？應修改哪個欄位？寫出修正後的 selector，以及你會用什麼證據證明選對了。手機先完成這三件事即可；下面提供真正的叢集練習。

需要提示：如何把觀念轉成操作

kubectl 是操作 Kubernetes 的命令列工具；-n 指定 Namespace；get 讀取資源；edit 編輯既有資源。先執行 kubectl -n ckad-selector-lab get pods --show-labels 與 kubectl -n ckad-selector-lab get service store -o yaml，再用 kubectl -n ckad-selector-lab edit service store。只修改 selector 裡必要的值。

叢集實作：準備練習環境（不計時）

在可拋棄的練習叢集操作。先用 kubectl config current-context 確認目前叢集；不要在工作環境執行。下載 練習初始設定，存成 selector-setup.yaml。這份檔案建立專用 Namespace、三個 Pod，以及故意選錯後端的 Service。

kubectl apply -f selector-setup.yaml
kubectl -n ckad-selector-lab wait --for=condition=Ready pod --all --timeout=120s

若等待失敗，先用 kubectl -n ckad-selector-lab describe pods 查看原因；映像下載或排程失敗不代表你答錯 selector。全部就緒後才開始解題。重新套用初始檔案會重設本題的 Service。

需要瀏覽器練習環境時，可從 Killercoda CKAD 社群練習挑選環境；部分課程需付費，本課不要求購買。GitHub Pages 本身沒有 Kubernetes 終端機。

完成後核對：解法與驗收

原本選到 store-back。應將 spec.selector.tier 改成 frontend，保留 app: store。除了 edit，也可用 patch（只更新指定欄位）：

kubectl -n ckad-selector-lab patch service store --type=merge -p '{"spec":{"selector":{"tier":"frontend"}}}'
kubectl -n ckad-selector-lab get service store -o yaml
kubectl -n ckad-selector-lab get pods -l app=store,tier=frontend -o wide
kubectl -n ckad-selector-lab get endpointslices -l kubernetes.io/service-name=store -o yaml

-l 依標籤篩選。EndpointSlice 是 Kubernetes 維護的 Service 後端清單；控制器更新需要少許時間。

  • Service selector 恰為 app=store、tier=frontend，原本 type、port、targetPort 保持不變。
  • 三個 Pod 的標籤保持不變；標籤查詢只列出 store-front。
  • EndpointSlice 的 endpoints 中，targetRef.name 只指向 store-front，conditions.ready 為 true；雙協定環境可能有多份 Slice，不能只數檔案或 IP。

這些證據驗收「選取與後端登錄」，不代表 HTTP 已連通。三個 Pod 都用 nginx，單看收到歡迎頁也不足以證明選對 Pod。

實作後貼回：修改指令／YAML、驗收輸出、花費時間、是否看過提示。只讀過解析請標記「尚未實作」。練習結束，確認名稱後可刪除本題專用 Namespace：kubectl delete namespace ckad-selector-lab。

變化題：隔一次學習再做

現在需求改為「選到 store 的前端與後端，但排除 billing」。只改 Service selector，寫出解法。想一想：把 app 改對，卻留下 tier 條件，會造成什麼結果？

作答後核對

selector 只保留 app: store，刪除 tier 條件，才能選到 store-front 與 store-back。若用 merge patch，必須明確移除舊鍵：

kubectl -n ckad-selector-lab patch service store --type=merge -p '{"spec":{"selector":{"app":"store","tier":null}}}'

重新核對 Pod 標籤與 EndpointSlice；只送 app 欄位不會自動清除原有 tier。

公開題型延伸：CKAD-exercises：Services and Networking（建立 Service、檢查後端的社群題）。本題另行設計修復情境與驗收。技術依據：Service 官方文件、kubectl patch。

今天留下這三件事

  • Label 是 Pod 帶著的鍵值標記；selector 是 Service 要求的條件。
  • 所有條件都必須符合；Pod 可以有額外標籤。
  • 判斷選取結果，和驗證真正連線，是兩個不同步驟。
