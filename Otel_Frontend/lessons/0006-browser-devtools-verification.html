Browser-Side Verification with DevTools

Milestone 3 · 不再猜「有沒有送」，而是用 Browser 證據逐層確認 click → Faro → /alloy

這堂課的目標
當你在 Foreman Assistant 操作一個真實 UI 元素後，你要能用 Browser DevTools 回答四件事：目前 live DOM 上實際有什麼 tracking attribute、Browser 是否有 click listener、Faro 是否真的產生 /alloy request，以及 request 的 payload / response 能證明到哪一層。

Lesson 5 已經建立這條預期資料流：

Browser click
   │ Browser dispatches event
   ▼
ClickInstrumentation
   │ extracts configured data-* values
   ▼
Faro event
   │ Transport batches / sends
   ▼
POST /alloy
   │
   └─ Browser CORS rules may apply

Lesson 6 不再只看「程式應該怎麼跑」。這堂課只接受你在 Browser 當下可以拿到的證據。

1. 先建立 Debug 原則：畫面有反應，不等於 telemetry 成功

你點一個 UI 元素後，頁面有反應，只能直接證明 application 的某個操作有發生。

它不能單獨證明：

  • 目前 click target 或 ancestor 真的有 data-link-name。
  • ClickInstrumentation 真的建立了 click telemetry。
  • Transport 真的送出了 /alloy request。
  • CORS 允許了這次 request。
  • Alloy 後面的 Collector / storage 已經成功。

因此 Browser-side debug 依序找三層證據：

① DOM evidence
   我現在實際選到哪個 node？tracking attribute 在哪裡？

② Runtime evidence
   Browser 現在是否真的有 click listener / callback 路徑？

③ Network evidence
   Browser 是否真的送出 /alloy？request 裡實際有什麼？
先找到第一個不符合 expected state 的 boundary，再決定往哪裡查。

2. Elements：先分清楚 source template 與 live DOM

Elements 顯示的是目前頁面正在使用的 live DOM。對 Lesson 6 而言，它不是拿來看 HTML 排版，而是拿來驗證 Browser 這一刻實際有哪些 node 與 attribute。

Chrome DevTools 官方：Elements panel overview、Get started with viewing and changing the DOM。

Foreman Assistant 的 source evidence 已驗證主畫面 template 有這個 dynamic binding：

<p-button [attr.data-link-name]="item.subsystem" ...>

這份 source evidence 可以證明：

item.subsystem 的 runtime 值
   │ Angular binding writes
   ▼
data-link-name attribute

但它不能證明目前部署中的某一個 subsystem 一定叫什麼名字。item.subsystem 是 runtime data；特定值必須從你眼前的 live DOM 讀出來，不能從教材先寫死。

Foreman Assistant source contract：foreman-integration evidence。目前 evidence 證明的是 dynamic binding 與 component boundary，不是某個固定 business subsystem 名稱。

另外，已驗證的 PrimeNG source 顯示 <p-button> host 會 render 內部 native <button>。因此 source model 可能是：

p-button[data-link-name="...runtime value..."]
   │ contains / renders
   ▼
button
   │ user click may hit this inner node
   ▼
event.target

注意「可能」兩個字：Lesson 6 的工作仍然是用 Elements 驗證目前 deployment 的實際 DOM，而不是拿 source model 當 runtime 結果。

3. Console：直接重做 ClickInstrumentation 的 DOM lookup

在 Elements 選中的 node，可以在 Console 用 $0 取得。

Chrome 官方：Access nodes in the Console、Console Utilities API。

目前 package 已驗證的 click contract 是：從 event.target 開始，對 configured attribute 執行 closest()，沿 ancestor 往上找。

現行 package contract：faro-click-tracking evidence。

所以選中一個真實 UI node 後，直接執行：

$0.tagName
$0.closest('[data-link-name]')
$0.closest('[data-link-name]')?.getAttribute('data-link-name')

只有兩種值得保留的結果：

結果你現在能證明什麼
得到一個字串目前這個 node 的 ancestor path 上真的存在 data-link-name；這個字串就是這次 runtime evidence。
得到 null / undefined目前這個 node 的 ancestor path 沒找到該 attribute；不要自行補一個預期值。

如果得到一個實際字串，把它抄下來。下面 Lab 會把這個「你自己讀到的原始值」稱為 TRACKING_VALUE。這只是 Lab 筆記名稱，不是 Foreman 的程式變數。

document 上真的有 click listener 嗎？

Chrome DevTools 還提供 getEventListeners() utility：

getEventListeners(document).click

如果得到 listener 陣列，你可以證明目前 document 上存在 click listener registrations；但不能只靠這個陣列就宣稱其中某個一定是 Faro。

真的需要 execution evidence 時，再使用 Sources → Event Listener Breakpoints → click，重做一次 click，從暫停位置與 call stack 看實際 callback。

Chrome 官方：Event listener breakpoints。

4. Network：真正回答 telemetry 有沒有離開 Browser

DOM 與 listener 都只是前置條件。要回答「Faro 有沒有往 receiver 送」，要看 Network。

Chrome 官方：Network panel overview、Network features reference。

最小流程：

  1. 開啟 DevTools → Network。
  2. 確認 recording 開啟。
  3. 清掉舊 request。
  4. Filter 輸入 alloy。
  5. 再做一次你準備驗證的 UI 操作。

不要建立這個錯誤等式：

1 click = 1 request = 1 event

目前 package 有 click throttle，而 Faro Transport 也可能 batch telemetry。因此你要找的是：操作之後產生的 request，能不能用 payload 裡的實際資料與剛才的 DOM evidence 對上。

5. 一個 /alloy request，固定看五個地方

1. Request URL / Method
2. Request Headers
3. Payload
4. Status / Response Headers
5. Response

5.1 URL / Method

先看 Browser 實際送去哪裡，不要從目前頁面的 hostname 猜 receiver。

目前 verified package resolver 是：

tw-stage → https://pek8s-staging.garmin.com/alloy
tw-prod  → https://shixpa-peproxy00.garmin.com/alloy

但 Lesson 6 的 runtime 判斷仍以 Network 顯示的 Request URL 為準。

Endpoint / CORS runtime evidence：browser-to-alloy evidence。

5.2 Headers

至少觀察：

Origin
Content-Type
X-Faro-Session-Id（如果有）
traceparent（目前只記錄有／沒有）

traceparent 的 propagation 意義留到 Lesson 7；這堂課只把它當成 Network evidence。

5.3 Payload

這裡不要先背 JSON path。先做最直接的 correlation：

Live DOM 讀到的 TRACKING_VALUE
   │ ClickInstrumentation extracts
   ▼
click event data
   │ Faro Transport sends
   ▼
/alloy request body 裡能找到同一個值

如果 request 存在，但找不到剛才的 TRACKING_VALUE，你現在只能說「這個 request 尚未證明就是剛才那個 tracked click」，不能直接把問題丟給 Collector。

接著再觀察 meta 裡實際出現的 user / session / device / app context。source configuration 只能告訴你「應該怎麼設定」，Network payload 才是這一刻的 runtime evidence。

5.4 Status / Response / CORS

如果看到 OPTIONS，那通常是 CORS preflight，不是 telemetry POST 本身。

OPTIONS
  ├─ Access-Control-Request-Method
  └─ Access-Control-Request-Headers

server response
  ├─ Access-Control-Allow-Origin
  ├─ Access-Control-Allow-Methods
  └─ Access-Control-Allow-Headers

目前 2026-09-12 的 read-only runtime evidence 只驗證 stage / prod endpoint 對測試 preflight 回過 204 與允許 headers；它沒有送 telemetry POST，因此不能拿那次結果取代你現在 Browser 裡的 POST evidence。

現行 CORS evidence：Browser Faro endpoint and Alloy receiver。

沒有看到 OPTIONS，不等於沒有 CORS
Browser 可能重用已快取的 preflight 結果。判斷這次是否成功，仍要一起看真正 POST、response 與 Console evidence。

MDN：Preflight request。

Hands-on Lab｜用現在看得到的 Foreman Assistant UI 跑一次

Lab 的核心規則：先觀察，再命名
這個 Lab 不預設任何 Foreman business function 名稱，也不預設某個 query parameter 一定存在。你只使用「目前 Stage 頁面真的看得到、Elements 真的選得到、Console 真的讀得到」的值。

使用 Stage Foreman Assistant：開啟 Stage Foreman Assistant 主畫面。

最後要拿到這五份 evidence：

Evidence你要回答的問題
Live DOM我實際選到哪個 node？ancestor path 有沒有 data-link-name？
Tracking value如果有，Browser 現在實際讀到的值是什麼？
Runtime listenerdocument 現在是否存在 click listeners？
Network request這次 UI 操作後是否產生可關聯的 /alloy request？
Payload / Response同一個 tracking value 是否進入 payload？HTTP boundary 結果是什麼？

Lab 0｜先把畫面與 Network 清乾淨

  1. 登入 Stage Foreman Assistant，停在 /foreman-assistant/#/main。
  2. 按 F12 打開 DevTools。
  3. 到 Network，確認 recording 開啟。
  4. 勾選 Preserve log。
  5. 按 Clear，Filter 輸入 alloy。
  6. 先不要做你要驗證的正常 click。

目的只有一個：減少舊 telemetry，讓後面的 request 比較容易跟這次操作做時間與 payload correlation。

Lab 1｜Element Picker：先找一個目前真的存在的 UI 元素

  1. 點 DevTools 左上角 Select an element，或按 Ctrl+Shift+C。
  2. 在 Foreman Assistant 主畫面，選一個你現在真的看得到的可點 UI 元素。不要照教材搜尋固定名稱。
  3. Elements 停住後，切到 Console。
  4. 執行：
$0.tagName
$0.closest('[data-link-name]')
$0.closest('[data-link-name]')?.getAttribute('data-link-name')

現在分兩條路：

A. 得到實際字串
   → 抄下原字串，後面稱為 TRACKING_VALUE

B. 得到 null / undefined
   → 這個 node 的 ancestor path 沒有 data-link-name
   → 這本身就是有效 evidence
   → 若你要完成 tracked-click E2E，再換另一個目前可見的 UI 元素測
不要因為 source 說 main template 有 dynamic binding，就替 runtime 補值
source 只證明 [attr.data-link-name]="item.subsystem" 這條 binding 存在於已驗證的 source revision。Lab 必須用 live DOM 證明目前部署實際 render 了什麼值、實際 ancestor 關係長什麼樣。

Lab 2｜確認 runtime listener 前置條件

Console 執行：

getEventListeners(document).click

記錄結果：

  • 有陣列：可以證明 document 現在有 click listener registrations。
  • 空或沒有：source expectation 與目前 runtime observation 不一致，這就是要定位的 boundary。

如果你需要證明某個 listener 是否真的執行 Faro 的 click callback，再使用 Event Listener Breakpoint；不要只看 listener 數量猜。

Lab 3｜正常操作一次，再看 /alloy

  1. 回 Network，再 Clear 一次，Filter 保持 alloy。
  2. 正常操作 Lab 1 選定的 UI 一次。
  3. 觀察這次操作之後新增的 /alloy request。
  4. 不要要求「一定立刻出現一個一對一 request」；Transport 可能 batch。

你現在只能做這兩種判斷：

有新的 /alloy request
   → Browser transport boundary 有 request evidence
   → 下一步看 payload 能否跟 TRACKING_VALUE 對上

沒有可觀察到的新 /alloy request
   → 還不能往 Collector 查
   → 回 Browser / Faro event / Transport boundary 定位

Lab 4｜用你自己讀到的 TRACKING_VALUE 做 payload correlation

如果 Lab 1 得到了一個實際 tracking value，現在打開操作後新增的 /alloy POST，切到 Payload。

直接找那個完全相同的原字串。

Live DOM
  data-link-name = TRACKING_VALUE
          │
          ▼
/alloy payload
  click event data 內找到同一個 TRACKING_VALUE

找到：你有一條從 live DOM → click extraction → network payload 的 runtime evidence chain。

找不到：只代表目前這個 request 還不能證明帶了那次 tracked click。回頭看 event callback、batching / request correlation 與 Transport，不要直接跳到 downstream。

接著再看 payload 實際存在的 user / session / device / app meta；只記錄你真的看到的欄位。

Lab 5｜最後才看 Headers / Response / CORS

對真正的 POST /alloy 記錄：

Request URL
Request Method
Origin
Content-Type
X-Faro-Session-Id（如果有）
traceparent（有／沒有）
Status
Response Headers
Response

如果同時看到 OPTIONS，再看它的 preflight request / response headers。不要把 OPTIONS 204 當成 POST 成功。

6. 證據層級：每一層能證明什麼

證據能證明不能單獨證明
頁面操作有反應Application 某段 UI 行為發生。Faro telemetry 已送出。
Live DOM 有 data-link-name目前 ancestor path 有可抽取資料。pushEvent() 已執行。
document 有 click listener目前有 listener registration。該 listener 一定是 Faro 或已執行。
/alloy POST 出現Browser 建立並送出 HTTP request。這個 request 一定含剛才的 click。
Payload 找到同一 tracking value這個 request 可與剛才 tracked click 關聯。Collector / storage 已成功。
POST 有成功 responseBrowser → receiver 這一跳有成功 evidence。Alloy 後續 pipeline 已完整成功。
Primary source 與 evidence
本課沿用 PI 前端監控案例 的 Foreman Assistant 情境、Grafana Faro & Alloy - 前端可觀測性 的 instrumentation / transport / meta 模型，以及 Faro-Click-Tracking Introduction 的 package 主線。現行 host integration 以 foreman-integration evidence 為準；click contract 以 faro-click-tracking evidence 為準；receiver / CORS 以 browser-to-alloy evidence 為準。

Self-check

Q1. Source template 有 [attr.data-link-name]="item.subsystem"，最合理的結論是？
Q2. $0.closest('[data-link-name]') 回傳 null，第一個合理結論是？
Q3. Network 完全沒有新的 /alloy request，下一步最合理的是？
Q4. Network 看到 OPTIONS 204，可以直接證明哪一件事？

Recap

  • Source template 與 runtime DOM 是兩層 evidence；dynamic binding 可以證明資料來源位置，不能替你證明目前實際值。
  • Elements + $0 用來驗證目前 target / ancestor path 是否真的有 data-link-name。
  • 找不到 attribute 也是有效 evidence；不要補一個教材預設值。
  • getEventListeners(document).click 能證明 listener registrations 存在，但不能單獨證明某個 callback 就是 Faro。
  • Network 才能回答 Browser 是否真的建立 / 送出 /alloy request。
  • 1 click 不保證 1 request；要用 live DOM 讀到的 tracking value 與 payload 做 correlation。
  • OPTIONS 是 preflight evidence，不等於 telemetry POST 成功。
  • POST 成功 response 只證明 Browser → receiver 這一跳；Alloy / Collector / storage 仍是後續 fault domains。
  • Debug 順序：Expected state → observed evidence → first broken boundary。
