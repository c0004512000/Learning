Browser-Side Verification with DevTools

Milestone 3 · 用 Elements、Console、Sources、Network 把 click → Faro → /alloy 一層一層證明

這堂課的目標
不是叫你「照著 DevTools 點幾個按鈕」。你要能看懂每一層畫面到底在證明什麼：live DOM 有沒有 tracking attribute、document 上有沒有 click listener、那個 listener 是否真的執行、哪一筆 Network request 才是 telemetry POST，以及 preflight / POST 分別該看 Headers、Payload 還是 Response。

Lesson 5 已經建立預期資料流：

Browser click
   │ Browser dispatches Event
   ▼
ClickInstrumentation
   │ extracts data-* value
   ▼
Faro click event
   │ Transport sends HTTP request
   ▼
POST /alloy

Lesson 6 要做的是把每一條箭頭換成 runtime evidence。

1. 先建立這堂課的 Debug 順序

① Elements / Console
   這個 UI 的 live DOM 到底有沒有 data-link-name？

② Console / Sources
   document 有 click listener 嗎？
   需要時，click 發生後到底執行了哪段 callback？

③ Network
   Browser 有沒有送 /alloy？
   哪一筆是 preflight？哪一筆才是 telemetry POST？

④ Payload / Response
   POST 裡有沒有剛才那個 click？
   receiver 對這筆 POST 回了什麼？
Expected state → observed evidence → first broken boundary。

2. Elements + Console：先把「我點了什麼」變成可驗證資料

Foreman Assistant source 已驗證主畫面 template 有：

<p-button [attr.data-link-name]="item.subsystem" ...>

這只能證明 source 會把 runtime 的 item.subsystem 寫進 data-link-name；實際值仍要看 live DOM。

Source contract：Foreman Assistant host integration。

用 Element Picker 選中你真的看得到的 UI，再到 Console 執行：

$0.tagName
$0.closest('[data-link-name]')
$0.closest('[data-link-name]')?.getAttribute('data-link-name')

你這次實際看到的是：

$0.tagName
→ "SPAN"

$0.closest('[data-link-name]')
→ p-button[data-link-name="EfficiencyAbnormalReport"]

getAttribute('data-link-name')
→ "EfficiencyAbnormalReport"

所以這次 runtime evidence 是：

SPAN
  │ closest('[data-link-name]') 往 ancestor 找
  ▼
p-button[data-link-name="EfficiencyAbnormalReport"]
這裡不需要任何 TRACKING_VALUE 之類的新名詞
後面只要一直說「剛才從 live DOM 讀到的 data-link-name 值」。你這次的值就是 EfficiencyAbnormalReport。這是目前這一次 runtime observation，不代表所有環境永遠都有同一個名稱。

本次實際 Browser observation：Foreman Assistant Browser DevTools lab evidence。

3. getEventListeners(document).click：畫面很多，但你只需要讀五件事

Console 執行：

getEventListeners(document).click

DevTools 回傳的是「目前註冊在 document 上的 click listeners 清單」。畫面裡會有很多 JavaScript object 細節，但這個 Lab 不需要全部懂。

你畫面上的欄位這堂課要怎麼讀
length: 1DevTools 目前看到 1 個 document click listener registration。
type: "click"這個 registration 處理的是 click event。
useCapture: false不是 capture listener；它在 bubbling 路徑上處理 click。
listener.name: "globalZoneAwareCallback"DevTools 目前露出的是 Zone.js wrapper function，不是直接把 Faro 的函式名稱顯示給你。
[[FunctionLocation]]: zone.js:1201這個 wrapper function 的程式位置。它只能證明目前看到的是 Zone.js 這層。

passive、once、Scopes、Prototype 等欄位目前不是 Lesson 6 的重點，不要被它們拖走。

你目前已經證明什麼？
document 上確實有一個 click listener registration，而且 DevTools 顯示它目前經過 Zone.js wrapper。你還沒有證明這個 wrapper 最後一定呼叫 Faro 的 click callback。

4. Event Listener Breakpoint：真正看「click 發生後跑了哪段程式」

getEventListeners() 看的是「已註冊什麼」。Event Listener Breakpoint 看的是「事件真的發生時，Browser 正在執行什麼」。Chrome 官方對這種 breakpoint 的定義就是：指定事件發生後，在 listener code 執行時暫停。

Chrome DevTools · Event listener breakpoints。

Lab 2A｜把 click breakpoint 打開

  1. 切到 Sources。
  2. 在右側找到 Event Listener Breakpoints。如果右側面板太窄，先展開側欄。
  3. 展開包含 click 的事件分類（Chromium DevTools 通常會放在 Mouse 類別）。
  4. 勾選 click。
  5. 回到 Foreman Assistant，正常點剛才那個 UI。
  6. JavaScript 會暫停；回 Sources 看目前停在哪一行，以及右側 Call Stack。

如果先停在 zone.js，不代表失敗

你剛才的 listener 本來就顯示 globalZoneAwareCallback 與 zone.js，所以 breakpoint 先停在 Zone.js wrapper 是合理結果。

Browser dispatch click
   │ calls registered listener
   ▼
Zone.js wrapper
   │ invokes wrapped callback/task
   ▼
實際 application / library callback

這時主要看 Call Stack，必要時使用 Step into 繼續往真正 callback 走。你要找的不是某個固定行號，而是能辨識 ClickInstrumentation 行為的 evidence，例如：

closest('[data-link-name]')
getAttribute('data-link-name')
pushEvent('click', ...)

如果 source map 能直接顯示 faro-click-tracking / clickInstrumentation，那會更容易；如果目前只能看到 Zone.js wrapper、無法追到 Faro callback，就要誠實記成「document click listener 已執行，但尚未把 execution path 證明到 Faro callback」。

5. 進 Network 以前，先學會看 request list

Network filter 輸入 alloy 後，你的畫面出現兩種不同 request：

Network row角色這堂課主要看哪裡
Type: preflight
Method: OPTIONS
Status: 204		Browser 先問 receiver：「接下來這種 cross-origin POST 可以送嗎？」Headers。不要期待 Payload；Response body 也通常不是重點。
Type: fetch
Method: POST
Status: 202		真正送 Faro telemetry 的 HTTP request。Headers + Payload + Status。Response body 有可能是空的。

所以不要看到每一列都從 Headers、Payload、Preview、Response 全部翻一次。不同 request 有不同問題。

Network list 的欄位先只讀這些

欄位你現在要知道的意思
Namerequest 的資源名稱；這裡都是 alloy，所以單靠 Name 分不出是哪一筆。
StatusHTTP status。你目前看到 preflight 204、POST 202。
Type快速分辨 preflight 與真正 fetch。
Initiator哪段 runtime code 觸發 request；看到 zone.js 只代表目前顯示的呼叫入口，不等於那筆一定是 click telemetry。
Time這筆 request 花多久；目前不是判斷 click 是否正確的主要 evidence。

6. Preflight：只回答「Browser 被允許送 POST 嗎？」

先點 Type = preflight 的那一列。你的畫面顯示：

Request Method: OPTIONS
Status Code: 204 No Content
Request URL: https://shixpa-peproxy00.garmin.com/alloy

這一筆主要看 Headers。

Request Headers 要問

Origin 是誰？
Access-Control-Request-Method 想送什麼 method？
Access-Control-Request-Headers 想帶哪些 headers？

Response Headers 要問

Access-Control-Allow-Origin 允許這個 origin 嗎？
Access-Control-Allow-Methods 允許 POST 嗎？
Access-Control-Allow-Headers 允許 Browser 想帶的 headers 嗎？

你這次畫面至少能看到 receiver 回：

Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: content-type,x-faro-session-id
Access-Control-Allow-Origin: *

DevTools 在 Response 顯示：

Failed to load response data
No content available for preflight request

在你這筆 204 No Content preflight 裡，這不是「request 壞掉」的證據。204 本來就表示沒有 response body；對 preflight，真正要看的就是 status 與 CORS response headers。

Preflight 成功 ≠ telemetry POST 成功
它只代表 Browser 在這組條件下得到「可以繼續送真正 request」的 CORS permission evidence。後面仍然要看 POST。

7. POST：這才是你要找 click telemetry 的地方

接著點 Type = fetch 的 alloy 列。先看 Headers → General：

Request Method: POST
Status Code: 202 Accepted
Request URL: https://shixpa-peproxy00.garmin.com/alloy

202 Accepted 可以證明 receiver 在 HTTP boundary 接受了這筆 request。它不能單獨證明 Collector / OpenSearch 已經成功。

POST 最重要的是 Payload

因為你現在要回答：

這幾筆 POST 裡，到底哪一筆是剛才那個 EfficiencyAbnormalReport click？

做法不是靠 request 順序猜，而是逐筆點 POST 的 Payload，找：

events
  └─ name: "click"
      └─ attributes
          └─ link_name: "EfficiencyAbnormalReport"

你這次已經找到一筆：

Live DOM
  data-link-name="EfficiencyAbnormalReport"
          │
          │ ClickInstrumentation extracts
          ▼
POST /alloy Payload
  events[0].name = "click"
  events[0].attributes.link_name = "EfficiencyAbnormalReport"
          │
          ▼
HTTP response
  202 Accepted
這才是 Lesson 6 最重要的一條 runtime evidence chain
不是「我看到一堆 alloy request」，而是「我在 DOM 讀到的同一個值，真的出現在某一筆 click event payload 裡，而且那筆 POST 收到 202」。

本次 runtime evidence：Foreman Assistant Browser DevTools lab evidence。

為什麼你看到好幾筆 202 POST？

不要先假設每一筆都是同一個 click。Faro 可以送不同 telemetry，Transport 也可能 batch。Lesson 6 的判斷方式永遠是看 Payload 內容做 correlation，不是看到四筆 POST 就猜「click 被送四次」。

8. POST 的 Response 要不要看？要，但它回答的是另一個問題

POST 的判讀順序：

General
  → URL / Method / Status 對不對？

Payload
  → 裡面是不是我剛才要驗證的 click？

Response Headers / Response
  → receiver 對這筆 request 回什麼？

你這次 POST 是 202 Accepted，Response header 還顯示 Content-Length: 0。因此 Response body 空白本身並不奇怪。

這層能證明：

Browser
  │ POST /alloy
  │ Payload contains matching click
  ▼
receiver
  │ returns 202
  ▼
Browser → receiver boundary 有成功 evidence

但下一段：

receiver → Alloy pipeline → Collector → storage

仍然需要後續 evidence，不能靠 202 直接推論完成。

Hands-on Lab｜完整重跑一次

Lab 0｜準備

  1. 登入 Stage Foreman Assistant 主畫面。
  2. 開 DevTools。
  3. Network 勾 Keep log / Preserve log，Filter 輸入 alloy。
  4. 先 Clear，避免舊 request 混進來。

Lab 1｜DOM

  1. Element Picker 選一個目前真的可點 UI。
  2. Console 執行 $0.tagName。
  3. 執行 $0.closest('[data-link-name]')。
  4. 執行 $0.closest('[data-link-name]')?.getAttribute('data-link-name')。
  5. 直接記住「剛才讀到的 data-link-name 值」，不要另外發明變數名稱。

Lab 2｜Listener registration

  1. 執行 getEventListeners(document).click。
  2. 只記錄：listener 數量、type、useCapture、listener function name / location。
  3. 不要因為看到 Zone.js wrapper 就宣稱已證明 Faro callback。

Lab 2A｜Listener execution

  1. Sources → Event Listener Breakpoints。
  2. 展開 click 所在分類並勾選 click。
  3. 正常操作同一個 UI。
  4. 暫停後看目前 source line 與 Call Stack。
  5. 若停在 Zone.js，沿 stack / Step into 繼續找真正 callback。
  6. 只有找到可辨識的 ClickInstrumentation execution path，才把「Faro click callback 已執行」記成已證實。

Lab 3｜Network：先分類，不要直接亂點 tab

  1. 回 Network，重新 Clear。
  2. 正常 click 一次。
  3. 先看每一列的 Type：preflight 還是 fetch。
  4. preflight → 看 Headers 的 CORS request / response headers。
  5. fetch POST → 先看 General 的 URL / Method / Status，再看 Payload。

Lab 4｜找出真正對應這次 click 的 POST

  1. 逐筆打開 fetch POST。
  2. 到 Payload 找 events[].name = "click"。
  3. 再找 attributes.link_name。
  4. 只有 link_name 等於剛才 live DOM 讀到的 data-link-name 值，才把這筆 POST 跟剛才 click 關聯起來。

Lab 5｜判斷 Browser → receiver boundary

  1. 確認這筆 matching POST 的 status。
  2. 看 Response Headers。
  3. Response body 空白時先看 status 與 Content-Length，不要自動當成失敗。
  4. 若 POST 成功，只把 Browser → receiver 標成有成功 evidence；不要跨到 Collector / storage。

Lab 6｜Evidence card

DOM:
  selected node = ?
  data-link-name ancestor = ?
  data-link-name value = ?

Listener registration:
  document click listener count = ?
  listener wrapper/name/location = ?

Listener execution:
  event breakpoint paused at = ?
  Faro callback path proven = yes / no / not yet

Preflight:
  OPTIONS URL = ?
  status = ?
  allow-origin / methods / headers = ?

Matching POST:
  POST URL = ?
  status = ?
  events[].name = ?
  attributes.link_name = ?
  是否等於 DOM 的 data-link-name = ?

Boundary conclusion:
  first broken boundary = ? / none observed through receiver

Recap

  • live DOM 的實際值先讀出來；不要拿教材 placeholder 取代 runtime evidence。
  • getEventListeners() 只先證明 registration；你這次看到的是 Zone.js wrapper。
  • Event Listener Breakpoint 用來取得 execution evidence；停在 Zone.js 時再沿 Call Stack / Step into 找真正 callback。
  • preflight 與 POST 是兩個不同問題：preflight 主要看 CORS Headers；POST 才看 click Payload。
  • 多筆 POST 不靠順序猜；用 DOM 的 data-link-name 與 Payload 的 link_name 做 correlation。
  • 202 Accepted 只證明 Browser → receiver；不能直接跳到 Collector / storage。
  • 本次 runtime 額外證明：Stage Foreman page 實際以 tw-prod Faro environment 送到 prod receiver；是否符合 intended policy 另行驗證。

如果 Event Listener Breakpoint 下一步停住，把 Sources 畫面 + Call Stack 截圖丟回來，就可以接著判讀那一層是不是 Faro callback。
