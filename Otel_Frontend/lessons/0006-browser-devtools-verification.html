Browser-Side Verification with DevTools

Milestone 3 · 用 Elements、Console、Sources、Network 把 click → Faro → /alloy 一層一層證明

這堂課的目標
不是叫你「照著 DevTools 點幾個按鈕」。你要能看懂每一層畫面到底在證明什麼：live DOM 有沒有 tracking attribute、document 上有沒有 click listener、那個 listener 是否真的執行、哪一筆 Network request 才是 telemetry POST，以及 preflight / POST 分別該看 Headers、Payload 還是 Response。

Lesson 5 已經建立預期資料流：

Browser click
   │ Browser dispatches Event
   ▼
ClickInstrumentation
   │ extracts data-* value
   ▼
Faro click event
   │ Transport sends HTTP request
   ▼
POST /alloy

Lesson 6 要做的是把每一條箭頭換成 runtime evidence。

兩份 observation，分開閱讀
原有教學例子沿用先前人工 DevTools evidence 的 EfficiencyAbnormalReport，來源見原文 evidence link。各節新增的「Runtime Lab 補充」使用 2026-09-16 Playwright + CDP 重新觀察的 DailySchedule；截圖與新 Evidence Card 對應這次補充，不替先前例子冒充 execution evidence。重跑時必須自己讀 live DOM，不預設任何名稱。

4. Event Listener Breakpoint：真正看「click 發生後跑了哪段程式」

getEventListeners() 看的是「已註冊什麼」。Event Listener Breakpoint 看的是「事件真的發生時，Browser 正在執行什麼」。Chrome 官方對這種 breakpoint 的定義就是：指定事件發生後，在 listener code 執行時暫停。

Chrome DevTools · Event listener breakpoints。

Lab 2A｜把 click breakpoint 打開

  1. 切到 Sources。
  2. 在右側找到 Event Listener Breakpoints。如果右側面板太窄，先展開側欄。
  3. 展開包含 click 的事件分類（Chromium DevTools 通常會放在 Mouse 類別）。
  4. 勾選 click。
  5. 回到 Foreman Assistant，正常點剛才那個 UI。
  6. JavaScript 會暫停；回 Sources 看目前停在哪一行，以及右側 Call Stack。

如果先停在 zone.js，不代表失敗

你剛才的 listener 本來就顯示 globalZoneAwareCallback 與 zone.js，所以 breakpoint 先停在 Zone.js wrapper 是合理結果。

Browser dispatch click
   │ calls registered listener
   ▼
Zone.js wrapper
   │ invokes wrapped callback/task
   ▼
實際 application / library callback

這時主要看 Call Stack，必要時使用 Step into 繼續往真正 callback 走。你要找的不是某個固定行號，而是能辨識 ClickInstrumentation 行為的 evidence，例如：

closest('[data-link-name]')
getAttribute('data-link-name')
pushEvent('click', ...)

如果 source map 能直接顯示 faro-click-tracking / clickInstrumentation，那會更容易；如果目前只能看到 Zone.js wrapper、無法追到 Faro callback，就要誠實記成「document click listener 已執行，但尚未把 execution path 證明到 Faro callback」。

Runtime Lab 補充｜4. Lab C｜breakpoint：從 Zone.js 走到 Faro callback

  1. 先勾 click，再對已選定、安全的 live UI 操作；停點出現後先讀 pause reason、script 與 Call Stack。
  2. 停在 Zone.js 或 Playwright 注入 listener 都不能直接叫 Faro。source map／ignore list 會影響第一個可見 frame；必要時顯示 ignore-listed frames，有限 stepping 或在已核對的 runtime callback 設 line breakpoint。
  3. 確認 handleClick 的 execution 停點後，再找 extraction／pushEvent；最後 Resume 並移除所有 breakpoint。停住期間 request 未完成，不應直接判 transport failure。

CDP 啟用 Debugger，再用 DOMDebugger.setEventListenerBreakpoint({ eventName: 'click' })。Playwright 點擊同一個 DailySchedule element 後，Browser 回報 Debugger.paused。

第一次停點確實是 Zone.js wrapper。Lab 沒有因此宣稱 Faro 已執行，而是對 #document listener 做有限 120 次 stepInto；總計保存 125 個 pause snapshots，最後實際走到：

pause reason = EventListener
top frame    = globalZoneAwareCallback
script       = /foreman-assistant/polyfills.js:970

bounded stepInto 後：
ClickInstrumentation.handleClick  /foreman-assistant/main.js:131710
getTrackedAttributeValue          /foreman-assistant/main.js:131697
toPayloadKey                      /foreman-assistant/main.js:131694
pushEvent                         /foreman-assistant/main.js:123009

這比「call stack 裡好像有 zone.js」更強：它把 Browser dispatch → Zone.js wrapper → Faro callback → extraction → pushEvent 串成 execution chain。行號是當次 deployed bundle 的 1-based line，只是 evidence locator，不是永久 contract。

Raw evidence：lesson6-click-breakpoint.json。

6. Preflight：只回答「Browser 被允許送 POST 嗎？」

先點 Type = preflight 的那一列。你的畫面顯示：

Request Method: OPTIONS
Status Code: 204 No Content
Request URL: https://shixpa-peproxy00.garmin.com/alloy

這一筆主要看 Headers。

Request Headers 要問

Origin 是誰？
Access-Control-Request-Method 想送什麼 method？
Access-Control-Request-Headers 想帶哪些 headers？

Response Headers 要問

Access-Control-Allow-Origin 允許這個 origin 嗎？
Access-Control-Allow-Methods 允許 POST 嗎？
Access-Control-Allow-Headers 允許 Browser 想帶的 headers 嗎？

你這次畫面至少能看到 receiver 回：

Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: content-type,x-faro-session-id
Access-Control-Allow-Origin: *

DevTools 在 Response 顯示：

Failed to load response data
No content available for preflight request

在你這筆 204 No Content preflight 裡，這不是「request 壞掉」的證據。204 本來就表示沒有 response body；對 preflight，真正要看的就是 status 與 CORS response headers。

Preflight 成功 ≠ telemetry POST 成功
它只代表 Browser 在這組條件下得到「可以繼續送真正 request」的 CORS permission evidence。後面仍然要看 POST。

Runtime Lab 補充｜6. Lab E｜OPTIONS：Browser 先問「我可以這樣 POST 嗎？」

此次 response body 是 Not available。在 204 No Content preflight，沒有 body 是正常可能結果；不能把 DevTools 的「No content available for preflight request」直接解讀成 request failure。

7. POST：這才是你要找 click telemetry 的地方

接著點 Type = fetch 的 alloy 列。先看 Headers → General：

Request Method: POST
Status Code: 202 Accepted
Request URL: https://shixpa-peproxy00.garmin.com/alloy

202 Accepted 可以證明 receiver 在 HTTP boundary 接受了這筆 request。它不能單獨證明 Collector / OpenSearch 已經成功。

POST 最重要的是 Payload

因為你現在要回答：

這幾筆 POST 裡，到底哪一筆是剛才那個 EfficiencyAbnormalReport click？

做法不是靠 request 順序猜，而是逐筆點 POST 的 Payload，找：

events
  └─ name: "click"
      └─ attributes
          └─ link_name: "EfficiencyAbnormalReport"

你這次已經找到一筆：

Live DOM
  data-link-name="EfficiencyAbnormalReport"
          │
          │ ClickInstrumentation extracts
          ▼
POST /alloy Payload
  events[0].name = "click"
  events[0].attributes.link_name = "EfficiencyAbnormalReport"
          │
          ▼
HTTP response
  202 Accepted
這才是 Lesson 6 最重要的一條 runtime evidence chain
不是「我看到一堆 alloy request」，而是「我在 DOM 讀到的同一個值，真的出現在某一筆 click event payload 裡，而且那筆 POST 收到 202」。

本次 runtime evidence：Foreman Assistant Browser DevTools lab evidence。

為什麼你看到好幾筆 202 POST？

不要先假設每一筆都是同一個 click。Faro 可以送不同 telemetry，Transport 也可能 batch。Lesson 6 的判斷方式永遠是看 Payload 內容做 correlation，不是看到四筆 POST 就猜「click 被送四次」。

  4. 只有 link_name 等於剛才 live DOM 讀到的 data-link-name 值，才把這筆 POST 跟剛才 click 關聯起來。

Lab 5｜判斷 Browser → receiver boundary

  1. 確認這筆 matching POST 的 status。
  2. 看 Response Headers。
  3. Response body 空白時先看 status 與 Content-Length，不要自動當成失敗。
  4. 若 POST 成功，只把 Browser → receiver 標成有成功 evidence；不要跨到 Collector / storage。

Recap

  • live DOM 的實際值先讀出來；不要拿教材 placeholder 取代 runtime evidence。
  • getEventListeners() 只先證明 registration；你這次看到的是 Zone.js wrapper。
  • Event Listener Breakpoint 用來取得 execution evidence；停在 Zone.js 時再沿 Call Stack / Step into 找真正 callback。
  • preflight 與 POST 是兩個不同問題：preflight 主要看 CORS Headers；POST 才看 click Payload。
  • 多筆 POST 不靠順序猜；用 DOM 的 data-link-name 與 Payload 的 link_name 做 correlation。
  • 202 Accepted 只證明 Browser → receiver；不能直接跳到 Collector / storage。
  • 本次 runtime 額外證明：Stage Foreman page 實際以 tw-prod Faro environment 送到 prod receiver；是否符合 intended policy 另行驗證。

如果 Event Listener Breakpoint 下一步停住，把 Sources 畫面 + Call Stack 截圖丟回來，就可以接著判讀那一層是不是 Faro callback。
