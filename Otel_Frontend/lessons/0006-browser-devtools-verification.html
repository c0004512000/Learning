Browser-Side Verification with DevTools

Milestone 3 · 不再猜「有沒有送」，而是用 Browser 證據逐層確認 click → Faro → /alloy

這堂課的目標
當你在前端頁面點一下之後，不再只看「畫面有沒有反應」。你要能用 Browser DevTools 回答：實際點到哪個 DOM element、Faro 會從哪裡讀取追蹤欄位、click listener 是否存在、/alloy request 是否真的出現、request 裡帶了什麼，以及失敗時應該把問題留在 Browser 還是往 Alloy 後面追。

Lesson 5 已經建立這條因果鏈：

Browser click
   │
   ▼
ClickInstrumentation
   │ creates Faro telemetry
   ▼
Faro Transport
   │ sends HTTP request
   ▼
/alloy
   │
   └─ Browser CORS rules may apply

但這仍然只是程式應該怎麼運作。

Lesson 6 要做的，是把「應該」變成「我在 Browser 裡真的看到了什麼」。

1. 先建立 Debug 原則：畫面有反應，不等於 telemetry 成功

假設你在 Foreman Assistant 點了一個連結，頁面成功換頁。

這只能證明：

使用者 click
   │
   └─ 某段 application 行為成功發生

它不能直接證明：

  • Faro ClickInstrumentation 真的讀到了正確的 data-link-name。
  • api.pushEvent() 真的產生了 click telemetry。
  • Transport 真的送出了 /alloy request。
  • CORS 沒有擋住 request。
  • Alloy 已經收到並往後送到 Collector。

所以 Browser-side debug 要依序留下三類證據：

① DOM evidence
   「我實際點到什麼？追蹤 attribute 在哪裡？」

② Runtime evidence
   「Browser 上是否真的有 click listener / callback 路徑？」

③ Network evidence
   「Faro 是否真的把 request 送到 /alloy？送了什麼？收到什麼？」

順序很重要：如果第一層就不對，不要先跳去查 Alloy。

2. Elements：先證明你實際點到哪個 DOM element

Elements 是 DevTools 用來查看目前頁面 live DOM 的面板。Chrome 官方文件也把它定位成檢查與操作 DOM element 的主要介面。

Chrome DevTools 官方：Elements panel overview、Get started with viewing and changing the DOM。

對 Faro click tracking，第一個問題不是「Network 有沒有 request」，而是：

Browser 認為我剛才點的那個 element，到底是哪一個 DOM object？

操作方式：

  1. 在頁面上對你準備測試的文字、按鈕或連結按右鍵。
  2. 選擇 Inspect。
  3. Elements 會直接選中那個 DOM node。
  4. 檢查它自己或 ancestor 是否存在目前 package 會追蹤的 data-link-name。

例如畫面實際 DOM 可能是：

<a data-link-name="DailySchedule" href="...">
  <span>每日生產排程</span>
</a>

如果使用者實際點到的是內層 <span>，那麼 Browser Event 的 target 可以是這個 <span>。

但 Lesson 2 已經建立過：目前 ClickInstrumentation 不只檢查 target 自己，而是從 event.target 開始執行 closest('[data-link-name]') 往 ancestor 找。

span  ← actual click target
  │ closest('[data-link-name]')
  ▼
a[data-link-name="DailySchedule"]
  │ getAttribute(...)
  ▼
"DailySchedule"

現行 package contract 以 faro-click-tracking evidence 為準：listener 從 event.target 開始，對每個設定的 data-* attribute 使用 closest() 往 ancestor 查找。

Elements 在這裡不是拿來「看 HTML 長得漂不漂亮」
它是在回答第一個 fault-domain 問題：如果 target / ancestor 根本沒有需要的 data-link-name，那麼 click payload 缺欄位是合理結果；此時問題仍在 DOM / host integration，還沒資格往 Network 查。

3. Console：把 Elements 選中的 DOM object 拿來直接驗證

Chrome DevTools 有一個很實用的橋接：你在 Elements 目前選中的 DOM node，可以在 Console 用 $0 取得。

Chrome 官方文件：Elements 選中的 node 可透過 Console 的 $0 直接參照：Access nodes in the Console、Console Utilities API。

所以選中剛才的 element 後，你可以先輸入：

$0

接著直接重做 ClickInstrumentation 最關鍵的 DOM lookup：

$0.closest('[data-link-name]')

如果有命中，再看值：

$0.closest('[data-link-name]')?.getAttribute('data-link-name')

如果得到：

"DailySchedule"

你現在證明的是：

目前選中的 DOM target
   │
   └─ 沿 ancestor chain 可以找到 data-link-name
          │
          └─ 值是 "DailySchedule"

這比「我看 source code 覺得應該抓得到」更強，因為你檢查的是目前 Browser 裡實際存在的 DOM。

那 document 上的 click listener 呢？

Chrome Console 還提供 DevTools 專用的 getEventListeners() utility。它不是你 application source code 的標準 JavaScript API，而是 DevTools 提供的除錯工具。

可以檢查：

getEventListeners(document).click

如果目前頁面真的已經初始化 ClickInstrumentation，你預期會在 document 上看到 click listener；但不要因為「看到一個 click listener」就直接宣稱那一定是 Faro，因為同一頁也可能有其他程式註冊 document click listener。

因此這一層證據的正確說法是：

「document 上存在 click listener；若要證明其中某一個就是 Faro 的 handleClick，還需要進一步看 handler source 或在事件執行時暫停。」
只有真的需要證明 callback 執行時才做這一步
DevTools 可以在 click event listener 執行時暫停 JavaScript。Chrome 官方稱為 Event listener breakpoint：先告訴 Browser「下一次 click listener 被執行時暫停」，再重做 click，就能從實際暫停位置與 call stack 看目前是哪個 callback 在跑。這是 execution evidence，不需要每次正常驗證都開。

Chrome DevTools · Event listener breakpoints。

4. Network：真正回答「telemetry 有沒有離開 Browser」

到這裡你只證明了 DOM 與 runtime 前置條件。下一個問題才是：

這次操作之後，Browser 有沒有真的送出 Faro network request？

Chrome 的 Network panel 會在 DevTools 開啟期間記錄 network requests，並讓你查看 request 的 URL、method、headers、payload、response 與 status。

Chrome 官方：Network panel overview、Network features reference。

最小驗證流程：

  1. 先打開 DevTools → Network。
  2. 清掉舊 request，避免把之前的 request 誤認成這次 click。
  3. Filter 輸入 alloy。
  4. 回到頁面做一次測試 click。
  5. 觀察是否出現新的 /alloy request。

如果完全沒有新的 /alloy request，先不要碰 Alloy config。

DOM attribute 正常
   │
   ▼
listener / callback path 是否正常？
   │
   ▼
Faro telemetry 是否真的產生？
   │
   ▼
Transport 是否真的送出？

[ Network 完全沒有 /alloy ]
→ fault domain 仍在 Browser / Faro 端

5. 一個 /alloy request，要固定看這五個地方

點開 Network 中的 /alloy request 後，不要先亂翻。固定用同一個順序看：

1. Request URL / Method
2. Request Headers
3. Payload
4. Status / Response Headers
5. Response

5.1 Request URL / Method：先確認是不是送到你以為的環境

Lesson 5 已經知道 environment 會決定 receiver URL。

所以第一眼先看：

Request URL: https://.../alloy
Request Method: POST  或  OPTIONS

如果你正在 tw-stage 測試，但實際 request URL 指到 production host，第一個問題就不是 CORS，也不是 Alloy parser，而是：

host environment
   │
   ▼
package environment resolver
   │
   ▼
receiver URL

目前 verified stage/prod mapping 與 receiver contract：browser-to-alloy evidence。

5.2 Request Headers：看 HTTP transport contract

Lesson 5 已經建立一個重要邊界：

telemetry body ≠ HTTP headers

所以在 Headers 裡，至少確認：

  • Origin：是哪個頁面 origin 發起這次 cross-origin request。
  • Content-Type：Browser 實際送出的 content type。
  • X-Faro-Session-Id：若這次 transport 有帶，確認它是在 HTTP header 層。
  • traceparent：目前先只觀察「有沒有」，其 propagation 意義留到 Lesson 7。
不要提前展開 traceparent
Lesson 6 只把它當成「你可以在 Network Headers 看見的證據」。它怎麼把 frontend/backend 接成同一條 trace，是 Lesson 7 的主題。

5.3 Payload：確認「這次 request 實際帶了什麼」

Lesson 5 已經知道 network request 是傳輸單位，不一定等於單一 telemetry event。

所以打開 Payload 時，不要預設：

1 click = 1 request = 1 event

而是找：

request body
  ├─ meta
  ├─ events[]
  ├─ logs[]
  ├─ exceptions[]
  ├─ measurements[]
  └─ traces ...

如果這次是測試 click tracking，你要把問題拆成兩個：

  1. 事件本身：events 裡有沒有你剛才那個 click 對應的資料，例如由 data-link-name 轉出的欄位。
  2. 背景資訊：meta 裡的 app / user / session / device 是否符合你預期。

這就是 Lesson 4 與 Lesson 5 的模型真正變成可觀察證據的地方：

DOM data-link-name
   │ ClickInstrumentation extracts
   ▼
click payload

getUser / device / app context
   │ Faro meta system attaches
   ▼
meta

payload + meta
   │ Transport batches / sends
   ▼
Network request body

Primary materials 對 Faro events / meta / transport 的描述：Grafana Faro & Alloy - 前端可觀測性；目前 click payload extraction contract：faro-click-tracking evidence。

5.4 Status / Response Headers：判斷 Browser 到 receiver 這一跳發生了什麼

如果 Network 看到的是 OPTIONS，它通常不是 telemetry body 本身，而是 Browser 的 CORS preflight。

這時要看 response headers 是否允許真正 request 所需要的條件，例如：

Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers

目前 2026-09-12 的 read-only runtime evidence 已經驗證 stage/prod /alloy endpoint 對測試中的：

POST
content-type
x-faro-session-id
traceparent

回過允許的 preflight response。

但這個 evidence 只證明當時測試的 CORS contract，不等於你現在這一筆 Browser POST 已經成功。

現行 evidence：Browser Faro endpoint and Alloy receiver。該次驗證只有 OPTIONS，刻意沒有送 telemetry POST。

5.5 Response：不要把「有 request」誤當成「receiver 接受成功」

Network list 出現 /alloy 只證明 Browser 建立過這次 request 記錄。

你還需要看：

  • Status 是否成功。
  • Browser 是否顯示 CORS error / blocked 狀態。
  • Response body 是否有 receiver 回覆內容。

如果 Browser 已經拿到成功 response，你才有理由把下一個問題往後推：

Browser
   │ POST /alloy
   │ ← success response
   ▼
[ Browser → receiver 這一跳有成功證據 ]

下一步才是：
Alloy 收到後有沒有送 Collector？
Collector 有沒有 export？
storage 有沒有寫入？

Alloy 內部與 Collector pipeline 是 Lesson 9，這堂課不要跳過 fault-domain boundary。

6. CORS 問題要怎麼看，才不會只盯 Console error

Console 出現 CORS error 很有用，但它是症狀入口，不是完整證據。

真正 Debug 時，把 Console 與 Network 配在一起：

Console
  └─ 告訴你 Browser 判定 cross-origin access 失敗

Network
  ├─ 有沒有 OPTIONS？
  ├─ OPTIONS 去哪個 URL？
  ├─ request 要求哪些 method / headers？
  ├─ server 回了哪些 Access-Control-Allow-*？
  └─ 真正 POST 有沒有發生？

這樣你才能區分：

觀察到的證據比較合理的下一步
沒有 /alloy request留在 Browser / Faro lifecycle / Transport 查。
有 OPTIONS，但 preflight 被拒絕查 origin、requested method/headers 與 receiver/gateway CORS response。
OPTIONS 成功，但 POST 沒出現回查 Browser console、Transport 執行與 request 建立條件。
POST 出現，但 HTTP response 失敗查 receiver route、gateway、Alloy endpoint 接收結果。
POST 成功，但 Grafana/OpenSearch 沒資料Browser-side boundary 已有成功證據，往 Alloy / Collector / storage 查。

7. 一次完整驗證：從 click 到 /alloy

在允許產生測試 telemetry 的環境中，可以固定照這個順序：

  1. Elements：Inspect 要測的 element。
  2. Console：用 $0.closest('[data-link-name]') 驗證實際 DOM lookup。
  3. Console：必要時用 getEventListeners(document).click 確認 document 上存在 click listeners。
  4. Network：清除舊紀錄，filter alloy。
  5. 重做一次 click。
  6. Headers：核對 URL、method、Origin、transport headers。
  7. Payload：核對 click event data 與 meta。
  8. Response：確認 Browser 到 receiver 的 HTTP 結果。
  9. 最後才決定下一個 fault domain。

把它壓成一句 SRE debugging model：

Expected state → observed evidence → first broken boundary。

例如：

Expected:
click DailySchedule
  → payload 有 link_name
  → POST 到 stage /alloy
  → HTTP success

Observed:
DOM 有 data-link-name
Network 完全沒有 /alloy

Conclusion:
先不要查 Collector。
第一個 broken boundary 還在 Faro / Browser transport 之前。

8. 這堂課最重要的不是 DevTools 按鈕，而是「證據層級」

證據它能證明什麼它不能單獨證明什麼
頁面成功換頁Application 的某個 click 行為有效。Faro telemetry 已產生或送出。
Elements 有 data-link-name目前 live DOM 有可供 extraction 的資料。pushEvent() 一定已執行。
document 有 click listener至少有程式向 document 註冊 click listener。那個 listener 一定是 Faro，或剛才已執行。
Network 有 /alloy POSTBrowser 建立並送出該 HTTP request。Collector / storage 已成功。
POST 有成功 responseBrowser → receiver 這一跳有成功證據。Alloy 後續 pipeline 已完整成功。
Primary source 與 evidence
本課沿用 PI 前端監控案例 的 Foreman Assistant click-tracking情境、Grafana Faro & Alloy - 前端可觀測性 的 instrumentation / transport / meta 模型，以及 Faro-Click-Tracking Introduction 的 package 主線。現行 click contract 以 faro-click-tracking evidence 為準；stage/prod receiver 與 CORS contract 以 browser-to-alloy evidence 為準。DevTools 操作則以 Chrome 官方 Elements / Console / Network 文件補足原教材沒有完整教學的操作細節。

Self-check

Q1. 你點了一個連結，頁面正常換頁。這件事本身最能證明什麼？
Q2. Elements 選中的 node 在 Console 用 $0 取得後，最適合怎麼驗證目前 click attribute lookup？
Q3. Network 完全沒有新的 /alloy request 時，第一個合理結論是什麼？
Q4. Network 看到 OPTIONS 204，可以直接證明哪一件事？
Q5. /alloy POST 有成功 response，但 Grafana / OpenSearch 沒資料，下一步應該往哪裡查？

Recap

  • 畫面有反應不是 telemetry evidence；Browser-side verification 要拆成 DOM、runtime、network 三層。
  • Elements 用來檢查目前 live DOM，先確認實際 target / ancestor 是否真的有追蹤所需的 data-*。
  • $0 把 Elements 目前選中的 DOM node 帶到 Console，可直接重做 closest() lookup。
  • getEventListeners(document).click 可確認 document 上有哪些 click listeners；看到 listener 不代表已證明它就是 Faro callback。
  • 需要 execution evidence 時，event listener breakpoint 可以在 click callback 真正執行時暫停。
  • Network 才能回答 telemetry 是否真的跨 Browser network boundary 往 /alloy 送。
  • Headers 驗證 HTTP transport contract；Payload 驗證 events / meta 實際資料；兩者不要混成同一層。
  • OPTIONS 是 preflight evidence，不等於 telemetry POST 已成功。
  • POST 成功 response 才代表 Browser → receiver 這一跳有成功證據；Alloy / Collector / storage 仍是後續 fault domains。
  • Debug 順序：Expected state → observed evidence → first broken boundary。
