Special Lesson｜從 Frontend Repo 到 Grafana

工作導向插課：設計、審查與除錯 Faro 自動導入 Skill

這堂課的交付物

你要能審查一個 Agent Skill：它是否真的找到 Frontend 的執行路徑、補上最小 Faro 變更，並用 Browser 與 Grafana 的資料驗收。這堂課不要求你重建觀測平台，也不改變主線 Lesson 順序。

本課的 runtime example 都標成 Jeter stage demo。先看畫面，再用短解釋建立模型；完整 raw evidence 放在課後來源，不是主要操作路徑。

1. Agent 面對陌生 repo，先找真正的 runtime path

Agent 不應一拿到 repo 就貼入 Faro 初始化。先回答「應用從哪裡啟動」與「真正的 API request 從哪裡送出」，才能避免改到沒有被 Browser 執行的檔案。

先找的實物它回答什麼找不到怎麼辦
package-lock.json、yarn.lock、pnpm-lock.yamlpackage manager 與可重現的指令讀 repo 既有 script，不要猜指令。
entry point、Faro dependency、初始化Faro 是否已在 Browser 啟動已有初始化先檢查，避免雙重初始化。
runtime config、backend base URL部署後實際呼叫哪個 API向專案取得環境 URL，不要硬編碼 Jeter URL。
fetch、XHR、axios、custom wrapper哪個程式送出 business request追 wrapper，並用 Browser Network 確認。

Foreman 是 Angular、Jeter 是 React；它們只提供辨識方法的對照。參考：Foreman source evidence、Jeter source evidence。

2. 先分清兩條網路路徑

backendUrls 是 tracing instrumentation 用來匹配業務 API URL 的設定概念；它不是 Alloy receiver URL。Business request 也不是 telemetry export request。即使 header 傳出去了，Frontend span 還是要靠 Path B 送到 Tempo，Backend span 也要有自己的 export。

參考：trace context、Browser → Alloy、Collector pipeline。

3. Jeter：用一筆 Slow request 驗收 distributed trace

先記住操作，而不是先背 ID：按一次 Slow，接著在 Network 找同一個 business request。

你現在看到的是 Path A 的 request。下一個觀察是它的 Request Headers，因為跨 Browser 與 Backend 的 relationship 會放在那裡。

先不用背整串。只取兩個值：T 是整條 trace，A 是 Browser 這個 client span。

把 header 讀成關係

Tempo：先查 T，再看兩端 span

查詢欄的 T 是 e0a53e… 這一筆 runtime trace。圖中的省略只為了降低 working-memory 負擔；不要拿另一筆 trace 的 ID 來比。

因此這一筆 Jeter Slow request 的結論是：

Browser 的 traceparent 帶出 T 與 A；Tempo 查到同一個 T；Backend server span 的 parent 是 A。這是這一筆 request 的證明，不是所有 endpoint 或所有 Frontend repo 的保證。

Lab 1｜重做一次 Browser 檢查

做什麼：在有授權的 Jeter stage demo 開啟 DevTools → Network，清空舊列，按一次 Slow，再選 GET 的 scenario/slow。

看哪裡：Headers → Request Headers → traceparent。把當次 T 與 A 記到私人筆記，不要把 credential 或 cookie 存進 repo。

判斷：有 header 才能繼續查關係；HTTP 200 只證明 API 回應成功。沒有 header 時，檢查實際 URL 是否匹配 propagation pattern、HTTP wrapper 是否被 instrumentation 覆蓋，以及 CORS 是否允許 header。

Lab 2｜把當次 T 帶到 Tempo

做什麼：到有權限的 Grafana Explore，選 Tempo，貼上當次 trace ID。

判斷：同一 T 加上 Frontend client 與 Backend server 才是第一層證據；Backend parent = Frontend span 才完成 join。只有其中一端時，先查該端的 telemetry export 或 context extraction。

4. Frontend error：從 Console 走到 Loki

這次使用 Jeter stage 的受控錯誤 marker OTEL_VISUAL_CHECK_20260920_B。它是 unique test identifier，不是時間戳，也沒有改動業務資料。因為沒有觀察到安全的 error button，這一段是 Evidence Walkthrough，不是要求 learner 注入 exception 的 Lab。

第一個 boundary 已證明：Browser 有 error。接著看同一個 marker 是否進入 Faro 的 outbound payload。

這裡不是用舊的 Foreman dashboard query。查詢條件必須與當前 runtime service 和 marker 相符。

現在才可以下完整結論：同一個 marker 從 Browser Console → Faro exceptions[] → receiver 202 → Grafana Loki result 被對上。Collector 的 record-specific receive/export metrics 沒有在本次 capture 取得，因此不能把每一個 Collector hop 寫成已逐跳觀察。

觀察這次能證明還不能證明
Console markerBrowser 真的發生 errorFaro 或 storage 已收到
exceptions[]Faro 把 error 放進 outbound payloaddownstream storage 可查
HTTP 202receiver 接受 requestLoki 一定有資料
Loki Total: 1這筆 marker 在 Grafana 可查所有 Collector hop 都有逐筆 metrics
Evidence source 與限制

完整去敏紀錄在 visual runtime evidence 與 raw projection。既有 Alloy → Collector → Loki 路徑屬於 source/config evidence；本次只把 receiver acceptance 與 Loki visibility 分開驗證，沒有改 dashboard 或 production data。

5. 把觀察抽象成 Agent Skill decision flow

GENERIC｜可重用的 Skill 工作

  • 找 entry point 與 package manager
  • 找 Faro dependency / initialization
  • 找 fetch、XHR、axios、custom client
  • 找 backend base URL 與 propagation pattern
  • 檢查 error capture、API tracing、Faro export
  • build/test，做 Browser 與 Grafana runtime verify

PROJECT-SPECIFIC｜不能硬套的語意

  • Foreman 的 data-link-name
  • Foreman 的 subsystem
  • business KPI 與 click semantics
  • 特定 user callback 或 domain event
  • 部署 URL、CORS policy、可用的安全測試 path

通用 Skill 應把左欄做成檢查流程；右欄要保留現有專案語意，或明確要求 project-specific input。不能因為 Foreman 有欄位，就把它變成所有 Frontend 的 Faro requirement。

Agent 必做的檢查分類找不到／失敗時
1. Detect frontend frameworkgeneric讀 package scripts 與 source 結構；不確定就保留未知。
2. Detect package managergeneric用 lockfile 決定安裝／驗證指令，不要猜。
3. Detect existing Faro dependencygeneric缺少才規劃導入；已有則檢查版本與用途。
4. Find application entry pointgeneric追到 Browser 真正載入的 module。
5. Find Faro initializationgeneric已有初始化先保留，避免雙重初始化。
6. Find runtime environment / config sourcegeneric method / project value確認 deployment config；不要把 stage URL 寫死。
7. Detect HTTP mechanismgeneric檢查 fetch、XHR、axios 與 custom wrapper。
8. Detect backend base URLsgeneric method / project valueURL 不明不可猜，需要 project input。
9. Determine trace propagation URL patternsgeneric method / project value用實際 Network request 確認 pattern 是否 match。
10. Check frontend error instrumentationgeneric分開確認 Console error 是否進 Faro payload。
11. Check API request tracinggeneric確認 business request 是否產生 client span。
12. Preserve existing business instrumentationgeneric rule / project fields保留 business logic，不移植 Foreman 欄位。
13. Apply minimal code changesgeneric只補已證明的缺口，避免重寫既有 client。
14. Build / testgenericbuild 成功不等於 runtime 成功。
15. Verify browser telemetrygeneric method / environment access看 Console、Network、payload 與 status。
16. Verify collector deliverygeneric method / environment access若沒有 record-specific evidence，標為未證明。
17. Verify Grafana visibilitygeneric method / environment access用正確 datasource、時間與 query 查 storage。
18. Verify frontend-backend correlation when tracing existsconditional generic用當次 T 檢查 Backend parent = Frontend span；沒有 Backend tracing 就標明未適用。

這個順序整理自 skill-design findings；它是設計與審查 checklist，不是現在要直接寫出的完整 Skill。

6. Debug 時找第一個證據中斷

審查 Agent 結果時，記三欄：預期、實際觀察、證據位置。只有設定時寫「configuration verified」；有 Browser header 不等於 Tempo join；有 202 不等於 Loki visibility。

Self-check

Q1. Browser business API request 有 traceparent，可以宣稱 Tempo 一定有完整 frontend + backend trace 嗎？
Q2. Faro POST 回 202，能直接宣稱 Grafana 查得到嗎？
Q3. 通用 Frontend Faro Skill 應把 Foreman 的 data-link-name 寫成每個 repo 的必要欄位嗎？

Recap

  • Agent 先找 repo 的 entry point、Faro、HTTP client 與 runtime URL，再決定最小修改。
  • Business request 傳 traceparent；Faro 的 /alloy POST 送 telemetry，兩條路徑分開驗證。
  • Jeter Slow 的一筆 request 已以同一 T、Frontend span A、Backend parent = A 證明 runtime join。
  • Jeter 受控 error 已以 Console marker、exceptions[]、202 與 Loki result 完成對應；逐筆 Collector hop 仍保留為未觀察 boundary。
  • Foreman 的 data-link-name 與 subsystem 是 project-specific，不是通用 Faro requirement。
