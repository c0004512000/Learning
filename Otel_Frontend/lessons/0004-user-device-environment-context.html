User, Device, and Environment Context

Milestone 2 · 一筆 telemetry 的背景，誰提供、何時更新

本課目標
看到 user、device、environment 時，能判斷資料來源與更新時機；需要做統計時，能先分清「計數的事件」與「事件的背景」。

Lesson 2 的 { link_name: "DailySchedule" } 回答「點了哪個入口」。誰操作、當時使用何種輸入、在哪個環境，則是另一組問題。這些描述發生背景的資訊稱為 context，不是 ClickInstrumentation 從 DOM 擷取的欄位。

以下依 內部套件實作證據與 Foreman 整合紀錄解說；User 與 device 是依需求啟用的能力，不是每個前端導入都必須收集的資料。

1. 先找真正知道資料的角色

資料來源套件責任
User宿主應用的登入狀態。詢問並同步至 Faro user state。
DeviceBrowser 提供的能力與實際輸入。依既定規則維護分類。
Environment宿主應用／部署設定。使用傳入值解析接收位置。

Lesson 3 已建立：套件保存的是同一個 Faro object 的 reference。後續同步資料作用在這個 object，不是每次再初始化一個 Faro。

2. getUser：把讀取入口交給套件

Foreman 選擇把員工資料放在 localStorage，也就是 Browser 提供的一塊持久儲存空間。這是應用的設計，不代表所有應用都應把登入資訊放在相同位置。

// 說明責任的 skeleton；省略其他必要初始化參數。
initFaro({
  getUser: () => {
    const employee = /* 從宿主的既有狀態讀取 */;
    if (!employee) return null;
    return {
      id: employee.empID,
      username: employee.ename
    };
  }
});

宿主先傳入一個 function reference，套件需要資料時才呼叫這個 function；這就是此處的 callback。getUser 負責回傳目前使用者或 null，不是直接把資料推進 Faro。只提供已核准的身分欄位，不把 credential 或 token 當成識別資料。

宿主應用提供 getUser function
  │ 套件之後呼叫
  ▼
立即回傳 current user / null
  │ 套件比較並同步
  ▼
同一個 Faro object 的 user state

getUser() 應快速、同步回傳既有狀態；不要在 callback 裡才等待遠端 API。Callback 仍不清楚時，先讀 Callback Reference，再回到這一節。

3. 登入狀態會變，所以不能永遠只讀第一次

頁面載入，尚未登入 → getUser() 回傳 null
  │ 使用者稍後登入
  ▼
宿主已有 user A
  │ 如果套件從此不再詢問
  ▼
後續 telemetry 仍可能沿用舊 user state

已查核的 UserSyncInstrumentation 在下列時機重新詢問：

時機先理解發生什麼
初始化完成Faro object 已建立，可以同步初始狀態。
Browser click收到點擊時重新確認登入狀態。
visibilitychangeBrowser 通知頁面從可見變不可見，或反過來。
storage event其他共用同份 localStorage 的頁面改了資料，通知目前頁面。

visibilitychange 與 storage 都是 Browser event，不是 Faro 專有名詞。修改 localStorage 的頁面本身不會收到自己的 storage event；它不能取代應用所有登入／登出狀態轉換的驗證。

重新呼叫 getUser()
  │ 比較 user id
  ├─ 改變 → setFaroUser(...) / clearFaroUser()
  └─ 未變 → 不重複更新

這是已查核版本的比較規則；不能自行推論同一 id 下其他欄位的變更必然同步。宿主決定資料來源，套件決定詢問與同步時機。

userSync.ts 實作證據；Browser 定義：visibilitychange、storage。

4. Device 是會更新的分類，不是永久硬體身分

Foreman 明確啟用 enableDeviceTypeDetection: true。套件先讀 navigator.maxTouchPoints，也就是 Browser 宣告最多可同時辨識幾個觸控接觸點，建立起始值：

maxTouchPoints > 0 → tablet
maxTouchPoints = 0 → desktop

之後收到 pointerdown，也就是滑鼠按下或手指觸碰等「指標開始按下」事件時，讀取事件的 pointerType：

mouse → desktop
touch → tablet
其他值 → 保持原值

所以有觸控螢幕的筆電可以先被分類為 tablet，使用滑鼠後變成 desktop，再以手指操作時變回 tablet。依這個實作，欄位較接近「初始觸控能力／最近一次可辨識輸入的分類」，不能直接當作永久硬體機型。

deviceTypeDetector.ts 實作證據。

5. Device 放在背景資料，不是 click payload

Faro 把描述 telemetry 發生背景的資料稱為 meta。套件註冊一個提供資料的 function，讓 Faro 需要 meta 時讀到目前分類：

faro.metas.add(() => ({
  device: { type: currentDeviceType }
}));

這是套件內部的實作片段，不是要求宿主額外建立另一套 Faro lifecycle。

DOM 標記
  │ ClickInstrumentation 擷取
  ▼
click payload.link_name

Browser 輸入
  │ device detector 更新
  ▼
currentDeviceType
  │ meta provider 讀取
  ▼
meta.device.type

兩條路可以在同筆 telemetry 會合，但不是點到 data-link-name 後才開始偵測裝置。

6. Environment 是初始化輸入，也可能決定送往哪裡

在這組歷史實作中，宿主呼叫 initFaro({ environment: 'tw-stage', ... })，套件以 environment 查表解析 receiver URL，再接上 /alloy。它不會自己從 Kubernetes namespace 或目前頁面網址猜環境。

因此 environment 不只是畫面標籤：值錯了，資料也可能被送到錯的接收位置。實際導入時要核對正在使用的 SDK contract，而不是照抄歷史範例的環境字串。

Context生命週期
User初始化與後續重新檢查點同步。
Device起始判定後，依 pointer input 更新。
Environment初始化提供；此版本沒有 user 那樣的重新詢問流程。

environmentUrls.ts / initFaro.ts 證據。Browser 實際接收 URL、payload 與 environment 的核對，接續 Lesson 5；source 設定本身不證明某個部署的實際輸出。

7. 做統計前，先定義拿什麼來計數

假設想知道主要功能入口的 tablet／desktop 使用比例，先拆成兩部分：

signal：被拿來計數的觀測資料
  例如一筆 tracked subsystem entry click

context：該筆資料發生時的背景
  例如 device.type = tablet

若分母是被追蹤的入口事件，得到的是這些入口事件的裝置分類分布，不是所有 sessions、users、操作或使用時間的比例。沒有必要為這個狹義 KPI 強制標記每一顆 Submit／Cancel；但也不能因此宣稱已取得完整使用者操作歷程。

同一個 user 在電腦與平板開兩個 Browser，各自有自己的 runtime 與 device state。平板若停在功能頁，後續只做未標記操作，可能沒有新的入口 signal 被計數；那是 coverage 問題，不代表電腦第一次 click 把所有裝置都鎖成 desktop。

證據邊界
Source 證明 click extraction 與 device meta 是不同路徑；尚不能單憑這點宣稱 production 已能用 user + device.type + link_name 完整聚合。仍需要實際 payload、下游欄位與查詢結果，以及產品對 KPI 分母的定義。

8. 用預期與觀察定位責任

預期／觀察先查哪裡
link_name 正確，登入身分不符。宿主 getUser() 回值、user sync 時機。
觸控筆電顯示 desktop。最近一次 pointerType；依目前規則可能正確。
Stage 資料疑似送錯位置。實際 initFaro environment 與解析出的 receiver。
click payload 本身沒有 user/device。先分清 payload 與 meta，不先判定遺失。
很多平板操作，入口事件數卻沒增加。KPI signal 定義與實際 tracking coverage。

不同宿主可以沿用相同介面：歷史 Foreman 從 localStorage 取 user、source 傳 tw-prod；Jeter 從記憶體取 current user、由 FARO_ENVIRONMENT 設定環境。來源不同不等於共用套件應猜測資料；source 值也不能替代已部署頁面的觀察。

Recap

  • Context 描述資料發生的背景；來源與 click payload 不同。
  • getUser 是宿主提供的同步讀取 callback；套件在初始化及後續檢查點同步同一個 Faro。
  • visibilitychange 是可見狀態通知；storage 不通知同一個寫入頁面。
  • Device 依初始能力與後續 pointer input 更新，透過 meta provider 提供，不是永久硬體分類。
  • Environment 在初始化提供；source 設定與 deployed runtime 必須分開驗證。
  • Signal 決定計數單位，context 用來分組；入口事件分布不能擴大解釋為所有使用行為。
