User, Device, and Environment Context

Milestone 2 · 同一筆 telemetry 的背景資料，誰提供、何時更新、Faro 怎麼使用

這堂課的目標
看到 user、device、environment 時，你要能判斷三件事：資料原本由誰知道、package 什麼時候取得或更新它、它和 click payload 有什麼不同。最後你應該能判斷一個欄位應該由宿主應用提供，還是由共用 package 處理。

先沿用 Lesson 2 已建立的一件事：一次 click 可以產生這種資料：

{
  link_name: "DailyProductionSchedule"
}

這筆資料能回答：

使用者點了哪個被標記的操作？

但實際維運時，通常還會想知道另外三件事：

誰做的？       → user
使用什麼輸入？ → device
在哪個環境？   → environment

這些都不是 ClickInstrumentation 從 data-* 抽出來的 click 欄位。

它們是在描述「這筆 telemetry 發生時的背景」。這堂課把這類背景資料統稱為 context。

1. 第一個邊界：不是所有 context 都應該由 Faro 自己猜

先不看程式碼，只問一個最基本的問題：

誰最接近真正的資料來源？
資料真正知道它的是誰？原因
User宿主應用登入狀態、員工資料放在哪裡，是應用自己的設計。
DeviceBrowser + packageBrowser 能提供觸控與實際輸入資訊，package 可以依固定規則判定。
Environment宿主應用／部署設定只有導入方知道這次啟動應該代表 tw-stage、tw-prod 或其他環境。

因此 package 的責任不是「擁有所有真相」，而是建立一致的接法：

宿主應用知道的資料
  │ provides
  ▼
@sre2/faro-click-tracking
  │ converts / synchronizes
  ▼
同一個 Faro object

這裡的「同一個 Faro object」沿用 Lesson 3 已建立的模型：initializeFaro() 建立一個 Faro object，package 只是保存它的 reference，沒有再建立第二顆。

接下來分別看三條路徑。

2. User：package 不知道誰登入，所以它向宿主應用詢問

以 Foreman Assistant 為例，真正知道目前員工是誰的不是 Faro package，而是 Foreman 自己。

Foreman 把員工資料放在 Browser 提供的 localStorage。這裡只需要把它理解成：Foreman 選擇用 Browser 裡的一塊持久儲存空間保存目前員工資料。

Foreman 初始化 Faro 時會提供一個 getUser function。概念可以縮成：

initFaro({
  getUser: () => {
    const employee = /* 從 Foreman 自己的 localStorage 取得 */

    if (!employee) return null

    return {
      id: employee.empID,
      username: employee.ename
    }
  }
})

這是依 Foreman integration evidence 中 src/main.ts:11-34 整理的等價 skeleton，不是逐字 source。

這裡的設計重點不是 localStorage 本身，而是責任：

Foreman
  │ knows where its login state lives
  │ provides getUser function reference
  ▼
package
  │ calls getUser() later when it needs fresh user state
  ▼
Faro user state

宿主應用先把一個 function reference 交給 package，package 之後需要時才呼叫它。這就是這裡的 callback。

Callback 這條線如果還不穩
只回看這個概念即可：Reference｜Callback 到底是什麼 →。看完直接回到這裡，不需要重讀前面整課。

所以 getUser 不是「把 user 推進 Faro 的 function」。它比較像：

package 要同步 user 時，用這個入口向宿主應用問：「你現在認為登入者是誰？」

3. User 為什麼不能只在初始化時讀一次？

先看一個具體情境：

頁面載入：尚未登入
  ↓
Faro 第一次詢問 → getUser() 回傳 null
  ↓
使用者稍後登入：employee = A123
  ↓
如果 package 永遠不再問 getUser()
  ↓
後面的 telemetry 仍會沿用舊的 user 狀態

所以 package 需要在「有可能值得重新確認 user」的時機，再問一次 getUser()。

目前 implementation 選了四種時機：

實際發生的事Browser / package 看見什麼接下來做什麼
initFaro() 剛完成 Faro object 已建立並保存 立即呼叫一次 getUser()
使用者在頁面點了一下 Browser 分派已經熟悉的 click event 再呼叫一次 getUser()
使用者切到別的頁籤、把 Browser 放到背景，或稍後切回來 Browser 知道「這個頁面現在可見／不可見的狀態改變了」；這個通知叫 visibilitychange 再呼叫一次 getUser()
另一個同網站頁籤改了和目前頁面共用的 localStorage Browser 通知目前頁面「共用儲存內容被別的頁面改了」；這個通知叫 storage event 再呼叫一次 getUser()

所以 visibilitychange 不是某個 Faro 專有名詞。它只是 Browser 對「頁面可見狀態改變」的正式 event 名稱。

storage event 也不是「這個頁面自己每次寫 localStorage 都會收到」。對 localStorage 而言，它主要讓其他共用同一份 storage 的頁面／頁籤知道資料被改了；做出修改的那個頁面本身不會收到自己的 storage event。

這四種時機的共同目的都不是「處理 click」或「處理頁籤切換」本身，而是：

出現一個合理的重新檢查點時，再問宿主應用：「現在的 user 還是一樣嗎？」

負責這套重新檢查邏輯的 package 元件，現行程式名稱叫 UserSyncInstrumentation。

同步時，package 會比較 user id。如果身份真的改變，就更新或清除 Faro user state。

package calls getUser()
        │
        ▼
宿主應用立即回傳 current user / null
        │
        ▼
user id changed?
├── yes → setFaroUser(...) 或 clearFaroUser()
└── no  → 不重複更新

目前 getUser 的要求是：呼叫後要很快、直接回傳結果。不要在這個 callback 裡才開始等一個遠端 API request 回來。

現行 user sync 時機與比較規則依據：faro-click-tracking implementation evidence，對應 userSync.ts:5-71。

責任邊界
「user 資料放哪裡、怎麼取得」由宿主應用決定；「哪些時機重新詢問、如何寫入 Faro user state」由共用 package 決定。

4. Device：宿主應用只決定要不要開，實際判定由 package 做

Device 的責任分法不同。

宿主應用只需要明確決定要不要啟用：

enableDeviceTypeDetection: true

一旦開啟，目前 package 先從 Browser 已知道的觸控能力建立起始值。

第一步：頁面剛啟動時

Browser 會提供一些目前裝置能力資訊。其中 navigator.maxTouchPoints 表示 Browser 宣告「最多可以同時辨識幾個觸控接觸點」。

navigator.maxTouchPoints > 0 ?
├── yes → tablet
└── no  → desktop

所以這一步只是利用「裝置有沒有觸控能力」建立一個起始判定。

第二步：之後真的收到輸入時

頁面啟動後，實際輸入能提供更新的線索。例如使用者按下滑鼠按鍵，或手指碰到觸控螢幕時，Browser 會分派一個代表「指標剛按下」的 event；這個 event 名稱叫 pointerdown。

這個 Event 裡的 pointerType 會告訴程式這次輸入是哪一類，例如 mouse、touch 或其他值。

目前 package 的規則是：

pointerType === 'mouse' → desktop
pointerType === 'touch' → tablet
其他值                → 保持原值

因此一台有觸控螢幕的筆電可能出現這個時間線：

頁面載入
maxTouchPoints > 0
  │ sets
  ▼
tablet

使用者接著用滑鼠
pointerType = 'mouse'
  │ updates
  ▼
desktop

之後再用手指觸控
pointerType = 'touch'
  │ updates
  ▼
tablet

所以這裡的 device.type 更接近「目前最近一次可辨識的輸入型態」；不要把它理解成永久不變的硬體分類。

現行 device 判定依據：faro-click-tracking implementation evidence，對應 deviceTypeDetector.ts:5-75。

5. Device 寫在哪裡？不是塞進 click payload

Lesson 2 的 click payload 是這條路：

DOM data-*
  → ClickInstrumentation
  → api.pushEvent('click', payload)

Device 走的是另一條路。

Faro 可以在 telemetry 旁邊附上「描述當下背景」的資料。這類背景資料在 Faro 裡叫 meta。

package 會向 Faro 註冊一個 function，讓 Faro 需要背景資料時取得目前的 device type。source 中的核心形式是：

faro.metas.add(() => ({
  device: {
    type: currentDeviceType
  }
}))

因此：

click payload.link_name  ← DOM data-* 決定
meta.device.type         ← device detector 決定

兩者可以一起進入後續 telemetry 流程，但來源與更新機制完全不同。

6. Environment：宿主應用在初始化時就要說清楚

Browser 最後必須知道：Faro 資料要送到哪個接收 URL。

但 package 不能憑空知道目前是 stage 還是 production，所以 initFaro() 要求宿主應用明確傳入 environment：

initFaro({
  environment: 'tw-stage'
})

package 不會自己看 Kubernetes namespace、網址或 window.location 然後猜這是哪個環境。

目前 implementation 會用 environment 當查找條件，從 package 內建對照找到相對應的 Faro 接收 URL，最後加上 /alloy 路徑。

environment
  │ package uses as lookup key
  ▼
對應的 Faro 接收 URL
  │ append path
  ▼
/alloy

所以 environment 不只是顯示用的文字。給錯值，Browser 後續就可能被設定成把 Faro 資料送往錯的接收位置。

environment 與接收 URL 對照依據：faro-click-tracking implementation evidence，對應 environmentUrls.ts:4-45 與 initFaro.ts:13-146。HTTP、request 與 CORS 細節留到 Lesson 5。

它的更新方式也和 user 不同：

Context什麼時候提供／更新？
User初始化後立即同步；之後在幾個合理的重新檢查點再次詢問宿主應用。
Device初始化時先判定；之後依實際滑鼠／觸控輸入更新。
EnvironmentinitFaro() 時提供；目前 package 沒有像 user 一樣的後續重新詢問流程。
Evidence boundary
現在能證實的是：environment 是初始化必要設定，而且會決定接收 URL。Learning repo 尚未保存一筆 Browser request，直接證明 environment 在實際送出的資料裡最後長在哪個欄位；這會在 Lesson 5 用 Browser Network / payload evidence 驗證，不在這裡把未觀察結果寫成既成事實。

7. Foreman 與 Jeter：同一個 package，宿主資料來源可以不同

前面的責任切分，讓不同宿主應用可以用同一個 package，而不用共享同一套登入實作。

Foreman AssistantJeter demo
User source讀自己的 localStorage employee 資料。讀應用目前保存在記憶體裡的 current user id。
Device開啟 package device detection。同樣開啟 package device detection。
Environment目前 source 直接傳 tw-prod。由 FARO_ENVIRONMENT runtime config 提供。

package 不需要知道 Foreman 的 employee schema，也不需要知道 Jeter 的登入狀態怎麼實作。

它只要求雙方遵守相同的介面規則：

你告訴我 environment
你需要 user sync → 給我 getUser()
你需要 device detection → 明確 enable

剩下同步與 Faro integration 的共同邏輯
由 package 統一處理

宿主差異依據：Foreman integration evidence 與 Jeter integration evidence。Foreman repository source 的 environment: 'tw-prod' 只證明 source 怎麼設定，不能直接證明 tw-stage 已部署 bundle 此刻實際送出的 environment；runtime delivery 仍需 Browser evidence。

8. 最重要的模型：三種 context 不走同一條管線

                         ┌─ getUser() ───────────────→ Faro user state
宿主應用 initFaro(...) ─┼─ environment ─────────────→ 選擇 Faro 接收 URL
                         └─ enableDeviceDetection ───→ device detector
                                                          │
Browser 實際滑鼠／觸控輸入 ────────────────────────────────┘
                                                          │ updates
                                                          ▼
                                                   Faro device meta

DOM data-* ─→ ClickInstrumentation ─→ click payload

如果把它們全部想成「Faro click 裡面的欄位」，debug 時就會查錯地方。

正確問題應該是：

  • User 錯了：宿主應用的 getUser() 回了什麼？package 有沒有到達重新檢查 user 的時機？
  • Device 錯了：初始化時的 maxTouchPoints 是多少？最近一次實際輸入的 pointerType 是什麼？
  • Environment 錯了：宿主應用傳給 initFaro() 的值是什麼？它選到哪個 Faro 接收 URL？
  • Click 欄位錯了：回到 Lesson 2，檢查 trackAttributes、DOM data-* 與 closest()。

Q2. 一台有觸控螢幕的筆電載入後先判成 tablet，接著使用者按下滑鼠。依目前 detector，下一個 device type 是什麼？

Recap

  • Context 是描述 telemetry 發生背景的資料；User、Device、Environment 不等於 click payload。
  • User 的真實來源由宿主應用掌握；package 透過 getUser() callback 取得並同步到 Faro user state。
  • User 重新同步：初始化後立即檢查；之後 click、頁面切到背景／回到前景（visibilitychange）、或其他共用頁面改了 localStorage（storage event）時，再重新詢問 user。
  • Device 需要宿主應用明確開啟；起始值看 maxTouchPoints，之後由實際輸入的 pointerType 更新。
  • Device meta 是 Faro 附在 telemetry 旁邊的背景資料，不是由 DOM data-* 建立的 click payload。
  • Environment 是宿主應用在 initFaro() 提供的必要設定，並決定 package 選到哪個 Faro 接收 URL。
  • 責任邊界：宿主應用提供它自己才知道的登入／部署資料；共用 package 統一 user 同步、device 判定與 Faro 接法。
  • Debug 時先判斷資料走哪一條路，再檢查對應來源；不要把 user、device、environment 都當成 ClickInstrumentation 欄位。
