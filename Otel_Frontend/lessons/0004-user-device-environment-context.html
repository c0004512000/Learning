User, Device, and Environment Context

Milestone 2 · 同一筆 telemetry 的背景資料，到底是誰知道、誰更新、誰寫進 Faro

這堂課的目標
看到 user、device、environment 時，你要能判斷三件事：資料原本由誰知道、package 什麼時候取得或更新它、它和 Lesson 2 的 click payload 有什麼不同。最後你應該能判斷一個欄位應該由宿主應用提供，還是由共用 package 處理。

Lesson 2 已經知道，一次 click 可以產生這種資料：

{
  link_name: "DailyProductionSchedule"
}

這筆資料能回答：

使用者點了哪個被標記的操作？

但實際維運時，通常還會想知道另外三件事：

誰做的？       → user
使用什麼輸入？ → device
在哪個環境？   → environment

這些都不是 ClickInstrumentation 從 data-* 抽出來的 click 欄位。

它們是在描述「這筆 telemetry 發生時的背景」。這堂課把這類背景資料統稱為 context。

1. 第一個邊界：不是所有 context 都應該由 Faro 自己猜

先不看程式碼，只問一個最基本的問題：

誰最接近真正的資料來源？
資料真正知道它的是誰？原因
User宿主應用登入狀態、員工資料放在哪裡，是應用自己的設計。
DeviceBrowser + packageBrowser 能提供 touch / pointer 資訊，package 可以依既定規則判定。
Environment宿主應用／部署設定只有導入方知道這次啟動應該代表 tw-stage、tw-prod 或其他環境。

因此 package 的責任不是「擁有所有真相」，而是建立一致的接法：

宿主應用知道的資料
  │ provides
  ▼
@sre2/faro-click-tracking
  │ converts / synchronizes
  ▼
同一個 Faro object

接下來分別看三條路徑。

2. User：package 不知道誰登入，所以它向宿主應用詢問

以 Foreman Assistant 為例，真正知道目前員工是誰的不是 Faro package，而是 Foreman 自己。

Foreman 初始化時會提供一個 getUser function。概念可以縮成：

initFaro({
  getUser: () => {
    const employee = /* 從 Foreman 自己的 localStorage 取得 */

    if (!employee) return null

    return {
      id: employee.empID,
      username: employee.ename
    }
  }
})

這是依 Foreman src/main.ts:11-34 verified evidence 整理的等價 skeleton，不是逐字 source。

這裡的設計重點不是 localStorage 本身，而是責任：

Foreman
  │ knows where its login state lives
  │ provides getUser()
  ▼
package
  │ calls getUser() when it needs fresh user state
  ▼
Faro user state

宿主應用把一個 function 交給 package，等 package 需要時再呼叫。這就是 callback。

所以 getUser 不是「把 user 推進 Faro 的 function」。它比較像：

package 要同步 user 時，用這個入口向宿主應用問：「你現在認為登入者是誰？」

3. User 不是只在初始化時讀一次

如果 user 只在頁面載入時讀一次，就會有問題：

頁面載入：尚未登入
  ↓
稍後登入：employee = A123
  ↓
如果 Faro 永遠不再讀取
  ↓
後面的 telemetry 仍不知道新 user

因此目前 package 有一個 UserSyncInstrumentation。它會在幾個時機重新呼叫 getUser()：

  • initFaro() 成功並保存 Faro instance 後，立即同步一次。
  • Browser 發生 click 時。
  • 頁面 visibilitychange 時。
  • Browser 發生 storage event 時。

同步時，package 會比較 user id。如果身份真的改變，就更新或清除 Faro user state。

package calls getUser()
        │
        ▼
宿主應用回傳 current user / null
        │
        ▼
user id changed?
├── yes → setFaroUser(...) 或 clearFaroUser()
└── no  → 不重複更新

現行 user lifecycle 依據：userSync.ts:5-71。目前 contract 要求 getUser 是同步而且便宜的 function；不要把遠端 API request 直接塞進這個 callback。

責任邊界
「user 資料放哪裡、怎麼取得」由宿主應用決定；「什麼時候重新同步、如何寫入 Faro user state」由共用 package 決定。

4. Device：宿主應用只決定要不要開，實際判定由 package 做

Device 的責任分法不同。

宿主應用只需要決定：

enableDeviceTypeDetection: true

一旦開啟，目前 package 的判定規則只有兩個來源。

第一步：頁面剛啟動時

navigator.maxTouchPoints > 0 ?
├── yes → tablet
└── no  → desktop

navigator.maxTouchPoints 是 Browser 提供的數值，表示這個裝置宣告可同時支援多少個 touch point。

這一步只是在初始化時建立一個起始判定。

第二步：之後真的收到 pointer input 時

package 會監聽全域 pointerdown，再看 Browser 提供的 pointerType：

pointerType === 'mouse' → desktop
pointerType === 'touch' → tablet
其他值                → 保持原值

因此一台有觸控螢幕的筆電可能出現這個時間線：

頁面載入
maxTouchPoints > 0
  │ sets
  ▼
tablet

使用者接著用滑鼠
pointerType = 'mouse'
  │ updates
  ▼
desktop

之後再用手指觸控
pointerType = 'touch'
  │ updates
  ▼
tablet

所以這裡的 device.type 更接近「目前最近一次可辨識的輸入型態」；不要把它理解成永久不變的硬體分類。

5. Device 寫在哪裡？不是塞進 click payload

Lesson 2 的 click payload 是這條路：

DOM data-*
  → ClickInstrumentation
  → api.pushEvent('click', payload)

Device 走的是另一條路。

package 會向 Faro 註冊一個 function，讓 Faro 在需要背景資料時取得目前的 device type。source 中的核心形式是：

faro.metas.add(() => ({
  device: {
    type: currentDeviceType
  }
}))

這裡的 meta 可以先理解成：Faro 附在 telemetry 旁邊、用來描述當下背景的資料。

因此：

click payload.link_name  ← DOM data-* 決定
meta.device.type         ← device detector 決定

兩者可以一起出現在後續 telemetry 流程裡，但來源與更新機制完全不同。

6. Environment：這是宿主應用在初始化時做的選擇

environment 是目前 initFaro() 的 required config。

也就是宿主應用必須明確告訴 package：

initFaro({
  environment: 'tw-stage'
})

package 不會自己看 Kubernetes namespace、網址或 window.location 然後猜這是哪個環境。

目前 verified source 至少證實 environment 會被拿去做 collector URL resolution：

environment
  │ lookup by package
  ▼
內建 environment → collector URL 對照
  │ append
  ▼
/alloy

所以 environment 不只是顯示用的文字。給錯值，package 就可能解析到錯的 Faro receiver endpoint。

它的 lifecycle 也和 user 不同：

Context什麼時候提供／更新？
User初始化後立即同步，之後遇到指定事件再重新詢問宿主應用。
Device初始化時先判定，之後由實際 pointer input 動態更新。
EnvironmentinitFaro() 時提供；目前 package 沒有 user 那種後續同步流程。
Evidence boundary
目前 source evidence 已能證實 environment 是 required init config，而且會決定 collector URL。Learning repo 尚未保存「每一筆 Browser request 中 environment 最終序列化在哪個 payload/meta 欄位」的 runtime sample；這會在 Lesson 5 用 Browser Network / payload evidence 驗證，不在這裡把未取樣結果寫成既成事實。

7. Foreman 與 Jeter：同一個 package，宿主資料來源可以完全不同

這正是 callback / config boundary 存在的原因。

Foreman AssistantJeter demo
User source讀自己的 localStorage employee 資料。讀 application memory 裡的 current user id。
Device開啟 package device detection。同樣開啟 package device detection。
Environment目前 source 直接傳 tw-prod。由 FARO_ENVIRONMENT runtime config 提供。

package 不需要知道 Foreman 的 employee schema，也不需要知道 Jeter 的 mock login 怎麼實作。

它只要求雙方遵守共同 contract：

你告訴我 environment
你需要 user sync → 給我 getUser()
你需要 device detection → 明確 enable

剩下同步與 Faro integration 的共同邏輯
由 package 統一處理

Foreman 現行 source 的 environment: 'tw-prod' 只能證明 repository source 怎麼設定，不能直接證明 tw-stage 已部署 bundle 此刻實際送出的 environment；runtime delivery 仍需 Browser evidence。Jeter stage runtime config 已觀察到 tw-stage。

8. 最重要的模型：三種 context 不走同一條管線

                         ┌─ getUser() ───────────────→ Faro user state
宿主應用 initFaro(...) ─┼─ environment ─────────────→ init / endpoint resolution
                         └─ enableDeviceDetection ───→ device detector
                                                          │
Browser pointer input ─────────────────────────────────────┘
                                                          │ updates
                                                          ▼
                                                   Faro device meta

DOM data-* ─→ ClickInstrumentation ─→ click payload

如果把它們全部想成「Faro click 裡面的欄位」，debug 時就會查錯地方。

正確問題應該是：

  • User 錯了：宿主應用的 getUser() 回了什麼？package 有沒有觸發同步？
  • Device 錯了：初始化時的 maxTouchPoints 是多少？最近一次 pointerType 是什麼？
  • Environment 錯了：宿主應用傳給 initFaro() 的值是什麼？它解析到哪個 collector URL？
  • Click 欄位錯了：回到 Lesson 2，檢查 trackAttributes、DOM data-* 與 closest()。

9. Production-style check：症狀要先對到責任邊界

link_name 正確，但 user 不對getUser() 與 user syncUser 不是由 ClickInstrumentation 從 DOM 抽出的。
觸控筆電被標成 desktop最近一次 pointerTypemouse pointerdown 會把 current device type 更新成 desktop。

Recap

  • Context 是描述 telemetry 發生背景的資料；User、Device、Environment 不等於 Lesson 2 的 click payload。
  • User 的真實來源由宿主應用掌握；package 透過 getUser() callback 取得並同步到 Faro user state。
  • User lifecycle 不是只讀一次；初始化後會立即同步，之後在 click、visibilitychange、storage 等時機重新檢查 user id。
  • Device 需要宿主應用明確 opt in；起始值看 maxTouchPoints，之後由 pointerType 動態更新。
  • Device meta 透過 Faro meta 路徑提供，不是由 DOM data-* 建立的 click payload。
  • Environment 是宿主應用在 initFaro() 提供的 required config，並參與 collector URL resolution。
  • 責任邊界：宿主應用提供它才知道的 business/deployment truth；共用 package 統一同步、偵測與 Faro integration 機制。
  • Debug 時先判斷資料走哪一條路，再檢查對應來源；不要把 user、device、environment 都當成 ClickInstrumentation 欄位。

主要 verified evidence：faro-click-tracking release line commit 937d4a32e725877188a8d8a223529dece0449d4d 的 userSync.ts:5-71、deviceTypeDetector.ts:5-75、environmentUrls.ts:4-45、initFaro.ts:13-146；Foreman main commit 4e032babef7aa30e5d13d7a506abe208945a5dee；Jeter dev commit 3edd27eb44ac2af13d5c987f68e2be232aa0f6dd。Runtime user PII 與每一筆 meta delivery 未取樣，因此本課不把未觀察到的 serialized payload 細節當成事實。
