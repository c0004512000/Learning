User, Device, and Environment Context

Milestone 2 · 同一筆 telemetry 的背景資料，誰提供、何時更新、Faro 怎麼使用

這堂課的目標
看到 user、device、environment 時，你要能判斷：資料原本由誰知道、package 何時取得或更新它、它和 click payload 有什麼不同。最後要能把 Foreman 的 tablet / desktop adoption 問題拆成「拿什麼 signal 當分母」與「signal 發生時的 device context 是什麼」。

Lesson 2 已建立：一次被標記的 click 可以形成：

{
  link_name: "DailySchedule"
}

它回答：

這次 click 對應到哪個被標記的 Foreman 功能入口？

但實際維運還會問：

誰做的？             → user
當下是哪種輸入型態？ → device
在哪個環境？         → environment

這些不是 ClickInstrumentation 從 DOM data-* 抽出的欄位；它們描述 telemetry 發生時的背景。這堂課把這類背景資料統稱為 context。

1. 第一個邊界：不是所有 context 都應由 Faro 自己猜

先問：

誰最接近真正的資料來源？
資料真正知道它的是誰？原因
User宿主應用登入狀態、員工資料放哪裡，是應用自己的設計。
DeviceBrowser + packageBrowser 能提供觸控能力與實際 pointer input；package 依固定規則維護分類。
Environment宿主應用／部署設定只有導入方知道這次啟動應該代表 tw-stage、tw-prod 或其他環境。
 
宿主應用知道的資料
  │ provides
  ▼
@sre2/faro-click-tracking
  │ converts / synchronizes
  ▼

「同一個 Faro object」沿用 Lesson 3：initializeFaro() 建立 Faro object，package 保存的是同一個 object 的 reference。

2. User：package 不知道誰登入，所以向宿主應用詢問

Foreman 才知道目前員工是誰。它把員工資料放在 Browser 的 localStorage，並在初始化 Faro 時提供 getUser callback。概念可縮成：

initFaro({
  getUser: () => {
    const employee = /* Foreman 自己的 current employee */
    if (!employee) return null

    return {
      id: employee.empID,
      username: employee.ename
    }
  }
})

責任是：

Foreman
  │ knows where login state lives
  │ provides getUser function
  ▼
package
  │ calls getUser() when it needs current state
  ▼
Faro user state

getUser 不是「把 user 推進 Faro」的 function；它是 package 需要同步 user 時，向宿主應用問：「你現在認為登入者是誰？」

Callback 如果還不穩
看 Reference｜Callback 到底是什麼 →，再回來即可。

3. User 為什麼不能只在初始化時讀一次？

頁面載入：尚未登入
  ↓
第一次 getUser() → null
  ↓
使用者稍後登入：A123
  ↓
如果 package 永遠不再詢問
  ↓
後續 telemetry 會沿用錯誤的 user state

目前 implementation 會在幾個合理的重新檢查點再呼叫 getUser()：

時機目的
initFaro() 完成後建立初始 user state。
Browser click重新確認 user 是否已改變。
visibilitychange頁面離開／回到前景時重新確認。
storage event其他同網站頁籤改變共用 localStorage 時重新確認。

同步時比較 user id；真的改變才更新或清除 Faro user state。

package calls getUser()
        │
        ▼
current user / null
        │
        ▼
user id changed?
├── yes → setFaroUser(...) / clearFaroUser()
└── no  → 不重複更新

現行 user sync 依據：faro-click-tracking evidence 的 userSync.ts。

4. Device：宿主應用只決定要不要開，package 維護分類

Foreman 會明確啟用：

enableDeviceTypeDetection: true

第一步：頁面剛啟動

package 先使用 Browser 的 navigator.maxTouchPoints 建立起始值：

navigator.maxTouchPoints > 0 ?
├── yes → tablet
└── no  → desktop

第二步：收到實際 pointer input

之後 Browser 的 pointerdown event 提供 pointerType，目前規則是：

pointerType === 'mouse' → desktop
pointerType === 'touch' → tablet
其他值                → 保持原值

所以一台有觸控螢幕的筆電可能：

頁面載入
maxTouchPoints > 0
  │ sets
  ▼
tablet

使用者接著用滑鼠
pointerType = 'mouse'
  │ updates
  ▼
desktop

再用手指觸控
pointerType = 'touch'
  │ updates
  ▼
tablet
不要把 device.type 理解成永久硬體分類。
依目前實作，它更接近「目前最近一次可辨識的輸入型態」。這也是為什麼同一台 hybrid device 可以在 tablet / desktop 間更新。

現行 device 判定依據：deviceTypeDetector evidence。

5. Device 寫在哪裡？不是塞進 click payload

Lesson 2 的 click 路徑：

DOM data-link-name
  → ClickInstrumentation
  → api.pushEvent('click', { link_name: ... })

Device 走另一條路。package 向 Faro 註冊 meta provider：

faro.metas.add(() => ({
  device: {
    type: currentDeviceType
  }
}))

所以：

click payload.link_name  ← DOM tracking attribute
meta.device.type         ← device detector

兩者可以一起進後續 telemetry 流程，但來源、生命週期和更新機制不同。

把這條線接回 Foreman 的 tablet / desktop adoption 需求

原始產品問題不是「完整記錄每一個 UI click」，而是想知道 Foreman 的使用情況有多少來自 tablet、多少來自 desktop。

這時一定要把 signal 和 context 分開：

signal：
這次有一筆什麼 telemetry 可以拿來計數？
例如 tracked subsystem entry click

context：
這筆 telemetry 發生時的背景是什麼？
例如 device.type = tablet

所以不是：

點到 data-link-name
→ 才開始 detect device

而是：

Browser runtime 持續維護 current device type
                 │
                 └──────────────┐
                                ▼
tracked subsystem click → Faro telemetry
                                │
                                └→ 可以取得當下 device context

如果產品決定把「有 data-link-name 的主要 subsystem entry event」當 observation point，那可以統計：

tracked feature-entry events
├── tablet
└── desktop
分母要說清楚。
這能代表「被追蹤的主要功能入口事件中，tablet / desktop 的分布」。它不自動等於所有 Foreman sessions、所有 users、所有操作，或使用時間占比。

這也解釋為什麼不必要求每一顆 Submit、Cancel、Dropdown 都加 data-link-name 才能做這個 KPI；如果產品只想量主要功能入口的使用裝置，Main subsystem tiles 可以是穩定 observation point。但若產品日後要問完整 user journey，就需要不同的 instrumentation coverage。

同一個 user 在電腦和平板之間切換呢？

電腦 Browser 與平板 Browser 是兩個不同 runtime，各自維護自己的 device state。電腦先送出 desktop event，不會把另一台平板永久標成 desktop。

真正可能漏掉的是 signal：如果平板已停在某個功能頁，後續只做未標記的操作，而 KPI 又只數有 data-link-name 的 entry events，那這些後續操作不會提供新的 link_name event。這是 observation coverage 問題，不是 device detector 被鎖死。

Evidence boundary
Source 已證明 device meta 與 click extraction 是不同路徑；但若要宣稱 production 上已能直接用 user + device.type + link_name 做完整聚合，還需要實際 runtime payload / backend query evidence。不要把 implementation 可能性直接寫成已驗證結果。

6. Environment：宿主應用在初始化時就要說清楚

Browser 最後必須知道 Faro 資料要送到哪個接收 URL。package 不能憑空知道目前是 stage 還是 production，所以 initFaro() 要求宿主應用傳入 environment。

initFaro({
  environment: 'tw-stage'
})

目前 implementation 會用 environment 查表，找到對應 Faro 接收 URL，再加上 /alloy。

environment
  │ lookup
  ▼
Faro receiver URL
  │ append
  ▼
/alloy

因此 environment 不只是顯示用文字；給錯值，Browser 後續可能被設定成送往錯的接收位置。

Context何時提供／更新？
User初始化後立即同步；之後在合理重新檢查點再詢問宿主。
Device初始化時先判定；之後依實際 pointer input 更新。
EnvironmentinitFaro() 時提供；目前沒有像 user 一樣的後續重新詢問。

7. Foreman 與 Jeter：同一個 package，宿主資料來源可以不同

Foreman AssistantJeter demo

8. 最重要的模型：四條資料路徑不要混在一起

                         ┌─ getUser() ───────────────→ Faro user state
宿主應用 initFaro(...) ─┼─ environment ─────────────→ 選擇 Faro 接收 URL
                         └─ enableDeviceDetection ───→ device detector
                                                          │
Browser 實際滑鼠／觸控輸入 ────────────────────────────────┘
                                                          │ updates
                                                          ▼
                                                   Faro device meta

DOM data-link-name ─→ ClickInstrumentation ─→ click payload.link_name

如果把它們全部想成「Faro click 裡面的欄位」，debug 時就會查錯地方。

Recap

  • Context 描述 telemetry 發生背景；User、Device、Environment 不等於 click payload。
  • User 由宿主應用掌握，package 透過 getUser() 同步到 Faro user state。
  • Device 初始化先看 maxTouchPoints，之後依 pointerType 更新；不是永久硬體分類。
  • Device meta 與 link_name 是不同資料路徑；不是點到 tracking attribute 才開始 detect device。
  • Signal vs context：KPI 必須先決定哪種 telemetry event 當分母，再用 device context 分組。
  • Subsystem entry KPI 能代表被追蹤的主要功能入口事件分布，不能自動擴大成全部 sessions / users / actions。
  • 多裝置：不同 browser runtime 各自維護 device state；真正可能漏的是沒有新的被計數 signal。
  • Environment 由宿主在 initFaro() 提供，並決定 package 選到哪個 receiver URL。
  • Debug 時先判斷資料走哪一條路，再檢查對應來源。
