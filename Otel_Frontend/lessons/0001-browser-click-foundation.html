瀏覽器如何知道你點了哪裡

Milestone 1 · 先把 browser 原生 click 的因果鏈建立正確，再回到 Faro

這堂課只回答一件事：
Faro 還沒介入以前，使用者點一下畫面後，瀏覽器怎麼知道點到哪個頁面元素，又怎麼讓 JavaScript 收到這件事？

這堂課會刻意把幾個很容易混在一起的東西分開：HTML、DOM、畫面、JavaScript、Event。後面所有 Faro click tracking 都建立在這些東西的責任邊界上。

1. 先從最具體的 HTML 開始

假設宿主應用的 HTML 裡有一顆按鈕：

<main>
  <button id="daily-schedule-button">
    每日生產排程
  </button>
</main>

這一段首先只是文字格式的 HTML source。瀏覽器收到並解析它之後，才會在自己的記憶體裡建立一套可以操作的文件結構：DOM。

HTML source text
      │
      │ 瀏覽器解析
      ▼
DOM objects（瀏覽器建立、瀏覽器管理）
      │
      │ 再搭配 CSS 做 layout / paint
      ▼
使用者看到的畫面
東西這堂課的精確理解
HTML source原始標記文字，例如 <button>...</button>。
DOM瀏覽器根據文件建立並維護的一組物件，以及這些物件之間的 tree 關係。
Rendered 畫面瀏覽器依 DOM、CSS、layout、paint 等流程真正顯示出的像素結果。
JavaScript可以透過瀏覽器提供的 DOM API 取得這些 DOM objects 的 reference，然後讀取或操作它們。

2. 為什麼又叫「object」？DOM 不是瀏覽器在管嗎？

對，DOM 就是瀏覽器建立與管理的。「DOM object」不是在說「這是 JavaScript 自己創造的物件」。

這裡的 object 只是說：瀏覽器在記憶體裡，用一個有資料、有方法、彼此有關係的程式物件來代表頁面上的元素。

HTML 裡：
<button id="daily-schedule-button">每日生產排程</button>

瀏覽器解析後：
建立一個代表這顆 button 的 DOM object
型別／介面名稱可以看到：HTMLButtonElement
不要把它理解成「DOM 變成 JavaScript object」。
比較正確的是：瀏覽器本來就建立了一個 DOM object；JavaScript 只是拿到它的 reference。

那為什麼不叫「HTML object」？因為 HTML 是輸入文件的標記語言；DOM 是瀏覽器解析文件後提供給程式操作的 object model。HTMLButtonElement 這個名稱表示「這是一個對應 HTML button element 的 DOM 介面／物件型別」，不是另一種叫做「HTML object」的東西。

HTML 標記                       DOM 中對應的物件
<button>...</button>   ─────►   HTMLButtonElement

左邊：文件中的標記
右邊：瀏覽器記憶體中的 DOM object

3. id 與 #daily-schedule-button 到底是什麼？

daily-schedule-button 沒有任何特殊意義。它只是這份範例 HTML 的作者替按鈕取的一個 id。

<button id="daily-schedule-button">每日生產排程</button>
               ↑
        只是作者取的 id 名稱

而前面的 # 是 CSS selector 語法：

#daily-schedule-button
↑
表示：找 id="daily-schedule-button" 的 element

因此 JavaScript 可以寫：

const button = document.querySelector('#daily-schedule-button')

意思不是「找一個叫 schedule 的特殊 browser 東西」，而只是：

從目前文件的 DOM tree 裡，找出 id 等於 daily-schedule-button 的那顆 DOM element。

4. document 是目前頁面的 Document object

頁面 JavaScript 裡的 document，指向「目前這份 HTML 文件」所對應的 Document DOM object。

下面是一棵階層樹，不是四個平行物件。每往下一層，就是上一層的 child：

Document                     ← 最外層
└── html                     ← Document 的 child
    └── body                 ← html 的 child
        └── main             ← body 的 child
            └── button       ← main 的 child
                id="daily-schedule-button"
讀 tree 的方法：
button 在 main 裡，main 在 body 裡，body 在 html 裡。縮排代表「包含／父子關係」，不是流程箭頭。

所以：

document.querySelector('#daily-schedule-button')

就是從目前 Document 的 DOM tree 找到那顆 button DOM object，並把它的 reference 交給 JavaScript。

5. 使用者真的點下去：先動的是瀏覽器，不是 JavaScript

當使用者用滑鼠或手指點擊時，JavaScript 並不是一直輪詢畫面問「有人點了嗎？」。

簡化後的因果鏈是：

使用者產生滑鼠／觸控輸入
        │
        ▼
瀏覽器先收到輸入
        │
        ▼
瀏覽器判斷這個位置對應哪個 DOM element
        │
        ▼
瀏覽器決定這次 click 的 target
        │
        ▼
瀏覽器建立 click Event object

例如這次真的點到那顆按鈕：

event.type
→ "click"

event.target
→ 那顆 button DOM object
event.target 不是「誰創造了 Event」。
Event 是瀏覽器建立的；target 表示瀏覽器判定「這次 Event 最初指向哪個 DOM object」。

6. Event object 不等於 Faro telemetry

此時存在的是 browser 原生的 Event object。它是瀏覽器在處理這次互動時使用的 runtime 資料。

Browser Event object
- type = "click"
- target = button DOM object
- bubbles = ...
- eventPhase = ...
- ...

它不會因為存在就自動變成可在 Grafana / OpenSearch 查詢的 click history。要成為 telemetry，後面還需要 Faro 的程式讀取、轉換並送出。

7. JavaScript 先登記 callback，不是事後去「抓 Event」

function handleClick(event) {
  console.log(event.target)
}

document.addEventListener('click', handleClick)

這段程式現在做的事情是：

在 document 這個 EventTarget 上登記：

- event type = "click"
- callback   = handleClick
- capture    = false（預設）

這時候還沒有未來那次 click Event。只是先把「以後遇到 click 時要呼叫哪個函式」登記給瀏覽器。

Callback 的控制方向：
JavaScript 先把 handleClick 這個函式交給瀏覽器；真正 click 發生後，是瀏覽器在適當時機主動呼叫 handleClick(event)。

8. 瀏覽器接著 dispatch Event

知道 target = button 只回答「這次 click 指向誰」。瀏覽器還需要沿著這顆 target 所在的 DOM 階層，決定哪些已登記的 listeners 要被呼叫、順序是什麼。這個過程叫做 event dispatch（事件分派）。

先看 DOM 階層：

Document
└── html
    └── body
        └── main
            └── button  ← event.target 已經確定

然後才是同一次 Event dispatch 的三個 phase：

Capture phase
Document → html → body → main → button

Target phase
button

Bubble phase
main → body → html → Document
兩個非常重要的邊界：
① Capture 開始以前，target 已經知道了；Capture 不是拿來一路找 target。
② Bubble 是從 target 的 parent 往外處理 ancestors；button 自己不會因為進入 Bubble 就自動再執行一次同一個 listener。

9. Listener 什麼時候真的執行？

當 dispatch 走到某個 EventTarget 時，瀏覽器會檢查那裡有沒有符合這次 Event type 與 phase 條件的 listener registration。

例如先前登記的是：

document.addEventListener('click', handleClick)

它是 document 上的 non-capture listener。對 descendant button 的一般 bubbling click 而言，Event 在 Target phase 處理完 button 後往 ancestor bubble，最後抵達 document；這時瀏覽器找到登記好的 callback，主動執行：

handleClick(event)
            ↑
     瀏覽器把本次 Event object
     當參數傳進 callback

所以完整控制流不是：

JavaScript 不停找 click  ✗

而是：

JavaScript 先登記 callback
        ↓
未來使用者 click
        ↓
Browser 建立 Event
        ↓
Browser dispatch Event
        ↓
Browser 找到符合的 listener registration
        ↓
Browser 呼叫 callback(event)
        ↓
JavaScript engine 執行 callback 裡的程式

10. 把 Lesson 1 的整條因果鏈串起來

HTML source
  → Browser 建立／管理 DOM objects

使用者 click
  → Browser 收到輸入
  → Browser 決定 DOM target
  → Browser 建立 click Event object
  → Browser dispatch Event
  → 找到相符 listener registration
  → Browser 呼叫 callback(event)
  → JavaScript 在 callback 中讀 event.target

11. Faro 會從哪裡接手？

到這裡都還是瀏覽器原生事件機制。Lesson 2 才把 Faro 接進來：

Browser click Event
        ↓
document 上事先登記的 Faro listener
        ↓
ClickInstrumentation.handleClick(event)
        ↓
從 DOM 讀 data-* 等 telemetry semantic
        ↓
Faro pushEvent(...)

Recap

  • HTML source、DOM objects、rendered 畫面是不同層次。
  • DOM object 是瀏覽器建立與管理；JavaScript 取得的是它的 reference。
  • HTMLButtonElement 是 button 對應的 DOM 介面／物件型別，不代表存在另一種「HTML object」。
  • id="daily-schedule-button" 是範例作者取的識別名稱；#daily-schedule-button 是 selector。
  • DOM tree 的縮排代表 parent / child hierarchy，不是流程。
  • click Event 是瀏覽器建立的；event.target 是瀏覽器判定這次 Event 最初指向的 DOM object。
  • JavaScript 先登記 callback；Browser dispatch Event 時才主動呼叫 callback。
  • Capture / Target / Bubble 是同一次 Event dispatch 的不同階段；target 在這些 phase 開始以前就已確定。
  • Bubble 從 target 的 parent 往外走，不會讓 target 的同一個 listener 自動再跑一次。
  • Browser Event object 不等於 Faro telemetry。
