    ↓

現在往上追一層：

頁面剛啟動時，誰把 ClickInstrumentation 建起來？它又怎麼拿到 Faro 的 API？

1. 先分清楚三個角色

Foreman Assistant
      │ calls
      ▼
@sre2/faro-click-tracking
      │ calls
      ▼
Grafana Faro Web SDK
角色這堂課只先記住
Foreman Assistant真正的前端應用；決定要開始使用這個 monitoring package。
@sre2/faro-click-tracking公司共用套件；統一驗證設定、建立公司需要的 instrumentations，再呼叫 Faro SDK。
Grafana Faro Web SDK底層 SDK；真正建立 Faro runtime，並讓 instrumentations 開始工作。

所以 @sre2/faro-click-tracking 不是 Faro 本身。它是公司包在 Faro Web SDK 外面的那一層。

2. Foreman 是從 initFaro() 進來的

目前 Foreman Assistant 在 application bootstrap 前呼叫一次：

initFaro(config)

這是公司套件公開給應用使用的入口。也就是說，Foreman 只需要知道這個公開 contract，不需要自己去操作套件裡每一個 internal helper。

Foreman Assistant
    │ calls public API
    ▼
initFaro(config)
    │
    └── 套件內部怎麼拆檔、怎麼保存 instance
        都是 package implementation

這就是這裡所說的 public API：宿主應用被允許依賴的穩定入口。

3. initFaro() 和 initializeFaro() 不是同一個東西

名字很像，但責任不同：

Function屬於誰做什麼
initFaro(config)公司共用套件驗證與組裝公司需要的設定，再呼叫底層 SDK。
initializeFaro({...})Grafana Faro Web SDK真正建立 Faro runtime instance，並啟動 instrumentations。
 
Foreman
  │ calls
  ▼
initFaro(config)          ← 公司套件
  │ internally calls
  ▼
initializeFaro({...})     ← Grafana Faro SDK
  │ returns
  ▼
Faro instance

4. Lesson 2 的 ClickInstrumentation 就是在這裡被啟動

initFaro() 會準備公司需要的 instrumentations，其中包含 Lesson 2 的 ClickInstrumentation，然後把它交給 Faro SDK：

initFaro(config)
    │ creates
    ▼
ClickInstrumentation
    │ passes into
    ▼
initializeFaro({ instrumentations: [...] })
    │ SDK initializes
    ▼
ClickInstrumentation.initialize()
    │ registers
    ▼
document click listener

所以 Lesson 2 的 listener 並不是一直天然存在於 Browser 裡。它是在 application 啟動、Faro package 初始化成功後才被註冊。

因果順序
先有 initFaro() → SDK 建立 runtime → ClickInstrumentation 被 initialize → 才有 document listener → 後面的 click 才可能進 Faro。

5. 為什麼初始化要特別防止「做第二次」？

因為初始化不是單純算出一個值。它會改變 Browser runtime：

initializeFaro(...)
    ├── 建立 Faro runtime
    ├── 啟動 instrumentations
    ├── 註冊 listeners
    └── 啟動 telemetry transport

也就是說，初始化具有 runtime side effects：程式執行後，Browser 裡真的多了會持續工作的東西。

因此第二次初始化不能等做到一半才發現：

第二次 initFaro()
    ↓
ensureNotInitialized()
    ├── 已經初始化 → throw，停止
    └── 尚未初始化 → 才繼續

目前 implementation 已驗證：這個檢查發生在新的 initializeFaro() 之前，因此第二次呼叫會在建立另一個 Faro runtime 前失敗。

6. 第一個 Faro instance 建好後，為什麼還要保存起來？

initializeFaro() 會回傳一個 Faro instance。可以先把它理解成：

目前這個頁面正在使用的 Faro runtime 的程式入口。

套件會把這個 reference 保存起來：

initializeFaro(...)
    │ returns
    ▼
Faro instance
    │ registerFaroInstance(faro)
    ▼
套件內保存的 faroInstance reference

原因是 ClickInstrumentation 自己在 Faro instrumentation lifecycle 裡，可以直接取得 SDK 提供的 api；但套件裡其他普通 exported functions 不一定身處這個 instrumentation object 裡。

這些 function 若之後需要操作同一個 Faro runtime，就必須能找到先前建立的那個 instance。

Lesson 4 會正式處理 User、Device、Environment。這裡只需要知道：有些後續 public API 需要取得「同一個已初始化的 Faro instance」，所以 package 必須保存它。

7. 保存一個 instance，就是這裡的 Singleton

先從需求推回來：

頁面只初始化一次
        ↓
只建立一個主要 Faro runtime
        ↓
package 只保存一個 faroInstance reference
        ↓
後續 package functions 都拿同一個 instance

現行核心可以簡化成：

let faroInstance = undefined

initFaro() 成功後：
faroInstance = faro

這種「module 裡刻意只保存一個 instance」的狀態，這堂課才把它命名為 module-level singleton state。

它不是 JavaScript 語言規定 Faro 只能建立一個 object，也不是 Browser 自帶的限制；是這個 package 自己選擇的 lifecycle contract。

8. 所以現行初始化順序可以縮成四步

1. ensureNotInitialized()
      ↓
2. validate / prepare config
      ↓
3. initializeFaro({...})
      ↓ returns Faro instance
4. registerFaroInstance(faro)

這四步裡最重要的兩個邊界：

  • ensureNotInitialized() 在 runtime side effects 發生以前阻止第二次初始化。
  • registerFaroInstance() 把成功建立的 Faro instance 保存給 package 後續使用。

至於 User 怎麼同步、Device 怎麼判斷、Environment 怎麼決定 endpoint，全部留到 Lesson 4，不在這一課展開。

Recap

  • Foreman 呼叫公司套件的 initFaro(config)；公司套件再呼叫 Grafana SDK 的 initializeFaro()。
  • initializeFaro() 建立真正的 Faro runtime，並讓 ClickInstrumentation 開始工作。
  • 因此 Lesson 2 的 document listener 是 package initialization 的 runtime side effect 之一。
  • 第二次 initFaro() 會在新的 Faro runtime 建立前被拒絕。
  • 成功建立的 Faro instance 會被 package 保存，讓後續 package functions 能存取同一個 runtime。
  • 這個「只保存一個 Faro instance reference」才是目前 package 的 singleton state。
  • User、Device、Environment 的實際資料來源與 lifecycle 留到 Lesson 4。
如果你能不用看圖，自己從「Foreman 呼叫 initFaro()」一路說到「document click listener 被註冊」，這堂課的主模型就建立了。任何一段不確定，都可以直接問我那一段。
