2. initFaro() 裡面真正重要的控制順序

目前 source 已驗證的順序可以縮成下面這個等價骨架：

function initFaro(config) {
  ensureNotInitialized()

  // validate config ...

  const faro = initializeFaro({
    // package 自己建立的 ClickInstrumentation 會交給 Faro
  })

  registerFaroInstance(faro)
  return faro
}

這段是依現行 initFaro.ts:13-146 的已驗證呼叫順序整理出的等價 skeleton，不宣稱是逐字 source。對照：faro-click-tracking implementation evidence。

名稱這堂課怎麼理解
initFaro()公司 package 的入口。宿主應用呼叫它。
initializeFaro()Grafana Faro Web SDK 提供的 function。公司 package 會呼叫它，真正建立 Faro object。

SDK 在這裡只需要理解成：Grafana 提供、讓前端程式直接使用 Faro 的程式庫。

3. ClickInstrumentation 是公司 package 自己實作的

ClickInstrumentation 不是 Grafana Faro SDK 直接提供的現成 click tracker。它是 @sre2/faro-click-tracking package 自己的程式物件，現行 implementation 位於 features/click/clickInstrumentation.ts。

先只看這個 object 對本課重要的兩個 function：

ClickInstrumentation object
├── initialize()
│     └── 負責註冊 document click listener
│
└── handleClick(event)
      └── click 發生後讀 event、組 payload、pushEvent(...)

package 建立這個物件，再把它交給 Faro SDK；Faro 初始化它時，才會執行它的 initialize()。

@sre2/faro-click-tracking
  │ creates
  ▼
ClickInstrumentation object
  │ passes to
  ▼
Grafana initializeFaro(...)
  │ initializes
  ▼
ClickInstrumentation.initialize()

這裡只使用目前 implementation evidence 已證實的責任邊界。對照：Click implementation / initialization evidence。

這一課不用深入 Faro SDK 為什麼能啟動自訂 instrumentation。現在只需要知道責任邊界：ClickInstrumentation 是 package 寫的；Faro SDK 負責在初始化流程中啟動它。

4. listener、callback、handleClick 是三個不同層次

ClickInstrumentation.initialize() 會做出類似這件事：

document.addEventListener(
  'click',
  this.handleClick
)

這行不是現在執行 handleClick()。它是在 Browser 裡建立一條 listener registration：

listener registration
├── EventTarget = document
├── event type  = click
└── callback    = this.handleClick

所以四個角色要分開：

角色在這裡是什麼
ClickInstrumentation公司 package 自己實作、負責 click tracking 的 object。
listener registrationBrowser 保存的監聽規則：在哪個 object、監聽哪種 event、之後要 call 哪個 callback。
handleClick一個 function reference；被 listener registration 保存成 callback。
handleClick(event)未來 Browser dispatch click 時，實際呼叫 callback 的那一次執行。
 
ClickInstrumentation.initialize()
  │ calls Browser API
  ▼
document.addEventListener('click', this.handleClick)
  │ creates
  ▼
Browser listener registration
  │ stores callback reference to
  ▼
this.handleClick
  │ Browser calls later during click dispatch
  ▼
handleClick(event)

因此「click listener 的 callback」在目前這個 implementation 裡，就是 handleClick。

如果這裡的「為什麼傳 handleClick 而不是 handleClick()」還不直覺，直接看 Reference：Callback 到底是什麼。這張 Reference 專門拆 function reference、listener registration 與 Browser 之後呼叫 callback 的關係。

5. 為什麼第二次 initFaro() 要被擋掉？

第一次初始化完成後，Browser 裡已經有持續工作的東西，例如上面的 click listener registration。

第一次 initFaro()
  → Faro object 建立
  → ClickInstrumentation.initialize()
  → document click listener 已註冊

因此第二次呼叫時，package 先做：

ensureNotInitialized()

已經初始化？
├── yes → throw，停止
└── no  → 才繼續 initializeFaro()

重點不是背 ensureNotInitialized，而是看懂檢查發生在另一個 Faro object 與另一組功能建立以前。

6. initializeFaro() 回傳的是一個實際 object

const faro = initializeFaro(...)

initializeFaro() 成功後會回傳實際建立出的 Faro JavaScript object。這個實際 object 就是這裡說的 instance。

Faro                 → 一種東西／型別概念
faro 這個實際 object → 這次建立出的 instance

7. 為什麼還需要 registerFaroInstance(faro)？

關鍵不是「還需不需要再建立 Faro」。不需要。 Faro object 在 initializeFaro() 時就已經建立好了。

真正的問題是：faro 是 initFaro() 裡面的 local variable，也就是只有這個 function 內的程式可以直接用這個名字。

function initFaro() {
  const faro = initializeFaro()

  // 這裡看得到 faro
}

function anotherPackageFunction() {
  // 這裡不能直接使用上面的 local faro
}

所以 package 若希望 initFaro() 結束後，其他 function 還能取得同一個 Faro object，就需要把它的 reference 保存到 function 外面的 variable。這裡的 module-level variable 只表示「寫在 function 外、由這個 package module 內的程式共用的 variable」。

let faroInstance

function initFaro() {
  const faro = initializeFaro()
  registerFaroInstance(faro)
}

function registerFaroInstance(faro) {
  faroInstance = faro
}

這時不是兩顆 Faro：

local variable:  faro ──────────────┐
                                    │ references
                                    ▼
                              Faro object A
                                    ▲
                                    │ references
module variable: faroInstance ──────┘

faro 與 faroInstance 是兩個 variable，但它們保存的是指向同一顆 object 的 reference。沒有 clone，也沒有第二次建立 instance。

等 initFaro() 執行結束後，local variable faro 不再是其他 package function 可直接使用的名稱；module-level faroInstance 仍然可以被 package 其他程式取得。

需求與 implementation 要分開：
真正需要的是「把同一個 Faro object 的 reference 保存到 initFaro() local scope 外」。registerFaroInstance() 是目前 package 選擇實作這個需求的 function；不是 JavaScript 規定一定要有這個 function。

現行 source 已驗證 package 使用 module-scope faroInstance，並透過 registerFaroInstance() 保存成功建立的 Faro instance。對照：singleton / public-surface evidence，來源位置為 faroInstance.ts:6-47。

Optional terminology
這種「package 只保存一份主要 instance，並阻止重複初始化」的做法有時會被稱為 singleton-style state。名稱不是本課考點；先理解 object 與 reference 的實際行為即可。

Recap

  • 宿主應用呼叫公司 package 的 initFaro()；package 再呼叫 Grafana 的 initializeFaro()。
  • ClickInstrumentation 是公司 package 自己實作的 object，不是 Faro SDK 內建的現成 click tracker。
  • ClickInstrumentation.initialize() 會建立 Browser listener registration；這條 registration 的 callback reference 是 handleClick。
  • 真正 click dispatch 到 document 時，Browser 才呼叫 handleClick(event)。
  • initializeFaro() 建立並回傳實際 Faro object；這就是本課說的 instance。
  • registerFaroInstance() 不會建立第二個 instance；它把同一個 object 的 reference 保存到 module-level faroInstance。
  • 保存 module-level reference 的原因，是讓 initFaro() local scope 結束後，其他 package function 仍能取得同一個 Faro object。
  • 第二次 initFaro() 會在另一個 Faro object 與另一組功能建立以前被拒絕。
