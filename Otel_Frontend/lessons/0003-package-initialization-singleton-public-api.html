Package Initialization, Singleton, and Public API

Milestone 2 · 宿主應用 → faro-click-tracking → Grafana Faro SDK

這堂課的目標
學完後，你應該能從宿主應用呼叫 initFaro(config) 開始，一路解釋套件如何建立 Faro runtime、為什麼要保存唯一的 Faro instance、為什麼重複初始化必須被阻止，以及 public API 與套件內部 helper 的責任邊界。

Lesson 2 已經追到 ClickInstrumentation 的內部：

Browser click
  → document listener
  → ClickInstrumentation.handleClick(event)
  → build payload
  → api.pushEvent('click', payload)

但還有一個更上游的問題：

這個 ClickInstrumentation 到底是誰建立、誰啟動，裡面的 api 又從哪裡來？

答案從宿主應用第一次初始化整個套件開始。

1. 先把三個角色分開

這堂課只需要先建立三層：

宿主應用
  │ calls
  ▼
@sre2/faro-click-tracking
  │ calls / configures
  ▼
Grafana Faro Web SDK
角色先理解成什麼
宿主應用真正的前端產品。它知道自己的 app name、environment、要追哪些 DOM attributes，以及何時初始化。
@sre2/faro-click-tracking公司共用套件。它把宿主設定轉成一致的 Faro 初始化方式，並加上 Click、User、Device 等公司需要的行為。
Grafana Faro Web SDK真正提供 Faro runtime、telemetry API、transport 與 instrumentation framework 的底層 SDK。

所以共用套件不是 Faro 本身；它是包在 Faro SDK 外面的公司層。

2. Public API 是「宿主應用被允許依賴的入口」

宿主應用不應該知道套件裡每一個 internal file。它只應該依賴套件公開的 contract。

最重要的入口就是：

initFaro(config)

另外像：

setFaroUser(...)
clearFaroUser(...)

也是宿主可以呼叫的 public API。

但下面這些屬於套件內部機制：

ensureNotInitialized()
registerFaroInstance(...)
getFaroInstanceOrThrow(...)
邊界
Public API 是宿主應用的 contract；internal helper 是套件為了實作 contract 使用的工具。宿主不應該直接依賴 internal helper，否則套件內部一重構，宿主也會被綁死。

3. 最容易混淆的兩個名字：initFaro() vs initializeFaro()

它們不是同一個 function。

Function屬於誰作用
initFaro(config)@sre2/faro-click-tracking公司共用套件提供給宿主應用的初始化入口。
initializeFaro({...})Grafana Faro Web SDK真正建立 Faro runtime instance，啟動 SDK 的 transports / instrumentations。

控制方向是：

宿主應用
  │ calls
  ▼
initFaro(config)                 ← 公司共用套件
  │ internally calls
  ▼
initializeFaro({...})            ← Grafana Faro SDK
  │ returns
  ▼
Faro instance

因此你之後看 code 時，只要看到這兩個名字，就先問：「現在是在公司 wrapper 還是 Grafana SDK？」

4. 為什麼初始化不是單純「new 一個 object」？

初始化會產生 runtime side effects。

例如 Lesson 2 看過的：

new ClickInstrumentation(...)
        │
        │ handed to Faro SDK
        ▼
initializeFaro(...)
        │ initializes instrumentation
        ▼
document.addEventListener('click', ...)

換句話說，成功初始化後，不只是記憶體裡多一個 object；Browser 裡已經開始有 listener、transport 與 telemetry runtime 在工作。

這也是為什麼「初始化幾次」是一個重要 lifecycle 問題。

5. initFaro() 的主流程

把現行實作先壓成最重要的順序：

宿主應用 calls initFaro(config)
        │
        ▼
ensureNotInitialized()
        │
        ├── 已初始化 → throw，立即停止
        │
        ▼
validate / prepare config
        │
        ▼
建立需要的 instrumentations
        │
        ├── Faro web instrumentations
        ├── TracingInstrumentation
        ├── ClickInstrumentation
        └── UserSyncInstrumentation?   ← 有設定才建立
        │
        ▼
Grafana initializeFaro({...})
        │
        ├── 建立 Faro runtime
        └── 啟動 instrumentations / transport
        │
        ▼
得到 faro instance
        │
        ▼
registerFaroInstance(faro)
        │
        ▼
其他 opt-in setup
        │
        ▼
return faro

Lesson 3 不需要先深入 User、Device、Environment 的細節；那些是下一課。這裡只要先抓住：

initFaro() 是公司共用套件的 orchestration layer：它把設定、公司自訂 instrumentation 與 Grafana Faro SDK 接起來。

6. Lesson 2 的 ClickInstrumentation 在這裡被接上 Faro

Lesson 2 我們是從 ClickInstrumentation 裡面往下看。

現在從上面看：

initFaro(config)
  │
  ├── new ClickInstrumentation({
  │     trackAttributes: config.trackAttributes
  │   })
  │
  ▼
initializeFaro({
  instrumentations: [
    ...,
    ClickInstrumentation,
    ...
  ]
})

也就是：

宿主 config.trackAttributes
        │ passed into
        ▼
ClickInstrumentation
        │ registered with
        ▼
Grafana Faro SDK instrumentation framework

因此 ClickInstrumentation 不是宿主應用自己手動呼叫 initialize()；它被交給 Faro SDK，SDK 在初始化 instrumentation 時讓它開始工作。

7. 為什麼套件要保存 Faro instance？

關鍵原因不是「想做 singleton pattern」本身，而是後來出現了另一類 public API。

ClickInstrumentation 身處 Faro instrumentation framework 裡，所以它能取得 SDK 提供的 API，最後呼叫：

this.api.pushEvent(...)

但 setFaroUser() 只是一般 exported function：

宿主應用
  │ calls
  ▼
setFaroUser(user)

它不在 instrumentation object 裡，沒有一個天然的 this.api 可以使用。

因此套件需要一個共同可取得的 Faro instance：

initFaro()
  │ gets
  ▼
Faro instance
  │ registerFaroInstance(faro)
  ▼
module-level faroInstance
  │ later read by
  ▼
setFaroUser() / clearFaroUser() / other internal consumers

這才是現行 singleton 的因果來源。

8. 這裡的 Singleton 到底是什麼？

先不要把 Singleton 想成複雜 design pattern。現行核心就是一個 module-scope variable：

let faroInstance: Faro | undefined;

初始化前：

faroInstance === undefined

initFaro() 成功後：

faroInstance = faro

因此同一份套件 module 在這個網頁應用 runtime 中，大家都透過同一個變數取得同一個 Faro instance。

精確說法
這裡是「module-level singleton state」：套件刻意只保存一個 Faro instance reference。不是 Browser 自帶的全域 singleton，也不是 JavaScript 語言強制只能建立一個 Faro object。

9. 第二次 initFaro() 的防護與可能風險

先分開 evidence 與風險推演
現行 source 與 tests 直接證明：成功初始化後再次呼叫 initFaro()，會在建立新的 SDK runtime 前 throw。下面的 duplicate listener／telemetry 是「如果沒有這項防護」的合理風險情境；目前 evidence 沒有證明它就是作者留下這項設計的完整歷史理由。

假設完全沒有防護：

第一次 initFaro()
  → ClickInstrumentation A
  → document listener A

第二次 initFaro()
  → ClickInstrumentation B
  → document listener B

此時一次 Browser click 可能同時走進兩條 listener：

one Browser click
  ├── listener A → pushEvent(...)
  └── listener B → pushEvent(...)

你看到的症狀就可能是「同一次互動送出重複 telemetry」。更糟的是，第二個 runtime 還可能覆蓋套件保存的 instance reference，讓實際啟動的 runtime 與 public API 使用的 instance lifecycle 變得不一致。

可以直接由現行 implementation 證實的行為是：

initFaro()
  ↓
ensureNotInitialized()
  ↓
已經有 faroInstance ?
  ├── yes → throw
  └── no  → 才能繼續建立 Faro runtime

10. 在 initializeFaro() 之前檢查的效果

因為如果先做：

initializeFaro(...)
  ↓
listener / transport 已經建立
  ↓
最後才發現「其實已初始化過」
  ↓
throw

那錯誤雖然拋了，但副作用已經發生。

現行實作先做：

ensureNotInitialized()
  ↓
確認安全
  ↓
initializeFaro(...)

這個順序形成 fail-fast boundary：重複初始化會在新的 runtime side effect 發生前被拒絕。這是可由呼叫順序直接證明的 implementation effect；不需要進一步假定作者動機。

而 registerFaroInstance(faro) 存入 instance 前又再檢查一次，是最後一道防線。

11. Public API 在初始化前被呼叫會怎樣？

以 user API 為例：

setFaroUser(user)
  ↓
getFaroInstanceOrThrow('setFaroUser')
  ↓
faroInstance 有值嗎？
  ├── no  → throw：請先 initFaro()
  └── yes → faro.api.setUser(user)

所以套件 lifecycle 有一個明確順序：

未初始化
  │
  │ initFaro(config)
  ▼
已初始化
  │
  ├── setFaroUser(...)
  ├── clearFaroUser(...)
  └── 其他需要 Faro instance 的 API

不能把這個順序倒過來。

12. Cleanup / dispose 的 public API 邊界

ClickInstrumentation.destroy() 與 UserSyncInstrumentation.destroy() 會移除它們各自建立的 listeners，device detector 也有 package-internal stop mechanism。這證明 SDK lifecycle 內部存在 cleanup 行為。

但目前 @sre2/faro-click-tracking 的 public exports 沒有 dispose()、reset() 或其他完整 teardown API。因此宿主應用不能依目前 package contract 假設：

initFaro()
  → public dispose()
  → 再次 initFaro()
精確邊界：可以證實 instrumentation 內部有 destroy()；不能教成宿主目前有公開的完整 cleanup／re-initialization lifecycle。

Self-check

1. initFaro() 和 initializeFaro() 是同一個 function 嗎？

不是。initFaro() 是公司共用套件給宿主應用的 public API；initializeFaro() 是 Grafana Faro Web SDK 的初始化 function，前者內部會呼叫後者。

2. 為什麼套件需要保存 faroInstance？

因為像 setFaroUser() 這種一般 exported function 不在 Faro instrumentation framework 裡，沒有自動取得的 this.api；它需要透過套件保存的 Faro instance 去呼叫 Faro API。

3. Singleton 是 Browser 或 JavaScript 強制只能有一個 Faro object 嗎？

不是。這是套件自己的 module-level state 設計：只保存一個 Faro instance reference，並主動阻止第二次 initFaro()。

4. Source 直接證明重複初始化一定會產生 duplicate telemetry 嗎？

沒有。Source 直接證明第二次 initFaro() 會在建立新 runtime 前 throw；duplicate listener／telemetry 是移除防護後的合理風險推演，不是已證實的歷史設計理由。

5. 為什麼 ensureNotInitialized() 必須放在 initializeFaro() 之前？

要在任何 runtime side effect 發生前 fail fast。否則即使最後 throw，listener 或 transport 可能早已建立。

6. 宿主目前能呼叫 package public dispose() 後重新初始化嗎？

不能由目前 contract 得出這個結論。Instrumentation 內部有 destroy()，但 package public exports 沒有完整 dispose()／reset API。

Recap

  • 宿主應用呼叫公司套件的 initFaro(config)；公司套件再呼叫 Grafana SDK 的 initializeFaro()。
  • initFaro() 是 orchestration layer：驗證設定、建立公司 instrumentation、呼叫底層 Faro SDK。
  • Grafana initializeFaro() 建立真正的 Faro runtime，並啟動 transport / instrumentations。
  • ClickInstrumentation 是在 package initialization 時交給 Faro SDK，因此 Lesson 2 的 document listener 也是在這個 lifecycle 中被啟動。
  • 套件以 module-scope faroInstance 保存唯一的 Faro instance，讓一般 public API 也能存取 Faro API。
  • 第二次 initFaro() 會在建立新 runtime 前被阻止；duplicate listener／telemetry 是缺少防護時的風險推演，不是已證實的作者 rationale。
  • ensureNotInitialized() 在建立 runtime 前 fail fast；registerFaroInstance() 再做最後一道檢查。
  • 需要 Faro instance 的 public API 若在初始化前被呼叫，會透過 getFaroInstanceOrThrow() 明確失敗。
  • 內部 instrumentations 有 cleanup hooks，但 package 沒有公開完整的 dispose()／reset API。
