1. 先從宿主應用的真實設定開始

這裡固定用「宿主應用」表示實際導入 Faro package 的前端；目前的例子就是 Foreman Assistant。

Foreman 的 main.ts 已驗證會在 app bootstrap 前呼叫一次 initFaro()，而且目前設定至少包含：

initFaro({
  environment: 'tw-prod',
  trackAttributes: ['data-link-name'],
  enableDeviceTypeDetection: true,
  getUser: /* Lesson 4 再看 */
})

上面只保留目前 evidence 已驗證的欄位與值，用來讀控制流程；不是逐字複製整份 main.ts。來源：Foreman src/main.ts:11-34。

先只看一件事：

宿主應用
  │ calls
  ▼
initFaro(...)

initFaro() 是 @sre2/faro-click-tracking 這個公司共用 package 提供給宿主應用的入口。

2. initFaro() 裡面真正重要的控制順序

目前 source 已驗證的順序可以縮成下面這個等價骨架：

function initFaro(config) {
  ensureNotInitialized()

  // validate config ...

  const faro = initializeFaro({
    // ClickInstrumentation 等功能會在這裡交給 Faro
  })

  registerFaroInstance(faro)
  return faro
}

這段是依現行 initFaro.ts:13-146 的已驗證呼叫順序整理出的等價 skeleton，不宣稱是逐字 source。

目前只需要認識兩個名字：

名稱這堂課怎麼理解
initFaro()公司 package 的入口。宿主應用呼叫它。
initializeFaro()Grafana Faro Web SDK 提供的 function。公司 package 會呼叫它，真正建立 Faro。

SDK 在這裡只需要理解成：Grafana 提供、讓前端程式直接使用 Faro 的程式庫。

3. Lesson 2 的 ClickInstrumentation 在這裡被啟動

ClickInstrumentation 你已經在 Lesson 2 看過：它就是那個會註冊 document click listener、收到 Browser Event 後建立 Faro click telemetry 的物件。

Lesson 3 新增的只有它「何時開始工作」：

宿主應用 calls initFaro()
        │
        │ package prepares ClickInstrumentation
        ▼
initializeFaro(...)
        │ Faro initializes ClickInstrumentation
        ▼
ClickInstrumentation.initialize()
        │ registers
        ▼
document.addEventListener('click', ...)

所以 document listener 並不是 Browser 天生就有，也不是第一次 click 發生時才建立。

它是在頁面啟動階段，Faro 初始化這個功能時被註冊。

4. 為什麼第二次 initFaro() 要被擋掉？

因為第一次初始化完成後，Browser 裡已經真的多了持續工作的東西，例如 Lesson 2 的 click listener。

第一次 initFaro()
  → Faro 建立
  → ClickInstrumentation.initialize()
  → document click listener 已存在

因此第二次呼叫時，package 先做：

ensureNotInitialized()

已經初始化？
├── yes → throw，停止
└── no  → 才繼續 initializeFaro()

重點不是記住 ensureNotInitialized 這個名字，而是看懂檢查發生在新的 Faro 建立以前。

因此目前可直接由 source 證實的是：

第二次 initFaro() 會在建立第二個 Faro object 與另一組功能以前失敗。

5. initializeFaro() 回傳的東西是什麼？

initializeFaro() 成功後會回傳一個實際建立出來的 Faro JavaScript object：

const faro = initializeFaro(...)

這個「實際建立出來的 object」就是這裡說的 instance。

不要先把 instance 想成特殊設計名詞。這裡只是在分：

Faro                 → 一種東西／型別概念
faro 這個實際 object → 這次建立出的 instance

6. 為什麼 package 還要把這個 Faro object 存起來？

因為 initFaro() 結束後，package 裡其他 function 之後還可能需要操作同一個 Faro object。

現行 source 已驗證 package 會保存一個 faroInstance reference：

let faroInstance

function registerFaroInstance(faro) {
  faroInstance = faro
}

這段用真實名稱表達目前 faroInstance.ts:6-47 已驗證的核心行為；為了教學省略 error handling 與其他細節。

因果關係是：

initializeFaro(...)
  │ returns the created Faro object
  ▼
faro
  │ saved by
  ▼
registerFaroInstance(faro)
  │
  ▼
package 之後仍能拿到同一個 Faro object

Lesson 4 才會看到「哪些後續功能會用到它」。這一課不需要先學 User / Device 的細節。

Optional terminology
這種「package 只保存一份主要 instance，並阻止重複初始化」的做法有時會被稱為 singleton-style state。這個名稱不是本課考點；只要理解上面的實際行為即可。

Recap

  • 宿主應用呼叫公司 package 的 initFaro()。
  • initFaro() 內部再呼叫 Grafana 的 initializeFaro()。
  • Faro 初始化 ClickInstrumentation 時，Lesson 2 的 document click listener 才被註冊。
  • 第二次 initFaro() 會在另一個 Faro object 與另一組功能建立以前被拒絕。
  • initializeFaro() 回傳的實際 Faro object，就是這裡說的 instance。
  • package 保存 faroInstance，讓後續 function 還能取得同一個 Faro object。
  • 「singleton」只是這種設計可能使用的名稱，不是本課需要背的概念。
