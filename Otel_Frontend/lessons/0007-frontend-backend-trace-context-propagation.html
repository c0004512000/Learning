Frontend-to-Backend Trace Context Propagation

Milestone 4 · 先理解為什麼 parent relationship 會在 HTTP 邊界消失，再看 traceparent 怎麼把它帶過去

這堂課的目標
你要能從第一性原理解釋：Browser 與 backend 明明是兩個不同 process／runtime，為什麼最後還能在 tracing system 裡變成同一條 trace；以及 backendUrls、traceparent、backend instrumentation 各自負責哪一段。

Lesson 6 已經建立一個重要習慣：不要因為設定存在就宣稱 runtime 已成功。Lesson 7 繼續沿用這個 evidence boundary。

1. 先不談 traceparent：為什麼跨到 backend 後關係會消失？

假設 Browser 正在執行一個 HTTP request，tracing library 在 Browser memory 裡知道：

Browser memory

Trace T
└─ HTTP client span A

這裡的「Trace T 裡有 span A」只是一個 runtime 裡的資料關係。

接著 Browser 真的送出 HTTP request：

Browser runtime                         Backend runtime

Trace T
└─ span A
     │
     │ sends HTTP request
     ├───────────────────────────────────────> request arrives
                                             │
                                             └─ backend only sees HTTP data

問題來了：

Backend process 根本看不到 Browser memory 裡的 span A。那它怎麼知道「我現在處理的這筆 request，應該接在 span A 後面」？

HTTP 只會跨 process boundary 傳送實際被序列化的資料，例如 URL、method、headers、body。Browser 裡面的 JavaScript object、span object、function reference，都不會自己穿過網路。

所以 propagation 必須存在
如果想保留 parent/child 關係，就必須把「足以重建 trace 關係的最小資訊」轉成 HTTP 可以攜帶的資料，再由 backend 讀回來。

2. 先建立最小 trace / span 模型

這堂課只需要兩個 ID：

概念先這樣理解
trace ID整次跨系統工作共用的 ID。只要還在同一條 distributed trace，frontend / backend spans 都保留同一個 trace ID。
span ID某一個 operation 自己的 ID。每個 span 有自己的 span ID。

例如：

Trace ID = T

Browser HTTP client span
  span ID = A

Backend server span
  span ID = B
  parent = A

Backend DB span
  span ID = C
  parent = B

這樣 tracing system 才能畫成：

Trace T

A  Browser HTTP client span
└─ B  Backend server span
   └─ C  Database span

注意：同一條 trace 不代表所有 span 都共用同一個 span ID。共用的是 trace ID；每個 operation 有自己的 span ID，再另外記住 parent relationship。

3. traceparent 就是跨 HTTP 邊界的「最小關係描述」

W3C Trace Context 把這套跨服務資訊標準化成 HTTP header。核心 header 叫：

traceparent

version 00 的格式是：

traceparent: 00-<trace-id>-<parent-id>-<trace-flags>

用一組教材假值：

traceparent: 00-7f3a9c0d21b54e7aa4b0e7d3c8712f60-5c1d7a9b3e204f11-01
             │  │                                │                │
             │  │                                │                └─ trace-flags
             │  │                                └─ parent-id
             │  └─ trace-id
             └─ version
Field意義
00traceparent format version。
trace-id整條 trace 的 ID；version 00 是 32 個 lowercase hex characters。
parent-idcaller 目前 operation/request 的 ID；常見 tracing system 中就是 caller span ID，version 00 是 16 個 lowercase hex characters。
trace-flagstracing flags；01 常見地表示 sampled bit 被設置，但它不是「一定成功寫入 storage」的保證。

W3C 定義見 Trace Context §3.2；本課重用的查表版在 Reference｜W3C traceparent 快速查表。

4. 最容易誤會：parent-id 不是 backend 要沿用的 span ID

假設 Browser 這次 outbound HTTP span 是：

traceId = T
spanId  = A

那 Browser 送出去的 context 可以表示成：

traceparent = 00-T-A-...

Backend 收到後，不是把自己的 span ID 也設成 A。Backend 要建立自己的 operation：

Browser                         HTTP                        Backend

client span A
traceId = T
spanId  = A
    │
    │ injects context
    ▼
traceparent = 00-T-A-...
                               │
                               │ carries caller context
                               ▼
                                                   server span B
                                                   traceId      = T
                                                   spanId       = B
                                                   parentSpanId = A

所以真正的關係是：

同一個 traceId T

A (Browser)
└─ B (Backend)
記憶點
trace-id 回答「我們是不是同一條 trace？」；parent-id 回答「接收端的新 operation 應該接在 caller 的哪個 operation 後面？」

5. 這件事在你們的 Faro package 裡是怎麼接起來的？

你們的宿主專案不是直接操作 OpenTelemetry 的 propagation API；它是透過公司 package：

initFaro({
  ...,
  backendUrls: [
    'https://api.example.com',
    /^https:\/\/.*\.example\.com$/,
  ],
})

現行 package evidence 已確認：

host app
  │ passes
  ▼
backendUrls
  │
  │ package forwards as
  ▼
TracingInstrumentation
  └─ instrumentationOptions.propagateTraceHeaderCorsUrls

接著 Faro Web SDK v2.9.0 的實作再做兩件事：

TracingInstrumentation
  │
  ├─ registers → W3CTraceContextPropagator
  │
  └─ registers → Fetch / XHR instrumentation
                    │
                    └─ receives propagateTraceHeaderCorsUrls

所以三個角色要分開：

角色責任
backendUrls告訴 package 哪些 backend/business API URL 應該被納入 cross-origin trace-header propagation 設定。
Fetch / XHR instrumentation觀察 Browser network operation，建立／管理 HTTP tracing span，並在適用的 request 上使用 propagator。
W3CTraceContextPropagator把目前 trace context 序列化成標準 W3C header，或從 incoming carrier 還原 context。

Internal contract：faro-click-tracking evidence。Faro v2.9.0 source verification：trace-context and Faro web-tracing source pointers。

backendUrls 不是 Alloy URL
它是「哪些 business/backend request 要參與 propagation」的設定。Faro telemetry 要送去哪個 receiver，是另一條 transport/export 路徑。

6. 這裡其實有兩條完全不同的網路路徑

這是 Lesson 7 最重要的責任邊界。

Propagation 傳的是 context；export 傳的是 span telemetry。

這代表幾個很實際的情境：

情境可能看到什麼
Propagation 失敗，但 API request 本身成功Frontend 與 backend 都有 trace，但變成兩條不同 trace。
Propagation 成功，但 Browser span export 失敗Backend 可能延續同一個 trace context，但 Tempo 裡缺 frontend parent span。
Propagation 成功，但 backend span export 失敗Browser span 可見，但 backend operation 沒出現在 trace backend。
兩邊都 export，但 trace ID 不同要查 propagation / extraction，而不是先怪 Tempo grouping。

同一次 API request 還可能有另一個 Browser 視角：faro.performance.resource

Tracing 不是 Faro 對 Browser HTTP request 唯一能產生的 telemetry。Jeter stage 的實際 observation 顯示，同一次 business request 同時產生了 tracing telemetry 與一筆 faro.performance.resource event。

同一次 Browser API request
        │
        ├─ tracing instrumentation
        │    └─ faro.tracing.fetch + resourceSpans
        │         └─ trace / span
        │              └─ Tempo
        │
        └─ Browser performance instrumentation
             └─ faro.performance.resource
                  └─ event
                       └─ current stage pipeline → Loki

這兩種 telemetry 回答的是不同問題：

Evidence主要回答什麼常見 Debug 用途
Tempo trace / spans這次 distributed operation 經過哪些 operations，以及時間花在哪裡。找 frontend、backend、DB、downstream 哪個 span 真正耗時。
faro.performance.resource in LokiBrowser 對這個 HTTP resource 實際觀察到什麼。看 URL、status、總 duration、TTFB、response transfer、size、cache 等 Browser-side evidence。
不要把它寫成固定的「先查哪一個」
如果目標是定位「API 到底慢在哪個 operation」，而完整 trace 存在，Trace 是更直接的 root-cause evidence。faro.performance.resource 是互補的 Browser-side evidence；如果 matching trace 因 sampling、retention 或其他原因不可用，它仍可能保留 URL / status / duration / TTFB 等線索。

faroResourceId、faroNavigationId 是 Faro 對 resource/navigation 的識別資訊，不要把它們當成 trace_id 或 span_id。要驗證 distributed trace，仍然回到 traceparent、trace ID、span ID 與 parent relationship。

這個 Browser performance event 的實際 Jeter payload、Loki storage path 與 Debug scope 見 Faro performance resource runtime verification。這裡只建立 tracing 與 Browser resource performance 的責任邊界，不展開完整 Resource Timing API。

7. Backend 收到 traceparent 後發生什麼？

先不綁死某個 framework，從 tracing system 的必要行為理解：

Incoming HTTP request
  │
  ├─ has valid traceparent?
  │       │
  │       ├─ yes → extract traceId + caller parent context
  │       │          │
  │       │          └─ create current server operation in same trace
  │       │
  │       └─ no  → no incoming parent context
  │                  │
  │                  └─ create a new trace context
  ▼
Backend handles request

W3C processing model 明確區分「收到 traceparent」與「沒收到 traceparent」兩種情況。收到合法 context 時，tracing system 才有資訊延續原本的 trace；沒有時，它只能從自己這邊建立新的 trace context。

Specification basis: W3C Trace Context §4 Processing Model。

Jeter backend 已知設定與 runtime proof

現有 evidence 已確認 Jeter backend：

  • 是 ASP.NET Core application。
  • 啟用了 OpenTelemetry ASP.NET Core tracing instrumentation。
  • backend spans 透過 OTLP exporter 送往設定的 Collector endpoint。
  • CORS policy 對設定的 frontend origin 開放 method / headers。

此外，2026-09-20 已完成一筆 Jeter Slow scenario 的 runtime join verification：Browser business request 的 traceparent parent ID 與 Tempo 中 frontend client span ID 相同，backend server span 的 parent 也等於該 frontend span ID，而且 frontend / backend spans 共用同一個 trace ID。

Browser business request
traceparent = 00-T-A-01
              │  │
              │  └─ caller/frontend span A
              └─ trace T

Tempo trace T
A  frontend client span
└─ B  backend server span
      parent = A

這是一筆具體 Jeter Slow request的 runtime proof，不代表所有 Jeter endpoint、所有 Browser session 或其他 frontend 專案都已自動證明正確。

Configuration evidence: Jeter host integration and tracing chain。單筆 runtime join proof: Jeter frontend → backend trace runtime verification。

Self-check

Q1. 為什麼 Browser 裡已經存在 span，backend 還需要 traceparent？
Q2. traceparent 裡的 parent-id 最精確代表什麼？
Q3. API 回 200 OK，但 Browser business request 沒有 traceparent，最合理的 tracing 結論是？
Q4. Browser request 有正確 traceparent，backend 也延續同一 trace，但 Tempo 缺 frontend span。下一個最該查哪條 path？

Recap

  • Browser 與 backend 是不同 runtime：Browser memory 裡的 span relationship 不會自己跨 HTTP。
  • Propagation 的必要性：要延續 parent/child 關係，必須把最小 trace context 序列化進 request。
  • trace-id 是整條 trace 的 ID；同一條 distributed trace 裡的 spans 共用它。
  • parent-id 是 caller 目前 operation 的 ID；backend 會建立新的 span ID，再把 caller ID 記成 parent。
  • Faro 預設使用 W3C Trace Context propagator，並把 URL propagation 設定交給 Fetch/XHR tracing instrumentation。
  • 你們 package 的 backendUrls 是 backend/business API pattern，不是 Alloy Faro receiver URL。
  • Business propagation 與 telemetry export 是兩條 path：traceparent 傳 context；Faro/OTLP 傳 span telemetry。
  • 同一次 HTTP request 還可能產生 Browser resource-performance event；它不是 span，Current stage evidence 顯示它以 log record 進 Loki，提供 Browser-side HTTP experience。
  • Trace 與 resource performance 是互補 evidence：Trace 用來定位 distributed operation 慢在哪裡；resource event 用來看 Browser 觀察到的 URL/status/duration/TTFB/transfer 等資訊。
  • Cross-origin propagation 還受 CORS 控制；backend 需要允許實際要送的 tracing header。
  • Jeter 已有一筆 runtime join proof：Browser traceparent parent ID = frontend client span ID = backend server span parent ID，且同一 trace ID；Lesson 8 仍負責把這項能力變成 learner 可獨立重跑的驗證流程。
Primary source 與 evidence
本課以 前後端 Trace 串接範例 為 primary source，搭配 trace-context propagation evidence、faro-click-tracking contract、Jeter tracing evidence、Jeter runtime trace join，並用 W3C Trace Context 與 Faro Web SDK v2.9.0 source 補足標準與 implementation semantics。Browser resource-performance 與 tracing 的責任邊界則以 2026-09-21 performance resource runtime evidence 為準。
