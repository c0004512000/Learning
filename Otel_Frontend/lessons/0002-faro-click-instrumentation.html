How ClickInstrumentation Handles Browser Clicks

Milestone 1 · Browser Event → Faro click telemetry

這堂課的目標
學完後，你應該能從 document.addEventListener('click', ...) 一路解釋到 api.pushEvent('click', payload)，並分清楚 Browser Event、DOM attributes、ClickInstrumentation 與 Faro telemetry 的責任邊界。

Lesson 1 已經建立 Browser 原生 click 機制：

User click
  → Browser determines target
  → Browser creates Event
  → Browser dispatches Event
  → Browser reaches listener
  → Browser calls callback(event)

現在問題變成：

ClickInstrumentation 收到這個 Browser Event 之後，怎麼決定「要不要記錄」以及「要記錄什麼」？

1. ClickInstrumentation 的第一個工作：先掛一條 listener

核心初始化可以先看成：

initialize()
  ↓
document.addEventListener('click', this.handleClick)

這代表 ClickInstrumentation 沒有自己偵測滑鼠或觸控輸入。它只是使用 Browser 已有的 Event system，在 document 上登記一個 click callback。

ClickInstrumentation.initialize()
        │ registers
        ▼
document click listener
        │
        │ later, Browser dispatches click
        ▼
this.handleClick(event)

沒有傳 { capture: true }，所以這條 listener 是 non-capture listener。一般 descendant click 若允許 bubbling，會在 Bubble phase 往上抵達 document。

2. 全域 listener 只解決「在哪裡接 Event」

把 listener 掛在 document 有一個重要效果：

不用替每一顆 button、link 或其他 element 各自註冊一條 JavaScript click listener。

但這不代表每一次 click 都會被送成 telemetry。

Browser click reaches document
        │
        ▼
handleClick(event)
        │
        ▼
extract configured data
        │
        ├── 找到可用資料 → 繼續
        └── 完全沒有資料 → 不送

因此要把兩件事分開：

問題由什麼決定
ClickInstrumentation 能不能收到這次 click？Browser Event dispatch 是否抵達 document listener。
這次 click 要不要變成 Faro telemetry？ClickInstrumentation 是否能抽出有效 payload，以及後續 gate / throttle。

3. Telemetry 需要「業務語意」，不能只知道有 click

Browser Event 本身已經知道：

event.type = "click"
event.target = 某顆 DOM element

但對監控來說，只知道「有人點了」通常不夠。你往往還需要知道：

點的是哪個 logical action？
在哪個 page？
在哪個 panel / section？

這些不是 Browser 自動理解的業務語意。宿主應用需要把它們放在 DOM 上，ClickInstrumentation 才能讀。

4. 宿主應用用 data-* 把語意放進 DOM

例如：

<button
  id="daily-schedule-button"
  data-link-name="daily-schedule"
>
  每日生產排程
</button>

Browser 解析後，這些 attributes 都屬於同一顆 button DOM element：

HTMLButtonElement
├── id = "daily-schedule-button"
└── data-link-name = "daily-schedule"

data-* 是 HTML custom data attribute；不是 Faro object，也不是另外一顆 DOM object。

一般 JavaScript 本來就可以讀它：

button.getAttribute('data-link-name')
// "daily-schedule"

button.dataset.linkName
// "daily-schedule"

5. trackAttributes 定義「要抽哪些欄位」

假設初始化設定：

trackAttributes: [
  'data-link-name',
  'data-page',
  'data-panel-topic',
]

這不是三條 listeners。listener 仍然只有一條：

document click listener
        │
        ▼
handleClick(event)
        │
        ▼
for each trackAttribute
        │
        └── 去 DOM 找對應 value

所以 trackAttributes 最適合先理解成：

這個 click telemetry payload 要從 DOM 抽取哪些 attributes 的 schema。

目前 package contract 要求名稱必須是 data-*。這是套件自己的規則，不是 Browser / DOM 的限制。

6. 為什麼不能只讀 event.target？

因為使用者點到的最內層 element，不一定就是放 telemetry attribute 的 element。

例如：

<section data-page="production">
  <button data-action="save">
    <span>儲存</span>
  </button>
</section>

如果使用者剛好點到文字 span：

event.target = span

但 telemetry 可能需要：

data-action = save

data-page = production

它們分別在不同 ancestors 上。

7. closest()：從 target 沿 parent chain 往上找

對每一個設定的 attribute，ClickInstrumentation 可以從 target 開始，用 closest() 往 parent chain 找第一個有該 attribute 的 element。

target = span

find data-action:
span      ✗
  ↑ parent
button    ✓ data-action="save"

find data-page:
span      ✗
  ↑ parent
button    ✗
  ↑ parent
section   ✓ data-page="production"
closest() 的「closest」是 DOM ancestry 上最近的 matching element，不是畫面座標距離。它不往 child 或 sibling 找。

而且每個 attribute 是獨立查一次，因此 payload 可以由不同 ancestors 的值組成。

8. Attribute name 如何變成 payload key？

套件收集到 DOM attribute 後，會把它整理成送給 Faro 的 payload。

概念上：

data-page="production"
        ↓ extract
page: "production"

data-action="save"
        ↓ extract
action: "save"

最後得到類似：

{
  page: "production",
  action: "save"
}

這一步非常重要：Browser Event 本身不是 telemetry payload。ClickInstrumentation 是在這裡把 DOM context 轉成 telemetry data。

9. 空 payload 是第一道 gate

如果所有設定的 attributes 都找不到：

handleClick(event)
  ↓
extract data-page      → not found
extract data-action    → not found
extract data-link-name → not found
  ↓
payload = {}
  ↓
return
  ↓
不 pushEvent()

因此：

document listener 可以收到 click，但 ClickInstrumentation 仍然可以決定「這次沒有足夠語意，不形成 telemetry」。

10. 同 target 的短時間重複 click 會被 throttle

現行行為還有一層重複事件保護：同一個 target 在很短時間內再次觸發時，約 300ms 內的重複 click 會被忽略。

click target A at t=0ms
        ↓ allowed

click target A at t=120ms
        ↓ throttled

click target A after window
        ↓ allowed

這不是 Browser Event system 的規則，而是 ClickInstrumentation 自己加上的 telemetry policy。

11. 最後才建立 Faro click telemetry

當 payload 有資料，而且沒有被 throttle 擋掉，ClickInstrumentation 才會呼叫：

api.pushEvent('click', payload)

這裡就是 Browser runtime 世界與 Faro telemetry 世界的明確交界。

Browser click Event object
        │
        │ handleClick reads
        ▼
DOM attributes
        │
        │ extraction / shaping
        ▼
payload
        │
        │ api.pushEvent('click', payload)
        ▼
Faro telemetry event
階段主要責任
Browser接收輸入、決定 target、建立並 dispatch Event。
宿主應用在 DOM 上提供可追蹤的業務語意，例如 data-page、data-action。
ClickInstrumentation接 Browser Event、抽 DOM context、套用 gate / throttle、形成 payload。
Faro API接收 pushEvent()，把 payload 送進後續 Faro telemetry 流程。

12. 把整條資料流串起來

User click
    │
    ▼
Browser creates + dispatches click Event
    │
    ▼
document listener
    │
    ▼
ClickInstrumentation.handleClick(event)
    │
    ├── read event.target
    │
    ├── for each trackAttribute
    │      └── closest(...) up ancestor chain
    │
    ├── build payload
    │
    ├── empty payload? → stop
    │
    ├── same-target short repeat? → stop
    │
    ▼
api.pushEvent('click', payload)
    │
    ▼
Faro click telemetry

Self-check

1. trackAttributes 是 listener 清單嗎？

不是。document 上仍是一條 click listener；trackAttributes 定義收到 click 後要從 DOM 抽哪些 attributes。

2. 為什麼需要 closest()？

因為 event.target 可能是最內層 child，而 telemetry attributes 可能放在 target 自己或任一 ancestor 上。

3. document listener 收到 click，就一定會 pushEvent() 嗎？

不一定。抽不到任何 configured attributes 時 payload 為空，會直接停止；短時間同 target 重複 click 也可能被 throttle。

4. Browser Event 和 Faro event 是同一個 object 嗎？

不是。Browser Event 是 runtime input event；ClickInstrumentation 從它和 DOM context 抽資料後，才透過 api.pushEvent() 建立 Faro telemetry。

Recap

  • ClickInstrumentation 不製造 click；它在 document 上註冊 listener 等 Browser dispatch。
  • 全域 listener 解決「在哪裡接 Event」，不等於所有 click 都要送 telemetry。
  • 宿主應用透過 data-* 把業務語意放在 DOM 上。
  • trackAttributes 是 payload extraction schema，不是 listener 清單。
  • 每個 attribute 都可從 event.target 用 closest() 獨立往 ancestor 找。
  • 空 payload 與短時間同 target 重複 click 都可能讓流程停止。
  • api.pushEvent('click', payload) 是 Browser Event / DOM context 轉成 Faro telemetry 的邊界。
如果你能不用看上面的流程圖，自己從 document.addEventListener() 重建到 api.pushEvent()，Lesson 2 的主模型就算建立起來了。
