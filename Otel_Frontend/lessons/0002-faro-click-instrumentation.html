How ClickInstrumentation Handles Browser Clicks

Milestone 1 · 從 Browser Event 到有應用語意的 click telemetry

本課目標
給你一個被點擊的 DOM element，能沿著 listener、attribute extraction 與 payload，說明這次 click 是否會形成 Faro event。

先沿用 Lesson 1：Browser 決定點擊的 target，再依事件路徑呼叫 listener。這堂課只追 listener 收到事件之後，套件如何讀取應用標記。

本課的 Foreman 設定與數量以 2026-09-17 source investigation、同日 template inventory及 套件實作證據為準；不是所有 Faro 應用的固定設定。

1. Listener 所在位置，不等於點擊起點

document.addEventListener('click', this.handleClick)

currentTarget = document
  → 這次 callback 所屬 listener 的位置

target = 使用者原先點到的 element
  → 例如按鈕裡的 span

Listener 掛在 document，不代表要從 document 讀業務資料。套件要知道「這次點擊對應哪個功能」，所以從 event.target 開始查找。

2. 從內層文字，找回被標記的入口

<p-button data-link-name="DailySchedule">
  <button>
    <span>每日生產排程</span>
  </button>
</p-button>

點到 span 時，標記卻在外層。closest() 先檢查自己，再沿 parent 往上找第一個符合條件的 element：

span（target，沒有標記）
  ↑ 查 parent
button（沒有標記）
  ↑ 查 parent
p-button（有 data-link-name）
  → 找到，讀取 "DailySchedule"
target.closest('[data-link-name]')
      ?.getAttribute('data-link-name')

整句是 JavaScript，但兩個字串的用途不同：closest() 接受 CSS selector，[data-link-name] 表示「具有這個 attribute」；getAttribute() 接受 attribute 名稱，因此不加中括號。?. 表示前一步沒找到 element 時，不再呼叫後面的讀取。

這是在找被標記的 element，不是在尋找 listener；listener 早已註冊在 document。

3. 同一個值，經過三個不同層次

Foreman 在導入 Faro 前就有 subsystem 功能識別值，例如 DailySchedule。原本的應用也會把它交給自己的 insertForemanWebLog(topic, system.subsystem)；這是應用函式，不是 Browser API。

2026-08-20 的整合 commit 才把該值寫入 Main template 的 tracking attribute：

[attr.data-link-name]="item.subsystem"
Application state
item.subsystem = "DailySchedule"
  │ Angular binding 寫入
  ▼
DOM attribute
data-link-name="DailySchedule"
  │ ClickInstrumentation 讀取並改寫 key
  ▼
Telemetry payload
{ link_name: "DailySchedule" }

值可以相同，但位置與責任不同：宿主應用提供語意，Angular 把值寫到 DOM，套件從 DOM 擷取。套件不是直接讀 Angular 的 item，也不是從畫面文字猜功能名稱。

HTML 提供標準的 data-* 自訂屬性機制；data-link-name 這個具體名稱則是這個整合選用的 contract，不是 HTML、Faro 或 OpenTelemetry 通用必填欄位。

4. 設定決定讀哪些欄位，標記決定涵蓋哪些入口

trackAttributes: ['data-link-name']

trackAttributes 是要擷取的欄位清單，不是 listener 清單。若設定多個 attribute，套件會從同一個 target 分別執行各自的 closest() 查找；不同欄位可以來自不同 ancestor。

在已查核的 Foreman template inventory 中，48 個 p-button declaration 只有 6 個自身帶有 data-link-name：一個 Main subsystem tile template，以及五個 Toolbar 功能。Main template 會經迴圈產生多個實際入口，所以「6 個 declaration」不等於「畫面只有 6 顆按鈕」。

UserGuide.UserGuide
ReferenceDocument.SDS
ReferenceDocument.AI
ReferenceDocument.ForemanManual
Contact.ContactAdministrator

同份 inventory 的兩個原生 <a> declaration 沒有這個標記。因此這裡的 link 不是「所有超連結」：目前是選擇性追蹤功能入口，不是完整 clickstream。未標記 element 的 click 仍可能因 ancestor 有標記而被擷取；應沿實際 DOM 路徑判斷。

5. 先形成 payload，再判斷是否送出

data-link-name
  │ 移除 data- 前綴
  ▼
link-name
  │ 將 - 改為 _
  ▼
link_name

命中 data-link-name="DailySchedule" 後，核心 click payload 是 { link_name: "DailySchedule" }。DOM 上其他未設定的欄位不會因為存在就自動全部收集。

Browser Event 到達 document listener
  │ 呼叫 handler
  ▼
從 event.target 依 trackAttributes 查找
  ├─ 沒有讀到資料 → payload 為空 → 不送 event
  └─ 有讀到資料 → 組成 payload
       │ 檢查同 target 的重複 click
       ├─ 約 300 ms 內重複 → throttle
       └─ 通過 → api.pushEvent('click', payload)

如果事件在抵達 document 前被阻止冒泡，這個 listener 也收不到它。反過來，即使 listener 收到了 Browser click，也不代表一定會送出 Faro event。

Browser Event 與 Faro telemetry event 是不同物件。前者供 Browser 分派 callback；後者是套件依設定建立的觀測資料。pushEvent() 也不等於當場完成一個 HTTP POST；傳送機制留到 Lesson 5。

6. Click 語意與背景資料分開理解

DOM data-link-name → click payload.link_name
宿主的 getUser()  → Faro user state
device detector  → Faro device meta

User 與 device 不是這個 handler 額外從 DOM 抽出的 click attributes。先把本課的 extraction 模型穩住；Lesson 4 再說明背景資料何時更新，以及如何與 click signal 組合。

Recap

  • Listener 在 document，extraction 從 event.target 開始；closest 依 CSS selector 找自己或 ancestor。
  • Application subsystem、DOM data-link-name、payload link_name 是不同層次，可承載同一個值。
  • trackAttributes 決定欄位；各欄位獨立查找。實際標記與事件路徑決定 coverage。
  • 空 payload、未到達 listener、同 target 的短時間重複 click，都可能使這類 telemetry 不產生。
  • Browser Event、Faro event 與 HTTP request 不是同一個單位；User/device 另有資料來源。
