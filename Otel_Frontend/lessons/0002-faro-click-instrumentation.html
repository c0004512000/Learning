Faro ClickInstrumentation 如何接手 browser click

Milestone 1 · Browser Event 到 Faro telemetry 的第一個交界

這堂課的目標
學完後，你應該能從 document.addEventListener('click', ...) 一路解釋到 api.pushEvent('click', payload)，並清楚分辨：Browser、DOM、data-*、host application 與 ClickInstrumentation 各自負責什麼。

Lesson 1 最後停在這裡：

使用者 click
  → browser 決定 target
  → browser 建立 click Event
  → browser 分派 Event
  → browser 找到 listener registration
  → browser 呼叫 callback(event)
ClickInstrumentation 不會製造 click。 click 已經由 Browser 建立並開始分派；ClickInstrumentation 只是事先登記一個 listener，等 Browser 把既有的 click Event 交給它。

1. ClickInstrumentation 到底是什麼？

ClickInstrumentation 是這個共用套件裡自訂的 instrumentation。先把 instrumentation 理解成：

一個專門「接到某種 runtime 行為 → 讀資料 → 轉成 Faro telemetry」的元件。
export class ClickInstrumentation extends BaseInstrumentation {
  initialize(): void {
    document.addEventListener('click', this.handleClick);
  }

  destroy(): void {
    document.removeEventListener('click', this.handleClick);
  }
}

翻成 Lesson 1 的語言：

initialize()
  ↓
在 document 這個 EventTarget 上登記：
- event type = click
- callback   = this.handleClick

之後真的有人 click
  ↓
Browser 分派 click Event
  ↓
Event path 走到 document
  ↓
Browser 呼叫 this.handleClick(event)
「全域監聽 click」不等於「所有 click 都一定會變成 telemetry」。
listener 確實掛在 document，所以它有機會看到大量 bubbling clicks；但收到 click 之後，仍要看能不能從 DOM 找到設定中的 trackAttributes。最後 payload 為空就不會送出 Faro click event。

2. 它是在 Capture 還是 Bubble 接手？

現行程式沒有傳 { capture: true }：

document.addEventListener('click', this.handleClick)

所以這是一個 non-capture listener。以 descendant element 被點擊為例，click 正常會在 Target phase 後往 ancestor bubble，直到 document：

Target
button
  │
  │ Bubble
  ▼
main
  ▼
body
  ▼
html
  ▼
document
  │
  └── Browser 呼叫 ClickInstrumentation.handleClick(event)
如果內層程式在 Event 抵達 document 前用 stopPropagation() 截斷 propagation，這個 listener 就可能看不到那次 click。

3. trackAttributes 不是 listener 清單

假設初始化時設定：

trackAttributes: [
  'data-link-name',
  'data-page',
  'data-panel-topic',
]

這不是建立三條 click listeners。真正的模型是：

只有一條 document click listener
                │
                │ Browser 把 click Event 傳進 handleClick
                ▼
       ClickInstrumentation
                │
                └── 再按照 trackAttributes
                    去 DOM 找這次要抽哪些資料

trackAttributes 比較像「click payload 的資料擷取 schema」。

4. data-* 到底是 HTML、DOM，還是 Faro 的東西？

這裡先把一個很重要的 prerequisite 補齊。看這段 HTML：

<button
  id="schedule"
  data-link-name="daily-schedule"
>
  每日生產排程
</button>

Browser parse 之後，不是產生三顆 object。概念上是一顆 button DOM element object，上面帶著 attributes：

HTMLButtonElement
│
├── id = "schedule"
└── data-link-name = "daily-schedule"

所以：

event.target
    ↓
某一顆 DOM element object
    │
    ├── id
    ├── class
    ├── href（某些 element 才有）
    └── data-* attributes
data-* 不是 Faro object。
它首先是 HTML 的 custom data attribute；Browser render 後，它存在於對應的 DOM element 上。Faro 只是後來透過 DOM API 去讀它。

JavaScript 自己也可以讀：

const button = document.querySelector('button');

button.getAttribute('data-link-name');
// "daily-schedule"

button.dataset.linkName;
// "daily-schedule"

你剛才的 retrieval 題答案 B 是正確的：一顆 button DOM object，上面有 id 與 data-link-name attributes。

5. 現行套件的規則：Faro 不會替你建立 data-*

這裡不是「建議」或「通常」。以目前 faro-click-tracking 的 package contract 而言：

trackAttributes 中的名稱
        │
        ├── data-*   → 允許
        │
        └── 非 data-* → initFaro() validation error

目前程式會檢查：

if (!name.startsWith('data-')) {
  throw new Error(...);
}

所以以下設定不被目前套件接受：

trackAttributes: ['id']     // 不允許
trackAttributes: ['href']   // 不允許
trackAttributes: ['class']  // 不允許
trackAttributes: ['key']    // 不允許

如果你要讓 ClickInstrumentation 收集某個 telemetry semantic，例如 link_name，那個值必須先存在於 DOM 的某個設定過的 data-* attribute 上。套件不會自動替 host application 加 attribute。

Host application 寫：
<button data-link-name="daily-schedule">...</button>

           ↓ Browser render

DOM element 上真的出現：
data-link-name="daily-schedule"

           ↓ ClickInstrumentation

才能從 DOM 讀到
這是你們目前這個 package 的 contract，不是 HTML / DOM 的限制。Browser 當然可以讀 id、href、class；只是這套 ClickInstrumentation 刻意不讓它們直接進 trackAttributes。

6. 那是不是每一顆 button 都要加 data-*？

不是。要先問的是：「你想不想讓這個 interaction 產生 click telemetry？以及你需不需要知道是哪一個 action？」

情況 A：這顆 button 根本不需要追蹤

<button>展開說明</button>

如果從這顆 button 到它的 ancestors 都找不到任何設定在 trackAttributes 裡的 data-*，最後 payload 是空的，這次 click 就不送 Faro event。

click
  ↓
document listener 仍然可能收到
  ↓
找 trackAttributes
  ↓
全部找不到
  ↓
payload = {}
  ↓
return，不 pushEvent()

先把 closest() 講清楚：它不是「找畫面上最近的東西」

closest(selector) 的意思是：從這顆 DOM element 自己開始，沿著 parent chain 一層一層往上，找到第一個符合 selector 的 element。

<section data-page="production">
  <button data-action="save">
    <span>儲存</span>   ← event.target
  </button>
</section>

如果 target 是 span：

target.closest('[data-action]')

span      不符合
  ↑ parent
button    符合 data-action
  → 停止，回傳 button

另一個 attribute 會重新獨立查一次：

target.closest('[data-page]')

span      不符合
  ↑
button    不符合
  ↑
section   符合 data-page
  → 停止，回傳 section
ancestor 就是 parent、parent 的 parent、再更上層的 parent。
closest() 不會往 child 找，也不會跑去看 sibling。這裡的「closest」是 DOM parent chain 上最近的 matching element，不是螢幕座標距離。

情況 B：共同 context 不需要每顆 button 重複寫

因為實作使用 closest() 沿 parent chain 往上找，所以共同資訊可以放在上層：

<section data-page="production">
  <button data-action="save">儲存</button>
  <button data-action="cancel">取消</button>
</section>

搭配：

trackAttributes: [
  'data-page',
  'data-action',
]

點「儲存」可能得到：

{
  page: "production",
  action: "save"
}

點「取消」可能得到：

{
  page: "production",
  action: "cancel"
}

所以 data-page 不必複製到每顆 button；但如果你要區分每一個 logical action，就必須在 target → ancestor 路徑上存在能區分它們的 semantic，例如各自不同的 data-action。

情況 C：只在 ancestor 放共同欄位，會發生什麼？

<section data-page="production">
  <button>儲存</button>
  <button>取消</button>
</section>

如果只設定：

trackAttributes: ['data-page']

兩顆 button 的 click 都可能送：

{ page: "production" }

你知道「production page 有 click」，但不知道是「儲存」還是「取消」。因此：

全域 listener 解決的是「不用替每顆 button 各掛一個 JS click listener」；它沒有解決「每個 action 的業務語意從哪裡來」。
導入工作量的正確理解：
不是「所有 DOM node 都加 attribute」。而是先決定哪些 business interactions 要觀測；共用 context 放 ancestor，需要區分的 action 才提供 action-specific data-*。如果需求真的是「每顆按鈕都要可區分」，那每個 logical action 確實需要有可區分的 semantic 資料。
目前不能把 shared Button / Link 當成 Foreman / Jeter 的已知事實。
「若 application 有共用 Button / Link component，可以在 component 層集中 render telemetry data-*」仍是 integration architecture pattern。針對 Foreman HEAD 的 bounded scan 已保存於 Foreman integration evidence：未找到 app-level generic shared Button / Link，且 PrimeNG p-button 的 host attribute 可由 inner button 的 ancestor path 找到；Jeter 或未來 wrapper、portal 仍須各自做 targeted verification。

7. ClickInstrumentation 怎麼從 target 找 attribute？

現行實作不是只看 event.target 自己。它對每個 trackAttributes 名稱，各自從 target 使用 closest() 往 ancestor 找。

<section data-page="production">
  <button data-action="save">
    <span>儲存</span>
  </button>
</section>

假設真正點到的是 <span>：

event.target = span

找 data-action：
span
  ↑
button[data-action="save"]
  → save

找 data-page：
span
  ↑
button
  ↑
section[data-page="production"]
  → production

所以不同欄位可以來自不同 ancestor。

8. Attribute 名稱怎麼變成 payload key？

現行實作會經過 toPayloadKey()：

data-link-name    → link_name
data-page         → page
data-panel-topic  → panel_topic

也就是去掉開頭的 data-，其餘 - 改成 _。歷史文件記錄這個 normalization 與 downstream Loki 欄位名稱含連字號不好查詢有關。

9. 收到 click 不代表一定會送 telemetry

handleClick(event)
  │
  ├─ 1. event.target 是 Element 嗎？
  │      否 → return
  │
  ├─ 2. 對每個 trackAttributes 用 closest() 找值
  │
  ├─ 3. payload 有任何欄位嗎？
  │      否 → return
  │
  ├─ 4. 同一個 target 距上次送出 < 300ms 嗎？
  │      是 → return
  │
  └─ 5. api.pushEvent('click', payload)

這讓「global listener」與「實際被記錄的 click」可以清楚分開：

Browser click 很多
      ↓
document listener 有機會看到
      ↓
只有能組出非空 payload 的 click
      ↓
才進 Faro pushEvent()

10. api.pushEvent() 是兩個世界的邊界

Browser 世界
click Event
- target
- propagation
- DOM
        │
        │ ClickInstrumentation 讀取與轉換
        ▼
Faro 世界
pushEvent('click', payload)
- event name
- telemetry payload

Browser click Event 與 Faro click telemetry event 不是同一個 object。ClickInstrumentation 是中間的轉換層。

自我檢查

Q1. <button id="schedule" data-link-name="daily-schedule"> 被 Browser parse 後，哪個模型最正確？
Q2. 是否所有 button 都必須加 data-*？
Q3. section 有 data-page="production"，裡面 Save / Cancel 兩顆 button 都沒有 action-specific attribute；trackAttributes 只有 data-page。結果最可能是？
Q4. trackAttributes: ['href'] 在目前 package contract 下會怎樣？

Recap

  • data-* 是 DOM element 上的 HTML custom data attribute，不是另一顆 DOM object，也不是 Faro object。
  • Faro 不會替 host 自動建立 data-*。
  • 目前 faro-click-tracking 的 trackAttributes 強制只接受 data-* 名稱。
  • document 上只有一條全域 click listener；trackAttributes 是 payload extraction schema。
  • 不是所有 button 都必須加 attribute；沒有 tracked attribute 命中的 click 會因空 payload 被丟掉。
  • closest() 是從 target 自己開始沿 parent chain 往上找第一個符合 selector 的 element，不是找畫面上距離最近的 element。
  • 共同 context 可以放 ancestor，因為實作會用 closest() 往上找。
  • 如果要區分每一個 logical action，就必須提供能區分 action 的 semantic；global listener 無法憑空知道業務語意。
  • 目前 Foreman HEAD 的 bounded scan 未找到 app-level generic shared Button / Link；PrimeNG p-button 會 render inner native button，而 host 上的 data-link-name 仍可由 closest() 沿 ancestor 找到。其他 wrapper、portal 或未標記 control 仍需各自驗證。
  • api.pushEvent('click', payload) 是 Browser Event 世界轉進 Faro telemetry 世界的邊界。
