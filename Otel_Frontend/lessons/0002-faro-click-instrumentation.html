1. listener 在哪裡，和 click 從哪裡開始，是兩件事

ClickInstrumentation 註冊的是：

document.addEventListener('click', this.handleClick)

當 descendant click bubble 到 document，Browser 呼叫 handleClick(event)。這時：

event.currentTarget → document
                      目前正在執行 listener 的 object

event.target        → 使用者最初點到的 element
                      例如 span / button / a

currentTarget 回答「listener 現在在哪裡執行」；target 回答「這次 click 最初命中哪個 element」。

2. 為什麼 extraction 要從 event.target 開始？

因為 currentTarget 在這條 listener 裡只會把你帶回：

currentTarget = document

但 ClickInstrumentation 真正要回答的是：

這次 click 所在的 DOM 位置，自己或 ancestors 上有沒有宿主應用刻意標記的 tracking attribute？

所以搜尋起點必須是 event.target。

讀 event.target 不代表 listener 掛在 target 上。
listener 仍在 document；target 只是 Browser Event 保留的原始命中 element reference。

3. closest()：從實際命中位置找回被標記的 UI 入口

<p-button data-link-name="DailySchedule">
  <button>
    <span>每日生產排程</span>
  </button>
</p-button>

使用者可能實際點到內層 span：

event.target = span

document
  └── ...
      └── p-button[data-link-name="DailySchedule"]
          └── button
              └── span  ← target

ClickInstrumentation 從 span 往 ancestor 找：

span                                      ✗
  ↑ parent
button                                    ✗
  ↑ parent
p-button[data-link-name="DailySchedule"]  ✓

這就是 closest('[data-link-name]') 的用途：找「離 target 最近、具有指定 attribute 的 self / ancestor」。

為什麼有 [ ]？
整句仍是 JavaScript，但 closest() 接受的是 CSS selector 字串。CSS selector 裡 [data-link-name] 表示「具有這個 attribute 的 element」。找到 element 後，getAttribute('data-link-name') 接受的是 attribute name，所以不使用 selector 的中括號。完整對照見 Reference。

4. 最重要的三層：subsystem → data-link-name → link_name

Foreman 的 source history 把這件事分得很清楚。

第一層：Application state。 Faro 導入以前，Foreman 就已經有 subsystem 這種功能識別值，例如 DailySchedule。它不是 HTML attribute，而是 Angular / TypeScript 裡的資料。

item.subsystem
→ "DailySchedule"

原本的 Foreman application logic 也已經會使用這個 identifier：

this.insertForemanWebLog(topic, system.subsystem)

這只能證明 subsystem 在 Faro 以前就有 application semantic；insertForemanWebLog() 是 Foreman 自己的 TypeScript function，不是 Browser / DOM 固有概念。

第二層：DOM attribute。 2026-08-20 Faro integration 時，才在原本的 Main template 上增加：

[attr.data-link-name]="item.subsystem"

Angular runtime 會把 application value 寫到 DOM：

item.subsystem = "DailySchedule"
        │ Angular binding writes value
        ▼
<p-button data-link-name="DailySchedule">

第三層：Telemetry field。 Faro package 不直接讀 item.subsystem；它只從 DOM 讀 configured attribute，最後轉成：

data-link-name="DailySchedule"
        │ ClickInstrumentation extracts
        ▼
{ link_name: "DailySchedule" }
因此不是兩個不同值。
item.subsystem 與 data-link-name 可以承載同一個字串，但存在於不同層；Faro 真正讀的是 DOM attribute。

5. data-link-name 不是業界固定 convention，也不是所有 click 都有

HTML 標準提供 data-* 作為 custom data attribute 的正式機制，但 data-link-name 這個具體名稱不是 HTML、Faro 或 OpenTelemetry 的固定欄位。

Foreman 現在明確設定：

trackAttributes: [
  'data-link-name'
]

目前已驗證的 render 位置是：

  • Main subsystem tile template：[attr.data-link-name]="item.subsystem"。這是一個 template declaration，可透過迴圈 render 多顆 subsystem 入口。
  • Toolbar 五個固定功能：UserGuide.UserGuide、ReferenceDocument.SDS、ReferenceDocument.AI、ReferenceDocument.ForemanManual、Contact.ContactAdministrator。

完整 template inventory 有 48 個 p-button declarations，但只有 6 個 declaration 自己有 data-link-name；兩個 native <a> declaration 也都沒有。

所以這裡的 link 不能理解成「HTML hyperlink」。更接近：

宿主應用刻意挑出、需要穩定 telemetry 名稱的 UI 功能入口。

也因此目前 implementation 比較像 selective feature-entry / navigation tracking，不是完整 clickstream。

6. 現在 payload 會送什麼？

例如 ancestor 上有：

data-link-name="DailySchedule"

ClickInstrumentation 會形成：

{
  link_name: "DailySchedule"
}

key normalization：

data-link-name
  │ remove "data-"
  ▼
link-name
  │ replace "-" with "_"
  ▼
link_name

現行 click payload 只包含命中的 configured trackAttributes；不會自動塞入所有 DOM 資訊。

7. User / device 是另外的 state / metadata 路徑

Click payload
└── link_name       ← DOM data-link-name

User state
└── id / username   ← getUser() / Faro user state

Device meta
└── device.type     ← device detector

因此不要把 user、device 誤認為 ClickInstrumentation 從 DOM 抽出的額外 click attributes。這條邊界會在 Lesson 4 展開。

8. 什麼情況不會送這類 click telemetry？

第一種：target 與 ancestors 都找不到 configured tracking attribute。

closest('[data-link-name]') → not found
payload = {}
→ stop
→ 不呼叫 pushEvent()

因此 document listener 有收到 Browser click，不代表一定會產生 Faro click event。

第二種：同一個 EventTarget 在約 300 ms 內重複 click，後續事件會被 throttle。

另外，如果 Browser Event 在抵達 document 前被其他程式阻止 bubbling，這個 document listener 也收不到它。

9. 目前 Foreman 的完整 click 資料流

User click
    │ Browser determines target
    ▼
Browser Event
    │ target = original clicked element
    ▼
document listener
    │ Browser dispatch reaches document
    ▼
ClickInstrumentation.handleClick(event)
    │
    ├── start from event.target
    │
    ├── configured schema
    │      └── data-link-name only
    │
    ├── closest('[data-link-name]')
    │
    ├── not found → empty payload → stop
    │
    ├── found → getAttribute('data-link-name')
    │              ↓
    │            value originally came from host markup / app state
    │
    ├── normalize key → link_name
    │
    ├── same target within ~300 ms → stop
    │
    ▼
api.pushEvent('click', { link_name: value })
    │
    ▼
Faro click telemetry

Recap

  • currentTarget 是 listener 當下所在 object；這裡是 document。
  • target 保留原始 click element，所以是 closest() 搜尋的起點。
  • closest('[data-link-name]') 是 JavaScript 呼叫 DOM API，但參數使用 CSS attribute selector 語法。
  • Foreman 在 Faro 導入前就有 subsystem 功能識別值；Faro integration 才新增 DOM 的 data-link-name。
  • [attr.data-link-name]="item.subsystem" 是把 application value 投影到 DOM，不是 Faro 同時抓兩個值。
  • data-link-name 不是業界固定 convention；Foreman 目前只選擇性標記 Main subsystem template 與五個 Toolbar 功能。
  • data-link-name="DailySchedule" 會形成 { link_name: "DailySchedule" }。
  • User / device 走其他 state / metadata 路徑；不是 click payload extraction。
  • 找不到 tracked attribute 就不送這類 click telemetry；document listener 收到 click 不等於一定 push event。
