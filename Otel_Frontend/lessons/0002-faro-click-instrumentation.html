Faro ClickInstrumentation 如何接手 browser click

Milestone 1 · Browser Event 到 Faro telemetry 的第一個交界

這堂課的目標
學完後，你應該能從 document.addEventListener('click', ...) 一路解釋到 api.pushEvent('click', payload)，並清楚分辨：哪些事情是 browser 做的、哪些事情是 ClickInstrumentation 做的、哪些資料又必須由 host application 自己提供。

Lesson 1 最後停在這裡：

使用者 click
  → browser 決定 target
  → browser 建立 click Event
  → browser 分派 Event
  → browser 找到 listener registration
  → browser 呼叫 callback(event)

現在終於把 Faro 放回來。最重要的第一句是：

ClickInstrumentation 不會製造 click。 click 已經由 browser 建立並開始分派；ClickInstrumentation 只是事先登記一個 listener，等 browser 把既有的 click Event 交給它。

1. ClickInstrumentation 到底是什麼？

ClickInstrumentation 是這個共用套件裡自訂的 instrumentation。這裡的 instrumentation 可以先理解成：

一個專門「接到某種 runtime 行為 → 讀資料 → 轉成 Faro telemetry」的元件。

它繼承 Faro SDK 的 BaseInstrumentation。你現在不用先背 Faro SDK 的 class hierarchy，只要知道 BaseInstrumentation 提供了一個生命週期框架：Faro 啟動 instrumentation 時會呼叫它的 initialize()；移除時則可呼叫 destroy()。

export class ClickInstrumentation extends BaseInstrumentation {
  initialize(): void {
    document.addEventListener('click', this.handleClick);
  }

  destroy(): void {
    document.removeEventListener('click', this.handleClick);
  }
}

把這段翻成 Lesson 1 的語言：

initialize()
  ↓
在 document 這個 EventTarget 上登記：
- event type = click
- callback   = this.handleClick

之後真的有人 click
  ↓
browser 分派 click Event
  ↓
如果 event path 能走到 document 的這個 listener
  ↓
browser 呼叫 this.handleClick(event)
所以「全域監聽 click」不是魔法。
現行實作就是把一個 click listener 登記在 document 上。它利用 browser 原生 Event propagation，讓大量 descendant clicks 最後有機會被同一個 callback 看見。

2. 它是在 Capture 還是 Bubble 接手？

現行程式是：

document.addEventListener('click', this.handleClick)

沒有傳 { capture: true }，所以這是一個 non-capture listener。當你點頁面中的 descendant element 時，正常情況下 click 會在 Target phase 後往 ancestor bubble，最後走到 document，browser 才呼叫 handleClick(event)。

例如你點 button：

Target
button
  │
  │ Bubble
  ▼
main
  ▼
body
  ▼
html
  ▼
document
  │
  └── browser 呼叫 ClickInstrumentation.handleClick(event)
這直接連回 Lesson 1 的 stopPropagation()。
因為 Faro listener 在 document 的 non-capture 路徑上，如果更內層程式在 Event 抵達 document 前就把 propagation 截斷，這個 listener 就可能看不到那次 click。這不是 Faro 「漏抓」，而是 browser Event 根本沒有傳到它登記 listener 的位置。

3. 一個最容易搞混的地方：trackAttributes 不是「要監聽哪些 click」

初始化時會看到：

new ClickInstrumentation({
  trackAttributes: config.trackAttributes,
})

假設 host application 傳：

trackAttributes: [
  'data-link-name',
  'data-page',
  'data-panel-topic',
]

不要把它理解成：

❌ 建立 3 個 listener
❌ 只監聽帶有這 3 個 attribute 的 click event type
❌ browser 會替 Faro 自動把這些 attribute 塞進 Event object

真正的模型是：

只有一條 document click listener
                │
                │ browser 把 click Event 傳進 handleClick
                ▼
       ClickInstrumentation
                │
                └── 再按照 trackAttributes
                    去 DOM 找這次要抽哪些資料
trackAttributes 比較像「資料擷取 schema」。
它告訴套件：收到 click 之後，請嘗試從這次 target 附近的 DOM hierarchy 找出哪些 data-* attribute，並把命中的值放進 telemetry payload。

4. 為什麼 host 要自己加 data-*？

假設頁面原本有：

<a href="/schedule">每日生產排程</a>

人看得懂「每日生產排程」，但監控系統若直接依顯示文字當識別值，會碰到很多不穩定因素：翻譯、文案修改、空白、格式等。這個套件歷史上確實曾經用元素文字產生 link_name，後來才逐步改成 host 明確宣告 telemetry 欄位。

現行設計會希望 host 寫成：

<a
  href="/schedule"
  data-link-name="daily-schedule"
  data-page="production"
>
  每日生產排程
</a>

然後初始化時宣告：

trackAttributes: ['data-link-name', 'data-page']

這樣責任就很清楚：

誰負責什麼
Host application決定「這個 UI 在業務語意上應該叫什麼」，並把穩定值寫成 data-*。
ClickInstrumentation按照 trackAttributes 找值、組 payload、決定這次 click 要不要送。
Browser建立／分派原生 click Event，提供 target 與 DOM API。

5. ClickInstrumentation 怎麼從 target 找 attribute？

這裡不是只看 event.target 自己有沒有 attribute。現行實作對每個 trackAttributes 名稱，各自從 target 開始使用 closest() 往 ancestor 找。

例如 DOM 是：

<section data-page="production">
  <button data-link-name="daily-schedule">
    <span>每日生產排程</span>
  </button>
</section>

你實際點到文字所在的 <span>，所以：

event.target
  ↓
span

但設定是：

trackAttributes = [
  'data-link-name',
  'data-page',
]

套件會分兩次獨立查找：

找 data-link-name：
span
  ↑ closest(...)
button[data-link-name="daily-schedule"]
  → 命中 daily-schedule

找 data-page：
span
  ↑
button
  ↑ closest(...)
section[data-page="production"]
  → 命中 production

所以兩個欄位甚至可以來自不同 ancestor。這也是為什麼不能把 trackAttributes 想成「target 自己有哪些欄位」。

預測一下：
如果 data-page 找得到，但 data-link-name 從 target 一路往上都找不到，這次 click 會怎樣？
看答案

不是 error。找不到的欄位直接省略；data-page 仍可進 payload。只有最後整個 payload 一個欄位都沒有時，這次 click 才不送出。

6. Attribute 名稱不會原封不動變成 payload key

現行實作會先經過 toPayloadKey()：

data-link-name    → link_name
data-page         → page
data-panel-topic  → panel_topic

規則很單純：

  1. 去掉開頭的 data-。
  2. 剩下的 - 改成 _。

例如剛才那次 click 最後可能先形成：

{
  link_name: "daily-schedule",
  page: "production"
}

trackAttributes 也會在初始化前驗證：名稱必須以 data- 開頭，而且轉成 payload key 後不能與清單中的其他項目撞名。

因此 id、href、class 並不會因為 DOM 本來就有，就自動成為 click telemetry。
現行 package contract 要 host 明確新增並宣告 data-*；payload 也沒有「順便把常見 DOM 欄位全部帶上」這種 default 行為。

7. handleClick() 不是收到 Event 就一定送 telemetry

把現行控制流壓縮成最重要的 5 步：

handleClick(event)
  │
  ├─ 1. event.target 是 Element 嗎？
  │      否 → return
  │
  ├─ 2. 對每個 trackAttributes 用 closest() 找值
  │
  ├─ 3. payload 有任何欄位嗎？
  │      否 → return
  │
  ├─ 4. 同一個 target 距上次送出 < 300ms 嗎？
  │      是 → return
  │
  └─ 5. api.pushEvent('click', payload)

第一道：target 必須是 Element

event.target 的型別概念上是 EventTarget，但 closest()、getAttribute() 是 Element 層級的 DOM API。因此實作先確認：

const target = event.target;
if (!(target instanceof Element)) {
  return;
}

這不是在「重新找 target」；browser 早就決定 target 了。這只是確認這個 target 能不能用接下來需要的 Element API。

第二道：payload 必須真的有資料

if (Object.keys(payload).length === 0) {
  return;
}

現行 click payload 完全、僅由 trackAttributes 的命中結果組成。沒有命中任何欄位，就沒有要送的 click event。

第三道：同一個 target 300ms 節流

套件用 WeakMap<EventTarget, number> 記錄 target 上次成功送出的時間。同一個 target 若在 300ms 內再次進來，第二次會被丟掉。

第一次點 button A  → 送出
100ms 後再點 A     → 不送
350ms 後再點 A     → 可以再送

button A 剛送完
立刻點 button B    → B 是不同 target，不會因 A 的時間戳被擋

注意：如果 payload 原本就是空的，它會在節流判斷前 return，因此不會佔用這個 target 的節流時間戳。

8. 最後的 api.pushEvent() 到底代表什麼？

this.api.pushEvent('click', payload)

到這一步，ClickInstrumentation 已經把 browser Event 轉成了 Faro 世界裡的 click telemetry event：

Browser 世界
MouseEvent / click
- target
- propagation
- browser lifecycle
        │
        │ ClickInstrumentation 讀取與轉換
        ▼
Faro 世界
pushEvent('click', payload)
- event name: click
- host-defined payload fields

這兩個「event」不要混在一起：

Browser click EventFaro click telemetry event
由 browser 建立。由 instrumentation 呼叫 Faro API 建立／送入 Faro pipeline。
服務 DOM event dispatch。服務 observability / telemetry。
event.target 是 DOM Event 的資料。payload 是套件抽取後另外組出的資料。
本身不等於可查詢歷史紀錄。之後還要經 Faro transport / collector / backend 才能成為可查資料。
這堂課先停在 pushEvent() 邊界。
「Faro instance 怎麼初始化、this.api 從哪裡來、singleton 如何管理」會在 Lesson 3 正式拆；「送出去後怎麼到 Alloy」則是後面的 browser → collector 主線。現在先不要把三層混在一起。

9. 為什麼現在設計成 host-defined payload？

文件 4 記錄了一段很值得理解的演進。它不是要你背版本，而是在回答：「為什麼現在不直接幫你猜 link_name？」

早期
元素顯示文字
  → 自動變成 link_name

問題
i18n / 文案修改 / 髒字串
  → telemetry identity 不穩定

中期
data-link-name + fallback + mode + 額外 trackAttributes
  → 機制愈來愈重疊

現行
host 明確新增 data-* 並宣告 trackAttributes
  → ClickInstrumentation 只負責通用抽取與送出

這個設計背後的責任原則是：

共用套件知道「怎麼收集」，但 host application 才真正知道「這個 UI 在業務上代表什麼」。

同樣的原因，device.type 也不應硬塞進 click 的 trackAttributes：device type 不是某個 DOM element 的 attribute，而且它應該能跟著各種 signal，而不是只有 click。現行設計把它放在 Faro meta；詳細 user/device/environment context 留到 Lesson 4。

10. 把整條因果鏈一次講完

host 啟動 Faro
  → ClickInstrumentation.initialize()
  → document 記住 click listener registration

之後使用者 click
  → browser 決定 target
  → browser 建立並分派 click Event
  → Event bubble 到 document
  → browser 呼叫 handleClick(event)
  → 確認 target 是 Element
  → 依 trackAttributes，各自從 target 用 closest() 往上找
  → 命中的 data-* 轉成 payload key
  → payload 空：不送
  → 同 target 300ms 節流：命中則不送
  → api.pushEvent('click', payload)
  → 進入 Faro telemetry 世界

自我檢查

Q1. trackAttributes: ['data-link-name', 'data-page'] 最精確代表什麼？
Q2. 使用者點到 <span>，data-link-name 在它外層的 <button>。現行實作可能找到這個值嗎？
Q3. 這次 click 的所有 trackAttributes 都找不到，現行 ClickInstrumentation 會怎樣？
Q4. 為什麼內層程式的 stopPropagation() 可能讓現行 ClickInstrumentation 看不到 click？
Q5. 哪一句最能描述 browser Event 與 Faro telemetry event 的關係？

Recap

  • ClickInstrumentation 不製造 click；browser 先建立並分派原生 click Event。
  • 現行實作在 document 登記一條 non-capture click listener，callback 是 handleClick。
  • trackAttributes 是資料擷取設定，不是 event listener 清單。
  • 每個 tracked data-* 都會從 event.target 開始用 closest() 獨立往 ancestor 查找。
  • 找到的 attribute 名稱會轉成 payload key，例如 data-panel-topic → panel_topic。
  • 現行 click payload 沒有內建 default 欄位；payload 完全由 trackAttributes 命中結果組成。
  • payload 空就不送；同一個 target 300ms 內只成功送一次。
  • api.pushEvent('click', payload) 是 browser Event 世界轉進 Faro telemetry 世界的關鍵邊界。
  • Host application 決定 UI 的業務語意；共用 instrumentation 負責通用收集機制。
