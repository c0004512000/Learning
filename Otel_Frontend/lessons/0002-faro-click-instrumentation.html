How ClickInstrumentation Handles Browser Clicks

Milestone 1 · Browser Event 到 Faro telemetry 的第一個交界

這堂課的目標
學完後，你應該能從 document.addEventListener('click', ...) 一路解釋到 api.pushEvent('click', payload)，並分清楚：瀏覽器、DOM、data-*、宿主應用與 ClickInstrumentation 各自負責什麼。
這堂課的名詞固定：
「宿主應用」指實際導入這個 Faro click tracking 套件的前端應用，例如領班助手。後面不再交替使用 host、host application、Foreman Assistant 等不同稱呼來表示同一個角色。

Lesson 1 最後停在這裡：

使用者 click
  → 瀏覽器決定 target
  → 瀏覽器建立 click Event
  → 瀏覽器分派 Event
  → 找到 listener registration
  → 瀏覽器呼叫 callback(event)
ClickInstrumentation 不會製造 click。 click 已由瀏覽器建立並開始分派；ClickInstrumentation 只是事先登記一個 listener，等瀏覽器把既有的 click Event 交給它。

1. ClickInstrumentation 到底是什麼？

ClickInstrumentation 是共用套件裡自訂的 instrumentation。這裡先把 instrumentation 理解成：

一個專門「接到某種 runtime 行為 → 讀資料 → 轉成 Faro telemetry」的元件。
export class ClickInstrumentation extends BaseInstrumentation {
  initialize(): void {
    document.addEventListener('click', this.handleClick);
  }

  destroy(): void {
    document.removeEventListener('click', this.handleClick);
  }
}

翻成 Lesson 1 的語言：

initialize()
  ↓
在 document 這個 EventTarget 上登記：
- event type = click
- callback   = this.handleClick

之後真的有人 click
  ↓
瀏覽器分派 click Event
  ↓
Event path 走到 document
  ↓
瀏覽器呼叫 this.handleClick(event)
「全域監聽 click」不等於「所有 click 都一定會變成 telemetry」。
listener 掛在 document，因此有機會收到大量 bubbling clicks；但收到 click 之後，還要看能不能依 trackAttributes 從 DOM 找到資料。最後 payload 為空就不會送出 Faro click event。

2. 它是在 Capture 還是 Bubble 接手？

現行程式沒有傳 { capture: true }：

document.addEventListener('click', this.handleClick)

所以這是一個 non-capture listener。以 descendant element 被點擊為例，target 在 dispatch 前已確定；Target phase 後，允許 bubbling 的 click 會沿 ancestor 往外走：

Target phase
button

Bubble phase
main
  ↓
body
  ↓
html
  ↓
document
  ↓
瀏覽器呼叫 ClickInstrumentation.handleClick(event)
這張圖不是在說 button listener 又跑一次。
button 已在 Target phase 處理；Bubble 接著處理的是它的 ancestors。若內層程式在 Event 抵達 document 前呼叫 stopPropagation()，document 上這條 listener 就可能看不到那次 click。

3. trackAttributes 不是 listener 清單

假設初始化時設定：

trackAttributes: [
  'data-link-name',
  'data-page',
  'data-panel-topic',
]

這不是建立三條 click listeners。真正的模型是：

只有一條 document click listener
                │
                │ 瀏覽器把 click Event 傳進 handleClick
                ▼
       ClickInstrumentation
                │
                └── 再按照 trackAttributes
                    去 DOM 找這次要抽哪些資料

trackAttributes 比較像「click payload 的資料擷取 schema」。

4. data-* 到底是 HTML、DOM，還是 Faro 的東西？

先看一段宿主應用的 HTML：

<button
  id="daily-schedule-button"
  data-link-name="daily-schedule"
>
  每日生產排程
</button>

daily-schedule-button 只是這個範例的 id 名稱；沒有任何特殊 browser 意義。

瀏覽器解析後，概念上是一顆 button DOM element object，上面帶著 attributes：

HTMLButtonElement
│
├── id = "daily-schedule-button"
└── data-link-name = "daily-schedule"

注意：不是 button、id、data-link-name 三顆平行 DOM objects。id 與 data-link-name 都是同一顆 button element 的資料。

event.target
    ↓
某一顆 DOM element object
    │
    ├── id
    ├── class
    ├── href（某些 element 才有）
    └── data-* attributes
data-* 不是 Faro object。
它首先是 HTML custom data attribute；瀏覽器建立對應 DOM element 後，可以透過 DOM API 從那顆 element 讀到它。Faro 只是後來去讀。

JavaScript 自己也可以讀：

const button = document.querySelector('#daily-schedule-button')

button.getAttribute('data-link-name')
// "daily-schedule"

button.dataset.linkName
// "daily-schedule"

5. 現行套件規則：Faro 不會替宿主應用建立 data-*

以目前 faro-click-tracking 的 package contract 而言，trackAttributes 名稱必須以 data- 開頭：

trackAttributes 中的名稱
        │
        ├── data-*     → 允許
        │
        └── 非 data-* → initFaro() validation error
if (!name.startsWith('data-')) {
  throw new Error(...)
}

所以以下設定不被目前套件接受：

trackAttributes: ['id']
trackAttributes: ['href']
trackAttributes: ['class']
trackAttributes: ['key']

如果要讓 ClickInstrumentation 收集某個 telemetry semantic，例如 link_name，那個值必須先存在於 target → ancestor 路徑上的某個設定過的 data-* attribute。套件不會自動替宿主應用加 attribute。

宿主應用宣告：
<button data-link-name="daily-schedule">...</button>

           ↓ 瀏覽器解析並建立 DOM

DOM element 上可讀到：
data-link-name="daily-schedule"

           ↓ ClickInstrumentation

才能從 DOM 讀到
這是目前這個 package 的 contract，不是 HTML / DOM 的限制。瀏覽器本來就能讓 JavaScript 讀 id、href、class；只是這套 ClickInstrumentation 刻意不讓它們直接進 trackAttributes。

6. 那是不是每一顆 button 都要加 data-*？

不是。要問的是：「這個 interaction 要不要產生 click telemetry？如果要，是否需要知道是哪個 logical action？」

情況 A：這顆 button 不需要追蹤

<button>展開說明</button>

如果從這顆 button 到 ancestors 都找不到任何設定在 trackAttributes 裡的 data-*，最後 payload 是空的，這次 click 就不送 Faro event。

click
  ↓
document listener 仍可能收到
  ↓
依 trackAttributes 找資料
  ↓
全部找不到
  ↓
payload = {}
  ↓
return，不 pushEvent()

先把 closest() 講清楚

closest(selector) 不是「找畫面上最近的東西」。它是：

從目前這顆 DOM element 自己開始，沿著 parent chain 一層一層往上，找到第一個符合 selector 的 element。
<section data-page="production">
  <button data-action="save">
    <span>儲存</span>   ← event.target
  </button>
</section>

如果 target 是 span：

target.closest('[data-action]')

span      不符合
  ↑ parent
button    符合 data-action
  → 停止，回傳 button

另一個 attribute 會重新獨立查一次：

target.closest('[data-page]')

span      不符合
  ↑ parent
button    不符合
  ↑ parent
section   符合 data-page
  → 停止，回傳 section
ancestor = parent、parent 的 parent、再更上層的 parent。
closest() 不往 child 找，也不找 sibling。這裡的 closest 是 DOM parent chain 上最近的 matching element，不是螢幕座標距離。

情況 B：共同 context 放 ancestor

<section data-page="production">
  <button data-action="save">儲存</button>
  <button data-action="cancel">取消</button>
</section>
trackAttributes: [
  'data-page',
  'data-action',
]

點「儲存」可能得到：

{
  page: "production",
  action: "save"
}

點「取消」可能得到：

{
  page: "production",
  action: "cancel"
}

所以共同的 data-page 不必複製到每顆 button；但如果要區分 logical action，就需要存在能區分它們的 semantic，例如不同的 data-action。

情況 C：只有共同 context，沒有 action identity

<section data-page="production">
  <button>儲存</button>
  <button>取消</button>
</section>
trackAttributes: ['data-page']

兩顆 button 的 click 都可能只送：

{ page: "production" }

你知道 production page 有 click，但不知道是儲存還是取消。

全域 listener 解決的是「不用替每顆 button 各掛一個 JavaScript click listener」；它沒有解決「每個 action 的業務語意從哪裡來」。
不要把 shared Button / Link 當成宿主應用已存在的事實。
「如果宿主應用有共用 Button / Link component，可以集中 render telemetry data-*」只是一種 integration pattern。是否真的有這種 component、是否所有 business buttons 都經過它，必須看實際 source evidence。

7. ClickInstrumentation 怎麼從 target 找 attribute？

現行實作不是只看 event.target 自己。它會對每個 trackAttributes 名稱，各自從 target 使用 closest() 往 ancestor 找。

<section data-page="production">
  <button data-action="save">
    <span>儲存</span>
  </button>
</section>

假設真正點到的是 <span>：

event.target = span

找 data-action：
span
  ↑
button[data-action="save"]
  → save

找 data-page：
span
  ↑
button
  ↑
section[data-page="production"]
  → production

所以不同欄位可以來自不同 ancestor。

8. Attribute 名稱怎麼變成 payload key？

現行實作會經過 toPayloadKey()：

data-link-name    → link_name
data-page         → page
data-panel-topic  → panel_topic

也就是去掉開頭的 data-，其餘 - 改成 _。歷史文件記錄這個 normalization 與 downstream Loki 欄位名稱含連字號不好查詢有關。

9. 收到 click 不代表一定會送 telemetry

handleClick(event)
  │
  ├─ 1. event.target 是 Element 嗎？
  │      否 → return
  │
  ├─ 2. 對每個 trackAttributes 用 closest() 找值
  │
  ├─ 3. payload 有任何欄位嗎？
  │      否 → return
  │
  ├─ 4. 同一個 target 距上次送出 < 300ms 嗎？
  │      是 → return
  │
  └─ 5. api.pushEvent('click', payload)

因此：

Browser click 很多
      ↓
document listener 有機會收到
      ↓
只有能組出非空 payload 的 click
      ↓
再通過 throttle
      ↓
才進 Faro pushEvent()

10. api.pushEvent() 是兩個世界的邊界

Browser 世界
click Event object
- target
- propagation
- DOM
        │
        │ ClickInstrumentation 讀取與轉換
        ▼
Faro 世界
pushEvent('click', payload)
- event name
- telemetry payload

Browser click Event 與 Faro click telemetry event 不是同一個 object。 ClickInstrumentation 是中間的轉換層。

自我檢查

Q1. <button id="daily-schedule-button" data-link-name="daily-schedule"> 被瀏覽器解析後，哪個模型最正確？
Q2. 是否所有 button 都必須加 data-*？
Q3. section 有 data-page="production"，Save / Cancel 兩顆 button 都沒有 action-specific attribute；trackAttributes 只有 data-page。最可能的結果？
Q4. trackAttributes: ['href'] 在目前 package contract 下會怎樣？

Recap

  • ClickInstrumentation 不製造 click；它事先在 document 登記 listener，等瀏覽器分派 Event。
  • trackAttributes 是 payload extraction schema，不是 listener 清單。
  • data-* 是 DOM element 上可讀取的 HTML custom data attribute，不是另一顆 DOM object，也不是 Faro object。
  • Faro 不會替宿主應用自動建立 data-*；現行 package contract 強制 trackAttributes 只接受 data-* 名稱。
  • 不是所有 button 都必須加 attribute；沒有 tracked attribute 命中的 click 會因空 payload 被丟掉。
  • closest() 從 target 自己開始沿 parent chain 往上找第一個 matching element。
  • 共同 context 可以放 ancestor；要區分 logical action，則必須提供能區分 action 的 semantic。
  • shared Button / Link 是否存在是宿主應用 source fact，不能沒有證據就當成現況。
  • api.pushEvent('click', payload) 是 Browser Event 世界轉進 Faro telemetry 世界的重要邊界。
