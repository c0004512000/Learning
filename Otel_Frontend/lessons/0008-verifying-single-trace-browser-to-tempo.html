Verifying a Single Trace from Browser to Tempo

Milestone 4 · 不再只理解 propagation，而是親手證明「這一筆 request」真的接成同一條 distributed trace

這堂課的 tangible win
給你一筆 Browser business request，你要能從 traceparent 取出 trace ID 與 frontend span ID，拿 trace ID 去 Tempo 找到同一條 trace，再確認 backend server span 的 parent 正好就是那個 frontend span ID。

Lesson 7 已經回答「為什麼跨 Browser / backend runtime 需要 traceparent」。Lesson 8 不再重教格式；這次只問一件 SRE 真正會遇到的問題：

你怎麼用 runtime evidence 證明前後端不是「各自都有 trace」，而是真的同一條 trace？

1. 先定義成功：你到底要證明什麼？

先把 Lesson 7 的模型縮成三個符號：

T = 這一整條 distributed trace 的 trace ID
A = Browser / frontend HTTP client span ID
B = Backend HTTP server span ID

如果前後端真的 join 成功，runtime relationship 應該是：

驗證不是「看到某個畫面就算成功」
真正關鍵的是 identity equality：Browser header 裡的 T 要等於 Tempo trace ID；Browser header 裡的 A 要等於 frontend client span ID，也要等於 backend server span 的 parent ID。

2. 四個常見觀察，各自只能證明到哪裡？

你看到的 evidence它能證明它不能單獨證明
API 回 200 OK這筆 business request 功能上成功。前後端 trace relationship 正確。
Request 有 traceparentBrowser 對這筆 request 注入了 caller context。Backend 一定有 extraction，也不能證明 span 已進 Tempo。
Tempo 看得到 frontend spanFrontend span 至少已被儲存並可查詢。Backend 一定接在它下面。
Tempo 畫出 frontend → backend treeUI 顯示兩個 service 的 parent/child hierarchy。若要做嚴格驗收，仍應核對 exact trace/span/parent IDs。

所以 Lesson 8 的 workflow 不是「去 Grafana 看起來像有資料」，而是：

① 固定一筆 Browser request
      ↓ extract T / A
② 用 T 查 exact Tempo trace
      ↓ find frontend span A
③ 找 backend server span B
      ↓ verify B.parent = A
④ 三段 identity 全部對上
      ↓
   才能宣稱這一筆 runtime join verified

3. 實際案例：Jeter stage 的 Slow request

以下不是教材假資料。這是 2026-09-20 在 tw-stage 對 Jeter Faro Trace Demo 保留下來的一筆 runtime evidence。先從同一個操作開始。

Step 1｜在 Network 固定「這一筆」business request

在 Chrome Network 找到 Slow scenario 對應的 request：

這次實際 request 是：

GET https://pek8s-staging.garmin.com/
    jeter-faro-trace-demo-backend/api/scenario/slow

HTTP 200

200 先只記成「business request 成功」。不要把它升級成「tracing 成功」。

Step 2｜讀 Request Headers 的 traceparent

這筆 request 的實際值：

traceparent:
00-6faa6779a2970a3f82ad77e9ab9f4eb7-483e269e249ac6b4-01
T｜trace ID 6faa6779a2970a3f82ad77e9ab9f4eb7
A｜caller / frontend span ID 483e269e249ac6b4

到這裡，能下的結論只有：

Browser propagation evidence 成立
這筆 business request 實際帶出了 trace ID T 與 caller operation ID A。但我們還不知道 backend 有沒有使用它，也還不知道兩邊 span 是否真的進了 Tempo。

01 的 sampled bit 在這筆 context 中是設置的；但它仍不是「一定成功寫入 Tempo」的保證。Sampling decision、telemetry export、Collector / storage、retention 是不同 boundary。

4. Step 3｜拿 Browser 的 T 去 Tempo 查 exact trace

不要先用 service name、時間範圍、關鍵字猜是哪條 trace。你現在已經從 Browser 拿到最強的 correlation key：exact trace ID T。

查到 trace 之後，還不能停。下一個問題是：這個 trace 裡的 frontend span 真的是剛才 header 裡的 A 嗎？Backend 又真的把 A 當 parent 嗎？

5. Step 4｜核對 frontend A 與 backend parent

這筆 Tempo runtime record 的 exact IDs 是：

Frontend HTTP client span
trace ID = 6faa6779a2970a3f82ad77e9ab9f4eb7
span ID = 483e269e249ac6b4
Backend HTTP server span
trace ID = 6faa6779a2970a3f82ad77e9ab9f4eb7
span ID = bcaf1c3a1ff7cb07
parent = 483e269e249ac6b4

現在把 Browser 與 Tempo 疊在一起看：

Browser traceparent
trace ID  = 6faa6779a2970a3f82ad77e9ab9f4eb7 ───────────────┐
parent ID = 483e269e249ac6b4 ───────────────────────────┐ │
                                                       │ │
Tempo                                                  │ │
frontend client span                                   │ │
  trace ID = 6faa6779a2970a3f82ad77e9ab9f4eb7  <──────┘ │
  span ID  = 483e269e249ac6b4                   <────────┘
       │
       │ is parent of
       ▼
backend server span
  trace ID = 6faa6779a2970a3f82ad77e9ab9f4eb7
  span ID  = bcaf1c3a1ff7cb07
  parent   = 483e269e249ac6b4

這才是 decisive equality：

Browser.trace-id     == Tempo.frontend.trace-id == Tempo.backend.trace-id
Browser.parent-id    == Tempo.frontend.span-id
Tempo.backend.parent == Tempo.frontend.span-id
這一筆可以正式下結論
Jeter Slow scenario 的 Browser header → frontend client span → backend server parent relationship 已對上，因此這一筆 request 的 frontend/backend runtime join verified。這個結論只涵蓋這筆被驗證的 request，不自動擴張到所有 endpoint、所有 session 或其他 frontend 專案。

6. SRE Debug：哪一段 equality 先斷，就往哪個 boundary 查

實務上最有用的不是背操作順序，而是知道每個觀察把 fault domain 縮到哪裡。

Observed state目前能判斷下一個 boundary
API 200，但 request 沒 traceparentBusiness 功能正常；Browser propagation 沒有被證明。Frontend tracing、backendUrls matching、Fetch/XHR instrumentation、CORS。
Header 有 T/A，backend trace 卻是另一個 TBrowser injection 成功，但 backend 沒延續同一 trace。Backend context extraction / server instrumentation。
Header 的 T 正確，Tempo 有 backend，但缺 frontend APropagation 可能已成功；frontend span visibility 不完整。Frontend sampling、export、Faro receiver、Collector、Tempo retention/query。
Tempo 有 frontend A，但完全沒有 backend spanFrontend export 成功；backend span visibility 不完整。Backend instrumentation、sampling、OTLP export、Collector / Tempo。
同一 T 裡兩邊都有 span，但 backend parent ≠ A不能宣稱 expected parent/child join 成立。核對實際 request、nested spans、extraction / parent selection。
用 T 在 Tempo 完全查不到只能說「目前沒有 query visibility」。Sampling、export、ingest、retention、query window；不要直接判定 propagation 失敗。
Expected state → observed identity → first broken boundary。

為什麼「Tempo 查不到」不能直接等於 propagation 壞了？

traceparent 是 business request 上的 propagation evidence；Tempo 是 span telemetry 的 storage/query evidence。中間還隔著 sampling、export、receiver / Collector、storage 與 retention。只要其中任何一段讓 span 沒有留下來，Tempo 都可能查不到。

因此 Debug 時：

Header T/A 不存在
  → 先查 propagation

Header T/A 存在，但 Tempo 不完整
  → 先把 propagation 與 telemetry visibility 分開
  → 再查 sampling / export / ingest / retention

這也是為什麼 Browser 的 faro.performance.resource 有時仍有價值：matching trace 因 sampling 或 retention 不可用時，它可能還保留 Browser-side URL、status、duration、TTFB 等線索。但它不是替代 span relationship 的 trace proof。

7. 你自己的驗收 checklist

之後協助其他 frontend 導入時，不需要背 Jeter 的 ID；照這個 checklist 重跑新的 request：

  1. 產生一筆可辨識的 business request，記下 endpoint 與時間。
  2. 在 Browser Network 鎖定同一筆 request，不要拿 /alloy telemetry POST 混在一起。
  3. 抄下 traceparent 的 T / A；沒有 header 就先停在 propagation boundary。
  4. 用 exact T 查 Tempo，避免只靠時間或 service name 猜。
  5. 確認 frontend client span 的 span ID = A。
  6. 確認 backend server span trace ID = T，parent = A。
  7. 記錄 scope：你證明的是哪個 environment、哪個 request、哪個時間點，不把單筆 evidence 擴張成全系統保證。
驗收句型
「在 environment / time / endpoint 的這一筆 request，Browser traceparent 的 trace ID 與 parent ID，分別對上 Tempo 的 shared trace ID 與 frontend client span ID；backend server span 的 parent 也等於該 frontend span ID。因此這一筆 frontend → backend trace join 已驗證。」

Self-check

Q3. Header 的 T/A 已存在，backend 也延續 T，但 Tempo 缺 frontend A。下一個 fault domain 最合理是哪裡？
Q4. 用 exact T 在 Tempo 查不到資料，哪個結論最精確？

Recap

  • Lesson 8 驗證的是單筆 runtime join，不是「設定看起來正確」。
  • Browser traceparent 提供 T / A：T 是 exact trace identity，A 是 caller/frontend operation identity。
  • Tempo 要用 exact T 查，再核對 frontend span ID 是否等於 A。
  • Backend server span 必須保留同一個 T，且 parent = A，這才建立預期 parent/child relationship。
  • HTTP 200、有 header、有單邊 span 都只是部分 evidence，不能單獨升級成 end-to-end join 成功。
  • Tempo 查不到不等於 propagation 失敗；sampling、export、ingest、storage、retention 都會影響 query visibility。
  • Runtime proof 有 scope：一筆 request 的成功不能自動代表所有 endpoint 或所有應用都成功。
