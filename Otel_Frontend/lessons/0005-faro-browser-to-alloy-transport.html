Faro Browser-to-Alloy Transport

Milestone 3 · 從 environment 選出 receiver URL，到 Browser 準備把 telemetry 送進 /alloy

這堂課的目標
看到 Faro 的 network request 時，你要能回答四件事：它為什麼送到這個 URL、Transport 在這裡負責什麼、telemetry 本身的 payload 和背景 meta 有什麼不同，以及 Browser 為什麼可能在真正的 POST 前先處理 CORS。這堂課只走到 Alloy 的接收入口，不展開 Alloy 收到後的 pipeline。

Lesson 4 最後停在這裡：

宿主應用 initFaro(...)
  │
  ├─ getUser()              → Faro user state
  ├─ device detection       → Faro device meta
  └─ environment: tw-stage  → 選擇 Faro receiver URL

其中 environment 已經不是單純的標籤。現行 package 會用它選出 receiver URL：

tw-stage
   │ resolve
   ▼
https://pek8s-staging.garmin.com/alloy

現行對照來自 Browser Faro endpoint and Alloy receiver evidence 與 faro-click-tracking implementation evidence。Lesson 4 已建立 environment → URL 的因果關係；這堂課從「URL 已選出」繼續往下追。

但到這裡還缺了一段：

Faro 已經有 telemetry，也知道接收 URL。那資料到底怎麼離開 Browser？

1. 先把角色分開：Instrumentation 產生資料，Transport 負責送資料

先回到 Lesson 2 的 click：

Browser click
   │
   ▼
ClickInstrumentation
   │ extracts the tracked data
   ▼
api.pushEvent(...)

這條線解決的是：

「要產生什麼 telemetry？」

但 pushEvent() 本身不是我們現在要追的最後網路邊界。Faro 裡還有另一個角色：Transport。

Instrumentation / Faro API
   │ creates telemetry
   ▼
Faro internal data
   │
   ▼
Transport
   │ sends data out
   ▼
remote receiver URL

可以先把 Transport 理解成：

Faro 裡專門負責「把已經產生的 telemetry 送出去」的元件。

Faro Web SDK 的預設 Web transport 使用 Browser 的 fetch() 能力送資料，所以常看到名稱 FetchTransport。

原始教材也把 Transport 定義成負責提交 Faro 已收集資料的元件，並列出 FetchTransport／ConsoleTransport：Grafana Faro & Alloy - 前端可觀測性。上游 Faro source 的 Transport architecture 也明確把 Transport 定義為 data processors 的最後一站：Grafana Faro Web SDK · Transports。

這裡不要把 fetch() 想成 JavaScript 語言本身
fetch() 是 Browser 提供給 JavaScript 的 Web API。這個 runtime 邊界已在 Lesson 0｜Browser Runtime Foundation 建立過；這裡只沿用，不重新展開。

2. 完整第一條線：environment → receiver URL → Transport

把 Lesson 4 和剛才的 Transport 接起來：

宿主應用
  │
  │ initFaro({ environment: "tw-stage" })
  ▼
@sre2/faro-click-tracking
  │
  │ resolve environment
  ▼
https://pek8s-staging.garmin.com/alloy
  │
  │ becomes Faro receiver destination
  ▼
Faro Transport
  │
  │ Browser HTTP request
  ▼
/alloy

這就是為什麼 environment 給錯，不只是「Grafana 上看起來標籤錯了」。更前面的問題是：package 可能直接選錯資料要送去的 receiver。

目前 package 的 verified mapping 包含：

environmentreceiver URL
tw-stagehttps://pek8s-staging.garmin.com/alloy
tw-prodhttps://shixpa-peproxy00.garmin.com/alloy

以上是 2026-09-12 verified implementation/runtime evidence；見 browser-to-alloy evidence。host 傳的是 environment，不是任意 receiver URL。

3. Payload 和 Meta：一個回答「發生什麼」，一個回答「發生時的背景」

Lesson 4 一直強調 user、device、environment 不等於 click 自訂欄位。現在可以看到 Faro 本身也有這個分界。

上游 Faro 的 TransportItem 型別，把一筆要交給 Transport 的資料拆成：

TransportItem
  ├─ type
  ├─ payload
  └─ meta

先不要管實際 TypeScript 型別名稱，只看責任：

部分回答的問題這堂課的例子
payload這筆 telemetry 本身發生了什麼？Click event 的 event data、log 內容、measurement、exception 等。
meta這筆 telemetry 發生時，是在什麼背景？app、user、session、device、browser 等。

所以沿用前面的 click，可以先建立這個概念模型：

telemetry item
  │
  ├─ payload
  │    └─ 「使用者剛剛做了哪個被追蹤的操作」
  │
  └─ meta
       ├─ app / environment
       ├─ user
       ├─ session
       └─ device

這裡最重要的不是背欄位，而是 debug 時不要走錯路：

  • link_name 不對 → 回頭查 ClickInstrumentation / DOM data。
  • user 不對 → 查 Lesson 4 的 getUser() / user sync。
  • device 不對 → 查 device detection。
  • environment 不對 → 查宿主應用傳入值與 package resolver。

上游 Faro current source：packages/core/src/transports/types.ts 的 TransportItem 明確具有 type、payload、meta；packages/core/src/metas/types.ts 的 Meta 包含 app、user、session、page、browser、device 等類別。

4. 真正送 HTTP 時，不一定是一筆 item 就一個 request

如果把前面的模型直接想成：

1 click = 1 HTTP request

會太早下結論。

Faro 的 Transport 可以批次處理資料。上游 current TransportBody 會把不同 signal 類型分組，例如：

HTTP request body
  ├─ meta
  ├─ events[]
  ├─ logs[]
  ├─ exceptions[]
  ├─ measurements[]
  └─ traces   (如果有)

因此 network request 是傳輸單位，telemetry event 是資料單位，兩者不要畫上等號。

這個分界對 DevTools 很重要
之後在 Network 看到一個 /alloy request 時，不要只問「這是不是剛才那一下 click？」；還要打開 request body，確認裡面包含哪些 signal，以及當下附了哪些 meta。

Request body 類型同樣來自上游 current Transport types。這裡只建立資料結構，不宣稱目前公司頁面的某一次 click 已經以特定 batch 形式被 runtime 捕捉。

5. Session ID 為什麼同時可能出現在 body 和 request header？

Session 是用來把同一段 Browser 使用期間的 telemetry 關聯起來的背景資訊之一。

Faro current default Fetch transport 還會在 HTTP request 放：

X-Faro-Session-Id: ...

這不是另一個獨立 session；它是在 HTTP 層把這次 request 對應的 Faro session identity 帶給 receiver。

Faro session
   │
   ├─ meta.session.id        → request body 裡的背景資料
   │
   └─ X-Faro-Session-Id      → HTTP request header

所以看到「同一個資訊在不同層出現」時，不要立刻理解成 duplication bug。先問：

這個值現在是在描述 telemetry body，還是在描述 HTTP transport contract？

上游 Faro current transport docs 與 tests 都驗證 default Fetch transport 使用 X-Faro-Session-Id，並使它對應 payload 的 session identity：Transports。公司 stage/prod receiver 的 2026-09-12 OPTIONS verification 也確認目前 endpoint 允許這個 header；見 browser-to-alloy evidence。

6. Browser 為什麼需要 CORS？先從「頁面和 receiver 是不是同一個 origin」開始

現在 Browser 準備執行：

page JavaScript
   │
   │ fetch(...)
   ▼
https://.../alloy

Browser 不會因為 JavaScript 想送就無條件允許所有跨網站 request。

它先看頁面本身的 origin 和目標 URL 的 origin。

這裡把 origin 只理解成三個部分就夠：

scheme + host + port

https://app.example.com:443
│       │               │
scheme  host            port

只要其中需要比較的部分不同，就可能形成 cross-origin request。

例如：

頁面：    https://app.example.com
receiver: https://collector.example.com/alloy

host 不同
→ cross-origin

CORS (Cross-Origin Resource Sharing) 可以先理解成 Browser 執行的一套規則：目標 server 必須用 response header 表明「哪些 origin / method / request headers 可以跨 origin 使用我」。

想再深入 CORS / Preflight？
Lesson 5 主線只保留理解 Browser → /alloy 所需的最小模型。Request options 如何變成 preflight、Alloy receiver 的 CORS 設定、各個 Access-Control-* response header 怎麼讀，以及 FastAPI CORSMiddleware 的對照，整理在 Reference｜CORS 與 Preflight。

7. Preflight：Browser 可能先問「我可不可以這樣 POST？」

某些 cross-origin request 在真正送出前，Browser 會先送一個 OPTIONS request。這叫 preflight。

第一性原理可以把它想成兩階段：

Browser
  │
  │ 1. OPTIONS：我想用 POST，還想帶這些 headers，可以嗎？
  ▼
receiver / gateway
  │
  │ 2. response：允許哪些 origin / method / headers
  ▼
Browser
  │
  ├─ allowed   → 才繼續真正 request
  └─ not allowed → Browser 在這裡擋下

注意：不是所有 request 都一定會 preflight。是否需要 preflight，是 Browser 依 request 是否跨 origin、method、headers、content type 等條件決定。

Evidence boundary
2026-09-12 的驗證是主動對 stage/prod /alloy 發送 read-only OPTIONS，確認 receiver contract；它證明目前 endpoint 對這組 CORS 問法怎麼回答，不等於已捕捉到某個實際產品頁面的 Browser 自動發出同一個 preflight。

8. 目前 stage / prod 的 CORS evidence 實際證明了什麼？

驗證時詢問的需求是：

method: POST
headers:
  content-type
  x-faro-session-id
  traceparent

stage 與 prod 的 endpoint 都回：

HTTP 204
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers:
  content-type,x-faro-session-id,traceparent

因此目前可以說：

  • 這兩個 /alloy endpoint 對這個 OPTIONS 問法，允許 POST。
  • 它們允許測試中要求的三個 request headers。
  • 它們當下回覆 Access-Control-Allow-Origin: *。

但目前不能因此說：

  • 某一筆真實 Faro telemetry POST 已經成功寫入 Alloy。
  • 某一個實際產品頁面的 Browser 已經自動觸發這個 OPTIONS。
  • POST 之後的 Alloy → Collector → storage 全部成功。

以上界線全部來自 Browser Faro endpoint and Alloy receiver evidence；該次驗證刻意沒有送 telemetry POST。

9. 一個很容易查錯的設定：backendUrls 不是 Faro receiver URL

package 還有一個名稱很像「後端 URL」的設定：

backendUrls

很容易直覺猜成：

「這是不是告訴 Faro 要把 telemetry POST 到哪裡？」

不是。

現行 package evidence 顯示：

environment
  │
  └─ decides → Faro receiver URL → /alloy

backendUrls
  │
  └─ used by → tracing configuration
               └─ 哪些 backend request 可以傳遞 trace header

Tracing 的 header propagation 會在後面的 tracing Lessons 才展開。Lesson 5 只需要記住責任邊界：

backendUrls 不是用來設定 Faro telemetry receiver。

現行 package implementation evidence：faro-click-tracking evidence。其中 backendUrls 僅用於 TracingInstrumentation 的 trace-header propagation；receiver URL 由 environment resolver 決定。

11. Production-style troubleshooting：症狀先對到哪一層

症狀第一個檢查點理由
click event 根本沒產生ClickInstrumentation / DOM data資料還沒到 Transport。
資料準備送到錯的 hostinitFaro({ environment }) + resolverenvironment 決定 receiver URL。
Browser Console 出現 CORS 錯誤頁面 origin、目標 origin、preflight response這是 Browser network boundary 的存取規則。
以為 backendUrls 可以改 receiver停止查 backendUrls它屬於 tracing header propagation，不是 Faro telemetry destination。
/alloy request 有送，但後端仍查不到資料先看 /alloy 的 HTTP response；如果這一段成功，再查 Alloy 收到後往哪裡送Browser 成功送到 /alloy，不代表 Alloy 後面的處理也一定成功。

本課的原始概念來源是 Grafana Faro & Alloy - 前端可觀測性；公司目前 environment mapping、stage/prod /alloy 與 CORS runtime evidence 以 browser-to-alloy evidence 為準；package 責任邊界以 faro-click-tracking evidence 為準。Faro payload/meta/transport 結構則對照 upstream current source。

Recap

  • Instrumentation 解決「要產生什麼 telemetry」；Transport 解決「已產生的 telemetry 怎麼送出去」。
  • Environment 在現行 package 中會解析成 Faro receiver URL；tw-stage 與 tw-prod 目前分別對應各自的 /alloy endpoint。
  • Payload 描述 telemetry 本身；Meta 描述 telemetry 發生時的背景。
  • HTTP request 不等於單一 event；Transport 可以把 signal 組成 request body 再傳送。
  • Session identity 可以同時存在 meta 與 HTTP transport header；先分清資料層與 transport 層。
  • CORS 是 Browser 對 cross-origin network access 執行的規則；某些 request 會先以 OPTIONS 做 preflight。
  • 目前 runtime evidence 證實 stage/prod /alloy 的 OPTIONS contract，但沒有證實一筆真實 telemetry POST 已成功寫入。
  • backendUrls 是 tracing header propagation 的設定，不是 Faro telemetry receiver URL。
  • Lesson 5 邊界：到 Browser → /alloy receiver entry 為止；Alloy 收到後的內部 pipeline 留到後續 Lesson。
