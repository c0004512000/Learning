Faro Browser-to-Alloy Transport

Milestone 3 · 從一筆 telemetry 產生，到 Browser 將它送至 receiver

本課目標
看到 /alloy request，能說明目的地從哪裡來、body 裝了什麼、為什麼操作與 POST 不一對一，以及 HTTP 接收結果能證明到哪裡。

Lesson 4 已建立資料來源：click payload 來自 DOM extraction，user/device 是背景，environment 在初始化提供。現在先用一筆 click 追「資料如何離開 Browser」。

1. 產生資料與送出資料，是兩個責任

Browser click
  │ document listener 呼叫 handler
  ▼
ClickInstrumentation
  │ 讀取標記並建立資料
  ▼
api.pushEvent('click', { link_name: 'DailySchedule' })
  │ 交給 Faro 的處理與傳送流程
  ▼
Transport
  │ 使用 Browser network API
  ▼
receiver URL

Transport 是負責把已產生的 telemetry 交給外部接收端的元件。Faro 的 Web transport 使用 Browser 的 fetch()，所以名稱是 FetchTransport。Fetch 是 Browser 提供的 Web API，不是 JavaScript 核心語言自己擁有的網路能力。

因此 pushEvent() 表示把資料交進流程，不能直接當成「Network 已出現 POST」或「儲存端已收到」。

主教材：Grafana Faro & Alloy；前置：Browser runtime。

3. 單筆資料的 payload，與 HTTP body 分開看

Faro 內部的一個 TransportItem
  ├─ type    ：這是哪種資料
  ├─ payload ：這筆資料發生了什麼
  └─ meta    ：發生時的 app／page／session 等背景

例如 payload.link_name 說明入口語意；meta.device.type 描述當時的分類。前者不對，回查 DOM extraction；後者不對，回查 device detector，而不是改 tracking attribute。

到了 Network 的 Payload 分頁，看到的則是整個 HTTP request body，不是單一 TransportItem 的 payload：

POST /alloy body
  ├─ meta
  ├─ events[]
  ├─ logs[]
  ├─ exceptions[]
  ├─ measurements[]
  └─ traces（有匯出的 spans 時）

不同類別可以同時存在，也可能只出現其中一種。Span 可以先理解為記錄一次操作起訖的資料；spans 如何組成分散式 trace，後續再展開。

events[].trace 若存在，是 event 關聯的 trace/span ID；頂層 traces 才裝完整 span 資料。兩者要核對實際 ID，不能只靠 key 名稱判定同一筆。詳見 Payload 判讀表。

歷史 FetchTransport 另會把 session identity 放在 X-Faro-Session-Id request header，body 裡則有 meta.session.id。同一個 identity 出現在傳輸契約與背景欄位，不是兩個不同 session。

Faro transport types、既有 session-header evidence。

4. 操作數量、資料數量與 POST 數量不相等

一次 business HTTP request 可以被不同 instrumentation 觀察，各自產生 tracing 與 resource-performance 資料。SDK 可以先把資料暫存，再一起送出；這就是此處的 batching。

一次 business GET
  ├─ resource-performance event → 可能落入 batch A
  └─ tracing event + span      → 可能落入 batch B

2026-09-21 的 Jeter 案例確實看見兩種不同內容的 /alloy POST；它證明兩個 payload 不同，不代表每次操作永遠拆成兩包，也不代表 SDK 重送了同一包資料。

2026-10-05 的 IDP Portal 唯讀 reload 則捕捉到四筆 business XHR，以及：

Batch A：meta + events + measurements
  4 個 resource-performance events；0 個 trace spans

Batch B：meta + traces + events
  4 個 tracing events；包含 4 個不同 trace IDs

所以一個 batch 可以混 signal、完全沒有 traces，或同時容納不同 trace。不要把「第 N 個業務 request」配給「第 N 個 /alloy」。

Jeter evidence、IDP Portal evidence。

Trace 還要分清兩層暫存

HTTP instrumentation 結束 span
  │ ended span 交給
  ▼
OTel span processor queue
  │ exporter 匯出並呼叫 pushTraces()
  ▼
Faro TransportItem queue
  │ flush：交出當時累積的資料
  ▼
FetchTransport → POST /alloy

Queue 是待處理資料的記憶體暫存區；flush 是把當時累積的資料交給下一階段。v2.12.1 的 Faro queue 預設每 250 ms 檢查，或達到 50 個 TransportItems 時 flush；它不是一定等滿 50 次操作。

低流量時一個 batch 只有一筆資料也正常；依 meta 分組後，同次 flush 也可能產生多個 POST。Timer、資料單位與第一層 span processor 的細節收在 Queue／Batch 支線，不把預設時間當成送達上限。

Collector POST 不應再形成無限的 tracing POST

既有 v2.12.1 evidence 顯示 transport 的 receiver URL 會提供給 HTTP tracing 的 ignore URLs，避免把正常 /alloy delivery 又變成待匯出的 HTTP span。這不是讓 Network 看不到 /alloy，也不能只因出現多筆 POST 就判定 self-tracing loop；要看 payload 是否反覆包含指向 collector 的 tracing spans。

已保存的 deployed-bundle / runtime evidence；timer 與 grouping 的版本核查見 2026-10-22 verification。

5. Cross-origin 時，Browser 還有 CORS 規則

Origin 由 scheme + host + port 組成；路徑不同不會自己變成跨來源。例如 https://app.example.com 與 https://collector.example.com 的 host 不同，就是 cross-origin。

CORS 是 Browser 依 server response headers 執行的跨來源存取規則。某些 request 還需要先做 preflight，也就是詢問是否允許所需 method 與 request headers：

Browser OPTIONS
  │ 詢問 origin／method／headers 是否允許
  ▼
receiver / gateway 回應政策
  │ Browser 檢查
  ├─ 不通過 → 正式 request 被擋
  └─ 通過   → 可繼續正式 request

不是所有跨來源 request 都先 OPTIONS；符合 safelisted 條件的 request 可以不先 preflight，但 response 仍受 CORS 讀取限制。同源則不需要這層 CORS 授權。Preflight cache 也會使需要 preflight 的 request 不必每次重新送 OPTIONS。

既有 /alloy OPTIONS 證據的範圍

2026-09-12 的主動 OPTIONS 檢查，詢問 POST 與 content-type、x-faro-session-id、traceparent；當時 stage/prod 回 204 並允許這組條件與 origin *。它只證明當時 endpoint 如何回答該次詢問，不證明 Browser 已送出 telemetry，也不證明下游可查。Credentials 與其他 headers 的情況要另按實際 request 核對。

Business API 的 CORS 與 collector 的 CORS 是各自的契約。詳見 CORS 前置 Reference；針對 traceparent 的設定邊界見 Trace propagation CORS 對照。

歷史 OPTIONS evidence、MDN CORS。

6. 每一層只下它能支持的結論

觀察能支持尚不能支持
資料已進 queue。已交入這層暫存。Network 已送出。
Network 出現 POST body。Browser 有這次傳送觀察。接收端與下游全部成功。
/alloy 回 HTTP 202。接收端回覆接受處理。Tempo／Loki 已可查或永久保存。
Tempo 找到 exact span。該 span 此時可查。其他 spans 或全部請求都完整。

看到多筆 POST，先看 Method 與 Payload 類型；看到空查詢，先核對應用身分、時間範圍及資料途徑。下一堂 Lesson 6 把這些判讀轉成 DevTools 操作；Lesson 9 才追接收端之後的 signal 分流。

Recap

  • Instrumentation 產生資料；Transport 負責送到 receiver。
  • Receiver destination 與 business API 的 backendUrls 是不同契約。
  • 單筆 TransportItem 的 payload/meta，與 Network 的整個 body 要分層看。
  • 操作、signal、span、batch 與 POST 不一對一；trace 另經兩層暫存。
  • Collector tracing exclusion 用來避免回饋循環，不代表 Network 沒有 POST。
  • CORS 與 preflight 不是同義詞；相同來源和有效 cache 都會影響觀察。
  • 排隊、送出、HTTP 接收與查詢可見性，必須各自拿證據。

可把一個已遮蔽敏感資料的 Network payload 交給教學 agent，一起判讀它包含的資料種類與證據界線。
