先建立預期
一筆 Faro POST 不一定只有 custom click event。SDK 啟用相應 instrumentation 後，也會根據 Browser 的觀測自動產生 telemetry；Web Vitals 是其中一種。Lesson 5 用這份查表理解「送出去的內容有哪些」，Lesson 6 用它辨認 Payload 裡的 measurements。

1. 沒寫 custom event，仍可能有 telemetry

頁面載入、使用者點擊、Browser 更新畫面，都有可觀測的時間或視覺變化。Web Vitals instrumentation 註冊相關 callback，接收 Browser 衍生的指標，再交給 Faro measurement API。你不需要為每一次效能觀測手動呼叫 pushEvent('click', ...)。

Browser 效能觀測
  │ Web Vitals library 計算指標
  ▼
WebVitalsInstrumentation
  │ 自動呼叫 measurement API
  ▼
Faro measurement
  │ Transport 組成並送出 HTTP body
  ▼
POST /alloy → body.measurements[]

「自動」仍有條件：SDK 必須初始化、該 instrumentation 必須啟用，Browser 必須提供觀測，且要達到該指標的回報時機。它不表示每一筆 POST 都有全部指標。

對照 runtime 的 meta.sdk.version = "2.9.0"，使用同版 預設 instrumentation list 與 初始化入口，避免拿不同版本的欄位當保證。

2. DevTools：先找到送出的 body，再找指標

步驟 1｜先開頁面與 recording，再重新載入

  1. 開啟已授權的 Foreman Assistant Stage main 並登入。
  2. 按 F12 或 Ctrl + Shift + I，選 Network。窄視窗時從 » 找工作區。
  3. 確認 recording icon 為紅色，開 Keep log／Preserve log，Filter 輸入 alloy，按 Clear。
  4. 重新載入頁面，保持前景，等主要內容出現。只看開 DevTools 前的紀錄，可能漏掉載入 telemetry。

步驟 2｜在 /alloy 清單分辨 POST 與 OPTIONS

  1. 若沒有 Method 欄，右鍵點表頭並開啟 Method。
  2. 找 POST，常見 Type 是 fetch；OPTIONS / preflight 回答 CORS 許可，不是 metrics body。
  3. 點 POST 的 Name cell，才會出現 request 詳細 tabs。先到 Headers → General 讀 URL、Method、Status。

步驟 3｜Payload → measurements → type → values → context

  1. 點 Payload，展開 Request payload 的頂層 object。
  2. 找 measurements，展開陣列，再展開每個 index。不要固定只看 0。
  3. 讀 type，找 "web-vitals"。不要把 events[].name 當 measurement type。
  4. 展開同一個 measurement 的 values。找 inp、cls 或 lcp；它們可能分在不同 measurements／POST 中。
  5. 展開同一個 measurement 的 context，讀 rating 與 navigation_type。不要把另一筆 measurement 的 context 配到這個值。
  6. 若只看到 events 或 logs，繼續逐筆檢查 POST；不要因一筆沒有 measurements 就說 SDK 不會送。

Payload 是 Browser 送出的 body；Response 是 receiver 回覆。要證明 SDK 送了 metrics，去 Payload；要證明 HTTP 是否接受，回同筆 Headers 看 status。

Chrome 官方 Network / Payload 操作

步驟 4｜讓互動與回報時機真的發生

  1. 頁面載入完成後，做一次安全的 click、tap 或鍵盤操作，例如既有唯讀導覽。只捲動或 hover 不足以產生 INP 互動。
  2. 切到另一個 tab，讓原頁面進入 hidden，再切回；保留 Network log，等 SDK 的 batch／回報完成。
  3. 回去逐筆讀 POST，記錄實際找到的 metric 與 request。reportAllChanges 設定與生命週期會影響何時回報，不能預設 click 後第一筆 POST 一定有 INP。
  4. 測試完先保留原始效能資料，再對保存的截圖遮罩敏感區；不要先插入大型遮罩 DOM，避免改變被量測的畫面。

目前保存的 capture 沒有 INP／CLS；重跑若仍缺少，就記「未捕捉」，再檢查 recording、是否有 qualifying interaction、hidden 時機、SDK 設定與 Browser 支援。CLS 是分數，可能為零；零與欄位不存在不是同一件事。

先看 element，再決定數字能拿來做什麼
這筆 element 指向 capture 加入的遮罩。它證明 Web Vitals telemetry 確實出現在 HTTP body，但 3156 與 needs-improvement 不能拿來評估 Foreman 原本的產品效能。
欄位怎麼讀
measurements量測訊號陣列；與 events 並列。
type這筆量測的類型；web-vitals。
values.lcp最大可見內容的 render milestone，毫秒；此例受遮罩影響。
values.delta相對該 metric 前一次回報的變化量；不是 HTTP 耗時。
element_render_delay／time_to_first_byteLCP attribution 的 render delay／首位元組時間，毫秒；不是 INP constituents。
timestampmeasurement 的時間，不保證等於 HTTP 發送時間。
context.idmetric identity，不是 user ID。
rating該 metric 的等級；不是全站健康度。
navigation_typenavigation 情境；此例 navigate，不能當成 business subsystem。
navigation_entry_id／elementnavigation 關聯與被量測 element 的線索。

4. INP／CLS：重跑時要找的欄位

下表是 Faro 2.9.0 source 的查找指南，尚未在這次 runtime evidence 看到。它沒有任何捏造的數值。

查找路徑體感與用途
values.inp使用者操作後，到下一個畫面回饋的延遲，毫秒；頁面 INP 代表整段訪問的互動反應，不能把每一次 click 都當成最終 INP。
values.cls閱讀或準備點擊時，內容意外跳動的視覺不穩定程度；沒有時間單位。
input_delay／processing_duration／presentation_delay位於 INP measurement 的 values；把反應延遲拆成等待、處理、呈現。
interaction_time／next_paint_timeINP values 的時間位置線索，勿當三個 duration 再加總。
context.interaction_target／interaction_type／load_state可能的互動 target、互動類型與載入階段；不會自動提供 business link_name。
largest_shift_value／largest_shift_time／context.largest_shift_targetCLS attribution 的線索；value/time 在 values，target 在 context。

2.9.0 對 optional attribution 使用 truthiness guard，值為零可能省略。找不到 input_delay，不能直接推論 Browser 完全沒等待。

5. INP 的因果拆解：點了，為什麼還沒看到回饋？

先從使用者出發：手指點下後，Browser 不一定立刻執行 handler；執行完 handler 也不等於畫面已更新。

如果 input delay 偏長，先找互動前 main thread 是否被其他工作佔住；processing 偏長，找 handlers 的同步工作；presentation 偏長，找 handler 結束後到下一個 frame 的等待與 render 工作。這是縮小調查方向，不能單靠某個欄位斷言是哪段程式造成。

INP 看的是下一個 frame 的回饋，不是「遠端查詢完成、整個業務流程成功」。例如按鈕很快顯示 loading，API 十秒後才完成，兩者是不同 boundary。

6. SDK 懂時間，business semantics 仍由應用提供

資料誰負責給它意義
Web Vitals measurementsBrowser performance observation 與 SDK instrumentation：延遲、視覺穩定性、載入體感。
data-link-name／subsystem宿主 markup／business model，再由 custom ClickInstrumentation 擷取；Browser 不知道此 UI 是哪個業務入口。
業務 user context宿主提供 getUser 或明確設定 user，再由 UserSync/Faro 附帶；SDK session identity 不等於業務登入身分。

因此，看到 Web Vitals 不代表 link_name 或 user context 都有正確 instrumentation；缺少 business attribute 也不代表 Browser 無法提供效能指標。

7. 什麼足以支持「SDK 自動送的」？

Payload 中的 measurements／web-vitals，直接證明 request 含這類 measurement；同版 source 則證明預設 instrumentation 會從 Browser observation 自動呼叫 measurement API。兩者一起支持自動收集的機制與實際傳送事實。

但 type 字串本身不是 call-stack proof：應用也能手動用相同 type 呼叫 pushMeasurement。若要把某筆 measurement 的起源完整證明到自動 callback，還要確認部署中的 instrumentation 初始化與 callback execution；本次沒有捕捉那段 stack。重跑時不要手動 push metric，再把自己的 API 呼叫當成 automatic evidence。

同筆 POST 回 202 只證明 receiver HTTP boundary 接受。它不證明 Alloy → Collector → storage 全部成功。

Self-check

看到四筆 POST，要怎麼找 Web Vitals？

逐筆打開 Payload 的 measurements，按 type 與 values 辨認；不能按 request 順序或 202 status 猜內容。

INP 有值，是否代表 data-link-name 或登入 user 都正確？

沒有這種推論。效能與 business semantics 來源不同，要分別找 evidence。

此例 LCP = 3156，能評估 Foreman 原本的效能嗎？

不能。context.element 指向 capture 加入的遮罩，只能用來辨認 measurement 結構與傳送事實。

Recap

  • Faro POST 可含 automatic telemetry 與 custom events；一筆 request 不等於一個 click。
  • 先找 POST，再看 Payload → measurements → type → values → 同筆 context。
  • 已保存 LCP 的真實 payload；INP／CLS 與展開截圖仍待取得。
  • INP 分等待、處理、呈現；CLS 是視覺穩定性分數；LCP 是載入呈現時間。
  • Business link_name／subsystem／user 需要宿主與額外 instrumentation。
  • Payload、callback origin、HTTP 接受與 storage 寫入，各有自己的證據邊界。

如果找不到某個欄位，帶著 measurement 路徑、操作時機與已遮罩截圖向 agent 追問，再回到主線。
