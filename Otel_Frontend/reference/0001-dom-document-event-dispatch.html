DOM、document 與事件分派

把抽象名詞還原成瀏覽器記憶體裡的物件、事件路徑與實際 callback 呼叫流程

先抓住一句話： JavaScript 並不是不停搜尋「有沒有 click」。瀏覽器負責接收輸入、決定事件目標、建立 Event、分派（dispatch）Event；JavaScript 先把 callback 登記好，瀏覽器在分派過程走到符合條件的 listener 時才呼叫它。

1. DOM 具體來說是什麼？

假設頁面 HTML 是：

<html>
  <body>
    <main>
      <button id="schedule">每日生產排程</button>
    </main>
  </body>
</html>

HTML 是文字。瀏覽器解析後，會在記憶體中建立一組彼此有父子關係的 DOM 物件：

Document 物件代表目前整份網頁文件
HTMLHtmlElement 物件對應 <html>
HTMLBodyElement 物件對應 <body>
HTMLElement 物件對應 <main>
HTMLButtonElement 物件對應 <button id="schedule">
所以 DOM 不是畫面，也不是 HTML 字串。 它是瀏覽器建立的可操作物件，以及這些物件之間的 tree 關係。

2. document 是什麼？

每一份 HTML document 都由一個 Document 物件表示。頁面 JavaScript 中的全域變數 document，就是取得「目前這一頁的 Document 物件」的入口。

document
└── html
    └── body
        └── main
            └── button#schedule

document.querySelector(...) 不是搜尋 HTML 原始字串，而是在目前 DOM tree 中找對應的 DOM 物件。

3. addEventListener() 記住的是什麼？

function handleClick(event) {
  console.log(event.target)
}

document.addEventListener('click', handleClick)

它不是啟動 polling。它是把 listener registration 登記在 document 這個 EventTarget 上：

listener registration
- type: "click"
- callback: handleClick
- capture: false

真正被保存的是 listener registration。每一次 click 的 Event object 是事件發生時才建立，不會自動成為永久紀錄。

4. 點擊如何一路變成 JavaScript 執行？

  1. 使用者輸入發生。 滑鼠、觸控或其他 pointing device 產生平台輸入。
  2. 瀏覽器收到輸入。 不是 JavaScript 主動去抓。
  3. 瀏覽器決定目標。 例如 DOM 中的 button#schedule。
  4. 瀏覽器建立 Event object。 其中包含 type、target 等資料。
  5. 瀏覽器建立這次 dispatch 會經過的 event path。
  6. 瀏覽器開始沿 path 分派 Event。 走到符合條件的 listener 時，當下就呼叫 callback。
所以你的理解「會不會邊找邊執行？」大致是對的。 更精確地說：event path 先由瀏覽器確定；dispatch 時瀏覽器按規則走這條 path，走到某個 EventTarget 時檢查相符 listener，符合就立刻 invoke callback，再繼續下一個位置。

5. Capture、Target、Bubble 到底是什麼？

假設你真正點到的是：

document
└── html
    └── body
        └── main
            └── button#schedule  ← event.target

瀏覽器不是只看 button。因為 button 位於一棵 DOM tree 裡，所以這次事件有一條 ancestor path。DOM event dispatch 把這條 path 分成三個階段理解：

① Capturing phase
   document → html → body → main → button

② Target phase
                               button

③ Bubbling phase（如果這個 event 會 bubble）
   document ← html ← body ← main ← button

Capturing phase：從外層往 target 走

Capture 可以先翻成「捕獲階段」。 它的意思不是「找出 target」；target 在 dispatch 前已經決定好了。Capture phase 是：瀏覽器沿已知的 event path，從較外層 ancestor 往 target 方向走，執行那些登記成 capture: true 的 listeners。

document.addEventListener('click', handleClick, {
  capture: true
})

如果 listener 這樣登記，那麼 event path 在往 button 走的 capture 階段經過 document 時，就會呼叫 handleClick(event)。

Target phase：到達真正的 target

走到 button#schedule 時，event.eventPhase 會是 AT_TARGET。此時 target 自己的 listener 會依 DOM dispatch 規則被處理。

Bubbling phase：從 target 往 ancestor 回走

Bubble 可以翻成「冒泡」。 想像水底的一顆氣泡從最深的地方往上浮。事件的 target 是最內層 button；如果這個 event 的 bubbles 是 true，瀏覽器會再由 target 的 ancestor 往外層走：

button
  ↑
main
  ↑
body
  ↑
html
  ↑
document

這一趟會執行一般沒有設定 capture: true 的 ancestor listeners。

6. 所以一般 document.addEventListener() 什麼時候執行？

document.addEventListener('click', handleClick)

因為沒有設定 capture: true，它預設是 non-capture listener。

這句話要直接記住：
在 document 這個 DOM EventTarget 上登記一個 click listener。未來如果某次 click 的 event path 在 bubbling 階段經過 document，請瀏覽器呼叫 handleClick(event)。

所以你問「相反就是 bubble 時才執行嗎？」——對於掛在 ancestor 上、而且 capture: false 的 listener，可以這樣理解。規格上先呼叫 capture listeners；如果 event 的 bubbles 為 true，再反向走 ancestors 呼叫 non-capture listeners。

7. 為什麼還要區分 capture 與 bubble？

先不要把它理解成「瀏覽器多此一舉走兩遍」。兩個方向讓 ancestor 可以選擇在 target 被處理前或在 target 之後往上傳遞時觀察／介入事件。

階段方向ancestor 可以做什麼
Capture外 → 內在事件到達 target 前先觀察或攔截。
Targettarget 本身處理真正被指向的物件。
Bubble內 → 外讓父層在子元素事件發生後統一處理；event delegation 常靠這個。

對你現在的 Faro 情境，最重要的是 bubbling：高層的 document listener 可以不用替每顆 button 個別註冊 listener，而是等 click 從子元素一路 bubble 上來，再看 event.target 判斷真正點了誰。

8. 「click 是會 bubble 的事件」到底是什麼意思？

每個 Event object 都有一個 bubbles 布林值。這不是「有沒有 Event」；它只控制：到達 target 後，要不要再沿 ancestors 的反向順序執行 non-capture listeners。

event.bubbles === true
→ target 處理完後，還會往 ancestor 方向進入 bubbling phase

 event.bubbles === false
→ 不做 ancestor 的 bubbling phase

所以「click 會 bubble」的意思是：

瀏覽器建立／fire 的 click event 具備會沿 target ancestors 往外傳遞給 non-capture listeners 的行為。

9. 為什麼有些事件會 bubble，有些不會？

這不是由「DOM tree 自動推導」出來，而是該事件種類的規格／初始化方式決定它的 bubbles 行為。DOM Standard 本身只提供通用機制：Event 有一個 bubbles 屬性；若為 true，就執行 ancestor 的 bubbling listeners，否則不執行。

因此不要背成「所有 DOM event 都會往上」。正確判斷是：

這次 event 有 target
        ↓
一定可以有 dispatch path / capture 處理
        ↓
到達 target
        ↓
檢查 event.bubbles
   ├── true  → 再做 ancestor bubbling
   └── false → 不做 ancestor bubbling
此階段先不要硬背整張 event 類型表。 你真正需要的是知道：bubbles 是 Event 的一個行為屬性；不同 event type 是否設定為會 bubble，要看該 event 的規格。等 Faro 實際用到某個 event type，再查它的 bubbles 行為。

10. event.target 與 event.currentTarget

欄位回答的問題
event.target這次 event 最初 dispatch 到哪個 target，例如 button。
event.currentTarget此刻正在執行的是哪個 EventTarget 上的 listener，例如 document。
event.eventPhase現在處於 capture、target 還是 bubble。
event.bubbles是否會進行 ancestor 的 bubbling 處理。

Recap

  • target 在 dispatch 前就已確定；capture 不是用來「找 target」。
  • Dispatch 時會沿 event path 處理，而且會在符合條件的位置直接 invoke listener callback。
  • Capture：ancestor → target，處理 capture: true listeners。
  • Target：到達真正 target。
  • Bubble：若 event.bubbles === true，再由 target ancestors 反向往外處理 non-capture listeners。
  • 一般 addEventListener(...) 預設 capture: false，所以 ancestor listener 常在 bubbling 階段被呼叫。
  • 「click 會 bubble」不是說 click 被複製；是同一個 event dispatch 會包含 ancestor bubbling 處理。
  • 是否會 bubble 是 event 行為的一部分，不是所有 event 都一樣。
