DOM、document 與事件分派

從具體物件與呼叫順序理解：DOM 是誰建立、Event 是誰建立、listener 又在什麼時候執行。

這張 Reference 的目標：讀完後，你應該能從一次 button click 開始，自己重建 target → event path → capture → target phase → bubble → callback(event)，而不需要把它背成名詞表。

1. HTML、DOM、JavaScript 的責任邊界

① HTML原始標記文字，例如 <button>每日生產排程</button>。
↓ browser parses
② DOM瀏覽器在記憶體中建立並維護的文件物件樹。
↓ browser exposes DOM APIs
③ JavaScript透過 DOM API 取得 DOM object 的 reference，然後讀取或操作它。
精確模型：DOM object 是瀏覽器建立與管理的物件；JavaScript 可以透過瀏覽器提供的 DOM API 取得 reference 並操作它。

例如：

<button id="daily-schedule">每日生產排程</button>

瀏覽器解析後會建立代表這顆按鈕的 DOM object。JavaScript 取得它：

const button = document.querySelector('#daily-schedule')
console.log(button.constructor.name)
// HTMLButtonElement
HTML element
原始文件中的標記，例如 <button ...>。
DOM object
瀏覽器解析文件後在記憶體中建立的物件。
HTMLButtonElement
按鈕 DOM object 對程式暴露的介面／型別名稱。

2. #daily-schedule 是 selector

daily-schedule 是 HTML 作者替 element 指定的 id；前面的 # 是 CSS selector 語法，表示「找 id 等於這個值的 element」。

<button id="daily-schedule">每日生產排程</button>

const button = document.querySelector('#daily-schedule')
                                      ↑
                         找 id="daily-schedule"

button#daily-schedule 則只是「button，且 id 是 daily-schedule」的 selector 表示法，不是 HTML 原始語法。

3. document 與 DOM tree

Document
└── html
    └── body
        └── main
            └── button id="daily-schedule"

document 是頁面 JavaScript 取得目前 HTML document 所對應 Document object 的入口。因此 document.querySelector(...) 是從目前 Document 的 DOM tree 中找符合 selector 的 DOM object。

4. Click 發生後，是誰建立 Event？

button 不是 Event 的製造者。簡化後的因果鏈是：

手指 / 滑鼠輸入
      ↓ browser receives input
瀏覽器取得輸入位置
      ↓ hit testing
瀏覽器判定該位置對應 button
      ↓ sets target
button 成為這次 click 的 target
      ↓ creates
瀏覽器建立 click Event object
所以 event.target 是「這次 event 最初指向哪個 DOM object」，不是「哪個 DOM object 創造了 event」。

5. 為什麼建立 Event 之後還需要 dispatch？

知道 target = button 只回答「這次 click 指向誰」。瀏覽器接著還要回答另一題：

這次 event 應該讓 DOM path 上哪些已登記的 listener 執行，而且按照什麼順序執行？

這個處理過程就是 event dispatch（事件分派）。它不是把 Event 掛回 button，也不是把 Event 送上網路。

6. Listener 是在 event 發生以前先登記

function handleClick(event) {
  console.log(event.target)
}

document.addEventListener('click', handleClick)

這一步先在 document 這個 EventTarget 上建立 listener registration：它記住 event type、callback 與 options。它不會預先建立未來的 click Event。

document 上先記住：
- type: "click"
- callback: handleClick
- capture: false（預設）

7. Target 已經知道後，dispatch 才沿 event path 執行 listener

假設 target 是最內層 button：

document
└── html
    └── body
        └── main
            └── button  ← event.target

Capture 並不是一邊往下走、一邊尋找「到底點到誰」。target 與 event path 已經先確定；dispatch 才開始按照 path 與 listener options 決定呼叫順序。

Capture phase（捕獲階段）｜外 → 內document → html → body → main → button
瀏覽器沿 path 朝 target 走。走到某個 EventTarget 時，如果那裡有符合 event type 且 capture: true 的 listener，就在這一趟呼叫它。
Target phase（目標階段）event 到達 button，也就是這次 event 的 target。
Bubble phase（冒泡階段）｜內 → 外button → main → body → html → document
如果這個 Event 允許 bubbling，dispatch 會再沿 ancestors 往外處理 non-capture listeners。

所以「邊走邊執行」可以用，但要說完整：

不是邊找 target 邊執行；而是 target/path 已確定後，在 dispatch 過程中沿 path 走，遇到符合目前 phase 與 event type 的 listener 就呼叫。

8. 為什麼要區分 Capture 和 Bubble？

因為 ancestor 可能希望在不同時機介入同一個 descendant event：

Capture：ancestor 想在 event 抵達 target 前收到

Target：event 抵達真正 target

Bubble：ancestor 想在 target 之後，從 descendant 的 event 往上收到

addEventListener() 的 capture option 就是在選 listener 要參與哪一趟：

// 在 capture 階段經過 document 時呼叫
 document.addEventListener('click', handleClick, { capture: true })

// 預設 capture: false；對會 bubble 的 click，通常在 bubble 階段經過 document 時呼叫
 document.addEventListener('click', handleClick)

9. 「Bubble」到底是什麼意思？

Bubble 的字面意象就是氣泡從較深的位置往上冒。在 DOM tree 中，target 通常位於某個 ancestor chain 的內層，因此：

button  ← target
   ↑
 main
   ↑
 body
   ↑
 html
   ↑
document

這不是 Event 被複製很多份，也不是 button 把 Event 手動送給 parent；是同一次 event dispatch 正在按規則處理 ancestor listeners。

10. 「click 是會 bubble 的 event」是什麼意思？

Event 有一個 boolean 性質：

event.bubbles  // true 或 false

如果 event.bubbles === true，代表 target phase 之後，dispatch 允許再沿 ancestors 往外處理 bubbling listeners。一般 browser click event 會 bubble。

click Event
bubbles = true

Target: button
   ↓
Bubble:
button → main → body → html → document

如果某個 Event 的 bubbles === false，就不能依賴「從 target 往 ancestors 冒泡」這條路讓 ancestor 的 non-capture listener 收到它。

為什麼有 true / false？DOM Event 模型提供 bubbles 這個事件性質；不同 event type／event 初始化規則決定它是否採用 bubbling。現在不需要背一張事件清單。真正遇到某個 event type 時，再查它的規格與 bubbles 行為。

11. 為什麼 document.addEventListener('click', ...) 能收到 button click？

現在可以把這句話精確翻成：

在 document 這個 DOM EventTarget 上登記一個 click listener。未來如果某次 click 的 event path 在 bubbling 階段經過 document，請瀏覽器呼叫 handleClick(event)。

這也是 event delegation（事件委派）的基礎：不必替每個 descendant 都各掛一個 click listener；ancestor 可以接住會 bubble 上來的 click，再用 event.target 判斷最初的 target。

12. event.target 和 event.currentTarget

你點 button
    ↓
event.target = button

同一個 Event bubble 到 document
    ↓
document 上的 listener 正在執行
    ↓
event.currentTarget = document
event.target
這次 event 最初指向的 DOM object。
event.currentTarget
目前正在執行的 listener 所屬的 EventTarget。

不看上面的流程，試著回答：
  1. Capture 開始時，browser 還在找 target 嗎？
  2. 一般 document.addEventListener('click', handler) 為什麼能收到 descendant button 的 click？
  3. event.bubbles === false 最直接改變哪一段 dispatch 行為？

Recap

  • DOM object 由 browser 建立與管理；JavaScript 透過 DOM API 取得 reference。
  • button 不是 click Event 的 creator；browser 收到輸入、判定 target，再建立 Event。
  • dispatch 是 target/path 已知後，依 event path、phase 與 listener registration 決定並執行 callbacks。
  • Capture 是外 → 內；符合 capture: true 的 ancestor listener 在這一趟執行。
  • Bubble 是 target → ancestors；對 bubbles === true 的 Event，ancestor 的 non-capture listeners 可在這一趟執行。
  • click 會 bubble，所以 document listener 可以收到 descendant button 的 click。
  • event.target 保留最初 target；event.currentTarget 表示目前執行哪個 EventTarget 上的 listener。
  • Browser Event object 與 Faro telemetry 是不同層次。
