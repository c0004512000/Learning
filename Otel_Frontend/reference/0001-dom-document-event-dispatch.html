DOM、document 與事件分派

從具體物件與呼叫順序理解：DOM 是誰建立、Event 是誰建立、listener 又在什麼時候執行。

這張 Reference 的目標：讀完後，你應該能從一次 button click 開始，自己重建 target → event path → capture → target → bubble → callback(event)，並知道什麼情況會選 capture: true 或預設的 capture: false。

1. HTML、DOM、JavaScript 的責任邊界

① HTML原始標記文字，例如 <button>每日生產排程</button>。
↓ browser parses（瀏覽器解析）
② DOM瀏覽器在記憶體中建立並維護的文件物件樹。
↓ browser exposes DOM APIs（瀏覽器提供操作介面）
③ JavaScript透過 DOM API 取得 DOM object 的 reference，然後讀取或操作它。
精確模型：DOM object 是瀏覽器建立與管理的物件；JavaScript 可以透過瀏覽器提供的 DOM API 取得 reference 並操作它。

例如：

<button id="daily-schedule">每日生產排程</button>

瀏覽器解析後會建立代表這顆按鈕的 DOM object。JavaScript 取得它：

const button = document.querySelector('#daily-schedule')
console.log(button.constructor.name)
// HTMLButtonElement
HTML element
原始文件中的標記，例如 <button ...>。
DOM object
瀏覽器解析文件後在記憶體中建立的物件。
HTMLButtonElement
按鈕 DOM object 對程式暴露的介面／型別名稱。

2. #daily-schedule 是 selector

daily-schedule 是 HTML 作者替 element 指定的 id；前面的 # 是 selector 語法，表示「找 id 等於這個值的 element」。

<button id="daily-schedule">每日生產排程</button>

const button = document.querySelector('#daily-schedule')
                                      ↑
                         找 id="daily-schedule"

button#daily-schedule 則只是「button，且 id 是 daily-schedule」的 selector 表示法，不是 HTML 原始語法。

3. document 與 DOM tree

Document
└── html
    └── body
        └── main
            └── button id="daily-schedule"

document 是頁面 JavaScript 取得目前 HTML document 所對應 Document object 的入口。因此 document.querySelector(...) 是從目前 Document 的 DOM tree 中找符合 selector 的 DOM object。

4. Click 發生後，是誰建立 Event？

button 不是 Event 的製造者。簡化後的因果鏈是：

手指 / 滑鼠輸入
      ↓ browser receives input（瀏覽器收到輸入）
瀏覽器取得輸入位置
      ↓ hit testing（判斷該位置落在哪個畫面元素）
瀏覽器判定該位置對應 button
      ↓ sets target（指定本次事件目標）
button 成為這次 click 的 target
      ↓ creates（建立）
瀏覽器建立 click Event object
所以 event.target 是「這次 event 最初指向哪個 DOM object」，不是「哪個 DOM object 創造了 event」。

5. 為什麼建立 Event 之後還需要 dispatch？

知道 target = button 只回答「這次 click 指向誰」。瀏覽器接著還要回答另一題：

這次 event 應該讓 DOM path 上哪些已登記的 listener 執行，而且按照什麼順序執行？

這個處理過程就是 event dispatch（事件分派）。它不是把 Event 掛回 button，也不是把 Event 送上網路。

6. Listener 是在 event 發生以前先登記

function handleClick(event) {
  console.log(event.target)
}

document.addEventListener('click', handleClick)

document、button、main 這類可以登記 event listener 的物件，都具有 EventTarget 的能力。這裡先把 EventTarget 理解成：

可以讓程式登記 listener，並在 event dispatch 經過它時讓瀏覽器呼叫相符 callback 的物件。

addEventListener() 這一步只是在 document 上建立 listener registration：

document 上先記住：
- type: "click"
- callback: handleClick
- capture: false（預設）

它不會預先建立未來的 click Event。

7. 先定義「phase」：同一次 dispatch 現在走到哪一段

這裡的 phase（階段） 不是另一種 Event，也不是重新觸發一次 click。它只是在描述：

同一個 Event 正在被 dispatch 時，現在走到整條處理路徑的哪一段？

假設 target 已經確定是最內層 button：

document
└── html
    └── body
        └── main
            └── button  ← event.target 已經確定

Capture 並不是一邊往下走、一邊尋找「到底點到誰」。target 與 event path 已經先確定；dispatch 才按照 path 與 listener registration 決定 callback 的呼叫順序。

Capture phase（捕獲階段）｜外 → 內document → html → body → main → button
瀏覽器朝 target 走。經過某個 ancestor 時，如果那裡有符合 event type 且 capture: true 的 listener，就在這一趟呼叫 callback。
Target phase（目標階段）event 到達 button，也就是這次 event 的 target。
Bubble phase（冒泡階段）｜內 → 外button → main → body → html → document
如果這個 Event 允許 bubbling，dispatch 會再沿 ancestors 往外處理 capture: false 的 ancestor listeners。
所以不是「在 Capture 或 Bubble 階段觸發 Event」。Event 在這之前就已經建立了。你選的是「這個 listener callback 要在哪一段 dispatch 被呼叫」。

8. capture: true / false 真正選的是什麼？

先修正一句很容易過度簡化的說法：不是「Bubble 是預設」；精確地說，是 capture: false 為預設。

// capture: true
// → 不在 ancestor 的 bubble phase 執行；會參與 capture
 document.addEventListener('click', handleClick, { capture: true })

// capture: false（預設）
// → 不在 ancestor 的 capture phase 執行
 document.addEventListener('click', handleClick)

如果這個 listener 掛在 ancestor，而這個 event 又會 bubble，capture: false 的 listener 通常就是在 Bubble phase 收到它。

但 capture: false 不等於「永遠 eventPhase = Bubble」。如果 listener 所在的物件本身就是 event.target，它是在 Target phase 被呼叫。反過來，capture: true 的 listener 如果剛好就掛在 target 上，也是在 Target phase。capture 是 listener 的登記設定；phase 是這次 dispatch 當下的位置。兩者不是同一個欄位。

9. 什麼時候選 Capture？什麼時候選 Bubble？

不要從「哪個比較高級」判斷，而是問：我需要在 descendant 的 handler 執行之前看到這次互動，還是等它到達 target 之後再從下往上處理？

想在子元素 handler 前先觀察
選 capture: true。例如全頁 telemetry 想盡可能早看到 click，或某些 descendant 後面可能停止 event 繼續傳遞。
一般 UI click handler
通常不需要 capture。直接掛在 target，使用預設 capture: false 即可。
Ancestor 統一接後代 click
通常使用 capture: false + bubbling，也就是 event delegation。ancestor 等 descendant click 往上冒，再用 event.target 判斷來源。
想觀察 target handler 已改變的狀態
Bubble 比較符合時序：target handler 先執行，ancestor bubble listener 後執行。注意 browser 的 default action 不應被等同於「此時一定已完成」。

為什麼 API 預設是 capture: false？規格直接把它定義成預設值。實務上可以把 capture 視為「我有理由要在 descendant handler 前介入」時才打開的選項；如果沒有這個時序需求，就不需要特別開 capture。

10. 用 Trace 來看：Capture / Bubble 可能真的改變因果關係

這裡先用你熟悉的 tracing 心智模型。嚴格說不是「加一條 trace」，而通常是在 click listener 裡建立一個 interaction Span；和它有親子關係的其他 Spans 才共同形成一條 Trace。

假設 app 本身在 button handler 裡立刻呼叫 API：

document
└── button
    └── app click handler
        └── fetch('/api/orders')

如果 telemetry listener 在 document Capture，它有機會在 app 的 button handler 前先執行：

document capture listener
  ↓ executes before descendant handler
建立 click interaction Span / tracing context
  ↓ browser continues dispatch
button app handler
  ↓ calls
fetch('/api/orders')

如果 instrumentation 能把這個 click Span 的 context 正確保持／傳遞到後面的 app handler 與 fetch，理想的 trace topology 才可能是：

click interaction Span
└── HTTP /api/orders Span

如果你直到 document Bubble 才建立 click Span：

button app handler
  ↓ calls
fetch('/api/orders')   ← 這個 request / span 可能已經開始
  ↓ browser continues dispatch
 document bubble listener
  ↓
現在才建立 click Span

那它已經太晚，不能事後把一個已建立的 HTTP Span「改成自己的 child」。所以若你的目的真的是建立「使用者 click → app work → HTTP request」的因果父子關係，listener 的執行時機就很重要。

但 Capture 本身還不夠。OpenTelemetry 的 parent/child 關係依賴「active context」。如果你只在 capture callback 裡 startSpan() 然後 callback 一結束 context 就沒有延續到後續 handler，下面的 fetch 仍不會自動變成 child。要不要、以及怎麼跨後續 listener / async work 傳遞 context，是 instrumentation 必須另外正確處理的問題。

所以可以分成兩種需求：

只想記錄「發生一次 click」
→ Capture / Bubble 可能只影響記錄時機、能否被 stopPropagation 擋住、以及當時可觀察到的狀態。

想讓 click Span 成為後續工作／HTTP Span 的 parent
→ 必須在那些工作建立之前建立並啟用 tracing context；
  Capture 提供比較早的觀察點，但仍需要正確的 context propagation。
來源邊界：上面的 Trace 段落是為理解 browser event timing 所補的 OpenTelemetry prerequisite，不是在宣稱目前 @sre2/faro-click-tracking 的實作一定採用這個 tracing 策略。實際 Faro instrumentation 怎麼做，要回主線時以 source document / code 驗證。

11. Bubble 到底是什麼意思？

Bubble 的字面意象就是氣泡從較深的位置往上冒。在 DOM tree 中：

button  ← target
   ↑ bubbles toward ancestor
 main
   ↑ bubbles toward ancestor
 body
   ↑
 html
   ↑
document

這不是 Event 被複製很多份，也不是 button 手動把 Event 傳給 parent；是同一次 event dispatch 正在按規則處理 ancestor listeners。

12. 「click 是會 bubble 的 event」是什麼意思？

Event object 有一個 boolean 性質：

event.bubbles  // true 或 false

如果 event.bubbles === true，代表 target phase 之後，dispatch 允許再沿 ancestors 往外處理 bubbling listeners。browser 的 click event 會 bubble。

如果某個 Event 的 bubbles === false，就不能依賴「從 target 往 ancestors 冒泡」讓 ancestor 的 capture: false listener 收到它。

現在不用背哪些 event 會 bubble。不同 event type 的規格會定義這項行為。真正遇到某一種 event 時，再查它的 bubbles 行為。

13. 為什麼 document.addEventListener('click', ...) 能收到 button click？

現在可以把這句話精確翻成：

在 document 這個 DOM EventTarget 上登記一個 click listener。未來如果某次 click 的 event path 在 bubbling 階段經過 document，請瀏覽器呼叫 handleClick(event)。

這也是 event delegation（事件委派）的基礎：不必替每個 descendant 都各掛一個 click listener；ancestor 可以接住會 bubble 上來的 click，再用 event.target 判斷最初的 target。

14. event.target 和 event.currentTarget

你點 button
    ↓
event.target = button

同一個 Event bubble 到 document
    ↓
document 上的 listener 正在執行
    ↓
event.currentTarget = document
event.target
這次 event 最初指向的 DOM object。
event.currentTarget
目前正在執行的 listener 所屬 EventTarget。

15. 最後才看 event.eventPhase

前面已經先定義了 phase。現在這個 property 就只是把「目前走到哪一段」用程式可以讀的值表示出來：

NONE (0)
Event 現在沒有處於 dispatch 中。
CAPTURING_PHASE (1)
目前正在 target 之前的 Capture 階段。
AT_TARGET (2)
目前正在 event.target 本身。
BUBBLING_PHASE (3)
目前正在 target 之後往 ancestors 的 Bubble 階段。
不要把數字 1 / 2 / 3 當成要背的知識。先理解 Capture / Target / Bubble 的位置；eventPhase 只是 browser API 把這個 runtime 狀態暴露出來。

自我檢查

不看上面的流程，試著回答：
  1. Capture 開始時，browser 還在找 target 嗎？
  2. capture: false 是否等於 listener 永遠只會在 Bubble phase 執行？
  3. 如果 button handler 會立刻建立 HTTP Span，為什麼 document Bubble listener 才開始 click Span 可能太晚？

Recap

  • DOM object 由 browser 建立與管理；JavaScript 透過 DOM API 取得 reference。
  • button 不是 click Event 的 creator；browser 收到輸入、判定 target，再建立 Event。
  • phase 只是同一次 event dispatch 目前走到哪一段。
  • dispatch 是 target/path 已知後，依 event path、phase 與 listener registration 決定並執行 callbacks。
  • capture: false 才是 API 的預設；它不等於「一定在 Bubble phase」。
  • Capture 適合需要在 descendant handler 前先觀察／介入的 listener；Bubble 適合一般 ancestor delegation 與 target 之後的處理。
  • click 會 bubble，所以 document 的 non-capture listener 可以收到 descendant button 的 click。
  • event.eventPhase 只是把 Capture / Target / Bubble 的當下 runtime 狀態暴露成 0 / 1 / 2 / 3。
  • Tracing 若要形成 click → downstream work 的 parent/child 因果鏈，除了 listener timing，還必須正確建立與傳遞 active context。
  • Browser Event object 與 Faro telemetry 是不同層次。
