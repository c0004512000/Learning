要能做出的判斷
一次操作後出現數筆 /alloy、或某個 batch 只有一筆資料時，能先看它包含的內容與資料產生時間，不先判定 batching 失效或重複傳送。

使用者操作一次，並不表示 SDK 只產生一筆資料。HTTP span、tracing event 與 resource-performance event 可能在不同時間完成。先把「資料」與「裝資料的 HTTP request」分開，才看得懂 queue。

起點：主／支線對話來源紀錄。以下版本細節另以 Faro v2.12.1 source 核查為依據；不代表所有 SDK 版本或內部封裝都採相同設定。

1. Queue 收的是資料，不是使用者操作

Queue 是記憶體裡暫存、等待處理的資料；flush 是把當時累積的資料交給下一階段。交出去不代表接收端已持久化。

點一次 Add Credential
  ├─ HTTP instrumentation 完成一個 span
  ├─ 可能產生 tracing event
  └─ 可能產生 resource-performance event

Faro queue 內的一個單位：TransportItem
  ├─ type：哪種資料
  ├─ payload：資料本身
  └─ meta：產生時的背景

一個 trace TransportItem 可以已經包含多個 spans。因此 50 個 TransportItems ≠ 50 個 spans ≠ 50 次操作。Browser Network 的 POST 數量又是另一個單位。

2. Trace 先經過 span queue，再進入 Faro queue

Business HTTP request 執行中
  │ HTTP instrumentation 結束 span
  ▼
OTel BatchSpanProcessor
  │ 收集 ended spans，再交給 exporter
  ▼
FaroTraceExporter → api.pushTraces()
  │ 建立 trace TransportItem
  ▼
Faro signalBuffer
  │ 與其他種類的 TransportItems 一起排隊
  ▼
依 meta 分組 → FetchTransport → POST /alloy
  │ 接收與下游處理
  ▼
Tempo / Loki 等查詢端

v2.12.1 的預設 tracing 初始化使用 BatchSpanProcessor：scheduledDelayMillis = 1000、maxExportBatchSize = 30。這裡計數的是 spans；若配置了替代 spanProcessor，就不能直接套用這組預設值。

接著才是 Faro 的批次處理：sendTimeout = 250 ms、itemLimit = 50。這裡計數的是 TransportItems。不要把 OTel 的 30 與 Faro 的 50 當成同一個 queue 的兩個限制。

版本化原始碼：TracingInstrumentation、BatchExecutor。

3. 250 ms 是固定 timer tick，不是每筆資料重新倒數

在 batching 已啟動、未暫停，且 event loop 能如期執行的簡化例子中：

Timer：  0 ───── 250 ───── 500 ───── 750 ms
                        ↑       ↑
                   410 加入    500 flush
                    item       等待約 90 ms

這個實作使用 setInterval。一筆資料在 251 ms 加入，接近等 249 ms；410 ms 加入，接近等 90 ms。新資料進來不會把該 timer 重新設定為「再等 250 ms」。空 queue 到達 tick 時不會因此送出空 POST。

這不是 250 ms 的送達保證。Browser 排程延遲、背景分頁節流、前一層 span processing、網路、接收端與查詢可見性，都可能增加時間。1000 + 250 也不是端到端延遲上限。

4. 不必等到 50 筆才送

v2.12.1 的觸發點可以推導什麼
固定 timer tick有一筆也可以 flush；空 queue 則不送。
加入 item 後達到 itemLimit可以在下一個 tick 前就 flush。
visibilitychange 變成 hidden嘗試 flush Faro 當時已有的 queue。

Hidden 時的 flush 不等於「關閉 Browser 前所有資料必達」。它不保證事件一定發生，也不能憑空補出尚未結束或仍在前一層的 span。核查到的 flush() 是 BatchExecutor 私有方法；這不能直接改寫成應用可呼叫的公開 SDK API。

5. 一次 flush 也可能對應多個 POST

BatchExecutor 以 JSON.stringify(item.meta) 的結果分組。背景資料不同的 items 可以落在不同組，再各自交給 transport：

同一次 flush 的 snapshot
  ├─ meta A：event 1、event 2 → transport body A
  └─ meta B：trace item 1   → transport body B

因此「一個 flush」、「一個 POST」、「一條 trace」都不是一對一。低流量時單筆 batch 正常；高流量時同一 body 也可能含多個 signal 類別、多個 trace IDs。

在 Network 判讀時，先辨認 Method，再看 events、logs、exceptions、measurements 與 traces。計算 span 數要走訪所有 resourceSpans → scopeSpans → spans，不能只看第一個 resource 或把 resourceSpans.length 當成 span 數。

單筆 payload 只能告訴你實際送出的內容，不能單靠截圖證明是哪個內部觸發點造成這次 flush。反過來，兩筆 /alloy 內容不同，也不能稱為同一包資料重送。

Self-check

固定 tick 在 250、500、750 ms；410 ms 加入一個 item，沒有其他觸發與排程延遲。預期在哪個 tick flush？
一個 trace TransportItem 內有 20 個 spans；Faro 的 50-item 限制會把它算成多少個 item？
看到一個 /alloy body 只有一個 event，單靠這個觀察能說什麼？

Recap

  • 先分清操作、span、TransportItem、batch body 與 POST。
  • Ended spans 經 OTel 處理，再成為 Faro queue 的 trace item；不是一個 queue。
  • 250 ms 是此版本的固定 tick，50 是 item 門檻；單筆也能形成 batch。
  • 同次 flush 依 meta 分組，可以形成多個 transport bodies。
  • 排隊、交給 transport、HTTP 接收與可查詢是不同證據；任何預設 timer 都不是送達 SLA。

練習時可提供一個簡化的「資料何時加入」時間線，請教學 agent 一起推導；不需要對真實 Credential 重複建立資料。
