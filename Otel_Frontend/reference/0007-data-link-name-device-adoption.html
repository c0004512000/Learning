1. 原本有的是 subsystem，不是 data-link-name

Git history 已驗證：Foreman 在 Faro 導入前就有 Subsytem identifiers 與 system.subsystem。例如 DailySchedule、MaterialTracking、EfficiencyAbnormalReport。它們用來識別「這個 Foreman 功能／子系統是誰」。

原本的 application logic 甚至已經會把這個值交給 Foreman 自己的 Web Log：

this.insertForemanWebLog(topic, system.subsystem)

insertForemanWebLog() 是 Foreman 自己的 TypeScript function，不是 Browser / HTML 的固定名詞，也不是一個 DOM attribute。這行只證明 subsystem 在 Faro 以前就已經具有 application semantic；Web Log 最後如何儲存，要看該 function 的實作。

2. Faro 導入時，才把既有值投影到 DOM

2026-08-20 的可達 Foreman commit 同時加入 Faro initialization 與這條 template binding：

<p-button
  [pTooltip]="getSystemTooltip(item)"
  [attr.data-link-name]="item.subsystem"
  (onClick)="openSystemLink(panel.topic, item)"
>

這裡要分清兩層：

東西存在位置例子
item.subsystemAngular / TypeScript application state"DailySchedule"
data-link-nameBrowser runtime DOM attributedata-link-name="DailySchedule"

所以不是 Faro 同時抓兩個值；而是同一個 application value 被 Angular 寫到 DOM，Faro 再從 DOM 讀它。

3. data-* 是標準 custom-data 機制，但 data-link-name 不是業界固定名稱

HTML 的 data-* 是標準化的 custom data attribute 機制。Browser 通常也會保留其他未知 attribute，但 data-* 才是 HTML 明確提供給 application 放自訂資料的標準路徑。

data-link-name 這個具體名稱不是 HTML、Faro 或 OpenTelemetry 的固定 convention。Foreman 之所以使用它，是因為公司 Faro package 的 tracking contract 設定：

trackAttributes: ['data-link-name']

它的 value 也不是 Browser 從畫面文字、href 或 route 自動推導；Main page 直接使用 item.subsystem。

4. 為什麼 closest('[data-link-name]') 有中括號？

整句是 JavaScript；但 closest() 的參數是一個 CSS selector string。

$0.closest('[data-link-name]')
│  │       └────────────────── CSS selector：有這個 attribute 的 element
│  └────────────────────────── JavaScript DOM method
└───────────────────────────── DevTools 目前選到的 DOM element

CSS selector 的 attribute 語法是：

[data-link-name]                 → 有這個 attribute
[data-link-name="DailySchedule"] → attribute value 等於 DailySchedule

找到 element 後，getAttribute() 做的是另一件事：它直接接受 attribute name，所以不用 selector 的中括號。

$0.closest('[data-link-name]')?.getAttribute('data-link-name')
          │ 找 element                         │ 讀 attribute value
          │ 參數是 selector                    │ 參數是 attribute name
          ▼                                    ▼
[data-link-name]                           data-link-name

5. link 在這裡不等於 HTML <a>

Source inventory 已確認：有 data-link-name 的主要位置是 Main subsystem tile template，以及 Toolbar 的五個固定功能：

UserGuide.UserGuide
ReferenceDocument.SDS
ReferenceDocument.AI
ReferenceDocument.ForemanManual
Contact.ContactAdministrator

這些標記掛在 <p-button> host，不代表 HTML hyperlink。反過來，inventory 中的兩個 <a> declaration 都沒有 data-link-name。

因此在這個專案裡，data-link-name 更接近「被選定來做 telemetry 的 UI 功能入口識別值」，而不是「超連結顯示文字」。

6. 不是所有 click 都要形成 Faro click event

目前 template inventory 有 48 個 p-button declarations，其中只有 6 個 declaration 自己有 data-link-name；Main 那一個 declaration 會透過迴圈 render 多顆 subsystem tiles。

ClickInstrumentation 雖然把 listener 掛在 document，但收到 click 後仍要找到 configured tracking attribute 才會送：

Browser click
  │ bubbles to document
  ▼
ClickInstrumentation
  │ starts at event.target
  ▼
closest('[data-link-name]')
  ├── found     → { link_name: value } → pushEvent('click', ...)
  └── not found → empty payload        → stop

所以「Browser 看到了 click」和「Faro 送出一筆有業務語意的 click telemetry」不是同一件事。

7. 這跟 tablet / desktop 的原始需求怎麼接起來？

這個學習案例的產品問題是：Foreman 正在推動平板化，希望知道使用行為裡 tablet 與 desktop 的比例。

這時要分清兩條資料：

這次操作是哪個功能？
→ click payload.link_name

這次 telemetry 的當下輸入分類？
→ meta.device.type

Device detection 不是等到 data-link-name click 才啟動。Foreman 初始化時開啟 enableDeviceTypeDetection；package 維護目前 device type，並透過 Faro meta provider 提供背景資料。

目前 implementation 的 device type 也不是永久硬體類別：初始值看 maxTouchPoints；之後 pointerType='mouse' 會更新為 desktop，pointerType='touch' 會更新為 tablet。更精確地說，它表示「目前最近一次可辨識的輸入型態」。

8. 為什麼只追主要入口，仍可能足以回答 KPI？

如果產品 KPI 真正問的是：

使用者進入 Foreman 的主要功能時，是使用 tablet 還是 desktop？

那 subsystem entry 是一個穩定的 observation point：

user = A123
link_name = DailySchedule
device.type = tablet

此時不必把每個 Submit、Cancel、Dropdown 都標上 data-link-name，也能統計「被追蹤的主要功能入口」使用何種 device。

但不要把指標說大了
如果分母是這些 tracked feature-entry events，得到的是「主要功能入口事件的 tablet / desktop 分布」。它不自動等於「所有 Foreman sessions 的裝置分布」、也不等於「所有 user 的裝置分布」。分母必須先定義。

9. 電腦與平板切換：真正可能漏掉的是 signal，不是 device context 被鎖死

同一個 user 在電腦與平板各開一個 Foreman browser，會是兩個不同 browser runtime，各自維護自己的 device state。平板不會因為電腦先送過 click，就永久被算成 desktop。

真正的 coverage 問題是：

平板上後續有沒有產生「你拿來當 KPI 分母」的可靠 telemetry signal？

如果 KPI 只統計有 data-link-name 的 feature-entry clicks，而使用者已經停在某個功能頁、之後只按未標記的 Submit，那些操作不會靠目前的 ClickInstrumentation 形成新的 link_name event。這表示 clickstream coverage 有限；不表示 device detector 不再工作。
