CORS 與 Preflight

Reference · 從 Browser request options，一路對到 Alloy / FastAPI receiver 的 CORS 設定

← 回到 Lesson 5：Faro Browser-to-Alloy Transport

最短版本
CORS 全名是 Cross-Origin Resource Sharing。它不是「讓 request 可以送出去的 client library」，而是 Browser 執行的一套跨 origin 存取規則。當 request 不符合簡單請求條件時，Browser 可能先自動送 OPTIONS preflight，問 server：「我等等想用這個 method、帶這些 headers，你允許嗎？」

1. 先建立整條因果鏈

Faro / page code
  │ decides actual request
  │ method = POST
  │ headers = Content-Type, X-Faro-Session-Id, traceparent ...
  ▼
Browser
  │ sees cross-origin request
  │ decides whether preflight is required
  ▼
OPTIONS /alloy
  │ Origin
  │ Access-Control-Request-Method: POST
  │ Access-Control-Request-Headers: ...
  ▼
receiver / gateway
  │ answers CORS policy
  ▼
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
  │
  ├─ allowed     → Browser sends the real POST
  └─ not allowed → Browser blocks before the real POST

所以最重要的責任邊界是：

誰負責什麼
Faro / JavaScript決定真正想送的 request：URL、method、body、request headers 等。
Browser判斷是不是 cross-origin、是否需要 preflight，並自動產生 CORS preflight headers。
Receiver / Gateway用 response headers 宣告自己允許哪些 origin、method、headers。

2. 「Exporter / options 可以設定什麼？」先分成兩層

如果你是在想 Browser 端的 request options，可以先用一般 fetch() 建立 mental model：

fetch(receiverUrl, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Faro-Session-Id": "...",
    "traceparent": "..."
  },
  body: "...",
  mode: "cors",
  credentials: "omit"
})

這些設定會影響 Browser 最後需要做什麼，但你通常不自己寫 preflight request。

Client request 設定對 Preflight 的影響
methodBrowser 可能把它寫成 Access-Control-Request-Method。
headers需要事先詢問的 header 名稱，會出現在 Access-Control-Request-Headers。
Content-Type某些值不屬於 CORS safelisted content type，會使 request 需要 preflight。
credentials如果要帶 Cookie / HTTP credentials，server 的 CORS policy 也必須允許 credentials，而且 origin wildcard 會受到限制。
mode: "cors"告訴 Fetch 依 CORS 規則處理；它不會替你「繞過」CORS。
不要手動塞這些 header
Origin、Access-Control-Request-Method、Access-Control-Request-Headers 是 Browser CORS 機制的一部分。正常的 Browser fetch() 流程中，是 Browser 依真正 request 自動產生，不是 Faro exporter 自己硬塞一份 preflight protocol。

3. Preflight request 到底在問什麼？

以目前 Faro → /alloy 的驗證條件為例，概念上 Browser 會問：

OPTIONS /alloy HTTP/1.1
Origin: https://some-frontend.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,x-faro-session-id,traceparent

翻成白話就是：

「我是從這個 origin 來的。我等等想用 POST，而且 request 會帶這三種 headers。你允許嗎？」

OPTIONS 本身不是 telemetry POST。它只是 Browser 在真正 request 前做的能力詢問。

4. Receiver 的 CORS response 怎麼跟 request 一一對上？

你目前驗證到 stage / prod 回：

HTTP 204
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers:
  content-type,x-faro-session-id,traceparent

可以直接逐欄對：

Browser 問Server 回意思
Origin: https://...Access-Control-Allow-Origin: *這個 response 表示目前允許任意 origin。
Access-Control-Request-Method: POSTAccess-Control-Allow-Methods: POSTServer 表示真正 request 可以使用 POST。
Access-Control-Request-Headers: ...Access-Control-Allow-Headers: ...Server 表示真正 POST 可以帶這些 request headers。

HTTP 204 在這裡只代表 OPTIONS response 沒有 body 且 request 本身成功處理；真正決定 Browser 能不能繼續的，是 CORS response headers 是否符合它剛才問的條件。

很重要：Preflight 成功 ≠ telemetry 成功
Preflight 通過，只代表 Browser 被允許「接著嘗試 POST」。POST 可能仍然得到 4xx / 5xx，也可能成功進 Alloy 後在後續 pipeline 出問題。

5. 常見 CORS response headers

Response header回答什麼問題
Access-Control-Allow-Origin哪些 origin 可以讓 Browser 使用這個 response。
Access-Control-Allow-MethodsPreflight 後允許真正 request 使用哪些 HTTP methods。
Access-Control-Allow-Headers真正 request 可以帶哪些 request headers。
Access-Control-Allow-Credentials是否允許帶 credentials 的跨 origin request。
Access-Control-Max-AgeBrowser 可以把這次 preflight 結果 cache 多久。
Access-Control-Expose-Headers哪些 response headers 可以讓 page JavaScript 讀到。

Allow-Headers 和 Expose-Headers 很容易搞混：

Allow-Headers
  → client 在 request 裡「可以送哪些 header」

Expose-Headers
  → server response 回來後，JavaScript「可以讀哪些 response header」

6. Alloy otelcol.receiver.faro 的 CORS 可以怎麼設？

Grafana Alloy current documentation 的 otelcol.receiver.faro 提供 cors block：

otelcol.receiver.faro "frontend" {
  endpoint = "0.0.0.0:12347"

  cors {
    allowed_origins = ["https://my-webapp.example.com"]
    allowed_headers = ["X-Faro-Session-Id", "traceparent"]
    exposed_headers = []
    max_age         = 3600
  }

  output {
    logs   = [...]
    traces = [...]
  }
}
Alloy setting大致對應
allowed_originsAccess-Control-Allow-Origin
allowed_headersAccess-Control-Allow-Headers
exposed_headersAccess-Control-Expose-Headers
max_ageAccess-Control-Max-Age

目前官方文件列出的 otelcol.receiver.faro.cors 參數裡，沒有獨立的 allowed_methods 設定。因此不要預期在這個 block 裡找到：

allowed_methods = ["POST"]   # current otelcol.receiver.faro docs 沒有這個欄位

你目前 runtime 實際觀察到的 preflight response 是 Access-Control-Allow-Methods: POST。這是 endpoint 實際 CORS response 的證據；如果要理解它是 receiver implementation 如何產生，就要再往 Faro receiver 的 HTTP handler / upstream implementation 查，而不是憑空假設 Alloy 有一個沒文件化的 allowed_methods field。

另外，Alloy 文件指出 Content-Type 等部分 headers 會被 CORS helper 隱含允許；allowed_headers = ["*"] 則代表允許所有 headers。你的 2026-09-12 runtime evidence 記錄目前 stage/prod receiver 的 origins / headers 是 permissive *。

7. Client request 和 Alloy CORS 設定怎麼對照？

真正 POST 想做的事
────────────────────────────
method: POST
headers:
  Content-Type
  X-Faro-Session-Id
  traceparent

         │ Browser derives preflight
         ▼
OPTIONS
Access-Control-Request-Method: POST
Access-Control-Request-Headers:
  content-type,x-faro-session-id,traceparent

         │ receiver checks policy
         ▼
Alloy cors {
  allowed_origins = [...]
  allowed_headers = [...]
}

         │ receiver answers
         ▼
Access-Control-Allow-Origin: ...
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: ...

也就是說，不是 client 和 receiver 各自寫一份完全相同的 CORS 設定。Client 定義「我真正想送什麼」；Browser 把需求翻成 preflight；receiver policy 再回答「我允不允許」。

8. FastAPI 裡通常怎麼做？

FastAPI 通常使用 CORSMiddleware：

from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],
    allow_methods=["POST"],
    allow_headers=[
        "Content-Type",
        "X-Faro-Session-Id",
        "traceparent",
    ],
    allow_credentials=False,
    expose_headers=[],
    max_age=600,
)

這裡就可以看到比 Alloy otelcol.receiver.faro 更直接的 mapping：

FastAPI CORSMiddleware控制的概念
allow_origins允許哪些 Browser origins。
allow_methods允許哪些 cross-origin HTTP methods。
allow_headers允許 client request 帶哪些 headers。
allow_credentials是否允許 credentials。
expose_headers哪些 response headers 可被 Browser JavaScript 讀取。
max_agepreflight 結果可 cache 多久。

9. FastAPI / API Server 實務上要注意什麼？

  • CORS 不是 authentication / authorization。允許某個 origin，不代表那個 caller 已經通過身分驗證或有 API 權限。
  • CORS 主要是 Browser enforcement。curl、server-to-server client 不會因為缺 CORS header 就被 Browser 擋，因為根本沒有 Browser 在中間執行這套限制。
  • 不要無腦 *。如果服務只應該被少數前端使用，明確列出 origins 比全部開放更容易控制。
  • credentials 和 wildcard 要特別小心。FastAPI 官方文件明確指出，當 allow_credentials=True 時，origins / methods / headers 不能全部直接使用 wildcard，必須明確指定。
  • Ingress / reverse proxy 可能也會碰 CORS。最後 Browser 看到的是整條 HTTP path 最終回覆的 headers；如果 gateway 增刪 CORS header，你只看 FastAPI / Alloy application config 可能會誤判。
  • Preflight cache 會讓你覺得「怎麼沒有 OPTIONS」。如果之前的 preflight 還在 cache，有些後續 request 不一定每次都重新發 OPTIONS。

10. 用你目前的 /alloy evidence 練一次

Browser 想要：
  POST /alloy
  Content-Type: ...
  X-Faro-Session-Id: ...
  traceparent: ...

你主動驗證的 OPTIONS 問：
  Method = POST
  Headers = content-type,x-faro-session-id,traceparent

stage / prod 回：
  204
  Allow-Origin: *
  Allow-Methods: POST
  Allow-Headers: content-type,x-faro-session-id,traceparent

因此截至 2026-09-12，你可以下的結論只有：

這兩個 endpoint 對這組 preflight 條件回覆「允許」。

你還不能把它推成：

真實 Faro POST 已成功進 Alloy，或 Alloy 後續 pipeline 已成功。

11. Debug 時照這個順序看

1. DevTools Network 找 OPTIONS
   │
   ├─ Request Origin 對嗎？
   ├─ Access-Control-Request-Method 對嗎？
   └─ Access-Control-Request-Headers 有哪些？

2. 看 OPTIONS response
   │
   ├─ Allow-Origin 有匹配嗎？
   ├─ Allow-Methods 包含真正 method 嗎？
   └─ Allow-Headers 包含真正要送的 headers 嗎？

3. Preflight 通過後，再找真正 POST
   │
   ├─ POST 有沒有真的出現？
   └─ POST response status 是什麼？

4. POST 這一段成功後
   │
   └─ 才往 Alloy 收到資料後的 pipeline 查
把 Lesson 5 原本的「fault domain」換成人話
Browser 把 HTTP request 成功送到 /alloy，只證明「Browser → Alloy HTTP endpoint」這一段成功。Alloy 收到後能不能解析、batch、再送 Collector，是下一段問題。前一段成功，不代表後一段成功。

Recap

  • CORS = Cross-Origin Resource Sharing。
  • 真正 request 的 method / headers 來自 client；是否需要 preflight 是 Browser 決定。
  • Preflight 是 Browser 自動送的 OPTIONS，不是 telemetry POST。
  • Access-Control-Request-* 是 Browser 的問題；Access-Control-Allow-* 是 server 的回答。
  • Alloy otelcol.receiver.faro current CORS block 可設定 origins、headers、exposed headers、max age；官方 current docs 沒有獨立 allowed_methods field。
  • FastAPI CORSMiddleware 則可以直接設定 origins、methods、headers、credentials、exposed headers、max age。
  • Preflight 成功只代表 Browser 可以繼續真正 request，不代表 telemetry pipeline 已成功。
