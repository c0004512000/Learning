Faro tracing ownership 與 propagation 邊界

Internal package → Faro → OpenTelemetry：service.name 的產生與 traceparent 的傳遞

一句話版本
@sre2/faro-click-tracking 沒有自己實作 W3C propagation。它負責把 host 的 backendUrls 設定交給 Faro；Faro 負責把 tracing 元件接起來；真正提供 W3CTraceContextPropagator、Fetch instrumentation 等底層能力的是 OpenTelemetry。

1. 先看完整三層 ownership

最重要的 boundary
Internal package 是「幫你配置」；Faro 是「把元件接起來」；OpenTelemetry 是「提供真正的 tracing / propagation primitives」。不要把三層都叫成「Faro SDK 自己做的」。

2. app.name 是怎麼變成 service.name 的？

先用已知的應用設定 app.name = "idp-portal" 開始。OpenTelemetry 除了儲存每個 operation 的 Span，也需要描述「產生這些 spans 的服務」；這份服務層級的資訊稱為 Resource，其中一個欄位是 service.name。

誰做的？公司 SDK 把 app config 傳給 Grafana Faro 並啟用 tracing；Grafana @grafana/faro-web-tracing 讀取設定、指定 Resource attribute；OpenTelemetry 提供 Resource 與 WebTracerProvider。Faro v2.8.2 的實際程式碼是：

if (this.config.app.name) {
  attributes[ATTR_SERVICE_NAME] = this.config.app.name;
}
Object.assign(attributes, options.resourceAttributes);
const resource = defaultResource().merge(
  resourceFromAttributes(attributes)
);
const provider = new WebTracerProvider({ resource, /* ... */ });

ATTR_SERVICE_NAME 對應標準屬性鍵 "service.name"。上面的指定直接保留原字串；預設不改大寫、小寫、句點或連字號，例如 IDP.Portal 不會因此變成 IDP-Portal。

精確的成立條件
  • app.name 必須有值，Faro 才會走這段指定。
  • 接著才執行 Object.assign(attributes, options.resourceAttributes)；若低階 Faro tracing option 明確提供同名 service.name，就可能覆寫。這不代表公司內部 SDK 已公開這個 option。

四種名稱／ID，不要混在一起

資訊所在位置作用
service.namefrontend OTel Resource這些 frontend spans 屬於哪個應用／服務。
traceId / spanIdSpan tracing context區分整條 trace 和個別 operation。
traceparentBusiness HTTP request header跨 Browser/backend 傳 trace ID、parent ID 與 flags；不含 service name。
Grafana Dashboard Job另一條 release / Dashboard 流程查詢要篩哪個名字；Faro 不會自動建立或同步 Job。

同一條 distributed trace 的 frontend 和 backend 可以有不同的 service.name。它們靠 trace ID 與 span parent 關係串接，而不是靠服務名稱相同。Loki 的 service_name 則是 downstream logs 的查詢 label，不能說是同一行 Resource 指派。

Production case｜Trace 存在，Dashboard 卻找不到
IDP Portal 的 runtime evidence 記錄 app.name="idp-portal"，但 Dashboard Job 選的是 IDP-Portal。應先用 exact trace ID 在 Tempo 找 frontend Resource，核對 service.name 與 Dashboard filter 是否相符；不能看到空結果就認定 tracing 失敗。Lesson 8 實務驗證 →

3. 設定階段：這時候還沒有任何 request

先把 runtime request 拿掉，只看初始化。

host application
  │
  │ initFaro({ backendUrls })
  ▼
internal package
  │
  │ backendUrls
  │        maps to
  ▼
propagateTraceHeaderCorsUrls
  │
  │ passed into
  ▼
Faro TracingInstrumentation
  │
  ├─ register W3CTraceContextPropagator
  └─ register Fetch / XHR instrumentation

到這一步只是把 tracing runtime 準備好。還沒有產生 traceparent，因為真正的 business request 還沒發生。

4. Request 發生時：traceparent 到底怎麼被放進 header？

所以「傳遞」不是把 Browser span object 傳去 backend。真正跨網路的只有序列化後的 header value；backend 再從 header 還原 parent context。

5. 到底是誰「寫」traceparent？

元件是不是實際負責內容？責任
@sre2/faro-click-tracking不是提供 backendUrls，把設定映射到 Faro tracing options。
TracingInstrumentation（Faro）不是自己手刻 header註冊 provider、propagator、HTTP instrumentations，完成 wiring。
Fetch / XHR instrumentation觸發 propagation攔截 outbound request、建立/管理 HTTP span，並在符合設定時讓 propagation 對 request carrier 注入 context。
W3CTraceContextPropagator（OpenTelemetry）是，負責 W3C 格式序列化把目前 SpanContext 轉成 traceparent 等 propagation fields，寫入 carrier。

因此最精確的說法是：

Faro 把 OpenTelemetry 的 HTTP instrumentation 與 W3C propagator 接起來；HTTP instrumentation 在 outbound request 時使用 propagation 機制，而 W3C propagator 負責把目前 SpanContext 序列化成標準 header。

6. backendUrls 到底控制什麼？

backendUrls
   │
   │ internal package maps to
   ▼
propagateTraceHeaderCorsUrls
   │
   │ controls
   ▼
哪些 cross-origin business request
允許被加入 trace context headers

它不是：

  • 不是 trace ID generator。
  • 不是 traceparent serializer。
  • 不是 Alloy / Faro receiver URL。
  • 不是 backend extraction 設定。

它的責任很單純：告訴 browser HTTP instrumentation，哪些 target URL 可以參與 cross-origin trace-header propagation。

7. 為什麼一定要把 propagation 與 telemetry export 畫成兩條線？

Path A — Business request / context propagation

Browser client span A
   │
   │ HTTP request header: traceparent = 00-T-A-...
   ▼
Backend API
   │
   └─ creates backend span B in trace T, parent = A


Path B — Telemetry export

Browser span A
   │
   └─ Faro transport → receiver / Alloy / Collector → Tempo

Backend span B
   │
   └─ OTLP → Collector → Tempo

Path A 決定 frontend 與 backend 是否知道彼此的 parent relationship。Path B 決定那些 spans 最後有沒有被觀測系統收到。

所以 request 裡看到 traceparent，不等於 Tempo 一定會看到完整 trace；反過來，兩邊都有 spans，也不代表它們一定被串成同一條 trace。

8. 一張表記住 ownership

問題主要 owner
Application 要怎麼宣告哪些 backend 要 propagation？Internal package 的 backendUrls API

9. Source evidence

這個 ownership 不是從 package 名稱猜出來的，而是直接從 source chain 切分：

  • Internal package evidence：backendUrls 只被映射到 propagateTraceHeaderCorsUrls。
  • Grafana Faro v2.9.0 TracingInstrumentation：建立 WebTracerProvider、register W3CTraceContextPropagator、把 propagation URL options 傳入 default instrumentations。
  • Grafana Faro default instrumentations：建立 FetchInstrumentation 與 Faro XHR instrumentation。
  • Grafana Faro v2.9.0 dependencies：直接依賴 OpenTelemetry API、core、web tracer provider、Fetch/XHR instrumentation packages。
  • Lesson 7 propagation evidence：整理前後端 context propagation 與 telemetry export 的 evidence boundary。
看到問題時怎麼定位
如果 traceparent 根本沒出現在 business request：先查 frontend instrumentation / URL matching / propagation。若 header 已存在但 backend trace ID 不同：查 backend extraction。若 relationship 正確但 Tempo 缺 span：再查 export pipeline。
