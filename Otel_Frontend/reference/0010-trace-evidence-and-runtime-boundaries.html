同一個 business request 可以帶出 traceparent，稍後又在 /alloy 出現 event 與完整 span。它們不是重複的 HTTP 操作，而是同一筆活動在不同觀察位置留下的資料。

來源：2026-10-22 匯出的主線對話及 獨立核查與限制。對話中的歷史 runtime 報告不等於本次重新查詢了內部 Grafana。

1. 先辨認這包資料是什麼

欄位回答什麼判讀邊界
meta應用、頁面、session 等背景。不是 span，也不是每個部署都必有 user 欄位。
events發生了什麼事件，包含 name、時間與 attributes。tracing event 與 resource-performance event 不是相同資料。
logsLog records。console/error 最終如何映射，要看實際 instrumentation 與 payload。
exceptions例外資料，例如型別、訊息與 stack。不要把 exceptions 陣列和 logs 陣列當同一欄位。
measurements數值量測，例如 Web Vitals。有數值不表示這包包含 distributed trace。
traces匯出的 OpenTelemetry span 資料。往 resourceSpans／scopeSpans／spans 找真正的 span。

這是欄位分類，不是宣告應用啟用了所有功能。沒有 traces 的 batch 可能完全正常；faro.performance.resource 不能替代 backend child span 的證據。

events[i].trace
  trace_id + span_id
  → 這個 event 關聯到哪個 span

traces.resourceSpans[*].scopeSpans[*].spans[*]
  traceId、spanId、parentSpanId、kind、時間、attributes…
  → span 本身的觀測資料

單數 trace 是關聯資訊；複數 traces 是 span 資料容器。並非每個 event 都必有 trace 關聯。要確認是同一個 span，必須比對實際 ID，不能只因同一 body 同時有這兩個 key 就宣稱吻合。

結構可對照 Faro transport types與既有 mixed batch evidence。

2. 一個 Span ID，在上下游有不同角色名稱

00-3295c1225c7a9afdc7ce066a20e0503a-6ac9514f41c5b99d-01
│  │                                │                │
版本 整條 trace 的 ID                 上游 span 的 ID   flags

W3C version 00 的正式欄位名依序是 version、trace-id、parent-id、trace-flags。Trace ID 為 32 位 hex；parent-id 為 16 位 hex，兩種 ID 都不能全零。

Browser span A
  spanId = 6ac9514f41c5b99d
  │ 把 A 放進 outgoing header 的 parent-id
  ▼
Backend span B（直接接續且沒有中間 span 的例子）
  spanId       = 後端自己的新 ID
  parentSpanId = 6ac9514f41c5b99d
  traceId      = 與 A 相同

因此「上游 Span ID」與 header 的「parent-id」不矛盾：前者說這個值屬於誰，後者說它在傳輸格式中的角色。01 表示 sampled bit 已設定，不保證 export、接收、保存或保留期限內查詢都成功。

W3C Trace Context；完整查表與 sampler 問答見 Reference 0006。

3. 把三個觀察串成一段有邊界的說明

Business request 的 traceparent = T / A
  │ ID 比對
  ├─ Faro event.trace = T / A
  └─ 匯出的 Browser span = T / A
       │ 再到 Tempo 核對
       ▼
同 trace T 的 Backend span B
  parentSpanId = A（直接 parent 的情況）

前三個觀察支持「Browser 建立 context、帶入業務 request，並在 telemetry 中送出相關資料」。最後一個觀察才支持「Backend 接續了這個上游 context」。Browser 可以看到自己產生的 spans 及其中的 parent 欄位，但一般不會從自己的 /alloy payload 看到後端獨立匯出的 server span。

若中間有已插樁的 gateway／proxy，Backend 的直接 parent 可以是中間 span，不必直接等於 A；此時要逐段驗證同 trace 的 ancestor chain。單看時間接近、相同 Trace ID 或 UI 顏色，都不等於已證明直接父子關係。

4. 用產生資料的 Runtime 判斷前後端，不用顏色

先找 span 所屬的 Resource，也就是描述產生資料之服務與執行環境的共同屬性，再看 instrumentation scope 與 span 的操作角色。

Resourceprocess.runtime.name = browser；telemetry.sdk.language = webjs；Faro distro。telemetry.sdk.language = dotnet；另有 container／Kubernetes 部署屬性。

CLIENT 是這次 operation 的呼叫角色，不是「前端」的同義詞。後端呼叫其他服務也會建立 CLIENT span。UI 的顏色沒有「黃色必為 frontend」這種 Trace Context 語意；主線對話也記錄了不同服務顏色相同的觀察。判讀分界要回到資料來源與呼叫關係。

5. Parent 欄位未顯示時，查原始 Trace 資料

某些 Grafana detail view 只顯示 Span ID。Tree 的縮排表達關係，但要直接做等號比對，需使用可取得的 trace 匯出資料或該 datasource 的 query API。UI 按鈕與 API 路徑依版本／部署而異；本次沒有重新驗證內部介面，不編造按鈕位置。

主線對話記錄的歷史 Trace fd778573afcedbadfb854d68716708cf 有以下摘錄：

Portal CLIENT
  spanId = "WdMbrwohow0="

Keychain SERVER
  spanId       = "k6tmuVMYCm8="
  parentSpanId = "WdMbrwohow0="

這份摘錄支持直接比較兩個相同字串；但原始 API 回應未隨附件提供，所以它是對話報告的案例，不是本次新捕捉的 runtime evidence。

Base64 WdMbrwohow0= → bytes → hex 59d31baf0a21a30d
Base64 k6tmuVMYCm8= → bytes → hex 93ab66b953180a6f

上述轉換已做離線核對。不要把「JSON ID 一律是 Base64」當規則：一般 Protobuf JSON bytes 可用 Base64，但 OTLP/JSON 對 trace/span IDs 採 hex。先確認來源與表示法，再以相同 bytes／hex 比對；不能對已是 hex 的 ID 又做 Base64 decode。

OTLP JSON Protobuf Encoding；既有完整 Browser／Tempo 範例與截圖請回 Lesson 8。

6. 分清「沒有觀測證據」與「確定沒有發生」

觀察下一步與限制
操作後才開 Network。Preserve log 不能補回未記錄的 request。從有界時間窗、service、method、URL 找候選，保留關聯強度的限制。
Dashboard Job 選了前端但沒有結果。檢查 time range、大小寫、duration 單位、method、URL、namespace 與 panel 實際 query；不是自動判定 propagation 失敗。
後端 span 看起來沒有 parent。只能先描述儲存資料；缺少原 request／完整 trace 時，不能只靠它斷言 Browser 沒送 header。
舊分頁失敗，重新載入後成功。支持優先核對實際載入版本與初始化狀態；沒有 bundle／runtime 證據，不能宣稱已唯一定位根因。
POST /alloy 回 202。是 HTTP 接收結果，不是 Tempo／Loki 可查詢或長期保存保證。
長 trace 有多個慢 child spans。先看起訖與重疊，不直接相加。最長 downstream call 是候選瓶頸，不是僅憑一個 duration 就證明根因。

原紀錄中的 41 秒案例 Trace ID 字串只有 31 位，不符合本課採用的 32 位 W3C 表示；未取得原始回應前不自行補零或猜字元，也不據此判定當時查詢必然失敗。其他歷史 Trace 也可能已超過 retention；查不到舊例子不等於目前平台故障。

安全的重現方式
優先使用唯讀 request、已核准的測試環境或隔離測試。單次 abort 不保證後續 interceptor／OAuth retry 不會送出另一筆寫入；不可把「預計攔截」當作「一定不建立 Credential」的保證。本教材不要求對真實資料重播建立／刪除操作。

7. 跨來源傳播需要允許實際 Request 的條件

同源由 scheme、host、port 判斷；同源 request 不需要 CORS 授權，但仍需要 instrumentation 與 propagation 正常運作。跨來源加入 traceparent 這種非 safelisted request header 時，需要通過適用的 preflight；若已有有效 preflight cache，Network 不一定每次出現新的 OPTIONS。

既有合法的 ASP.NET Core CORS policy 要接受一個跨來源的 JSON POST，且實際只有 Content-Type 與 traceparent 這兩個相關 request headers 時，可對照：

// Policy 內容範例；仍須註冊並套用到正確 endpoint。
policy
    .WithOrigins("https://frontend.example.com")
    .WithMethods("POST")
    .WithHeaders("Content-Type", "traceparent");

這不是完整 Program.cs。實際有 Authorization、credentials 或其他 headers，必須保留並依需求一併允許；不要用只剩 traceparent 的 WithHeaders 覆蓋原有清單。Access-Control-Expose-Headers 則控制 JavaScript 可讀的 response headers，不能替代 request header 的允許設定。

traceparent 足以承載這個基本 parent 關係；tracestate 用於額外 tracing-system state，不是每筆都必有。但實際 propagator 會送出 tracestate 時，就應按需要允許並保留，不應因簡化範例而全面移除。baggage 也不是本案例必填。

Cross-origin safelisted（常稱 simple）request 可以不先 preflight，response 仍受 CORS 讀取限制。因此「沒有 OPTIONS」不等於「沒有 CORS」。業務 API 的 CORS 與 collector /alloy 的 CORS 是兩個 endpoint 的契約，不能混用。

ASP.NET Core CORS、MDN CORS。前置概念見 Reference 0004。

Recap

  • meta 是背景；event.trace 是關聯；traces 裡才是完整 spans。
  • Header parent-id 承載上游 spanId；下游另建自己的 spanId。
  • Frontend／Backend 看 Resource、已知部署與 scope；CLIENT／SERVER 看操作角色。
  • 直接 parent equality 與經 proxy 的 ancestor chain 是不同驗證形態。
  • 原始 JSON 的表示法先辨認再轉換；歷史對話不能冒充本次 runtime capture。
  • 查詢空白、未錄到 header、HTTP 202 與 sampled flag 都有各自的證據上限。
  • CORS 允許真實 request 的 origin、method、headers；traceparent-only 片段不是完整應用設定。

實作練習請回主課，依同一筆 request 的 ID 一步一步比對；遇到無法支持的結論，先保留未知並向教學 agent 提供實際 evidence。
