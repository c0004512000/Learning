Grafana Faro & Alloy - 前端可觀測性

Confluence page ID: 2179628714 · Source: https://confluence.garmin.com/pages/viewpage.action?pageId=2179628714

Grafana Faro 概述

  • 是一個用來觀察使用者瀏覽器發生甚麼事情的工具
  • 對於已經使用 Grafana 全家桶的整合性是最好的。
  • 是 Grafana 的前端可觀測性 SDK 與資料蒐集機制，部署在 Web Application，從真實使用者的瀏覽器蒐集效能, 錯誤, log, 使用者事件等等。
  • 要將 Faro Web SDK 嵌入前端應用程式 (ex. React, Vue .etc)
  • 透過 Grafana Alloy faro.receiver 接收與轉送

涵蓋範疇

  1. 效能監控(Performance Monitoring)
    1. Web Vitals
    2. Real User Monitoring (RUM)
    3. 資源載入時間
  2. 錯誤追蹤(Error Tracking)
    1. API 請求失敗、資源載入失敗(404、CORS)
  3. 使用者行為與 Session
    1. 重播使用者操作路徑, 協助重現 bug

Instrumentation

Faro Web SDK 透過 Instrumentation 在前端收集數據, 可以把 Instrumentation 想像成插件, 主要用來記錄收集重要的操作 ex. HTTP request, log, error

這些數據會透過 HTTP request 傳送到 Grafana Alloy, 會將數據分成以下幾種:

  1. logs
  2. exceptions
  3. events
  4. measurements
  5. meta

Transports

負責把上述收集到的資料 ex. logs, events 實際送出去的元件, 負責提交 Faro Web SDK 收集到的資料, 可以同時設定多個 transport

  1. FetchTransport (預設)
    用 fetch API 把資料送到遠端 endpoint. 類似於 sendBean API, 在頁面關閉後還可以持續存活
  2. ConsoleTransport
    直接在 console 內列出, 適用於開發者除錯時使用

Metas

Faro 會將 metas 附加在每一筆被收集的資料上, 只有 App meta 必填, 但通常會再添加 Session meta & User meta
Session Meta

  • 負責把收集到的資料與目前的 faro session 綁定, 一次 session 定義為單次網頁存取

User meta

  • 可包含 user name, email, user ID
NoteSession meta 和 user meta 可以用來查詢某個特定 session 或使用者所產生的全部資料


透過 pushEvent 傳遞的資料會在 otel.receiver.faro 被添加 "event_data_" 前綴

  • 會被自動添加 event_data_ 的原因是因為 faro.api.pushEvent 傳遞的 attributes 是完全客製化命名, 為了避免命名重疊導致覆蓋掉既有的值, 因此添加前綴避免命名衝突的問題
  • 不只 pushEvent 傳遞的資料會被添加 event_data_ 前綴, 也不是只有 event_data_ 這個前綴, 更多的欄位名稱命名可以查看 https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/pkg/translator/faro/logs_to_faro.go#L104

如何實現前後端串接

Background

Faro 提供 Instrumentation, 負責決定蒐集哪些資料 (ex. Tracing Instrumentation 負責蒐集前端 Span, traceparent Trace Context 的傳遞), 是一個負責攔截與產生特定類型遙測資料的功能模組, 預設是關閉的, 因為會產生大量資料, 可能會影響效能, 底層是使用 OTel Instrumentations, 詳細可看Faro Instrumentation

實現方法

  • 透過 W3C Trace Context, 注入 traceparent header → Faro TracingInstrumentation 把當前 span context 注入到 HTTP header.
  • 後端透過此 header 得知要使用哪一個 trace_id 接續 span → 由 OTel AspNetCoreInstrumentation 解析
  • 可以參考範例 前後端 Trace 串接範例


Note

若不添加 traceparent, 後端會獨自創建 traceId, 變成不會去套用前端的 traceId, 等於無法將前端請求進到後端服務的完整流程記錄起來。

若前後端不同源, 需要建立 CORS policy, 以及 allow header, 因為 traceparent header 屬於自建的 header, 後端需要允許該 header


Granafa Alloy

  • 就是 Grafana 版的 OTel Collector, 若將 OTel Collector 升級到 v0.133.0+, 可以穩定支援 faro receiver, 即不需要使用 Alloy Server.
  • Alloy 的底層就是 OTel Collector, OTel Collector 有的 Alloy 也有
  • 各環境Otel collector 版本可以參考 升級 Otel Stack

特點

Alloy UI

  • 可以藉由 Graph 功能查看整個資料流的 Pipeline
  • 目前沒有設定 virtual service 將 Alloy UI 暴露, 暫時只能透過 port forward 到 localhost, ex. http://localhost:12347/alloy
  • 提供給開發者視覺化的工具
