filter processor

Note是 OTel Collecotr 裡的一個元件, 當資料流過時, 符合某個條件的就會被 「丟棄」, 要注意不是留下來, 是資料被丟掉

 configuration 說明

filter/only_foreman_assistant:
  logs: # 說明這個 filter 只作用在 logs
    log_record: # 意思是要對每一筆 log 去做判斷
      - 'resource.attributes["service.name"] != "foreman-assistant"' # 去讀這筆 log 附帶的 resource 內 service.name 這個 key 的值, 若值不是 foreman-assistant 就丟掉
  • 若只想要特定服務的log流到 OpenSearch, 需要設定 filter
  • 可以參考 tw-stage filter processor 設定
  • 更多其他的 filter processor 可以參考 filter processor configuration

transform processor

  • 根據自定義的規則將資料做處理

將 body 攤平在 opensearch document

  • 當前 log body 對於 OpenSearch 而言, 無法使用 filter 讀取 body 內的 key-value, 會將 body 視為 key, body 內的資料都是 value, 儲存的格式是 TEXT
  • 為了要解決此問題, 因此添加 transform processor 將 body 複製一份後攤平, 讓 OpenSearch 可以 filter key.
  • 可以參考 tw-stage transform/opensearch_body

 configuration 說明

processors:
  transform/opensearch_body:
      error_mode: ignore # ignore 代表有錯誤的話 log 還是照樣往下一步走
      log_statements: # 代表這組規則只作用在 logs
        - context: log # 在每一筆 LogRecord 運作, 底下的設定都是運作在一筆 log 內, 不用寫成 ex. log.body, log.attributes
          statements: 
            - merge_maps(attributes, ParseKeyValue(body), "upsert") where IsString(body)

語法

說明
body一整串文字(TEXT), 長得像 key1=value1 key2=value2
ParseKeyValue(body)

把上述文字拆開, 變成一個 map, ex.  

{key1: "value1", key2: "value 2"}
merge_maps(A,B, 操作)把 B 的內容合併進 A 裡, 套用在 transform/opensearch_body 的設定, 意思是把 ParseKeyValue(body) 的結果合併進 attributes 底下
attributes合併的目標
upsert合併的策略, 遇到同名欄位就覆蓋、沒有就新增(update + insert 的合體), 可以想像成 RESTful API 的 PUT method.
IsString(body)只有 body 現在的型別確實是字串時,才執行這句話;不是字串就跳過,避免出錯

若有興趣了解更多的 configuration 可以參考 otel transform processor

Before

  • 將 body 作為 key, 其餘的都塞成 value, 導致無法在 filter 內看到原先在 body 內的 key

After

  • 將 body 攤平在 attributes 底下, 可以藉由 filter 篩選值
  • 並且原先的 body 也會保留
  • 可以到 OpenSearch Dashboard → Discover 查看

transform processor (v0.101.0)

processors:
  transform/opensearch_event_data:
    error_mode: ignore
    log_statements:
      - context: log
        statements:
          # ===== 步驟一：body → attributes（攤平）=====
          # 把 logfmt 字串解析出來，upsert 進 attributes 最上層
          - merge_maps(attributes, ParseKeyValue(body), "upsert")

          # ===== 步驟二：attributes → attributes["event_data"]（重新分組）=====
          # 2-1 先準備空的巢狀箱子
          - set(attributes["event_data"], ParseJSON("{}"))

          # 2-2 逐一搬移 + 刪除舊 key
          - set(attributes["event_data"]["link_name"], attributes["event_data_link_name"]) where attributes["event_data_link_name"] != nil
          - delete_key(attributes, "event_data_link_name")

          # 之後 faro-click-tracking 每多送出一個新的 event_data_xxx 欄位，
          # 就在這裡照樣式多補一組 set + delete_key

 transform processor (v0.158.0) (Recommend)

processors:
  transform/opensearch_event_data:
    error_mode: ignore
    log_statements:
      - context: log
        statements:
          # ===== 步驟一：body → attributes（攤平，跟之前一樣）=====
          - merge_maps(attributes, ParseKeyValue(body), "upsert")

          # ===== 步驟二：attributes → attributes["event_data"]=====

          # 2-1 把整包 attributes 複製一份到暫存箱 cache
          #     用 "insert" 是為了避免蓋掉 cache 裡可能已存在的其他暫存資料
          - merge_maps(cache, attributes, "insert")

          # 2-2 在 cache 這份複本裡，只留下 event_data_ 開頭的欄位，其他丟掉
          - keep_matching_keys(cache, "^event_data_")

          # 2-3 把 cache 裡剩下的欄位名稱去掉 event_data_ 字首
          #     event_data_deviceType → deviceType
          - replace_all_patterns(cache, "key", "^event_data_", "")

          # 2-4 把清理乾淨的 cache 整包塞進 attributes["event_data"]
          - set(attributes["event_data"], cache)

          # 2-5 把 attributes 最上層原本打平的 event_data_ 欄位整批刪掉
          - delete_matching_keys(attributes, "^event_data_")

Exporter

  • 可以參考 tw-stage Opensearch exporter 設定
  • 連線資訊可以查看 OpenSearch Connection
  • 依照該設定就可以順利將資料送到 OpenSearch
opensearch: 
    http:
      endpoint: http://tw-opensearch-stage.garmin.com:9200
      auth:
        authenticator: basicauth/opensearch
    dataset: "foreman-assistant"
    namespace: "tw-stage"
    mapping:
      mode: "ss4o"

ss4o

  • mapping mode 就是 OpenSearch 儲存資料的格式 (schema)
  • otel collector v0.101.0 支援三種 mapping mode: ss4o, ecs, flatten_attributes, default mode 是 ss4o
  • 選擇 ss4o 的理由是, 不管 logs/traces/metrics 從哪個地方送進來, 欄位名稱在 OpenSearch 上都可以長一樣
欄位型別用途查詢方式
body固定 text保留原始訊息內容全文搜尋, 不能精確篩選
attributes動態 object (看到新欄位就會自動建立 mapping)結構化 key-value metadata可以精確篩選, 但太多欄位要小心 mapping 爆炸

Index 命名規則

ss4o_{type}-{dataset}-{namespace}

  • 目前的 Index → ss4o_logs-foreman-assistant-tw-stage
  • ss4o_ 前綴是預設的, 不是因為 mapping mode 填寫 ss4o, 可以看官方 Indexing Options,
Note

官方 indexing options 是較新的版本, 但目前的 otel collector 是v0.101.0, 並沒有支援 Placeholder Syntax (動態建立 index), 只能透過 namespace, dataset 創建 index, 目前collector的版本支援的 mode 前綴都是帶 ss4o_


欄位屬性

type

固定是 logs, traces. mertics 三選一, 由訊號類型決定
datasetconfig 裡的 dataset 參數, 預設是 default, 語意是「這筆資料的來源分類」(ex. foreman-assistant)
namepspace

config 裡的 namespace 參數,預設值 namespace,語意是「用來分組」(ex. tw-stage)
