Span Attribute 決策卡

先問：這個值真的值得放進這一次 Span 嗎？

這張卡只解決 Attribute。 如果你的問題已經變成「我想記的不是一個值，而是一件發生過的事」或「這段工作是不是應該有自己的時間與因果位置」，先不要在這裡背新名詞；請直接進入 Lesson 5：Span 邊界與欄位設計。 那一課會從第一性原理完整比較 Span、Event、Attribute 的存在理由、使用時機與實際範例。

最小判斷流程

我想記一個值
   |
   v
它描述的是「這一次 Span 所代表的 operation」嗎？
   |
   +-- 否 → 先不要放進 Span Attribute
   |
   +-- 是
        |
        v
事故時我會拿它 filter / group / compare / debug 嗎？
        |
        +-- 否 → 通常不要記
        |
        +-- 是 → Attribute
一句話：Attribute 是附在 Span 上、描述這一次 operation，而且值得查詢的 key-value metadata；不是把所有 local variable 都抄進 telemetry。

四道守門

問題判斷
它描述的是這一次 operation 嗎？不是的話，先不要把它當 Span Attribute。
事故時我會用它回答什麼問題？答不出來通常就不值得記。
值會不會非常多、甚至無界成長？先確認 queryability 與 backend 成本。
含個資、credential、完整 payload 嗎？不要直接記；移除、遮罩或改成安全分類。

套回 Lesson 3

span.set_attribute("app.cart.item_count", 3)
span.set_attribute("app.cart.total_cents", 3674)
欄位判讀
app.cart.item_count描述這次計算處理多少 item；若要比較 item 數量與 latency，可以有明確 debug 價值。
app.cart.total_cents資料模型上可以，但是否值得 production 記錄，要看是否有實際 query/debug 需求與資料安全考量。
service.name這不是單次 operation 的資訊；在目前課程裡它屬於 Resource。
SRE 判斷：telemetry 的價值不是欄位越多越好，而是能否用合理成本幫你回答事故問題。

下一個設計問題在哪裡學？

當你已經不只是問「這個值該不該成為 Attribute」，而是在比較不同 telemetry 表達方式時， 請進入 Lesson 5。 它會用同一個 checkout 情境回答：什麼時候只加 Attribute、什麼時候需要記錄一個發生時刻、什麼時候值得拆出另一個 Span，以及為什麼。
