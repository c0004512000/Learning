Telemetry 設計決策卡

Span / Event / Attribute / Log：先問「事故時我要什麼證據？」

總原則：不要從程式碼結構決定 telemetry；從 SRE 想回答的事故問題決定。

四種模型一句話

模型什麼時候用例子
Attribute描述這次 operation 的可查值payment.provider="a"
EventSpan 期間某一個重要時刻retry.started
Child Span子工作值得獨立量 duration / outcomeinvoice.render_pdf
Log需要詳細 message / stack / diagnosticsexception stack trace
Child Span 不是新資料型別：它仍然是 Span，只是 parent 是另一個 Span。

最小 decision tree

我想留下什麼證據？
│
├─ 一段子工作的 duration / outcome？ → Child Span
├─ 某一刻發生的重要事情？           → Event
├─ 描述這次 operation 的可查值？     → Attribute
├─ 詳細 message / stack / diagnostics？ → Log
└─ 都不是                           → 可能不需要記

常見模糊情境

情境比較好的選擇理由
retry 何時發生Event只需要 timestamp。
每次 retry latencyChild Span每次 attempt 都要獨立 duration。
這次最後 retry 幾次Attribute只是 operation 結果值。
payment timeout stackSpan + LogSpan 看 causal/duration；Log 看細節。
helper function 0.1ms通常不記沒有獨立診斷價值。

Attribute 三個實際問題

原本術語實際要問自己例子
Queryability事故時我真的會拿它 filter / group / compare 嗎？payment.provider
Cardinalitybackend 可能看到多少種不同值？env 很少；order.id 幾乎每次不同
Availability需要它做決策時，當下已經知道這個值嗎？head sampling 在 Span 建立時就做決定

Failure：Span 還是 Log？

需要知道「哪個 operation fail、花多久、在 trace 哪裡」？
  → Span

需要 stack / verbose message / raw diagnostic detail？
  → Log

兩種問題都要回答？
  → Span + correlated Log
不要因為 function 會 fail 就自動建立 Span。 只有當它的 latency、failure boundary 或 causal position 對排障有獨立價值時才拆 Span。

主要來源： OpenTelemetry Trace API、 OpenTelemetry Logging Specification。
