Span / Event / Attribute 決策卡

先分清楚：是在既有 Span 裡補證據，還是需要新的 Child Span

先不要把三者想成平行資料型別。 在 tracing 裡，Span 代表 operation；Span 可以帶 Attributes 與 Events，而 Event 自己還可以帶 Event Attributes。 只有需要另一段獨立 operation 時，才新增另一個 Span。

先記依附關係

Span
├─ Span Attributes
├─ Span Events
│  └─ Event Attributes
└─ Child Span
   ├─ Span Attributes
   └─ Span Events
Child Span 不是新 telemetry type： 它就是另一個 Span，只是 parent 指向目前這個 Span。

最小 decision tree

目前已經有一個 Span 正在描述這段 operation
│
├─ 某個子工作需要自己的 start/end、duration、結果與 parent/child 關係？
│    └─ 是 → 建立新的 Child Span
│
└─ 不需要新的 Child Span
     ├─ 只是描述目前 Span 的一個值？
     │    └─ 是 → 在目前 Span 加 Attribute
     │
     └─ 是目前 Span 期間的一個重要時刻？
          └─ 是 → 在目前 Span 加 Event

三種動作快速對照

你要回答的問題動作例子
這段子工作花多久？結果如何？它是誰的子工作？新增 Child Spaninvoice.render_pdf
目前這個 Span 期間，某件重要事情何時發生？在目前 Span 加 Eventretry.started
目前這個 Span 有什麼值得 filter / group / compare 的特徵？在目前 Span 加 Attributepayment.provider="a"

兩個常見抽象詞

詞在這一課真正的意思
Outcome這段 operation 最後得到什麼結果，例如成功、錯誤或某個 business result。不是固定叫 outcome 的 Span 欄位。
Causal positioncausal = 因果的。指這個 Span 在 parent/child 因果關係中的位置，例如 payment.authorize 是 POST /checkout 的 child。

process 內部 function：什麼情況可能值得 Span？

不是只有 DB / HTTP。只要你真的需要把它獨立定位，就可能合理：

  • PDF / report rendering：要分辨是不是 render 造成數秒 latency。
  • 大量 serialization / compression：要分辨 CPU processing 是否成為 bottleneck。
  • fraud / pricing rule evaluation：要知道哪個 business stage 慢或失敗。
  • lock / semaphore wait：要分辨是在計算，還是在等待 contention。
  • large batch validation：要知道大量資料時 validation 是否成為獨立瓶頸。

反過來，固定極快、事故時不會單獨定位的 helper，不應只因為它是一個 function 就建 Span。

Attribute：不要背術語，問具體問題

術語真正要問的問題直覺例子
Queryability事故時我真的會拿它 filter / group / compare 嗎？payment.provider 常有用；loop_index 通常沒有。
Cardinality這個欄位可能出現多少種不同值？environment 約 3 種；order.id 可能幾乎每筆不同。
Sensitivity它是不是 credential、個資或不該進 telemetry 的 payload？auth.token 不應記。
Timing這個值最早什麼時候才知道？Timing 不決定它能不能當 Attribute，而是決定最早何時能寫入，以及更早發生的機制能不能看到它。payment.provider 可一開始寫；retry.count 可執行中再寫。
Timing 小結： 只要 Span 還沒 End，執行中才知道的值仍可加入 Attribute；Span End 後不能再修改。建立 Span 當下已存在的 Attributes 才可能被當下的 sampling decision 使用，正式原因留到 Lesson 9。
Duration 不要重複做成 Attribute： Span 本身已有 start/end timestamp，因此 duration 本來就是 Span 的核心時間資料；通常不需要再額外做一個 latency Attribute。

Failure 不是自動建立 Span 的理由

如果一個子工作需要自己的 latency、結果與 parent/child 位置，才考慮 Child Span。 如果你的問題開始變成「我要保存詳細錯誤文字」或「我要把 application Log 對回某個 Span」，這已超出本卡範圍；先回 Lesson 5 看最低必要解釋，完整模型在 Lesson 25，快速參考在 Log correlation 卡。

想把這些判斷練成工作能力： 進入 SRE Telemetry Design Labs，用 production-style 情境練過度埋點、缺少證據、Span vs Log 與 Attribute 設計。
