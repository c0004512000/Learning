Span / Event / Attribute 決策卡

先問「這份資訊要幫我回答什麼問題？」

先決定它是不是 Attribute

這份資訊描述的是「整段 operation 的性質或結果」？
  ├─ 否 → 它是一個有診斷意義的時間點？
  │        ├─ 是 → Event
  │        └─ 否 → 它需要自己的 duration / outcome / causal node？
  │                 ├─ 是 → Child Span
  │                 └─ 否 → 通常不要記
  │
  └─ 是 → 我之後會用它 filter / group / compare / debug 嗎？
           ├─ 否 → 通常不要記
           └─ 是 → Attribute
一句話：Attribute 是「這一次 operation 的可查 metadata」，不是把所有 local variable 都抄進 Span。

四個相鄰概念不要混在一起

資訊適合放哪裡例子
這次 operation 的可查特徵Attributecart.item_count=3、error.type=timeout
Span 期間某一刻發生的事Eventretry.started
需要自己的時間與因果位置的工作Child Spandatabase query、outgoing HTTP call
所有 Span 共用的 telemetry producer identityResourceservice.name=checkout-service

Attribute 五道守門

守門問題若答不出來
事故時我會用它回答什麼問題？先不要記錄。
它描述的是整段 operation，而不是某一瞬間嗎？考慮 Event 或 Child Span。
值或值組合會無界成長嗎？改成穩定分類，或確認 backend 成本。
含個資、credential、完整 payload 嗎？移除、遮罩或只記安全分類。
Sampler 做決策時就需要知道嗎？若需要，優先在 Span 建立時就提供。

套回 Lesson 3 的購物車範例

span.set_attribute("app.cart.item_count", 3)
span.set_attribute("app.cart.total_cents", 3674)

item_count 和 total_cents 都是在描述「這一次 calculate_total operation 的背景／結果」， 所以資料模型上可以是 Attribute；但「可以」不等於「production 一定應該記」。 如果你沒有任何查詢或除錯需求會用到 total_cents，就不必為了欄位多而留下它。

SRE 判斷：telemetry 的價值不是欄位數量，而是它能否用可接受的成本排除事故假設。
