Span / Event / Attribute 決策卡

從「我需要哪種證據？」決定 telemetry model

先不要看 function 名稱。 問事故時你要回答什麼問題，再決定需要 Span、Event、Attribute，或根本不記。

最小 decision tree

這份資訊需要自己的 start / end / duration / outcome？
  ├─ 是 → Span
  │        如果 parent 已經是另一個 Span → Child Span
  │
  └─ 否 → 重點是「某一刻發生」嗎？
           ├─ 是 → Event
           └─ 否 → 是描述這次 operation 的可查值嗎？
                    ├─ 是 → Attribute
                    └─ 否 → 可能不需要記
Child Span 不是新 telemetry type： 它就是 Span，只是它的 parent 是另一個 Span。

三個模型快速對照

模型你要回答的問題例子
Span / Child Span這段工作花多久？成功嗎？它在因果鏈哪裡？invoice.render_pdf
Event這個重要事情是在 Span 的哪個時間點發生？retry.started
Attribute這次 operation 有什麼值得 filter / group / compare 的特徵？payment.provider="a"

process 內部 function：什麼情況可能值得 Span？

不是只有 DB / HTTP。只要你真的需要把它獨立定位，就可能合理：

  • PDF / report rendering：要分辨是不是 render 造成數秒 latency。
  • 大量 serialization / compression：要分辨 CPU processing 是否成為 bottleneck。
  • fraud / pricing rule evaluation：要知道哪個 business stage 慢或失敗。
  • lock / semaphore wait：要分辨是在計算，還是在等待 contention。
  • large batch validation：要知道大量資料時 validation 是否成為獨立瓶頸。

反過來，固定極快、事故時不會單獨定位的 helper，不應只因為它是一個 function 就建 Span。

Attribute：不要背術語，問具體問題

術語真正要問的問題直覺例子
Queryability事故時我真的會拿它 filter / group / compare 嗎？payment.provider 常有用；loop_index 通常沒有。
Cardinality這個欄位可能出現多少種不同值？environment 約 3 種；order.id 可能幾乎每筆不同。
Sensitivity它是不是 credential、個資或不該進 telemetry 的 payload？auth.token 不應記。
Timing這個值在 Span 開始前、執行中，還是結束後才知道？route 可很早知道；final latency 要結束才知道。
Timing 為什麼重要？ 目前只要理解「決策當下不能使用未來才出現的資料」。它和 sampling 的正式關係，到 Lesson 9 再學，不需要在這張卡先背 head sampler。

Failure 不是自動建立 Span 的理由

如果一個子工作需要自己的 latency / outcome / causal position，才考慮 Child Span。 若你需要的是詳細 exception、stack、message，Log 更自然；完整 Span / Log correlation 會在 Lesson 25 正式學。

想把這些判斷練成工作能力： 進入 SRE Telemetry Design Labs，用 production-style 情境練過度埋點、缺少證據、Span vs Log 與 Attribute 設計。
