DOM、document 與 event 到底是什麼？

從「瀏覽器記憶體裡真的有什麼」一路走到「JS callback 為什麼會被呼叫」

先抓住一句話： JavaScript 並不是不停搜尋「有沒有 click」。瀏覽器負責接收使用者輸入、決定事件目標、建立 event、dispatch event；JavaScript 只是在事前把 callback 登記好，等瀏覽器在 dispatch 過程中呼叫它。

1. 先把 DOM 從抽象名詞變成「瀏覽器記憶體裡的物件」

假設伺服器送來這段 HTML：

<html>
  <body>
    <main>
      <button id="schedule">每日生產排程</button>
    </main>
  </body>
</html>

HTML 本身是一串文字。瀏覽器解析它之後，會建立一組彼此有父子關係的 DOM 物件。你可以先把它想成瀏覽器記憶體裡真的存在這些東西：

Document 物件代表目前整份網頁文件
HTMLHtmlElement 物件對應 <html>
HTMLBodyElement 物件對應 <body>
HTMLElement 物件對應 <main>
HTMLButtonElement 物件對應 <button id="schedule">

所以 DOM 不是「畫面」，也不是「HTML 字串」。它是瀏覽器根據文件建立的一組可操作物件，以及這些物件之間的 tree 關係。

具體判斷法： 你在 DevTools Console 輸入 document.querySelector('#schedule') 得到的不是 HTML 原始文字，而是代表那顆按鈕的 DOM JavaScript 物件。

2. 那 document 到底是什麼？

每一份被瀏覽器載入的 HTML document，都會由一個 Document 物件代表。瀏覽器又把「目前頁面的那個 Document 物件」提供給頁面 JavaScript，通常就可以直接用變數 document 取得。

// document 指向目前頁面的 Document 物件
console.log(document)

// 從 Document 往 DOM tree 裡找 body
console.log(document.body)

// 再從 DOM tree 找到某顆按鈕
const button = document.querySelector('#schedule')

因此：

document
   │
   └── html
        └── body
             └── main
                  └── button#schedule

document 可以看成你從 JavaScript 進入「目前這張網頁 DOM tree」最常用的入口之一。HTML Standard 明確定義：每一份 HTML document 都由一個 Document object 表示。

3. document.addEventListener(...) 到底做了什麼？

先看這段：

function handleClick(event) {
  console.log(event.target)
}

document.addEventListener('click', handleClick)

它不是：

JavaScript 開始無限迴圈，不斷去問瀏覽器「現在有 click 嗎？」

它做的事情比較接近：

Document 物件內部的 listener list

原本：[]

執行 addEventListener 後：
[
  {
    type: "click",
    callback: handleClick,
    capture: false
  }
]

這不是瀏覽器實作一定長成上述 JavaScript object；它是用來幫你具體理解規格中的資料關係。DOM Standard 定義每個 EventTarget 都有自己的 event listener list，而 addEventListener() 會把指定 type、callback 與 options 加入該 list。

所以真正被「記住」的是 listener。 handleClick 這個 callback 被登記起來，等待未來符合條件的 event 被 dispatch 經過 document。

4. 使用者真的點一下之後，event 從哪裡來？

以滑鼠或觸控點擊按鈕為例，可以先用這條具體因果鏈理解：

  1. 實體輸入發生。 使用者按滑鼠、手指碰觸螢幕或其他 pointing device 產生平台輸入。
  2. 瀏覽器接收到輸入。 這件事先發生在瀏覽器／平台層，不是你的 JavaScript 主動偵測。
  3. 瀏覽器決定此次互動對應哪個頁面目標。 在我們的例子中，結果是 DOM 裡的 button#schedule。
  4. 瀏覽器建立對應的 Event 物件。 例如 click 對應一個事件物件，其中會有 type、target 等資訊。
  5. 瀏覽器 dispatch 這個 event。 它依 DOM tree 建立 event path，檢查路徑上的 EventTarget 有沒有符合這個 event type 的 listener。
  6. 找到 listener 時，瀏覽器呼叫 callback。 你的 JavaScript 函式這時才真正開始執行，而且 event object 會被當成參數傳進 callback。

5. JS 到底怎麼「拿到」event？

關鍵不是 JS 去抓，而是瀏覽器呼叫 JS 時把 event 傳進來。

function handleClick(event) {
  //        ↑
  // 不是你自己建立的。
  // 瀏覽器呼叫 handleClick 時，把本次 Event object 傳進來。

  console.log(event.type)   // "click"
  console.log(event.target) // 真正被點到的 DOM node
}

document.addEventListener('click', handleClick)

把它翻成近似的人話：

你的 JS：
「瀏覽器，以後 click 經過 document 時，請呼叫 handleClick。」

                    ↓ 過了一段時間

使用者：點 button
                    ↓
瀏覽器：建立 click Event
                    ↓
瀏覽器：dispatch event
                    ↓
瀏覽器：在 document 的 listener list 找到 handleClick
                    ↓
瀏覽器：handleClick(這一次的 event object)
                    ↓
你的 JS：開始執行 handleClick 裡的程式

6. 為什麼 listener 掛在 document，卻能知道是 button 被點？

這是 DOM event propagation。假設 DOM 是：

document
└── html
    └── body
        └── main
            └── button   ← event.target

當 button 是目標時，event 會有一條 propagation path。簡化後可以理解成：

Capture： document → html → body → main → button
Target：                                      button
Bubble：  button → main → body → html → document

一般 document.addEventListener('click', handleClick) 沒有設定 capture: true，所以通常是在 bubbling 階段看到從子節點一路往上的 click。

欄位此例代表什麼
event.target最初真正被點到的 DOM object，例如 button 或 button 裡的 span
event.currentTarget此刻正在執行哪一個 EventTarget 上登記的 listener；若 listener 掛在 document，這裡就是 document
event.type事件類型，例如 click

7. 最容易混淆的地方：event 有沒有被「記錄」？

瀏覽器為了處理這次互動，會建立／dispatch event；但這不等於它會替你的應用程式保留一份永久 click history。

東西何時存在會自動成為歷史紀錄嗎？
listener registrationaddEventListener() 後，直到被移除或相關物件生命週期結束它是設定，不是使用者點擊歷史
本次 Event object此次事件建立與 dispatch／callback 執行期間可被程式取得不會自動變成你的 telemetry 紀錄
Faro / analytics event你的監控程式在 listener 中讀 event，再建立自己的資料若程式送出並由 backend 儲存，才成為之後可查的紀錄

因此 Faro click tracking 的概念邊界可以先看成：

瀏覽器原生世界
使用者 click
  → Browser Event
  → DOM event dispatch
  → listener callback(event)

                ↓ Faro 在這裡接手

監控資料世界
callback 讀取 event.target / 其他資訊
  → 整理成 Faro telemetry payload
  → transport
  → collector / backend
  → 儲存、查詢

9. 一張圖記住責任分界

Recap

  • DOM 是瀏覽器記憶體中的文件物件樹，不是單純 HTML 字串，也不是螢幕畫面。
  • document 是目前 HTML 文件的 Document 物件，也是 DOM tree 的主要入口。
  • Document、Element 等可以是 EventTarget，因此可以登記 event listener。
  • addEventListener() 登記的是「事件種類 + callback + options」。
  • JavaScript 不需要 polling 去抓 click；瀏覽器 dispatch event 時會主動呼叫已登記的 callback。
  • callback 的 event 參數是瀏覽器在呼叫函式時傳入的本次 Event object。
  • event.target 是事件原始目標；event.currentTarget 是目前正在執行 listener 的 EventTarget。
  • 原生 browser event 不等於永久 telemetry；Faro 必須另外讀取、轉換、送出與儲存。
