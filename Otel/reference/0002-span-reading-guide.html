Span 五問判讀卡

不要依賴 JSON 位置；依賴欄位語義

順序要回答的問題優先找的證據常見誤判
1屬於哪條因果鏈？Trace ID、Span ID、Parent Span ID把 Trace ID 當 request ID；把空 parent 當資料遺失
2觀測哪段工作？Name、Kind用動態值命名；把 INTERNAL 當 incoming request
3花多久、結果如何？Start、End、Status把 UNSET 當 unknown/error；把 OK 當一般成功預設值
4有哪些診斷脈絡？Attributes、Events、Links把有 timestamp 的事件硬塞成 attribute
5誰產生 telemetry？Resource、Instrumentation Scope把 service.name 當 Span name

Status 快速判讀

值先怎麼讀
UNSET預設值；沒有把 operation 標成 Error。一般正常成功通常維持 UNSET。
ERROR這段 operation 最後包含應被視為錯誤的結果。
OKApplication developer 或 Operator 明確宣告這段 operation 已確認成功；不是所有成功 Span 都要設。
不要混：Span Status 不是 HTTP status code，也不是 exception object。它是對整段 operation 的結果判定；具體何時算 Error 要看該 operation 的語義與 Semantic Conventions。

四層不要混用

資料模型：欄位代表什麼
Semantic Conventions：常見欄位叫什麼、值代表什麼
Exporter 顯示：人目前看到什麼排版
OTLP：資料如何編碼、傳輸與交付
Debug 分岔：畫面沒看到欄位時，先問「instrumentation 沒設定、pipeline 丟棄、 還是 UI 沒顯示？」不要直接由 UI 缺欄位推論 SDK 沒產生資料。

主要來源：OpenTelemetry — Traces、Trace API — Set Status、OTLP specification
