Log correlation 與重複資料判斷卡

先知道「正常應該長怎樣」，再用 checklist 找是哪一層壞掉

這張卡只處理兩種 troubleshooting 症狀：
  1. 你原本預期某筆 application Log 能對回目前 Span，但最後看不到 TraceId/SpanId。
  2. 同一個 logical LogRecord 在同一個預期目的地意外出現兩次以上。
如果這兩個前提都不存在，就不需要跑下面的 checklist。

先建立正常模型

Span 與 LogRecord 是兩份獨立 telemetry。若 application 在一個 active Span 執行期間 emit Log， 而 logging integration 有把目前 Span 的 IDs 帶進 LogRecord，那麼這筆 Log 可以長成： 

Span: payment.authorize
  trace_id = abc123
  span_id  = def456

LogRecord: "payment timeout"
  trace_id = abc123
  span_id  = def456

same TraceId + SpanId
        ↓
backend 可以把這筆 Log 對回 payment.authorize

這叫 log correlation。但 TraceId/SpanId 並不是每一筆 Log 都必須有： 如果 process startup、background task 或其他 Log emit 當下根本沒有 active Span，沒有 trace fields 是正常的。

所以不要把規則記成「Log 沒有 TraceId = 錯」。
真正的異常是：你明明知道這筆 Log 是在某個 active Span 裡產生，而且你也有設定 correlation，最後卻沒有 IDs。

Case A：預期有 TraceId / SpanId，結果卻沒有

這表示「Span context → LogRecord → backend」這條鏈的某一層沒有把 IDs 帶下去。

active Span
   ↓
Log emit
   ↓
logging integration 讀取 current Context
   ↓
LogRecord 帶 TraceId / SpanId
   ↓
Exporter / Collector 保留欄位
   ↓
backend 可查詢與顯示
檢查問題你其實在驗證什麼
Log emit 時是否真的位於 current Span 內？如果 emit 當下根本沒有 active Span，就沒有 Span IDs 可以帶進 Log。
Async/thread boundary 是否保留 Context？原本有 Span，但工作切到另一個 task/thread 後，current Context 可能沒有跟過去。
Logging bridge / integration 是否擷取 trace fields？就算 current Span 存在，也需要 logging integration 把 TraceId/SpanId 寫進 LogRecord。
Exporter / Collector / backend mapping 是否保留欄位？LogRecord 原本可能有 IDs，但下游轉換、mapping 或 indexing 把它們丟掉。
Debug 方向：從最靠近 source 的地方開始確認 IDs 何時消失。不要一開始就猜是 Collector 或 backend。

Case B：同一 Log 在同一 backend 意外出現兩次

這張卡假設你原本的設計是：一次 application log emission，在同一個目的 backend 應該只形成一筆 logical record。 如果完全相同的一筆資料出現兩份，通常代表同一筆 Log 被兩條 emission / collection path 都送到了同一目的地。 

原本期待：
logger.warning(...)
      ↓
   一條路徑
      ↓
backend：1 筆

異常情況：
logger.warning(...)
   ├─ path A ─┐
   └─ path B ─┴─→ backend：2 筆

這通常不是你想要的，因為它可能造成 log count 被放大、告警或統計失真、storage/indexing 成本增加， 也讓 SRE 誤以為同一事件真的發生兩次。

檢查問題可能的重複來源
同一 logger 是否有多個 handlers？一次 log call 被兩個 handler 都送出。
logger.propagate 是否又送到 root handler？child logger 自己送一次，之後又 propagation 到 root 再送一次。
是否同時 direct OTLP 與 stdout/file collection？application 直接 export 一份，同一筆 stdout/file 又被 agent/Collector 收一次。
Collector 是否有重複 receivers/routes？同一筆資料在 Collector topology 裡被兩條 pipeline/routes 再次送往相同 backend。
例外：如果你是刻意把同一 Log 同時送到不同目的地，例如一份到 SIEM、一份到一般 log backend，這不叫「同一 backend 的重複資料問題」。 這張卡只處理非預期 duplicate。

不要和 Span Event 混在一起

東西資料關係
Span Event真的存在 Span 裡，是 Span timeline 上的一個 timestamped event。
LogRecord是獨立 Logs signal；backend 可用 TraceId / SpanId 把它顯示在相關 Span 附近。

一句話 Recap

沒有 TraceId：不一定有問題；只有「本來預期這筆 Log 應該和 active Span 關聯」時才需要 debug。

同一 Log 出現兩次：如果是在同一目的 backend 非預期重複，通常代表同一筆 Log 走了兩條以上的 emission / collection path。
