11. Collector pipeline 為何存在

把 telemetry 的接收、治理與目的地從 application 解耦 · Lesson 11 of N

沒有 Collector 時，application 承擔什麼？

Application SDK 可以直接把 OTLP 送到 backend，但每個 service 都要知道 endpoint、credentials、TLS、 retry、batching、vendor exporter 與 routing policy。當目的地改變，數十個語言與服務可能都要改設定或重新部署。

Collector 在 application 與 backend 之間建立一個 telemetry control point：接收多種來源、依 policy 處理， 再送往一個或多個目的地。它降低應用程式對 backend 的耦合，並讓治理、轉換與路由可獨立演進。

能力邊界：Collector 不能補回 application 從未產生的 Span、修復錯誤的 Span name， 也不能憑空重建未 propagation 的 parent relationship。Application instrumentation 決定原始證據的語義； Collector 處理已收到的 telemetry。

主要來源：OpenTelemetry Collector — Architecture

Pipeline 是一條有方向的資料路徑

telemetry source
      │
      ▼
  Receiver
      │  接受並解碼
      ▼
 Processor 1
      │  依順序處理
      ▼
 Processor 2
      │
      ▼
   fan-out
   ├──────────► Exporter A ──► Backend A
   └──────────► Exporter B ──► Backend B

箭頭表示 telemetry data flow。Processors 是有順序的；最後一個 processor 將資料交給所有已設定 exporters， 每個 exporter 取得資料副本。Pipeline 在 Collector startup 由 configuration 建立，不是每筆 Span 動態組裝。

每個 component 只解一類問題

Component核心責任常見例子不是什麼
Receiver取得、接受並解碼 telemetry。OTLP receiver 接受 gRPC/HTTP。不代表資料已抵達 backend。
Processor依序轉換、批次、限制、取樣或丟棄資料。batch、memory_limiter、filter。不是 network listener 或最終目的地。
Exporter把 pipeline 結果送到 Collector 外部目的地。OTLP exporter、debug exporter。不建立 application Span。
Pipeline把支援同一 signal 的 components 接成可執行路徑。traces、metrics、logs pipeline。不是單一 component。

「宣告」不等於「啟用」

Collector configuration 有兩個不同層次：

receivers:
  otlp: {}          # 定義一個 component instance

processors:
  batch: {}

exporters:
  debug: {}

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]   # 在 pipeline 中引用，才形成 active path

上半部回答「有哪些 component、各自怎麼設定」；service.pipelines 回答「哪些 component 以什麼順序服務哪一種 signal」。只在頂層定義 exporter，卻沒有放進 pipeline，不會自動收到任何資料。

Signal type 是 pipeline 的型別約束

Traces、metrics、logs 的資料模型不同。Pipeline 名稱中的 type 決定它處理哪個 signal；其中使用的 receiver、 processor 與 exporter 都必須支援該 signal。traces pipeline 不會因為 OTLP receiver 同時能收 metrics， 就自動把 metrics 也送出去；metrics 需要自己的 pipeline。 

service:
  pipelines:
    traces:      # trace signal path
      ...
    metrics:     # separate metric signal path
      ...
    logs:        # separate log signal path
      ...

Processor 順序為何有語義？

Processor 是串接的 function：前一個輸出成為下一個輸入。因此「先刪除敏感欄位再 export」與 「先依欄位做 sampling、再刪除」可能得到不同結果。順序不是 YAML 美觀問題，而是 data transformation 的因果順序。

同理，processor 可以 drop telemetry。Receiver 成功接收只證明資料進入 Collector，不代表資料一定走到 exporter。 Debug 時必須分站觀測，而不是把 Collector 當成一個黑盒。

Collector 解耦了什麼，沒有消除什麼？

Collector 可集中處理仍需 application / platform 負責
Backend endpoints 與 credentials建立有正確業務語義的 Spans
Batch、retry、routing 與多目的地在正確 operation boundary 埋點
Attribute transform / redaction policy避免一開始就收集不該出 process 的 secrets
Central tail sampling正確 propagation Trace / Parent relationships
Protocol translationCollector 自身的部署、容量、HA 與監控

SRE debugging lab：Collector 收得到，但 backend 沒資料

已知 application OTLP export 無連線錯誤，Collector 也在監聽。請依 pipeline 逐站建立假設：

  1. Receiver：正確 protocol / port / signal pipeline 是否啟用？
  2. Processors：filter / sampling 是否 drop？transform 是否產生 invalid data？
  3. Exporter：endpoint、TLS、credentials、queue、retry 是否正常？
  4. Backend：是否接受 request，query time range / tenant / service filter 是否正確？

一個安全的定位方法，是在同一 traces pipeline 暫時增加 debug exporter：

exporters:
  debug:
  otlp/backend:
    endpoint: backend.example:4317

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug, otlp/backend]
如何解讀結果
  • Debug exporter 有 Span、backend 沒有：receiver 與前置 processors 已通過；優先查 backend exporter、network 或 backend ingestion。
  • Debug exporter 也沒有：優先查 application→receiver、signal pipeline activation，或 processors 是否 drop。
  • Debug exporter 的欄位已錯：問題發生在 application 或前置 processor；不要只盯 backend UI。
觀測點不是證明全部：Debug exporter 位於 processors 之後，所以它能證明資料已走過該 pipeline 的 receiver 與 processors；它不能證明另一個 exporter 或 backend 已成功。
