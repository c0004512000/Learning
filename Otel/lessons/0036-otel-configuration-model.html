36. Collector Configuration Model

設定不是 YAML 文字；它是經過解析後，用來建構 runtime graph 的資料模型 · Lesson 36 of N

本課成果

你會把 Collector 設定拆成 source、resolution、merge、decode、graph construction 與 runtime start； 理解 component ID、declaration/activation、config provider、substitution 與 final configuration，並能系統化定位設定問題。

主要來源：Collector Configuration、Collector Components

本章談的是 Collector configuration。OTel 另有給 application SDK 的 Declarative Configuration data model； 兩者目的與 schema 不同，不要因為都使用 YAML 與 environment substitution 就混為一談。

第一性原理：設定的工作是建立可執行物件與資料流

YAML 只是 serialization。Collector 真正需要的是：

configuration sources
  → resolve references/substitutions
  → merge + override
  → decode into typed component configs
  → instantiate components
  → connect active service pipelines
  → start runtime resources

因此「檔案看起來正確」不代表 final model 正確，更不代表 runtime 能啟動。 每個階段有不同 failure：找不到 source、env 缺值、merge 覆寫、unknown component、dangling reference、port collision、TLS/auth failure。

Component ID = type[/name]

Collector component instance 用 ID 辨識：

otlp                  # type=otlp, name empty
otlp/edge             # type=otlp, name=edge
otlp/backend-primary  # type=otlp, name=backend-primary

斜線前的 type 決定由哪個 component factory 解碼與建立；斜線後的 name 只是在同 type 下區分 instances。 把 otlp/foo 改名成 otlp/bar 不會改變功能；把 type 改成 distribution 不包含的 component，則 decode/build 會失敗。

同一 instance 可被多條 pipelines reference；那通常表示共享同一 runtime component，而不是複製多份設定。 共享 receiver 可能只 bind 一次 port；共享 exporter 也代表共同 endpoint/queue state。是否共享應由 failure/resource ownership 推導，不只為了少寫 YAML。

Declaration 與 Activation 是兩件事

receivers:
  otlp/edge: {...}       # declare an instance

service:
  pipelines:
    traces/prod:
      receivers: [otlp/edge]  # reference it in an active graph

頂層 sections 是 component catalog；service.pipelines 才把它們連成 active graph。 宣告但未 reference 的普通 pipeline component 不會因存在於 catalog 就自動處理資料。 反過來，pipeline reference 一個未宣告 ID，graph 無法完成。

Pipeline ID 也可寫成 signal[/name]，例如 traces/prod、metrics/internal；斜線後名稱用來區分用途，不改變 signal 型別。

Config Provider：值從哪裡來

Collector 的 --config 可接受路徑或 config URI。官方列出的 provider 包含 file、env、 yaml、http、https。Provider 解決「取得 configuration bytes/map」；component config 解決「這些欄位代表什麼」。

Provider適合主要風險
file:版本化、可審查的 base configmount/path、rollout drift
env:由 runtime 注入小型 config sourceescaping、大小、不可見漂移
yaml:精準 override 小欄位CLI quoting 與難以稽核
http(s):集中提供 configurationbootstrap availability、trust/TLS、變更治理

Provider 來源不是越多越好。來源增加會擴大 precedence 與 provenance 問題：事故時若無法回答「這個 final value 從哪來」，設定就不可操作。

Substitution：把 deployment-specific value 延後到 resolution

範例 examples/0036-collector-config-model.yaml 使用：

${env:OTLP_GRPC_ENDPOINT:-0.0.0.0:4317}
${env:BACKEND_OTLP_ENDPOINT}
${env:BACKEND_AUTH_HEADER}

第一個有 default，後兩個沒有。Substitution 的價值是把穩定 graph 與環境特定 endpoint/credential 分離； 風險是 missing value 可能 resolve 成空值，而錯誤直到 decode 或 runtime 才顯現。 Secret 不應因 substitution 而出現在 Git，但它仍可能出現在 process environment、resolved config 或 debug output；必須控制讀取與遮蔽。

Merge 與 Override：Final Config 才是事實

Collector 可接受多個 --config sources，也可用 --set 在 sources resolve/merge 後覆寫欄位。 多檔能分離 base、environment 與 secret references，但語意取決於 merge 結果；不要只審查其中一個 fragment。 

base + environment overlay + emergency override
                  ↓
             final config
                  ↓
             runtime graph

同一路徑若在多處定義，必須知道 precedence；list/map 的合併也不能憑直覺猜。 Production 變更應保存可重建的 source set、版本與 final non-secret fingerprint，讓「同一版本」真的可比較。

Validation 只證明到哪一層？

官方提供 Collector validate command。它非常重要，但成功不等於端到端可用：

  • 能證明 config 可取得、解析，且 component schema/graph 基本有效。
  • 不能完整證明 production DNS、network policy、remote certificate、credential permission。
  • 不能證明真實負載下 queue、memory、cardinality、sampling 語意正確。
  • 不能證明 backend 接收到的 resource identity 與 dashboard query 相容。

所以驗證分層：static validation → canary startup → synthetic telemetry → backend query → load/failure test。 本課因全域安全限制只提供閱讀與靜態推理，不執行 Collector 或任何 Windows executable。

SRE 附加練習：同一 ConfigMap，為何兩台行為不同？

把問題拆成 deterministic stages，不先怪「Collector 有 cache」：

  1. 比對實際 binary distribution 與版本；相同 YAML 在不同 component set 可能 decode 不同。
  2. 列出每台實際啟動參數與全部 config URIs，而不是只看預期 deployment manifest。
  3. 比對 environment substitution 是否存在、是否空值、是否 default 生效。
  4. 重建 merge/override 後的 final config；敏感欄位只比較存在性或 hash，不輸出明文。
  5. 比對 active graph、listen endpoints、DNS/TLS/auth 與 Collector internal telemetry。

快速流程可存成 Collector 設定解析卡。

動手推理（不執行）

  1. 在範例中找出 type、instance name、pipeline signal 與 pipeline name。
  2. 假設 BACKEND_OTLP_ENDPOINT 未設定，指出 failure 最早可能在哪個 stage 被發現，為何不能保證只在一處。
  3. 把 otlp/edge 從 pipeline reference 移除但保留 declaration，畫出 active graph。
  4. 設計 production config provenance 記錄：至少包含 binary version、source revisions、non-secret final hash 與 rollout ID。

本課總結

  • Collector config 是建構 runtime graph 的資料模型；YAML 只是其中一種來源表示。
  • Component ID 的 type 決定 factory，name 區分 instances；declaration 不等於 activation。
  • Provider、substitution、merge 與 override 共同決定 final config。
  • Static validation、runtime connectivity 與 telemetry semantics 是不同證明層級。
