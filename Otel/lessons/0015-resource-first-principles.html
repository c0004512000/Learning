15. Resource 與 service identity

先回答「誰產生 telemetry」，再分析「發生什麼工作」 · Lesson 15 of N

本課成果

你會從 entity identity 推導 Resource 的用途，正確區分 logical service、runtime instance、版本與環境； 也能判斷一個 attribute 應屬 Resource 還是 Span。這是跨 traces、metrics、logs 的共同基礎，不是 backend tag 命名技巧。

主要來源：OpenTelemetry — Resources、Service semantic conventions

第一性原理：觀測值若不知道來源，就無法比較

假設你只收到兩筆資料：

latency = 850 ms
error = true

它們本身無法回答是哪個系統、服務、版本、環境或 instance。Telemetry 至少需要兩類描述： 

Resource：哪個 entity 產生資料？
Signal record：這一次 observation / operation 是什麼？

Resource(service.name=checkout, service.version=2.4.1)
  └─ Span(checkout.validate_cart, app.cart.item_count=3)

Resource 是一組 attributes，代表產生 telemetry 的 entity。它在 Provider 初始化時關聯；由該 Provider 建立的 Spans 都帶著同一 Resource。這正是為何 service.name 不應在每個 request 中隨意改變。

Resource attribute 還是 Span attribute？用變化尺度判斷

問題若答案是…通常歸屬
它描述誰產生 telemetry 嗎？service、process、container、pod、host、cloud resourceResource
同一 Provider 的所有 observations 都應相同嗎？service identity、deployment environment、版本Resource
它描述某一次 operation 嗎？route、status code、cart size、DB operationSpan
它會隨每個 request 改變嗎？通常是 request/operation contextSpan（仍須控制基數與敏感性）

不是「不常變」就一定是 Resource；判斷核心是 entity semantics。例如 feature flag 可能一小時才改一次， 但若它是一次 request 的 evaluation result，仍不因此成為 service identity。

Service identity 的四個層級

1. service.namespace：哪一個系統群組？

它把相關 services 放進同一 logical system，例如 store。同一 namespace 內的 service.name 應可區分不同 services。Namespace 不是 Kubernetes namespace 的自動別名；若要表達 Kubernetes identity，使用對應 k8s.* Resource attributes。

2. service.name：哪一個 logical service？

例如 checkout。所有水平 replicas 必須使用相同值，因為它們共同提供同一 logical function。 若把 pod name、host name 或隨機 suffix 拼進去，backend 會把 replicas 誤認為多個 services，service graph、SLO 與聚合都被拆碎。

SDK 在未指定時會提供 unknown_service 類 fallback，但那只讓資料仍具合法 identity，不代表操作上足夠。 應明確設定 service.name，否則多個應用可能被錯誤混在一起。

3. service.instance.id：同一 service 的哪個執行 instance？

它要區分同時運行的 replicas。這讓 SRE 能問：「錯誤是否集中在單一 instance？」它不取代 service.name； 兩者回答不同聚合層級。Instance ID 應為 opaque、在同一 namespace/name 下唯一，且避免直接洩露不必要的基礎設施細節。

4. service.version 與環境：哪個 deployment cohort？

service.version 識別實際 artifact 版本，例如 semantic version 或 commit hash； deployment.environment.name 識別 production、staging 等 logical environment。 兩者讓同名 service 能按 rollout cohort 比較，而不是改寫 service.name 成 checkout-prod-v2。

正規化的價值：service.name=checkout 保持穩定，version、environment、instance 分別放自己的維度。 如此「整體 checkout」、「只看 production」、「比較 v2.4.0/v2.4.1」、「隔離單一 instance」都能由同一資料模型推導。

閱讀 Python 範例

範例位於 examples/0015-resource-identity.py：

resource = Resource.create({
    "service.namespace": "store",
    "service.name": "checkout",
    "service.version": os.environ.get("SERVICE_VERSION", "dev"),
    "deployment.environment.name": os.environ.get(
        "DEPLOYMENT_ENVIRONMENT", "local"
    ),
    "service.instance.id": os.environ.get(
        "SERVICE_INSTANCE_ID", str(uuid.uuid4())
    ),
})

Code 提供 deterministic local defaults 與 deployment injection points。真正平台通常可透過 environment、Resource detectors 或部署工具提供 identity；關鍵不是「一定寫死在 code」，而是最後合併出的 Resource 必須語意正確且來源衝突可預期。 

with tracer.start_as_current_span("checkout.validate_cart") as span:
    span.set_attribute("app.cart.item_count", 3)

Item count 只描述這一次 cart validation，所以放 Span。若把它放 Resource，它會錯誤地套到 Provider 後續建立的所有 Spans， 而且 Resource 在 Provider 建立後不能拿來當 request-scoped mutable bag。

SRE debugging lab：identity 錯誤會偽裝成什麼症狀？

Case A：service graph 突然出現幾百個 checkout services

先 group by service.name 檢查是否含 pod/host/random suffix，再與 service.instance.id 對照。 若每個 replica 都有不同 service.name，根因是 identity level 混淆，不是服務真的被拆成幾百個邏輯元件。

Case B：production 與 staging traces 混在一起

確認 deployment.environment.name 是否缺失、拼字漂移或被不同來源覆寫。不要只用 Collector endpoint 推測環境； route destination 是 transport configuration，不是 telemetry 自身的 environment identity。

Case C：只有少數 replicas 高延遲，但 service aggregate 看不出來

先以穩定 service identity 篩選，再按 service.instance.id 分組。若 instance IDs 碰撞或全部相同， 資料模型無法隔離單一 runtime，應修正產生 identity 的來源，而非在 Span name 拼 instance。

練習：為每個值選擇正確位置
  • checkout → service.name
  • 8ae73a artifact → service.version
  • production → deployment.environment.name
  • 某個 runtime UUID → service.instance.id
  • 這次 request 的 http.response.status_code=503 → Span attribute
