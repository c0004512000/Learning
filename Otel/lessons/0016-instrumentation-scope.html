16. Instrumentation Scope 與來源責任

在 service identity 與 operation 之間，標記誰負責產生 telemetry · Lesson 16 of N

本課成果

你會理解同一個 service 為何需要多個 Instrumentation Scopes，並能區分 service version、scope version 與 Span attributes。 你也會用 scope 定位重複埋點或特定 instrumentation library 的行為，但 debug 只是這個資料模型的自然用途。

主要來源：OpenTelemetry — Instrumentation scope

第一性原理：知道「哪個 service」仍不知道「哪段 code」

一個 checkout service 可能同時包含 HTTP framework 自動埋點、database client instrumentation、cache library 與 application 手動埋點。 Resource 會把它們都正確標成 service.name=checkout，但這仍無法回答是哪套 telemetry-producing code 建立某個 Span。 

Resource：store / checkout / version 2.4.1
  ├─ Scope: HTTP framework instrumentation 1.2.0
  │    └─ Span: POST /checkout
  ├─ Scope: acme.checkout.application 0.3.0
  │    └─ Span: checkout.validate_cart
  └─ Scope: cache instrumentation 1.8.2
       └─ Span: cache.get

Instrumentation Scope 是 telemetry producer 的 logical software unit。它可以代表 module、package、class、library 或 framework。 取得 Tracer、Meter 或 Logger 時指定 scope；由該實例產生的 records 都與 scope 關聯。

Scope identity 是一個 tuple

(name, version, schema_url, attributes)
       required  optional  optional    optional
  • Name：穩定且能唯一識別 producer，通常採 fully qualified module/library name。
  • Version：該 instrumentation code 的版本。
  • Schema URL：描述 telemetry schema 對應的版本／位置，供 schema-aware consumer 解讀。
  • Attributes：描述 scope 本身的額外 metadata；不是 request attributes。

本課先實作 name/version。重點不是欄位數量，而是責任歸屬：Scope metadata 描述 producer；Span data 描述 operation； Resource 描述產生 telemetry 的 entity。

三種 version 不可互換

Version它版本化什麼？例子變更原因
service.version部署中的 service artifact2.4.1新 release/deploy
scope version產生 telemetry 的 module/library/instrumentation1.8.2instrumentation package 升級
semantic convention/schema version欄位語意契約由 schema URL 表達telemetry schema 演進

同一 service release 可以包含多個不同版本的 instrumentation libraries；同一 instrumentation version 也可能部署於多個 service versions。 把 scope version 寫成 service version，會失去定位 producer regression 的能力。

閱讀 Python 範例

範例位於 examples/0016-instrumentation-scopes.py：

checkout_tracer = trace.get_tracer(
    "acme.checkout.application", "0.3.0"
)
cache_tracer = trace.get_tracer(
    "acme.cache.instrumentation", "1.8.2"
)

兩個 Tracers 使用同一 Provider，因此共享 Resource、sampler 與 processors；但各自保留 producer identity。 這不是建立兩個 services，也不是建立兩條 Trace。當第二個 Span 在第一個 current Span 內開始，parent/child 關係仍由 Context 決定。 

Resource: service.name=checkout, service.version=2.4.1

Span checkout.validate_cart
  scope.name=acme.checkout.application
  scope.version=0.3.0

└─ Span cache.get
     scope.name=acme.cache.instrumentation
     scope.version=1.8.2
關鍵獨立性：Trace topology 由 trace/span IDs 與 Context 建立；Scope 說明 producer；Resource 說明 entity。 不同 scopes 的 Spans 完全可以屬於同一條 Trace。

Scope name 如何選？

Library/framework 應使用自己的 fully qualified name 與 version；若你替不支援 OTel 的 library 寫 instrumentation， scope 應識別 instrumentation library 本身。Application code 可用穩定 module/class boundary。

避免下列不穩定名稱：

  • checkout.request.7f3a...：把 request ID 放入 scope，造成無界 scopes。
  • checkout-pod-a7f9：這是 instance identity 問題，不是 producer identity。
  • tracer1：過度模糊，跨團隊或升級時無法追責。
  • checkout 只因 service.name 也是 checkout：混淆 entity 與 producer。

SRE debugging lab：用 Scope 找重複與回歸

Case A：同一次 HTTP request 出現兩個幾乎相同的 client Spans

先比較兩筆 Span 的 scope name/version。若一筆來自 framework auto-instrumentation，另一筆來自 application manual wrapper， 則重複不是 Collector 複製資料的第一證據，而可能是兩個 producers 都觀測同一 operation。

Case B：升級後 database Span names 或 attributes 改變

同時按 service.version 與 scope version 分組。如果 service artifact 沒變但 scope version 變了， 調查 instrumentation dependency/schema 演進；若反之，調查 application deploy。兩種 version 是正交維度。

Case C：想關掉某 library 的 telemetry

Scope 是可靠識別來源的 metadata，但「在 Collector filter 掉」只會阻止下游保存，不能追回 application 已付出的 Span creation/export 成本。 若目標是降低 source overhead，優先在 instrumentation configuration/SDK 層處理；若目標是下游 routing，才考慮 Collector policy。

練習：三層歸因

看到一筆慢 Span 時，先寫三行：

Entity: service.name + service.version + instance
Producer: scope.name + scope.version
Operation: span.name + kind + relevant attributes/status

每一行都回答不同問題，不要把缺失欄位用另一層猜出來。
