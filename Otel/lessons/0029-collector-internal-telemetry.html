29. 用 Collector internal telemetry 觀測觀測系統

Backend 沒資料只是症狀；accepted、refused、queued、sent 才能定位資料命運 · Lesson 29 of N

本課成果

你會把 Collector 視為一個有 ingress、processing、queues、egress 與 resources 的服務，使用 internal metrics/logs 建立 evidence chain； 能解讀 accepted/refused、processor incoming/outgoing、queue size/capacity、enqueue/send failures 與 sent counters，而不把單一 failure counter 等同資料遺失。

主要來源：Collector Internal Telemetry、Collector Troubleshooting

第一性原理：Observability pipeline 也有自己的未知狀態

Backend 查不到 Trace，可能是 application 沒產生、SDK sampling/drop、network、receiver refusal、processor filter、queue full、export retry、 backend reject 或 query 錯誤。只觀察 backend absence，這些假設完全混在一起。 

Application → Receiver → Processor(s) → Sending queue → Exporter → Backend
                 │            │              │             │
              accepted/     in/out       size/capacity   sent/failed
               refused

Internal telemetry 是 Collector 對自己狀態的 observations。它把 end-to-end black box 拆成可檢驗邊界， 但仍不取代 application SDK 與 backend 自身 telemetry。

預設可見性與安全邊界

Collector 預設提供兩個最短 feedback paths：

  • Internal metrics：Prometheus interface，預設 http://127.0.0.1:8888/metrics。
  • Internal logs：預設寫到 stderr。

Loopback default 避免無意公開 operational details。Container/Kubernetes 若需遠端 scrape，才設計 bind/publish、NetworkPolicy、authentication/TLS 與 access control；不能為了方便直接把 internal endpoint 公開到所有網路。

監控路徑要能在主路徑壞時留下證據：若 Collector internal telemetry 只透過同一個故障 backend/exporter 送出， 事故時可能同時失明。保留 local logs、local scrape 或適度獨立的監控路徑，但也避免形成無限自我觀測循環。

Internal telemetry 也需要 Resource identity

Collector 會為 internal signals 提供 service.name、service.version、service.instance.id 等 Resource attributes。 多個 Collector replicas 若沒有 instance/deployment identity，queue/reset/CPU data 可能被錯誤合併。

範例片段位於 examples/0029-internal-telemetry-fragment.yaml：

service:
  telemetry:
    resource:
      service.name: otel-collector-training
      deployment.environment.name: local
    logs:
      level: info
    metrics:
      level: detailed

Metrics verbosity 有 none/basic/normal/detailed，default 是 normal。Detailed 增加可見性，也可能增加 dimensions/cost； 應依 troubleshooting 需求選擇。Internal telemetry declarative config schema 仍在演進，實作時必須以 pinned Collector version 文件驗證。 本片段沒有執行，也沒有改變 listener exposure。

Ingress：accepted 與 refused

以 Traces 為例：

  • otelcol_receiver_accepted_spans：receiver 已成功 ingest 並推入 pipeline 的 Spans。
  • otelcol_receiver_refused_spans：無法推入 pipeline 的 Spans。

Metrics/Logs 有對應 metric_points/log_records variants。這些是 cumulative Counters，觀察時通常取 rate/increase， 不是把絕對值當「目前有多少」。Accepted 上升證明資料跨過 receiver boundary，但不保證走到 exporter/backend。

Refused 持續上升表示 errors 回到 clients；是否實際 loss 取決於 client retry/buffer 與錯誤處理。Refusal 是風險證據，不等於每一筆都已永久消失。

Processors：incoming 與 outgoing 要結合 policy 解讀

  • otelcol_processor_incoming_items
  • otelcol_processor_outgoing_items

Filter/sampling processor 的 outgoing 少於 incoming 可能是預期 policy；batch processor 改變 batches/cadence，但不應任意改變 signal semantic counts。 差值只有在知道 component type、attributes 與配置後才有意義。不要對所有 processors 套「in 必須等於 out」告警。

Sending queue：state 與 failure counters

  • otelcol_exporter_queue_size：目前 queue batches。
  • otelcol_exporter_queue_capacity：固定 capacity，單位 batches。
  • otelcol_exporter_enqueue_failed_spans 等：Exporter 無法把 items 放進 sending queue。

Queue utilization 可近似 size / capacity。單次尖峰不一定異常；持續接近 1 且 enqueue failures 增加，才強烈支持 queue saturation/loss risk。 Queue size 是 Gauge，要看 current/trend；enqueue failures 是 Counter，要看 rate/increase。

Egress：sent 與 send_failed

  • otelcol_exporter_sent_spans 等：Exporter 成功送往 destination 的 items。
  • otelcol_exporter_send_failed_spans 等：送出嘗試失敗的 items。

Send failures 不天然等於 data loss，因為 queue/retry 可能稍後成功。判讀要同時看 sent rate、queue trend、retry deadline、enqueue failures 與 backend response。 若 failed spike 後 sent 上升、queue 回落，較像 transient outage 已恢復；若 queue 滿且 failures 持續，loss risk 高。

Metric naming：先看 transport representation

官方表列的是 OTLP names，例如 otelcol_exporter_send_failed_spans。Prometheus exporter 對 Sum metrics 通常加 _total，unit suffix 設定也可能改變 exposition name；不同 Collector 版本的 instrumentation names 曾演進。

因此 dashboard/query 應先查看實際 /metrics exposition 與 pinned version 文件，不因搜尋不到 raw OTLP name 就判定 Collector 沒 emit。 升級時把 internal telemetry schema/names 當 compatibility surface 測試。

SRE debugging lab：Backend 沒有新 Traces

1. Accepted rate 是零

問題在 receiver 之前或 activation：application exporter、DNS/network/TLS、endpoint/protocol/path、receiver listening/pipeline reference。 此時不需先調 backend query。

2. Accepted 上升，processor outgoing 變零

定位第一個 incoming 有、outgoing 無的 processor；檢查 filter/sampling/order/transform errors。若這是預期 drop policy，則資料缺失符合 config， 需要檢討 policy 而非 transport。

3. Accepted 上升、queue 上升、sent 接近零

出口/back-end bottleneck：查 send failures、endpoint/TLS/auth、backend throttling 與 retry。依 Lesson 28 計算 time-to-full， 先保護 loss budget，再處理根因。

4. Sent 上升，backend query 仍空

Collector 已完成自己的 egress contract，但仍需查 backend acceptance semantics、tenant/index/routing、retention/query time range 與 ingestion delay。 Sent 不是「使用者 UI 一定能查到」的保證。

練習：依數字定位 
accepted_spans rate = 2,000/s
refused_spans rate = 0
queue_size = 900 / capacity 1,000 and rising
send_failed_spans rate = 1,800/s
sent_spans rate = 200/s

先計算 net backlog 趨勢，估計接近 full；將故障域放在 exporter/downstream，而非 application instrumentation。
