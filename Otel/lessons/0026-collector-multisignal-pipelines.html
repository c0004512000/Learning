26. Collector 多信號 pipelines 與隔離

共享 ingress，不混合 data model；分開 graph，仍共享 process resources · Lesson 26 of N

本課成果

你會把 Traces、Metrics、Logs 還原成三條 typed Collector graphs，理解同一 receiver declaration 如何服務多種信號、具名 component instances 如何建立 signal-specific policy，以及 config-level isolation 與 process-level isolation 的差異。

主要來源：Collector Configuration、Collector Architecture

第一性原理：共同 transport 不等於共同資料模型

OTLP 能在同一 gRPC/HTTP listener 接收 Traces、Metrics、Logs，但三種信號有不同 records、aggregation/lifecycle 與 processors。 Receiver 負責 ingress/protocol decode；pipeline 的 signal type 決定資料接下來能流向哪些 compatible components。 

OTLP receiver 127.0.0.1:4318
  ├─ /v1/traces  → traces pipeline  → Span batches
  ├─ /v1/metrics → metrics pipeline → Metric data
  └─ /v1/logs    → logs pipeline    → LogRecords

「都走 OTLP」不會把 Metric 轉成 Span，也不會讓 traces pipeline 自動處理 Logs。Protocol envelope 統一搬運方式， signal data model 仍維持 typed separation。

讀懂三條 active graphs

範例位於 examples/0026-multisignal-collector.yaml：

traces:  otlp → batch/traces  → debug/traces
metrics: otlp → batch/metrics → debug/metrics
logs:    otlp → batch/logs    → debug/logs

Top-level otlp receiver 只宣告一次，三條 pipelines 都引用它。每條 graph 仍有自己的 signal type、processor instance 與 exporter instance。這讓 log batch policy 不必與 traces 相同，也讓 debug output 的 component identity 可分辨信號。

type/name 讓同一 component type 有多個 policy instances

batch/traces
batch/metrics
batch/logs

三者 type 都是 batch，斜線後是 instance name。Named instances 可有不同 queue/batch parameters 並被不同 pipelines 引用。 名稱本身沒有功能；功能來自 type、config 與 active reference。

Instance範例 batch size教學意圖
batch/traces256與其他 signals 分開觀察，不宣稱是 production 最佳值。
batch/metrics512Metric export payload/cadence 可獨立設計。
batch/logs128高 volume/big records 可有另一組 policy。

這些值只用來讓 instance 差異可見，未經 workload measurement 不能當作 production recommendation。

Declaration、activation、compatibility 再次套用

  1. Declaration：列出 otlp、三個 batch/*、三個 debug/*。
  2. Activation：從 service.pipelines.traces|metrics|logs 解析 references。
  3. Compatibility：確認每個 component/distribution 支援該 signal。
  4. Order：每條 graph 依 receiver → processors → exporters。
  5. Evidence：為每條 signal 定義獨立成功與 failure evidence。

若只宣告 debug/logs 卻沒放進 logs pipeline，它不會收到資料；若只建立 traces pipeline，OTLP receiver 不會因為能解析 Logs 就替你創造 logs graph。Lesson 12 的規則跨 signals 不變。

Config 分離不等於故障域完全分離

Logical isolation:
  separate queues/config/exporters/pipeline evidence

Shared process reality:
  Collector CPU + memory + network + GC + process lifecycle

三條 pipelines 在同一 Collector process 中，log storm 仍可能耗盡 shared CPU/memory/network，間接影響 Trace/Metric latency/drop。 Named processors 降低 policy coupling，但不提供硬式 resource isolation。若 SLO、tenant、security 或 volume 差異很大， 才進一步評估拆成不同 Collector deployments/processes；這是 deployment architecture 決策，不是多取幾個 instance name 就完成。

隔離是一條光譜：不同 component config → 不同 pipelines → 不同 Collector processes → 不同 nodes/accounts。 每往右成本與操作複雜度上升，也增加故障/安全隔離。先從威脅與 SLO 推導，不追求形式上的「全部分開」。

跨信號 correlation 依賴共同 identity，不是 pipeline merge

Traces、Metrics、Logs 各自輸出，但若 application providers 使用一致的 service.namespace/name/version/instance Resource， backend 才能把它們歸到同一 entity。Log 的 TraceId/SpanId、Metric Exemplar 再建立 record-level correlation。

Collector 三條 pipelines 不會因為同一 receiver 就自動補齊 identity。若 application signals 的 service.name 不一致， 應修正 source/Resource enrichment policy；不要用模糊字串匹配假裝關聯。

Transport success 要按 signal/endpoint 精確描述

OTLP/HTTP 4318 listener 活著只能證明 socket/service 層的一部分。Traces 送到 /v1/traces 成功，不代表 application 已建立 MeterProvider/MetricReader，或 /v1/metrics request 成功。Shared host/port 提供部分排除證據，但每個 signal 仍有獨立 source/export/pipeline。

SRE debugging lab：Traces 有、Metrics 無

以已知成功的 traces 縮小範圍：

  1. Collector process、host reachability、OTLP/HTTP listener 大致可用。
  2. 不要重查 Trace instrumentation；改查 application MeterProvider、MetricReader、collection/shutdown。
  3. 確認 Metric exporter endpoint/path 是 /v1/metrics，不是 traces path。
  4. 確認 Collector metrics pipeline active 且引用 otlp。
  5. 查看 batch/metrics 與 debug/metrics 的 signal-specific evidence。

若 Traces 使用 gRPC 4317、Metrics 使用 HTTP 4318，Trace success 甚至不能完全證明 Metrics transport path； 每項推論要列出共同邊界與不同邊界。

故障注入 A：移除 metrics pipeline

Receiver declaration 仍在，Traces/Logs 可正常；Metrics 沒有 active graph。預測 config validation/startup 行為與 client export evidence， 再用實際 distribution 驗證，不把「receiver 有 metrics capability」當 activation。

故障注入 B：大量 Logs 造成全 signals 延遲

查看 Collector process memory/CPU、各 receiver accepted/refused、processor queue/batch/export latency 與 exporter failures。 若三條 signal 同時惡化，shared resource saturation 比三個獨立 instrumentation bugs 更值得先驗證。

練習：畫 fault-domain matrix

列 rows：application SDK、transport、receiver、signal pipeline、shared Collector process、backend；列 columns：traces/metrics/logs。 在每格填成功證據。只要某 column 成功，就標出它能排除哪些 shared rows、不能排除哪些 signal-specific cells。
