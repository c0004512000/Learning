3. 讓第一個 Python Span 出現在眼前

先建立 Span，再從「為什麼看不到？」推導 Processor 與 Exporter · Lesson 3 of N

這一課只要拿下一個勝利

Lesson 2 已經建立：TracerProvider 提供 Tracer，Tracer 建立 Span。 這一課只做下一件事：真的執行 Python，讓一個 Span 出現在 terminal，並理解為什麼需要新的元件。

1. 先只使用你已經懂的三個角色

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider

provider = TracerProvider()
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("training.checkout")

with tracer.start_as_current_span("checkout.calculate_total"):
    total = 100 + 200

到這裡的因果關係只有：

TracerProvider
    | 提供
    v
  Tracer
    | 建立
    v
   Span

但是你執行這段程式時，terminal 幾乎什麼 Span 資料都看不到。 這不是因為 Tracer 不存在，而是我們還沒有回答另一個問題： 已經完成的 Span 要怎麼離開 SDK，變成我們看得見的輸出？

2. 先推出 Exporter：誰真的把資料輸出去？

如果目標只是學習，我們最簡單的需求是：把 Span 印到 terminal。 因此需要一個知道「怎麼把 Span 輸出到某個目的地」的角色。 OpenTelemetry 把這個角色叫做 SpanExporter。

本課使用它的一個具體實作：

ConsoleSpanExporter()
ConsoleSpanExporter = 把可輸出的 Span 資料寫到 terminal 的 exporter。 它不是 backend，也不會儲存歷史 Trace；它只是讓資料離開 SDK、變成 stdout 上看得到的文字。

來源：OpenTelemetry — Standard output Span Exporter

3. 但又出現一個問題：誰在 Span 結束時呼叫 Exporter？

Tracer 的責任是建立 Span。Exporter 的責任是輸出。 還需要一個 SDK lifecycle hook，在 Span 結束時接到它，再交給 Exporter。 這個角色叫做 SpanProcessor。

為了先看懂最直接的版本，本課使用：

SimpleSpanProcessor(ConsoleSpanExporter())

可以直接讀成：

Span 結束
   |
   v
SimpleSpanProcessor
   | 立即交給
   v
ConsoleSpanExporter
   | 寫到
   v
terminal
為什麼先用 Simple，不用 Batch？ SimpleSpanProcessor 在 Span 結束後直接交給 exporter，因果關係最容易看清楚。 Production 常見的 BatchSpanProcessor 會再加入 queue、batch、timer 等行為；等需要理解效能與可靠性時再學。

來源：Tracing SDK — Span processor

4. 現在把 Processor 掛到誰身上？

Lesson 2 已經知道，application 共用的 tracing configuration 放在 TracerProvider。 所以 Processor 也不是掛在某一個 Tracer 上，而是註冊到 Provider： 

provider = TracerProvider()
provider.add_span_processor(
    SimpleSpanProcessor(ConsoleSpanExporter())
)
trace.set_tracer_provider(provider)

現在完整路徑才成立：

5. 用 Python logging 再對照一次

這個結構可以用熟悉的 logging 做角色類比： 

Logging                         Tracing

Logger                          Tracer
  |                               |
  | 產生                          | 建立
  v                               v
Log Record                       Span
  |                               |
  | Handler 處理/輸出              | SpanProcessor 接生命週期
  v                               v
StreamHandler / FileHandler     SpanExporter
  |                               |
  v                               v
terminal / file                 terminal / OTLP / ...

兩套系統的細節並不相同；這個對照只幫你抓住「產生 telemetry 的物件」與「把 telemetry 送往目的地的元件」是不同責任。

6. 再加一個很實際的問題：這份 telemetry 是哪個 service 產生的？

Span 已經能輸出了，但 terminal 上最好能知道它屬於哪個 service。 這種描述 telemetry producer 的共用資訊，OTel 放在 Resource。 

from opentelemetry.sdk.resources import Resource

resource = Resource.create({
    "service.name": "checkout-demo"
})

provider = TracerProvider(resource=resource)

service.name 描述的是「哪個 logical service 產生這些 telemetry」， 不是這一次 Span 做了什麼。這就是為什麼它屬於 application 共用的 Resource，而不是 Span name。

7. 最後才組成完整的可執行程式

實際範例在 examples/0003-first-span.py： 

from opentelemetry import trace
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import (
    SimpleSpanProcessor,
    ConsoleSpanExporter,
)

resource = Resource.create({"service.name": "checkout-demo"})
provider = TracerProvider(resource=resource)
provider.add_span_processor(
    SimpleSpanProcessor(ConsoleSpanExporter())
)
trace.set_tracer_provider(provider)

tracer = trace.get_tracer("training.checkout")

with tracer.start_as_current_span("checkout.calculate_total") as span:
    prices = [1999, 1250, 425]
    span.set_attribute("app.cart.item_count", len(prices))
    total = sum(prices)
    span.set_attribute("app.cart.total_cents", total)
    print(f"Total: {total} cents")

8. 執行它

在教學 workspace 根目錄以 PowerShell 執行：

python -m venv .venv
.\.venv\Scripts\python.exe -m pip install opentelemetry-api opentelemetry-sdk
.\.venv\Scripts\python.exe .\examples\0003-first-span.py

你應該先看到 business output：

Total: 3674 cents

接著看到 ConsoleSpanExporter 印出的 Span。實際欄位順序可能隨 SDK 版本不同，但應能找到類似：

  "name": "checkout.calculate_total",
  "context": {
    "trace_id": "0x...",
    "span_id": "0x..."
  },

注意：ConsoleSpanExporter 的文字格式只是 debugging / learning 用的顯示方式，並不是 OTLP wire format。 下一課會專門練習如何讀這份 Span，而不是背 JSON 排版。

9. SRE debug：如果 terminal 沒有 Span，要從哪裡切？

不要一次懷疑所有元件，沿剛才的因果鏈往後查：

1. Tracer 有沒有真的進入 start_as_current_span()？
2. Span 有沒有結束？
3. Provider 有沒有註冊 SpanProcessor？
4. SpanProcessor 有沒有連到 ConsoleSpanExporter？
5. Exporter 的 stdout 是否真的可見？

這就是之後 debug OTel pipeline 的基本習慣：先找資料最後在哪個已知節點存在，再檢查它到下一個節點的交接。

練習：從缺少的能力推出元件

Q1. Tracer 已成功建立 Span，但你需要把完成的 Span 寫到 terminal。哪個元件真正負責輸出？
Q2. 為什麼還需要 SpanProcessor？
Q3. service.name 為什麼放在 Resource？

最後 Recap：每個名詞只留一句話

Span：某一次工作的觀測資料。

Trace：同一次端到端 operation 中，彼此有因果關係的一組 Span。

Tracer：程式拿來建立 Span 的物件。

TracerProvider：管理 application 共用 tracing 設定，並提供 Tracer 的物件。

SpanProcessor：接收 Span 的 lifecycle，並決定如何把完成的 Span 交給 Exporter。

SpanExporter：把可輸出的 Span 資料送往某個目的地。

ConsoleSpanExporter：把 Span 寫到 terminal，方便學習與 debug。

Resource：描述產生 telemetry 的實體或服務的共用 metadata。

你現在應該能自己畫出這條鏈： TracerProvider → Tracer → Span → SpanProcessor → SpanExporter。 如果任何一個箭頭你說不出「為什麼需要下一個」，就把那個箭頭丟給我，我們只拆那一段。
