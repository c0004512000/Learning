3. 讓第一個 Python Span 出現在眼前

把已理解的元件角色實作成第一條 telemetry pipeline · Lesson 3 of N

先把 Lesson 2 的角色地圖翻成 Python

這一課不會引入新的 pipeline。它只把你已經理解的兩個階段寫成程式： application startup 時設定 Provider、Processor 與 Exporter；每次 operation 執行時， Tracer 建立 Span，Span 結束後再由 Processor 交給 Exporter。 

Startup（一次）:
  TracerProvider + BatchSpanProcessor + ConsoleSpanExporter
  -> 取得 Tracer

Runtime（每次被觀測的工作）:
  Tracer -> Span 開始 -> 執行工作 -> Span 結束
  -> BatchSpanProcessor -> ConsoleSpanExporter -> terminal output

這個拆分讓 business instrumentation 不需知道最終資料目的地； 日後把 ConsoleSpanExporter 換成送往 Collector 的 Exporter，主要改的是 startup configuration。

這一課的實作成果

執行 examples/0003-first-span.py， 讓終端機印出一個真的 Span。這不是 tracing backend，只是最短的 feedback loop： 你能親眼確認 provider、processor、exporter 與 Span data model 都有作用。

設定環境並執行

在這個教學工作區的根目錄，以 PowerShell 執行：

python -m venv .venv
.\.venv\Scripts\python.exe -m pip install opentelemetry-api opentelemetry-sdk
.\.venv\Scripts\python.exe .\examples\0003-first-span.py
為什麼 application 需要 SDK？ opentelemetry-api 提供 vendor-neutral 的埋點介面；SDK 才負責真正的 recording、 sampling、processing 與 exporting。相反地，若你在寫一個可被別人引用的 library，通常只依賴 API， 讓使用該 library 的 application 決定是否安裝 SDK 與資料目的地。

逐段判讀程式

1. Resource：誰產生 telemetry？

resource = Resource.create({"service.name": "checkout-demo"})

service.name 不是這次工作做了什麼，而是「哪個 logical service 產生所有這些資料」。 Resource 會在 provider 建立時附加，並關聯到它之後產生的所有 Spans。若未設定， SDK 預設會使用 unknown_service。

2. Provider、Processor、Exporter：結束的 Span 怎麼離開 process？

provider = TracerProvider(resource=resource)
provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)

TracerProvider 是 process 層級的 SDK configuration owner； 它擁有 Resource、sampling 與 span processors 等設定。 BatchSpanProcessor 將已結束的 Span 放入 queue 後批次交給 exporter， 避免每個 request 都在 application thread 上直接輸出或送網路。 ConsoleSpanExporter 只是本課的可見 sink；production 通常會改用 OTLP exporter。

3. Tracer：哪一段程式在埋點？

tracer = trace.get_tracer("training.checkout", "0.1.0")

這個名稱是 instrumentation scope，用來識別哪個 module/library 產生 Span； 它不是 service.name。一個 service 可以包含多個 instrumentation scopes。

4. Context manager：工作何時開始、何時結束？

with tracer.start_as_current_span("checkout.calculate_total") as span:
    # 被觀測的工作
    ...

進入 with 時會開始並設為 current Span；離開時即使 block 因 exception 離開， Span 也會結束。這個「current」概念是下一階段讓 child Span 與跨服務 propagation 自動找到 parent 的基礎。

5. Attributes：這一次 operation 有什麼可查資料？

span.set_attribute("app.cart.item_count", len(item_prices_cents))
span.set_attribute("app.cart.total_cents", total_cents)

這兩個是 custom domain Attributes，用於描述這一次的計算；它們不是 service identity， 也不是 Span identity。後續會學何時應使用 Semantic Conventions、何時須避免敏感資料或高基數 values。

你應該在 console 看到什麼？

實際欄位順序與值會隨 SDK 版本而異，但結構應接近：

{
  "name": "checkout.calculate_total",
  "context": {
    "trace_id": "0x...",
    "span_id": "0x..."
  },
  "parent_id": null,
  "attributes": {
    "app.cart.item_count": 3,
    "app.cart.total_cents": 3674
  },
  "resource": {
    "attributes": {
      "service.name": "checkout-demo"
    }
  }
}
檢查你的輸出：先找 name、parent_id、 attributes 與 resource.service.name。如果任何一項不符合預期， 把完整輸出貼給我；我們會用它練習像 SRE 一樣從 telemetry 反推設定問題。
