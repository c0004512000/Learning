2. 從 Python 看懂 Tracing API、SDK、Provider 與 Tracer

先看程式裡「誰從哪裡 import、誰呼叫誰」，再談抽象名詞 · Lesson 2 of N

這一課只要拿下一個勝利

看完後，你應該能打開一段 OpenTelemetry Python 程式，指出： 哪一段是 API、哪一段是 SDK、TracerProvider 在 startup 做什麼、Tracer 在 runtime 做什麼。

先不要背整條 pipeline。 你上次卡住的原因，是 Tracing API、SDK、TracerProvider、 Tracer、SpanProcessor、Exporter 被當成同一層級的名詞一起介紹。 其實它們不是同一種東西。本課先把「層」和「物件」拆開。

第一步：API 與 SDK 甚至是兩個不同的 Python package

pip install opentelemetry-api
pip install opentelemetry-sdk

再看最關鍵的兩個 import：

# API：埋點程式呼叫的公開操作
from opentelemetry import trace

# SDK：application 啟動時選擇的具體實作
from opentelemetry.sdk.trace import TracerProvider
你現在看到的東西 它屬於哪一層 程式為什麼碰它
trace.get_tracer(...) Tracing API 埋點程式要求「給我一個可以建立 Span 的 Tracer」
tracer.start_as_current_span(...) Tracing API 埋點程式要求「開始描述這段工作」
TracerProvider() Tracing SDK implementation application 建立真正負責 tracing 行為與設定的 provider

來源： OpenTelemetry Python — Manual Instrumentation。 官方明確區分：application 用 SDK 初始化 OpenTelemetry，再用 API 做 instrumentation。

如果只有 API，會發生什麼？

先看一段完全合法的 instrumentation：

from opentelemetry import trace

tracer = trace.get_tracer("checkout")

with tracer.start_as_current_span("checkout.calculate_total"):
    total = 100 + 200

這段程式知道怎麼「要求開始一個 Span」，但它完全沒有說： 要不要真的記錄？要怎麼處理？最後送去哪裡？

關鍵事實： 在沒有安裝／設定 SDK 的情況下，Trace API 的一般行為是 no-op： 程式仍能呼叫 API，但新的 Span 不會被真正記錄與輸出。 這也是為什麼一個 library 可以安全地只依賴 API，而不替使用它的 application 決定 tracing backend。

來源： OpenTelemetry Trace API Specification — Behavior without an SDK 。

那 SDK 到底補上了什麼？

application startup 時加上這三行：

provider = TracerProvider()
trace.set_tracer_provider(provider)

tracer = trace.get_tracer("checkout")

先只看這三行，不要管 Processor 或 Exporter。

所以 API 不是另一個 tracing engine。 API 是 application / library 用來提出 tracing 操作的公開介面； SDK 則提供被 application 安裝進去的具體 tracing 行為。

TracerProvider 跟 Tracer 為什麼不能只留一個？

直接看它們在程式中的生命週期：

# startup：通常做一次
provider = TracerProvider()
trace.set_tracer_provider(provider)

# instrumentation：取得後重複使用
checkout_tracer = trace.get_tracer("checkout")
db_tracer = trace.get_tracer("database")
TracerProvider Tracer
主要時機 application startup instrumentation runtime
主要責任 持有／提供這組 tracing 的共用設定與 Tracer 提供建立 Span 的操作入口
你會寫的程式 TracerProvider() tracer.start_as_current_span(...)
它會直接 export 嗎？ 不直接 export 不直接 export
名稱上的陷阱： OpenTelemetry specification 裡的 TracerProvider 是一個 API contract； 而 Python 的 opentelemetry.sdk.trace.TracerProvider 是 SDK 提供、你真的會 instantiate 的具體實作。 不要把「角色名稱」和「Python class 從哪個 package import」混成同一件事。

來源： Tracing API — TracerProvider、 Tracing SDK — Tracer Creation。

現在才加入 Processor 與 Exporter

到這裡，你已經知道 Span 是怎麼被建立的。下一個問題才是： Span 結束後，SDK 要怎麼把它送出 process？ 

from opentelemetry.sdk.trace.export import (
    BatchSpanProcessor,
    ConsoleSpanExporter,
)

processor = BatchSpanProcessor(ConsoleSpanExporter())
provider.add_span_processor(processor)

這裡最容易被名字騙到，所以先分「角色」與「具體實作」：

SpanProcessor          ← 一種 SDK 角色 / extension point
└── BatchSpanProcessor ← 其中一種具體實作：queue + batch

SpanExporter           ← 一種 SDK 角色 / extension point
└── ConsoleSpanExporter← 其中一種具體實作：寫到 terminal

因此 BatchSpanProcessor 不是「另一種 Tracer」， ConsoleSpanExporter 也不是「Trace 儲存庫」。 前者處理 Span lifecycle 與批次交付；後者只是把資料輸出到一個具體目的地。

把全部組回一支最小 Python 程式

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import (
    BatchSpanProcessor,
    ConsoleSpanExporter,
)

# ── SDK configuration：application startup ──
provider = TracerProvider()
processor = BatchSpanProcessor(ConsoleSpanExporter())
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)

# ── Tracing API：instrumentation/runtime ──
tracer = trace.get_tracer("training.checkout")

with tracer.start_as_current_span("checkout.calculate_total"):
    total = 100 + 200
讀這支程式時，不要再背「A → B → C → D」。
先問兩題：
  1. 這行是在 設定 SDK 行為，還是在 透過 API 描述我要觀測的工作？
  2. 這個名字是「抽象角色」，還是這次 Python 程式真的 instantiate 的「具體 implementation」？

SRE Debug 視角：Span 沒出現在 terminal 時，怎麼拆？

不要從「OTel 壞了」開始猜。沿著責任邊界檢查：

1. instrumentation 有沒有真的執行？
   └─ tracer.start_as_current_span(...) 有走到嗎？

2. Span 有沒有被 SDK 記錄？
   └─ span.is_recording() 是 True 嗎？

3. Provider 有沒有掛 Processor？
   └─ provider.add_span_processor(...) 有設定嗎？

4. Processor 後面有沒有正確 Exporter？
   └─ ConsoleSpanExporter() 是否真的被接上？

這就是之後 debug Collector、OTLP 或 production pipeline 時要養成的思路： 先確認資料在哪一個責任邊界消失，而不是一次猜整條鏈。

這一課真正要留下的四句話

  1. Tracing API 是 instrumentation code 使用的操作介面。
  2. SDK 是 application 安裝並設定在 API 背後的具體 tracing 實作。
  3. TracerProvider 管共用 tracing 行為並提供 Tracer；Tracer 被 instrumentation 用來建立 Span。
  4. BatchSpanProcessor 與 ConsoleSpanExporter 是 SDK 裡兩個具體實作，負責 Span 結束後的處理與輸出。
