2. Tracing 元件如何一起工作

用同一個 Python process 看懂 startup 與 runtime · Lesson 2 of N

這一課只解一個問題

看到 Tracer、TracerProvider、SpanProcessor 和 Exporter 時，你應該能回答：它們在什麼時間被建立？彼此如何連接？ 每次 request 到來時，資料又沿著哪條路走？

先固定一個具體情境：把 Checkout application 想成一個會持續執行的 Python process。它啟動一次，接著可能處理 100 個 checkout requests。Startup 是在 process 裡建造一條可重用的 tracing 路徑；runtime 是每個 request 使用這條路徑。 本課術語可隨時查閱 Tracing SDK building blocks glossary。

先分清楚兩種東西

種類 它是什麼 在這一課的例子
長期存在的元件 Startup 建立後留在 process 記憶體中，等待之後的工作。 Provider、Processor、Exporter、Tracer
每次工作的資料 Runtime 為某個 operation 新增，結束後交給處理路徑。 Span、它的 attributes 和 events

圖 1：Startup 建造什麼，誰持有誰？

先不要把這張圖當成時間順序。它是在回答物件關係：application 建立 TracerProvider，Provider 持有共用設定，並把 SpanProcessor 接到它的處理路徑；Processor 再使用 Exporter 把資料送出去。 這條由元件組成的處理路徑，就是常說的 tracing pipeline。

因此，startup 完成後不是「Provider 把每個 Span 傳給 Tracer」。正確的理解是： Provider 先把處理規則與 pipeline 準備好，再提供一個可重複使用的 Tracer； runtime 的 instrumentation 透過這個 Tracer 建立 Span。

圖 2：同一個 process 的時間軸

這張圖才是時間順序。先從左到右看上面的 Startup lane；它走完一次後， process 不會消失，而是繼續往下等待 request。下面的 Runtime lane 可以重複很多次。

用一句話重畫這兩張圖： Startup 建立 Provider → Processor → Exporter 的關係， 並取得 Tracer；每次 runtime request 則使用既有的 Tracer 建立新的 Span，Span 結束後回到既有的 Processor，再由 Exporter 輸出。

把因果關係拆成 4 個事件

  1. Provider 先存在：沒有 startup 的設定，Tracer 不知道要採用什麼 SDK 行為。
  2. Tracer 才能被重用：instrumentation 不必知道 queue、batch 或目的地的細節。
  3. Span 結束才交接：Processor 收到的是已完成的 Span 資料，而不是尚未完成的 operation。
  4. Batch 可能延後輸出：Span 已經交給 Processor，不代表 Exporter 會在同一個 CPU 時刻立刻輸出。

為什麼 OTel 要分成 API 與 SDK？

假設一個 HTTP library 想在「處理 request」前後建立 Span。這段 instrumentation （加上 observability 行為的程式碼）只需要知道如何取得 Tracer、開始和結束 Span； 它不應該被迫綁定某一家 tracing backend。

Library / instrumentation 只描述「我要追蹤這段工作」
遵循契約
Tracing API vendor-neutral 的共通操作
由 application 安裝
SDK 真正 recording、processing、exporting 的實作

在 Python，opentelemetry.trace 是 tracing API 的主要入口；Tracer 是程式透過 API 取得、用來建立 Span 的物件。「Tracer API」不是要另外尋找的 TracerAPI class。 API 定義「程式可以要求什麼」；SDK 實作「這個要求 如何被記錄、處理與輸出」。

每個元件只解決一個問題

元件 它解決的問題 它不是什麼
Tracing API 提供 vendor-neutral 的共通操作，例如取得 Tracer、開始 Span。 不是 storage backend，也不替 application 選 exporter。
SDK 實作 API 的實際行為：record Span、套用設定、處理與輸出。 不是單一後端產品。
TracerProvider application 的 tracing control center；建立 Tracer 並擁有共用 SDK configuration。 不是每個 Span 的資料 transport。
Tracer 某段 instrumentation 用來建立 Span 的 handle。 不負責儲存、查詢或直接 export Span。
SpanProcessor 在 Span 開始或結束的適當時機接手資料；本課聚焦它在 Span 結束後交給 Exporter 的工作。 不是 telemetry 的最終目的地。
BatchSpanProcessor 一種 SpanProcessor：先將結束的 Span 放入暫存 queue，再成批輸出，降低每次 operation 的直接 I/O 成本。 不是後端，也不改變 Span 的 parent-child 關係。
Exporter 將 Span 送到一個具體目的地的轉接元件。 不決定業務程式要建立哪些 Span。
ConsoleSpanExporter 把 Span 印到 terminal output，提供最快的本機 feedback loop。 不是可搜尋、可長期保存的 tracing backend。

SDK configuration 到底指什麼？

它不是一個額外元件，而是 application 在 startup 對 Provider 做的一組選擇： 使用哪個 SDK、Span 結束後交給哪個 Processor、最後由哪個 Exporter 送往何處， 以及資料屬於哪個 service。可以把它理解成建造圖 1 那條處理路徑時的決策集合。

例如，ConsoleSpanExporter 只適合本機 feedback；日後若改成送往 Collector 的 exporter，主要改動發生在 startup 的 destination configuration。runtime 的 Tracer 建 Span 原則上保持不變，這就是 API/SDK separation 的實際價值。
