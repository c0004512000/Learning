2. 從 Span 推導 Tracer 與 TracerProvider

先從 Span 問「誰建立它？」，再釐清 Tracer 的 scope 與 Provider 真正提供什麼 · Lesson 2 of N

這一課只要拿下一個勝利

看完後，你應該能不用背架構圖，自己解釋：Span 是什麼、Tracer 做什麼、 get_tracer(name) 的 name 代表什麼、TracerProvider 為什麼即使只有一個 Tracer 仍然需要存在。

本課不把 Tracer 當成 Trace 裡的一層。 Trace / Span 是「工作發生了什麼」的資料；Tracer / TracerProvider 是 application 產生這些資料時使用的程式物件。 這兩個世界要分開看。

1. 先從 Span 開始：我們到底要產生什麼？

Lesson 1 已經知道，Span 是某一次工作的觀測資料。 假設程式正在執行： 

calculate_total()

如果我們想觀測這一次執行，就需要留下類似：

name = "calculate_total"
start_time = ...
end_time = ...
duration = ...
attributes = ...

這一份「描述某一次工作」的資料，就是 Span。

calculate_total 第 1 次執行  -> Span A
calculate_total 第 2 次執行  -> Span B
calculate_total 第 3 次執行  -> Span C

來源：OpenTelemetry — Traces

2. 下一個必要問題：Python 程式要怎麼建立 Span？

既然我們需要 Span，那程式裡一定要有某個東西負責建立它。 OpenTelemetry 把這個物件叫做 Tracer。 

span = tracer.start_span("calculate_total")
Tracer = 程式拿來建立 Span 的物件。

3. 用 Python Logger 對照 Tracer

如果你用過 Python logging，這個角色很像：

import logging

logger = logging.getLogger("checkout")
logger.info("calculating total")

Logger 不是那一筆 log 本身；它是程式拿來產生 log record 的物件。 Tracer 也不是 Trace 資料本身；它是程式拿來建立 Span 的物件。

LoggingTracing
LoggerTracer
產生 Log Record建立 Span
logger.info(...)tracer.start_span(...)
類比的邊界：Logger 與 Tracer 的內部實作不同；這個類比只用來抓住角色： 「程式持有一個物件，再用它產生 telemetry」。

4. 一個 application 可以從頭到尾只用同一個 Tracer 嗎？

可以。 不同程式片段並不必然需要不同 Tracer。

tracer = trace.get_tracer("myapp")

with tracer.start_as_current_span("calculate_total"):
    ...

with tracer.start_as_current_span("charge_card"):
    ...

with tracer.start_as_current_span("save_order"):
    ...

同一個 Tracer 可以持續建立很多不同 Span：

Tracer("myapp")
   |
   +-- Span("calculate_total")
   +-- Span("charge_card")
   +-- Span("save_order")
所以不要把 Tracer 理解成「一段程式碼的代表」。 要不要拆成多個 Tracer，是 instrumentation 如何劃分「telemetry 產生來源」的設計選擇，不是 Trace parent/child 關係的要求。

5. 那 get_tracer("myapp.checkout") 的名字到底代表什麼？

from opentelemetry import trace

tracer = trace.get_tracer("myapp.checkout")
span = tracer.start_span("calculate_total")

這兩個名稱回答完全不同的問題：

名稱回答的問題
"myapp.checkout"哪個 instrumentation scope 產生這些 telemetry？
"calculate_total"這一個 Span 描述的是什麼工作？

OpenTelemetry 把前者正式稱作 Instrumentation Scope。 它是一個「產生 telemetry 的邏輯軟體單位」，常見可以是 instrumentation library、package、module、class 或 application component。 所以這個 name 不是「被觀測的程式碼片段名稱」，也不只是隨便替 Tracer 取 nickname；它是在標記 telemetry 的產生來源。 

# Python 常見做法：用 module 名稱當 scope
tracer = trace.get_tracer(__name__)

來源：OpenTelemetry — Instrumentation Scope、 Trace API — Get a Tracer

6. Tracer 反映在 Trace / Span 圖上會是哪一個節點？

答案：它不是 Trace tree 裡的節點。

Trace
|
+-- Span: POST /checkout
|     scope = http-framework
|
+-- Span: calculate_total
|     scope = myapp.checkout
|
+-- Span: charge_card
|     scope = myapp.payment
|
+-- Span: SELECT orders
      scope = sqlalchemy

Trace tree 的節點是 Span；Tracer 不會插在 parent / child 中間。 Tracer 的 scope identity 會和它建立出的 telemetry 關聯，讓你知道「這個 Span 是哪份 instrumentation 產生的」。

Trace / Span：描述工作本身與工作之間的因果關係。
Tracer：建立 Span 的程式物件，並帶著 instrumentation source 的身份。

7. 現在才問 TracerProvider：它到底 provide 什麼？

先看最容易誤讀的一行：

provider = TracerProvider()

這一行還沒有 provide 一個 Tracer。 它就和普通 Python class 一樣：TracerProvider 是 class，TracerProvider() 呼叫 constructor， 建立一個 TracerProvider instance。 

TracerProvider      # class
TracerProvider()    # 建立 instance
provider            # 變數指向這個 instance

接著：

trace.set_tracer_provider(provider)
tracer = trace.get_tracer("myapp.checkout")

可以翻成人話：

TracerProvider()
# 建立一個 stateful tracing configuration owner

set_tracer_provider(provider)
# 告訴 OTel：之後取得 Tracer 時使用這個 Provider

get_tracer("myapp.checkout")
# 由目前的 Provider 提供一個對應 scope 的 Tracer
TracerProvider 真正 provide 的東西就是 Tracer。 同時，它是 application tracing 共用 configuration 的持有者。

來源：OpenTelemetry Trace API — TracerProvider

8. Provider 不是因為「有很多 Tracer」才需要存在

前一版教材把理由講成「application 有很多 Tracer，所以需要 Provider 管理它們」，這是不夠精確的推導。 即使 application 從頭到尾只有一個 Tracer，TracerProvider 仍然有存在理由。

因為 Tracer 的工作應該保持簡單：

Tracer
  -> 建立 Span

而 application-level tracing 規則集中在 Provider：

TracerProvider
  -> 持有共用 tracing configuration
  -> 提供 Tracer

Tracer
  -> 依 Provider 的 configuration 建立 Span

OpenTelemetry SDK specification 明確要求，SpanProcessors、Sampler、SpanLimits、IdGenerator 等 configuration 由 TracerProvider 擁有； Tracer 不應各自攜帶一份獨立設定。

來源：OpenTelemetry Tracing SDK — Configuration

9. TracerProvider 常見會放哪些共用設定？

目前先抓三個最常用、最能建立直覺的：

設定它回答的問題例子
Resource 這些 telemetry 是誰產生的？ service.name = checkout-service
Sampler 這個 Span 建立時，要不要 record / sample？ 全留、全丟、依比例或 parent 決策
SpanProcessor Span lifecycle 發生時，完成的 Span 接下來怎麼處理？ 下一課接到 ConsoleSpanExporter

Python 會開始長成：

resource = Resource.create({
    "service.name": "checkout-service"
})

provider = TracerProvider(
    resource=resource,
    sampler=my_sampler,
)

provider.add_span_processor(my_span_processor)

Resource 一旦和 TracerProvider 關聯，從這個 Provider 的 Tracer 產生的 Span 都會和該 Resource 關聯； Sampler 會在 Span 建立時參與 sampling decision；SpanProcessor 則收到 Span lifecycle callbacks。

現在不用背進階項目：Provider 還可以擁有 SpanLimits、IdGenerator 等設定。 先把心智模型壓成：Resource = 誰產生、Sampler = 記不記、SpanProcessor = 之後怎麼處理。 SpanProcessor / Exporter 下一課再完整推導。

來源：OpenTelemetry Resource SDK、 OpenTelemetry Tracing SDK

10. 到現在才補 API / SDK 的位置

現在物件角色已經清楚，再看 package boundary：

# instrumentation 呼叫的公開 tracing 操作
from opentelemetry import trace

# application 安裝的具體 tracing implementation
from opentelemetry.sdk.trace import TracerProvider

Tracing API 是 instrumentation code 可以呼叫的操作介面，例如 get_tracer()、start_span()； Tracing SDK 則提供真正 recording、sampling、processing 等行為的具體實作。 如果 application 沒有安裝 SDK provider，API 仍可以被 library 呼叫，但預設不會產生可輸出的 recorded telemetry。

來源：OpenTelemetry Python — Manual Instrumentation、 Trace API — Behavior without an SDK

練習：不要背名詞，從需要反推

Q1. 一個 application 有三種不同工作，要建立三種 Span。它一定需要三個不同 Tracer 嗎？
Q2. trace.get_tracer("myapp.checkout") 裡的 name 最主要是在識別什麼？
Q3. 即使 application 只用一個 Tracer，為什麼仍然需要 TracerProvider？

最後 Recap：每個名詞只留一句話

Span：某一次工作的觀測資料。

Trace：同一次端到端 operation 中，彼此有因果關係的一組 Span。

Tracer：程式拿來建立 Span 的可重複使用物件；它不在 Trace tree 裡。

Instrumentation Scope：識別是哪個邏輯軟體單位／instrumentation 產生 telemetry。

get_tracer(name)：向目前的 TracerProvider 取得代表該 instrumentation scope 的 Tracer。

TracerProvider：持有 application 共用 tracing configuration，並提供 Tracer 的 stateful object。

Resource：描述產生 telemetry 的服務或實體的共用 metadata。

Sampler：在 Span 建立時決定 recording / sampling 行為的規則。

Tracing API：instrumentation code 呼叫 tracing 功能的公開介面。

Tracing SDK：真正執行 recording 與 tracing configuration 的具體實作。
