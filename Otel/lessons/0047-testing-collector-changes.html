47. Testing Collector Changes

Config 可解析，只證明 syntax/schema；production-safe 必須逐層證明語意、容量、故障與 rollout · Lesson 47 of N

本課成果

你會建立 Collector change 的六層證明：resolve/validate、graph、semantic fixtures、end-to-end、load/failure、canary rollout； 理解每層能捕捉的 failure class，並在變更前寫好 rollback trigger、state/queue treatment 與 success criteria。

主要來源：Collector Configuration / Validate、Collector Troubleshooting、Collector Test Strategy

第一性原理：測試是在排除 Failure Classes

一個 Collector change 可能失敗於不同層：

source/resolution → schema → graph → data semantics
    → performance → failure recovery → production rollout

單一測試無法涵蓋全部。Config validate 通過，不能證明 OTTL condition 正確；一筆 fixture 正確，不能證明 60k spans/s 不 OOM； load test 正常，不能證明 backend outage 後 queue 可恢復；staging 正常，也不能證明 production tenant/routing mix。

Gate 1：Exact Distribution + Resolved Config

固定 binary/image digest、Collector/contrib version 與 component set，再解析所有 sources/substitutions/overrides：

  • 同名 component 在 core/contrib/custom distribution 未必存在或版本一致。
  • 不要只 validate base fragment；要 validate production 會使用的 final config。
  • 敏感值在診斷輸出中遮蔽；比較存在性、來源與 hash。
  • 官方 validate command 可檢查 configuration，但本章不執行 binary。

Gate 2：Graph Invariants

把 final config 轉成 active graph，驗證：

  • 每條 pipeline receiver/processor/exporter reference 都存在且 signal 相容。
  • Connector 同時是上游 exporter、下游 receiver；無意外 cycle/zero-route。
  • Memory limiter first、batch/drop/sampling/connector order 符合語意。
  • Security/auth extensions 已啟用並被 consuming component reference。
  • Stateful component 的 affinity/single-writer ownership 沒被 deployment change 破壞。

Gate 3：Semantic Fixtures

Fixture 是小而精確的 input→expected output contract。每條重要 policy 至少測：

Input class目的
Representative validhappy path transformation/routing
Missing attributenil/default/condition 行為
Wrong typeOTTL error mode、partial transform/drop
Sensitive valueredaction fail-open/fail-closed invariant
High-cardinality/extreme sizelimits、overflow、request bytes
Relationship caseparent-child、links、logs correlation、metric stream identity

Assertions 不只看「輸出存在」，也看 forbidden fields/destinations 不存在、count 不 duplicate、原本值是否被錯覆寫。 對 filter/routing 用 truth table；對 OTTL 逐 statement 算 state transition。

Gate 4：End-to-End Canary

把第 46 章 canary 從 realistic producer boundary 送過 production-like auth/network/config，到真 backend query。 這能捕捉 protocol/TLS/auth、backend schema/index/query 與多 hop config mismatch，這些不是 local debug exporter 可證明。

同時保留 component boundary evidence，否則 canary 只告訴你「壞了」卻不能定位 first bad edge。

Gate 5：Load 與 Failure

負載測試必須匹配 items + bytes + cardinality + signal mix：

  • Steady、peak、burst duration、peak+headroom。
  • CPU/item、allocated bytes/item、batch items/bytes、queue slope/age。
  • Backend request/payload limits、throttle 與 recovery throughput。

Failure test 不是附加彩蛋，而是 reliability contract：

  • Backend unavailable/slow/429/503；queue 到哪、何時 drop、多久 drain。
  • Collector restart；memory queue vs persistent queue、graceful shutdown。
  • Network partition/TLS rotation/auth expiry。
  • Scale/rollout；tail sampling/span metrics/metric stream state 是否分裂或 reset。

Gate 6：Canary Rollout 與 Old/New Comparison

Staging workload 永遠不完全等於 production。先用少量 instances/tenant/region，將 old/new 在同一 traffic window 比較： acceptance/refusal、selection ratio、batch bytes、queue、export failures、freshness、correctness、resource/cardinality 與 cost。

不要只比較 absolute totals，因 load 可能不同；用 per-input ratios、matched cohorts 與 canary assertions。 觀察窗口要涵蓋 batch/metric flush、tail sampling decision、retry、backend indexing 與至少一個預期 peak。

Rollback 是 Change Contract 的一部分

變更前就寫：

  • 立即 rollback：cross-tenant routing、redaction/security invariant failure。
  • Burn-rate rollback：unexpected refusal/drop/freshness/error-budget 消耗。
  • Capacity rollback：queue/memory 持續正斜率且無 recovery headroom。
  • Known-good artifact：exact image/config/digest，不是口頭說「上一版」。
  • State/queue：rollback 時 pending queues、WAL、tail state、metric writer overlap 如何處理。

Rollback 不是一定無損；binary/schema/storage incompatibility 或 state ownership change 可能讓回退更危險。先測回退路徑，必要時選 roll-forward。

Test Contract Artifact

使用 examples/0047-change-test-contract.yaml 把 gates 與 triggers 版本化。 它是 planning artifact，不會執行 CI、Docker 或 Windows executable。實際 automation 可在核准環境用固定 Docker images 實作，以符合 executable policy。

SRE 附加練習：OTTL Rename 變更

變更：user.tier → app.user_tier。

  1. Fixtures：old only、new only、both conflict、neither、wrong type。
  2. Assertions：新 key 值、舊 key 是否刪、collision precedence、error mode。
  3. Pipeline effects：filter/routing/spanmetrics/dashboard 是否讀 old/new key，order 是否正確。
  4. Canary：查 backend 新 key，negative assert 舊 key 不殘留（若契約要求）。
  5. Rollout：比較 missing-field ratio、OTTL errors、route/filter selection、metric cardinality。
  6. Rollback：若 downstream 已開始只寫/讀新 key，單純退 Collector 是否造成 schema split？

Review 時使用 Collector Change Review Card。

動手推理（不執行）

  1. 選一個 routing change，為 static、fixture、E2E、load/failure、rollout 各寫一個不可互相替代的 assertion。
  2. 說明 config validate 為何不能捕捉 condition=true 導致所有資料錯 route。
  3. 為 backend outage test 寫 input rate、duration、queue budget、expected drops、recovery/drain success criteria。
  4. 列出一個 rollback 會破壞 state continuity 的案例，提出 drain/overlap/roll-forward 選項。

本課總結

  • 每層 test 排除不同 failure class；validate 只是起點。
  • Graph invariants、semantic fixtures、E2E canary、load/failure、rollout comparison 缺一不可。
  • 測試 workload 要包含 production 的 bytes/cardinality/signal mix 與 failure state。
  • Rollback trigger、known-good artifact 與 state/queue treatment 必須在變更前定義。
