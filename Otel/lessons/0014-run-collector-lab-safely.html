14. 安全執行 Collector lab 與建立證據鏈

先理解 network namespace 與可證明的成功，再談啟動指令 · Lesson 14 of N

本課成果與執行界線

你會讀懂一個最小 Collector container lab，特別是 bind address、published port、volume mount 與 pinned image 各自在保護哪個不變量。這章提供未來可由你選擇執行的步驟與證據，但我沒有替你下載 image、安裝軟體， 也沒有執行 Docker 或任何 Windows .exe。

主要來源：OpenTelemetry Collector — Docker installation、Collector configuration

第一性原理：port 屬於 network namespace

「4318」本身不是全域位置。Windows host 與 Collector container 各有自己的 network namespace； 同一個 port number 可以在兩邊各自存在。要讓 host application 到達 container，必須同時滿足兩件事： 

Collector 在 container 內 listen：0.0.0.0:4318
Docker 在 host 發布：127.0.0.1:4318 → container:4318

Python application 連線：http://127.0.0.1:4318/v1/traces

Container config 不能沿用 Lesson 12 的 127.0.0.1:4318：在 container 內，loopback 只指向 container 自己， 從 Docker bridge 轉進來的封包不一定能抵達 loopback-only listener。因此 lab config 在 container 內 bind 0.0.0.0；但 host publish 明確限制在 127.0.0.1，不對 LAN 公開。

不要把兩個 0.0.0.0 混為一談：container 內 bind all interfaces 是為了接住 Docker forwarding； host 端若發布成 0.0.0.0:4318，才會把入口擴展到所有 host interfaces。安全邊界要逐 namespace 判讀。

兩份 lab artifact

  • 0014-collector-container.yaml：Collector active traces graph。
  • 0014-compose.yaml：image、read-only mount 與 host port publication。
services:
  collector:
    image: otel/opentelemetry-collector:0.158.0
    command: ["--config=/etc/otelcol/config.yaml"]
    volumes:
      - ./0014-collector-container.yaml:/etc/otelcol/config.yaml:ro
    ports:
      - "127.0.0.1:4318:4318"

為什麼 pin image version？

Lab 的目標是建立因果關係。如果使用 floating tag，同一份 YAML 可能在不同日期由不同 Collector build 解讀， 讓「我的操作」與「外部版本變化」混在一起。Pinning 不是保證永遠安全，而是固定實驗變因；日後升級要明確改版並重驗。

為什麼 config mount 是 read-only？

Collector 只需讀設定。:ro 把不需要的寫入能力移除，讓 container 不能修改 host 上的教材檔案。 這是 least privilege 的小型示範，不影響 OTel data model，卻讓 lab 邊界更清楚。

先建立 success contract，再決定是否執行

「跑起來」太含糊。本 lab 的完成條件應拆成下列證據：

  1. Compose model 指向預期的 pinned image、config mount 與 localhost-only port。
  2. Collector 接受 config，並顯示 OTLP/HTTP receiver 已 ready。
  3. Lesson 13 application 沒有 transport/export failure。
  4. Collector debug output 出現 service.name=checkout-demo。
  5. 同一輸出可找到 checkout.calculate_total 與兩個 cart attributes。

每一步只增加一項知識。第 2 步成功不能證明第 3 步；第 3 步沒有 error 也不能取代第 4、5 步的 payload evidence。 這就是把 observability lab 從「看起來有動」改成可反駁的證據鏈。

未來由你明確選擇執行時的順序

# 1. 只展開並檢查 Compose model
docker compose -f examples/0014-compose.yaml config

# 2. 啟動 Collector，保留前景 log 作為證據
docker compose -f examples/0014-compose.yaml up

# 3. 在另一個 terminal 執行 Lesson 13 application
# （只在你已自行準備相依套件的受控 Python environment 中）

# 4. Lab 結束後停止並移除該 Compose 建立的 container/network
docker compose -f examples/0014-compose.yaml down

第一個命令驗證 Compose model，不驗證 Collector component schema；啟動時 Collector 才會解析 mounted config。 若你的環境沒有既有 Docker，依政策應先停下來評估，不應轉而下載 Windows Collector binary。

SRE debugging lab：三種「connection refused」以外的失敗

Case A：host publish 正確，container listener 卻只 bind loopback

Compose 顯示 127.0.0.1:4318:4318 並不能證明 container process 接受 bridge traffic。 查 container config 的 bind address，將 namespace 邊界畫出來，避免只盯 host port mapping。

Case B：Collector log 有 Span，但你認為 application 沒送成功

Collector debug payload 是比 application「沒有報錯」更高階的正面證據。先核對 service、span name、trace ID 與 attributes， 再確認是否其實看錯 process 的 console，或把 application console exporter 的舊預期帶進 OTLP lab。

Case C：Collector ready，但沒有 payload

Ready 只證明 startup/config 的一部分。依序檢查 application 是否 recording、是否 flush、HTTP endpoint 是否含 /v1/traces、receiver 是否位於 active traces pipeline。不要從 readiness 直接推論 end-to-end success。

證據階梯：先修最低一個失敗層
  1. Compose model materialized。
  2. Collector startup/config accepted。
  3. Host-to-container transport reachable。
  4. Receiver accepted telemetry。
  5. Debug exporter emitted expected payload。

某層未成立時，先不要用更高層的 backend/query 假設解釋。
