30. 端到端 OTel debugging 方法

用資料契約與第一個失敗邊界，整合前 29 章的基礎模型 · Lesson 30 of N

本課定位

這不是用 troubleshooting tips 取代 OTel 基礎；相反地，它把已學的 Resource、Scope、Context、sampling、limits、processors、queues、 temporality、Logs/Metrics/Traces data model 變成一套可重複的診斷演算法。沒有前面的 why/how，這章只會剩下指令清單。

延伸來源：Collector Troubleshooting、Collector Internal Telemetry

第一性原理：缺失資料不是根因，而是一串未驗證命題

「Backend 找不到 checkout Trace」暗中包含：

  1. Application 建立 recording Span。
  2. Sampler 允許 export，Span 正常 end。
  3. Processor 接手，queue/flush 沒丟。
  4. Application exporter 使用正確 OTLP transport/endpoint。
  5. Collector receiver 接受。
  6. Ordered processors 未意外 drop/corrupt。
  7. Sending queue/exporter 成功交給 backend。
  8. Backend ingest 到正確 tenant/index。
  9. Query 使用正確 Resource identity/time range。

任一命題為假都產生相同表面症狀。Debug 的核心不是列更多可能性，而是用最便宜、最靠近資料的 evidence 找到第一個為假的命題。

Step 1：把 symptom 寫到不可誤解

不要寫「OTel 沒資料」，至少寫：

Signal: traces
Entity: service.namespace=store, service.name=checkout, version=2.4.1
Expected: SERVER span name=POST /checkout
Observed: backend query returns zero results
Window: 2026-08-20 14:00–14:10 Asia/Taipei
Scope: production, one canary instance vs all replicas

Signal、identity、record、time、cohort 決定要查哪條 pipeline。模糊 symptom 會讓不同人同時修 SDK、Collector、backend，破壞因果。

Step 2：畫 expected path，不從工具 UI 開始

Source instrumentation
  → API/SDK recording + sampling/limits
  → Processor/Reader + application exporter
  → OTLP transport
  → Collector receiver
  → ordered processor chain
  → sending queue/retry
  → Collector exporter
  → backend ingestion/index
  → query/UI

Metric 要加 aggregation/View/temporality，Log 要加 bridge/file receiver，Trace 要加 Context/parent/sampling； 但骨架相同：每一層有 input、state transition、output contract。

Step 3：為每個邊界定義「正面成功證據」

Boundary較強的正面證據常見假證據
Source → SDKrecording state、固定 test record、sampling decisionCode 看起來有呼叫 API
SDK → exporterConsole/controlled exporter output、flush result、export errorsSpan 已 end
Transport → receiverreceiver accepted counter、protocol responsePort open/readiness
Processorsper-processor in/out、postcondition payloadConfig validation passed
Queue → exporterqueue trend、sent/failed/enqueue_failed rates沒有 error log
Backend → queryingestion acknowledgment/metrics、raw query by exact identityDashboard panel 空白

Evidence strength 來自它直接觀察 contract output，而不是間接 absence。Port open 只證明 socket/listener，不證明 payload 被 pipeline 接受。

Step 4：找第一個 broken boundary

演算法：

  1. 從 source 開始，標記每層 pass / fail / unknown。
  2. 找到最後一個 pass。
  3. 只測試緊鄰的下一個 unknown/fail。
  4. 提出一個會被證據推翻的 hypothesis。
  5. 一次只改一個變因，保留 before/after。
  6. 修復後沿完整 path 重驗，不只看局部 log 消失。
二分的不是伺服器數，而是知識空間：Collector accepted_spans 上升後，source→receiver 大片假設已降低優先度； 接著比較 processor outgoing 與 exporter queue，而不是重裝 SDK。

Step 5：用其他 signals 當 shared-boundary evidence

Traces 有、Metrics 無，不代表「Collector 正常」或「Collector 壞」；要拆共同與不同部分：

共同：Collector process、某 host/network、OTLP receiver declaration
不同：App provider/reader、signal path、pipeline、processor/exporter instance、backend index

成功 signal 能排除 shared boundary 的部分 failure modes，但不能證明另一 signal 的 source/transport path/pipeline。 這是 Lesson 26 matrix 的用途。

先分類能避免用 missing-data playbook 處理 distorted metric。例如 Counter restart 負 rate 有資料，只是 temporality/reset 被誤讀； 重啟 Collector 不會修正 query 數學。

Controlled probe 的設計原則

需要測試資料時，probe 應：

  • 使用非敏感 synthetic values。
  • 有唯一但 bounded 的 test marker，避免成為長期高 cardinality 維度。
  • 一次只走一條已知 signal/path。
  • 記錄預期 Resource、Scope、Trace/metric/log fields。
  • 有明確 cleanup/expiry，不污染 production SLO。
  • 先在 local/debug exporter 驗證，再逐步加入遠端邊界。

不要用真實 authorization token 當 marker，也不要為了找一筆測試 metric 放 request UUID attribute。

五個整合 fault-injection 思考題

1. OTLP/HTTP exporter 指向 4317

預期第一個 broken boundary：application exporter → Collector listener，因 transport mismatch；receiver accepted 不上升。

2. Trace sampler 改 AlwaysOff

Span 可能 non-recording/non-exported；Metric 仍可聚合，但 TraceBased Exemplars 候選減少。不要從 Metrics 正常推論 Trace pipeline 正常。

3. 短命 process 移除 shutdown

Source Span 已 end，BatchSpanProcessor pending data 未必 export；broken boundary 在 processor lifecycle，而非 Collector。

4. Collector filter 依賴尚未 enrichment 的 attribute

Receiver accepted 上升，該 processor incoming 有資料、outgoing 可能為零；order/precondition failure。

5. Backend outage 超過 queue budget

Accepted 持續、send_failed/queue 上升，最終 enqueue_failed/refusal/loss risk；修復 backend 後仍需 surplus drain capacity。

不要在事故中同時做的事

  • 同時改 SDK sampler、Collector config、backend query。
  • 為「多看一點」開 detailed debug 並輸出真實 secrets/payload。
  • 清空 queue/volume 後才開始蒐證。
  • 把所有 limits 調到無限，讓被保護資源先耗盡。
  • 只因 error log 消失就宣告資料恢復。
