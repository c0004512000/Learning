8. Python 手動 inject / extract

用一個 dictionary 看見跨 service 因果關係如何成立 · Lesson 8 of N

為什麼先不用 Flask 或真正網路？

真正的 HTTP framework 會同時引入 routing、socket、middleware、auto-instrumentation 與多個 process， 增加工作記憶負擔。本課先用 Python function 模擬兩個 services、用 dictionary 模擬 HTTP headers。 我們只改變一個變數：context 是否經 carrier 傳遞。

這不是 production 架構，而是 controlled experiment。當你能由輸出證明 parent relationship， 下一步再把同一機制放進 Flask/requests，debug 時才知道應檢查 framework 還是 propagation 本身。

主要來源：OpenTelemetry Python — Propagation

實驗的三個預期不變量

Checkout SERVER Span:  trace=T, span=C0, parent=null
Checkout CLIENT Span:  trace=T, span=C1, parent=C0
Inventory SERVER Span: trace=T, span=I1, parent=C1
  1. 三個 Span 共用同一個 Trace ID。
  2. 每個 operation 都有不同 Span ID。
  3. Inventory SERVER Span 的 Parent Span ID 等於 Checkout CLIENT Span 的 Span ID。

執行實驗

程式在 examples/0008-manual-propagation.py。 若你已完成 Lesson 3，同一個 virtual environment 已有需要的套件： 

.\.venv\Scripts\python.exe .\examples\0008-manual-propagation.py
安裝界線：本課不需 Flask、requests、Collector 或新 executable；只使用 Lesson 3 已安裝的 opentelemetry-api 與 opentelemetry-sdk。

兩個 Provider 為何可以在一個 process？

checkout_provider, checkout_tracer = build_tracing(
    "checkout-demo", "training.checkout"
)
inventory_provider, inventory_tracer = build_tracing(
    "inventory-demo", "training.inventory"
)

真實部署會是兩個 process，各有自己的 Provider 與 Resource。本課為了不引入網路，把兩組 SDK pipeline 放在同一個 Python process，並刻意不使用 global provider。兩個 service.name 讓 console 輸出仍可區分 telemetry emitter。這是一個測試替身，不改變 propagation 的資料需求。

Sender：把 current SpanContext inject 到 carrier

with checkout_tracer.start_as_current_span(
    "GET /inventory/{itemId}", kind=SpanKind.CLIENT
):
    carrier: dict[str, str] = {}
    propagate.inject(carrier=carrier)
    print(f"Outgoing carrier: {carrier}")

進入 with 後，CLIENT Span 是 current Span。propagate.inject 讀取 current Context， 用已設定的 propagator 把必要欄位寫進 dictionary。預期可看到類似： 

{'traceparent': '00-<trace-id>-<client-span-id>-01'}

Inject 不會 export Span，也不會送網路；它只修改 carrier。真實 HTTP client library 下一步才會把這個 dictionary 變成 request headers 並送出。

Receiver：先 extract，再建立 SERVER Span

remote_context = propagate.extract(carrier=carrier)

with tracer.start_as_current_span(
    "GET /inventory/{itemId}",
    context=remote_context,
    kind=SpanKind.SERVER,
) as span:
    ...

extract 把 header 字串解析成包含 remote SpanContext 的 Context；建立 SERVER Span 時， 明確以它作 parent。新的 SERVER Span 會沿用 Trace ID，產生自己的 Span ID，並把 header 中的 parent-id 設為自己的 Parent Span ID。

為何明確傳 context=remote_context？ 因為本課兩個「services」暫時共用同一 thread；若依賴 thread-local current state，可能意外繼承 sender Span， 掩蓋 carrier 是否真的有效。明確傳入 extracted Context，才能讓實驗只由 carrier 決定 parent。

從 console 輸出驗證，而不是相信程式碼

找到三個 Span，以以下順序建立一張表：

service.namenamekindTrace IDSpan IDParent ID
checkout-demoPOST /checkoutSERVERTC0null
checkout-demoGET /inventory/{itemId}CLIENTTC1C0
inventory-demoGET /inventory/{itemId}SERVERTI1C1

實際 ID 每次執行都不同；你驗證的是 equality relationships，不是特定值。這是 SRE debug 的核心： 把預期寫成不變量，再用 telemetry 證偽，而不是只看 UI 覺得「好像接起來了」。

SRE debugging lab：故意切斷 propagation

把以下一行暫時註解：

# propagate.inject(carrier=carrier)

重新執行並預測結果，再核對：

預期症狀與原因
  1. carrier 不再有 traceparent。
  2. extract 找不到 remote SpanContext，不會憑空知道 checkout 的 IDs。
  3. Inventory SERVER Span 成為新 Trace 的 root：Trace ID 改變，Parent ID 為 null。
  4. 兩邊仍可各自 export，所以 console 仍有三個 Spans；壞的是 propagation，不是 exporter。

完成後把 inject 恢復。接著可做第二個變體：保留 inject，將 carrier 的 traceparent 改成非法字串。 Receiver 應安全地忽略無法解析的值，而不是讓 application request 因 telemetry header crash。
