46. Synthetic Telemetry Canaries

用已知輸入與可驗證輸出，直接量測 pipeline outcome · Lesson 46 of N

本課成果

你會從 observability gap 推導 synthetic canary 的 input contract、marker、positive/negative assertions、freshness 與 failure attribution； 能設計同時覆蓋 traces/metrics/logs、routing/redaction/correlation 的低成本 probe，並避免 canary 自身與 production path 的盲點。

主要來源：OpenTelemetry telemetrygen、Collector Internal Telemetry、Collector Troubleshooting

第一性原理：未知 Input 無法證明 Output Completeness

真實 production traffic 的「應該有多少 telemetry」通常未知：sampling、retries、user load、deploy 都在變。 Internal metrics 能證明 component boundary，但若整條 pipeline 或 monitoring path 同時壞，仍可能沒有可信 end-to-end evidence。

Canary 把問題改造成 controlled experiment：

known input I at time t₀
  → real telemetry path
  → query backend for marker M
  → assert output O before deadline t₁

if O != expected(I), investigate first failed boundary

它不是大量 load test，而是小、持續、可重複的 proof。關鍵不在 generator 工具，而在 input 與 expected output 的契約。

Canary 必須覆蓋真實 Boundary

Canary 放置位置決定能證明什麼：

起點覆蓋Blind spot
Gateway localhostGateway processor/export/backendSDK、agent、network、auth ingress
Agent nodeAgent→gateway→backendApplication SDK/instrumentation
Canary applicationSDK→agent/gateway→backend query只代表該 runtime/network identity
每 region/tenant class分段 routing/auth topology成本與 governance 增加

最少要有一個真正從 producer side 發出、經 production auth/routing、最後由 backend query 驗證的 canary；component-local probes 可輔助定位。

Marker：可關聯，不可污染 Cardinality

每次 run 需要 globally unique canary.id 與 UTC sent_at，用來：

  • 精確查詢本次 trace/log。
  • 偵測 duplicate 與錯送 destination。
  • 計算 queryable freshness。
  • 區分 canary scheduler 重送與 pipeline retry。

但 unique ID 不可作 metric dimension，否則每次 probe 建新 time series。Metric 可用固定低-cardinality attributes， run identity 放在 trace/log 或 exemplar/correlation 中；canary data 要有短 retention/TTL。

Positive 與 Negative Assertions

「有看到一筆」證明太弱。完整 contract 至少包含：

  • Arrival：deadline 內可查。
  • Count：期望 2 spans/1 log，而非 0 或 duplicate 4。
  • Relationship：parent-child、trace/log correlation 保持。
  • Identity：resource/service/environment/tenant 正確。
  • Transformation：normalized fields 有、legacy key 已移除。
  • Redaction：forbidden sensitive attributes 不存在。
  • Routing：應到 primary；不可到 other tenant/backend。
  • Metric semantics：counter increment、unit/temporality/attributes 合法。

Negative assertion 很重要：只查 primary 有資料，無法證明資料沒有外洩到錯 tenant。

Cross-signal Canary

one synthetic operation
  ├─ root + child spans
  ├─ correlated log with same trace/span context
  └─ bounded metric increment (+ optional exemplar)

這可同時驗證 propagation、logs correlation、span/metric route 與 multi-signal freshness。 但 signals export intervals 不同，deadline/queries 應分別設定，不能要求 log、trace、metric 同毫秒出現。

Canary Contract Artifact

閱讀 examples/0046-canary-contract.yaml。 它定義 identity、signals、assertions 與 governance，是設計文件而非可執行設定。OpenTelemetry contrib 提供 alpha 的 telemetrygen 可產生 traces/metrics/logs， 但本課不下載、安裝或執行工具；未來實作時也應固定 image/version，而不是使用漂移的 latest。

Probe 也可能壞：避免 False Positive/Negative

Canary system 有自己的 dependencies：

  • Scheduler 沒執行：看起來像 pipeline 沒資料。
  • Query credential/endpoint 壞：資料已到但 verifier 查不到。
  • Clock skew：freshness 被高估/低估。
  • Query eventual consistency：deadline 太緊造成 false alert。
  • Canary 被特殊 allowlist：真實 traffic 壞但 canary 綠。

所以至少記錄 send attempt/ack、run ID、query attempt/error 與 state machine；用不同來源監控 scheduler，並讓 canary 盡量走與 production 相同 policy，只有資料內容是安全 synthetic。

SRE 附加練習：Canary Trace 到了，Log 沒到

  1. 確認同一 run ID 的 producer 是否真的 emit/export log，且 log 帶 trace context。
  2. 分 signal 查 SDK exporter、Agent receiver accepted、log-specific filter/parser、Gateway pipeline 與 exporter destination。
  3. 比較 trace/log routing predicates；是否 severity/filter 把 canary log intentional drop。
  4. 查 log exporter queue/send/partial rejection 與 backend indexing/query delay。
  5. 驗證 query 語法不是用錯 resource vs log attribute。
  6. 修復後重新用新 run ID，確認 positive arrival 與 forbidden destination negative assertion。

設計與事故可用 Telemetry Canary Design Card。

動手推理（不執行）

  1. 為一個 prod/eu pipeline 寫 canary 的 producer start、auth identity、expected destination 與 forbidden destination。
  2. 設計兩個 positive、兩個 negative assertions，其中至少一個驗證 redaction。
  3. 說明為何 run UUID 適合 trace/log attribute，卻不適合 metric dimension。
  4. Canary missing 時畫出 generator、OTLP path、backend query 三個 failure domains及各自 evidence。

本課總結

  • Canary 是 known input 經真實 path 到 expected output 的持續實驗。
  • Marker 要唯一可查，但不可污染 metric cardinality；資料要 synthetic、低量、可過期。
  • Assertions 應覆蓋 arrival、count、relationships、identity、redaction、routing 與 negative outcomes。
  • Canary system 也需自我監控，且起點/identity 要覆蓋真實 production boundary。
