40. OTLP Security Boundaries

加密、完整性、peer identity、authorization 與 availability 是不同問題 · Lesson 40 of N

本課成果

你會從 threat model 推導 OTLP receiver/exporter 的 TLS、mTLS、authentication 與 network exposure； 能解釋 insecure、insecure_skip_verify、CA/cert/key 的方向性，並分層定位連線、TLS、auth、protocol 與 pipeline 問題。

主要來源：OpenTelemetry Security、Collector Configuration Security、Collector TLS Configuration、Authenticator Architecture

第一性原理：先列 Asset、Adversary、Guarantee

Telemetry 可能包含 service topology、user identifiers、query fragments、errors、tokens 或商業事件。對一條 OTLP hop，先問：

  • Confidentiality：旁觀者能否讀 payload？
  • Integrity：傳輸中能否被竄改而不被發現？
  • Server identity：client 是否真的連到預期 Collector/backend？
  • Client identity：receiver 是否知道誰在送？
  • Authorization：該 identity 被允許送哪些 signal/tenant/volume？
  • Availability：誰能耗盡 connection、CPU、memory、queue？

沒有單一開關同時回答所有問題。TLS 主要提供 encrypted/integrity-protected channel 與 server authentication； mTLS 再讓 server 驗證 client certificate。Bearer/OIDC 等 authenticator 可建立應用層 principal；authorization、rate limit、data minimization 仍需額外 policy。

單向 TLS：Client 驗證 Server

Client                              Server
  -- ClientHello -------------------->
  <- certificate + proof ------------
  verify chain + hostname/SAN
  == encrypted channel established ==

Client 使用 trusted root CA 驗證 server certificate chain，並驗證連線 hostname 是否在 certificate SAN 中。 成功後能合理相信 endpoint identity，且後續 payload 加密/完整性保護。它不代表 server 知道 client 是誰；任何能連線的 client 仍可能送資料。

mTLS：Server 也驗證 Client Certificate

Client cert/key                    Server cert/key
       \                              /
        mutual certificate verification
                 ↓
        encrypted authenticated channel

Receiver 的 client_ca_file 指定用來驗證 client certificate 的 CA，並要求/驗證 client cert。 Exporter 作為 client 時，cert_file + key_file 提供 client identity；ca_file 則用來驗證 server。

位置檔案用途
Receiver/serverserver cert + private key向 clients 證明 server identity
Receiver/serverclient CA驗證 incoming client certificates
Exporter/clientserver CA驗證 backend certificate
Exporter/clientclient cert + private keybackend 要求 mTLS 時證明 client identity

insecure 與 insecure_skip_verify 不同

Client settingEncryptionServer certificate verification主要風險
正常 TLS有有需正確 CA/SAN/clock
insecure: true無無明文與竄改風險
insecure_skip_verify: true有跳過不能可靠辨識 server，可能遭 MITM

「有加密」不等於「加密給正確對象」。insecure_skip_verify 常讓測試暫時通過，卻把 trust failure 隱藏掉； Production 修復應補正 CA chain、SAN、DNS 或 clock，而不是永久跳過 verification。

Authentication Extension 的位置

Collector authenticators 由 extensions 實作。Server authenticator 掛到 receiver，攔截 incoming HTTP/gRPC request； client authenticator 掛到 exporter，替 outgoing request 加 authentication material。只有在 distribution 包含 extension、 service.extensions 啟用，且 receiver/exporter reference 它時才有效。

Token-based auth 必須搭配 TLS，否則 bearer token 可能被網路旁觀者取得。mTLS certificate verified 也只建立 certificate principal； 是否允許該 principal 寫 tenant A、最大 rate 為何、certificate revocation/rotation 怎麼做，是 authorization/lifecycle policy。

Bind Address 是 Attack Surface

Receiver bind 127.0.0.1、Pod IP、node interface 或 0.0.0.0，決定哪些 network paths 能到達它。 官方安全建議是只 bind 所需 interface，並搭配 firewall/network policy/auth；現行 Collector server default 已傾向 localhost， 但 deployment manifests 常顯式改回 broad bind。

TLS/auth 不能阻止所有 authenticated client 發送過量 payload。還需要 connection/request size/concurrency controls、memory limiter、bounded queues、 resource limits 與 internal telemetry。Security 包含 availability，不只 confidentiality。

TLS 不會清洗 Payload

TLS 保護資料在 hop 上傳輸，backend 解密後仍看得到完整內容。若 span/log 含 password、session token、PII，TLS 不會讓它變安全資料。 正確順序是 data minimization at source，必要時在可信邊界內 redaction/transform，再經 authenticated encrypted channel 送出。 

collect minimum → sanitize in trusted boundary → authorize destination → encrypt in transit

Certificate Rotation 是時間問題

Certificates 有 not-before/not-after，keys/CA 也會輪替。Rotation 設計需回答：新舊 trust bundle 重疊多久、cert/key 是否原子更新、 component 是否 reload、既有 connection 何時重建、clock skew 多大、失敗如何 rollback。 只測「今天能 handshake」不能證明下週 rotation 安全。

SRE 附加練習：分層定位 OTLP 連線失敗

不要先改成 insecure。依最底層可證明 boundary 往上查：

  1. Name/route：client 實際解析哪個 IP/port？Service/proxy/network policy 指向誰？
  2. TCP：receiver 是否 bind 正確 interface；是 refused、timeout 還是 reset？
  3. TLS：版本、CA chain、SAN/hostname、有效期、clock、client cert/key 是否匹配。
  4. Authentication：server 是否接受 principal/token；401/Unauthenticated 與 TLS handshake failure 不同。
  5. OTLP protocol：gRPC/HTTP、4317/4318、path、content type、compression 是否一致。
  6. Pipeline：receiver accepted 後，processor/filter/exporter 是否 drop/fail/retry。

每層保留 timestamp、client/server identity、endpoint 與 error class，但不要把 token/private key/完整敏感 payload 貼入 ticket。 可使用 OTLP Connection Debug Card。

本課總結

  • Confidentiality、integrity、server/client identity、authorization、availability 是不同 guarantees。
  • TLS 驗 server；mTLS 再驗 client；authorization 與 payload sanitization 仍需獨立設計。
  • insecure 關掉 TLS；insecure_skip_verify 移除 server verification，兩者都不是 production 修復。
  • 除錯順序是 network → TLS → auth → OTLP → pipeline，保留證據且不洩漏 credentials。
