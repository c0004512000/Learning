39. Routing 第一性原理

Routing 將一筆 telemetry 映射到目的 pipeline 集合，table order 與 move/copy 決定結果 · Lesson 39 of N

本課成果

你會從 connector graph 推導 routing table 的 ordered semantics，理解 move、copy、default pipelines、context 與 error fallback； 能區分業務/tenant routing 與 stateful shard affinity，並用 destination truth table 驗證錯送、重送與無路由。

主要來源：Routing Connector、Collector Connectors

第一性原理：Routing 是一個 Destination Function

對每筆 telemetry item x，router 計算目的 pipelines 集合：

R(x) → {pipeline A, pipeline B, ...}

Filter 的結果是 keep/drop；routing 的結果是 destination set。Routing connector 不改變 signal type：traces→traces、metrics→metrics、logs→logs， 並以 connector 的雙重角色連接 ingress pipeline 與一或多條 destination pipelines。 

logs/in -- exporter:routing/logs
                    ├─ receiver:routing/logs --> logs/prod
                    ├─ receiver:routing/logs --> logs/errors
                    └─ receiver:routing/logs --> logs/quarantine

Table 是有順序的程式，不是無序 Map

每個 table entry 包含 predicate、action 與 pipelines。從上往下評估：

  • move（預設）：matched data 送到 target，並從後續 route evaluation 移除。
  • copy：matched data 複製到 target，但原資料繼續被後續 entries 評估。
  • default_pipelines：接收走完 table 後未被 move 的剩餘資料。

可用簡化 state machine 表示：

destinations = ∅
remaining = true

for entry in table order while remaining:
  if entry.condition(x):
    destinations += entry.pipelines
    if entry.action == move:
      remaining = false

if remaining:
  destinations += default_pipelines

因此 table 重排可能改變結果；這不是格式整理。多個 copy 可讓同一 item 進多條 pipelines， 而 copy 後仍 remaining，所以最後也可能進 default。若你只想二選一，使用明確的互斥 move routes。

prod ERROR 不會再到 prod，因 error route 的 move 先結束 evaluation。若需求是同時到 errors 與 prod， 可把 error action 改成 copy，但 then prod ERROR 會到 archive、errors、prod；成本與 duplicate query semantics 必須接受。

Default Pipeline 是已知未知的容器

沒有 default 時，unmatched data 的命運需要依 component/version 行為確認；production 設計不應讓未知 identity 靜默消失。 一條受監控的 quarantine/default pipeline 能保留 evidence：記錄 unmatched count、有限樣本與缺少的 routing key，再修正 producer/policy。

但 default 不是永遠的垃圾桶。要有 volume alert、retention、owner 與 remediation SLA；否則所有新 service/tenant 都可能長期被送錯 backend。

Routing Key 的 Trust Boundary

下面兩種值在安全性上不等價：

resource.attributes["tenant.id"]       # application payload can often set it
otelcol.client.metadata["X-Tenant"]   # transport metadata; still needs authentication/trust

若 tenant routing 決定資料隔離、billing 或 authorization，不能只相信 producer 任意寫入的 resource attribute。 即使使用 incoming header，也要由 authenticated gateway/proxy 驗證或重寫，防止 client spoof；Collector routing 是 distribution mechanism，不自動成為 identity provider。

先 authenticate，再把 verified principal 映射成 routing key；拒絕未知/矛盾 identity。不要把「header 存在」誤當「tenant 已驗證」。

Semantic Routing 不等於 Stateful Affinity

Routing connector 適合把資料送往固定的 policy pipelines/backend classes。Tail sampling 則要求同一 traceID 的所有 spans 到同一 state owner； span metrics 可能要求 service/metric stream affinity。這種 sharding 通常由 load-balancing exporter 等 topology mechanism 實作。

若用每個 span 的 attribute 作 route，可能把同一 trace 的 spans 分到不同 destinations，破壞 tail sampler 的完整視野。 問「這筆資料屬於哪個政策？」是 semantic route；問「相同 key 的所有資料由哪個 instance 持有 state？」是 affinity。兩者可串接，但不可混稱。

Context 與 Error Fallback

Routing connector 支援 resource、span、log、metric、datapoint 與 Collector request metadata paths，通常由 context-qualified path inference。 若 condition 不含可推導 path（如 literal true），需指定 context。

目前文件描述 error_mode 可為 ignore、silent、propagate；ignore/silent 遇 condition error 時資料會走 default pipelines，silent 不記錄。 Default 正因如此也可能混合「合法 unmatched」與「route evaluation 出錯」；internal errors 與 default volume 必須分開監控。

本課總結

  • Routing 是 R(x) → destination set，透過 connector 連接同 signal pipelines。
  • Table 有順序；move 結束後續評估，copy 保留後續資格，default 接剩餘資料。
  • Tenant/security routing 必須使用已驗證 identity；payload/header 本身不自動可信。
  • Semantic routing 與 stateful affinity 是不同問題，事故時要分辨錯送、重送與無路由。
