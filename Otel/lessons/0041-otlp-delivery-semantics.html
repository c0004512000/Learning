41. OTLP Delivery Semantics

Acknowledgement 只證明某一 hop 的 server 接受了 request；重試則在 loss 與 duplicate 間取捨 · Lesson 41 of N

本課成果

你會從 request/response 與 acknowledgement boundary 推導 full success、partial success、retryable/non-retryable failures、throttling 與 duplicates； 能區分 hop acceptance 和 end-to-end durability，並用 queue/response evidence 定位 loss、retry storm 與 duplicate。

主要來源：OTLP Specification、OTLP Protocol Specification Source、OTLP Exporter Specification

第一性原理：分散式系統看不到「送達」，只能看到 Evidence

最簡單的 OTLP interaction 是：

Client -- Export(request batch B) --> Server
Client <-- response/ack ------------ Server

Client 收到 response，才能知道 server 對 B 的判斷。若 connection 在 response 抵達前中斷，client 無法分辨：

  1. Server 完全沒收到 B。
  2. Server 收到但尚未處理。
  3. Server 已接受 B，只是 response 遺失。

若 client 為避免 loss 而重送，第 3 種情況會產生 duplicate；若 client 不重送，第 1 種情況會 loss。 OTLP 選擇在這種 ambiguity 下通常重送，接受 edge cases 可能 duplicate。它不是 end-to-end exactly-once protocol。

Acknowledgement Boundary：誰說「Accepted」？

SDK → Agent → Gateway → Backend storage
       ack₁     ack₂        ack₃

Agent 回 SDK success，表示 Agent 作為該 hop server 接受 request；不自動證明 Gateway 或 backend 已 durable。 Gateway 回 Agent success也只到 Gateway 的 acceptance boundary。若中間節點先 ack、後續 memory queue 尚未持久化就 crash，仍可能 loss。

所以每個 hop 都要定義：何時 ack、接受後放在哪個 memory/disk queue、shutdown/crash 時能否恢復、下一 hop 的 retry budget 多大。 「OTLP exporter success=100%」不能單獨證明 backend query 完整。

四類 Response Outcome

OutcomeServer 語意Client 動作
Full success該 request telemetry 被 server 接受此 destination 的 batch 可 dequeue
Partial success部分 rejected，或完整接受但帶 warning不得 retry 同 request；記 rejected/warning evidence
Retryable failure暫時無法處理，未承諾接受依 backoff/jitter/retry hint 重試
Non-retryable failurebad data/auth/permission 等，重送相同資料不會好不重試；drop 並記錄 evidence

Partial Success 為何不能 Retry？

Partial success response 會提供 rejected spans/datapoints/log records/profiles 數量與可選 error message；也可能 rejected=0、只帶 warning。 但 response 不提供一份可靠的「哪些 records 可安全重送」清單。重送整個 request 會 duplicate 已接受部分，因此規範要求 client 不重試該 request。

這代表 partial rejection 是 data loss signal，不能被 2xx/success transport graph 淹沒。SRE 應監控 rejected item counts 與 error messages， 並修 producer/schema/limits；它不是 exporter retry queue 能自動治癒的 transient failure。

Retryable 與 Non-retryable 由「相同 Request 稍後是否可能成功」區分

典型 gRPC retryable 包含 UNAVAILABLE、DEADLINE_EXCEEDED；HTTP 明列 429、502、503、504 應重試。

典型 non-retryable 包含 gRPC INVALID_ARGUMENT、UNAUTHENTICATED、PERMISSION_DENIED， 以及 HTTP 400 bad request。Retry 不能修正 malformed payload、錯 token 或被拒權限；持續重試只會放大負載與延遲。

判斷句：不改變 request、credential 或 server state，只等一段時間後，相同 request 是否合理可能成功？ 若答案是否定，應修正原因而不是 retry。

RESOURCE_EXHAUSTED 需要 Recovery Signal

gRPC RESOURCE_EXHAUSTED 只有 server 用 RetryInfo 表示可恢復時，才應視為 retryable；沒有該資訊時應視為 non-retryable。 因為它可能代表暫時 overload，也可能代表 request 永久超過 size limit。只看 status 名稱會把兩種機制混在一起。

Backpressure：Server 要讓 Client 慢下來

當 server 跟不上，gRPC 可用 retryable status + RetryInfo.retry_delay；HTTP 可用 429/503 + Retry-After。 Client 應尊重 hint，並使用 exponential backoff；沒有 hint 時也需 exponential backoff + random jitter，避免所有 clients 同步重試形成 thundering herd。 

attempt 1 fails → wait ~base + jitter
attempt 2 fails → wait ~2×base + jitter
attempt 3 fails → wait ~4×base + jitter
                         capped by policy

Backpressure 不會創造無限 buffer。若 outage 持續超過 queue capacity/retry elapsed time，client 最終仍 drop。 因此 capacity planning 要比較 incoming rate、queue items/bytes、oldest age、recovery throughput，而非只說「已開 retry」。

Duplicate 是哪一層的問題？

同一 telemetry 可能因不同機制重複：

  • OTLP request 已被接受但 acknowledgement 遺失，client 重送。
  • Routing copy 或多 exporters 刻意 fan-out 到同一實際 backend。
  • 兩個 receivers/agents 重複收同一 log/file/scrape target。
  • Producer 自己重建/重送同一 record。

Trace span 有 trace ID + span ID，可協助 backend deduplicate，但不應假設所有 backends/訊號都完全去重。 Metric 重複對 sums/counters 更危險；logs 可能需要 application event ID 才能可靠辨識。先找 duplicate 產生 boundary，再談 dedup。

Multi-destination 必須各自追蹤 Ack

             ┌→ backend A: acked
batch B ─────┤
             └→ backend B: retrying

若一份 telemetry 送多 destinations，每個 destination 應有獨立 queue/ack/retry state；A 成功不代表 B 成功，B 慢也不應迫使 A 重送。 共享 immutable payload 可降低 memory，但 delivery state 必須分離。事故 dashboard 應按 exporter/destination 維度觀察。

SRE 附加練習：Exporter Success 高但 Backend 缺資料

  1. 確定「success」是哪個 hop、哪個 component、哪段時間、哪個 signal。
  2. 檢查 partial success/rejected evidence；transport success 可能仍含 rejection/warning。
  3. 沿 Agent→Gateway→Backend 分別比較 accepted/sent/failed/retried/dropped，不跨 boundary 偷換分母。
  4. 檢查 queue oldest age、capacity、persistent storage 與 restart timeline，找 ack 後/next-hop 前的 vulnerability window。
  5. 用 stable identifiers/time windows 查 duplicate 或 missing；注意 sampling/filtering 可能是預期 selection。
  6. 若 outage，驗證 retry hints/backoff 是否被尊重，recovery throughput 是否高於 incoming rate，否則 backlog 永遠清不完。

本課總結

  • Ack 是 hop-local evidence；full success 不自動證明 end-to-end durable。
  • Partial success 不重試；retryable failures backoff 重試；non-retryable failures drop 並修根因。
  • Response ambiguity 使 loss 與 duplicate 無法同時完全消除；OTLP 接受 edge-case duplicates。
  • Backpressure、queue capacity 與 per-destination acknowledgment 共同決定 delivery reliability。
