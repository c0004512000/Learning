45. Collector SLO Design

Process up 不是目標；目標是 telemetry 依約可達、及時、正確、可用於決策 · Lesson 45 of N

本課成果

你會從 telemetry pipeline 的使用者結果設計 availability、loss、freshness、correctness 與 coverage SLIs； 理解 internal telemetry 的證明邊界、intentional selection 對分母的影響，以及如何用 error budget/burn rate 驅動告警。

主要來源：Collector Internal Telemetry、Collector Troubleshooting、OTel Self-Observability

第一性原理：先定義使用者要完成的工作

SRE/開發者真正依賴的不是「Collector pod Ready」，而是：

producer emits telemetry
  → pipeline accepts expected population
  → policy intentionally transforms/selects it
  → backend receives/indexes it
  → user can query it within freshness target
  → data still has correct identity/semantics

因此 process uptime 是 implementation indicator，不是完整 service level。Pod 可存活但 exporter queue 已滿；backend 可收到資料但晚 30 分鐘； counts 可完整但 service.name 被改壞。SLO 必須描述 observable outcome。

Boundary 決定你的 SLO 能證明什麼

Boundary能回答不能單獨回答
Collector processruntime/CPU/memory/uptimeproducer 是否送得到、backend 是否可查
Receiver→ExporterCollector 內 ingress/egress/dropupstream attempts、backend indexing
SDK→Backend ingestend-to-end delivery到 ingestquery/index freshness
Producer→Queryable result最接近使用者 outcome需跨系統 canary/inventory

先寫 boundary，才有 numerator/denominator。不同團隊可同時維護 component SLO 與 end-to-end SLO，但不可把前者冒充後者。

五種互補 SLI

1. Acceptance

accepted / (accepted + refused)

Collector 有 receiver accepted/refused counters，能看已抵達 receiver 的 items。但 client 因 DNS/TLS/network 完全到不了，不在分母； 因此它是 ingress boundary SLI，不是 producer attempt success。

2. Known Loss

Receiver refused、exporter enqueue failed、non-retryable terminal drops、OTLP partial rejected 都是 known loss evidence。 Exporter send failed 本身未必已 loss，因可能進 retry；必須結合 retry/queue 最終結果，避免把 transient attempts 當 unique lost items。

3. Freshness

freshness = queryable_time - event_or_observed_time

Queue size 只是 proxy；最接近 outcome 的量測是帶 production timestamp/unique marker 的 synthetic canary，直到 backend 可查。 要分 clock skew、SDK interval、batch、queue、retry 與 indexing delay。

4. Correctness

資料抵達但 service/tenant identity 錯、metric unit/temporality 壞、trace parent 關係斷，仍不可用。 Correctness 可用 canary assertions、schema checks、required-resource completeness、cardinality/relationship checks；安全 invariants 通常要求 100%。

5. Coverage

比較 expected producer/service inventory 與最近 telemetry。全局 throughput 正常仍可能掩蓋一個 region/team 完全消失；coverage 必須按 tenant、region、signal、service class 分段。

Intentional Selection 必須進入資料契約

Head/tail sampling、filter、routing、redaction 都可能讓 output count 小於 input。這不是自動 data loss；但若分母未建模，就無法分辨 policy 與事故。 

accepted input
  - intentionally filtered
  - intentionally unsampled
  = expected-to-deliver population

unexpected loss rate = unexpected missing / expected-to-deliver

Tail sampling 的 expected population 甚至要以 traces/policy decision 為單位，不可直接用 spans count 相除。每個 SLI 必須說明 signal unit、selection stage 與 aggregation key。

Internal Telemetry 是 Boundary Evidence

Collector basic internal metrics 可提供：

  • receiver accepted/refused by signal。
  • exporter sent、enqueue failed、send failed。
  • queue size/capacity、in-flight requests。
  • process CPU、RSS、heap、uptime，HTTP/gRPC request telemetry。

Metric name 會受 Collector version、OTLP vs Prometheus export、_total suffix 與 dots/underscores 轉換影響；dashboard/alerts 應固定版本契約並在升級時驗證。 此外不要讓 Collector 只透過自己正在監控的唯一故障路徑輸出 internal telemetry，否則 data path 壞時監控也同時消失。至少保留獨立 scrape/外部 health/canary boundary。

Error Budget 把 Reliability 變成可決策資源

若 28 天 success SLO 為 99.99%，allowed bad fraction 是 0.01%。Burn rate：

burn_rate = observed_bad_fraction / allowed_bad_fraction

Burn=1 表示正以剛好耗完整窗口 budget 的速度消耗；Burn=10 表示快十倍。 Multi-window alerts 可同時抓急性高 burn 與慢性低 burn，減少單點 threshold 噪音。不同 signal/tenant tier 可有不同 SLO，但安全 correctness 不應用 availability budget 抵銷。

SRE 附加練習：Pod 全綠但 Trace 查不到

  1. 確認 violated SLI：coverage、freshness、loss 或 correctness；限定 service/region/time。
  2. 查 producer-side export attempts/errors，補 receiver accepted 看 upstream→ingress gap。
  3. 沿每 hop 比較 accepted/refused、intentional sampling/filter、queue/enqueue failed、sent/send failed。
  4. 若 sent 正常，檢查 OTLP partial success、backend ingest/index/query 與 identity/schema。
  5. 用 canary 判斷 end-to-end；用真實 service inventory 判斷是否只是 canary path 健康。
  6. 找 first bad boundary，修復後用原 violated outcome 關閉，而非只看到 pod Ready。

可使用 Collector SLO Debug Card。

動手推理（不執行）

  1. Receiver accepted=999,900、refused=100，算 ingress acceptance；列出它看不到的兩種 loss。
  2. Exporter send_failed 增加但 queue 最終排空且 sent 補回，說明為何不能把所有 failed attempts 當 lost items。
  3. 設計一個 freshness canary：marker、timestamp、frequency、query condition、timeout 與 sensitive-data constraint。
  4. 列出三個 correctness invariants：resource identity、trace relationship、metric unit/temporality。

本課總結

  • SLO 從 user outcome 與 boundary 開始，不從現有 metric 名開始。
  • Acceptance、known loss、freshness、correctness、coverage 互補，不能只看 process uptime。
  • Intentional sampling/filter 必須明確扣出 expected-to-deliver population。
  • Internal telemetry 是 hop evidence；end-to-end canary、inventory 與獨立監控補足 blind spots。
