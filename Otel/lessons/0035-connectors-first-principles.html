35. Collector Connectors 與跨 Pipeline 資料流

Pipeline 是有 signal 型別的資料流；Connector 是兩條 Pipeline 之間的 edge · Lesson 35 of N

本課成果

你會從 pipeline 的封閉性推導 connector 為何同時扮演 exporter 與 receiver；能區分 processor、exporter、connector， 讀懂 traces → metrics 的 span metrics graph，並辨識啟用、型別、sampling、cardinality 與 state ownership 問題。

主要來源：Collector Connectors、Collector Configuration、Span Metrics Connector

第一性原理：一條 Pipeline 只處理一種 Signal

Collector pipeline 的基本形狀是：

receiver(signal X) → processors(signal X) → exporter(signal X)

它有清楚的入口、處理鏈與出口，而且屬於 traces、metrics 或 logs 其中一種 signal。 因此「讀 spans 並產生 metrics」不是普通 trace processor 能完整表達的事：輸入屬於 trace pipeline，輸出卻必須進入 metrics pipeline。

若把 Collector configuration 看成有向圖，pipeline 是一段有型別的路徑，connector 則是跨 pipeline 的 edge：

traces pipeline
OTLP → processors → [span_metrics as exporter]
                         │ traces → metrics
                         ▼
metrics pipeline
              [span_metrics as receiver] → processors → metrics backend

這解釋了 connector 的雙重角色：它在來源 pipeline 的末端消費資料，所以被列為 exporter； 它在目的 pipeline 的開頭提供資料，所以被列為 receiver。它可以保持 signal 型別做 routing/replication，也可以改變型別、產生摘要。

Processor、Exporter、Connector 不可只靠名字判斷

Component資料流角色典型用途心智問題
Processor一條 pipeline 內部filter、transform、batch、sampling這筆同 signal 資料如何被改變？
Exporterpipeline 終點送 backend/檔案/另一 Collector資料離開這條 pipeline 後去哪？
Connector一條 pipeline 的 exporter + 另一條的 receiverroute、replicate、signal-to-signal summary哪兩條 typed pipelines 被接起來？
宣告不等於啟用：只在頂層 connectors: 建立 instance，並不會讓資料流動。 同一 connector 必須同時出現在來源 pipeline 的 exporters 與目的 pipeline 的 receivers，而且 signal pair 必須受該 component 支援。

Span Metrics：把事件樣本聚合成 RED Metrics

一個 ended Span 是一次 operation 的事件紀錄；metrics 則是依時間與 dimensions 聚合的數值流。 Span Metrics Connector 讀 spans，依穩定 dimensions 分組，產生 Request、Error、Duration（RED）metrics： 

calls(service.name, span.name, span.kind, status.code) += 1
duration(...).record(span.end_time - span.start_time)

因此 metric 並非從 backend「猜」出來，而是 connector 持有 aggregation state，把多個離散 spans 壓縮成 counters/histograms。 這個壓縮換來低成本趨勢與 alerting，但會失去每個 request 的完整細節；需要 exemplar 時，可保留少量 metric datapoint 到 trace 的橋樑。

可閱讀 examples/0035-span-metrics-connector.yaml。 它是安全的規劃片段，本課不啟動 Collector。請先用圖驗證：span_metrics 在 trace pipeline 是 exporter， 在 metrics pipeline 是 receiver；trace 仍可同時送到另一 exporter，connector 不必是唯一出口。

衍生 Metrics 的真實語意受輸入集合限制

設真實 spans 集合為 T，進入 connector 的集合為 O。connector 只能聚合它看見的資料：

O ⊆ T
derived_metric = Aggregate(O), not automatically Aggregate(T)

若在 connector 前做 10% head sampling，普通計數得到的是 observed spans，而不是天然等於總流量。 錯誤率也可能偏誤：若 sampling decision 與 error/latency 相關，樣本不再代表母體。 所以 pipeline order 是 metric semantics 的一部分，不只是效能設定。

設計問題：若 RED metrics 要代表全部 requests，讓 connector 看完整合格輸入，或明確採用可校正 sampling 的設計； 不要在 dashboard 上把「sampled trace count」默默命名成「request count」。

Cardinality：每個 Dimension 都在乘法

每組唯一 dimensions 形成不同 metric stream。粗略上界可寫成：

series ≈ services × span_names × span_kinds × status_codes
         × environments × additional_dimension_values ...

把 raw URL、request ID、trace ID、user ID 加入 dimensions，會把 aggregation 退化成近乎「每 request 一條 series」。 這不只提高 backend 成本，也讓 connector cache/memory 上升。正確修復是先讓 span name 與 dimensions 保持低 cardinality； aggregation_cardinality_limit 是防護欄，不是語意修復器。

State、Temporality 與 Single Writer

Connector 必須持有 calls、histogram buckets、timestamps 與 series cache。Delta temporality 要輸出「自上次 flush 後的增量」； Cumulative 要維護從 start time 起的累積。若同一邏輯 metric stream 同時由多個無協調 instances 產生，backend 可能看到重疊、reset 或 out-of-order。

這與第 34 章相接：需要 aggregation state 的 connector 應有明確 owner 與 routing/identity 策略。 目前 span metrics connector 會加入 collector.instance.id 來協助維持 writer identity；不要在不理解 single-writer 後果時移除。 若用多 deployment，還要考慮 service affinity、stable resource identity 與 rollout 時的 stream continuity。

SRE 附加練習：Trace 有了，Metrics 為何沒有？

不要直接跳到 backend。沿 graph 的 causal boundary 收集證據：

  1. 確認使用的 Collector distribution/version 包含該 connector；core 與 contrib 的 component 集合不同。
  2. 確認 connector instance 已在頂層宣告，且同時掛在上游 exporters、下游 receivers。
  3. 在 connector 前證明有 spans；檢查 filter/sampling 是否先移除資料。
  4. 等待至少一個合理 flush interval，再檢查 connector 與下游 pipeline 的 accepted/failed/dropped internal telemetry。
  5. 用 debug exporter 暫時觀察衍生 metrics；若有輸出，再把問題邊界移到 downstream exporter/backend。
  6. 若只有部分 services 消失，查 resource identity、include scope、routing affinity 與 cardinality overflow。

把這套順序存成 Connector 除錯卡。它的核心不是背 metric 名，而是每次只證明 graph 的一條 edge。

動手推理（不執行）

  1. 在範例中刪掉 metrics/derived.receivers: [span_metrics]。畫出還存在的 graph，指出為何 declaration 仍在但 edge 不完整。
  2. 假設 trace pipeline 在 connector 前只保留 5% spans。寫一句 dashboard label，避免把衍生 calls 誤稱為全流量。
  3. 比較 http.route=/orders/{id} 與 url.full=/orders/7f8... 當 dimension；估計哪個乘數會失控，說明 why。
  4. 設計兩個證據點，區分「connector 沒產生 metrics」與「metrics exporter 送不出去」。

本課總結

  • Pipeline 是單一 signal 的有型別路徑；connector 是兩條 pipelines 間的 edge。
  • Connector 同時是上游 exporter 與下游 receiver；只宣告不會啟用。
  • Span metrics 是對 observed spans 的有狀態聚合；sampling、dimensions、temporality 都改變其語意。
  • 除錯時沿 edge 證明 input、state、output，再移往 backend。
