1. 從系統問題推導 OTel、Trace 與 Span

先理解需要什麼證據，再認識工具與資料模型 · Lesson 1 of N

出發點：SRE 想回答的是「為什麼？」

假設使用者說：「結帳很慢。」服務可能仍然健康、CPU 也可能正常；問題可能在 API Gateway、 Checkout Service、資料庫、或某個外部 payment call。系統的內部狀態無法直接看見， 你只能從系統發出的輸出推論發生了什麼。

這就是 observability 的第一性原理：不必預先知道故障模式，也能用系統輸出提出並回答 「為什麼會這樣？」。為了做到這件事，程式必須產生有足夠語意的 telemetry。

依據：OpenTelemetry 官方文件 — Observability Primer

重要界線：dashboard、query UI 與 alert rule 不會自己創造 observability。 它們只能處理已經存在的 telemetry。若程式沒有輸出可用證據，再好的 backend 也無法還原原因。

為什麼本課先學 Trace，而不是一次塞進三大支柱？

Metrics、logs 與 traces 都是 telemetry，但回答的問題不同。你現在不需要先精通它們： 只要先理解這個差別，就知道為何 Trace 是分散式除錯的好起點。

Signal 先回答的問題 本課的界線
Metric 系統整體是否異常？例如 request 是否變慢、錯誤是否變多？ 後續獨立學 Prometheus 與 metrics data model。
Log 某個 component 當時說了什麼細節？ 後續學 log correlation 與結構化欄位。
Trace 這一次工作經過哪些步驟？哪一步造成延遲或失敗？ 本課只深入這一列。

Metric 很適合告訴你「結帳變慢了」；單筆 log 很適合告訴你「資料庫 timeout」。 但要還原哪一個 request 依序呼叫了哪些 component，需要能保留因果關係的 Trace。 這不是三種資料誰比較好，而是它們保留的證據不同。

把「因果關係」拆成最小資料需求

考慮一個 checkout request： 

Browser -> API Gateway -> Checkout Service -> Payment Service -> Database

若要回答「為什麼它花了 2 秒」，每一段工作至少需要留下：

  1. 它是什麼工作？ 例如 POST /checkout 或 database query。
  2. 何時開始與結束？ 才能得到 duration。
  3. 它屬於哪一次端到端 operation？ 才能把不同 process 的資料放在一起。
  4. 它由哪一段工作引發？ 才能建立因果順序與巢狀結構。
  5. 還有什麼背景？ 例如 route、status code、錯誤類型。

這五項需求直接導出 OTel 的 Trace data model；它不是任意設計的一串欄位。

Trace 與 Span：因果模型的兩個層級

Span 是一個有起訖時間的工作單元，例如一次 HTTP request、資料庫查詢或函式執行。 Trace 則是一個端到端 operation 中所有相關 Span 的樹。 

Trace ID: T

API Gateway        Span A (parent: none)
└─ Checkout         Span B (parent: A)
   ├─ Payment       Span C (parent: B)
   └─ Database      Span D (parent: B)

所有 Span 共用 Trace ID，因此知道它們屬於同一條端到端路徑； child Span 的 Parent Span ID 指向直接 parent 的 Span ID， 因此知道誰引發誰。沒有 parent 的 Span 是 root span。

資料模型依據：OpenTelemetry 官方文件 — Traces

最實用的心智模型：Trace 不是「很多 log 串在一起」而已； 它是跨 process 仍能保存 identity、time、context 與 hierarchy 的結構化工作紀錄。 這些關係才讓你畫出時間對齊的工作樹，並找出造成整次 request 變慢的那條因果鏈。

OTel 解決的問題，以及它刻意不解決的問題

有了這個模型，下一個問題是：每個 library、service 和 backend 都用不同埋點 API、欄位名稱與傳輸格式， 要如何保留可攜性？OpenTelemetry（OTel）提供 vendor-neutral 的 specification、API、SDK、 semantic conventions 與 Collector，統一 telemetry 的產生、處理與輸出方式。 

instrumented application
  -> OTel API / SDK / Collector
  -> storage, query, visualization backend

OTel 不是 storage backend、dashboard 或 alerting system。它讓你在程式碼中保留同一套 instrumentation，而把資料目的地留給 exporter 與 backend 設定決定。這個解耦是避免 vendor lock-in、 並支援日後自建 observability agent 的基礎。

依據：OpenTelemetry 官方文件 — What is OpenTelemetry?

把需求對照到一個 Span

下面是為了閱讀而簡化的表示法，不是 OTLP/JSON wire format：

{
  "name": "GET /checkout",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId": "00f067aa0ba902b7",
  "parentSpanId": null,
  "startTimeUnixNano": 1700000000000000000,
  "endTimeUnixNano":   1700000000250000000,
  "attributes": {
    "http.request.method": "GET",
    "http.response.status_code": 200,
    "http.route": "/checkout"
  }
}
欄位 回答的問題
name 這是什麼有意義的 operation？
traceId 它屬於哪一個端到端 operation？
spanId / parentSpanId 它在因果樹中的位置是什麼？
start / end time 這段工作花了多久？
attributes 哪種 HTTP operation、route、結果或 domain context 能幫助查詢？

課程地圖：只在真正需要時建立前置主題

目前路徑是 本課的因果模型 → Python manual instrumentation → Span data model 與 Semantic Conventions → Context propagation。這裡不假設 Kubernetes、networking 或 Prometheus 知識；它們會在成為理解瓶頸時， 各自建立可回鏈的專題：HTTP/networking 用於 propagation，Prometheus 用於 metrics aggregation， Kubernetes 用於 Resource metadata 與 Collector deployment。

有不懂的地方嗎？ 可以直接問「為什麼 metric 不能取代 Trace？」 「Trace 的 parent 關係如何跨 process 成立？」或「為何 OTel 不做 backend？」； 這些問題比背名詞更接近 SRE 真正需要的判斷能力。
