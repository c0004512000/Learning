25. Logs 的第一性原理與 Trace correlation

主要來源：OpenTelemetry — Logs、Logs Data Model、Python Logs instrumentation

第一性原理：有些事實是離散事件，不是 duration 或 aggregate

「Inventory reservation 在 12:03:21 被拒絕，原因為 warehouse capacity」是一個有時間、嚴重度、內容與 metadata 的事件。 Span 擅長一段 operation 的 start/end 與因果，Metric 擅長大量 measurements 的聚合；Log 擅長保存一筆事件的豐富內容。 

Metric：最近 5 分鐘 inventory failures = 420
Trace：這一筆 checkout 如何走到 inventory failure
Log：拒絕事件的類型、原因、warehouse 與當時訊息

三者不是互相複製。若每個 Span attribute 都再印一次 log、每筆 log 都再做 Span Event，資料量與重複訊號會上升； 應依查詢與生命周期選最合適的 primary representation，再用 correlation 串接。

LogRecord 的標準欄位

欄位回答的問題
Timestamp事件在 source clock 何時發生？
ObservedTimestampCollection system 何時觀察到它？
SeverityText/Number來源 severity 與正規化嚴重度？
Body事件主要內容／payload？
Attributes哪些 typed metadata 可描述與查詢此事件？
Resource哪個 entity 產生 Log？
InstrumentationScope哪個 logger/bridge/instrumentation code emit？
TraceId/SpanId/TraceFlags它是否發生在某個 Trace/Span Context？
EventName是否為具標準類型的 Event？

Trace fields 是 optional。Process startup log、cron scheduler log 或沒有 active Span 的 background log 合理地可能沒有 trace/span IDs； 不能以「所有 logs 必須有 Trace」作資料品質規則。

Timestamp 與 ObservedTimestamp 能揭露 transport delay

Timestamp         = application 實際產生事件的時間
ObservedTimestamp = Collector/OTel 首次觀察到的時間

ingestion delay ≈ ObservedTimestamp - Timestamp
（還要考慮 source clock skew）

對 file tailing、離線 buffer 或網路中斷後補送，兩者差距可能很大。若 backend 只按 observed time 排序，舊事件可能看似剛發生； 若 source clock 漂移，timestamp 也可能不可靠。兩個欄位保留了判讀空間。

Structured 不等於「外面有 JSON 大括號」

Structured log 需要穩定 schema、field names、types 與 semantics，讓 downstream 能可靠解析。每筆都輸出不同 keys/types 的 JSON 仍只是 semistructured。穩定設計可將 body 保持可讀，並把可查詢 metadata 放 typed attributes： 

Body: "Inventory reservation is slow"
Severity: WARN
Attributes:
  app.inventory.warehouse = "tw-north"
  app.inventory.elapsed_ms = 820

避免把 password、token、完整 headers/body 或無限制 stack/context dump 寫入 logs。Log volume 近似事件率成長， 每筆 payload 大小會直接乘上輸出、network、storage 與 indexing 成本。

OTel 不要求你放棄既有 logging API

Application 常保留 Python logging 等既有 API，再由 bridge/handler 轉成 OTel LogRecords：

Application logging call
  → logging framework Logger
  → OTel LoggingHandler / bridge
  → LoggerProvider
  → LogRecordProcessor
  → LogRecordExporter
  → Collector / console / backend

這讓 library 不必依賴特定 telemetry backend，也保留現有 logger level/filter/handler 生態。Python Logs implementation 目前在官方 language support 表列為 Development，因此實務導入要 pin 版本並驗證 API/field mapping。

另一條路：先寫 stdout/file，再由 Collector 收

Application → stdout/file
  → container runtime / file
  → Collector filelog 或特定 receiver
  → parse/transform
  → logs pipeline exporter

這適合 legacy/system/third-party logs，Collector 可解析、正規化格式。Direct OTLP 與 file collection 都合理，但若同一 record 同時經兩條路徑送入同一 backend，就會重複。先畫 emission topology，再決定唯一 authoritative path。

Collector 能轉換，不能憑空恢復：若 source unstructured message 沒有明確 timestamp、severity 或 stable fields， regex/parser 只能猜測現有文字，無法恢復從未記錄的語意。First-party application 應盡量在 source 建立結構。

閱讀 Python correlation 範例

範例位於 examples/0025-python-log-correlation.py：

log_provider = LoggerProvider(resource=resource)
log_provider.add_log_record_processor(
    BatchLogRecordProcessor(ConsoleLogRecordExporter())
)
handler = LoggingHandler(
    level=logging.NOTSET,
    logger_provider=log_provider,
)

TraceProvider 與 LoggerProvider 共用同一 Resource，確保 signals 指向同一 checkout entity；LoggingHandler 將 Python records bridge 到 OTel log pipeline。這與 Instrumentation Scope、Resource 的責任不因 signal 改變。 

with tracer.start_as_current_span("checkout.reserve_inventory"):
    logger.warning(
        "Inventory reservation is slow",
        extra={...},
    )

Log emit 當下 current Context 含 Span，所以 bridge 可填 TraceId/SpanId/TraceFlags。若把 log 移到離開 with 後， current Span 已結束並 detach，correlation fields 可能為空；「程式同一函式」不等於「同一 current Context」。

SRE debugging lab：Log 有了，correlation 為何失敗？

Case A：Trace ID 為空

確認 emit 時 current Span 是否有效，而非 request 早先曾建立。跨 thread/task/queue 時檢查 Context propagation； 再查 bridge 是否擷取、exporter/Collector/backend 是否保留 trace fields。

Case B：有 Trace ID，但 backend 查不到 Trace

可能該 SpanContext 未 sampled、Trace exporter 失敗、signals 路由到不同 tenant/backend，或 Trace retention 已過期。 Log correlation field 表示當時知道 identity，不保證 Trace signal pipeline 成功保存。

Case C：同一 Log 出現兩次

檢查 logger handler 數量與 propagate 是否又送 root handler；再查是否同時 direct OTLP 與 stdout/file collection， 以及 Collector 是否有兩個 receivers/routes。Dedup backend 只能掩蓋，應先修 topology。

練習：把一段 unstructured log 正規化

請拆成 Timestamp、Severity、Body、兩個 typed Attributes、Resource 與 Scope；再說明哪些欄位必須由 source 提供，哪些 Collector 可可靠 parse。
