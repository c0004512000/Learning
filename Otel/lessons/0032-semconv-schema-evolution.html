32. Semantic Conventions 與 schema 演進

共同語言帶來可攜性；版本化 schema 讓共同語言能安全改進 · Lesson 32 of N

本課成果

你會理解 Semantic Conventions 不只是 attribute spelling，而是跨 producer/consumer 的語意契約；能區分 SDK、instrumentation scope、semconv、schema 四種版本，理解 schema URL 的能力邊界，並設計 rolling migration 而不讓 dashboards/alerts 在混合版本期間失明。

主要來源：OpenTelemetry — Semantic Conventions、Telemetry Schemas

第一性原理：相同 key 只有在相同語意下才可聚合

兩套 instrumentation 都輸出：

method = "GET"
status = 500
duration = 120

Consumer 仍不知道 method 是 HTTP/RPC/DB、status 是 protocol 或 application code、duration unit 是 ms/s、operation boundary 在哪裡。 共同 key spelling 不足；必須共同定義 namespace、type、unit、value semantics、Span name/kind、何時存在與 requirement level。

Semantic Conventions（semconv）為常見 HTTP、RPC、DB、messaging、Resource、Metrics、Logs 等定義共同語言， 讓不同語言/framework 的 producers 產生可由同一 dashboard/query 解讀的 telemetry。

Conventions 約束的不只 Attributes

  • Attribute names、types、well-known values 與 requirement levels。
  • Span names、SpanKinds 與 error/status recording。
  • Metric instrument names、units、instrument kinds 與 attributes。
  • Log/Event names 與 attributes。
  • Resource entity identity。

因此「把 custom key 改成 semconv key」前，要確認 value meaning 與 recording condition 也符合。若把毫秒 value 放進要求 seconds 的 metric， 名稱正確仍會造成千倍錯誤。

Custom domain data 仍然必要：Semconv 不會定義你的 cart rejection reason。使用清楚的自有 namespace （例如 app.checkout.*），不要借用已定義的 OTel key 表達不同意思；有標準 convention 時再採用。

四種 version 各自版本化不同東西

Version版本化的對象在哪裡觀察
OTel SDK versionrecord/process/export implementationtelemetry.sdk.version
Instrumentation Scope version產生 telemetry 的 library/moduleScope metadata
Semantic Convention version共同欄位/operation 語意規範release/documentation；producer release notes
Schema version/URL所 emitted telemetry schema identity 與可用 transformationsResource/Scope schema URL in OTLP

升級 SDK 不必然升級 instrumentation package；升級 instrumentation 也可能改 semconv emission mode。Debug migration 時四者都要 inventory， 不能只看 application release version。

為什麼需要 Telemetry Schema？

Semconv 必須演進：名稱可能修正、namespace 重組、理解更成熟。但 producers 與 consumers 無法同時升級： rolling deploy 期間舊/new telemetry 會共存，backend/dashboard 也有自己的發布節奏。 

Semconv evolves
   │
   ├─ Producer A emits old schema
   ├─ Producer B emits new schema
   └─ Consumer expects one target schema

Schema URL identifies what each producer emitted;
schema-aware consumer/translator may convert supported changes.

Schema file version化並描述可行 transformations；Schema URL 唯一識別版本。OTLP 可攜帶 schema URL，讓 consumer 不必靠 scope version 猜 schema。

Schema URL 不是魔法開關

Producer 附 schema URL 只提供 identity。只有 backend/Collector/consumer 明確實作並啟用 schema-aware transformation，欄位才會轉換。 普通 pipeline 不會因 URL 存在就自動 rename。

而且 Telemetry Schema 的目標不是完整描述所有可能 types/values；它聚焦讓 semconv 常見變更可轉換。無法無損轉換的變更仍可能是 breaking change， 必須由 migration policy 處理。

Rolling migration：Consumer compatibility 先行

規劃範例位於 examples/0032-semconv-migration-plan.yaml，以 HTTP legacy/new keys 示意：

legacy: http.method
target: http.request.method

legacy: http.status_code
target: http.response.status_code
  1. Inventory：按 service + scope name/version + schema URL 查看實際 raw fields。
  2. Pin target：由 platform/data contract owner 指定 target semconv/schema。
  3. Canary：升級一個 producer cohort，檢查 OTLP raw data、cardinality、queries。
  4. Dual-read：Dashboards/alerts 暫時接受 old OR new names，避免 rolling deploy 失明。
  5. Normalize once：若用 schema translation，明確指定唯一 owner/target，避免重複改寫。
  6. Retire：等舊 producers 歸零且舊資料 retention window 過後，再移除 compatibility query。

通常 consumer dual-read 比 producer dual-write 更安全：producer 同時寫兩套 Metric names 可能雙倍 streams/alerts；Span attributes 雙寫也增加 payload/limits 競爭。 若特定 instrumentation 官方提供 transition mode，仍需按其文件測試並設退場日期。

Schema translation 的 placement

位置優點風險
ProducerSource truth 直接符合 target所有 producers 要分批升級
Collector集中相容不支援 schema 的 backend需 state/version policy；錯誤轉換影響大量資料
Backend/query保留 raw schema、read-time 適配每個 consumer/query 複雜度增加

不要同時在 producer、Collector、backend 都 rename 同一欄位。每次 transformation 應有 input schema、target schema、owner、idempotency 與 evidence； 否則可能 new→old→new 或欄位 collision。

Stability 不是「永遠不變」

Semconv pages 會標示 group/attribute stability 與 requirement level。Development/experimental conventions 可能快速改；stable conventions 有更強相容承諾， 但仍可能透過 deprecation/schema evolution改善。Production adoption 要 pin 版本、讀 migration notes、用 contract tests 驗證。

Requirement level 也不是「全部 required 就全部寫」。它描述在 convention applicability 條件下的要求；敏感資料、availability 與語意前置條件仍要遵守。

SRE debugging lab：Instrumentation 升級後 dashboard 歸零

Case A：Raw telemetry 有新 key，query 只讀舊 key

按 scope version/schema URL 比較 canary 與 stable cohorts。先改 query dual-read/normalize，恢復 visibility；再完成 producer rollout， 不要回滾只是因 dashboard 沒跟上，除非還有真實 semantic regression。

Case B：Old/new keys 同時存在

可能是 rolling deploy、transition mode、兩套 instrumentation producers 或 Collector duplicate transform。按 Resource instance + Scope 分組找 owner， 避免 backend 將兩者當兩倍 requests/metrics。

Case C：名稱相同，值分布卻改變

這比 rename 更危險。檢查 unit、operation boundary、recording condition、status mapping；Schema URL 只能幫助識別契約， 不能保證 producer bug 不會違反契約。用 known inputs 的 contract test 驗證 values。

練習：設計一個 HTTP semconv 遷移

列出 producers/scopes、old/new keys、target schema、canary cohort、dual-read query、translation owner、old-data retention 與退場條件。 再寫一個「同名但 unit 錯」的 test，證明只檢查 key existence 不足。
