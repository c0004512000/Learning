6. HTTP server Span 的標準語義

讓不同語言、framework 與團隊產生可共同判讀的證據 · Lesson 6 of N

為什麼「有 Span」仍然可能無法觀測？

想像 Python 服務用 method=GET，Java 服務用 verb=GET，Node.js 服務用 httpMethod=GET；它們都記錄同一件事，但 query、dashboard 與 alert 必須為每個語言寫一套規則。 資料存在，卻無法可靠地跨服務比較。

Semantic Conventions 解決的是共同語言：對常見 operation 定義一致的 Span name、kind、 status 與 attribute 語義。它不是 exporter 或 Collector 設定，而是 instrumentation 與資料消費者之間的契約。

主要來源：OpenTelemetry — Semantic conventions for HTTP spans

先固定 server 的責任邊界

HTTP server Span 表示 server 收到並處理一個 incoming HTTP request 的時間區間，因此 SpanKind 是 SERVER。它的 parent 通常是 remote client Span；若 upstream 沒有傳來有效 context，它也可能成為一條新 Trace 的 root。 

upstream service                       current service
CLIENT Span: outbound HTTP call  ---> SERVER Span: incoming HTTP request
          inject trace context            extract context, create child

本課只設計右側 server Span。箭頭表示 network call 與 context 傳遞；真正的 propagation 機制留到 Lesson 7。

一個乾淨的 HTTP server Span

Span name: GET /v1/users/{userId}
Span kind: SERVER
Status: UNSET

Attributes:
  http.request.method = "GET"
  http.route = "/v1/users/{userId}"
  url.path = "/v1/users/42"
  server.address = "api.example.com"
  http.response.status_code = 200

Span name：method + 低基數 target

當低基數 route 可用時，HTTP Span name 應是 {method} {route}；server 的 target 通常來自 http.route。Instrumentation 不應預設用實際 URI path 當 target，因為動態 ID 會讓 name cardinality 隨 request 增長。

http.route：framework 匹配出的模板

/v1/users/{userId} 是 routing template；/v1/users/42 是這次 request 的 實際 url.path。route 在 Span 開始時可能尚未由 framework 決定；若稍後才知道， instrumentation 應在 Span 結束前補上，並更新 Span name。

server.address：請求所指向的 server

它回答「client 想連到哪個 server address」，不等於 framework route，也不等於 remote client IP。 在 reverse proxy、load balancer 或 service mesh 存在時，original client、直接 network peer 與目標 host 可能是三個不同概念；不要用一個含糊的 host key 混在一起。

精確欄位地圖：HTTP route、實際 URL 與 cardinality。

Status 為何不能只看數字直覺？

Status 表示「從這個 Span 所代表的 operation 視角，結果是否為 error」。同一個 HTTP code 在不同角色的語義可能不同： server 正確拒絕一個無權限 request，代表 server 成功完成協定責任；client 卻可能認為自己的目的未達成。

HTTP responseSERVER Span 預設判定Why
1xx / 2xx / 3xxUNSET正常協定結果；除非另有 network/body error。
4xxUNSET通常是 client-side condition；server 可能正確完成處理。
5xxERRORserver 無法正常完成 request。

這是沒有額外 application context 時的通用規則，不是「404 永遠成功」。例如 application 明確預期資源存在， 更精確的 instrumentation 可以依 context 判定 Error。關鍵是 status 描述 operation outcome， 而不是把 HTTP code 機械地複製成成功／失敗標籤。

把欄位映射回 SRE 問題

SRE 問題證據不要誤用
哪類 API 慢？Span name 或 method + route不要用實際 path 分組。
這次打到哪個實體 path？url.path不要當作 route template。
server 回了什麼結果？http.response.status_code不要把 code 與 Span Status 視為同一欄位。
server operation 是否失敗？Span Status + error.type不要假設所有 4xx 是 server error。
request 指向哪個 host？server.address不要和 client/peer address 混用。

SRE debugging lab：修復不可聚合的 HTTP telemetry

Service A (Python)
  name = "GET /users/42"
  kind = INTERNAL
  attributes = { "method": "GET", "route": "/users/42", "code": 404 }
  status = ERROR

Service B (Java)
  name = "handleUser"
  kind = SERVER
  attributes = { "http.request.method": "GET",
                 "http.route": "/users/{userId}",
                 "http.response.status_code": 404 }
  status = UNSET

參考判讀
  1. Service A 的 incoming request 應是 SERVER，不是 INTERNAL。
  2. Span name 應穩定為 GET /users/{userId}，不能含實際 ID。
  3. attributes 應採 canonical keys，且 http.route 必須是 template。
  4. 若沒有額外 application context，server 對 404 的 Span Status 應保留 UNSET。
  5. 修正後，兩個語言的 telemetry 才能用相同 query 比較 latency 與 response codes。
