20. Baggage 的用途、傳播與風險

把 request-scoped context 帶到下游，但不把它誤認為 telemetry 或可信事實 · Lesson 20 of N

本課成果

你會從跨 process 資訊需求推導 Baggage，分清它與 TraceContext、Resource、Span attributes 的角色； 也能解釋為何 Baggage 會增加 wire cost、跨信任邊界，且不能直接用作 authorization truth。

主要來源：OpenTelemetry — Baggage、Context propagation

第一性原理：下游有時需要上游才知道的 context

假設 API gateway 知道 account tier，而 database service 想把 tier 加入一筆慢查詢的 telemetry。 Function parameters 可在同一 process 傳遞，但跨 HTTP/message boundary 後，下游需要可序列化的 carrier mechanism。 

Gateway knows: app.account.tier=gold
  → inject into outbound carrier
  → network / message boundary
  → downstream extracts Context
  → downstream may read reviewed Baggage value
  → instrumentation may explicitly add it to selected telemetry

Baggage 是與 Context 一起傳播的 key-value store。它解決「讓 downstream code 取得 request-flow metadata」， 並不自動代表這些資料已成為 Span、Metric 或 Log 的一部分。

最常見誤解是「設了 Baggage，backend 就會自動看到」。Baggage 與 signal attributes 是分離的 stores； 若要查詢，instrumentation 或受控 processor 必須明確讀取、驗證並複製到某筆 telemetry。

傳播與記錄分離的價值：不是所有下游 context 都值得永久保存。這個分層讓你分別控制 「誰能在 execution path 讀取」與「哪些 observability records 要承擔儲存、索引與隱私成本」。

Baggage 的 Context 也是 immutable value

閱讀範例 examples/0020-baggage-roundtrip.py：

outbound_context = baggage.set_baggage(
    "app.account.tier", "gold"
)

這不是修改一個 global dictionary，而是回傳包含該 Baggage entry 的 derived Context。 若忽略回傳值，後續 inject 使用舊 Context，就不會帶出新 entry。這與 Lesson 7 的 context propagation 模型一致。 

carrier = {}
propagator.inject(carrier, context=outbound_context)

inbound_context = propagator.extract(carrier)
tier = baggage.get_baggage(
    "app.account.tier", context=inbound_context
)

Dictionary 模擬 HTTP headers，不發出網路。Inject 把 in-memory Baggage 轉成 carrier representation；Extract 把收到的 carrier 解析成新的 Context。Carrier 只是 transport adapter，不是 Context 本身。

Wire cost 會被 fan-out 放大

Baggage 常以 request headers 傳輸。若 baggage header 大小約為 H bytes，而一次 operation 發出 N 個 downstream calls，僅此 operation 的額外 outbound bytes 約為： 

extra bytes ≈ H × N

再乘 request rate R：
extra bytes / second ≈ H × N × R

這還沒包含 proxy parsing、serialization、memory allocation 與每一 hop 再 fan-out 的成本。因此 Baggage 應小、穩定、白名單化； 不要放大型 payload、完整 user profile 或「以後也許有用」的資料。

安全模型：Baggage 是跨邊界 input，不是可信 authority

自動 instrumentation/propagators 可能把 Baggage 帶到多數 outbound requests，甚至第三方 API。它會出現在 headers， 且 Baggage 本身沒有內建 integrity 保證，inbound value 可能由外部 client 偽造。

  • 不要放 passwords、access tokens、session secrets 或不必要的 PII。
  • 在 egress trust boundary 對 keys 做 allowlist/drop，不把內部 context 無條件送給第三方。
  • 在 ingress 驗證 key、value、長度與允許來源。
  • 不可用 account.role=admin Baggage 直接做 authorization；回到可信 identity system 驗證。
  • 複製進 Span attribute 前，再做一次 privacy 與 cardinality review。

何時值得使用 Baggage？

一個候選值需同時通過三關：

  1. Necessity：多個 downstream components 確實需要，但無法在當地可靠重建。
  2. Boundedness：keys/values 有有限集合或嚴格長度，wire 成本可預測。
  3. Trust policy：可明確定義 inbound validation、internal propagation 與 external egress handling。

例如 account tier 的小型列舉值可能適合；完整 account object 不適合。User ID 即使技術上可傳，也可能涉及高基數與個資， 需要組織政策與最小化設計，不能因官方示例提到就直接採用。

SRE debugging lab：Baggage 沒出現或不該出現

Case A：上游 set 了，下游 get 是 None

依序驗證：是否保留 set_baggage 回傳的新 Context、inject 是否使用該 Context、carrier 是否真的含 baggage header、 proxy 是否移除、下游是否配置 Baggage propagator、extract 後 get 是否使用 extracted Context。

Case B：下游能讀到，backend Span 卻沒有 attribute

這可能完全符合設計：Baggage 不會自動成為 Span attribute。檢查是否有明確 enrichment policy；若新增 copy， 要先決定允許哪些 keys、在哪些 Spans 記錄，以及如何控制 PII/cardinality。

Case C：第三方收到內部 Baggage

這是 egress policy failure，不是「header 顯示錯誤」。在 outbound trust boundary 移除非必要 entries 或使用受控 propagator； 同時盤點 logs/traces 是否已永久記錄敏感值並依事件處理程序處理。

練習：審查三個候選 Baggage items
  • app.account.tier=gold：小型 enum，可考慮，但仍需驗證與 egress policy。
  • authorization=Bearer ...：secret，禁止放 Baggage。
  • app.user.id=...：需先做 necessity、privacy、cardinality 與 retention review。
