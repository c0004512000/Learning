5. Span / Event / Attribute / Log 的設計邊界

從「事故時我需要什麼證據？」反推埋點，而不是從 function 名稱反推埋點 · Lesson 5 of N

這一課要拿下的能力

這一章不是教你背四個名詞，而是訓練一個 SRE 真正在工作上會反覆使用的判斷： 看到一段程式、一次 failure、或一個 troubleshooting 需求時，決定它該成為 Span、Event、Attribute、Log，還是根本不該記。

先記住唯一總原則： telemetry 不是「把程式裡發生的事情全部留下來」，而是「用可接受成本，留下足以回答事故問題的證據」。

1. 先不要想 OTel：事故時你到底想知道哪一種答案？

假設一個 checkout request 花了 2.8 秒。你可能會問四種完全不同的問題：

你真正想知道的問題需要的證據形狀OTel / observability 模型
「這次 checkout 是哪個 provider？有幾件商品？」描述整段工作的值Attribute
「retry 是在第幾毫秒發生？」Span 期間某一個時間點Event
「2.8 秒到底花在 pricing 還是 payment？」某個子工作的開始、結束、duration、outcomeChild Span
「payment library 當時丟了哪個 exception、stack、response detail？」一筆可獨立保存與搜尋的診斷紀錄Log

所以不是：

function → Span
error    → Log
value    → Attribute

而是：

我要回答什麼事故問題？
        ↓
需要哪一種證據？
        ↓
才決定 telemetry model

2. Child Span 到底是什麼？先把名字拆開

Child Span 不是另一種新的 telemetry 資料型別。 它就是一個普通 Span，只是它的 parent 是另一個 Span。 

Span: POST /checkout          ← parent
  |
  +-- Span: pricing.calculate ← child
  |
  +-- Span: payment.authorize ← child

為什麼要拆 child？因為 parent 只能告訴你 checkout 總共 2.8 秒； child 才能告訴你「其中 payment.authorize 花了 2.5 秒，而且它失敗了」。

Child Span 的第一性判斷： 只有當這個子工作值得擁有自己的 duration、outcome 或因果位置 時，才值得拆成另一個 Span。

process 內部 function 什麼時候真的值得一個 Span？

你前面問「除了 DB query 還有什麼？」以下都是 production 很常見、即使沒有跨 process，也可能值得獨立觀測的例子：

process 內部工作什麼情況值得 Child Span你想回答的 SRE 問題
PDF / report rendering有時 50ms、有時 2srequest 慢是不是卡在 render？
大量 JSON serializationpayload 大時 CPU 明顯升高latency 是 business logic 還是 serialize？
image resize / compression影像尺寸不同造成巨大 latency 差CPU hot spot 是哪個 processing stage？
encryption / signature verification偶發卡住或 failure 有獨立排障價值request failure 是 crypto 還是後續流程？
rule engine / pricing engine規則數量變多後 latency 上升哪個 business stage 在退化？
lock / semaphore wait真正問題可能是等待，不是執行本身慢是 CPU、I/O，還是 lock contention？
large batch validation某些 batch 需數百毫秒甚至數秒資料量與 validation latency 是否相關？
template rendering某模板特別慢或常失敗failure boundary 是否在 render stage？

反過來，這些通常不值得為了「它是一個 function」就建 Span：

normalize_email()
trim_whitespace()
parse_boolean()
calculate_tax_line_1()
calculate_tax_line_2()
small helper that always takes 0.1ms

因為即使你看到它們的 duration，通常也不會改變事故判斷。這叫做沒有獨立診斷價值。

3. Event 是什麼？它解決的是「某一刻發生了什麼」

Span 是一段時間：有 start、end、duration。 但有些東西不是一段工作，而是在這段工作期間發生的一個重要時刻。 

Span: payment.authorize
start ------------------------------------------------ end
          ↑                 ↑
     retry.started      fallback.selected
        Event               Event

Python 概念上會是：

with tracer.start_as_current_span("payment.authorize") as span:
    ...
    span.add_event("retry.started", {"retry.attempt": 2})
    ...

Event 有自己的 timestamp，也可以帶少量 attributes；但它沒有自己的 duration，也沒有自己的 Span ID。

最常見 Event 情境： cache miss、retry started、fallback selected、circuit breaker opened、state transition、exception recorded。

同一件事到底要 Event 還是 Child Span？

看你要回答的問題。

需求選擇原因
只想知道 retry 何時發生、attempt 幾次Event重點是一個時刻，不需要 duration。
每次 retry 都想比較各自 latency / outcomeChild Span每次 attempt 已成為值得單獨觀測的工作。
只想知道這次 request 最後有沒有 retryAttribute它只是這次 operation 的一個結果特徵。

4. Failure 為什麼不只寫 Log 就好？

這裡最容易誤解的是「error 發生 → 寫 log」。Log 當然很有用，但 Log 和 Span 回答的是不同問題。

假設 payment timeout：

2026-09-04 02:10:33 ERROR payment timeout after 2000ms

這筆 Log 能告訴你「某個時刻有 timeout」。但單獨一筆 Log 不自然回答：

它屬於哪一條 checkout request？
checkout 總共花多久？
payment 在整條 request 裡佔多久？
payment 的 parent 是誰？
同一條 trace 還有哪些下游工作？
```

這些是 Span 的強項。

你要的資訊SpanLog
operation duration很適合通常要自己由多筆 log 推算
parent / child 因果位置原生模型不是 log 的核心模型
operation outcome / failure boundary很適合可以描述，但不自然形成 trace tree
stack trace / verbose message / raw diagnostic detail不適合塞很多文字很適合
沒有 active trace 時仍要記錄不一定有 SpanLog 可以獨立存在
所以不是 Span 或 Log 二選一。 如果同一個 failure 同時需要「它在整條 request 的位置與 duration」和「詳細 exception / stack / message」，可以同時有 Span + Log；重點是不要把完全相同的文字無腦重複兩份。

什麼 failure 根本不值得多拆一個 Span？

例如：

checkout.process
  -> validate_coupon()  # 0.2ms，coupon invalid 很常見
```

如果 `validate_coupon()` 的 latency 不重要，failure 也只是 parent checkout 的一個正常 business outcome， 就不需要為了「它可能 fail」額外建 child span。你可以在 parent Span 留下結果 Attribute，必要時再記 Event 或 Log。

但如果：

fraud.evaluate()
通常 20ms
偶爾 1.8s
而且 failure 會阻擋 checkout
```

它就有獨立 latency / failure boundary，值得成為 Child Span。

來源：OpenTelemetry Trace API — Span / Event / child span guidance、 OpenTelemetry Logging — correlation with TraceId / SpanId

5. Queryability 不要背英文：把它翻成「我真的會怎麼查？」

原本教材寫「事故時會用它建立哪個查詢？」太抽象。實際意思是： 如果 production 出事，你能不能想像自己真的拿這個欄位去 filter、group 或 compare？

例如 payment latency 高：

我會不會想查：
payment.provider = "provider-a" 的 span 是否特別慢？

我會不會想 group by：
checkout.region = "TW" / "US" 哪個區域 error rate 特別高？

我會不會想 compare：
cart.item_count > 100 的 checkout 是否 latency 明顯上升？
```

如果答案是「會」，這個 Attribute 就有明確 query/debug 價值。

但：

loop_index = 17
internal_tmp_hash = "..."
random local variable = ...
```

如果你完全想不到事故時為什麼要搜尋它，就不要因為它存在於程式碼裡而留下來。

6. Cardinality 不要背定義：想像 backend 會出現多少種不同值

Cardinality = 這個欄位可能出現多少種不同值。

Attribute可能值直覺
deployment.environmentprod / stage / test非常有限
payment.provider3～5 家 provider有限
http.route數十～數百種 route template通常可控
user.id可能數百萬個高 cardinality
order.id幾乎每個 request 都不同接近 request 數量
request.uuid每次都唯一極高 cardinality

高 cardinality 不是自動等於禁止。Trace ID 本身就是高 cardinality。 真正的問題是：你是否真的需要用這個 business value 搜尋、backend 成本是否能接受、以及是否涉及個資或敏感資料。

SRE 問法： 不是「高 cardinality 可不可以？」；而是「這個高 cardinality 欄位提供的排障價值，值不值得它的 indexing / storage / privacy 成本？」

7. Availability 不要背：Sampler 是在 Span 一開始就做決定

假設你的系統使用 head sampling：Span 一建立時，就決定這條 trace 要不要被 sample。 可以把 Sampler 想成門口保全：人在進門那一刻就決定要不要放行，不會等你兩分鐘後才告訴他結果。 

Span 建立
   |
   +-- 此刻 Sampler 做決定
   |
   +-- 後來才知道 http.status_code = 500
   |
   +-- 更後來才知道 total_cents = 3674
```

因此：

資訊Span 建立時知道嗎？Head Sampler 能用嗎？
customer.tier = premium如果 request 一開始就知道可以在建立 Span 時提供
http.request.method = POST通常知道可以
http.response.status_code = 500通常 response 結束才知道不能改變已完成的 head sampling 決策
checkout.total_cents可能 business logic 後才算出若之後才 set，不能回頭改 head decision

所以官方才建議：如果某個 Attribute 要參與 sampling decision，盡量在 Span creation 時提供。 後面會再正式學 head sampling / tail sampling，現在只需要理解「決策時間點」這件事。

來源：OpenTelemetry Trace API — attributes at Span creation。

8. 最後才把四種模型放在同一張 decision tree

我想留下什麼證據？
│
├─ 這是一段值得獨立量 duration / outcome 的子工作嗎？
│    └─ 是 → Child Span
│
├─ 這只是目前 Span 期間某一刻發生的重要事情嗎？
│    └─ 是 → Event
│
├─ 這只是描述「這一次 operation」的可查值嗎？
│    └─ 是 → Attribute
│
├─ 我需要詳細 message / stack / diagnostics，或沒有 Span 也要獨立保存嗎？
│    └─ 是 → Log
│
└─ 都不是 → 很可能根本不用記
```
同一件事故可能需要不只一種 telemetry。 例如 payment timeout 可以有：payment Child Span（duration + causal position）、Event（retry 發生時間）、Attribute（provider / attempt count）、Log（詳細 exception）。 它們不是重複，而是在回答不同問題。

9. 一個 Python 情境，把四種模型放在一起

import logging
from opentelemetry import trace

logger = logging.getLogger(__name__)
tracer = trace.get_tracer(__name__)

with tracer.start_as_current_span("checkout.process") as checkout_span:
    checkout_span.set_attribute("cart.item_count", 3)

    checkout_span.add_event("promotion.fallback_selected")

    with tracer.start_as_current_span("pricing.calculate") as pricing_span:
        try:
            calculate_price()
        except Exception:
            pricing_span.add_event("pricing.failed")
            logger.exception("pricing calculation failed")
            raise
```

逐行不是背 API，而是看需求：

  • cart.item_count：描述整次 checkout → Attribute。
  • promotion.fallback_selected：某一刻發生 → Event。
  • pricing.calculate：要獨立知道 latency / failure → Child Span。
  • logger.exception(...)：需要詳細 exception / stack → Log。

10. SRE Lab 1：過度埋點，Trace 已經變成 call stack

某 checkout request 產生：

Span: checkout-user-brandon@example.com-order-9f1a...
  Span: normalize_email
  Span: trim_whitespace
  Span: validate_item_1
  Span: validate_item_2
  Span: validate_item_3
  Span: payment.authorize

Attribute: auth.token = "eyJ..."
Attribute: item.count = 3
```

先自己判斷：哪些資訊真的幫助 SRE？

展開 SRE 判讀

問題 1：Span name 過度具體。 Email 與 order UUID 讓每個 Span name 幾乎都不同，也有敏感資料風險。應改成穩定名稱，例如 checkout.process。

問題 2：helper functions 被誤做成 Span。 normalize / trim 沒有獨立 latency / failure 意義，不值得污染 trace tree。

問題 3：逐 item validation 過度拆 Span。 如果只是 3 個超短操作，保留 item.count=3 已足夠。只有 batch validation 本身真的可能慢時，才考慮一個 cart.validate Span。

問題 4：credential 不應進 telemetry。 auth.token 應移除。

保留： payment.authorize 通常是獨立 latency / failure boundary，很值得保留。

11. SRE Lab 2：Trace 太粗，只知道 request 很慢

Span: POST /invoice/generate     2.43s
  Attribute: template.type = "monthly"
```

Application log：

02:10:01.001 start render_pdf
02:10:03.210 render_pdf done
```

你現在已經有線索：2.43 秒裡，render_pdf 花了約 2.2 秒。但每次事故都靠人工對 log timestamp 很痛苦。

你會怎麼改埋點？

如果 PDF rendering 是 production 裡真正常見的 latency boundary，可以增加一個 invoice.render_pdf INTERNAL Child Span。

Span: POST /invoice/generate       2.43s
  └─ Span: invoice.render_pdf      2.21s
       Attribute: template.type = "monthly"

這不是「因為 render_pdf 是 function」，而是因為你已經證明 SRE 會需要單獨回答「時間是否花在 rendering」。

12. SRE Lab 3：只有 Error Log，為什麼還是不夠？

ERROR payment timeout provider=provider-a timeout_ms=2000
```

事故期間有 3% checkout 失敗。只有 log，你可以搜尋 timeout，但你很難快速回答「timeout 在整條 request 裡佔多少時間、是不是只有 provider-a、上游 checkout 總 latency 多久」。

較好的 telemetry 設計 
Span: POST /checkout                2.35s ERROR
  └─ Span: payment.authorize        2.01s ERROR
       Attribute: payment.provider = "provider-a"
       Event: retry.started @ +1005ms

Log correlated to same trace/span:
ERROR payment timeout ... stack / detailed message
```

Span 用來定位 failure boundary 與 duration；Log 保留 verbose diagnostic detail；Event 告訴你 retry 的時間點。

13. SRE Lab 4：Retry 到底用 Event 還是 Child Span？

需求 A：

只想知道 payment request 有沒有 retry、retry 幾次、何時發生。
```

這時一個 payment Span + retry Events 通常夠。

需求 B：

想比較 attempt 1 / 2 / 3 各自 latency、provider、error outcome。
```

這時每個 attempt 已經有自己的 operation 意義，可以考慮 child spans：

Span: payment.authorize
  ├─ Span: payment.attempt   800ms ERROR
  ├─ Span: payment.attempt  1200ms ERROR
  └─ Span: payment.attempt   110ms OK
```
不是「retry 一律 Event」或「retry 一律 Span」。 你需要的 evidence granularity 決定模型。

14. SRE Lab 5：哪些 Attribute 值得留下？

候選欄位：

deployment.environment = "prod"
payment.provider = "provider-a"
user.email = "brandon@example.com"
order.id = "9f1a..."
cart.item_count = 128
loop_index = 17
```
逐項判斷
  • deployment.environment：常用來 filter，值有限，通常合理。
  • payment.provider：可比較 provider latency / error，通常很有 SRE 價值。
  • user.email：高 cardinality + PII；除非有非常明確且合規需求，通常不要。
  • order.id：可能對單筆事故追蹤有用，但高 cardinality；需考量 backend、privacy 與是否已有其他 correlation ID。
  • cart.item_count：可檢查資料量是否造成 latency，常有分析價值。
  • loop_index：通常沒有 production troubleshooting 價值。

15. SRE Lab 6：你想用「錯誤」決定 sampling，但錯誤是最後才知道

需求：

只保留 HTTP 500 traces。
```

但使用 head sampling 時：

request start
  ↓
Sampler 此刻就決定 sample / drop
  ↓
business logic
  ↓
最後才知道 status_code = 500
```
為什麼這是設計上的矛盾？

因為 http.response.status_code 在 sampling decision 之後才出現，不能回頭改掉已做出的 head sampling decision。

這不是 set_attribute() 寫法錯，而是「你想拿一個未來才知道的資訊，去影響現在就要做的決策」。後續 sampling 章節會再處理 tail sampling 等方案。

16. 綜合 Debug：先讀 Trace，再決定哪裡需要更多 telemetry

Trace: checkout request

POST /checkout                 2850ms ERROR
├─ inventory.reserve            82ms OK
├─ pricing.calculate            41ms OK
└─ payment.authorize          2610ms ERROR
     Event retry.started      +820ms
     Event retry.started     +1810ms
     Attribute provider="provider-a"
```

用 SRE 的順序讀：

  1. 先找 latency concentration：2610 / 2850ms 幾乎都在 payment。
  2. 再找 failure boundary：payment.authorize ERROR，其他 child spans OK。
  3. 看 timeline marker：兩個 retry Event，代表 payment 期間至少發生兩次重試。
  4. 看可分組資訊：provider-a，可進一步查 provider-a 是否普遍 error/slow。
  5. 若還需要 stack / vendor response：跳到同 trace/span 的 Log，而不是再把大量文字塞進 Span。
好的埋點不是讓 Trace 看起來很滿。 好的埋點是讓你從「整條 request → 慢在哪 → 壞在哪 → 哪個條件相關 → 需要哪些細節」一路收斂，不必猜。

Q1. 一個 process 內的 PDF render 通常 40ms，但偶爾會花 2 秒，而且你需要單獨比較它的 latency。最合理的設計是？
Q2. 你只需要知道 payment Span 期間「第二次 retry 在何時發生」，不需要量每次 retry duration。最合理的是？
Q3. 哪個理由最能支持把 payment.provider 做成 Span Attribute？
Q4. Payment timeout 已經有一個 Child Span，但你還需要完整 exception stack。哪個做法最合理？
Q5. 哪個欄位最明顯屬於高 cardinality，而且通常需要特別評估成本與隱私？
Q6. 使用 head sampling 時，哪個資訊如果在 Span 建立後才知道，就不能回頭改變已做出的 sampling decision？

最後 Recap：每個名詞只留一句話

Span：一段值得獨立觀測 start、end、duration、outcome 與因果位置的 operation。

Child Span：仍然是一個 Span，只是它的 parent 是另一個 Span，用來表示值得獨立觀測的子工作。

Event：附在 Span 上、表示「某一個重要時刻發生了什麼」的 timestamped record。

Attribute：描述「這一次 operation」且值得查詢／分組／比較的 key-value metadata。

Log：一筆可獨立保存的事件紀錄，適合詳細 message、stack、diagnostic context，也可以用 TraceId / SpanId 與 trace 關聯。

Queryability：你是否真的會拿這個欄位去 filter、group、compare 或 debug。

Cardinality：一個欄位可能出現多少種不同值；值越接近每 request 唯一，越需要評估成本與隱私。

Availability：某個資訊在決策發生的當下是否已經知道；對 head sampling 而言，就是 Span 建立時是否已存在。

快速參考：Telemetry 設計決策卡：Span / Event / Attribute / Log
把真實 service flow 丟給我最有價值。 我們可以直接做 production-style instrumentation review：先決定 SRE 事故時要回答什麼，再逐段判斷哪裡是過度埋點、哪裡缺證據、哪個欄位有成本或 privacy 問題。

主要來源： OpenTelemetry Trace API、 OpenTelemetry Logging Specification、 OpenTelemetry Semantic Conventions。
