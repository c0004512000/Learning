5. Span 邊界與欄位設計

不是「能埋就埋」，而是保存恰好足夠的因果證據 · Lesson 5 of N

這一課解決什麼問題？

OpenTelemetry 允許你自由建立 Span 與 attributes，但自由不等於每個 function 都應該成為 Span。 每新增一個 Span，都會增加 application 端的建立與處理成本、export 流量、Collector 負荷、 backend 儲存量，以及 SRE 判讀時的雜訊。

因此 Span 設計的第一性問題不是「API 怎麼呼叫」，而是：未來發生故障時，哪一段子工作需要被單獨看成一個 Span， 讓你能獨立看到它花多久、最後得到什麼結果，以及它在 parent/child 關係中是誰的子工作？

先把兩個容易抽象化的字拆掉：
  • Outcome：就是「這段 operation 最後得到什麼結果」。最簡單可以是成功／錯誤；也可能是某個 business result。它不是 Span 裡一個叫 outcome 的固定欄位；實際上可能由 Span Status 或適當 Attribute 表達。
  • Causal position：causal 是「因果的」，不是 casual。這裡也不是一個固定欄位；它指這個 Span 在 parent/child 因果關係中的位置：誰引發它、它是哪個工作的子操作。
Span: POST /checkout            ← parent
├─ Span: calculate_total        ← child
└─ Span: payment.authorize      ← child

payment.authorize 的 causal position：
「它是 POST /checkout 底下的子工作」

官方基礎：OpenTelemetry — Spans；欄位語義：OpenTelemetry Trace API

先建立真正的依附關係：Event、Attribute 都掛在 Span 上

這裡不能把 Span、Event、Attribute 想成三種彼此平行、各自獨立存在的 tracing record。 在 OpenTelemetry Trace API 裡，Span 才是代表 operation 的主要資料；Span 內可以有 Attributes，也可以有一串 Events。 而一個 Event 自己還可以再帶 Event Attributes。 

Span: payment.authorize
├─ Span Attribute: payment.provider = "provider-a"
├─ Span Attribute: retry.count = 1
│
└─ Span Event: retry.started @ 02:00:00.321
   └─ Event Attribute: retry.attempt = 2
你現在缺的證據實際動作資料關係
描述目前這段 operation 的一個值，例如 provider、item count在既有 Span 上加 AttributeAttribute 依附於這個 Span。
記錄目前 Span 期間某個重要時刻，例如 retry、cache miss在既有 Span 上加 EventEvent 依附於這個 Span，並帶 timestamp。
某個子工作需要自己的 start/end、duration、結果與 parent/child 關係建立新的 Child Span這是一個新的 Span，parent 指向原本的 Span。
最小充分證據原則： 先以「目前已經有的 Span」為中心。只缺一個描述值，就在這個 Span 加 Attribute；只缺某個重要時刻，就在這個 Span 加 Event； 只有當某個子工作真的需要自己的開始／結束、duration、結果與 parent/child 關係時，才再建立一個 Child Span。
Child Span（子 Span）不是第四種資料。 它仍然是 Span，只是它的 parent 是另一個 Span。例如 POST /checkout 是 parent， 其中的 payment.authorize 可以是 child Span。

Span 邊界的兩個判斷軸

軸一：它有獨立的時間區間嗎？

「呼叫 payment service」有清楚開始與結束，也有可單獨診斷的 latency，因此適合成為 Span。 「cart 內有 3 件商品」沒有時間區間，只是 operation 的描述，應是目前 Span 的 Attribute。

軸二：它是需要保留的因果節點嗎？

跨 process 的 HTTP/database call 通常值得成為節點，因為你要知道時間花在本地還是遠端。 process 內部 function 則不能只看「它是一個 function」；要問：如果這段工作變慢或失敗，我是否需要在 Trace 裡把它單獨指出來，才能知道時間與故障到底卡在哪一段？

process 內部工作可能值得 Span 的原因SRE 真正想回答的問題
PDF / report rendering有時 40ms、有時 2srequest 變慢是不是卡在 render？
大量 JSON serializationpayload 大時 CPU latency 明顯增加慢在 business logic 還是 serialize？
image resize / compression輸入尺寸造成巨大耗時差CPU hot spot 是否在影像處理？
fraud / pricing rule evaluation規則增加後可能獨立退化或失敗哪一個 business stage 造成 latency / failure？
lock / semaphore wait等待時間可能遠大於真正運算慢是計算、I/O，還是 contention？
large batch validation資料量大時可從毫秒變成數秒validation 是否成為獨立 bottleneck？

反過來，像 trim_whitespace()、parse_boolean()、固定約 0.1ms 的 helper，通常就算能量到 duration，也不會改變事故判斷，不值得只因為 function boundary 而建 Span。

├─ 某個子工作需要自己的 start/end、duration、結果、parent/child 關係？
│    └─ 是 → 建立新的 Child Span
│

Failure：為什麼不是全部寫 Log 就好？

「會失敗」本身，不足以決定要不要多建一個 Span。 還是回到同一個問題：你需不需要把這個 failure 放回整條 request 的因果路徑裡，知道它是哪一段工作、花多久、parent 是誰？如果需要，Span 提供這種結構。

先把 stack trace 拆開：它其實只是「錯誤發生前的 function 呼叫路徑」

假設 Python 執行 checkout()，裡面呼叫 authorize_payment()，後者又呼叫 send_request()。 程式在進入下一層 function 時，runtime 必須記住「等這層做完要回到哪裡」，因此會維護目前正在執行的 function 呼叫層級。 這組尚未返回的 function 呼叫常被稱為 call stack（呼叫堆疊）。 

checkout()
  └─ authorize_payment()
       └─ send_request()
            └─ TimeoutError  ← 錯誤在這裡發生

當錯誤發生時，如果把這條「從哪個 function 一路呼叫到出錯位置」的路徑印出來，就是 stack trace。 Python 的錯誤輸出通常會看到 Traceback (most recent call last)；這就是 Python 呈現 stack trace 的常見形式。 它的價值是讓你知道：哪一行程式透過哪些 function calls 最後走到錯誤點。

那 Span 和 Log 到底怎麼關聯？先看它們其實是兩份不同資料

一筆 Log 並不是被塞在 Span 裡。Span 是 trace signal 的資料；LogRecord 是 log signal 的資料，它們可以各自送進不同的 pipeline / backend。 關聯的方法很簡單：讓 LogRecord 帶上「產生這筆 Log 當下，正在執行的 Span」的 TraceId 與 SpanId。 

Span
  trace_id = abc123
  span_id  = def456
  name     = payment.authorize

LogRecord
  trace_id = abc123   ← 一樣
  span_id  = def456   ← 一樣
  body     = "payment timeout"

相同 TraceId + SpanId
        ↓
backend 知道：這筆 Log 是 payment.authorize 執行期間產生的

這種「靠共同的 TraceId / SpanId 把 Log 與 Trace 對起來」就叫 log correlation（Log 關聯）。 而一筆已帶有這些 trace context 欄位、能被對回某個 Trace / Span 的 Log，常被口語稱為 correlated Log。 所以它不是另一種特殊 Log 類型；重點只是這筆 Log 帶有足以對回 Span 的 IDs。

先記一句： Span 與 LogRecord 是兩份獨立 telemetry；TraceId / SpanId 像共同索引鍵，讓 observability backend 可以把它們顯示在一起。

官方依據：OpenTelemetry Logging — Log Correlation：LogRecord 可包含 TraceId / SpanId，直接對應同一 execution context。

那為什麼我好像可以「在 Span 裡看到 Log」？

這裡有兩件非常容易混在一起的事：

你在 UI 看到的東西資料模型上到底是什麼
Span 裡有一個 exception、retry、cache miss 等時間點Span Event。它真的屬於 Span 的資料。
Span 頁面旁邊／下面顯示 application logs獨立 LogRecords。Backend 用相同 TraceId / SpanId 查出相關 Logs，再在 UI 放到 Span 附近。

OpenTelemetry 的 span.record_exception(error) 更容易造成混淆：它不是「寫一筆 Log 進 Span」，而是把 exception 記成一個 Span Event。 這個 exception Event 可以帶 exception.type、exception.message，以及描述 function 呼叫路徑的 exception.stacktrace。 因此 Trace UI 裡可能直接看到一大段錯誤文字，看起來很像 Log，但資料模型上仍是 Span Event。

官方依據：OpenTelemetry — Exceptions on Spans；recordException 是 AddEvent 的特化形式。

所以 failure 時 Span、Span Event、Log 怎麼先分？

你需要回答的問題較自然的資料
哪一段 operation 失敗？花多久？它在 Trace 的哪個 parent/child 位置？Span
這個 Span 執行期間 exception 在哪個時間點發生？Span Event（例如 exception Event）

validate_coupon() 0.2ms，invalid coupon 是正常 business result通常不新增 Child Span這個結果沒有獨立 latency，也不需要在 Trace tree 中另占一個子工作位置。

名稱為何必須穩定？

Span name 應描述一類 operation，而不是某一次 instance。若使用 GET /users/42、GET /users/99 當名字，backend 會看到大量幾乎相同、 卻不能自然聚合的 operation。穩定名稱 GET /users/{userId} 保留「這是哪類工作」； 必要的 instance context 再放到合適的 Attribute，並先評估敏感性與 cardinality。

設計例子後果
穩定 operation nameGET /users/{userId}可依 logical operation 聚合 latency 與 errors。
動態 instance nameGET /users/42名稱基數隨使用者增加，查詢與儲存成本上升。
沒有診斷語義handle_request值穩定但無法區分 operation，聚合結果失去解釋力。

Attribute 的四道守門問題

  1. Queryability：不要背這個字。直接問：「事故時我真的會拿它 filter / group / compare 嗎？」例如 payment 變慢時，payment.provider 可以讓你比較 provider A/B；loop_index=17 通常沒有這種用途。
  2. Cardinality：直接問：「這個欄位會出現多少種不同值？」environment 可能只有 prod/stage/test；order.id 可能幾乎每個 request 都不同。高 cardinality 不是自動錯，但你必須知道它帶來更高的索引、查詢與儲存成本，且是否真的值得。
  3. Sensitivity：是否含 token、email、完整 URL query、payload 或其他個資／機密？有的話不要因為 debug 方便就直接送進 telemetry。
  4. Availability / Timing：先只問：「這個值是在 Span 開始前就知道、執行中才知道，還是結束後才知道？」例如最終 latency 只有工作完成後才知道。它為什麼會影響 sampling，等 Lesson 9 建立 sampling 心智模型後再回來看；現在不需要先背 head sampler。

最後 Recap

Span：代表一段 operation；需要時可成為另一個 Span 的 parent 或 child，形成 Trace 的 parent/child 因果關係。

Child Span：仍然是 Span，只是它的 parent 是另一個 Span，因此可以獨立記錄自己的 start/end、duration 與結果。

Span Event：依附在某個 Span 上、描述該 Span 期間某個重要時間點的紀錄；它不能在 Trace tree 裡獨立成為一個 operation node。

Span Attribute：依附在某個 Span 上、描述這一次 operation 的 key-value metadata。

Event Attribute：依附在某個 Event 上，用 key-value 補充那個事件的細節。

Stack trace：錯誤發生時，從外層 function 一路呼叫到出錯位置的 function 呼叫路徑。

Log correlation：讓獨立的 LogRecord 帶上 TraceId / SpanId，以便 backend 對回產生它的 Trace / Span。

快速參考：Span / Event / Attribute 決策卡。
有問題就問我：你可以貼一段真實 service flow，我們一起決定哪些 operation 值得成為 Span。 最有價值的追問通常是：「如果不記這個欄位，我會失去哪個事故假設的驗證能力？」
