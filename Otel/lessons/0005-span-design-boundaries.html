5. Span 邊界與欄位設計

不是「能埋就埋」，而是保存恰好足夠的因果證據 · Lesson 5 of N

這一課解決什麼問題？

OpenTelemetry 允許你自由建立 Span 與 attributes，但自由不等於每個 function 都應該成為 Span。 每新增一個 Span，都會增加 application 端的建立與處理成本、export 流量、Collector 負荷、 backend 儲存量，以及 SRE 判讀時的雜訊。

因此 Span 設計的第一性問題不是「API 怎麼呼叫」，而是：未來發生故障時，哪個工作邊界 需要獨立的 duration、outcome 與 causal position，才能排除假設？

官方基礎：OpenTelemetry — Spans；跨語言欄位一致性的理由：Trace Semantic Conventions

從資訊需求推導三種模型

你需要保存的證據模型原因
一段有開始、結束、duration，且值得成為因果圖節點的工作Span它有自己的 lifecycle、Span ID、status 與 parent relationship。
Span 期間內一個有意義的時間點，例如 retry、cache miss、state transitionEvent它依附於 Span，保留 timestamp，但不冒充獨立 operation。
描述整段 operation 的穩定事實，例如 item count、route、methodAttribute它是可查詢的 key-value context，不需要自己的時間區間。
最小充分證據原則：若只需知道一個值，就用 Attribute；若需知道某事何時發生， 用 Event；只有當需要獨立 duration、outcome 或 causal node 時，才新增 Span。

Span 邊界的兩個判斷軸

軸一：它有獨立的時間區間嗎？

「呼叫 payment service」有清楚開始與結束，也有可單獨診斷的 latency，因此適合成為 Span。 「cart 內有 3 件商品」沒有時間區間，只是 operation 的描述，應是 Attribute。

軸二：它是需要保留的因果節點嗎？

跨 process 的 HTTP/database call 通常值得成為節點，因為你要知道時間花在本地還是遠端。 process 內部 function 只有在其 latency、failure 或子操作對 SRE 排障具有獨立意義時，才值得成為 INTERNAL Span。否則每層 helper function 都建 Span，只會把 call stack 偽裝成有用的 trace。 

需要獨立 duration / outcome / causal node？
  ├─ 是 → Span
  └─ 否 → 發生時間有診斷意義？
           ├─ 是 → Event
           └─ 否 → Attribute（或根本不記錄）

名稱為何必須穩定？

Span name 應描述一類 operation，而不是某一次 instance。若使用 GET /users/42、GET /users/99 當名字，backend 會看到大量幾乎相同、 卻不能自然聚合的 operation。穩定名稱 GET /users/{userId} 保留「這是哪類工作」； 必要的 instance context 再放到合適的 Attribute，並先評估敏感性與 cardinality。

設計例子後果
穩定 operation nameGET /users/{userId}可依 logical operation 聚合 latency 與 errors。
動態 instance nameGET /users/42名稱基數隨使用者增加，查詢與儲存成本上升。
沒有診斷語義handle_request值穩定但無法區分 operation，聚合結果失去解釋力。

Attribute 的四道守門問題

  1. Queryability：事故時會用它建立哪個查詢或分組？答不出來，先不要記。
  2. Cardinality：唯一值或值組合會不會隨 user、request、UUID 無界成長？
  3. Sensitivity：是否含 token、email、完整 URL query、payload 或其他個資／機密？
  4. Availability：建立 Span 時是否已知道？建立時加入的 attributes 才能供 head sampler 作決策。

高 cardinality 並非一律禁止；Trace 本來就需要高基數 Trace ID。問題是你是否真的需要把某個 高基數 business value 送進 telemetry、backend 是否能承受，以及它是否造成資料外洩風險。 設計要回答用途與成本，而不是背「高基數永遠錯」。

把 Lesson 3 的 checkout 重畫一次

Span: checkout.calculate_total
  Attribute: app.cart.item_count = 3
  Attribute: app.cart.total_cents = 3674
  Event（只有真的發生時）: pricing_rule_fallback
    Attribute: app.pricing.rule = "default"

不要建立：
  Span: sum_item_1
  Span: sum_item_2
  Span: sum_item_3

逐項加總沒有獨立排障價值時，三個 child Spans 只放大資料量。若日後發現「呼叫外部 pricing engine」 是獨立 latency 與 failure boundary，再把那段遠端 call 建成 CLIENT Span；這是由證據需求推導模型， 不是由程式碼縮排推導 Span。

參考修正
  • Span name 改成穩定的 checkout.process；email、order UUID 不放在 name。
  • 若逐項 validation 沒有獨立 duration/outcome 價值，移除 child Spans，保留 item count。
  • 移除 auth.token；它是 credential，不應送入 telemetry。
  • payment retry 是有意義的時間點，Event 合理；attempt number 放 Event Attribute。
