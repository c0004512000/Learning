44. Collector Capacity Model

Scale 的前提是知道 bottleneck、state ownership 與 backlog recovery，而不只是看到 CPU 高 · Lesson 44 of N

本課成果

你會用 rate、bytes、service time、concurrency、queue 與 recovery throughput 建立 Collector capacity model； 區分 stateless、scraper、stateful components 的 scaling 方法，並判斷何時增加 Collector 反而會惡化 backend overload。

主要來源：Scaling the Collector、Gateway Deployment Pattern、Collector Internal Telemetry

第一性原理：Capacity 是完成率，不是 Replica 數

一個穩態 pipeline 的必要條件：

long-term completion_rate ≥ incoming_rate

backlog_change = incoming_rate - completion_rate

Completion 是成功 export 或明確 drop 的速率；若 exporter/backend 長期只能完成 10k items/s，前面 receivers 收 20k， 不管 queue 多大都只是在延後 overflow。Replica 數只有在能增加瓶頸處 completion rate 時才有價值。

Items/s 不足以描述負載

同樣 10k spans/s，attribute/events/links 大小、processor complexity 與 exporter compression 可能完全不同。至少量：

  • items/s 與 bytes/s：steady、P95 peak、burst duration。
  • CPU seconds/item、allocated bytes/item、encoded bytes/item。
  • export latency distribution、request rate、batch bytes、success/failure/throttle。
  • state size：pending traces、metric series、connector caches、queue items/bytes。

Capacity benchmark 必須使用接近 production 的 signal mix、cardinality、payload size 與 failure mode；只用空 attributes 的 synthetic spans 會高估容量。

Little's Law：Concurrency、Throughput 與 Latency

對穩定系統，粗略關係：

in_flight ≈ throughput × average_time_in_system

若 exporter 完成 100 requests/s、每 request 平均停留 0.5s，約需 50 in-flight requests 才能維持該 throughput。 但增加 concurrency 只在 client/connection 是 bottleneck 時有效；若 backend 已飽和，更多 workers 會增加 contention、throttle 與 retry storm。

Queue 是時間緩衝，不是 Capacity

忽略 overhead，queue 可吸收 outage 的時間近似：

buffer_window_seconds ≈ queue_capacity_items / incoming_items_per_second

若 incoming 20k/s、queue 100k items，只約 5 秒。實務還需 bytes、batch unit、signal mix 與 existing occupancy。 Queue 變大會增加 memory/disk、recovery time 與 stale telemetry，不會提高 backend steady completion rate。

Recovery 要有 Spare Capacity

Outage 累積 backlog B 後，恢復期：

net_drain_rate = completion_rate - current_incoming_rate
drain_time = B / net_drain_rate       only if net_drain_rate > 0

若恢復後 completion 恰好等於 incoming，queue 不再長但永遠排不完。Capacity target 需保留 headroom，兼顧 burst、rollout、single-replica loss 與 backlog drain。

三類 Component，三種 Scaling 問題

類型例子Scale 關鍵
Stateless data pathOTLP receive、filter、transform、batch、exportLoad balance traffic；注意 gRPC long-lived connection 分布
Scraper/ownerPrometheus scrape、host collectionTargets 必須分配，避免 duplicate scrape 或漏 scrape
StatefulTail sampling、span metrics、temporality conversion相同 key affinity/single writer；scale 改變 ownership/state continuity

Stateless tier 可增 replicas 配 load balancer；gRPC L4 long-lived connections 可能長時間黏在少數 replicas，需理解連線重建/L7 行為。 Scraper 需 target allocator/ownership。Stateful tier 需 traceID、service 或 metric-stream affinity，並評估 rebalance 時 in-flight state 分裂。

Autoscaling Signal 要接近真正 Constraint

CPU 是有用訊號但不完整：

  • CPU 高 + queue 不長 + zero refusal：可能仍健康，只是有效工作多。
  • CPU 低 + exporter queue 長：可能在等慢 backend/network。
  • Memory refusal 增加：表示 process protection 已啟動，delivery 有風險。
  • Scrape duration 接近 interval：scraper ownership capacity 不足。
  • State cache/pending traces 接近 limit：stateful capacity/affinity 問題。

好的 scaling policy 常結合 traffic rate、CPU、memory/refusal、queue utilization/oldest age 與 backend latency；並設 scale-up 快、scale-down 慢與 minimum replicas。

何時不該 Scale Collector

若 exporter queues 同時成長、backend latency/throttle/failure 先上升，瓶頸在 downstream。增加 Collectors/workers 可能只讓更多 concurrent requests 壓向已過載 backend。 此時應協調 backend capacity、降 ingestion、sampling/filter、rate limit 或延長可承受 buffer，而不是把 upstream fan-out 加倍。

因果判斷：觀察哪個 constraint 先變壞，以及 scaling 後 completion rate 是否真的上升；不要以 correlation「Collector queue 高」就假設 Collector CPU 不夠。

SRE 附加練習：Queue 70%，要不要 Scale？

  1. 先看 queue slope 與 oldest age：短 burst 後下降，還是持續線性成長？
  2. 比較 incoming/completed rate，按 exporter/backend 分拆，不用 cluster aggregate 掩蓋 hotspot。
  3. 找 earliest saturation：CPU、memory refusal、network、backend latency/throttle/failure。
  4. 分類 component：stateless 可分流、scraper 要重分 target、stateful 要 preserve affinity。
  5. 估 scale 後 completion 是否提高；若 backend capped，先保護 downstream。
  6. 算 backlog drain time，設定 recovery SLO 與 scale-down guard。

本課總結

  • Capacity 核心是 completion rate、state/queue resource 與 latency，不是 replica count。
  • Queue 只能吸收有限時間；recovery 需要 completion 大於 incoming 的 spare capacity。
  • Stateless、scraper、stateful components 分別需要 load balance、target ownership、key affinity。
  • Scale 前先找瓶頸；downstream 飽和時增加 Collector 可能只放大壓力。
