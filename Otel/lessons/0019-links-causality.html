19. Links 與非樹狀因果關係

Parent 建立主樹，Links 保存額外因果邊 · Lesson 19 of N

本課成果

你會理解 parent/child 為何只能表達單一主階層，何時應使用 Link 關聯同一或不同 Trace 的 Span，並能為 batch、queue、fan-in 選擇不扭曲 causality 的模型。Links 不是 messaging 專用功能，而是一般性的因果關聯資料。

主要來源：OpenTelemetry Traces — Span Links、Tracing API — Specifying links

第一性原理：樹只有一個 parent，真實因果可以有很多來源

一個 Span 有零或一個 parent，因此 parent IDs 自然形成 tree。這非常適合同步 nested calls 與單一路徑 continuation： 

HTTP SERVER span
  ├─ checkout.validate
  └─ payment CLIENT span

但假設 worker 等到三則獨立 messages 後才做一個 batch：

message A ─┐
message B ─┼─causes─→ batch.process
message C ─┘

若任選 A 當 parent，B/C 的因果被抹去；若為每則 message 建一個相同 batch Span，又會虛構三次工作。 Links 允許一個 Span 關聯一個或多個其他 SpanContexts，表示 causal association，而不改寫主 parentage。

典型問題這個 operation 的主要上游是誰？還有哪些 operations 對它有因果貢獻？

Link 不是弱版 parent，也不是任意搜尋 tag。它攜帶 linked SpanContext，至少包含 trace/span identity；Link 自己也可帶 attributes 描述關聯，例如 input position。Correlation ID 可協助查詢，但沒有 SpanContext 的標準 causal semantics。

同一 Trace 還是新 Trace？先決定 operation lifetime

Async 不自動等於 Link。若一則 message 明確延續原 operation，consumer 可以 extract producer context 作 parent，讓工作留在同一 Trace。 若工作長時間解耦、獨立排程，或一個 operation 合併多個來源，常可開始新 Trace，再 Links 回來源。

決策順序：先問「這是同一 operation 的 continuation，還是新的 operation 但由舊工作引起？」； 再問「是否只有一個主要 causal parent？」。不要先看 backend UI 長相再反推資料模型。

為什麼最好在 Span creation 時提供 Links？

OTel API 允許在 Span 建立時記錄 Links，且 sampler 可把這些 Links 納入 sampling decision。 後來才追加的 Link 可能已錯過 sampling 時點，因為 head sampling 在 Span creation 時已決定。 

input_links = [Link(context_a), Link(context_b)]

tracer.start_as_current_span(
    "batch.process",
    links=input_links,
)

這與「重要 sampling attributes 應在 creation 提供」是同一原理：sampling decision 只能看到當下已知的 inputs。 先收集必要 causal contexts，再建立 batch Span，通常比建立後補 Link 更能保留決策資訊。

閱讀 Python fan-in 範例

範例位於 examples/0019-span-links.py：

with tracer.start_as_current_span("message.receive") as first_input:
    first_context = first_input.get_span_context()

with tracer.start_as_current_span("message.receive") as second_input:
    second_context = second_input.get_span_context()

兩個 blocks 依序完成，離開後 current context 回復，因此它們是不同 root Spans，擁有不同 Trace IDs。 SpanContext 在 Span 結束後仍可用來建立 Link；Link 表達的是 identity/causality，不要求 linked operation 仍在執行。 

input_links = [
    Link(first_context, attributes={"app.input.position": 0}),
    Link(second_context, attributes={"app.input.position": 1}),
]

with tracer.start_as_current_span("batch.process", links=input_links):
    ...

此時沒有 current parent，所以 batch.process 是新 Trace 的 root；它的兩個 Links 指回來源 traces。 若 backend 只畫 parent tree，Links 可能需要在 Span detail 中查看，視覺上沒有連線不等於 telemetry 沒有 Link。

Links 也受有限資源約束

Lesson 18 的 Link count 與 per-Link attribute limits 在此具體化。若 batch 含十萬 inputs，不應假設單一 Span 能無限保留十萬 Links； SDK 可能丟棄超限 links 並提供 dropped_links_count。要設計 representative linking、batch metadata 與成本政策， 而不是把 queue payload 全部複製進 telemetry。

SRE debugging lab：Trace 為何「斷掉」？

Case A：Async worker 是新 Trace，但其實有 Link

先看 Span detail 的 links，而非只看 parent tree。比較 linked trace/span IDs，回查 producer Trace。 若 backend UI 不顯示 Links，使用 raw OTLP/debug output 驗證資料層，再把 UI capability 與 instrumentation correctness 分開。

Case B：只有部分 batch inputs 可追溯

檢查 input contexts 是否都有效、Links 是否在 Span creation 傳入、link count/dropped count 是否超限，以及 producer traces 是否被 sampling 保留。 Link 可以指向未被 backend 保存的 Trace；consumer Link 存在不保證 linked Span 可查詢。

Case C：把 message ID 當成 Link

Message ID attribute 可用於搜尋，但不等於 OTel Link。若要標準 causal edge，必須傳遞／保存來源 SpanContext 並建立 Link； 同時仍可保留 message ID 作 domain debugging，但要控制敏感性與 cardinality 成本。

練習：四種 topology 選擇
  1. HTTP handler 同步呼叫 DB：parent/child。
  2. Producer 發一則 message，consumer 是同一工作延續：propagated context 作 parent。
  3. 100 messages 聚合成一個 batch：新 Span + multiple bounded Links。
  4. 一個 request 觸發隔天報表：依 operation boundary 建新 Trace，Link 回來源。
