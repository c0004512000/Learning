4. 用五個問題讀懂一個 Span

先讀證據的語義，再讀 exporter 顯示的欄位 · Lesson 4 of N

為什麼不能從 JSON key 開始背？

Lesson 3 的 ConsoleSpanExporter 印出一段像 JSON 的文字。它很適合讓人看見資料， 但那只是 exporter 的顯示方式。如果把顯示格式當成 OTel 本身，你會在換 SDK、 exporter 或 backend 後，因欄位名稱與巢狀位置不同而誤判資料消失。

第一性原理是：Span 必須保存足以回答 operation 因果與診斷問題的資訊；SDK、exporter 與 protocol 再把這份語義投影成不同表示。官方文件也特別提醒，概念頁的 JSON 範例不代表特定格式， 尤其不是 OTLP/JSON。

依據：OpenTelemetry 官方文件 — Traces

先拆清楚四個層次

層次解決的問題不保證什麼
Span data model定義一個 operation 需要哪些語義：identity、時間、attributes、events、status 等。不規定 terminal 要印成哪種 JSON 排版。
Semantic Conventions定義常見領域的 canonical 名稱與語義，例如 HTTP attributes。不是 transport，也不負責傳送資料。
Exporter display把 SDK 中的資料轉成人可見輸出，方便本機觀察。不是跨系統相容的 wire contract。
OTLP定義 telemetry 在來源、Collector、backend 之間的 encoding、transport 與 delivery。不是 Span 在 UI 中必須長怎樣。
一條不會混淆的因果鏈： instrumentation 建立符合資料模型語義的 Span → Semantic Conventions 讓常見欄位有一致名稱 → Exporter 選擇顯示或傳送方式 → 若使用 OTLP，資料依 OTLP 的 Protobuf schema 與 gRPC/HTTP transport 傳輸。

OTLP 的責任邊界依據：OpenTelemetry Protocol specification

判讀框架：固定問五個問題

以下輸出經過簡化，值只是範例；重點是把欄位還原成診斷問題。

{
  "name": "checkout.calculate_total",
  "context": {
    "trace_id": "0x7a...91",
    "span_id": "0x2b...e4",
    "trace_state": "[]"
  },
  "kind": "SpanKind.INTERNAL",
  "parent_id": null,
  "start_time": "2026-08-20T02:00:00.100Z",
  "end_time":   "2026-08-20T02:00:00.103Z",
  "status": { "status_code": "UNSET" },
  "attributes": {
    "app.cart.item_count": 3,
    "app.cart.total_cents": 3674
  },
  "events": [],
  "resource": {
    "attributes": { "service.name": "checkout-demo" }
  }
}

1. 它屬於哪條因果鏈？

先看 trace_id、span_id、parent_id。Trace ID 把多個 Span 關聯成同一條端到端工作；Span ID 識別目前節點；Parent Span ID 指向直接上游節點。 此例 parent_id: null，因此它是 root Span。這一步回答的是關聯與拓撲，不是結果成功與否。

2. 它觀測哪一段工作？

看 name 與 kind。name 應描述穩定、可理解的 operation；kind 描述這段工作 與 process boundary 的角色。此例是 INTERNAL，表示它不是 incoming server call、 outgoing client call 或 queue producer/consumer boundary，而是 process 內部工作。

3. 它花多久，結果如何？

duration 是 end_time - start_time，此例約 3 ms。status 回答 operation 的 整體結果判定；UNSET 是預設狀態，不能讀成「未知所以失敗」。若 operation 發生錯誤， instrumentation 應依該領域的 Semantic Conventions 設定 status。

4. 有哪些診斷脈絡？

attributes 是描述整段 operation 的 key-value metadata。若某件事是 Span 期間內 「有意義的單一時間點」，才適合用帶 timestamp 的 event。判斷規則不是「資料多就用 event」， 而是那個發生時刻是否具有診斷意義。

5. 誰產生這份 telemetry？

看 Resource 與 instrumentation scope。service.name=checkout-demo 描述 emitter identity； instrumentation scope 則描述是哪一段 library/module instrumentation 建立 Span。它們回答「誰產生」， 不應和 name 的「這次做什麼」混在一起。

重要精度：Console exporter 可能把 Resource、scope 與 Span 一起印在一個物件中； 這不代表 Resource 在所有協定表示中都必須是 Span 內的一個 JSON 欄位。OTLP 會用 ResourceSpans / ScopeSpans 等 envelope 組織資料。請保留語義關係，不要依賴畫面巢狀位置。

SRE debugging 練習：哪一層出了問題？
