21. Metrics 的第一性原理與 Traces 分工

用聚合換取規模與趨勢，用 Trace 保留個別因果 · Lesson 21 of N

本課成果

你會理解 measurement、instrument、attributes、aggregation、metric stream 的關係，能從可做的數學選擇 Counter、UpDownCounter、 Histogram、Gauge 或 asynchronous instrument，並知道何時 Metric 告訴你「有問題」、Trace 告訴你「哪個 operation 怎麼壞」。

主要來源：OpenTelemetry — Metrics、Python Metrics instrumentation

第一性原理：大量 observations 不可能都用個別事件回答

假設 checkout 每秒有 10,000 requests。SRE 想知道最近五分鐘的 request rate、failure ratio、p95 latency 與 active requests。 逐筆 Trace 保留豐富因果，但掃描每個 request 才算全域健康，成本高、易受 sampling 影響。Metric 在來源端先聚合 measurements： 

大量 measurement events
  + instrument semantics
  + bounded attribute dimensions
  + time window / temporality
  → sums, counts, buckets, current values
  → alerts, dashboards, scaling decisions

聚合犧牲個別 request identity 與完整因果，換取固定且較低的狀態成本。這不是低解析度 Trace；它是另一種資料模型。

Trace 與 Metric 的資訊交換

問題Metric 擅長Trace 擅長
現在是否異常？rate、ratio、distribution、saturation 趨勢不是全量聚合的首選
哪一條 request 路徑慢？只能指出哪個群組/時間窗異常Span topology、timing、attributes、events
能否做可靠 alert？適合以完整聚合 stream 告警sampling 可能讓個別計數不代表總體
根因在哪個 dependency？可縮小 service/operation 範圍呈現個別 causal path 與錯誤細節

典型工作流是 Metric 偵測與界定影響，Trace 深入 exemplars/代表性 operations。兩者互補；把 user ID 放入 Metrics 企圖還原每筆 request，會摧毀聚合成本模型。

Metric pipeline 的角色對照

MeterProvider（process-level configuration owner）
  ├─ Resource：誰產生 metrics
  ├─ MetricReader：何時 collect、以何種 temporality 讀取
  └─ Exporter：資料送去哪裡

Meter（Instrumentation Scope）
  └─ Instruments
       └─ measurements(value + attributes)

它與 Tracing 的 Provider/Tracer/Exporter 有家族相似性，但 MetricReader 是關鍵差異：aggregation state 要在 collection 時轉成 Metric data，再由 exporter 輸出。不要把 SpanProcessor API 原封不動套到 Metrics。

Instrument 不是資料型別，而是數學承諾

Counter：只增加的累積量

記錄 completed requests、bytes sent 等非負增量。Counter 的 monotonicity 讓 consumer 可安全計算 rate/delta； 用負值「修正」會破壞其語意。若值可上下變化，選別的 instrument。

UpDownCounter：可增加也可減少的累積狀態

適合 in-flight requests：開始 +1、結束 -1。它記錄變化，不是每次重設 absolute value。 Lifecycle 若漏掉 finally decrement，狀態會漂移，這是 instrumentation correctness 問題。

Histogram：保留 value distribution 的聚合資訊

每個 request 記錄 duration，SDK 將 values 聚合成 count、sum、buckets 等。平均值無法區分「全部約 100ms」與 「多數 10ms、少數 10s」；Histogram 讓你問 threshold counts、quantiles/尾延遲（精度依 aggregation/backend）。

Gauge：某時點的目前值

Gauge 表達 current measurement，不具 Counter 的 monotonic sum 語意。Synchronous Gauge 在 code path 直接 record； Asynchronous Gauge 在 collection 時 callback 觀測目前值。若你只在 scrape/collection 時才知道外部 queue size，async instrument 更自然。

Synchronous 與 asynchronous：何時知道 measurement？

模式觸發者適用資料風險
SynchronousBusiness code 發生事件時呼叫request completed、duration、active +/-hot path 成本與 attribute cardinality
AsynchronousSDK collection 時呼叫 callback只能查詢目前 aggregated state 的 runtime/external sourcecallback 慢、逾時、I/O 阻塞 collection

選擇依「資訊何時可取得」，而非喜歡 push 或 pull。若每個 request completion 已知 duration，就直接 Histogram record； 不必在 collection callback 重新掃 application state。

Attributes 會定義聚合分組

每組不同 measurement attributes 會形成不同 aggregation state：

app.checkout.requests{result="success"}
app.checkout.requests{result="failure"}

兩個 result values 產生兩個可分組 series，能計算 failure ratio。若改用 request ID，每個 request 都產生新 combination， aggregation state 逼近 request volume，失去 Metrics 的成本優勢。Resource/Scope identity 仍與 Lesson 15/16 相同， 不要為逃避 cardinality 把 request dimensions 誤放 Resource。

現行 SDK 保護：OTel Metrics SDK 對每個 metric stream 的 unique measurement attribute combinations 設 cardinality limit；超限 measurements 會進入帶 otel.metric.overflow=true 的 overflow point，以保留總值但失去原維度。 下一課會完整推導這個成本模型。

閱讀第一個 Python Metrics 範例

範例位於 examples/0021-first-metrics.py：

reader = PeriodicExportingMetricReader(ConsoleMetricExporter())
provider = MeterProvider(
    resource=Resource.create({"service.name": "checkout"}),
    metric_readers=[reader],
)
meter = metrics.get_meter("acme.checkout.application", "0.5.0")

Resource 識別 checkout service；Meter name/version 是產生 metrics 的 Instrumentation Scope；Reader/Exporter 建立 collection/output path。 範例只寫 console，不聯網，也沒有由我執行。 

active_requests.add(1)
try:
    duration.record(duration_ms, {"app.checkout.result": result})
    request_counter.add(1, {"app.checkout.result": result})
finally:
    active_requests.add(-1)

同一次 operation 產生三種不同數學語意：active 是可逆狀態、request completion 是 monotonic count、duration 是 distribution sample。 不是「三個數字都能畫折線」就該用同一 instrument。

SRE debugging lab：數字看起來合理，模型可能已錯

Case A：Active requests 長期只升不降

檢查所有 exit paths 是否對稱 decrement，尤其 exception/cancellation。若 metric instrumentation 沒用 finally， 它測到的是「累積 start 減少數 completion」的程式 bug，不是實際 active workload。

Case B：平均 latency 穩定，使用者仍抱怨

平均值可能掩蓋 tail。檢查 Histogram distribution/buckets/quantiles，按低基數 route/result 分組，再用對應時間窗的 Trace 找慢 requests。不要把每個 trace ID 放進 metric attributes。

Case C：Console 沒有立即印 metric

MetricReader 依 collection/export 週期輸出，不是每次 add 都同步 print。檢查 reader 是否註冊、process 是否活到 collection、 shutdown/force flush 是否執行，再查 exporter。這與 Span SimpleProcessor 的即時輸出模型不同。

練習：為 RED + saturation 選 instruments
  • Request rate：Counter 的 rate。
  • Error ratio：按 bounded result/status class 分組的 Counter ratio。
  • Duration：Histogram。
  • In-flight saturation：UpDownCounter；若只能定期讀 absolute current state，考慮 Observable instrument。
