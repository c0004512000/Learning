12. 讀懂最小 Collector YAML

把文字設定還原成 active telemetry graph · Lesson 12 of N

本課成果

你會把一份 Collector YAML 轉成可驗證的資料流，而不是只看 indentation 猜意思。這一課先建立讀圖能力； 不啟動 Collector、不安裝 binary，也不加入 backend、TLS、Kubernetes 或 production tuning。

主要來源：OpenTelemetry Collector — Configuration

最小設定

檔案位於 examples/0012-collector-minimal.yaml：

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 127.0.0.1:4317
      http:
        endpoint: 127.0.0.1:4318

processors:
  batch:

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]

先只讀 declarations

IdentifierTypeInstance name設定意圖
otlpotlp receiverdefault在 localhost 接受 OTLP/gRPC 4317 與 OTLP/HTTP 4318。
batchbatch processordefault將 telemetry 組批再交給下一站。
debugdebug exporterdefault把收到的 telemetry 印到 Collector logging output。

Component identifier 格式是 type[/name]。只有一個 instance 時可只寫 type；若要兩個 OTLP exporters， 可用 otlp/backend_a 與 otlp/backend_b。斜線後名稱只是 instance identity， 不會創造新的 component type。

再讀 activation graph

service.pipelines.traces
  receivers:  [otlp]
  processors: [batch]
  exporters:  [debug]

還原成：
OTLP receiver → batch processor → debug exporter

這是一條 traces-only pipeline。OTLP receiver 雖能接收多種信號，但 config 沒有 metrics / logs pipelines， 所以本例只為 Traces 建立 active path。

三個 endpoint 含義不要混

位置方向角色
127.0.0.1:4317application → CollectorReceiver 的 OTLP/gRPC listening endpoint。
127.0.0.1:4318application → CollectorReceiver 的 OTLP/HTTP listening endpoint。
本例沒有 backend endpointCollector → backend因為 debug exporter 寫 logging output，不送 network。
安全起點：本機 lab 綁定 127.0.0.1，只接受同一台主機連線。 改成 0.0.0.0 會擴大 network exposure；只有在容器／遠端 client 確實需要且已設計 firewall、 authentication 與 TLS 時才應這樣做。

為何先用 debug exporter？

它建立最短 feedback loop：只要 application 能送到 receiver、config 已啟用 traces pipeline、batch 能 forward， 你就能在 Collector output 看見 Span。此時尚未引入 backend credentials、DNS、TLS 或 vendor query UI， 所以失敗假設更少。

但 debug exporter 不是 production backend：它不提供長期保存、Trace query、service map 或 retention。 它是 pipeline probe，不是最終 observability solution。

固定的 config 閱讀演算法

  1. Inventory：列出頂層 receivers / processors / exporters 的 identifiers。
  2. Activation：逐一讀 service.pipelines，標出 signal type。
  3. Resolution：每個引用是否有對應 declaration？該 component 是否支援此 signal？
  4. Order：依 receivers → processors list order → exporters 畫箭頭。
  5. Boundaries：標出 listening endpoints、outbound destinations、TLS/auth 與 exposure。
  6. Evidence：為每一站決定可觀察的成功／失敗訊號。

SRE debugging lab：三份看似合理的錯誤 config

Case A：定義了，沒有啟用

exporters:
  debug:

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: []

判讀：debug component 存在，但沒有 active edge 連到它；不會收到 pipeline data。

Case B：引用不存在的 instance

exporters:
  debug:

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug/detailed]

判讀：debug/detailed 是另一個 identifier，不會自動繼承 debug declaration。

Case C：以為 OTLP receiver 自動啟用三種信號

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]

判讀：只有 traces active；metrics / logs 需要各自 pipeline。

修正的共同原則

不要靠 component 的存在推論資料流。以 service.pipelines 為根，解析每個 identifier， 確認 signal-compatible declarations，再依 list order 畫出 active graph。

還沒執行前，也能做哪些驗證？

  • YAML key 層級與 list 形狀是否正確。
  • 所有 pipeline references 是否有 declaration。
  • 本機 lab endpoints 是否只綁 localhost。
  • traces path 是否至少有 receiver 與 exporter。
  • production secrets 是否被硬編碼進 config（本例完全沒有）。

真正啟動前還應使用該 Collector distribution 自帶的 validate command，因為不同 distribution 包含的 components 可能不同。這一步留到容器化 lab；依你的 execution policy，優先使用 Docker image， 不下載或執行新的 Windows Collector executable。
