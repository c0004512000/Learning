37. OTTL 第一性原理

把每條語句視為：在特定 telemetry context 中，符合條件才執行的一次 mutation · Lesson 37 of N

本課成果

你會從 OTel 巢狀資料模型推導 OTTL 的 context、path、editor/converter、condition、statement order 與 error mode； 能在不執行設定的情況下追蹤 mutation，並知道 production rollout 前要證明哪些 invariants。

主要來源：OTTL、OTTL Language、Transform Processor

第一性原理：Telemetry 不是扁平 key-value

一個 span 所處的資料大致有多層 ownership：

Resource attributes        service/process/host identity
  └─ Scope attributes     instrumentation library identity
      └─ Span             operation fields + span attributes
          └─ Span Event   event fields + event attributes

Metrics 也有 resource → scope → metric → datapoint；logs 則有 resource → scope → log record。 相同字串 key 若位於不同層，就有不同生命週期與語意。修改 resource.attributes["service.name"] 與修改 span.attributes["service.name"] 不是同一件事。

OTTL（OpenTelemetry Transformation Language）是一個 telemetry-specific DSL，不是通用程式語言。其核心模型可簡化為：

statement = editor(target, value...) [where boolean_expression]

for each item in the chosen context:
  if condition is absent or true:
    mutate the item

Context 決定「現在的一筆」與可見 Paths

Context 不只控制可讀欄位，也控制 statement 被執行的粒度。Span context 通常對每個 span 評估；datapoint context 對每個 datapoint； resource context 則位於更高層。Transform processor 允許的常見 path prefixes 為：

Statement group可用的主要 contexts例子
trace_statementsresource、scope、span、spaneventspan.name
metric_statementsresource、scope、metric、datapointdatapoint.attributes["region"]
log_statementsresource、scope、loglog.body

因此把 span.attributes 放進 log_statements 不是「找不到 key」而已，而是 context/path 不相容。 有些 components 會 inference context；複雜規則仍應先明確寫下希望的 evaluation unit。

Path：指向欄位，不是隨意的字串

resource.attributes["service.name"]
span.name
span.attributes["http.request.method"]
log.body
datapoint.attributes["host.name"]

點號通常分隔結構欄位；方括號用 key/index 存取 map/slice。Map key 不存在時通常得到 nil， 所以可用 where ... == nil 做 defaulting。但 nil、string、int、map 不是同一型別；function 對錯型別可能回 error。

Editor 改資料，Converter 算出值

一條 OTTL statement 有一個主要 editor invocation；converter 可嵌在 argument 中提供值：

set(
  span.attributes["http.request.method"],
  ConvertCase(span.attributes["http.request.method"], "upper")
) where span.attributes["http.request.method"] != nil

set 是 editor：改變 target。ConvertCase 是 converter：讀 input、回傳新值。 可用 functions 由使用 OTTL 的 component 提供；看見網路上的 OTTL function 範例，不代表你的 component/distribution/version 一定支援。

Condition：控制 mutation domain

where 應被理解為 predicate，不是註解：

set(resource.attributes["deployment.environment.name"], "unknown")
where resource.attributes["deployment.environment.name"] == nil

這條語句保存既有值，只填 missing。若移除 condition，所有 environments 都被改成 unknown，破壞 identity。 Boolean expressions 支援 not、and、or 與括號；其中 not 優先於 and，and 優先於 or。 Production 規則應用括號表達意圖，不依賴讀者記 precedence。

Statement Order：每一步都讀前一步的結果

範例 examples/0037-ottl-transform.yaml 先 copy 再 delete：

before: user.tier = "gold", app.user_tier missing
1 copy: app.user_tier = "gold"
2 delete: user.tier missing
after:  app.user_tier = "gold"

若順序反轉，第二步再讀 user.tier 只會得到 nil，rename 失敗。 所以多條 statements 是 state transition sequence；review 時要逐步更新 state，不可把每條當成同時執行。

Error Mode 是資料可靠性政策

Mode遇到 statement error主要 trade-off
ignore記錄 error，繼續後續 statement可用性高，但可能輸出部分轉換資料
silent不記 error，繼續噪音低，但規則失效可能長期不可見
propagate把 error 回傳 pipelinefail closed；可能造成整個 payload dropped

Transform processor 目前 top-level 預設為 ignore，但不要依賴未寫出的 default；明確選擇並寫出理由。 像 normalization 常偏向 ignore + observable errors；法規要求的 secret removal 可能偏向 propagate/fail closed，避免未清洗資料外送。 沒有單一 mode 永遠正確，決策取決於「錯時寧願 loss 還是寧願不完整 mutation」。

Transform、Filter、Routing 的意圖不同

  • Transform：保留 telemetry item，但修改/新增/刪除欄位。
  • Filter：predicate 命中時丟棄 item；其條件語意常是 OR，必須讀 component 文件。
  • Routing：predicate 決定 item 前往哪條 pipeline；不等於 field mutation。

三者都可使用 OTTL，不代表語意相同。OTTL 提供 expression language；component 定義「expression 結果拿來做什麼」。

SRE 附加練習：規則上線後 Service 消失

假設 backend 中某些 services 不再出現，Collector 仍 running。用因果順序查：

  1. 取得 rollout 前後 exact statements、component/version、error mode 與 pipeline order。
  2. 選一筆可重現 input，寫出 resource/scope/span 的初始 state。
  3. 逐 statement 評估 context、condition、input type 與 mutation 後 state。
  4. 確認是否誤改/刪 service.name、是否產生空值或高 cardinality identity。
  5. 檢查 OTTL errors 與 processor accepted/dropped evidence；短時間 debug logging 可能顯示 initial/after TransformContext，但非常 verbose 且可能含敏感資料。
  6. 先 canary 修復，用 invariant 驗證「每筆 resource 都有合法 service.name」，再逐步 rollout。
OTTL debug context 可能包含完整 telemetry attributes/body。只在受控環境短時間啟用，限制存取與 retention，並先考慮資料敏感性。

Review 時可使用 OTTL Review Card。

動手推理（不執行）

  1. 對範例的四條 trace statements，手算 input：user.tier=gold、method=get、environment missing 的 final state。
  2. 把 copy/delete 順序反轉，再手算一次；說明哪個 invariant 被破壞。
  3. 令 method 是整數 7，推理 converter error 在 ignore 與 propagate 下對 payload 的差異。
  4. 為 sanitize processor 寫三列 truth table：token present、email restricted、兩者都 missing。

本課總結

  • OTTL statement 是特定 context 中、可帶 condition 的 mutation。
  • Context、path 與型別共同決定一條語句能否正確讀寫資料。
  • Statements 依序改變 state；error mode 決定錯誤時的 loss/partial-transform policy。
  • OTTL 是 expression DSL；transform、filter、routing 各自賦予結果不同操作語意。
