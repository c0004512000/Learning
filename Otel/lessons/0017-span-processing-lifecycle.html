17. Span Processor、批次與關閉生命週期

Span 結束只是資料交接的起點，不是遠端保存的終點 · Lesson 17 of N

本課成果

你會從 latency isolation 與有限資源推導 Span Processor 的角色，分辨 Simple/Batch processor，並精確說明 end、enqueue、export、force_flush、shutdown 各自保證到哪裡。

主要來源：OpenTelemetry Trace SDK — Span processor

第一性原理：request latency 與 telemetry I/O 不該被迫同步

Span 在 application thread 上建立與結束，但 OTLP export 涉及 serialization、network、timeout 與遠端負載。 若每個 request 都等一次 network export，observability path 會直接增加業務 latency，甚至在 Collector 故障時放大事故。 

業務工作完成
  → Span.end()
  → Processor 決定如何交接
  → Exporter 編碼並傳輸

Processor 是 lifecycle/cadence boundary
Exporter 是 protocol/destination boundary

Span Processor 提供 Span start/end hooks，內建 processors 負責把完成的 Span 轉成可 export 表示、批次化並交給 exporter。 只有 recording Spans 才會觸發 processor；這也把 Lesson 9 的 sampling 決策連到輸出成本。

Span.end() 到底完成了什麼？

End 設定結束時間，使 Span 成為已完成、不可再修改的 observation，並同步觸發 processor 的 end callback。 但它不等於：

  • bytes 已經離開 application process；
  • Collector receiver 已接受；
  • Collector exporter 已送往 backend；
  • backend 已完成 durable storage/indexing。

這些是串接但不同的狀態轉移。Debug 時若只看到 Span 已 end，就把結論推到 backend，會跨越多個尚未驗證的邊界。

Simple 與 Batch：差異不是名稱，而是等待發生在哪裡

面向SimpleSpanProcessorBatchSpanProcessor
交付時機Span 完成時立即交給 exporter先放 bounded queue，再依批次條件 export
request path 影響Exporter latency 更直接落在 end path通常只承擔 enqueue，network 在背景工作
失敗壓力慢 exporter 直接拖慢呼叫者慢 exporter 使 queue 成長，滿後 drop
典型用途開發、測試、最短可見 feedback一般 production export

Batch 不是「免費的非同步」。它只是把等待從 request path 移到有限 queue 與 background exporter。 只要長期 Span arrival rate 大於 export drain rate，任何有限 queue 最終都會滿： 

queue growth rate ≈ span arrival rate − successful drain rate

若 arrival > drain 持續成立：
time-to-full ≈ remaining queue capacity / (arrival − drain)

增加 queue size 只能延後滿載，也會增加記憶體與最壞等待時間；它不能修復長期 throughput deficit。

Batch processor 的四個控制旋鈕

參數控制的資源／時間錯誤直覺
max_queue_sizepending spans 上限越大就永不 drop
schedule_delay_millis定時觸發 export 的延遲它是 Span duration
max_export_batch_size單次 export 最大批量可以大於 queue
export_timeout_millis單次 export 的時間界線等於 backend retention

Batch 會在 timer、batch size threshold 或 ForceFlush 等條件觸發 export。參數要一起考慮：batch 太小增加 calls， 太大可能增加等待與 payload；queue 太小吸收不了 burst，太大則掩蓋持續壅塞並消耗更多 memory。

ForceFlush 與 Shutdown 的責任不同

force_flush(timeout)

要求 processors 儘快處理呼叫前已接手但尚未 export 的 Spans，並在 timeout 內回報成功、失敗或逾時。 它不關閉 Provider，適合 FaaS invocation 結束、測試 checkpoint 等少數需要明確同步點的場景；不應每個 request 都呼叫， 否則會消解 batching 的目的。

shutdown()

用於 SDK/process lifecycle 結束：包含 flush 效果並釋放 processors/exporters 資源，而且每個 Provider 應只呼叫一次。 Shutdown 後不應繼續正常建立 telemetry；長時間 service 應接到 graceful termination，而不是 request handler。

保證邊界：即使 SDK flush 回報成功，也只能依實作／協定證明 SDK pending work 已完成到指定界線； 不能跳過 Collector 與 backend 的 acknowledgment、storage、indexing 語意，宣稱 Trace 已可查詢。

閱讀 Python lifecycle 範例

範例位於 examples/0017-processor-lifecycle.py：

processor = BatchSpanProcessor(
    exporter,
    max_queue_size=256,
    schedule_delay_millis=1_000,
    max_export_batch_size=64,
    export_timeout_millis=5_000,
)

這些值是為了讓關係可見，不是 production tuning recommendation。Production 要從峰值 Span rate、允許 memory、出口 throughput、 network latency、可接受 loss 與 shutdown budget 量測推導。 

flush_completed = provider.force_flush(timeout_millis=3_000)
provider.shutdown()

第一行是仍保持 SDK 可用的 checkpoint；第二行是終止 lifecycle。範例印出 flush result，是為了提醒「呼叫了」與「在期限內完成」不是同義詞。

SRE debugging lab：程式正常，Trace 為何還會不見？

Case A：短命 process 沒有 graceful shutdown

Span 已 enqueue，但 process 在 background export 前退出。先重現並加入明確 flush/shutdown evidence；若改善，才支持 lifecycle hypothesis。 不要因此把所有 loss 都歸咎於 shutdown。

Case B：高峰期才遺失

比較 span arrival、queue usage/drop、自身 exporter errors 與 successful drain rate。若 arrival 長期高於 drain， 調大 queue 只延後問題；應檢查 sampling、export throughput、Collector capacity 與 downstream latency。

Case C：Exporter 持續 timeout

Processor 的 queue 會吸收短 burst，不能治療永久 unreachable endpoint。沿著 application exporter → network → Collector receiver 檢查 timeout/retry evidence；預設 Span Processor 不負責替 exporter 實作 network retry policy。

練習：為每個觀察寫出「最多能證明什麼」
  • span.is_recording() == True
  • Span.end() 已返回
  • force_flush() 回傳成功
  • Collector debug exporter 印出 Span
  • Backend query 找到 Trace

答案應形成逐層更強的證據，不可把前一層寫成後一層的保證。
