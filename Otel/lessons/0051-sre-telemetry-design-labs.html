51. SRE Telemetry Design Labs

把 Lesson 5 的 Span / Event / Attribute 判斷，練成 production debugging 能力

這不是新的主課順序。 這是一篇從 Lesson 5 分支出來的深度練習。 如果你只是沿主課往下學，Lesson 5 的下一課仍是 Lesson 6。

這篇要練的不是名詞，是一個 SRE 思考迴圈

看到 production 症狀
    ↓
先問：我現在缺哪一種證據？
    ↓
再看：現有 telemetry 能不能回答？
    ↓
不能 → 缺 Span / Event / Attribute，還是詳細 Log？
能   → 有沒有過度埋點、敏感資料或高成本欄位？
    ↓
最後才改 instrumentation

每一題都先自己停一下，再展開答案。重點不是猜中，而是練習把「事故問題」轉成「需要的 telemetry 證據」。

主要依據：OpenTelemetry Trace API、 OpenTelemetry Logging。

Lab 1：DB 很快，但 request 還是慢 2 秒

你接到告警：

POST /invoice   p95: 2.3s

Trace:
POST /invoice              2.28s
└─ SELECT invoice_items      41ms

Application code 大致是：

def create_invoice():
    items = load_items()
    pdf = render_pdf(items)
    return pdf

先判斷：你現在知道 2.2 秒到底去哪裡了嗎？render_pdf() 值不值得新增 Child Span？

展開 SRE 判讀

現有 Trace 已經排除「DB 是主要瓶頸」，但剩下約 2.2 秒仍被包在 parent Span 裡。這時 render_pdf() 是一個很合理的 Child Span 候選，因為 SRE 真的需要獨立回答：它花多久？成功還是失敗？慢 request 是否都卡在它？ 

POST /invoice                 2.28s
├─ SELECT invoice_items         41ms
└─ invoice.render_pdf         2.20s

Python 概念上：

with tracer.start_as_current_span("invoice.render_pdf") as span:
    span.set_attribute("document.template", template_name)
    pdf = render_pdf(items)

document.template 是否值得加，要再問：「某一種 template 是否可能特別慢？」如果會，這個 Attribute 有實際比較價值。 不需要因此把 load_font()、draw_line()、append_page() 每個 helper 都拆成 Span。

這一題的核心：process 內部 function 也可以值得 Span；boundary 不一定要跨 network。關鍵是它是否形成你需要獨立定位的 latency / outcome boundary。

Lab 2：「invalid coupon」算 failure，要不要 Error Log + Child Span？

業務規則允許使用者輸入過期 coupon。15% 的 checkout 會得到：

validate_coupon() → INVALID
execution time    → 0.2ms
checkout          → 繼續執行，回傳「優惠碼無效」

先判斷：既然結果是「失敗」，是不是應該建立 validate_coupon Child Span 並打一筆 ERROR log？

展開 SRE 判讀

不應該只因為回傳 INVALID 就把它當 observability failure。

這是預期中的 business outcome，不代表 system malfunction。如果這段 validation 固定極快、沒有獨立 latency 問題， 新增 Child Span 通常只會增加 trace noise。

若營運上真的需要比較 coupon outcome，可以在已有的 checkout Span 留一個穩定 Attribute：

app.coupon.result = "invalid"

ERROR log 也未必合理，因為大量「正常被拒絕」會污染 error signal。若程式出現 unexpected exception、rule engine crash、資料格式損壞， 那才是另一種真正需要 operational diagnostic 的 failure。

這一題的核心：failure 不是看到 false / invalid / rejected 就成立；先區分「正常 business result」與「系統 operation 沒有按預期完成」。

Lab 3：Payment timeout — Span、Log，還是兩個都要？

你看到：

Trace:
POST /checkout                2.42s
├─ checkout.calculate_total      7ms
└─ payment.authorize           2.10s  ERROR

Log:
ERROR payment timeout provider=a timeout_ms=2000
trace_id=4bf92... span_id=00f067...

先判斷：既然 Log 已經寫「payment timeout」，Span 還提供了什麼 Log 沒有自然提供的東西？反過來，Log 又補了什麼？

展開 SRE 判讀

Trace / Span 直接讓你看到：

  • 整條 checkout 花 2.42s。
  • payment.authorize 自己就佔 2.10s。
  • 它是 checkout 的哪一個因果子工作。
  • 其他 sibling work 是否同時正常。

Log 比較適合補：

  • exception message / stack trace。
  • SDK / library 回傳的詳細 error text。
  • 不適合塞成 Span attributes 的 verbose diagnostic detail。

所以這種 incident 很可能是 Span + correlated Log 最有用。Log 帶相同 TraceId / SpanId 時，backend 可以從 Trace 跳到那筆詳細紀錄。

不要雙寫同一份資料。 不是 Span 寫完整 stack、Log 又把所有 Span attributes 複製一次；兩個 signal 應該各自保存它擅長的證據。 完整 Logs 模型會在 Lesson 25 正式學。

Lab 4：Trace 很「詳細」，但其實是過度埋點

一個 cart 有 100 個 items，目前 Trace 長這樣：

checkout.validate_cart          18ms
├─ validate_line_1             0.12ms
├─ validate_line_2             0.15ms
├─ validate_line_3             0.11ms
├─ ...
└─ validate_line_100           0.13ms

先判斷：資訊很多是不是就代表 observability 很好？如果你是 on-call SRE，這 100 個 Child Spans 幫你回答了什麼？

展開 SRE 判讀

如果每個 item validation 都是相同、小而穩定的操作，而且事故時你只在乎「整批 validation 有沒有變慢／失敗」， 那 100 個 Child Spans 大多只是把 call loop 展開給你看。

較合理的設計可能是：

Span: checkout.validate_cart     18ms
  app.cart.item_count = 100
  app.cart.invalid_item_count = 2

如果只有某個特殊 validation stage 真的可能卡住數秒，再針對那個 stage 拆 Child Span。 這就是「不要把 call stack 偽裝成 trace design」。

Lab 5：哪些 Attribute 真的值得留下？

Payment team 想一次把以下欄位全部塞進 Span：

payment.provider       = "provider-a"
deployment.environment = "prod"
order.id               = "4df8..."
auth.token             = "eyJ..."
cart.item_count         = 120
loop_index              = 17

不要先背 Queryability / Cardinality。對每個欄位只做三個具體檢查：

1. 事故時，我真的會拿它 filter / group / compare 嗎？
2. 它可能會有幾種不同值？3 個？5 個？還是幾百萬個？
3. 它是不是敏感資料？
展開逐欄判讀
欄位SRE 判讀
payment.provider通常很有價值。可以直接比較不同 provider 的 latency / error；值通常有限。
deployment.environment值很少而且常有查詢價值；但若已由 Resource 提供，就不要每個 Span 重複自訂另一份。
order.id幾乎每筆都不同，cardinality 很高。不是「絕對禁止」，但要有明確 lookup / correlation 需求並理解 backend 成本與資料治理。
auth.token不要記。credential 的風險不是 observability convenience 可以合理化的。
cart.item_count若懷疑大購物車比較慢，它能直接支援比較；是否保留取決於實際 debug 問題。
loop_index通常沒有任何 production query 意義；只是 local variable 不代表值得成為 telemetry。
Cardinality 的最直覺版本：不是「高 = 錯」，而是「這個欄位會把 backend 的值空間撐到多大，而這個成本換來的診斷價值值不值得？」

Lab 6：目前的 Trace 證明「慢在本機」，但還是不知道哪裡

Incident：

POST /checkout              3.10s
├─ GET inventory              35ms
└─ POST payment               82ms

程式實際還有：

calculate_pricing()
apply_promotions()
build_response()
compress_response()

先判斷：從目前 Trace 你可以排除什麼？又不能證明什麼？下一個 instrumentation 應該怎麼加？

展開 SRE 判讀

你已經有證據排除 inventory 與 payment 是 3 秒主因；因此大部分 latency 位於 checkout process 內部。 但目前沒有證據指出是哪一個 local stage。

下一步不是四個 function 全部永久建 Span。先依 profile、code path、歷史事故或實驗挑最有嫌疑、最可能形成獨立 latency boundary 的 stage。 例如若 compression 隨 response size 急遽變慢： 

POST /checkout              3.10s
├─ GET inventory              35ms
├─ POST payment               82ms
└─ response.compress        2.74s

一旦這個 Span 出現，你就從「本機某處很慢」進步到「compression 是可獨立定位的 bottleneck」。這才是新增 Span 的價值。

Lab 7：Availability 到底在講什麼？先不要碰 Sampler 名詞

假設 request 一開始你知道：

route         = /checkout
customer_tier = premium

執行完才知道：

final_status  = 500
duration_ms   = 2400
retry_count   = 3

先判斷：「Availability」其實只是在問什麼？

展開答案

它首先只是一個時間問題：這個資訊在 operation 的哪個時間點才存在？ 

Span start ------------------------------ Span end
  route 已知                               duration 才確定
  tier 已知                                final_status 才確定
                                           retry_count 才確定

所以任何「Span 一開始就必須做出的決策」都不可能使用未來才知道的 duration_ms。 這就是 Lesson 5 原本那句 Availability 背後真正的因果關係。

至於哪個 OTel 元件會在 Span 建立時做什麼決策，等 Lesson 9：Sampling 為何存在 再正式建立；這裡不需要提前背 head sampler。

Sampling timing 延伸來源：OpenTelemetry Tracing SDK。

最後一題：從需求反推埋點

需求：「最近 checkout 偶發 3 秒以上。我們懷疑是某些 payment provider、超大 cart，或本機 compression，但現在只有一個 POST /checkout Span。」

在看答案前，先自己寫三行：

我會新增哪個 Child Span？
我會新增哪些 Attribute？
我會避免記哪些資料？
一個合理設計，不是唯一答案 
POST /checkout
  Attribute: payment.provider
  Attribute: app.cart.item_count

  Child Span: payment.authorize     # 如果目前尚未有
  Child Span: response.compress     # 若它是可獨立定位的 local latency stage

不要先加入 auth.token、完整 payload、每個 item 的 100 個 Child Spans。 如果 payment failure 需要 stack / library message，再保留 correlated Log；不要用 Log 取代 Trace 的 causal / duration 證據。

Retrieval practice

Q1. 一個 local function 最值得被拆成 Child Span 的理由是什麼？
Q2. Payment timeout 同時要定位耗時與查看 exception stack，較合理的設計是什麼？
Q3. 判斷 Attribute cardinality 時，最先要想的是哪一件事？
Q4. 為什麼 operation 結束後才知道的 latency 不能被開始時的決策直接使用？

最後 Recap

好的 Span boundary：讓 SRE 能把 latency、outcome 或因果位置獨立定位到有診斷意義的工作。

好的 Attribute：能回答具體 incident query，而且其成本與敏感性值得。

好的 Log：補充詳細事件內容，而不是取代 Trace 的 operation 結構。

好的 instrumentation：不是資料最多，而是事故發生時，最少的資料就足以排除錯誤假設。
