先看不可逃避的資源方程式

流量、每個 request 的 Spans、欄位大小或保留期任一項增長，都會放大 application CPU、queue memory、 network、Collector 與 backend 成本。若大多數 requests 都健康且行為相似，保存 100% Traces 不一定增加等比例的新知識。

Sampling 的目標不是隨機「丟資料省錢」而已；它要在成本限制內，保留能代表整體行為或符合事故價值的 Traces。 錯誤的 sampling policy 會讓最需要的證據消失，因此 sampling 本身也是 SRE 必須監控與驗證的系統。

CreateInstrumentation 要求 Tracer 開始一個 Span。Sampler 可能決定不 record。
RecordSDK 保存 attributes、events、status 等 Span 資料。不代表一定標記 sampled。
SampleSampler 決定 Span 是否成為要處理與 export 的樣本。後續 queue、network 仍可能丟失。
ExportProcessor / Exporter 將完成的資料送往下一站。Collector 或 backend 仍可能拒絕、過濾或遺失。
重要：「程式碼有建立 Span」不能推出「backend 一定找得到」；兩者之間至少還有 sampler、recording、processor queue、exporter、network、Collector processors 與 backend ingestion。

SDK sampler 的三種決策

決策Record?Sample / export?適合怎麼理解
DROP否否保留最小 propagation 行為，不保存 Span data。
RECORD_ONLY是否本地 record，但 sampled flag 不設為 sampled。
RECORD_AND_SAMPLE是是record 並交給後續 processing/export。

Sampling decision 在 Span 建立時發生，所以 sampler 只能看到當下可用的資訊：parent context、Trace ID、 Span name/kind，以及建立時提供的 attributes。Span 結束才知道的 error、最終 latency 或後加 attribute， head sampler 當下看不到。

Head sampling：早決策，資訊少

Head sampling 在 Trace 很早期做決策，常見方式是依 Trace ID 與設定比例做一致性 probability sampling。 優點是簡單、低成本，能在資料進入整條 pipeline 前就降低負荷；代價是看不到 Trace 最終結果。 

request arrives
  → root Span starts
  → HEAD DECISION（此時尚不知道最終 500、總 latency、下游錯誤）
  → remaining spans execute

因此「保留所有 error traces」不能只靠最早期的 head decision 完整做到：error 可能在數秒後、另一個 service 或深層 child Span 才出現。

Tail sampling：晚決策，資訊多

Tail sampling 等到看到一條 Trace 的全部或大部分 Spans 後再決定，可以依整體 latency、任一 Span error、 特定 attribute 或 service 做 policy。這換來更高的診斷選擇能力，也必須付出 stateful buffering、 等待時間、memory、trace routing 與營運複雜度。 

many services emit spans
  → Collector receives and groups by Trace ID
  → buffer until decision window
  → TAIL DECISION（可見 errors / latency / attributes）
  → export selected traces

Parent-based sampling 為何重要？

若每個 service 各自擲硬幣，可能只保留 Trace 的某些 Spans，形成難以解讀的 partial trace。 Parent-based sampler 讀取 propagated sampling flag，讓下游通常遵循上游決策；這能維持一條 distributed Trace 的一致性，也解釋了 Lesson 7 的 trace-flags 為何需要跨 boundary。

但 sampled flag 是決策訊號，不是 delivery receipt。01 不能證明 Collector 已收到 Span； 它只表示這條 context 被標記為 sampled，後續 pipeline 仍須另行觀測。

SRE debugging lab：為何 backend 找不到 Trace？

應用 log 有 Trace ID，但 backend 查不到。不要立刻怪 exporter；沿資料生命週期逐站問：

  1. Instrumentation：執行路徑真的建立 Span 了嗎？
  2. Sampling：root / parent decision 是 DROP、RECORD_ONLY 還是 RECORD_AND_SAMPLE？
  3. SDK pipeline：Span 是否 end、Processor queue 是否滿、shutdown 前是否 flush？
  4. Export transport：OTLP request 是否成功，是否 retry / timeout / reject？
  5. Collector：sampling/filter processors 是否 drop，tail buffer 是否過載？
  6. Backend：ingestion、retention、index delay 與 query scope 是否正確？

症狀先查原因

error traces 偶爾缺失head policy 資訊邊界決策時可能尚未知道後續 error。

Policy 設計練習

對一個高流量 checkout 系統，先不寫設定檔，只寫意圖：

  • 健康且快速的 Traces：保留一致的小比例，以估計常態分布。
  • 包含 5xx 或 exception 的 Traces：在容量允許下提高保留率。
  • 總 latency 超過 SLO threshold 的 Traces：提高保留率。
  • 新版本 / canary service：暫時提高保留率，驗證部署風險。
  • Tail sampler 自身：監控 buffer、dropped traces、decision latency 與 uneven routing。

這些是 evidence requirements，尚不是 production policy。真正配置前還要量化 traffic、Span size、 error rate、Collector memory 與最壞情況；先寫「為何保留」，再寫「如何配置」。
