48. Upgrading Collector Safely

Collector 版本只是容器標籤；真正遷移的是 component set、config、semantics、state 與 operational evidence · Lesson 48 of N

本課成果

你會把 Collector upgrade 拆成 artifact、distribution/component inventory、configuration schema、data semantics、state/storage 與 observability contract； 能設計跨版本 diff、canary rollout、rollback/roll-forward，並理解 distribution version 不等於每個 component 都 stable。

主要來源：OpenTelemetry Collector Status、Collector Versioning and Stability、Official Collector Distributions

第一性原理：版本是多個契約的集合

upgrade = binary/framework
        + included component factories
        + component config schemas/defaults
        + telemetry transformation semantics
        + state/storage formats
        + internal telemetry names/attributes
        + platform/runtime behavior

只把 image tag 從 A 改 B，實際同時改了上述多個契約。啟動成功只證明部分 config/runtime； 資料仍可能因 default、semantic convention、routing、sampling、metric temporality 或 internal metric rename 而悄悄改變。

Distribution 與 Component Stability 要分開

官方 releases 組裝 core（otelcol）、contrib、k8s、OTLP 等 distributions。它們包含的 component set 不同；custom distribution 又可完全不同。 同一個 Collector distribution 內，各 components 對 traces/metrics/logs 的 stability 也可不同。

因此「Collector image 是官方的」不等於你使用的 routing/span_metrics/tail_sampling feature 已 stable。 升級 inventory 必須記 distribution、digest、每個 component ID、signal stability、feature gates 與 config fields，而非只記版本號。

Pin Immutable Artifact，不用 Floating Tag 當證據

Production artifact 應以 image digest/verified release asset 表示。Tag 可被誤用或漂移，latest 更不能重建事故現場。 升級紀錄至少保存 current/target digest、distribution manifest、config source revisions 與 final non-secret config hash。

官方 releases repository 也提醒其 Git tags 用於觸發 release、可能因 release issue 調整；部署證據應以實際發布 artifact digest 為準。

Changelog 要讀完整的跨越區間

從 A 跳到 D，必須讀 A→B→C→D 的 core、contrib 與 releases notes，搜尋：

  • Breaking changes、removed/deprecated components/fields/aliases。
  • Default changes與 feature-gate lifecycle。
  • Component rename（例如 lower_snake_case migration）。
  • Data semantic/name/unit/temporality/resource identity changes。
  • Queue/retry/batch/TLS/auth/storage behavior changes。
  • Internal metric names、verbosity、Prometheus suffix/dot conversion。
  • Security fixes、known issues、platform support。

只讀目標版本 release headline，會漏掉中間版本先 deprecate、後 remove 的變化。

Target Binary 必須驗證 Final Config

Schema compatibility 由 target component factories 決定。用 target distribution resolve production 的全部 file/env/provider/override， 再 validate final config；current binary validate current config 不能證明 target 可用。

還要 diff default expansion：未明寫的 field 在 target 可能換 default。高風險 settings（error mode、TLS verification、sampling、queue、temporality、units）應明確寫出，不靠隱含 default。 本課不執行任何 Collector binary。

Semantic Diff 比 Text Diff 更重要

同一 input fixtures 同時送 current/target isolated environments，比較：

  • Items/counts、resource/scope/attributes、span relationships。
  • Filter/sampling/routing selection sets。
  • Metric names/units/types/temporality/start timestamps/cardinality。
  • Logs body/severity/correlation 與 redaction。
  • OTLP partial rejection、batch/request bytes、retry classification。

Text config 沒變，不代表 output 沒變；component implementation/default 可能改。反過來，config migration text 大改，也可能保持等價 output。升級 success criterion 是契約 outcome。

State 與 Storage 決定 Rollback 是否安全

Upgrade/rollback 可能跨越：

  • Persistent exporter queue/WAL/storage schema。
  • Tail sampling pending trace/decision cache。
  • Span metrics/cumulative conversion state與 writer identity。
  • Routing hash ring/backend membership。

若新版本寫入舊版本不懂的 storage format，rollback 可能啟動失敗或遺失 queue。Stateful rolling overlap 也可能造成同 key 多 writers、trace split、metric reset。 需從 component/storage 文件證明 backward compatibility；無法證明時，設計 drain、fresh storage、blue/green 或 roll-forward。

Internal Telemetry 也有 Consumer Contract

Dashboards/alerts/autoscalers/runbooks 都是 Collector internal telemetry 的 consumers。升級若改 metric 名、suffix、labels 或 verbosity， 資料路徑可能健康但監控全盲。Canary upgrade 必須同時驗證：

  • 必要 internal metrics/logs 仍產生。
  • Prometheus/OTLP representation 與 queries 相容。
  • Alert rules 在 test signal 下會 fire/recover。
  • Autoscaling inputs 不變或已同步 migration。

Upgrade Inventory

使用 examples/0048-upgrade-inventory.yaml 保存 current/target exact evidence、compatibility review 與 proof status。 它是不可執行的 planning artifact。

SRE 附加練習：Canary 綠，但 Metrics Reset

  1. 確認 reset 由 source process、Collector temporality/state、writer identity 或 backend ingest 哪層產生。
  2. 比對 current/target component defaults、feature gates、start timestamps 與 resource attributes。
  3. 檢查 rolling overlap 是否讓 old/new 同時寫同 stream；load-balancing affinity 是否 rebalance。
  4. 確認 canary 是否只驗 trace/log arrival，根本沒 assert metric continuity。
  5. 停止擴 rollout；依 storage/state compatibility 選 rollback、drain 或 roll-forward。
  6. 補 metric continuity fixture/canary 與 internal dashboard migration gate。

升級 review 可用 Collector Upgrade Card。

動手推理（不執行）

  1. 為現有 config 列 component inventory：type/name、distribution availability、signal stability、stateful/stateless。
  2. 選一個 default change，設計 current/target fixture output assertion，不依賴 config text。
  3. 寫出 rolling upgrade 中 old/new overlap 對 tail sampling 或 metric writer 的風險與避險方案。
  4. 列出三個 internal telemetry consumers，為每個寫 upgrade compatibility test。

本課總結

  • Upgrade 同時改 binary、component set/schema/defaults、data semantics、state/storage 與 internal telemetry。
  • Pin digest、讀完整跨越 changelogs，按 component/signal stability 建 inventory。
  • Target binary validate final config；semantic diff/canary/load/failure 才證明 outcome。
  • Rollback 前必須證明 state/storage compatibility；否則用 drain、blue/green 或 roll-forward。
