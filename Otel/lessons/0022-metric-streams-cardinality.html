22. Metric streams、Views 與 cardinality

每個 attribute combination 都是 aggregation state；Views 在 SDK 邊界重塑它 · Lesson 22 of N

本課成果

你會推導 measurement attributes 如何形成 metric points/streams 的 cardinality，估算組合爆炸，理解 SDK overflow 的保護與查詢副作用， 並使用 Python View allowlist dimensions、調整 Histogram buckets。核心是資料模型與資源成本，不是特定 backend 調參。

主要來源：Metrics — Views and cardinality、Python Metrics View API

第一性原理：Aggregation 必須為每個分組保存狀態

同一 Counter 收到三筆 measurements：

add(1, {route="/checkout", result="success"})
add(1, {route="/checkout", result="failure"})
add(1, {route="/cart",     result="success"})

若 consumer 要按 route/result 查詢，SDK 必須分別保存三組 aggregation state。Metric cardinality 就是該 stream 實際出現的 unique measurement attribute combinations 數。成本與 request count 不直接相等；它取決於 distinct combinations。 

memory cost per stream
≈ unique attribute combinations
 × aggregation state size

Histogram state 通常還包含多個 buckets，
所以同樣 cardinality 下會比單純 Sum 需要更多 state。

用笛卡兒積估算最壞組合

若 dimensions 大致獨立，理論上限可先用各 value cardinality 相乘：

20 routes × 3 results × 4 regions = 240 combinations

再加入 100,000 user IDs：
20 × 3 × 4 × 100,000 = 24,000,000 combinations

實際資料不一定填滿整個乘積，但這個上界能揭露設計是否有爆炸可能。User ID、request ID、trace ID、raw URL path、SQL text 通常沒有小而穩定的 value set，不應成為 metric measurement dimensions。

Template 而非 instance：http.route=/checkout/{cart_id} 的值集合由 routing table 限制； url.path=/checkout/cart-8cdb 隨每個 cart 改變。兩者看似都描述 HTTP，成本語意完全不同。

Instrument、View 與 Stream 的關係

Instrument
  name + kind + unit + description + Meter scope
       │ measurements(value, attributes)
       ▼
View matching
  選擇 instrument / scope / unit
  重命名、改 description、選 attribute keys、改 aggregation
       ▼
Metric stream(s)
  每個 retained attribute combination 各有 aggregation point

Instrument 是 application code 的 measurement contract；View 是 SDK owner 的輸出政策。這讓 platform/SRE 能在不改每個 call site 的情況下 移除不需要 dimensions、調整 buckets、drop instrument 或建立特定輸出 stream。但 View 不能把已失去的 request causality 變回 Trace。

View attribute allowlist：在聚合前降低維度

範例位於 examples/0022-metric-view.py：

latency_view = View(
    instrument_name="app.checkout.duration",
    attribute_keys={"http.route", "app.checkout.result"},
    aggregation=ExplicitBucketHistogramAggregation(
        boundaries=[10, 25, 50, 100, 250, 500, 1_000]
    ),
)

View 只保留 route template 與 bounded result。即使 call site 傳入 raw path/user ID，它們也不參與這個 output stream 的 identity； 具有相同 route/result 的 measurements 會聚合在一起。這是控制輸出 cardinality，不代表傳入敏感值就沒風險： 它仍曾存在 application memory，其他 Views/readers 或 logs 可能看到，source 端仍應避免產生不必要資料。

Histogram buckets 是你能回答哪些門檻問題

Explicit boundaries [10, 25, 50, 100, 250, 500, 1000] ms 會建立對應區間 counts。 若 SLO threshold 是 300ms，但 buckets 只有 250/500，就無法由 buckets 精確知道 ≤300ms 的 count；只能做區間推估或改 aggregation。

Buckets 太密會增加每個 attribute combination 的 state/payload；太疏則失去決策解析度。從 SLO thresholds、實際 latency range、 記憶體與 backend 支援推導，而非複製任意預設。

SDK cardinality limit 與 overflow point

現行 OTel Metrics model 的預設 cardinality limit 是每個 metric stream 2,000 unique measurement attribute combinations， 可由 View 覆寫（具體語言 SDK configuration surface 可能不同）。達到限制後，額外 combinations 的 measurements 不直接消失， 而是聚合到： 

{otel.metric.overflow=true}

這同時帶來三個結果：

  1. 總量保留：measurement values 仍進 overflow aggregation。
  2. 記憶體有界：不再為每個新 combination 建 state。
  3. 維度遺失：overflow point 不保留原本整組 measurement attributes。
最危險的誤判：overflow 不只移除那個高基數 key，而是移除整個 attribute combination。 若原 measurement 是 {raw_path=..., result="failure"}，進 overflow 後連 result 也不在； 按 result=failure 的 error-rate query 會低估，但全體 request total 仍可保持。

Resource/Scope 不受該 SDK measurement limit，不代表免費

Metrics cardinality limit 針對 Metrics API 記錄時提供的 measurement attributes；Resource 與 Instrumentation Scope attributes 不在此限制內，且在 overflow point 仍可查詢。但這不是把 user ID 搬到 Resource 的漏洞：Resource 必須描述 telemetry-producing entity。

此外，SDK 的 per-process/per-stream limit 與 backend 全域 series 成本是不同邊界。即使每個 process 只有少量 combinations， 上千個 instances/versions/environments 匯總後仍會形成更多 backend series。語意正確是必要條件，容量仍需端到端估算。

Delta 與 cumulative 對 state 回收的影響

對 synchronous instruments，delta temporality 每個 collection cycle 後重設該週期 state，因此 limit 約束當期 active combinations； cumulative temporality 跨 cycles 保留 state，新 combinations 一旦讓 stream overflow，通常會持續到 process restart。

Temporality 不是「哪個比較正確」，而是 producer/consumer 如何表達時間累積。後續會專章深入；本課先記住： cardinality 不只取決於 key/value，也取決於 aggregation state 保存多久。

SRE debugging lab：總量正常，error alert 卻沉默

Case A：檢查 overflow marker

查詢 otel.metric.overflow=true point 的 count/sum。若持續大於零，代表部分 measurements 已失去原 dimensions。 先找最近新增的 high-cardinality attribute、route template regression 或 View 變更。

Case B：比較 total 與分組總和

若全體 total ≈ success + failure + overflow，而 success/failure 分組總和偏低，overflow 正能解釋差額。 Alert 不能只依賴可能被 overflow 移除的 key；同時應對 overflow 建 data-quality alert。

Case C：View 上線後某 attribute 消失

先讀 View 的 attribute_keys，確認它是刻意 allowlist。若需要該維度，先算新增後 cardinality budget、確認 value set bounded， 再調整 View；不要直接放回所有 keys。

練習：計算並重設一個 metric budget

原設計：50 routes × 6 status codes × 3 regions × 20 versions = 18,000 combinations/process。

請嘗試：status 改為 5 classes、version 留在 Resource、route 只保留 20 個 templates。說明新的 SDK measurement combination 上限， 以及 backend 仍會如何受到跨 versions/instances 聚合影響。
