7. Context propagation 為何不可少

跨越 process boundary，重新建立可驗證的因果關係 · Lesson 7 of N

從物理限制開始

Service A 與 Service B 是不同 process：它們不共享 heap、不共享 Python object，也不共享「目前是哪個 Span」的執行狀態。 因此 B 收到 HTTP request 時，不可能只靠本機記憶體知道這個 request 是 A 哪一個 Span 造成的。

若要把兩邊的工作接成同一條 Trace，A 必須把最小的因果識別資訊寫進會跨 boundary 的 carrier； B 再讀出它，建立新的 child Span。這個序列化、傳遞與反序列化機制就是 context propagation。

主要來源：OpenTelemetry — Context propagation

五個常混淆的名詞

名詞責任不是什麼
Context在 execution unit 內攜帶目前相關狀態的容器，讓程式找到 current Span 等資訊。不是 HTTP header，也不是整條 Trace。
SpanContextSpan 的不可變 correlation identity：Trace ID、Span ID、TraceFlags、TraceState。不含 Span name、attributes、events 或 timestamps。
Carrier真正跨 boundary 的媒介，例如 HTTP headers、message properties。不是 OTel SDK object。
Propagator依格式把 Context 資訊 inject 到 carrier，或從 carrier extract 出來。不建立或 export Span。
traceparentW3C Trace Context 的 HTTP header 表示，承載 trace correlation fields。不是完整 Span 的 JSON。
關鍵界線：跨網路傳的是 SpanContext 的必要欄位，不是整個 Span。 完整 Span 仍由各 service 的 SDK 在本地結束後，經 Processor / Exporter 送往 telemetry pipeline。

Sender 與 receiver 的完整因果鏈

Service A（sender）
  current CLIENT Span
      │  inject：序列化目前 SpanContext
      ▼
  HTTP carrier: traceparent header
      │  network：只運送字串 header
      ▼
Service B（receiver）
  extract：解析 remote SpanContext
      │  以 remote context 作 parent
      ▼
  new SERVER Span
  1. A 建立 outbound CLIENT Span；它有 Trace ID T 與 Span ID A1。
  2. Propagator 在送出 request 前，把 T、A1 與 flags 寫入 headers。
  3. B 在建立 SERVER Span 前先 extract headers，得到 remote parent context。
  4. B 建立新的 Span ID B1，沿用 Trace ID T，並令 Parent Span ID = A1。

B 不可沿用 A 的 Span ID，因為 B 是新的 operation；它只沿用 Trace ID 並指向 A 的 Span ID。 這正是「同一條 Trace、不同因果節點」的最小資料需求。

拆解 traceparent

traceparent: 00-a0892f3577b34da6a3ce929d0e0e4736-f03067aa0ba902b7-01
             │  │                                │                └─ trace-flags
             │  │                                └─ parent-id（sender current Span ID）
             │  └─ trace-id
             └─ version
欄位長度下游如何使用
version2 hex chars決定 header 格式版本。
trace-id32 hex chars下游 Span 沿用，加入同一條 Trace。
parent-id16 hex chars下游新 Span 的 Parent Span ID。
trace-flags2 hex chars傳遞 sampling 等 bit flags；01 的最低位表示 sampled。

header 中稱為 parent-id，是因為它會成為接收端新 Span 的 parent；在送出端， 它其實是 sender 當下 current Span 自己的 Span ID。不要把它誤解成「sender 的 Parent Span ID」。

Propagation 與 export 是兩條不同路徑

Request path:   A -- traceparent --> B

Telemetry path:
  A Span -- Processor/Exporter --> Collector/backend
  B Span -- Processor/Exporter --> Collector/backend

即使 A 沒有設定 Span exporter，context propagation 仍可能運作；反過來，A/B 都成功 export Spans， 也可能因 headers 沒有 inject/extract 而變成兩條斷裂的 Traces。看到 backend 有資料，不代表 propagation 正確。

SRE debugging lab：Trace 在服務邊界斷掉

你在 backend 看到：

Service A CLIENT Span
  trace_id = aaa...
  span_id  = 111...

Service B SERVER Span
  trace_id = bbb...
  span_id  = 222...
  parent_id = null

這證明 B 建立了一條新 Trace，但還不能直接斷言是哪一行 code 壞了。依 boundary 逐步縮小：

  1. Sender：outgoing request 上是否真的有合法 traceparent？
  2. Transport：proxy、gateway 或 client library 是否保留 header？
  3. Receiver：instrumentation 是否在建立 SERVER Span 前 extract？
  4. Format：兩端是否使用相容 propagator，header 是否可解析？
  5. Execution context：inject 時正確的 CLIENT Span 是否為 current？
三種症狀如何定位
症狀優先假設
Outgoing request 沒有 traceparentsender instrumentation / inject / current context。
Header 到達 B，但 B 仍是 rootreceiver extract、propagator format 或建立順序。
A/B 同 Trace ID，但 B parent 指錯 Spaninject 時 current Span 錯誤，或 context attach/detach lifecycle 錯誤。

安全邊界

外部來源可以偽造 trace headers；送往不受信任的外部服務也可能暴露內部 correlation 資訊。 此外，Baggage 可攜帶任意 key-value，切勿放 credential、API key 或 PII。這不改變 propagation 的 核心機制，但 SRE 導入時必須明確定義 trust boundary 與 sanitization policy。
