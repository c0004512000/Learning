10. Python sampling 實驗

直接觀察 recording、sampled flag、child consistency 與 export · Lesson 10 of N

這次實驗要證明什麼？

Lesson 9 說明 sampled decision 不等於「程式碼有沒有呼叫 start Span」。本課固定同一段 instrumentation， 只替換 Provider 的 sampler，觀察四個結果：

  1. Span.is_recording() 是否為 true。
  2. trace_flags.sampled 是否為 true。
  3. Child Span 是否遵循 parent decision。
  4. ConsoleSpanExporter 是否收到並印出 Span。

API 依據：OpenTelemetry Python SDK — trace.sampling；概念依據：OpenTelemetry — Sampling

三組 sampler

CasePython samplerRoot decisionChild behavior
always_onDEFAULT_ON沒有 parent 時 sample遵循 sampled parent
always_offDEFAULT_OFF沒有 parent 時 drop遵循 not-sampled parent
ratio_25ParentBasedTraceIdRatio(0.25)依 Trace ID 與 25% rate遵循 root decision

這裡不用單獨的 ALWAYS_ON / ALWAYS_OFF，而用 parent-based defaults； 原因是 distributed tracing 希望 child 通常繼承 parent sampling decision，而不是每個 Span 各自重新決定。

執行

程式在 examples/0010-sampling-experiment.py：

.\.venv\Scripts\python.exe .\examples\0010-sampling-experiment.py
執行前預測：先寫下 always_on / always_off 各自的 recording、sampled、console export； 再猜 12 條 ratio traces 會保留幾條。實際數字不必剛好 3，因為 25% 是長期比例，不是每四條保證一條。

Sampler 在哪裡接入？

provider = TracerProvider(
    sampler=sampler,
    resource=Resource.create({"service.name": f"sampling-{label}"}),
)

Sampler 是 Provider 的共用 SDK configuration；每個新 root Span 都透過它做 decision。 這也說明為何 application startup 決策會影響所有 runtime requests，而不是每個 business function 自己挑選 exporter 或 sampler。

初始 Attributes 為何放在 Span 建立時？

with tracer.start_as_current_span(
    "checkout.request",
    attributes={"app.case": label, "app.iteration": index},
) as root:

Sampler decision 發生在 Span creation。若 custom sampler 需要某個 attribute，該值必須在建立時提供； 進入 with 後才 set_attribute，對已做完的 head decision 太晚。 本課的 built-in ratio sampler 只依 rate / Trace ID，但這個時序對未來設計 custom policy 很重要。

讀兩個不同訊號

root.is_recording()
root.get_span_context().trace_flags.sampled
  • is_recording() 回答 SDK 是否保存這個 Span 的資料。
  • trace_flags.sampled 回答 SpanContext 是否標記為 sampled，並可由 propagation 傳給下游。

不要用「console 有沒有 JSON」取代這兩個觀察值。Console output 還受到 Span 是否 end、Processor 是否 flush、 Exporter 是否成功影響；本課同時印 decision state，才能區分 sampling 與 export。

Parent-based consistency 的證據

with tracer.start_as_current_span("checkout.request") as root:
    with tracer.start_as_current_span("checkout.validate") as child:
        ...

每一列輸出中，root sampled 與 child sampled 應相同。對 ratio case 而言，是 root 依 Trace ID 做一次概率決策， child 再明確遵循 local parent。這個「明確遵循」很重要：上游可能使用不同 rate 或 custom policy； 下游不應只因自己的 sampler 設定不同，就推翻已經 propagation 過來的決策。

SRE debugging lab 1：有 Trace ID，為何沒有 export？

觀察 always_off：程式仍能取得 SpanContext 並印出 sampled=false，但 ConsoleSpanExporter 沒有該 case 的 Span JSON。 這證明「有 context 可 propagation」與「Span 被 record/export」是可分離的需求。

SRE debugging lab 2：一個會誤導你的對照

將 ratio case 暫時從 ParentBasedTraceIdRatio(0.25) 改為 TraceIdRatioBased(0.25)，並補上對應 import。你可能仍看到 root 與 child decision 相同。 這是否證明 sampler 有讀 parent？

為何這個結果不能證明 parent semantics

TraceIdRatioBased 依 Trace ID 做 deterministic decision，而同一 Trace 的 root/child 共用 Trace ID； 即使它沒採用 parent decision，也可能算出相同結果。要證明 ParentBased，必須提供一個已帶 sampled/not-sampled flag 的 remote parent，並讓下游 root policy 與上游 decision 衝突。這提醒你：測試必須能區分兩個 competing hypotheses，看到相同輸出不等於機制相同。

數據解讀陷阱

  • 12 條只是一個小樣本；0、2、3、5 條 sampled 都不能證明 25% 實作錯誤。
  • 要驗證 rate，應用大量 root traces，計算 confidence interval，而不是看一次 console。
  • 要驗證完整性，應檢查同一 Trace 的 parent/child sampled decisions，而不是只數 Span 總量。
  • 要驗證 delivery，還需看 Processor、Exporter、Collector 與 backend 指標。
