03. Node Exporter → Prometheus：Node metrics 的資料生命週期

從 Linux host state 到 Prometheus time series

這一章先建立 Node metrics 的底層模型。因為 Node Exporter Full 幾乎全部依賴 node_* metrics；如果不知道這些 metrics 從哪裡來，後面 128 個 panels 只會變成 PromQL 背誦。

1. 最原始的 CPU / Memory 資訊在哪裡？

在 Linux host 本身。Kernel 維護 CPU time、memory、filesystem、network、process 等狀態；Linux 也透過例如 /proc、/sys 等介面暴露大量 kernel/runtime state。

2. Node Exporter 做什麼？

Node Exporter 的 collectors 讀取 host state，轉成 Prometheus exposition format，透過 HTTP metrics endpoint 暴露。例如：

node_cpu_seconds_total{cpu="0",mode="idle"} ...
node_memory_MemTotal_bytes ...
node_filesystem_avail_bytes{mountpoint="/",...} ...

它的核心責任是「把 host state 轉成可 scrape 的 metrics」，不是長期儲存歷史資料，也不是畫 Dashboard。

3. Prometheus 怎麼取得它？

Prometheus 是 pull model：需要先透過 static targets 或 service discovery 找到 endpoint，再依 scrape interval 呼叫 metrics endpoint，把每個 sample 寫進 TSDB。

4. Metric family 為什麼不是「一條線」？

node_cpu_seconds_total{instance="node-a:9100",cpu="0",mode="idle"}
node_cpu_seconds_total{instance="node-a:9100",cpu="0",mode="system"}
node_cpu_seconds_total{instance="node-a:9100",cpu="1",mode="idle"}

Metric name 相同，但 label set 不同就是不同 time series。Node Exporter Full 的 $job、$node variable，本質就是在挑選這些 series。

5. Counter 為什麼還要 rate()？

node_cpu_seconds_total 是累積 CPU seconds。Dashboard 想看的通常是「最近這段時間 CPU 使用比例」，因此需要看 counter 的變化速率，而不是直接畫累積值。

raw counter
node_cpu_seconds_total
        ↓ rate(...[$__rate_interval])
每秒增加多少 CPU seconds
        ↓ idle → busy conversion
CPU Busy %

6. Taiwan Stage 還缺哪些 runtime proof？

待 source-of-truth
  • 實際 Node Exporter 是哪個 Helm release / chart / version。
  • 是否以 DaemonSet 部署、container args 與 enabled/disabled collectors。
  • host /proc、/sys 等 mounts 實際怎麼掛。
  • Service / ServiceMonitor / PodMonitor / annotations 哪一種機制供 Prometheus discovery。
  • 實際 metrics port、path、scrape interval、relabel config。
  • Prometheus runtime target 是否 UP，以及最後形成的 job/instance labels。

這些沒有被現有 Grafana inventory 直接證明，所以目前教材只把 Node Exporter → Prometheus 當作通用資料模型，不會偷換成 Taiwan Stage 實況。
