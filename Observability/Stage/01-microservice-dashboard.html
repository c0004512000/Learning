01. MicroService Dashboard：三條 signal 如何在一頁相遇

從實際 Stage datasource、variables、queries、panel rows 反推設計

先從成品反推：這個 Dashboard 不是「一個 Prometheus Dashboard」。最新 Stage inventory 顯示它有 29 個 panels、6 個 row sections、9 個 variables，而 panel targets 同時使用 Prometheus、Loki、Tempo。

第一步：先辨認它連到哪些 backend

第三步：同一個 Namespace，三個 backend 的欄位完全不同

# Prometheus
namespace=~"$Namespace"

# Loki
k8s_namespace_name=~"$Namespace"

# Tempo
resource.k8s.namespace.name=~"$Namespace"

這就是 Dashboard variable 的核心價值：它不是把三個 backend 合成同一張表，而是讓同一個 UI 選擇值，被代入三種不同的資料模型與 query language。

第四步：看三條真實 query

Pod CPU · PromQL

rate(container_cpu_usage_seconds_total{
  pod=~"(?i:(^$Job-.*))",
  namespace=~"$Namespace",
  kubernetes_io_hostname=~"$node"
}[3m])

這條 query 隱含一個 upstream contract：Prometheus 裡必須有 container_cpu_usage_seconds_total，而且 series 要帶 pod、namespace、kubernetes_io_hostname labels。

Error / Warning Log Count · LogQL

sum by(service_name) (
  count_over_time({
    service_name=~"$Job",
    k8s_namespace_name=~"$Namespace"
  } | severity_text = "Error" [1m])
)

HTTP / DB Trace · TraceQL

{ resource.service.name =~ "$Job"
  && span.db.system =~ "$DB_SYSTEM"
  && ("$Namespace" = ".*"
      || resource.k8s.namespace.name =~ "$Namespace") }

現在還不能從 Dashboard JSON 證明什麼？

待 source-of-truth 目前還不能單靠 Grafana JSON 證明：
  • container_* 在 Stage 是透過哪個 kubelet/cAdvisor scrape path 進 Prometheus。
  • k8s_namespace_name 是在哪個 log agent / processor 被附加。
  • resource.k8s.namespace.name 是 application instrumentation 還是 OTel Collector enrichment 產生。
  • traces_spanmetrics_* 的 production path 與 metrics-generator / connector 實際設定。
這些要靠 Stage Helm / Kubernetes / runtime config 逐條補證。
