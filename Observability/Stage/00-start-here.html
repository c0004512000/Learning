00. 從資料誕生到 Dashboard

先建立 Taiwan Stage Tier 1 scope 的完整 observability lifecycle 心智模型

這一章只回答一件事：你在 Grafana 看到一條 CPU 線、一筆 Log、或一條 Trace 之前，資料到底經過了哪些角色？先把這條因果鏈建立起來，後面看 Helm values、Prometheus scrape config、Grafana datasource 和 PromQL 才不會只是背設定。

先從畫面往回推

你現在 scope 裡有兩個 Dashboard：MicroService Dashboard 與 Node Exporter Full。它們表面上都是 Grafana 頁面，但背後依賴的資料來源不一樣。

Dashboard它真正依賴的資料Stage Grafana 目前看到的 backend
MicroService DashboardPod/Container metrics、Node metrics、application logs、application traces、部分 span-metricsPrometheus + Loki + Tempo
Node Exporter FullLinux host / node metrics，例如 CPU、Memory、Filesystem、Network、LoadPrometheus 類 datasource；目前 dashboard 內存在 stale UID 綁定問題

第一個重要結論：Grafana 本身不是 telemetry backend。它不負責長期保存這些 CPU samples、logs 或 traces；它只是透過 datasource 去 backend 查資料，再把 query result 畫成 panel。

一條完整生命週期有六層

如果你 debug 一個「Dashboard 沒資料」問題，這六層就是你的檢查順序。不要一開始只盯 Grafana。資料可能根本沒有生成、沒有被 scrape、被 collector drop、backend 沒 ingest、datasource 指錯，或 PromQL filter 把它全部篩掉。

Metrics 路徑：你看到 CPU 之前發生什麼？

以 Node Exporter Full 的 CPU panel 為例，Dashboard 查的不是一個叫「CPU Busy」的 metric。它查的是較原始的 node_cpu_seconds_total，再用 PromQL 的 rate()、aggregation 與算術算出 CPU Busy。

Linux host state
   ↓
node-exporter 暴露 node_cpu_seconds_total
   ↓ scrape
Prometheus 儲存 time series
   ↓ PromQL
rate(node_cpu_seconds_total{mode="idle"}[...])
   ↓ calculation
CPU Busy %
   ↓
Grafana panel

這裡每一層責任都不同：Node Exporter 把 host state 轉成 Prometheus metrics；Prometheus 負責 scrape 與保存；PromQL 負責把原始 series 算成你要看的 operational signal；Grafana 只負責呈現。

通用模型 上面是 Node Exporter + Prometheus 的標準資料模型。Taiwan Stage 實際是哪個 Helm release、DaemonSet、ServiceMonitor、scrape job、port 與 relabel config，目前還需要 runtime/source-of-truth 證據。後面章節會明確把「一般機制」與「Stage 已證實設定」分開。

Pod / Container metrics 路徑：為什麼 MicroService Dashboard 能看 Pod CPU？

MicroService Dashboard 的 Pod CPU panel 實際使用：

rate(
  container_cpu_usage_seconds_total{
    pod=~"(?i:(^$Job-.*))",
    namespace=~"$Namespace",
    kubernetes_io_hostname=~"$node"
  }[3m]
)

這段 query 已經暴露三件事情：第一，backend 裡必須存在 container_cpu_usage_seconds_total；第二，這些 series 必須帶有 pod、namespace、kubernetes_io_hostname 等 labels；第三，Grafana variables $Job、$Namespace、$node 會被插入 PromQL。

也就是說，Dashboard 能不能工作，不只取決於「有沒有 CPU metric」，還取決於metric label schema 是否符合 query 的假設。

Logs 路徑：同一個 Namespace filter 為什麼又能查 Loki？

MicroService Dashboard 的 Error log query 使用 Loki：

sum by(service_name) (
  count_over_time({
    service_name=~"$Job",
    k8s_namespace_name=~"$Namespace"
  } | severity_text = "Error" [1m])
)

這裡的 Namespace label 不是 Prometheus 的 namespace，而是 Loki stream 裡的 k8s_namespace_name。所以「同一個 UI filter」其實只是同一個變數值，被 Dashboard 分別插入不同 backend 的不同欄位。

Stage Grafana 已證實 Loki datasource UID 是 loki123，URL 指向 loki-query-frontend.loki.svc.cluster.local:3100。但「log 最初由哪個 agent 收、在哪一層補上 k8s_namespace_name」仍要再用 Stage runtime config 證明。

Traces 路徑：Grafana 怎麼知道要找哪條 Trace？

MicroService Dashboard 的 Tempo query 會直接查 span/resource attributes，例如：

{
  resource.service.name =~ "$Job"
  && span.http.request.method =~ "$Method"
  && ("$Namespace" = ".*"
      || resource.k8s.namespace.name =~ "$Namespace")
}

這代表 Trace 在進入 Tempo 之前，至少必須已經帶有 service.name、HTTP attributes，以及 Kubernetes namespace resource attribute。這些欄位可能來自 application instrumentation、SDK Resource、Collector processor 或其他 enrichment；光看 Dashboard 只能證明它「依賴這些欄位」，不能證明是哪一層產生。

Stage Grafana 已證實 Tempo datasource UID 是 temp123，URL 指向 tempo-distributed-v3-query-frontend.tempo-v3.svc.cluster.local:3200；Datasource 還配置了 traces-to-logs → Loki、service map → Prometheus。

Datasource 層到底做什麼？

你在 Grafana UI 新增 Prometheus datasource 時，本質上不是「把 Prometheus 的資料匯進 Grafana」，而是建立一個 connection definition：

type: prometheus
uid: prometheus
url: http://prometheus-server.prometheus.svc.cluster.local
access: proxy
httpMethod: GET

之後 Dashboard panel target 只需要引用 datasource UID prometheus，Grafana 就知道這條 PromQL 要送去哪一個 backend。

這也解釋了 Node Exporter Full 現在的一個實際問題：它大量 panel target 綁定 UID becxci96j0tfkc，但最新 Stage datasource inventory 裡找不到這個 UID。換句話說，即使 Prometheus backend 本身有完整 node metrics，Dashboard 仍可能因 datasource binding stale 而失效。

最後一層才是 Panel 與 Layout

到了這裡資料才真正變成你在 Grafana 上看到的畫面。Panel 還會決定：

  • 用 time series、stat、table 還是其他 visualization；
  • 數值 unit 是 bytes、percent、seconds；
  • legend 如何命名；
  • threshold 怎麼標示；
  • 多個 query 是否做 transformation；
  • 整個 Dashboard 用哪些 row/section 來安排 troubleshooting 順序。

所以一個 Dashboard 的「生成」不是在 Grafana 裡按幾個 UI 就完成。真正完整的生命週期是：

資料產生
→ 被收集 / scrape
→ metadata 被建立
→ backend ingest / store
→ Grafana datasource 能連到 backend
→ variable 取得 filter 值
→ PromQL / LogQL / TraceQL 查詢
→ panel visualization
→ dashboard layout
