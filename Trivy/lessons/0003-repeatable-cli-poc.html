PHASE 02 / LESSON 03 · 最小可重現實驗

我們怎麼證明 Trivy 真的有掃到？

先閱讀 CLI 基礎前導課：知道 Trivy 在哪裡執行、掃描目標從哪裡取得，以及 Target 與 Scanner 的差別。現在把「先辨識套件名稱與版本，再比對已知漏洞」這個模型變成可驗證的實驗。不必使用公司 Repo，也不需要先部署 Trivy Server。

本堂目標

對一個最小樣本，比較舊版、修正版、空目錄與建好的 Image 的掃描結果，能說出每個案例驗證了什麼。

前置閱讀：Phase 02 前導：Trivy CLI 的基本原理與使用方式。本頁是可重現實驗教材，以下預期結果並非本次執行紀錄。

01 / 先設計實驗，再下指令

假設只拿一個完全陌生的專案掃描，Trivy 回報 0 個漏洞。我們無法判斷它是沒有找到漏洞，還是沒有讀到套件。因此先挑一個已知有漏洞的版本，及一個修正該漏洞的版本，作為對照。

本次選 Python 的 requests：公開公告 CVE-2024-35195 指出 2.32.0 之前版本受此問題影響。用 2.31.0 與 2.32.5 做對照，只驗證這一個 CVE 是否消失，不要求修正版完全沒有其他漏洞。過程不需要執行有漏洞的程式。

Figure 03 · 四個受控輸入

  1. 舊版 requirements.txt → 應辨識 requests 2.31.0，並命中指定 CVE。
  2. 修正版 requirements.txt → 應辨識 requests 2.32.5，但不命中指定 CVE。
  3. 沒有套件清單的空目錄 → 不應聲稱 requests 已被辨識。
  4. 由舊版清單安裝套件的 Image → 應檢查 Image 中可辨識的 Python 套件與 OS 套件。

每個箭頭代表把該輸入交給 Scanner 觀察，並非事先宣稱測試成功。

02 / 準備環境與樣本

使用已核准的 Linux／WSL 測試環境，需要 Trivy CLI、jq、Docker（最後一個 Image 實驗才需要）。安裝方式請見 官方安裝文件；先選定核准的固定版本，不在公司 Runner 上擅自安裝。初次掃描需要能取得漏洞資料庫。

trivy --version
jq --version
docker version

mkdir -p trivy-poc
cd trivy-poc
mkdir -p old fixed empty reports

printf 'requests==2.31.0\n' > old/requirements.txt
printf 'requests==2.32.5\n' > fixed/requirements.txt

我們把 reports 放在掃描目錄外面，避免掃描結果成為下一次的輸入；在乾淨目錄中操作，避免既有 trivy.yaml、忽略規則或環境變數改變實驗條件。

03 / 第一次 Filesystem Scan

trivy fs --scanners vuln \
  --list-all-pkgs --format json \
  --output reports/old.json old

--scanners vuln 讓本次只測漏洞；--format json 是方便機器讀取的報告；--list-all-pkgs 讓沒有命中漏洞的可辨識套件也留在報告。掃描前、後都記錄 trivy --version，保留 CLI 及可取得的 DB 版本／更新時間。若資料庫在兩個案例之間更新，須記錄差異或用同一份已更新的 DB 重新比較。

jq -r '.Results[]? | .Packages[]? |
  [.Name, .Version] | @tsv' reports/old.json

jq -r '.Results[]? | .Vulnerabilities[]? |
  select(.VulnerabilityID=="CVE-2024-35195") |
  [.PkgName, .InstalledVersion, .FixedVersion] |
  @tsv' reports/old.json

第一個命令讀出套件清單，第二個只找指定漏洞。這樣就不需要靠漏洞總數來判定 scanner 是否正確辨識版本。

04 / 保持 Scanner 相同，只更換輸入

trivy fs --scanners vuln --list-all-pkgs \
  --format json -o reports/fixed.json fixed

trivy fs --scanners vuln --list-all-pkgs \
  --format json -o reports/empty.json empty

用上一節的 jq 命令檢查這兩份報告（換檔名）。預期 fixed 仍有 requests，但指定漏洞不再出現；empty 沒有 requests，不能把它當作修復成功。任何命令若非正常完成，先處理錯誤再解讀報告。

05 / 同一個樣本，改掃 Image

這次真的安裝舊版套件，再讀取最終 Image。這是隔離的教學 Image，不要執行服務、推送 Harbor 或部署。

cat > old/Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt \
    && rm requirements.txt
EOF

docker build -t trivy-poc:old old
docker image inspect --format '{{.Id}}' trivy-poc:old
trivy image --image-src docker --scanners vuln \
  --list-all-pkgs --format json \
  -o reports/image.json trivy-poc:old

Dockerfile 安裝套件後移除原宣告，以便觀察 Image 內的安裝套件 metadata；注意 Docker base tag 和間接依賴可能隨時間變化。正式重現時需固定 base digest、實際安裝版本與 Scanner DB，並保留 image ID。--image-src docker 限定本機 Docker，避免同名 registry Image 影響結果。

jq -r '.Results[]? |
  [.Target, .Class, .Type,
   ((.Packages // []) | length)] | @tsv' \
  reports/image.json

預期看到 Python 已安裝套件與 Linux OS 套件的結果分類；請以清單核對，而不是假設一定有固定數量。這就是第一章的 fs/image 差異在 CLI 中的具體表現。

06 / 什麼結果才算 PoC 通過？

案例必須觀察的結果（預期）
舊版requests 2.31.0 已辨識，指定 CVE 存在
修正版requests 2.32.5 已辨識，指定 CVE 不存在
空目錄requests 未辨識，不視同安全
Image掃描到指定 Image，核對 Python 及 OS 套件資訊

把實際輸出、CLI/DB 版本、錯誤與 Image ID 記錄下來。不符合預期時先找出是輸入、版本辨識、DB 或執行問題；不要直接降低驗收條件。

08 / 回顧

  • 用已知漏洞版本與修正版建立對照，而不是拿 0 筆報告猜測。
  • 套件清單與漏洞命中必須分開驗證。
  • 空目錄是負向輸入，不是安全證據。
  • Image scan 讀取已建置的 Image；比較時保留實際 Image 身分和資料庫版本。

有任何命令不符合預期，可以將去除機密的報告片段或錯誤貼回對話，我們一起定位問題。下一堂學會讀取報告與退出碼。
