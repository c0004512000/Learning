PHASE 06 / LESSON 12

Runner Readiness：CLI、網路、DB 與執行環境

本堂目標

能在 Linux ARC 與 Windows Runner 分別確認 Trivy 可執行、DB 可取得、報告可寫入、錯誤可辨識。

01 / 安裝成功不是掃描成功

Trivy 需要可執行檔、可讀輸入、可用的漏洞 DB、可寫報告位置，以及必要的網路與憑證。Filesystem Scan 不需要 Docker Socket、Harbor Image、Kubernetes API 或啟動應用程式。Runner image 或 Windows 主機的安裝、更新與權限須走核准流程。

層級驗證
Binary核准版本、OS／architecture、來源與 checksum／簽章（若提供）
Execution實際 runner service account、PATH、工作目錄與檔案權限
DBregistry 存取、CA、proxy、schema、freshness
Inputrepo checkout SHA、restore 成功、支援格式及範圍
Output可寫新目錄、JSON 可解析、exit code 捕捉、artifact 上傳

02 / Linux ARC：用實際 Job 身分測試

command -v trivy
trivy --version
trivy fs --help
id
pwd
CACHE=$(mktemp -d)
OUT=$(mktemp -d)
trivy --cache-dir "$CACHE" fs --download-db-only
trivy --cache-dir "$CACHE" --version

從 Job 內確認，而不是只在 worker node 安裝後就宣稱 ARC runner 可用。不同 Runner Pod 的 image、mount、service account 和 cache lifecycle 可能不同。DB 下載成功不代表每個 repo 的 package restore 也成功。

printf 'requests==2.31.0\n' > "$OUT/requirements.txt"
trivy --cache-dir "$CACHE" fs --scanners vuln --skip-db-update --list-all-pkgs --format json -o "$OUT/report.json" "$OUT/requirements.txt"
rc=$?
printf 'scan_exit=%s\n' "$rc"

在 Actions 的 Bash 預設 error handling 可能因非零立即終止；正式捕捉方式用 if/else 或明確的 shell error handling，如 Lesson 13。

03 / Windows：確認不是只在互動帳號有效

Get-Command trivy -ErrorAction Stop
trivy --version
if ($LASTEXITCODE -ne 0) { throw 'Trivy version failed' }
$cache = Join-Path $env:RUNNER_TEMP ('trivy-cache-' + [guid]::NewGuid())
$out = Join-Path $env:RUNNER_TEMP ('trivy-report-' + [guid]::NewGuid())
New-Item -ItemType Directory -Path $out -Force | Out-Null
trivy --cache-dir $cache fs --download-db-only
if ($LASTEXITCODE -ne 0) { throw 'DB preparation failed' }
Set-Content -Path (Join-Path $out 'requirements.txt') -Value 'requests==2.31.0' -Encoding ascii
trivy --cache-dir $cache fs --scanners vuln --skip-db-update --list-all-pkgs --format json -o (Join-Path $out 'report.json') (Join-Path $out 'requirements.txt')
$rc = $LASTEXITCODE
if ($rc -ne 0) { throw "Scan failed: $rc" }
Get-Content (Join-Path $out 'report.json') -Raw | ConvertFrom-Json | Out-Null

這段在 GitHub Actions Runner context 使用 RUNNER_TEMP，並假設 native command 可執行。Windows PowerShell 與 PowerShell 7 的錯誤處理可能不同；確認 native nonzero 行為，勿只看 $?. 長期 Runner 要避免前一個 Job 殘留檔案、環境變數、憑證或 DB 混進下一個 Job。

04 / 網路、Registry 與企業 CA

DB 由 OCI registry 分發，不等於 Image Scan。若需要透過 proxy 或內部 DB mirror，應驗證 DNS、TCP/TLS、registry API 及 blob 下載的完整路徑。企業 CA 透過核准信任方式設定，不把 insecure 當正常修復；不要公開 proxy credentials 或 debug log 中的敏感內容。

症狀下一步
command not found / not recognized核對實際 Runner PATH、架構、核准安裝位置
429 / rate limited確認 DB source、併發及 cache 策略
x509 / certificate verify檢查企業 CA、TLS interception、服務帳號信任存放區
DB metadata 舊檢查 UpdatedAt、更新排程、鏡像同步和有效設定
report JSON 缺失先看 exit、輸出權限、工作目錄，不讀舊報告
掃描 0 套件核對 restore、掃描 target、skip、支援格式及 dev scope

05 / Readiness Matrix

每種 runner class 分別完成：binary check、cold cache、warm cache、已知漏洞 fixture、修補 fixture、空輸入、故意無效 target、輸出上傳。保留 runner class、CLI 版號、DB metadata、結果與錯誤摘要。未取得證據的 class 標 NOT_VERIFIED，不因 Linux 成功就假設 Windows 可用。

理解驗收

在 ARC worker node 上 trivy --version 正常，但 workflow 顯示 command not found，下一步？

先自行回答，再查看解析

確認真正的 Runner Pod/image、容器 PATH 及 executable 是否存在；worker host 與 job execution environment 不同。

Windows 上 DB 下載成功，之後 scan 沒 report，能否視為零漏洞？

先自行回答，再查看解析

不能。確認 scan exit、路徑、JSON 是否有效及預期套件是否辨識。

本堂回顧

  • Runtime readiness 需在實際 job 身分驗證。
  • FS Scan 不需 Docker 或 K8s API。
  • 資料下載、掃描、輸出分開檢查。
  • ephemeral 與 persistent Runner 的 cache lifecycle 不同。

主要來源：CLI · DB · Cache · GitHub secure use。範例是教學及待驗證設計，非公司 Runner 實測；請以核准版本的 CLI help 與實際 workflow 核對。

有不清楚的地方，可將去識別後的命令、報告或推論帶回對話討論。
