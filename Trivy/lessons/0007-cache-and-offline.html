PHASE 03 / LESSON 06 · CACHE & OFFLINE

Cache、DB 更新與離線掃描

本堂目標

能分辨資料庫 cache 與 Scan Cache，設計一次預下載、可重複掃描並定位下載故障。

01 / Cache directory 不是 Scan Cache Backend

如果每次 scan 都下載 DB，成本會很高。因此 Trivy 保存已下載的資料；它也有保存分析結果的 scan cache，用來避免重複分析。兩者不是同一件事。

機制意義
--cache-dir本機 DB 與相關 cache 的目錄位置
--cache-backend分析結果的儲存方式：memory、fs、Redis（依版本與 target）
Filesystem Scan官方目前文件說明預設 scan cache 使用 memory；DB 仍可存在磁碟
ARC ephemeral runner如果 cache 存在 Pod 臨時檔案系統且沒有持久化機制，Pod 結束後即失去；實際取決於 mount／runner 設定

02 / 把下載與掃描拆開

CACHE="$PWD/lab-cache"
trivy --cache-dir "$CACHE" fs --download-db-only
trivy --cache-dir "$CACHE" --version
trivy --cache-dir "$CACHE" fs --scanners vuln \
  --skip-db-update ./project

第一次準備成功後才跳過更新。對不存在或不相容的 DB 不應直接跳過；遇到錯誤先停止並核對。這只停止漏洞 DB 更新，不代表 Java DB、其他網路查詢或版本檢查也停止。

Flag停止或改變的行為
--skip-db-update跳過漏洞 DB 更新
--skip-java-db-update跳過 Java index DB 更新
--skip-check-update跳過 checks bundle 更新
--offline-scan停止某些套件辨識的遠端查詢；可能降低覆蓋率
--download-java-db-only預先準備 Java index DB
--db-repository更換漏洞 DB OCI 來源
--java-db-repository更換 Java DB OCI 來源

真正隔離網路需準備掃描所需資料、處理版本／遙測等額外請求（依版本 help），並在受控環境實際驗證。單獨 offline-scan 並不能保證零網路流量。

03 / 多 Runner 的三種設計

方案取捨
每個 Job 直接下載簡單，但 ephemeral job 重複下載、可能遇限流
每個 Job 還原同一 DB cache snapshot降低重複下載；要做新鮮度、版本相容與 cache key 控制
中央更新 DB，內部 OCI Registry 分發統一對外連線與版本治理；仍要驗證媒體類型、權限、TLS、保留策略

避免多程序任意寫同一個 filesystem cache；官方文件有 lock／cache 併發限制。可以使用各 job 的獨立目錄、由中央發布版本化 DB snapshot。Harbor 只是候選方案，不代表目前已驗證。

trivy --cache-dir ./lab-cache fs \
  --db-repository registry.example.com/security/trivy-db:2 \
  --download-db-only

範例網址不是可用公司位址。需事先以支援 OCI artifact 的工具同步官方 artifact、保留 media type，確認 TLS 信任及讀取授權；不能當一般 Docker image 任意重包裝。

04 / 故障定位

觀察下一步
DB 下載 429查實際 registry、限流與併發；改用受控 cache/mirror
x509 unknown authority核對企業 CA、proxy TLS；不要將 insecure 當正式方案
DB schema 不相容核對 CLI 版號、metadata Version 與 DB tag
skip update 後錯誤查 cache-dir 是否一致、DB 是否準備成功
同一 commit 結果不同對照 DB metadata、CLI 版本、設定與輸入清單

清除 cache 前先記錄 metadata 與錯誤，避免破壞其他 job；以下只針對自己的 lab-cache。

trivy --cache-dir ./lab-cache clean --scan-cache
# 只有需要重建漏洞 DB 時才做：
trivy --cache-dir ./lab-cache clean --vuln-db

理解驗收

已使用 --offline-scan，但第一次執行還在下載 vulnerability DB，是否矛盾？

完成自己的推論後，查看解析

不矛盾；offline-scan 與 DB 更新控制不同。先預下載，再依 scanner 需求設定 skip flags。

100 個 Pod 共用相同 DB repository 是否代表它們共用本機 DB？

完成自己的推論後，查看解析

否。Registry 是下載來源；每個 Pod 的本機 cache 是否共用取決於實際掛載／還原方式。

本堂回顧

  • DB 與 scan cache 分開管理。
  • 預先下載與掃描可拆開；跳過更新需要可用 DB。
  • 離線模式不是單一 flag。
  • 中央 DB 分發方案需要驗證新鮮度、授權及併發。
