PHASE 06 / LESSON 15

Operations：版本控管、資料庫更新與持續掃描

本堂目標

能定義維運責任、觀測指標、重新掃描、分批導入與 rollback，形成可持續的企業服務。

01 / 為什麼每次 CI 跑一次還不夠？

一個 service 上週部署、今天新增公開漏洞公告，即使 repo 沒有任何 commit，風險也可能改變。需要把 CI 當成發現的入口之一，另建立對已部署版本的 dependency inventory 或可重現輸入的定期重掃。

每次 build：保存 commit、解析依賴與 report
↓ 建立可追溯 evidence
部署版本 ↔ 已保存依賴 snapshot / SBOM
↓ 新 DB 發布或定期重掃
新／變更的 findings
↓ 通知 owner、評估與修補
修補後重建、重掃、驗證部署版本

重新掃描原始 repo 目前分支不等於掃描當前部署版本。只轉換舊 JSON 不會重新對照新 DB；可用支援的 SBOM 再掃，或重掃保存的已解析輸入，驗證其元件與 scope 相符。本課不要求 Image Scan，也不聲稱 OS 漏洞覆蓋。

02 / 版本要分四層

版本控制方式
CLI binary核准 release、checksum／簽章、OS/arch；升級先測 fixture
DB snapshotschema、artifact digest 或可追溯 metadata、UpdatedAt；依相容性及 freshness 更新
Policy/config受控 commit/version，例外另有 owner 及有效期
Dependency inputsource SHA、restore context、lockfile hash、build/deploy identity

固定 CLI 不等於固定漏洞 DB；固定 schema tag :2 不等於固定 DB 內容。重現歷史報告需保存當時輸入、DB snapshot（或可重取的 digest）、設定及工具版本；新資料重掃則刻意採用新 DB。

03 / 中央 DB 維運

可能方案：受控 updater 從官方 OCI 分發取得 DB，檢查 metadata、完整性、schema、下載成功與已知 fixture，再發佈 snapshot 或內部 Registry。Job 取得已驗證快照，使用獨立 cache directory，依策略更新。只同步 registry tag 而不檢查 DB freshness 仍可能長期使用舊資料。

狀況建議處置
更新成功記錄來源、digest/metadata、時間及 fixture 結果
更新失敗但上一份仍符合政策是否暫用需明確授權；告警、記錄、重試與補掃
DB 超出允許年齡標 STALE，不宣稱結果為最新；依政策停止或轉 REVIEW
CLI 新版不相容保留已核准相容版本及 rollback；不能永遠凍結過期 DB
大量 runner 同時下載節流、分發快照、獨立本機 cache、觀察 registry 限流

freshness 門檻（例如多少小時）及排程頻率需依實際風險、網路能力與組織要求制定；本課不擅自指定。

04 / 觀測指標不是漏洞總數

指標定義
Scan success rate成功執行／應掃且已嘗試；另統計 skipped 或未觸發
Coverage已核對依賴／expected inventory；未知分母獨立列出
DB age現在時間 − DB UpdatedAt，非下載時間
Scan duration按 runner class、語言、repo 規模區分 p50/p95
Findings按 severity、fixability、scope、policy decision；明確計算 finding rows 或 unique IDs
Exception backlog有效、將到期、已過期及待審查
Deployment gate outcomesALLOW／BLOCK／REVIEW、scanner failures、authorized bypass

例如漏洞數從 10 增到 30，可能是 DB 新增或套件覆蓋改善，不一定表示風險變差；搭配 input scope、DB version 與 coverage 解讀。Metrics 不應把每個 CVE/commit/完整路徑變成高基數 label；詳細報告另存受控資料系統。

05 / 分批導入與回復策略

階段進入下一階段的證據
本地受控 CLI PoC正負樣本、flags、DB、report、exit code 正確
代表性 repos report-only多種語言、lockfile、workspace、runner／workflow 分支已驗證；不硬寫死樣本
共用 action/workflow 小範圍試行artifact、coverage、failure handling、權限及負向測試通過
分批啟用 gatepolicy 取得核准，owner/SLA/例外流程可操作，驗證真正阻擋部署
擴大與長期營運持續 freshness、覆蓋、故障告警、版本更新與定期重掃

rollback 不應刪除歷史報告或偷偷取消安全檢查；可由核准程序切換上一個可信 action/CLI/policy 版本或短期 report-only，記錄受影響範圍與後續補掃。工具供應鏈本身需版本與來源控管。

06 / Final Practice：提出一份可驗證的整合方案

選取至少一個現有代表性 repo，再挑一個有不同依賴格式或 Runner 的 repo。提出：dependency preparation、scan target、CLI/config、DB lifecycle、raw report 與 coverage、gate 插入點、錯誤策略、例外及重掃方式。使用受控版本與去識別報告驗證，而不是把範例直接套到 prod。

完成條件

能在沒有現成 command 的情況下解釋設計、找到錯誤原因並提出可重現驗證；能說清楚未支援／未實測範圍。課程閱讀完成不自動等同企業上線。

理解驗收

某服務沒有新 commit，但 DB 新增 CVE。只掃 PR 是否足夠？

先自行回答，再查看解析

不足。須對應已部署版本的依賴證據，定期或事件驅動重新掃描。

同一 repo 兩次掃描漏洞數差異很大，如何證明原因？

先自行回答，再查看解析

對照 CLI、DB snapshot、policy、input/coverage、scope 及 finding keys，逐一隔離變因。

DB updater 故障，cache 仍有舊資料。怎麼判斷是否允許部署？

先自行回答，再查看解析

依核准 freshness 與 failure policy、相容性、例外及告警條件決定；不能默認安全。

本堂回顧

  • 持續重掃需對應實際部署版本。
  • CLI、DB、policy、dependency input 是獨立版本。
  • 維運要監測 freshness、coverage 與失敗，不只漏洞數。
  • 分批 rollout 與 rollback 需保留安全證據。

主要來源：Databases · Cache · Reporting · Secure use。範例是教學及待驗證設計，非公司 Runner 實測；請以核准版本的 CLI help 與實際 workflow 核對。

有不清楚的地方，可將去識別後的命令、報告或推論帶回對話討論。
