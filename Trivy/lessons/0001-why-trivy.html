PHASE 01 / LESSON 01 · 第一性原理 · 只需理解既有 GitHub CI/CD

部署成功，
就代表相依套件安全嗎？

你已經有 GitHub Actions、Secret Scanning、E2E Test，也能順利將版本部署到 Kubernetes 或 IIS。這堂課先不安裝工具，只回答一個問題：這些檢查都通過，為什麼仍可能需要 Trivy？

本堂目標
  • 能說出「程式可以執行」與「使用的第三方套件沒有已知漏洞」的差別。
  • 能解釋 Trivy 如何幫 CI 新增一種安全訊號，以及它無法保證什麼。
  • 遇到掃描零筆結果時，不會直接下「安全」結論。

先備：知道應用程式會引用 NuGet、npm 或 pip 套件即可。正式 CLI 操作安排在 Phase 02。

01 / 從你熟悉的部署情境開始

假設一個 WES 後端服務使用 NuGet 第三方套件。開發者打了 release tag，GitHub Actions 編譯成功；E2E Test 全部通過；Argo CD 將新版本部署到叢集。

這只能證明：建置與受測的功能流程符合當時的檢查條件。它沒有回答「這次編譯進去的第三方套件版本，是否有公開通報的已知安全漏洞」。

假設某個套件版本之後被公開通報有問題，應用程式可能仍然編譯成功、API 仍回應 200、E2E 仍通過。這不是測試工具失效，而是它們問的問題本來就不同。

建立第一個因果關係

因為 CI 的 Build / E2E 並不一定比對套件的漏洞資料，所以我們需要另一種檢查：把實際使用的套件名稱與版本，拿去對照已知漏洞資訊。這類檢查稱為 Vulnerability Scanning；檢查軟體相依套件的風險時，常歸在 SCA（Software Composition Analysis）範疇。

02 / Trivy 是扮演什麼角色？

Trivy 是開源安全掃描工具。就我們目前的導入 Mission，先聚焦它的套件漏洞掃描，而不是一開始就研究它所有功能。

Figure 01 · 這個問題需要四個資料環節

  1. 輸入：專案的套件清單／Lockfile，或建置完成的 Container Image。
  2. 辨識：Trivy 讀取輸入，取得它能辨識的套件名稱與版本。
  3. 比對：Trivy 利用漏洞資料，尋找這些套件版本是否對應已知問題。
  4. 輸出：把發現的漏洞、嚴重度及可用的修補版本等資訊整理成結果。

箭頭語意是「前一階段提供資料給下一階段」，不是每一步都會執行你的程式。資料不足時，後續比對自然不完整。查看流程速查。

你之後可以讓 GitHub Actions 在部署前執行 Trivy，但要先記住：Trivy 負責產生風險訊號；是否停止部署，是我們另外訂的 CI Policy。掃描和阻擋不是同一件事。

03 / 它和現有工具在查什麼？

現有檢查它主要回答它不保證
Build程式能否編譯／封裝？套件版本沒有已知漏洞
E2E受測使用流程是否符合預期？所有第三方套件安全
Secret Scanning是否暴露密碼、Token 等機密？套件是否有公開漏洞
Trivy 漏洞掃描辨識到的套件版本是否命中已知漏洞？程式邏輯沒有漏洞、功能正常

Trivy 也能處理 Secrets、Misconfiguration、License 等議題；只是本次最小 PoC 先明確限定在 Vulnerability Scanning，避免同時測太多功能，弄不清結果代表什麼。

04 / 第一個容易誤判的地方

假設 GitHub CI 只把這份檔案交給 Scanner：

# requirements.txt（教學情境，不代表有漏洞）
requests>=2.28

這行只是在要求安裝符合條件的套件；它沒有告訴你最終安裝的精確版本，也沒有列出安裝過程帶入的間接套件。因此，即使 Trivy 執行沒有錯誤，也不能據此宣稱部署環境的所有相依套件都被檢查。

之後你會看到兩種不同問題：

  • 套件未被辨識：掃描輸入不足或格式不對，沒有完整套件資料可供比對。
  • 套件已辨識，但未發現已知漏洞：至少辨識階段有資料，但仍有資料庫、版本範圍和覆蓋範圍的限制。
重要界線：「沒有發現漏洞」不等於「證明沒有漏洞」。尤其在 Lockfile 缺失、掃描目標選錯或資料庫更新失敗的情況下，零筆結果可能沒有實際安全意義。

05 / 檢查你是否建立了正確的理解

情境 A：某個 release 的 Build、E2E 與部署都成功。現在能說什麼？

情境 B：Trivy 輸出 0 個漏洞，但依賴清單只有一行範圍版本。下一步應先確認什麼？

06 / 本堂最小結論

  • Build、E2E、Secret Scanning 與套件漏洞掃描，回答不同問題。
  • Trivy 要先取得「套件名稱＋版本」，才有條件比對公開漏洞。
  • 掃描成功、零筆漏洞與套件辨識完整，是三個不同概念。
  • Scanner 產生風險資訊；CI Gate 才決定是否停止部署。

如果不確定，回到 ChatGPT 用自己的話重述「為什麼 E2E 通過不夠」。閱讀完或答對單題不會自動記錄為理解通過。
