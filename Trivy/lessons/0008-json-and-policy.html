PHASE 04 / LESSON 08 · STRUCTURED OUTPUT

JSON、SARIF、SBOM 與掃描政策

本堂目標

能解析 JSON 結構、保存證據、區分資料過濾、例外與阻擋政策，並從輸出追蹤一筆漏洞。

01 / 為什麼不只用 Table？

Table 適合人看，但 CI 需要穩定地取得套件清單、漏洞欄位、目標與結果。JSON 是結構化資料，適合留存、統計和轉換。

trivy fs --scanners vuln --list-all-pkgs \\
  --format json --output ../report.json --exit-code 0 .

以下是縮短的示意 JSON，只展示重點，不是完整 schema 或實測結果。

{
  "SchemaVersion": 2,
  "ArtifactName": ".",
  "ArtifactType": "filesystem",
  "Results": [
    {
      "Target": "requirements.txt",
      "Class": "lang-pkgs",
      "Type": "pip",
      "Packages": [
        {
          "Name": "requests",
          "Version": "2.31.0"
        }
      ],
      "Vulnerabilities": [
        {
          "VulnerabilityID": "CVE-2024-35195",
          "PkgName": "requests",
          "InstalledVersion": "2.31.0",
          "FixedVersion": "2.32.0",
          "Severity": "MEDIUM",
          "Status": "fixed"
        }
      ]
    }
  ]
}
欄位用途
SchemaVersion報告 schema 版本；與 DB schema、CLI 版號不同
ArtifactName / ArtifactType本次掃描目標資訊；另行保存 commit SHA
Results[]各 target／類型的結果組
Target / Class / Type來源路徑、結果類別與生態系
Packages[]已辨識套件；部分版本 list-all-pkgs 預設不同
Vulnerabilities[]符合目前篩選規則的發現；可能缺少或為空
SeveritySource / CVSS / VendorSeverity理解評級來源與差異；可能缺少
PkgID / PkgIdentifier / PkgPath / Relationship若版本與格式提供，可協助確認套件身分、路徑或依賴關係
DataSource / PrimaryURL / References追溯漏洞公告或詳細資料；可能缺少

同一 CVE 可出現在多個 target 或套件中；漏洞列數不是全域 unique CVE 數，統計前要定義唯一鍵與目的。報告 JSON 不能自動代表整個 repo 的完整 inventory。

02 / 用 jq 讀出三種訊號

以下用 Bash 與 jq，PowerShell 可以用 ConvertFrom-Json。先驗證報告檔確實由本次成功掃描生成，再查內容。

jq -e 'type == "object" and has("SchemaVersion")' ../report.json
jq -r '.Results[]? | [.Target,.Type,((.Packages // [])|length)] | @tsv' ../report.json
jq -r '.Results[]? | .Target as $t | .Vulnerabilities[]? | [$t,.VulnerabilityID,.PkgName,.InstalledVersion,.Severity,(.FixedVersion // "")] | @tsv' ../report.json
jq '[.Results[]? | .Vulnerabilities[]?] | group_by(.Severity) | map({severity:.[0].Severity,count:length})' ../report.json

第一條只做基本格式檢查，不證明報告符合完整 schema 或掃描成功。第二條看各 target 的套件清單數，第三條列出命中，第四條按 severity 統計發現列。缺少 Results/Packages 必須另行判斷，不可只用 // [] 得出的 0 作為 gate 通過證據。

03 / 選擇輸出格式

格式適合場景與限制
table人讀快速摘要及漏洞明細
json原始結構化結果，後續解析與轉換
sarif安全發現交換；GitHub Code scanning 需相應功能與權限
cyclonedx / spdx-jsonSBOM 元件清單與相依資訊（支援範圍因格式、版本而異）；不等於完整漏洞報告
template自訂 HTML／文字等格式；僅用可信模板
trivy convert --format table --severity HIGH,CRITICAL ../report.json
trivy convert --format sarif -o ../report.sarif ../report.json
trivy convert --format cyclonedx -o ../report.cdx.json ../report.json

convert 不重新掃描，不會補出原 JSON 沒收集的資料。若 SBOM 要帶漏洞資訊，須確認 scanner 與該格式支援；例如 CycloneDX 掃描時可能需要明確啟用 vuln。

04 / Filter、例外、Gate 三者分工

設定實際影響
--severity HIGH,CRITICAL只保留符合嚴重度的漏洞列
--ignore-unfixed依漏洞修補狀態排除未修補的發現；不等於安全
--ignore-status排除指定漏洞狀態；不是 severity
--ignorefile / --ignore-policy / VEX針對已知發現做抑制或適用性判定，需管理理由、scope、owner、期限
--show-suppressed依版本顯示被抑制結果；JSON 欄位可能為實驗性
--exit-code當有符合條件的發現時選擇退出碼；不消除漏洞

建議先在受控、無非預期 suppressions 的設定下保存所有 severity 的 JSON，再由獨立政策選擇阻擋條件；UNKNOWN、無修補版本、既有漏洞仍可追蹤。若直接用 scanner 作 gate，必須清楚篩選後的報告不再是完整發現清單。

trivy fs --scanners vuln --severity HIGH,CRITICAL \\
  --ignore-unfixed --exit-code 1 .

這是政策示範，不是企業政策建議。這條命令可能同時隱藏無修補的 CRITICAL；exit 1 又可能與 scanner failure 混淆。若採獨立 gate，先使用 exit 0（findings 不阻擋），仍應檢查真正錯誤、報告與 inventory 覆蓋。

05 / CI 需要記錄的證據

保存 fresh report、有效設定、CLI 版本、DB metadata、commit SHA、掃描目標、實際退出碼與預期套件覆蓋。不要在掃描失敗時讀取上一個 job 殘留的 report。對 output 的存取權限與留存期限也需要規範。

本堂回顧

  • JSON 以 Results 分組，Packages 與 Vulnerabilities 是不同證據。
  • 欄位缺失不應被靜默當成零。
  • convert 只能使用原報告資料。
  • Filter、suppression 與阻擋政策是不同責任。
