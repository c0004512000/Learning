PHASE 06 / LESSON 13

CI/CD Integration：掃描時點與共用 Workflow 契約

本堂目標

能依真正依賴解析與部署副作用選擇位置，設計可重用、可審計的 scan/report/gate 介面。

01 / 先確認何時資料存在、何時部署發生

Checkout：固定 commit SHA
↓ 使用實際 build 條件 restore/install
已解析依賴：lockfile 或 freeze
↓ Trivy filesystem scan
JSON + inventory + scanner status
↓ Policy 判斷
允許後才執行需保護的 publish／deploy 動作

這是依賴關係，不是硬性規定所有 job 必須同樣排序。若 lockfile 已提交且可證明實際 install 使用它，可以在 install 前掃；若必須 restore 才生成，掃描就要等 restore。不能為了方便另跑不等價的 restore。

02 / 對照現有兩種 workflow 路徑

情境觀察與設計
Kubernetes Docker build固定歷史版本的 build workflow 將 docker build/push 放在同一步；dependency restore 可能在 Dockerfile 內。掃描已提交且有效的 lockfile，或在獨立 dependency-prep 階段用相同解析條件生成輸入；證明與 build 一致。不是改成 Image Scan。
GitOps deploy更新 Helm repo 會導致 Argo CD 部署；若要求部署 gate，必須在 GitOps 變更前完成並驗證同一 release SHA 的證據。
Windows backend歷史 workflow 有 nuget/dotnet restore，後續 publish profile 或 DeployOnBuild=true 可能已部署。掃描需放在任何部署副作用之前。
Windows frontend歷史 workflow 的 npm install、build、msdeploy 在同一個 deploy step；需要拆分或將 gate 插入真正部署前且依賴已解析的位置。

依據 固定修訂的 workflow 來源；這是靜態閱讀，不是當前生產設定或執行證明。實際導入需檢查更多 microservice 與 workflow，不能將單一 repo 路徑硬編碼。

03 / Composite Action 與 Reusable Workflow

方式責任與限制
Composite Action在 caller 的現有 job/runner/workspace 執行多個 step；適合直接使用 restore 產物。inputs/outputs 定義 step 介面。
Reusable Workflow由 jobs.<id>.uses 呼叫另一份 workflow，可有多個 job 與獨立 runner；不能像 step 一樣插入同一 job。需明確傳遞來源、artifact 及 outputs。
獨立 Gate Job集中讀 scan job output／artifact 並做 policy 判斷；不能假設共享 filesystem。

若 scanner 與 restore 在不同 job，要移交足夠的解析證據（包含 workspace context），或在 scan job 重建並驗證等價性。不能只傳一個相對路徑給另一台 Runner。

04 / 最小 contract

方向欄位與意義
Inputsource SHA、scan root、dependency scope、核准 scanner/config 版本、預期 inventory 來源
Scan outcomeSUCCESS／FAILED，另存原始 scanner exit code；不能以 vulnerability count 代替
CoverageVERIFIED／INSUFFICIENT／UNKNOWN／明確授權 NOT_APPLICABLE；保留原因
Evidenceraw report、CLI/DB 版本、有效設定、run/attempt、來源 commit、artifact checksum
Policy decisionALLOW／BLOCK／REVIEW；與 scanner outcome 分離，另含 policy version、reason
Caller依 decision 控制後續 build/deploy；報告存取權限及保留期限

不要接受 caller 隨意指定忽略 CVE、任意 policy 文件或可執行命令。掃描 repo 內的設定屬不可信輸入；中央配置與例外清單由受控位置供應。拒絕越界 scan-root、symlink 逸出或錯誤 commit/artifact 關聯；依平台實際驗證。

05 / Linux：最小 scan step 的核心

此片段是 Bash 教學範例：假設已 checkout、restore 完成、受控 cache/config/empty ignore file 與 scan root 都經驗證。不是可直接部署的共用 action。目的是保留真正的 exit code，不用 || true 隱藏失敗。

out=$(mktemp -d "$RUNNER_TEMP/trivy-report.XXXXXX")
printf "report_dir=%s\n" "$out" >> "$GITHUB_OUTPUT"
if trivy --config "$TRUSTED_CONFIG" --cache-dir "$CACHE" fs --scanners vuln --skip-db-update --ignorefile "$TRUSTED_IGNORE" --list-all-pkgs --severity UNKNOWN,LOW,MEDIUM,HIGH,CRITICAL --format json -o "$out/report.json" --exit-code 0 "$SCAN_ROOT"; then
  rc=0
else
  rc=$?
fi
printf "scanner_exit=%s\n" "$rc" >> "$GITHUB_OUTPUT"
if [ "$rc" -ne 0 ]; then
  printf "scan_outcome=FAILED\n" >> "$GITHUB_OUTPUT"
  exit "$rc"
fi
if ! jq -e 'type == "object" and has("SchemaVersion")' "$out/report.json" >/dev/null; then
  printf "scan_outcome=FAILED\n" >> "$GITHUB_OUTPUT"
  exit 1
fi
printf "scan_outcome=SUCCESS\n" >> "$GITHUB_OUTPUT"

此 JSON check 只做最低限度驗證，未驗證完整 schema 或 coverage。正式設計還須保存 DB metadata、input identity、有效設定及 coverage 結果；清理非預期 TRIVY_*、避免 repo 設定或不可信 VEX 影響結果。Windows 用原生 PowerShell 實作相同 contract，不盲目移植 Bash。

06 / Job dependency 與 Artifact

jobs:
  prepare-and-scan:
    # checkout / dependency preparation / scan / upload
    # 實際 jobs、runner、actions 與 inputs 由核准流程提供
  policy-gate:
    needs: prepare-and-scan
    if: ${{ !cancelled() }}
    # 驗證 needs result、artifact identity、coverage、policy
  deploy:
    needs: [prepare-and-scan, policy-gate]
    # 僅允許明確通過的狀態；實際 deploy job 另定義

上面是架構示意，不是完整合法 workflow（省略 runs-on/steps）。正式 gate 在 scan failure 或 skipped 時不得因 output 空白而 ALLOW。報告上傳可在未取消時執行，缺檔需明確分類。跨 job artifact 按 run/attempt、SHA、scope 和 checksum 驗證，不接受任意舊報告。

固定第三方 action／reusable workflow 的可信 commit SHA 或公司核准等價機制；最小 token 權限，不在 untrusted PR code 上提供部署 secrets 或具高權限的 persistent runner。Restore 本身可能執行 scripts/MSBuild targets，也需隔離。

理解驗收

掃描 job 只有 checkout，但 .NET lockfile 是另一個 build job restore 才產生。應如何處理？

先自行回答，再查看解析

在 restore 後同 job 掃描，或明確移交解析資料並驗證同一 SHA/context；不能假設 job 共享 workspace。

Windows MSBuild 使用 DeployOnBuild=true，在其後加 Trivy gate 是否足夠？

先自行回答，再查看解析

不夠。MSBuild 可能已完成部署；需將 scan/gate 放在該副作用之前。

本堂回顧

  • 掃描時點由可用資料與需要阻止的副作用決定。
  • Composite action 與 reusable workflow 的 workspace 責任不同。
  • scan、coverage、policy decision 需分離。
  • 共用介面不寫死單一 repo、語言或 runner。

主要來源：Reuse workflows · Artifact · Secure use · Trivy CLI。範例是教學及待驗證設計，非公司 Runner 實測；請以核准版本的 CLI help 與實際 workflow 核對。

有不清楚的地方，可將去識別後的命令、報告或推論帶回對話討論。
