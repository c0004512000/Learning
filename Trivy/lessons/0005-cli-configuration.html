PHASE 02 / LESSON 04 · CONFIGURATION

配置與 Flags：如何知道實際生效的是什麼

本堂目標

能解釋 CLI／環境變數／YAML 的優先順序、有效掃描範圍與過濾條件。

01 / 相同命令為何可能有不同結果？

Trivy 不只讀取你眼前寫的 flags。它還可能讀取目前工作目錄的 trivy.yaml、環境中的 TRIVY_*，以及預設 .trivyignore。掃描目標與設定載入位置不是同一件事。

CLI 明確指定的 Flag（最高）
↓ 未指定時由下一層提供
Environment Variable，例如 TRIVY_SEVERITY
↓ 未指定時由下一層提供
Configuration File，例如 trivy.yaml
↓ 未指定時使用
CLI 版本的預設值

對清單或空值不假設合併行為；以實際版本測試。環境變數命名通常將 flag 的連字號改底線並大寫，加上 TRIVY_。

02 / 用三種方式設定同一個掃描

trivy fs --scanners vuln --severity HIGH,CRITICAL .

TRIVY_SCANNERS=vuln TRIVY_SEVERITY=HIGH,CRITICAL trivy fs .

第二個是 Bash 的單次程序環境變數；PowerShell 須用 $env:TRIVY_SCANNERS = 'vuln' 等方式設定，再視需要清除，避免影響後續命令。

同樣也能將設定保存至 YAML：

scan:
  scanners:
    - vuln
severity:
  - HIGH
  - CRITICAL
format: json
trivy fs --config ./policy.yaml --output ../report.json .

設定檔集中管理共同參數；不要允許受掃 repo 自行改寫中央阻擋政策。受控配置可放 workspace 外、由 CI 指定絕對路徑。敏感值不得寫進 repo 或 log。

03 / 不同 flag 改變不同環節

類型常見 flag 與注意事項
輸入範圍--skip-dirs、--skip-files；可能導致套件完全不被辨識
套件辨識--pkg-types、--include-dev-deps（依生態系支援）、--detection-priority（precise/comprehensive 有取捨）
發現過濾--severity、--ignore-unfixed、--ignore-status、--ignorefile；不是改變套件版本
資料取得--cache-dir、--db-repository、--skip-db-update、--offline-scan；下一階段解釋
報告--format、--output、--list-all-pkgs；不會補出原本未被辨識的套件
執行--exit-code、--timeout、--debug、--quiet；避免初次除錯就隱藏訊息

04 / 驗證優先順序的小實驗

建立一份獨立的 policy.yaml，severity 設為 HIGH/CRITICAL。使用同一測試目標及已準備的 DB 比較：

trivy fs --config policy.yaml .
TRIVY_SEVERITY=LOW trivy fs --config policy.yaml .
TRIVY_SEVERITY=LOW trivy fs --config policy.yaml --severity MEDIUM .

預期三次採用不同 severity；若樣本沒有相關漏洞，不能只看總數驗證，應挑已知符合該級別的案例並查看有效設定與輸出。實驗不需要修改正式 pipeline。

本堂回顧

  • 設定優先順序為 CLI → 環境變數 → YAML → 預設。
  • 工作目錄決定預設設定檔位置；target 是另一個概念。
  • 掃描範圍、報告篩選與退出碼不要混為一談。
