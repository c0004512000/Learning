PHASE 06 / LESSON 14

Policy Gate：如何阻擋而不丟失風險資訊？

本堂目標

能依掃描品質、severity、修補狀態、baseline、例外與曝險制定可審計政策，區分工具錯誤和風險決策。

01 / Scanner 回答事實，政策回答是否允許

假設一份完整報告有 1 筆 CRITICAL 無修補、2 筆 HIGH 有修補、5 筆 LOW。是否阻擋不是 Trivy 自動替企業決定的事情。用 --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 會同時排除某些發現，導致報告無法保留完整風險。

Scanner：保留所有 in-scope 發現及 Packages
↓ 先驗證執行、資料新鮮度與 coverage
有效報告
↓ 政策：依規則評估每筆發現與例外
ALLOW／BLOCK／REVIEW ＋理由
↓ Caller 根據明確 decision 控制部署
原始證據與政策評估結果分開保存

02 / Severity、Fixability、Exploitability

維度問題
Severity技術嚴重程度；UNKNOWN 不是 LOW 也不是安全
FixedVersion / Status是否有已知修補；有修補不等於升級相容
Exploitability / 曝險實際使用方式、可達性、是否有已知利用證據；Trivy 套件命中本身不證明可利用
Baseline是已知存量、同一 commit 的新 DB 發現，還是變更引入？
Scoperuntime/build-time、直接/間接、服務/環境及依賴版本

LOW 仍應追蹤，可安排 SLA；UNKNOWN 需要查公告、評級來源和適用性，不應自動忽略。無修補版本的 CRITICAL 可能需要隔離、替代套件或風險接受。這些是政策維度，不預先替公司決定門檻。

03 / 先處理不可信的掃描

掃描結果政策輸入處理
正常且 coverage 符合要求進入風險規則
執行失敗／DB 太舊／報告無效標記 operational failure，不視為 CLEAN
覆蓋不足或未知標記 COVERAGE_ISSUE，依授權 rollout 策略決定
明確不適用需有依據與 owner；不可由 repo 隨意宣告

Report-only 可以不因漏洞發現阻擋，但仍要顯示掃描失敗。Blocking mode 的 fail-open／fail-closed 應分別針對 scanner failure、coverage、policy violation 設定，並經組織核准。fail-open 不等於掃描通過；需告警、紀錄及補掃。

04 / 一個可推論的示範政策（非公司正式政策）

條件示範 decision
掃描失敗／coverage 未確認REVIEW 或依已核准 fail-closed 轉 BLOCK
新引入的 HIGH/CRITICAL、有修補、無有效例外BLOCK
無修補 CRITICAL 或 UNKNOWNREVIEW，指派 owner 調查
既有存量／MEDIUM/LOW依 SLA 追蹤；可依曝險升級
無政策命中且所有必要前提成立ALLOW

同一 CVE 多次出現不能只用 CVE ID 作全域 baseline。建議依專案、套件生態系、套件、版本、vulnerability ID、target/context 定義 finding key；升級後仍受影響的版本要另判，避免把所有後續漏洞用既有 baseline 永久放行。另將「DB 新增發現」與「程式變更引入」區分，不能只靠 Git diff 推論。

05 / 例外是有範圍、可到期的決策

Trivy 的 ignorefile／VEX 能抑制發現，但需區分 false positive、not affected、暫時接受風險、無修補版本。不要只留 CVE ID，至少記錄 scope、理由、證據、owner、核准人、到期日與複核條件。以下為中央政策資料的虛構示意，並非 Trivy 的 ignorefile 格式。

finding_id: CVE-YYYY-NNNN
project: example-service
ecosystem: nuget
package: Example.Library
version: 1.2.3
scope: runtime
reason: temporary risk acceptance
owner: service-owner
approved_by: security-reviewer
expires_on: YYYY-MM-DD
evidence: approved-ticket-reference

Trivy 的 .trivyignore 純文字與 YAML 支援不同；YAML 必須依版本明確使用 --ignorefile，格式、paths、expired_at 等查官方文件。VEX 是可利用性／適用性的標準化聲明，不是所有例外的替代品。可先保存未抑制報告，再由中央 gate 記錄例外，避免讓被忽略項目消失。

06 / 驗收 gate 的五組樣本

樣本驗證
可修復 HIGH是否按政策 BLOCK 並留報告
無修補 CRITICAL是否可見且正確 REVIEW／BLOCK
UNKNOWN是否保留並有處理路徑
已核准例外／已過期例外有效才允許、過期重新判定
DB 失敗／空 inventory／缺報告不得被誤判為 0 漏洞 ALLOW

另外測試 gate skipped/cancelled、artifact SHA 不一致、policy version 不一致。只有控制案例實際驗證部署動作未發生，才能聲稱 deployment gate 已生效。

理解驗收

CRITICAL 沒有 FixedVersion，--ignore-unfixed 後報告 0；你是否允許直接宣稱安全？

先自行回答，再查看解析

不可以。它可能只是被過濾，需保留原始發現並依曝險、替代方案、例外政策評估。

同一 CVE 已有 exception，但另一個 repo 新增相同漏洞。可以自動套用嗎？

先自行回答，再查看解析

只有例外明確包含該 repo、套件、版本、scope 且仍有效時才可套用；不可只靠 CVE ID 全域放行。

本堂回顧

  • Scanner output 與企業 policy 分離。
  • Severity、修補、曝險及 baseline 都是不同維度。
  • UNKNOWN／無修補漏洞仍需追蹤。
  • 例外必須可審計、限定 scope 與到期。
  • Gate 必須驗證失敗、缺資料與取消情境。

主要來源：Filtering · VEX · Reporting · GitHub secure use。範例是教學及待驗證設計，非公司 Runner 實測；請以核准版本的 CLI help 與實際 workflow 核對。
