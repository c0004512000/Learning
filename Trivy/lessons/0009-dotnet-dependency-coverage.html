PHASE 05 / LESSON 10

.NET 套件辨識：Restore 到底提供了什麼？

本堂目標

能區分 PackageReference、packages.config、lockfile 與 runtime 依賴，從實際 restore 結果證明 scanner 的覆蓋。

01 / 宣告版本與解析版本

專案可能只宣告 A，A 又需要 B。Restore 根據 target framework、套件來源、版本約束與相依規則選出實際版本。Trivy 不是 NuGet resolver；掃描能看到什麼，取決於交給它的資料。

.csproj / Directory.Packages.props：宣告及集中管理版本
↓ NuGet restore 解析
project.assets.json：建置所用解析結果；packages.lock.json：可選的依賴快照
↓ Trivy 讀取受支援的輸入
Packages[]：辨識的名稱、版本、來源
↓ 比對漏洞 DB
Vulnerabilities[]：符合報告條件的發現

以 A 1.0 → B 2.0 為例，只有 A 的宣告不足以證明 B 的實際版本。最新官方文件也列出 *Packages.props 支援，但只能取得其提供的資訊，不能用中央版本宣告替代完整 resolved inventory。

02 / 先看專案採用哪種套件管理格式

輸入可回答的問題
packages.config常見於舊式 .NET Framework；平坦的已列套件名稱與版本，無法重建完整 dependency graph
packages.lock.jsonPackageReference restore 的解析依賴，包含直接及間接依賴、不同 target framework；支援 graph
*.deps.json建置／publish 後的 runtime 依賴資訊，不包含所有 build/dev dependencies
*Packages.props集中版本宣告；不代表每筆都被使用，也不保證傳遞依賴完整
obj/project.assets.jsonNuGet restore 的交叉核對證據；不要假設它必然是 Trivy 支援的掃描輸入

.NET Framework 4.8 也可能採用 PackageReference，.NET 9 也可能有不同組態。以檔案與 restore 工具為準，不可只靠 .NET 大版本分支。

03 / .NET 9：最小可重現的 restore 與 lockfile

在核准的測試 clone 中，使用與正式 build 一致的 SDK、NuGet source、configuration、framework、RID（如適用）及 restore flags。先確認現有 lockfile 是否由 repo 管理。

dotnet --info
dotnet restore ./Demo.sln --use-lock-file
dotnet list ./Demo.sln package --include-transitive

這是 .NET 9 CLI 語法，--use-lock-file 可能新增或更新專案旁的 lockfile。在已有受控 lockfile 時使用 dotnet restore ./Demo.sln --locked-mode 驗證版本沒有漂移；若需要重新產生，應在獨立工作區完成且記錄，不自動 commit 或覆蓋專案政策。不要對所有專案強加 locked mode。

trivy fs --scanners vuln --list-all-pkgs --format json -o ../dotnet.json .
jq -r '.Results[]? | .Target as $t | .Packages[]? | [$t,.Name,.Version] | @tsv' ../dotnet.json

在 PowerShell 可用 Get-ChildItem -Recurse -Filter packages.lock.json 找輸入，使用 ConvertFrom-Json 讀報告。比較每個 project/TFM/RID 的預期套件與 Trivy 對應 target，而非把整個 solution 的重複名稱加總。build 若再次 restore，應證明使用相同解析結果，或用已驗證的 no-restore 路徑。

04 / .NET Framework 4.8：packages.config

<packages>
  <package id="Example.A" version="1.0.0" targetFramework="net48" />
  <package id="Example.B" version="2.0.0" targetFramework="net48" />
</packages>

上例是虛構套件，目的是說明格式。既然名稱與版本已列出，Trivy 可以讀取它們，沒有必要為 packages.config 專案一律生成 lockfile。NuGet restore 仍需要在實際 build 流程成功完成，才能證明套件清單與建置一致。若混合兩種管理方式，分別核對。

nuget restore ./Legacy.sln
trivy fs --scanners vuln --list-all-pkgs --format json -o ../legacy.json .

此命令須在有相應 SDK／NuGet 工具與 feed 的核准環境執行。掃描不需安裝全部 Framework runtime，但不能藉此宣稱 Windows runtime 或 OS 已掃描。

05 / 如何判定覆蓋，而不是只計數

情境應如何驗證
既有 .NET 9 樣本：0/9 → 9/9確認九個 expected package/version 在對應 target；只表示特定樣本的辨識結果
Framework 4.8 樣本：2/2確認兩筆 packages.config；不代表整台 Windows 主機安全
兩個 project 使用相同套件不同版本保留 project/target context，不能只依套件名稱去重
沒有 lockfile、只有 props檢查是否可取得實際 restore 結果；不得因少量命中而宣稱完整
私有 NuGet 套件確認可辨識名稱與版本；公共 DB 未命中不證明私有程式碼無漏洞

可計算 coverage = matched expected identities / expected identities，但先定義 identity（ecosystem、名稱、版本、project/TFM context）以及排除項。若分母未知，標為 UNKNOWN_COVERAGE，不是 100%。

理解驗收

中央 props 列出 A、B、C，實際專案只引用 A，且 A 需要 D。可以把 props 的三筆當完整清單嗎？

先自行回答，再查看解析

不能。需要 restore 解析結果；B、C 可能未使用，D 可能是間接依賴。

Framework 4.8 專案已有 packages.config。是否必須套用 .NET 9 的 lockfile 生成方式？

先自行回答，再查看解析

不必。先確認套件管理格式；用 packages.config 的名稱與版本及實際 restore 作交叉核對。

本堂回顧

  • Restore 選出依賴，Trivy 讀取可辨識輸入。
  • lockfile 與 deps.json 的觀察範圍不同。
  • 依套件管理格式分支，而不是依 .NET 版本硬寫規則。
  • coverage 需依 project/context 比對，不以漏洞數判斷。

主要來源：Trivy .NET · NuGet PackageReference · MSBuild Restore。範例是教學及待驗證設計，非公司 Runner 實測；請以核准版本的 CLI help 與實際 workflow 核對。

有不清楚的地方，可將去識別後的命令、報告或推論帶回對話討論。
