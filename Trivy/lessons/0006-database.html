PHASE 03 / LESSON 05 · DATABASE

Trivy DB：漏洞資料從哪裡來？

本堂目標

理解 advisory、DB 建置、OCI 分發、schema tag、metadata 與本機比對的關係。

01 / 為什麼掃描引擎不能單獨回答漏洞問題？

假設已辨識 requests 2.31.0。只知道套件名稱與版本，仍不知道哪些版本受漏洞影響。漏洞公告提供受影響範圍、修復版本及其他資訊；Trivy 將這些資料整理成可在本機快速查詢的資料庫。

公開漏洞資訊來源：GHSA、NVD、各套件生態系／發行版公告
↓ Trivy DB build pipeline 彙整、轉換
Trivy Vulnerability DB（依資料庫 schema 打包）
↓ 作為 OCI artifact 發布至 Registry／mirror
Runner 下載並解壓至 cache directory
↓ Scanner 使用套件身分與版本查詢
已知漏洞命中與報告

GHSA 是資訊來源，Registry 是分發媒介。 OCI Registry 能儲存不只是可執行 container image 的 artifact。下載 trivy-db 不會啟動 container，也不是把你的 source code 上傳去查詢 GHSA。部分 Analyzer 仍可能有其他網路查詢。

02 / 三種資料不要混用

資料責任
trivy-db漏洞比對資料，涵蓋受支援的 OS／語言套件
trivy-java-db輔助辨識 Java JAR artifact 的套件資訊，不是 Java 專用 CVE DB
trivy-checksMisconfiguration 的檢查規則 bundle；vuln-only 不需為此啟用 misconfig

03 / DB Repository 與版本

官方 CLI 文件列出的預設 vulnerability DB 來源含 mirror.gcr.io/aquasec/trivy-db:2 與 ghcr.io/aquasecurity/trivy-db:2（依安裝版本確認順序）。:2 是 DB schema tag，不等於 Trivy CLI 2.x，也不是固定日期的 DB。它可以指向更新的內容。

trivy fs --help
trivy --version
trivy --cache-dir ./lab-cache fs --download-db-only
trivy --cache-dir ./lab-cache --version

先建立專用測試 cache。download-db-only 不需 target，僅準備 vulnerability DB。version 在 DB 已存在時可顯示其版本與時間資訊；實際格式依版本。常見本機檔案是 lab-cache/db/trivy.db 和 lab-cache/db/metadata.json。

cat ./lab-cache/db/metadata.json

常見 metadata：Version（schema）、UpdatedAt（資料更新時間）、NextUpdate（下次檢查更新的時間資訊）、DownloadedAt（本機下載時間）。不能用下載時間替代資料本身的新鮮度，也不要把 NextUpdate 當成漏洞資料絕對有效期限。

04 / 什麼時候更新？

Trivy DB 專案建置頻率和 CLI 下載頻率是兩件事。CLI 依本機 DB 與更新條件判斷是否需要下載；同一個 tag 的 artifact 也會改變。舊 Commit 隔天掃出新 CVE，可能是 DB 新增公告而非程式碼改動。比較兩份報告時保留 CLI 版本、DB metadata、掃描參數、輸入版本。

建置與發佈：trivy-db 專案。

本堂回顧

  • 公告來源與 DB 分發來源不同。
  • Java DB 用於辨識，vulnerability DB 用於比對。

  • DB 資料時間與下載時間不同。
