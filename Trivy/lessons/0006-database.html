PHASE 03 / LESSON 05

Trivy Vulnerability DB：從漏洞公告到 Runner 的資料庫

本堂目標

能解釋 Trivy 為什麼需要外部漏洞資料、誰建立 DB、DB 實際是什麼檔案、從哪裡下載、為什麼下載來源是 Registry，以及 CLI 如何使用下載好的 DB。下一堂才深入 Cache 與更新的判斷。

01 / 已經知道套件版本，為什麼還要有 DB？

先從你熟悉的 requirements.txt 開始。假設某個專案只有這一行：

requests==2.31.0

Trivy 讀取檔案後，知道這個專案使用 Python 生態系的 requests 2.31.0。但只看版本號，無法知道該版本是否有已知漏洞。必須有人研究或發現漏洞、確認受影響的版本，並提供這些資訊。

例如 CVE-2024-35195 / GHSA-9wx4-h78v-vm56 是一個 requests 的真實漏洞公告。為了方便理解，把公告中與版本判斷有關的資訊縮成下面這張表：

資訊示例
套件生態系Python / PyPI
套件名稱requests
漏洞識別碼CVE-2024-35195
受影響版本小於 2.32.0
已修復版本2.32.0

這類對外發布的漏洞資訊通常稱為 Security Advisory（安全公告）。有了公告，Trivy 就能進行版本比較：2.31.0 符合受影響範圍，2.32.5 不符合，所以前者會命中這筆漏洞、後者不會。這不代表 2.32.5 沒有其他漏洞。

如果有數萬種套件和大量漏洞公告，逐次上網逐個查詢很慢，也很難維持結果一致。Trivy 的做法是：把各個來源的漏洞資訊預先整理成一份可下載的資料庫，讓掃描工具在本機查詢。

核心模型

CLI 負責辨識與比對；DB 提供已知漏洞和影響版本資料。只安裝 CLI 不等於已經有可用的 Vulnerability DB。

02 / 漏洞資料從哪裡來？

沒有一個來源必然涵蓋所有套件、所有平台和所有漏洞。Trivy DB 的維護專案會從多種來源收集資料。

名稱這是什麼？
CVE（Common Vulnerabilities and Exposures）一套漏洞識別碼制度。CVE-2024-35195 是識別碼，不是下載漏洞 DB 的網站。
GHSA（GitHub Security Advisory）GitHub 安全公告體系；包含各語言套件的公告及受影響版本等資訊。GHSA ID 也可識別公告。
NVD（National Vulnerability Database）美國 NIST 維護的漏洞資料庫，提供 CVE 相關資訊及評級等資料。
Vendor / Ecosystem advisories例如 Debian、Red Hat 或套件生態系維護者發佈的公告。可能比通用上游版本資訊更適合特定發行版。

同一筆漏洞可能同時有 CVE ID 與 GHSA ID，並出現在多個資料來源；這不代表是兩個不同漏洞。不同公告可能有不同的版本範圍或評級。Trivy 會依套件類型、來源、適用的辨識及比對規則使用資料，不是只把所有文字拼在一起。

這些資料是 Trivy DB 的上游資訊來源。Runner 一般不需要在每次 vulnerability scan 時重新逐筆抓取 GHSA 或 NVD 才能進行比對。

03 / 誰把這些資料變成 Trivy DB？

Trivy 官方另有一個開源專案 aquasecurity/trivy-db。它不只是成品 DB 的名稱，也是負責建立 DB 的工具及程式庫。官方利用排程的 GitHub Actions 執行 DB 建置。這是官方自己的 pipeline，不是你公司執行 microservice build 的 pipeline。

該流程大致完成四件事：取得來源資料、整理成掃描器能查詢的結構、建立 DB 檔案、將檔案壓縮並發佈。完成的主要檔案如下：

檔案實際用途
trivy.db真正存放漏洞資料的嵌入式資料庫檔案（bbolt，一種可由程式直接開啟的 key-value database）。不需要啟動 MySQL、PostgreSQL 或另一台 DB Server。
metadata.json描述這一份 DB 的格式版本與時間資訊；CLI 會利用它判斷相容性及更新時機。
db.tar.gz用來分發上述兩份檔案的壓縮封裝。下載解壓後才是本機使用的檔案。

注意：trivy.db 不是 scanner 的結果報告，也不是你專案的套件清單。它可以供許多不同 repo 的掃描共同使用。

04 / 為什麼 DB 會放在 Container Registry？

官方建立了 db.tar.gz 之後，還需要一個地方讓全世界的 Trivy CLI 下載這份檔案。這是分發問題，與漏洞資料從哪裡來是兩件事。

你平常使用 Harbor 儲存 Docker Image。對 CLI 來說，Registry 本質上是一種可以透過網路上傳、儲存、辨識和下載封裝內容的服務；它不只是用來儲存之後要啟動成 Container 的檔案。只要儲存的內容符合支援的格式，也能分發其他檔案。

OCI（Open Container Initiative） 是定義容器相關標準的組織。在這裡，你需要知道的是它有一套描述、封裝及分發內容的標準。符合這套格式、可在 Registry 儲存的成品，可以廣義稱為 OCI Artifact。Trivy DB 就是利用這套分發能力，而不是把資料庫做成一個需要啟動的應用程式。

一個封裝通常包含描述內容的 manifest（清單）及實際內容 blob（資料）。對 Trivy DB 而言，內容是壓縮的 DB 檔案；其 media type（告訴讀取方內容是什麼的識別字串）不是一般應用程式 Image 的 filesystem layer 類型。因此不應假設普通 Docker pull/run 就能正確操作 DB。

Trivy 官方將 DB 發佈到 GitHub Container Registry（GHCR）等 Registry，並可透過 Google 的 Registry Mirror 取得。Mirror 是讓使用者從另一個分發位置取得相同上游內容的機制；不是 Google 幫 Trivy 另外建立一套漏洞資料庫，也不是把 GHSA 的查詢轉送給 Google。

你熟悉的概念Trivy DB 的對應
Harbor 裡的應用程式 imageGHCR 等 Registry 裡的 DB 封裝
docker pull 取得 imageTrivy 內建 OCI 下載邏輯取得 DB
image 裡的程式與依賴DB 封裝中的 trivy.db 和 metadata.json
docker run 啟動應用程式不需要；Trivy 直接開啟下載後的 DB 檔案

05 / 現在才把整條資料流串起來

逐步確認：① 誰提供事實？公告維護者。② 誰整理？Trivy DB 官方建置流程。③ 誰提供下載？Registry。④ 誰保存及讀取本機資料？執行中的 CLI。⑤ 誰產生報告？你的 Runner 上的 Trivy Scanner。

圖的 ③ → ④ 是 DB 從遠端流向本機的下載，不是將 repo 送給遠端掃描。圖的 ④ → ⑤ 還需要另一份輸入，就是 checkout 的專案資料。這是本課所使用的 Standalone 模式；部分套件辨識功能可能額外存取遠端服務，這與 DB 下載不同。

06 / DB Repository 的地址怎麼讀？

mirror.gcr.io/aquasec/trivy-db:2
ghcr.io/aquasecurity/trivy-db:2
部分含義
mirror.gcr.io / ghcr.ioRegistry host；CLI 要連線的服務。
aquasec / aquasecurityRegistry namespace（組織或命名空間）。
trivy-db儲存 Vulnerability DB 封裝的 Repository 名稱。
:2Tag；官方以 DB schema 版本命名。

Schema 是資料庫內部的資料結構與讀取約定。例如 scanner 要知道用哪個 key 取得某個套件的漏洞公告。若 DB 結構改變，舊 CLI 可能不懂如何讀取。:2 表示 schema 2 的 DB，不是 Trivy CLI 2.x，也不是 2026 年 11 月某一個固定快照。

同一個 :2 可以在下一次官方 DB 發佈時指向新的內容；如果需要精確識別某一份 OCI 封裝，可記錄它的 digest（依內容計算的雜湊識別碼）。CLI 固定版本、DB schema、DB 內容新鮮度與 OCI digest 是四個不同概念。

官方 CLI 文件的預設順序是 Google mirror → GHCR；只有需要下載時才使用這個清單。特定暫時性錯誤如 429、5xx 可依順序 fallback，不代表所有失敗都會 fallback，也不是同時把兩份 DB 合併。使用 --db-repository 設定其他來源時會覆蓋預設清單；省略 tag 時以支援的 schema 版本補入，而非一律使用 latest。

07 / 第一次真的下載 DB：逐行看 Command

以下是獨立的 Bash 教學實驗，不使用公司 repo。先在核准環境確認 trivy 已安裝。每次使用新的暫存 lab 目錄，不會清除原本的 cache。先確認沒有非預期 TRIVY_* 環境變數；例如 TRIVY_SKIP_DB_UPDATE 會改變行為。範例以官方目前支援的 --config "" 禁止載入工作目錄的設定檔，舊版請先查 help。

trivy --version
trivy fs --help
LAB=$(mktemp -d)
cd "$LAB"
mkdir project
printf 'requests==2.31.0\n' > project/requirements.txt

trivy --version 顯示 CLI 版本，可能同時顯示預設 cache 中的 DB 資訊；trivy fs --help 查看 fs 支援的參數。這兩條不是下載命令。後三行建立乾淨的實驗位置與可掃描的輸入。

trivy --config "" --cache-dir "$LAB/cache" --debug fs --scanners vuln --download-db-only
部分這次做什麼？
--config ""不讀取預設 trivy.yaml；不會清除 TRIVY_* 環境變數。
--cache-dir "$LAB/cache"指定本機存放資料的根目錄；不是遠端 Registry，也不是 scan target。
--debug顯示較詳細的 log，例如 DB 更新判斷與 metadata。
fs選擇 filesystem command；在這個特殊模式下不需要掃描路徑。
--scanners vuln選擇 vulnerability scanner，確保本次與漏洞 DB 有關。
--download-db-only先走 DB 準備／更新判斷，完成後結束，不分析專案、不產生漏洞報告。

第一次使用這個 cache 時，兩個 DB 檔案還不存在，所以預期需要下載。下列是依實際 log 類型縮短的示意，不是本次測得的輸出：

INFO  [vulndb] Need to update DB
INFO  [vulndb] Downloading vulnerability DB...
INFO  [vulndb] Downloading artifact... repo="mirror.gcr.io/aquasec/trivy-db:2"
INFO  [vulndb] Artifact successfully downloaded

第一行是判斷需要更新；第二行表示準備下載；第三行是實際選擇的 Registry；第四行才表示封裝下載成功。仍須確認 CLI 正常結束、檔案存在及 metadata 正常。因為使用 download-only，所以沒有漏洞表格是合理的。不是掃描失敗，也不是掃到零個漏洞。

ls -lh "$LAB/cache/db"
cat "$LAB/cache/db/metadata.json"
trivy --config "" --cache-dir "$LAB/cache" --version

ls 檢查檔案及大小；cat 閱讀 JSON metadata；最後一條讓 CLI 顯示自己的版本與指定 cache 的 DB 資訊。應看到 trivy.db 與 metadata.json。不要把 --cache-dir 指到 db 子目錄本身，否則 Trivy 仍會往其下尋找 db/。

trivy --config "" --cache-dir "$LAB/cache" fs --scanners vuln --skip-db-update "$LAB/project"

這次不再用 download-only，而是提供 project 作為 target，執行漏洞掃描。--skip-db-update 表示使用這份已準備且相容的 vulnerability DB，不進行其更新。預期可辨識 requests 2.31.0，並視實際 DB 及過濾設定找到該筆漏洞。下一堂會解釋省略此 flag 時如何決定更新。

08 / 為什麼還有 Java DB 與 Checks Bundle？

不是所有檢查都需要同樣的資料。先理解一個 JAR（Java 封裝檔）：如果只取得 JAR 本身，未必能從它的檔名或內容得知正確的套件座標與版本。Trivy Java DB 提供 Java artifact 的索引，輔助辨識這些資訊。辨識出 Java 套件後，漏洞仍由 vulnerability DB 比對。

Misconfiguration Scan 的任務不同，例如檢查設定是否符合某項安全規則。這種判斷需要檢查邏輯，而不是套件版本受影響範圍。Checks Bundle 就是這類檢查規則的集合，Trivy 也有內建規則作為特定情況的 fallback。

資料名稱負責哪一步？
trivy-db辨識套件之後，比對已知漏洞。包含受支援 Java 套件的漏洞資料。
trivy-java-db輔助辨識 JAR 等 Java 封裝中的套件身分，不是 Java CVE 專用 DB。
trivy-checksMisconfiguration 的檢查規則。不是漏洞公告資料庫。

因此只掃 .NET、npm 或 Python 的 dependency vulnerability，不需要因此先下載所有三種資料。是否用到 Java index 取決於實際掃描內容，不是由 repo 名稱決定。

理解驗收

某 CI log 從 mirror.gcr.io 下載 trivy-db:2，但命令是 trivy fs。請解釋從官方漏洞公告到本機報告的完整流程，是否做了 Image Scan？

先自行推論，再看解析

GHSA/NVD 等公告被官方整理為 DB，壓縮成 OCI 封裝發佈，Runner 的 CLI 透過 mirror 下載解壓，讀取本機專案套件並用本機 DB 比對。沒有做 Image Scan，也沒有啟動 DB Container。

只安裝一個 Trivy CLI binary，沒有本機 DB 檔案，又不允許網路。可以直接做已知漏洞掃描嗎？

先自行推論，再看解析

不行。需先提供相容的 vulnerability DB 和 metadata。沒有查詢資料來源不能得出安全結論。

隔天仍下載 trivy-db:2，是否代表 DB 完全相同？

先自行推論，再看解析

不一定。:2 是 schema tag，可指向新內容；比較 metadata 與可取得的 artifact digest。

本堂回顧

  • 已知漏洞公告提供受影響套件、版本與漏洞資訊；CVE/GHSA 是識別方式，不等於 DB 下載位置。
  • Trivy DB 由官方建置流程建立，以 bbolt 檔案及 metadata 分發，不需 DB Server。
  • OCI Registry 能分發 DB 壓縮封裝，與 Image Scan 無關。
  • DB Repository 決定遠端來源，cache-dir 決定本機位置。
  • download-db-only 不執行掃描；skip-db-update 使用已存在的相容 DB。
  • Java DB 幫助辨識；漏洞 DB 比對；Checks Bundle 做設定規則檢查。

主要來源：官方 DB · DB builder · 官方 Self-hosting · Filesystem CLI · DB 初始化原始碼 · Requests 公告。命令與預期輸出依官方文件及指定原始碼修訂設計，並非本次 Runner 實測；以實際核准版本為準。

若實際輸出不同，可將 CLI 版本、去識別的 log 與 metadata 帶回對話，從觀察推導原因。
