PHASE 02 / PREREQUISITE LESSON · CLI 基礎模型

先理解 Trivy CLI，
再開始掃描。

第一章知道 Trivy 會辨識套件、比對已知漏洞。但在下第一條指令之前，還有四個問題：Trivy 在哪裡執行？掃誰？怎麼拿到資料？可以做哪些掃描？ 這堂課只建立這個操作模型，不要求先安裝 CLI。

本堂目標
  • 分得清「Trivy 執行位置」、「Target 掃描目標」、「Scanner 檢查項目」。
  • 解釋 Trivy 不執行應用程式，也能找出已知套件漏洞的原因。
  • 能針對 GitHub Checkout、Docker Image、Harbor Image 選擇適合的掃描入口。

前置：Lesson 02 — Filesystem 與 Image 的差異。本頁依 官方 Trivy 文件 說明，不代表已在公司 Runner 實測。

01 / CLI 先是「執行程式」，不是一個 Server

CLI 是 Command-Line Interface。你安裝或取得 Trivy 執行檔後，在 Terminal、PowerShell、CI Runner 中呼叫它。它接收參數、取得要掃描的目標、執行檢查、輸出報告並結束。

不需要先建立一台 Trivy Server。Trivy 有 Standalone 與 Client/Server 等運作模式；Phase 02 先用最容易理解的 Standalone。它也可以藉由 GitHub Action、容器化 CLI 或安裝在 Runner 的執行檔來觸發，這些是「怎樣啟動 Scanner」的不同包裝，和「掃誰」是兩個問題。

Figure 01 · 誰呼叫誰？每一條箭頭有明確意義

GitHub Actions／Terminal執行 Trivy CLI，傳入參數
↓ 呼叫程式並指定 Target／Scanner
Trivy CLI（在 Runner 上）依目標類型取得資料：本機檔案、Docker Engine 或 Registry
↓ 解析內容，辨識軟體、版本和適用平台
套件辨識Lockfile／已安裝套件 metadata／OS 套件資料
↓ 用已辨識的套件與版本比對漏洞資料
漏洞資料庫（DB）提供已知 CVE、影響版本、修復資訊；Trivy 會依需求下載／更新並使用快取
↓ 產生匹配結果與執行狀態
結果Terminal 表格／JSON／SARIF／Exit Code

示意採「Vulnerability Scanner」範圍；其他 Scanner 會有不同的檢查邏輯。漏洞 DB 是比對資料來源，不是拿程式碼去遠端網站逐行執行。

Trivy 安裝檔提供掃描引擎，但漏洞資料是另外取得並更新的。**第一次使用可能需要下載 Vulnerability DB**；如果公司環境有 Proxy、CA 或 Registry 存取限制，就可能在這一步失敗。你能在 Runner 上正常呼叫 CLI，不代表 DB 就一定能下載成功。

官方：Standalone Mode、Trivy Databases。

02 / Target 與 Scanner 不要混在一起

想像你要做健康檢查，必須先決定「對象是誰」，再決定「要檢查什麼」。Trivy 一樣要作兩個決定。

問題你的選擇實際含義
掃誰？Targetfs、repo、image、sbom 等Scanner 到哪裡取得輸入資料
查什麼？Scannervuln、secret、misconfig、license對取得的內容執行哪種類型的檢查
怎麼呈現？Outputtable、json、sarif結果要顯示在畫面還是產生報告檔案
容易搞混的地方

trivy fs 的 fs 不等於漏洞掃描方法；它只是告訴 Trivy「讀本機檔案」。--scanners vuln 才是在要求「只檢查已知漏洞」。同一份目標也可以改做 Secret、Misconfiguration 等檢查。

03 / 掃描目標到底從哪裡來？

模式讀取位置與內容適用例子
fs
Filesystem		本機指定檔案或目錄；例如 Lockfile、套件清單GitHub Actions checkout 完的 workspace
repo
Repository		本機或遠端 Git repository；聚焦 Repo 內的可辨識清單與設定等掃描特定 Git branch、commit、tag
image
Container Image		本機 Docker／containerd／Podman，或遠端 Registry 的 ImageDocker build 後的 Image、Harbor Image
sbom
SBOM		已存在的軟體組成清單（需受支援格式）另一套流程先產 SBOM，Trivy 再檢查
其他目標rootfs、Kubernetes、VM Image 等後續擴充，不列入本章最小 PoC

特別注意：trivy repo 與 trivy image 的「遠端」含義不同。前者是從 Git Repository 取得專案內容；後者是從 Container Registry 取得已建置的 Image。指定 GitHub Repo URL 不代表它會替你 Docker build。

對私有 Git Repo 或私有 Harbor Image，還需要適當的認證與權限。你要掃遠端 Image，不代表 Runner 必須先自己執行 docker pull；Trivy 本身有 Registry 讀取能力。

官方：Filesystem、Code Repository、Container Image。

04 / 用一個選擇器建立使用方式的直覺

以下情境只是在教你「要選哪個掃描入口」；不會真的連到 GitHub、Docker 或 Harbor，也不會發起掃描。

適合從 trivy fs 開始。

Trivy 在目前執行位置讀取已 Checkout 的檔案。這不需要再次連到 GitHub 才能讀取本機 workspace。

trivy fs --scanners vuln .

此互動只展示建議入口及原因，不宣稱任何掃描已成功。

05 / 那它到底「怎麼掃到漏洞」？

以 Kubernetes Service 的 Image 為例：Image 裡可能同時存在 Linux 套件（例如由 apk、dpkg、rpm 安裝）與應用程式套件（例如 npm、pip、NuGet）。Trivy 先解析 Image 中可辨識的封裝內容、套件管理資訊及 metadata，取得這些套件和版本，再依套件生態系與 OS 版本選擇適用的漏洞資料來源比對。

所以 Trivy 一般不是「試著入侵 Image」；它也不需要為了辨識已安裝套件而先啟動 Container。對於 OS 由發行版維護的套件，會考慮相應發行版的安全公告，而不只是看到某個上游版本號就直接定案。

範例：為什麼同一個 Repo 會有兩份不同的掃描結果？

Repo 只有 requirements.txt，宣告 requests 的版本；Docker build 階段真正安裝 requests 及間接依賴。Repo 掃描能取得宣告的資訊；Image 掃描可能看見已安裝的間接依賴以及 Linux OS 套件。反過來，如果 multi-stage build 沒把建置用工具放進最終 Image，Image Scan 也可能看不到那些工具。

所以結論不是 Image 一定比較完整，而是觀察目標不同，能證明的範圍也不同。

官方：Vulnerability Scanning。

06 / 這四個指令，現在才有意義

先看結構，不必立刻執行。一般形式可以記成：trivy [目標模式] [選項] [目標位置]。

指令示例你在告訴 Trivy 什麼
trivy fs --scanners vuln .讀目前資料夾，只檢查已知漏洞
trivy repo --scanners vuln https://github.com/aquasecurity/trivy-ci-test從這個公開 Git Repo 取得內容，再執行漏洞掃描
trivy image --scanners vuln demo-app:1.0從可用的 Image 來源尋找這個名稱並掃描
trivy image --image-src remote --scanners vuln registry.example.com/team/app:1.0只嘗試遠端 Registry，不使用本機 Docker Image；網址只是格式示例

不要把 .、demo-app:1.0 和 Registry URL 當成一種通用的目標：前者是資料夾，後兩者是 Image 的識別名稱。

放進公司 CI 前多看一層

如果在 ARC Shell Runner 執行 trivy image，Trivy 是透過 Runner 可用的 Docker API／Registry 憑證取得 Image。這不要求 Trivy 安裝在每個 Pod 裡。未來 Harbor 掃描還要確認 Registry 認證、企業 CA、權限、可識別的 Image digest 與 DB 更新方式。

08 / 這堂課應該留下的觀念

  • Trivy CLI 是可以在本機或 Runner 執行的工具；基本 PoC 不需要先建立掃描 Server。
  • 掃描目標（fs／repo／image）決定從哪裡讀資料，Scanner（vuln／secret 等）決定檢查內容。
  • Trivy 先辨識元件與版本，再用漏洞資料庫做比對，並輸出報告與執行狀態。
  • 本機 Image 和遠端 Registry Image 都能掃，但取得路徑和認證不同。
  • 讀不到套件不代表套件安全；CLI 退出成功也不代表漏洞數為零。
離開本課的自我檢查：如果你在 ARC Shell Runner 上要掃「已 checkout 的 .NET 專案」與「剛推送 Harbor 的同一個服務」，你會選哪兩個 Target？它們各從哪裡取得資料？
