PHASE 02 / LESSON 04 · 從 CLI 報告建立可靠的判斷

Trivy 回傳 0，
到底代表什麼？

你以後把 Trivy 接到 GitHub Actions 時，Workflow 不只需要一份人看得懂的報告，還必須知道 Scanner 有沒有正常執行。這堂課先把訊號拆清楚，不開始訂正式阻擋門檻。

本堂目標

能判讀 JSON 與 SARIF 的用途、區分套件辨識和漏洞命中，並用退出碼及報告判斷本次掃描是否可信。

前置：Lesson 03 的四個樣本；可直接閱讀下方示意報告，不必先在手機執行指令。

01 / 先讀報告，再讀數字

假設有一份報告。以下為刻意簡化的教學 JSON（不是實測輸出）：

{
  "Results": [{
    "Target": "requirements.txt",
    "Class": "lang-pkgs",
    "Type": "pip",
    "Packages": [{
      "Name": "requests",
      "Version": "2.31.0"
    }],
    "Vulnerabilities": [{
      "VulnerabilityID": "CVE-2024-35195",
      "PkgName": "requests",
      "InstalledVersion": "2.31.0",
      "FixedVersion": "2.32.0",
      "Severity": "MEDIUM"
    }]
  }]
}

Results 按掃描目標或類型分組。Packages 告訴你辨識到了哪些套件；Vulnerabilities 告訴你哪些套件命中了漏洞。InstalledVersion 是受檢版本，FixedVersion 是資料庫提供的修復版本資訊（可能有多個或空白），Severity 是漏洞嚴重程度，不是公司部署政策。上例的嚴重程度僅作示意，以實際資料庫來源為準。

Figure 04 · 三種獨立訊號

  1. 執行訊號：CLI／DB 是否正常完成 → 終止狀態與 log。
  2. 覆蓋訊號：應被辨識的套件是否真的存在 → Packages 清單。
  3. 漏洞訊號：哪些套件版本命中已知漏洞 → Vulnerabilities 清單。

前一項正常，並不自動保證後一項完整。CI 最終要同時使用三種訊號。

02 / JSON、Table 和 SARIF 差在哪？

格式主要用途適合的場景
Table（預設）方便人閱讀漏洞本地 CLI 快速確認
JSON完整結構化結果，可列出套件清單CI 保存證據與自訂判定
SARIF標準化安全發現報告支援 SARIF 的工具或 GitHub Code scanning

JSON 是本次 PoC 的主要驗收依據；SARIF 不等同完整套件清單。私有／內部 Repo 若要在 GitHub Code scanning 畫面顯示，後續還須確認授權和啟用狀態。

trivy fs --scanners vuln --format table old
trivy convert --format sarif \
  --output reports/old.sarif reports/old.json

第二個命令將既有 JSON 轉成 SARIF，不需要重新掃描。請以使用版本的 trivy convert --help 確認支援格式。

03 / Exit code 不是漏洞數量

Exit code 是程式結束時給作業系統的數字。GitHub Actions 的 shell step 通常把非零狀態視為失敗。Trivy 預設即使發現漏洞，也可以正常結束並回傳 0；你可以用 --exit-code 指定有符合條件的發現時要回傳什麼。

用 Lesson 03 的 old 樣本做實驗（Bash）：

if trivy fs --scanners vuln --exit-code 0 old; then
  echo "exit=0"
else
  echo "exit=$?"
fi

if trivy fs --scanners vuln --exit-code 42 old; then
  echo "exit=0"
else
  echo "exit=$?"
fi

如果兩次都掃描正常且有漏洞，預期第一次為 0、第二次為 42。42 只是這次測試指定的值，不是 Trivy 固定的漏洞狀態，也不是正式公司的政策。

再測 severity 篩選：例如 --severity HIGH,CRITICAL 只看符合篩選的漏洞；請以實際報告確認結果，不要把篩選後的 0 筆當成所有嚴重度都沒有漏洞。

04 / 故意讓掃描失敗

if trivy fs --scanners vuln --exit-code 0 \
  --format json -o reports/missing.json \
  ./does-not-exist; then
  echo "exit=0"
else
  echo "exit=$?"
fi

此路徑應不存在，預期掃描失敗並回傳非零；先核對 log，不假定固定錯誤碼。真正 CI 還可能遇到 DB 下載失敗、CA 憑證、權限或 Docker 存取問題。沒有正常取得可驗證報告時，不可把缺少的結果當成 0 個漏洞。

05 / 把四種結果分清楚

觀察結果你能做的判斷
執行成功、應有套件已核對、命中漏洞掃描完成，有漏洞需評估
執行成功、應有套件已核對、沒有命中本次資料與篩選範圍未發現漏洞
執行成功，但應有套件未辨識資料覆蓋不足，不能宣稱安全
執行失敗或沒有有效報告掃描失敗，不能做安全判定

這是未來共用 CI 的判定模型。建議先用 report-only 的方式執行 Scanner，保留完整 JSON 及執行狀態；之後由獨立的 Policy 判斷是否阻擋部署。這樣可以避免 scanner 本身的錯誤和漏洞政策混在一起。

06 / 既有最小 PoC 結果如何解讀？

測試情境先前樣本辨識
.NET 9 無 Lockfile0/9
.NET 9 CI Restore 產生 Lockfile9/9
.NET Framework 4.8 packages.config2/2
npm Lockfile50/50
pnpm Lockfile52/52

這是既有 PoC 所記錄的特定樣本套件辨識結果，非本次重跑，也不是漏洞偵測率。例如 0/9 應視為該樣本的覆蓋不足，而不是九個套件都安全。Phase 03 要驗證這些補強方式能否用在真正公司建置上。

08 / 本章回顧

  • JSON 保存套件和漏洞資料；Table 方便人讀；SARIF 用於工具交換安全發現。
  • 預設 exit 0 只表示正常結束，不代表沒有漏洞。
  • severity 與其他篩選條件決定你看到的發現範圍。
  • 掃描失敗、覆蓋不足、未命中、有漏洞必須區分。
  • 正式 CI 的 gate 尚未啟用，先建立可以被驗證的掃描契約。
離開 Phase 02 前：

不看答案，說明為什麼「退出碼 0、漏洞 0、套件 0」不能算安全，並解釋 old/fixed 對照實驗要怎麼證明某個 CVE 消失。若做過實驗，請貼去識別後的 JSON 摘要和版本資訊供驗收。
