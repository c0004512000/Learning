PHASE 01 / LESSON 02 · 讀懂掃描目標與資訊流

Trivy 到底掃了什麼？

上一堂建立了「套件與版本要被辨識，才能與漏洞資料比對」。這堂要解決下一個問題：我們應該交給 Trivy 一份 Repo，還是一個建置完成的 Image？

本堂目標
  • 能說明 Filesystem（fs）與 Container Image（image）的資料來源差異。
  • 能指出為什麼 Lockfile、pip freeze 和 Image 內容影響偵測結果。
  • 在 Kubernetes 與 IIS 的情境下，選出需要驗證的掃描目標。

先備：Lesson 01｜為什麼需要 Trivy。

01 / Scanner 不是憑空知道套件

看起來是一份程式碼，但有三種不同資料：

  • Dependency declaration：開發者宣告要用什麼，例如 requests>=2.28，不一定是實際安裝版本。
  • Resolved dependency list：安裝、Restore 或 Lockfile 明確給出的套件及版本；可能包含間接依賴。
  • Deployed artifact：真的被部署出去的產物，例如 Docker Image 或 IIS publish output。

如果只檢查宣告，卻沒有看到最終實際使用的版本，Scanner 的結果就可能比部署內容少。所以掃描是否完整，首先取決於「餵了什麼」，而不只是下了哪條指令。

02 / 兩種最重要的掃描入口

比較Filesystem ScanImage Scan
給 Scanner 什麼工作目錄／專案檔案已存在的 Container Image

能看到什麼可辨識的 Lockfile、套件清單等Image 中的作業系統及應用套件資訊
常見盲點實際版本／間接依賴沒寫在檔案裡未封裝進 Image 的檔案／外部依賴不會憑空出現

兩者不是單純「Image 比 fs 進階」。它們回答的目標不同：Repo 內的依賴資訊 vs. 已封裝的 Image。你的企業導入最後可能同時需要其中兩種，但必須拿出驗證理由。

Figure 02 · 目標不同，看到的依賴也不同

  1. GitHub Checkout 包含 package.json / requirements.txt / .csproj 等
    ↓ Trivy fs 讀取可辨識的檔案
    取得檔案能證明的套件資訊
  2. Docker build 產出的 Image 可能包含 OS packages + 安裝的應用套件
    ↓ Trivy image 讀取實際封裝的內容
    取得 Image 能辨識的套件資訊
  3. 共同的後半段
    套件名稱／版本 → 比對漏洞資料 → 報告結果

「讀取」和「比對」是箭頭的動作；不是在說 fs 會先產生 image，也不是任何 Image 都一定能完整列出全部依賴。

03 / 用真實會遇到的套件格式理解

Python：為什麼只看 requirements 會少？

例如 requirements.txt 只寫 requests==2.28.2。Requests 安裝時還會需要其他套件，但檔案不一定列出它們。Trivy 無法只靠這一行完整還原當時環境實際裝了什麼。

如果 CI 已在正確的 Python 環境安裝完成，python -m pip freeze 可以取得當下環境的套件與版本，作為額外掃描輸入。但它不是可重現建置的 Lockfile，且若跑在錯誤的 venv，內容同樣不可靠。

官方 Python 套件偵測說明

.NET：格式差異不是小事

packages.config 可以提供套件名稱和版本；packages.lock.json 能呈現 NuGet 已解析的相依資訊；*.deps.json 則和執行時依賴有關。它們包含的資訊範圍不同，不能假設每份 .csproj 都能直接讓 Trivy 看見完整版本清單。

官方 .NET 支援格式

你先前的最小 CLI PoC 也觀察到：.NET 9 無 Lockfile 時樣本只辨識 0/9，補上後為 9/9；Python 只用 requirements 是 1/5，使用正確環境的 freeze 後為 5/5。這些是該樣本的套件辨識比例，不是漏洞偵測率，也不是 Trivy 對所有專案的固定限制。

04 / 一次掃描實際如何進行？

以下是 CLI 的概念示例（不是本次在公司 Runner 執行的證據）。指定 --scanners vuln 是為了限定這次學習的漏洞掃描範圍：

# 掃描本地專案資料夾
trivy fs --scanners vuln .

# 掃描已建好的 Image
trivy image --scanners vuln my-service:example-tag
  1. Trivy 接到掃描目標。
  2. 它嘗試辨識目標內的套件、版本與所屬環境資訊。
  3. 它利用漏洞資料進行比對，產生可讀的風險結果。
  4. CI 可保存報告，再依你們訂定的 Policy決定是否阻擋後續部署。

第一次執行通常還需準備漏洞資料庫；DB 下載失敗、套件辨識不足和「確實沒有命中漏洞」要分開看待。CLI 錯誤／退出碼與 JSON 報告會在 Phase 02 實際驗證。

05 / 套到你的兩種部署管線

Kubernetes / Harbor

Docker build 後掃 Image，可以評估進入 Image 的 OS/Application packages；若想在 push 前擋，需要先確認目前 Workflow 的 build/push 是否可拆開。之後還要明確比對實際部署的 tag 或 digest。

Windows IIS

因為通常沒有 Container Image，應該檢查 Restore/Install 完成後可取得的依賴清單及 publish output。更重要的是先確認 workflow 的 MSBuild 或 msdeploy 動作是否已經包含部署，不要到部署之後才設 Scan Gate。

這是根據現有 Workflow 內容辨識的待實測整合點，不代表已在生產 Runner 上執行掃描。查看固定版本 Workflow 來源。

07 / 本章回顧

  • Trivy 不是執行功能測試；它要從輸入辨識套件並查已知漏洞。
  • Filesystem Scan 與 Image Scan 的輸入、觀測範圍不同。
  • Lockfile／freeze 是為了讓精確版本和間接依賴更可見；必須確認符合真實環境。
  • 沒有發現漏洞 ≠ 所有套件都已辨識；沒有找到套件 ≠ 安全。
  • 導入 CI 之前要知道哪個建置或部署步驟會真的改變環境。
