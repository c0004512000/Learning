學習路線

PHASE 01

先懂 Trivy

理解它如何從套件與版本比對漏洞資料庫；分清 dependency、image 與程式碼品質掃描。

實驗／驗收：畫出：掃描輸入 → 套件辨識 → 漏洞資料庫 → 結果。說明掃不到不代表安全。

PHASE 02

最小 CLI PoC

對同一個專案做不同輸入的掃描；讀懂 JSON、SARIF、exit code、可修補版本。

實驗／驗收：記錄輸入、辨識套件數、漏洞數、退出碼與失敗原因。

PHASE 03

對齊實際建置

比較 .NET packages.config/lockfile、npm/pnpm lockfile、Python requirements/pip freeze 與真正部署產物。

實驗／驗收：證明掃描的依賴清單和 CI 最終建置一致；pip freeze 只反映當下環境。

PHASE 04

串接現有 CI

在 KubernetesDeployment 的 Docker build/push/deploy、WindowsDeployment 的 IIS publish/msdeploy 前安排掃描。

實驗／驗收：先 report-only；證明掃描報告產出且不會在部署後才擋。

PHASE 05

抽成共用能力

以 CommonActionDeployment 設計可重用的掃描 Action/Workflow，統一輸入、輸出、版本、快取與錯誤處理。

實驗／驗收：Linux/Windows Runner 都能執行；DB 下載失敗與掃描無結果要分開。

PHASE 06

治理與阻擋策略

定義漏洞嚴重度、修補可行性、既有問題基準、例外到期日與責任歸屬。

實驗／驗收：用真實 workflow 測試：該阻擋時，GitOps tag 更新與 IIS 部署都未發生。

PHASE 07

分批導入與維運

依語言、部署型態分批；安排漏洞 DB 更新、工具升級、重新掃描與可觀測性。

實驗／驗收：有覆蓋率、誤報處理、例外審查與升級回復機制。

已知的最小 PoC 現象

以下是先前樣本中「套件辨識」的結果，不是漏洞覆蓋率，更不是公司 Runner 的驗證。

  • .NET 9：無 lockfile 0/9；CI restore 產生 lockfile 後 9/9。
  • .NET Framework 4.8：packages.config 2/2。
  • Node.js：npm lockfile 50/50；pnpm lockfile 52/52。
  • Python：只用 requirements 1/5；在正確環境 pip freeze 後 5/5。

注意：套件被辨識到，不代表漏洞一定能被判定；掃描退出碼 0 也不必然代表安全。

與現有 Repo 的整合點

KubernetesDeployment

Docker build 與 push、GitOps deploy 之間要釐清掃描位置；若要在 push 前阻擋，必須拆分既有 build/push 步驟。

查看 build workflow

WindowsDeployment

IIS backend 的 publish/MSBuild 部分分支可能直接部署；frontend 的 npm install/build/msdeploy 也要拆開，避免掃描太晚。

查看 IIS workflows

CommonActionDeployment

集中管理掃描能力，並區分「掃描結果」與「是否阻擋」兩種責任，避免各專案各寫一套。
