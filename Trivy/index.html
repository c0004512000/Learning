這兩堂先建立什麼？

  1. 為什麼 E2E、Secret Scanning 都通過，仍無法回答套件版本的安全風險。
  2. Trivy 取得「套件名稱 + 版本」後，如何與已知漏洞資料比對。
  3. 為什麼同一個 Repo 的 Filesystem Scan 和建好的 Image Scan 可能看到不同依賴。
  4. 為什麼 pip freeze 與 Lockfile 的資訊範圍會影響你信任掃描結果的程度。

完整導入路線

Phase 01 · 先知道 Trivy 為何存在，資料如何流動

建立掃描的必要性、輸入與輸出的因果關係，再分辨 Filesystem 和 Image。

Phase 02 · 最小 CLI PoC 與結果解讀

只驗證 CLI；記錄什麼可行、不可行、如何改善，區分套件辨識和漏洞命中。

Phase 03 · 讓掃描資料與實際部署一致

檢查套件和建置格式：.NET、Node.js、Python，以及 Docker / IIS publish 的產物差別。

Phase 04 · 接到現有 GitHub Actions

以 Linux ARC 與 Windows IIS 的實際 workflow 決定掃描時機；先產報告，不阻擋。

Phase 05 · 抽成可以維護的共用 Workflow

統一命令、輸入、輸出與故障策略，避免每個服務使用不同的掃描邏輯。

Phase 06 · 企業治理與部署前阻擋

從報告到政策，界定新舊漏洞、修復、例外、到期與 CI 阻擋。

Phase 07 · 漸進導入與長期維運

掌握掃描覆蓋率、誤報、例外到期、更新及新 CVE 出現時的重新掃描。
