LESSON 0001 · 約 10–15 分鐘

一個容器停止了，為什麼需要 Kubernetes？

假設你的一個網站跑在一台機器的容器裡。容器停止、機器故障或流量上升時，單靠「啟動容器」還不能保證服務持續可用。你需要一個系統記住想要的狀態，持續觀察實際狀態，並在偏離時採取動作。

1. 先認識兩種狀態

期望狀態

例如：網站維持 2 份執行中的副本。

實際狀態

例如：現在只剩 1 份在執行。

你向 Kubernetes API 宣告想要的狀態；控制元件持續比較差距，嘗試把實際狀態帶回目標。這個反覆調整的過程稱為 reconciliation（調和）。API 接受設定不代表容器已成功執行。

官方：Kubernetes 物件與期望狀態

2. 哪些部分負責這件事？

Control plane（控制平面）接受與協調叢集的期望狀態；Node（節點）是實際執行工作負載的機器；Pod 是 Kubernetes 排程與管理容器的基本單位。一個 Pod 可以有一個或多個緊密協作的容器；這裡先看一個容器的情況。

看這條因果鏈：你用 kubectl 告訴 API「要兩份」→ 控制元件發現只有一份 → 排程選擇 Node → 該 Node 的 kubelet 協助啟動 Pod。若條件不允許，實際狀態可能暫時達不到期望值，必須看狀態與事件。

官方：Kubernetes Components · 官方：Pods

4. 把觀念連到觀察

在你授權的練習叢集，可用唯讀指令 kubectl get nodes、kubectl get pods -A 先分辨機器與 Pod。沒有叢集時，在手機上寫出兩個指令各回答什麼問題即可。此處沒有要求建立或破壞資源。

小任務：一個 Deployment 要維持 2 份應用，現在只有 1 份。用自己的話說：誰定義目標？誰執行容器？你要先查什麼？

今天記住

  • Kubernetes 管理期望與實際狀態的差距；設定成功不等於工作負載健康。
  • 控制平面負責協調；Node 承載 Pod；Pod 裡執行容器。
  • 遇到差距，先找實際狀態與事件，再決定操作。
