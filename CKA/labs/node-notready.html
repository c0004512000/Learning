一個 Node 變成 NotReady，先查什麼？

你值班時看到某台節點不再 Ready。直接重啟 kubelet 可能讓症狀暫時消失，卻沒有找到原因。先確認 Kubernetes 對「不就緒」提供了什麼證據。

1. 一個具體畫面

$ kubectl get nodes
NAME       STATUS     ROLES           AGE
worker-a   Ready      <none>          12d
worker-b   NotReady   <none>          12d

Node 是承載 Pod 的機器；kubelet 是每台 Node 上回報狀態、管理 Pod 的程序。這個輸出只說 worker-b 不就緒，還不能判斷是磁碟、網路、kubelet，還是其他原因。

kubectl describe node worker-b 會顯示 Conditions（條件）與 Events（事件）。兩者分別是目前狀態與最近發生過的事，要連同時間一起看。

Conditions:
Type             Status   Reason
MemoryPressure   False    KubeletHasSufficientMemory
DiskPressure     True     KubeletHasDiskPressure
Ready            False    KubeletNotReady
Events:
Warning  NodeHasDiskPressure  Node worker-b has disk pressure

這組證據優先指向節點磁碟壓力；但仍須在節點上查看磁碟使用與 kubelet 訊息，不能憑一個 Reason 直接刪資料。

3. CKA 風格任務

練習情境：worker-b 顯示 NotReady。找出最有力的故障線索，提出下一個檢查指令；不要在沒有證據時修改節點。

kubectl get nodes -o wide
kubectl describe node worker-b

你要回報：預期狀態 → 實際偏差 → 條件與事件 → 下一個檢查位置 → 修復後如何驗證。

如果有可拋棄的練習叢集，實際執行上面兩個唯讀指令，改用環境中真正的節點名稱。若全是 Ready，就只熟悉輸出欄位；不要在工作叢集故意製造故障。手機上先完成判讀並寫出會查的命令。

作答後看一個可行的驗收路徑

這個例子的 DiskPressure=True，下一步應先檢查 worker-b 的磁碟容量與 kubelet 日誌，而不是從控制平面盲目刪 Pod。例如在節點上執行 df -h、journalctl -u kubelet -n 100 --no-pager；確認原因後才修復，再看 kubectl describe node worker-b 的條件、事件與 Pod 狀態。若是 Ready=Unknown，則優先確認節點心跳與控制平面連通性。

4. 換一種線索

若 Ready 是 Unknown，而不是上例的 False，你還會直接假設磁碟壓力嗎？請用自己的話寫出先查什麼，以及為何。

記住三件事

  • NotReady 是症狀；Conditions、Events 與時間線是下一步證據。
  • Ready=False 與 Unknown 有不同訊號，不可一律當成磁碟問題。
  • 修復後要再次確認 Node 與受影響 Pod，不能只看到命令成功。
